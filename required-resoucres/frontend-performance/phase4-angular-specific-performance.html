1. Change Detection — Complete Deep Dive

📺 YouTube Tutorials
  • Angular Change Detection Explained — Decoded Frontend
  • Change Detection Deep Dive — Angular (Official)

What is Change Detection?

Change Detection (CD) is Angular's mechanism to synchronize the component's data model with the DOM. When data changes, Angular must figure out WHAT changed and update the DOM accordingly.

How Default Change Detection Works

Component Tree:
       AppComponent
       /     |     \
    Nav    Dashboard  Footer
          /    |    \
       Card  Chart  Table

Default Strategy (CheckAlways):
- Angular checks EVERY component from root to leaves
- On EVERY event (click, HTTP response, timer, Promise resolve)
- Checks EVERY binding: {{ expression }}, [property], (event)
- Compares old value vs new value for each binding
- If different → update DOM

For a tree with 100 components, each with 10 bindings:
= 1000 dirty checks per change detection cycle!

What Triggers Change Detection

TriggerExampleCD Runs?
DOM Eventsclick, input, keyup, scroll, mousemoveYes (full tree)
HTTP responsesHttpClient.get().subscribe()Yes (full tree)
setTimeout/setIntervalsetTimeout(() => {}, 1000)Yes (full tree)
Promise resolutionfetch().then()Yes (full tree)
WebSocket messagessocket.onmessageYes (full tree)
requestAnimationFramerAF callbackYes (if patched by Zone.js)
Manual markForCheck()this.cdr.markForCheck()Marks path to root
Async pipe{{ data$ | async }}Calls markForCheck()

Change Detection Process (Step by Step)

// For each component (top-down):
1. Update child component @Input bindings
2. Call ngOnChanges() (if inputs changed)
3. Call ngOnInit() (first time only)
4. Call ngDoCheck()
5. Call ngAfterContentInit() (first time only)
6. Call ngAfterContentChecked()
7. Update DOM bindings (interpolation, property bindings)
8. Run change detection on child components (recursive)
9. Call ngAfterViewInit() (first time only)
10. Call ngAfterViewChecked()

// The "checking" part:
// Angular evaluates each template expression and compares with previous value
// If different → update DOM node
// This comparison is FAST (===) but multiplied by thousands of bindings = expensive
Performance Killer: Functions/getters in templates get called on EVERY change detection cycle! 
// BAD: Called 10+ times per second on any interaction
<div>{{ getFullName() }}</div>
<div *ngIf="isAdmin()">Admin Panel</div>
<div [class.active]="calculateActive()"></div>

// GOOD: Pre-computed values or pipes
fullName = `${this.firstName} ${this.lastName}`;
isAdmin = this.user.role === 'admin';
// Or use pure pipes for transformation

2. OnPush Strategy & Immutability

📺 YouTube Tutorials
  • OnPush Change Detection — Decoded Frontend
  • OnPush Strategy Deep Dive — Angular University

How OnPush Changes the Game

@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  // ...
})
export class DashboardComponent { }

// OnPush tells Angular: "Only check this component when:"
// 1. An @Input reference changes (strict === comparison)
// 2. An event fires FROM this component or its children
// 3. async pipe receives a new value
// 4. markForCheck() or detectChanges() is called manually
// 5. A signal used in the template changes (Angular 16+)

// DOES NOT trigger CD for OnPush:
// - Parent running CD (unless inputs changed)
// - setTimeout/setInterval inside the component
// - HTTP responses (unless using async pipe)
// - Property mutations (obj.name = 'new') — reference same!

OnPush + Immutability Pattern

// BAD: Mutating objects — OnPush won't detect this!
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `<div>{{ user.name }}</div>`
})
export class UserCardComponent {
  @Input() user: User;
}

// Parent:
this.user.name = 'New Name'; // MUTATION! Same reference!
// OnPush won't trigger → DOM shows old name!

// GOOD: New reference — OnPush detects this
this.user = { ...this.user, name: 'New Name' }; // New object!
// OnPush sees new reference → triggers CD → DOM updates

// GOOD for arrays:
this.items = [...this.items, newItem];           // Add
this.items = this.items.filter(i => i.id !== id); // Remove
this.items = this.items.map(i =>                  // Update
  i.id === id ? { ...i, name: 'New' } : i
);

When to Use markForCheck() vs detectChanges()

@Component({
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class NotificationComponent implements OnInit {
  notifications: Notification[] = [];

  constructor(
    private cdr: ChangeDetectorRef,
    private ws: WebSocketService
  ) {}

  ngOnInit() {
    // WebSocket messages don't trigger CD in OnPush
    this.ws.messages$.subscribe(msg => {
      this.notifications.push(msg);
      this.cdr.markForCheck();  // Marks this component + ancestors dirty
      // CD will run on next cycle (batched with other changes)
    });

    // Alternative: detectChanges() — runs CD immediately (sync)
    // Use sparingly! Can cause performance issues if called too often
    this.ws.messages$.subscribe(msg => {
      this.notifications = [...this.notifications, msg];
      this.cdr.detectChanges(); // Immediate sync CD — use with caution
    });
  }
}

// BEST PATTERN: Use async pipe (auto markForCheck + auto unsubscribe)
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <div *ngFor="let n of notifications$ | async">
      {{ n.message }}
    </div>
  `
})
export class NotificationComponent {
  notifications$ = this.ws.messages$.pipe(
    scan((acc, msg) => [...acc, msg], [])
  );
}

OnPush Checklist for Maximum Performance

  • Make ALL components OnPush (default → opt-out for complex cases)
  • Use immutable data patterns (spread operator, Object.assign)
  • Use async pipe for all Observable subscriptions
  • Avoid function calls in templates — use pure pipes or pre-computed properties
  • Use trackBy for all *ngFor loops
  • Use signals for fine-grained reactivity (Angular 16+)

3. Angular Signals (Fine-Grained Reactivity)

What Are Signals?

Signals are Angular's new reactive primitive (Angular 16+) that provide fine-grained reactivity — only the parts of the template that depend on a changed signal get re-rendered.

// Traditional: Change detection checks ALL bindings
@Component({
  template: `
    <h1>{{ title }}</h1>         <!-- Checked even if only count changes -->
    <p>Count: {{ count }}</p>    <!-- Checked even if only title changes -->
    <p>{{ heavyComputation() }}</p> <!-- Called on every CD! -->
  `
})

// Signals: Only affected bindings update
@Component({
  template: `
    <h1>{{ title() }}</h1>       <!-- Only updates when title signal changes -->
    <p>Count: {{ count() }}</p>  <!-- Only updates when count signal changes -->
    <p>{{ doubled() }}</p>       <!-- Only recomputes when count changes -->
  `
})
export class CounterComponent {
  title = signal('My Counter');
  count = signal(0);
  doubled = computed(() => this.count() * 2); // Lazy, cached!

  increment() {
    this.count.update(c => c + 1);
    // Only bindings reading count() or doubled() re-render
    // title() binding is UNTOUCHED
  }
}

Signal APIs

import { signal, computed, effect } from '@angular/core';

// WritableSignal — readable and writable
const name = signal('Angular');
name();              // Read: 'Angular'
name.set('Signals'); // Replace value
name.update(n => n + '!'); // Update based on current value

// Computed Signal — derived, lazy, cached
const fullName = computed(() => `${firstName()} ${lastName()}`);
// Only recomputes when firstName or lastName changes
// Memoized: reading multiple times returns cached result

// Effect — side effect when dependencies change
effect(() => {
  console.log(`Name changed to: ${name()}`);
  // Automatically tracks which signals are read
  // Re-runs only when those signals change
});

// Signal-based inputs (Angular 17.1+)
@Component({
  template: `<p>Hello {{ name() }}</p>`
})
export class GreetComponent {
  name = input<string>();           // Required input
  title = input('Default');          // Optional with default
  count = input.required<number>(); // Required input

  // Computed from input signal
  greeting = computed(() => `Hello, ${this.name()}!`);
}

// Model signals (two-way binding, Angular 17.2+)
@Component({
  template: `<input [value]="query()" (input)="query.set($event.target.value)">`
})
export class SearchComponent {
  query = model(''); // Two-way bindable signal
}

Synchronous state✓ PerfectOverkill

Derived values✓ computed()combineLatest + map

// Converting between Signals and Observables
import { toSignal, toObservable } from '@angular/core/rxjs-interop';

// Observable → Signal
const users$ = this.http.get<User[]>('/api/users');
const users = toSignal(users$, { initialValue: [] });

// Signal → Observable (for RxJS pipelines)
const searchTerm = signal('');
const searchTerm$ = toObservable(this.searchTerm);
const results$ = searchTerm$.pipe(
  debounceTime(300),
  switchMap(term => this.http.get(`/api/search?q=${term}`))
);

4. Zone.js — How It Works & Performance Impact

📺 YouTube Tutorials
  • Zone.js Explained — Angular (Official, Minko Gechev)
  • Zone.js Internals — Maxim Koretskyi

What Zone.js Does

Zone.js is a library that monkey-patches all asynchronous APIs (setTimeout, Promise, addEventListener, etc.) to track when async operations complete, allowing Angular to know when to trigger change detection.

// Zone.js patches these (and more):
// Browser APIs:
setTimeout / setInterval / clearTimeout / clearInterval
requestAnimationFrame / cancelAnimationFrame
Promise.prototype.then / catch / finally
XMLHttpRequest.prototype.open / send
fetch()
addEventListener / removeEventListener
MutationObserver
IntersectionObserver
WebSocket
geolocation.getCurrentPosition

// What happens when you click a button:
1. User clicks button
2. Zone.js intercepts the click event (patched addEventListener)
3. Your handler runs: this.count++
4. Zone.js detects: "async task completed in Angular zone"
5. Zone.js notifies Angular: "something happened!"
6. Angular triggers change detection from root
7. Entire component tree is checked (default strategy)

Performance Cost of Zone.js

  • Bundle size: ~35KB (gzipped) added to polyfills
  • Monkey-patching overhead: Every async API call has wrapper function cost
  • Unnecessary CD triggers: mousemove, scroll, requestAnimationFrame all trigger CD
  • Third-party library conflicts: Some libraries don't work well with patched APIs

Running Code Outside Angular Zone

import { NgZone } from '@angular/core';

@Component({ /* ... */ })
export class MapComponent {
  constructor(private ngZone: NgZone) {}

  initMap() {
    // Run OUTSIDE zone — no change detection triggered!
    this.ngZone.runOutsideAngular(() => {
      // These won't trigger CD:
      this.map = new google.maps.Map(/*...*/);

      // Mouse move on map won't trigger CD (60+ events/sec saved!)
      this.map.addListener('mousemove', (e) => {
        this.updateCursor(e); // Pure DOM manipulation, no Angular needed
      });

      // Animation loop won't trigger CD
      const animate = () => {
        this.updateParticles();
        requestAnimationFrame(animate);
      };
      requestAnimationFrame(animate);
    });

    // When you DO need to update Angular bindings:
    this.map.addListener('click', (e) => {
      this.ngZone.run(() => {
        // Back in Angular zone — triggers CD
        this.selectedLocation = e.latLng;
      });
    });
  }
}

Common Zone.js Performance Traps

// TRAP 1: setInterval in component — triggers CD every interval
@Component({/*...*/})
export class ClockComponent implements OnInit, OnDestroy {
  time = '';
  private intervalId: any;

  // BAD: Triggers CD every second
  ngOnInit() {
    this.intervalId = setInterval(() => {
      this.time = new Date().toLocaleTimeString();
    }, 1000);
  }

  // BETTER: Run outside zone, manually trigger CD
  ngOnInit() {
    this.ngZone.runOutsideAngular(() => {
      this.intervalId = setInterval(() => {
        this.time = new Date().toLocaleTimeString();
        this.cdr.detectChanges(); // Only update this component
      }, 1000);
    });
  }

  ngOnDestroy() { clearInterval(this.intervalId); }
}

// TRAP 2: Scroll listeners triggering CD
// BAD: Every scroll event triggers full CD
@HostListener('window:scroll')
onScroll() { this.scrollY = window.scrollY; }

// GOOD: Outside zone + manual detection
constructor(private ngZone: NgZone, private cdr: ChangeDetectorRef) {
  this.ngZone.runOutsideAngular(() => {
    window.addEventListener('scroll', () => {
      this.scrollY = window.scrollY;
      // Only trigger CD when crossing thresholds
      if (this.shouldUpdate()) {
        this.cdr.detectChanges();
      }
    }, { passive: true });
  });
}

5. Zoneless Angular (The Future)

📺 YouTube Tutorials
  • Zoneless Angular — Angular (Official, Alex Rickabaugh)
  • Going Zoneless with Signals — Decoded Frontend

Why Zoneless?

// Angular 18+ experimental: provideExperimentalZonelessChangeDetection()
// Angular 19+: stable zoneless support

// Benefits:
// 1. Remove 35KB of zone.js from bundle
// 2. No unnecessary CD triggers (scroll, mousemove, timers)
// 3. Better performance with signals (fine-grained updates)
// 4. Better compatibility with third-party libraries
// 5. Simpler mental model (explicit reactivity)

// bootstrap.ts
import { bootstrapApplication } from '@angular/platform-browser';
import { provideExperimentalZonelessChangeDetection } from '@angular/core';

bootstrapApplication(AppComponent, {
  providers: [
    provideExperimentalZonelessChangeDetection()
    // No zone.js import needed in polyfills!
  ]
});

Zoneless Change Detection Model

// In zoneless mode, CD is triggered by:
// 1. Signal changes (in template)
// 2. Async pipe (Observable emissions)
// 3. markForCheck() manual call
// 4. Component events (output emissions)

// NOT triggered by (unlike zone-based):
// setTimeout, setInterval
// Raw Promise.then()
// fetch() responses
// addEventListener callbacks
// requestAnimationFrame

@Component({
  template: `
    <h1>{{ title() }}</h1>
    <button (click)="increment()">Count: {{ count() }}</button>
  `
})
export class ZonelessComponent {
  title = signal('Zoneless Angular');
  count = signal(0);

  increment() {
    this.count.update(c => c + 1); // Signal change → automatic CD
  }

  ngOnInit() {
    // This WON'T trigger CD in zoneless!
    setTimeout(() => {
      this.count.set(99); // Signal change → WILL trigger CD
      // But raw property assignment won't:
      // this.title = 'new'; // Won't work without signal!
    }, 1000);
  }
}

6. RxJS Performance Patterns

📺 YouTube Tutorials
  • RxJS Performance Tips — Decoded Frontend
  • RxJS Best Practices in Angular — Angular University

Subscription Management (Memory Leaks Prevention)

// Pattern 1: takeUntilDestroyed (Angular 16+ — BEST)
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';

@Component({/*...*/})
export class MyComponent {
  private destroyRef = inject(DestroyRef);

  ngOnInit() {
    this.dataService.getData().pipe(
      takeUntilDestroyed(this.destroyRef)
    ).subscribe(data => { /* ... */ });
  }
}

// Pattern 2: takeUntil with Subject (pre-Angular 16)
private destroy$ = new Subject<void>();
ngOnInit() {
  this.data$.pipe(takeUntil(this.destroy$)).subscribe(/*...*/);
}
ngOnDestroy() {
  this.destroy$.next();
  this.destroy$.complete();
}

// Pattern 3: async pipe (auto-unsubscribes, triggers markForCheck)
@Component({
  template: `{{ data$ | async }}`
})

// Pattern 4: toSignal (Angular 16+ — no subscription management needed)
data = toSignal(this.dataService.getData(), { initialValue: null });

Avoiding Excessive Emissions

// PROBLEM: Search input fires on every keystroke
searchControl = new FormControl('');

// BAD: API call on every keystroke
this.searchControl.valueChanges.subscribe(term => {
  this.http.get(`/api/search?q=${term}`).subscribe(/*...*/);
  // 10 keystrokes = 10 HTTP requests!
});

// GOOD: Debounce + distinct + switchMap
results$ = this.searchControl.valueChanges.pipe(
  debounceTime(300),           // Wait 300ms after last keystroke
  distinctUntilChanged(),      // Skip if value hasn't changed
  filter(term => term.length >= 2), // Minimum length
  switchMap(term =>            // Cancel previous request
    this.http.get(`/api/search?q=${term}`).pipe(
      catchError(() => of([]))  // Handle errors gracefully
    )
  ),
  shareReplay(1)               // Share result with multiple subscribers
);

shareReplay vs share — Multicasting

// Without sharing: Each subscriber triggers a new HTTP request!
const data$ = this.http.get('/api/data'); // Cold observable
data$.subscribe(d => this.component1 = d); // HTTP request 1
data$.subscribe(d => this.component2 = d); // HTTP request 2 (duplicate!)

// With shareReplay: Single HTTP request, result shared
const data$ = this.http.get('/api/data').pipe(
  shareReplay({ bufferSize: 1, refCount: true })
  // bufferSize: 1 = replay last value to new subscribers
  // refCount: true = unsubscribe from source when no subscribers
);
data$.subscribe(d => this.component1 = d); // HTTP request
data$.subscribe(d => this.component2 = d); // Gets cached value, no request!

// IMPORTANT: refCount: true prevents memory leaks
// Without it, the source stays subscribed forever

Efficient Data Transformation

// BAD: Multiple subscriptions + manual state management
ngOnInit() {
  this.userService.getUser().subscribe(user => {
    this.user = user;
    this.fullName = `${user.first} ${user.last}`;
    this.isAdmin = user.roles.includes('admin');
    this.avatar = this.getAvatarUrl(user);
  });
}

// GOOD: Derived observables + async pipe (no manual subscribe)
user$ = this.userService.getUser().pipe(shareReplay(1));
fullName$ = this.user$.pipe(map(u => `${u.first} ${u.last}`));
isAdmin$ = this.user$.pipe(map(u => u.roles.includes('admin')));
avatar$ = this.user$.pipe(map(u => this.getAvatarUrl(u)));

// Template: {{ fullName$ | async }}, *ngIf="isAdmin$ | async"

// BEST (Angular 16+): Signals
user = toSignal(this.userService.getUser());
fullName = computed(() => {
  const u = this.user();
  return u ? `${u.first} ${u.last}` : '';
});

Avoid Function Calls in Templates

// BAD: Function called on every CD cycle (potentially 20+ times/sec)
@Component({
  template: `
    <div>{{ getFormattedDate(item.date) }}</div>
    <div [class.active]="isActive(item)"></div>
    <div *ngIf="hasPermission('admin')">...</div>
  `
})
export class ItemComponent {
  getFormattedDate(date: Date): string {
    return new Intl.DateTimeFormat('en-US').format(date); // EXPENSIVE!
  }
}

// GOOD: Use pure pipes (cached by Angular)
@Pipe({ name: 'formatDate', pure: true })
export class FormatDatePipe implements PipeTransform {
  transform(date: Date, format?: string): string {
    return new Intl.DateTimeFormat('en-US').format(date);
  }
  // Pure pipe: Only recalculates when input REFERENCE changes
  // Called once, result cached until input changes
}
// Template: {{ item.date | formatDate }}

// GOOD: Pre-compute in component
ngOnInit() {
  this.formattedDate = this.formatDate(this.item.date);
  this.isActive = this.item.status === 'active';
}

// BEST: Signals (Angular 16+)
formattedDate = computed(() =>
  new Intl.DateTimeFormat('en-US').format(this.item().date)
);

NgIf vs NgSwitch vs NgClass Performance

// *ngIf: Completely removes/recreates DOM — use for large sections
// [hidden]: Keeps in DOM, just hides — use for frequent toggles

// LARGE SECTION (rare toggle): Use *ngIf — saves DOM nodes
<app-admin-panel *ngIf="isAdmin"></app-admin-panel>
// When false: component destroyed, no memory, no CD

// FREQUENT TOGGLE (tabs): Use [hidden] — avoids recreation cost
<div [hidden]="activeTab !== 'profile'">...heavy content...</div>
<div [hidden]="activeTab !== 'settings'">...heavy content...</div>
// Stays in DOM, avoids reconstruction but uses memory

// @if (Angular 17+ control flow — better performance than *ngIf)
@if (isAdmin) {
  <app-admin-panel />
} @else {
  <p>Access denied</p>
}
// Compiles to more efficient instructions than structural directives

Angular 17+ Control Flow (Built-in Performance)

// New control flow syntax is faster than structural directives because:
// 1. No extra DOM wrappers (ng-template, ng-container)
// 2. Optimized change detection (tracks dependencies)
// 3. Better type narrowing
// 4. Built-in trackBy equivalent

// @for with track (required!) — replaces *ngFor + trackBy
@for (item of items; track item.id) {
  <app-item-card [item]="item" />
} @empty {
  <p>No items found</p>
}

// @switch — replaces ngSwitch
@switch (status) {
  @case ('loading') { <app-spinner /> }
  @case ('error') { <app-error [msg]="errorMsg" /> }
  @case ('success') { <app-content [data]="data" /> }
  @default { <p>Unknown state</p> }
}

8. *ngFor & trackBy Deep Dive

📺 YouTube Tutorials
  • trackBy Explained — Angular University
  • Angular @for with track — Decoded Frontend

Why trackBy is Critical

// WITHOUT trackBy:
// When items array changes, Angular:
// 1. Destroys ALL existing DOM nodes
// 2. Creates ALL new DOM nodes
// Even if only 1 item was added/changed!

// With 100 items + complex components:
// Update 1 item → destroy 100 + create 100 components = SLOW

// WITH trackBy:
// Angular uses the tracking value to identify which items:
// - Were added (create only new ones)
// - Were removed (destroy only those)
// - Were moved (reorder DOM nodes)
// - Were unchanged (keep existing DOM nodes!)

@Component({
  template: `
    <!-- Old syntax -->
    <div *ngFor="let item of items; trackBy: trackById">
      <app-complex-card [data]="item"></app-complex-card>
    </div>

    <!-- Angular 17+ syntax -->
    @for (item of items; track item.id) {
      <app-complex-card [data]="item" />
    }
  `
})
export class ListComponent {
  trackById(index: number, item: Item): number {
    return item.id; // Unique, stable identifier
  }
}

trackBy Best Practices

// GOOD: Track by unique ID
trackById = (i: number, item: Item) => item.id;

// OK: Track by index (when items don't have IDs, but order is stable)
trackByIndex = (i: number) => i;
// WARNING: Don't use trackByIndex if items can be reordered/inserted!

// BAD: Track by object reference (equivalent to no trackBy)
trackByRef = (i: number, item: Item) => item; // Creates new ref each time!

// BAD: Track by compound value
trackByMultiple = (i: number, item: Item) => `${item.id}-${item.name}`;
// If name changes, Angular thinks it's a new item → destroys + recreates

// Performance comparison (1000 items, update 1):
// No trackBy:    ~150ms (destroys all, recreates all)
// trackBy: id:   ~2ms   (updates only 1 DOM node)

9. Pure Pipes vs Impure Pipes

📺 YouTube Tutorials
  • Pure vs Impure Pipes — Decoded Frontend
  • Angular Pipes Performance — Angular University

Pure Pipes (Default — Performance Optimized)

@Pipe({ name: 'filter', pure: true }) // DEFAULT
export class FilterPipe implements PipeTransform {
  transform(items: Item[], searchTerm: string): Item[] {
    return items.filter(item =>
      item.name.toLowerCase().includes(searchTerm.toLowerCase())
    );
  }
}

// Pure pipe behavior:
// - Called ONLY when input REFERENCE changes (===)
// - Memoized: same input → same output (cached)
// - NOT called on every CD cycle
// - PERFECT for OnPush components

// Usage: {{ items | filter:searchTerm }}
// Only recalculates when items array reference OR searchTerm changes

Impure Pipes (Use with Extreme Caution)

@Pipe({ name: 'filter', pure: false }) // IMPURE!
export class ImpureFilterPipe implements PipeTransform {
  transform(items: Item[], searchTerm: string): Item[] {
    return items.filter(item =>
      item.name.toLowerCase().includes(searchTerm.toLowerCase())
    );
  }
}

// Impure pipe behavior:
// - Called on EVERY change detection cycle
// - Even when inputs haven't changed!
// - Can react to array mutations (push, splice)
// - 99% of the time you DON'T need this

// WHEN to use impure: (almost never)
// - async pipe is impure (it's special-cased by Angular)
// - Pipe depends on external state that changes frequently
// - Pipe operates on mutable data structures (bad practice anyway)
Performance Rule: If you need an impure pipe because your array is mutated, fix the data flow instead. Use immutable patterns (spread, map, filter) and pure pipes. 100 impure pipes = 100 function calls per CD cycle!

// Network-aware preloading strategy
@Injectable()
export class NetworkAwarePreloadStrategy implements PreloadingStrategy {
  preload(route: Route, load: () => Observable<any>): Observable<any> {
    // Check network conditions
    const conn = (navigator as any).connection;

    if (conn) {
      // Don't preload on slow connections
      if (conn.saveData) return of(null);           // Data saver mode
      if (conn.effectiveType === '2g') return of(null); // Too slow
      if (conn.effectiveType === '3g') {
        // Only preload high-priority routes on 3G
        return route.data?.['priority'] === 'high' ? load() : of(null);
      }
    }

    // 4G or WiFi: preload everything
    return load();
  }
}

// Viewport-based preloading (like quicklink)
@Injectable()
export class ViewportPreloadStrategy implements PreloadingStrategy {
  private preloadQueue = new Map<string, () => Observable<any>>();
  private observer: IntersectionObserver;

  constructor() {
    this.observer = new IntersectionObserver((entries) => {
      entries.filter(e => e.isIntersecting).forEach(entry => {
        const path = (entry.target as HTMLAnchorElement).pathname;
        const loader = this.preloadQueue.get(path);
        if (loader) {
          loader().subscribe();
          this.preloadQueue.delete(path);
        }
      });
    });

    // Observe all router links
    document.querySelectorAll('a[routerLink]').forEach(link => {
      this.observer.observe(link);
    });
  }

  preload(route: Route, load: () => Observable<any>): Observable<any> {
    this.preloadQueue.set('/' + route.path, load);
    return of(null);
  }
}

// Hydration = attaching event listeners to server-rendered HTML
// WITHOUT destroying and re-creating DOM!

@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <div *ngIf="loading$ | async">Loading...</div>
    <div *ngIf="error$ | async as error">{{ error }}</div>
    <div *ngIf="(data$ | async) as data">
      <h2>{{ data.title }}</h2>
      <p>Items: {{ (filteredItems$ | async)?.length }}</p>

      </div>

export class DataComponent implements OnInit {

  error$ = new BehaviorSubject<string | null>(null);
  data$ = new BehaviorSubject<Data | null>(null);
  filter$ = new BehaviorSubject('');

    map(([data, filter]) =>
      data?.items.filter(i => i.name.includes(filter)) ?? []
    )

    this.loading$.next(true);
    this.dataService.getData().pipe(
      finalize(() => this.loading$.next(false))
    ).subscribe({
      next: data => this.data$.next(data),
      error: err => this.error$.next(err.message)
    });
  }
}

15. Interview Questions — Phase 4

Beginner Level

  1. Q: What is Change Detection in Angular?
    A: Change Detection is the mechanism Angular uses to synchronize component data with the DOM. By default, when an async event occurs (click, HTTP response, timer), Angular checks every component from root to leaves, evaluating template bindings and updating the DOM where values have changed.
  2. Q: What is the difference between Default and OnPush change detection?
    A: Default (CheckAlways): Angular checks the component on EVERY CD cycle, regardless of whether its data changed. OnPush: Angular ONLY checks when: (1) @Input reference changes, (2) event originates from this component, (3) async pipe emits, (4) markForCheck() called, (5) signal changes. OnPush can eliminate 90%+ of unnecessary checks.
  3. Q: What is trackBy in *ngFor and why is it important?
    A: trackBy provides Angular a way to identify items in a list by a unique key (like ID). Without it, when the array changes, Angular destroys and recreates ALL DOM nodes. With trackBy, Angular only creates/destroys nodes for items that were actually added/removed. Critical for lists with frequent updates or complex item templates.
  4. Q: Why should you avoid function calls in Angular templates?
    A: Functions in templates are called on EVERY change detection cycle (potentially 20+ times per second). Each call performs computation and returns a value that Angular compares. Use pure pipes (cached, called only on input change) or pre-computed properties instead.

Intermediate Level

  1. Q: Explain Zone.js and its performance implications.
    A: Zone.js monkey-patches all async APIs (setTimeout, Promise, addEventListener, etc.) to detect when async operations complete, triggering Angular's change detection. Performance impact: (1) 35KB bundle size addition, (2) Every async operation triggers full CD tree walk, (3) mousemove/scroll events cause unnecessary CD cycles, (4) Third-party code can trigger unneeded CD. Mitigation: runOutsideAngular() for operations that don't need CD, OnPush strategy, and the future zoneless approach with signals.
  2. Q: How do Angular Signals improve performance over the traditional approach?
    A: Signals provide fine-grained reactivity: (1) Only template bindings that READ a changed signal update (not the entire component tree). (2) computed() values are lazy and memoized — only recalculate when dependencies change. (3) No Zone.js needed — signals notify Angular directly about changes. (4) No need for async pipe boilerplate. (5) Better than OnPush because updates are binding-level granular, not component-level.
  3. Q: Explain the difference between markForCheck() and detectChanges().
    A: markForCheck(): Marks the component and ALL its ancestors as dirty. Change detection will include them in the NEXT cycle. It's batched and safe to call multiple times. detectChanges(): Runs change detection IMMEDIATELY and synchronously on this component and its children. Can cause performance issues if called too frequently. Use markForCheck() 99% of the time; detectChanges() only when you need immediate synchronous update.
  4. Q: How do you implement lazy loading in Angular and what are the performance benefits?
    A: Route-based: loadChildren: () => import('./module').then(m => m.Module) or loadComponent. Component-based (Angular 17+): @defer (on viewport) { <component /> }. Benefits: (1) Smaller initial bundle (faster TTFB, parse, execute), (2) Only load code when needed, (3) Parallel chunk loading with preloading strategies. The initial bundle can shrink from 2MB to 200KB, making the app load 10x faster on mobile.

Advanced Level

  1. Q: Explain Angular's hydration process and its performance impact.
    A: Pre-hydration: Server HTML is destroyed and recreated by client (flicker, double-rendering). With hydration (Angular 16+): Client JS finds existing server-rendered DOM nodes, attaches event listeners and Angular internals WITHOUT destroying/recreating them. This eliminates the flash/flicker, reduces LCP (content visible from server HTML), and avoids expensive DOM recreation. Incremental hydration (v18+) further optimizes by only hydrating components when they enter viewport or receive interaction.
  2. Q: How would you implement a zoneless Angular application and what changes are needed?
    A: (1) Use provideExperimentalZonelessChangeDetection() in bootstrap. (2) Remove zone.js from polyfills. (3) Convert all reactive state to signals. (4) Replace manual subscriptions with toSignal(). (5) Use async pipe or computed() for derived state. (6) Ensure all user-facing state changes go through signals (setTimeout won't trigger CD!). (7) For third-party libs that mutate state outside signals, use effect() or manual markForCheck(). Benefits: -35KB bundle, no unnecessary CD cycles, predictable reactivity model.
  3. Q: Design a performance strategy for an Angular app with 200+ components and complex data grids.
    A: (1) OnPush everywhere + immutable data patterns. (2) Virtual scrolling for large grids (CDK). (3) trackBy on all *ngFor. (4) Lazy load route modules + @defer for heavy components. (5) Web Workers for data processing/sorting. (6) Signal-based state management for fine-grained updates. (7) runOutsideAngular for animations/scroll handlers. (8) Pure pipes for all transformations. (9) content-visibility: auto for off-screen sections. (10) Bundle budgets in CI to prevent regression. (11) SSR for initial load performance. (12) Preloading strategy based on network conditions.
  4. Q: Explain the complete lifecycle of an Angular change detection cycle with OnPush.
    A: (1) Async event occurs (captured by Zone.js or signal change). (2) ApplicationRef.tick() is called. (3) Starting from root, Angular walks the component tree. (4) For each component: if Default strategy → always check. If OnPush → check ONLY if marked dirty. (5) "Checking" means: evaluate each template expression, compare with previous value (dirty checking). (6) If value changed → update the DOM binding. (7) After checking a component, recursively check children. (8) For OnPush children that aren't dirty → SKIP entire subtree (massive savings!). (9) After the full walk, the view is up to date. (10) In dev mode, Angular runs a second CD cycle to detect ExpressionChangedAfterItHasBeenCheckedError.

Scenario-Based Questions

  1. Q: Your Angular dashboard loads 3 seconds on mobile. How do you cut it to under 1 second?
    A: (1) Analyze bundle (source-map-explorer): identify largest chunks. (2) Lazy-load non-critical routes. (3) Use @defer for below-fold widgets (charts, tables). (4) Implement SSR for instant first paint. (5) Preload critical data in route resolver. (6) Optimize images (NgOptimizedImage, WebP, lazy-load). (7) Inline critical CSS. (8) Remove unused dependencies (lodash → lodash-es specific imports). (9) Enable Brotli compression. (10) Use CDN for static assets. Target: Initial bundle < 200KB gzipped.
  2. Q: Users report your Angular data table becomes laggy after sorting/filtering 10,000 rows.
    A: (1) Implement virtual scrolling (only render visible rows ~30). (2) Move sorting/filtering to Web Worker (off main thread). (3) Debounce filter input (300ms). (4) Use OnPush + trackBy. (5) Don't use functions in template cells (pre-compute or use pipes). (6) Consider server-side pagination/sorting for truly large datasets. (7) Use content-visibility: auto for non-visible rows. (8) Profile with Angular DevTools to identify specific bottleneck (CD cycles, DOM operations, or computation).
