1. Rapid-Fire Interview Questions (Top 30)

📺 YouTube Tutorials — Interview Prep

  • Frontend Performance Fundamentals — Todd Gardner (Frontend Masters)

These are the most commonly asked frontend performance questions across companies like Google, Microsoft, Amazon, Flipkart, and product-based companies.

Q1: What are Core Web Vitals? Easy

A: Three Google metrics measuring user experience: LCP (Largest Contentful Paint ≤2.5s — loading speed), INP (Interaction to Next Paint ≤200ms — responsiveness), CLS (Cumulative Layout Shift ≤0.1 — visual stability). They directly affect SEO rankings.

Q2: Difference between reflow, repaint, and composite? Easy

A: Reflow (Layout): Recalculates element geometry (expensive). Repaint: Fills visual pixels without geometry change. Composite: Draws pre-painted layers together (cheapest, GPU). Changing width → all three. Changing color → repaint + composite. Changing transform → composite only.

Q3: How do you achieve 60fps animations? Medium

A: Only animate transform and opacity — these run on the compositor thread without touching the main thread. Avoid animating width, height, top, left (trigger reflow). Use will-change to promote layers. Use requestAnimationFrame for JS animations. Budget: 10ms of JS per frame (16.67ms total for 60fps).

Q4: What is the Critical Rendering Path and how do you optimize it? Medium

A: CRP: HTML → DOM → CSSOM → Render Tree → Layout → Paint → Composite. Optimize: (1) Minimize critical resources (defer non-critical CSS/JS), (2) Reduce critical bytes (minify, compress), (3) Shorten critical path length (inline critical CSS in first 14KB), (4) Use defer/async for scripts, (5) Preload LCP resources.

Q5: Explain Angular Change Detection and OnPush strategy. Medium

A: Default CD checks every component on every async event. OnPush only checks when: @Input reference changes, event from the component, async pipe emits, or markForCheck() called. Combined with immutable data patterns, OnPush can skip 90%+ of unnecessary checks. Use with trackBy, pure pipes, and signals for maximum performance.

Q6: What is tree shaking and what prevents it? Medium

A: Tree shaking removes unused exports from bundles using static analysis of ES module imports. Prevented by: (1) CommonJS require() (not statically analyzable), (2) Side effects in modules, (3) Barrel files re-exporting everything, (4) Dynamic imports with variable paths. Fix: Use ES modules, mark packages as sideEffects: false, import from specific paths.

Q7: Explain lazy loading strategies in Angular. Medium

A: Route-based: loadChildren/loadComponent creates separate chunks loaded on navigation. Component-based (Angular 17+): @defer blocks with triggers (viewport, interaction, idle, timer). Preloading: PreloadAllModules (background load after initial), custom strategies (network-aware, viewport-based). Benefits: Reduces initial bundle from MBs to KBs, faster TTI.

Q8: How does HTTP/2 improve performance over HTTP/1.1? Medium

A: (1) Multiplexing: Multiple requests on single TCP connection (vs 6 parallel connections). (2) Header compression (HPACK): 85-90% smaller headers. (3) Stream prioritization. (4) Binary framing (more efficient parsing). Limitation: TCP head-of-line blocking. Solved by HTTP/3 (QUIC/UDP) which has per-stream flow control.

Q9: What causes memory leaks in Angular applications? Medium

A: (1) Unsubscribed RxJS subscriptions (use takeUntilDestroyed/takeUntil). (2) Event listeners on global objects (window, document) not removed in ngOnDestroy. (3) setInterval/setTimeout not cleared. (4) Detached DOM nodes (elements removed from DOM but referenced in JS). (5) Closures capturing large scopes. (6) Growing caches/arrays without eviction. Fix: Use async pipe, takeUntilDestroyed, proper cleanup in ngOnDestroy.

Q10: Explain the event loop and its performance implications. Medium

A: Event loop: Pick task → Execute → Drain ALL microtasks → Render (if needed) → Repeat. Performance implication: Long tasks (>50ms) block rendering and user input. Microtasks drain completely before rendering (can starve UI). Fix: Break long tasks with scheduler.yield() or setTimeout(0). Keep each task under 50ms for responsive UI.

Q11: What is layout thrashing and how do you prevent it? Medium

A: Layout thrashing: Reading layout properties (offsetWidth, getBoundingClientRect) then writing styles in a loop. Each read forces synchronous layout recalculation. Fix: Batch all reads first, then all writes. Or use requestAnimationFrame to separate read/write phases. Libraries like fastdom automate this pattern.

Q12: Explain Angular Signals and their performance benefits. Medium

A: Signals provide fine-grained reactivity: only template bindings that read a changed signal update (not entire component). computed() is lazy + memoized — only recalculates when dependencies change. Enables zoneless Angular (removes 35KB zone.js, eliminates unnecessary CD triggers). Better than OnPush because updates are binding-level, not component-level.

Q13: How does the browser preload scanner work? Hard

A: When the HTML parser is blocked (by synchronous JS), a secondary "preload scanner" looks ahead in the HTML source for resource URLs (img, link, script src). It initiates downloads in parallel while the parser waits. This means resources are discovered and fetched earlier. Anti-pattern: dynamically injecting resources via JS bypasses the preload scanner — those resources are invisible until JS executes.

Q14: Explain content-visibility: auto and its performance impact. Hard

A: content-visibility: auto tells the browser to skip rendering (style, layout, paint) of off-screen elements until they're near the viewport. It's built-in virtualization. Combined with contain-intrinsic-size (maintains scroll height), it can reduce initial rendering time by 50-85% for long pages. The browser still creates DOM but skips the rendering pipeline for off-screen sections.

Q15: What is the 14KB rule and why does it matter? Hard

A: TCP slow start begins with a congestion window of ~10 packets (~14KB). On a new connection, only 14KB can be sent in the first round trip. So: (1) Critical CSS + HTML should fit in 14KB for fastest FCP. (2) Inline critical CSS avoids additional round trips. (3) This is why HTTP/2 server push was valuable. (4) Connection reuse avoids re-entering slow start.

Q16: How do you optimize images for web performance? Medium

A: (1) Modern formats: AVIF (50% smaller than JPEG) → WebP → JPEG fallback using <picture>. (2) Responsive: srcset + sizes for multiple resolutions. (3) Lazy loading: loading="lazy" for below-fold. (4) Priority: fetchpriority="high" for LCP image + preload. (5) Dimensions: Always set width/height to prevent CLS. (6) Compression: Quality 75-80% for lossy. (7) Angular: NgOptimizedImage directive for automatic best practices.

Q17: Explain caching strategies for a Single Page Application. Medium

A: (1) index.html: no-cache (always revalidate for fresh deployments). (2) Hashed assets (main.abc123.js): max-age=31536000, immutable (cache forever, hash changes on deploy). (3) API: private, stale-while-revalidate. (4) Service Worker: Cache app shell for instant repeat visits. Key insight: The HTML must not be cached so users get new hashed asset references on each deploy.

Q18: What is Zone.js and its performance impact? Hard

A: Zone.js monkey-patches ALL async APIs (setTimeout, Promise, addEventListener) to detect when async operations complete, triggering Angular's change detection. Impact: 35KB bundle addition, every async event triggers full CD tree walk, mousemove/scroll cause unnecessary CD. Fix: runOutsideAngular() for non-Angular operations, OnPush strategy, and future zoneless approach with signals.

Q19: How do Web Workers improve performance? Medium

A: Web Workers run JavaScript on a separate thread, preventing heavy computation from blocking UI. Best for: sorting large datasets, image processing, crypto, data parsing. Limitations: No DOM access, communication via postMessage (serialization cost). Optimization: Use Transferable Objects for zero-copy transfer of ArrayBuffers. In Angular: ng generate web-worker.

Q20: Explain virtual scrolling and when to use it. Medium

A: Virtual scrolling renders only visible items in a list (+ small buffer), recycling DOM nodes as user scrolls. Instead of 10,000 DOM nodes, only 20-30 exist at any time. When to use: Lists with 100+ items, complex item templates, or any scenario where full DOM rendering causes jank. Angular CDK: <cdk-virtual-scroll-viewport> with *cdkVirtualFor.

Q21: What is INP and how does it differ from FID? Hard

A: FID measured only the input delay of the FIRST interaction. INP measures the FULL latency (input delay + processing time + presentation delay) of ALL interactions, reporting the 98th percentile worst. INP is better because: (1) Covers all interactions not just first, (2) Includes processing + render time, (3) Reflects real session experience. Replaced FID as Core Web Vital in March 2024.

Q22: Explain the FLIP animation technique. Hard

A: FLIP (First, Last, Invert, Play): Record initial position → Apply final layout → Calculate difference → Animate inverse transform to identity. Layout change happens instantly (no animation), visual animation uses only compositor-friendly transforms. Result: Layout-like animations at 60fps because only transform is animated (compositor thread). Used by Angular animations and Material CDK.

Q23: How does Angular hydration work? Hard

A: Pre-hydration: Client destroys server HTML and recreates (flicker). With hydration (Angular 16+): Client finds existing server-rendered DOM nodes, attaches event listeners WITHOUT re-creating DOM. Eliminates double-rendering, no flicker, maintains LCP element. Incremental hydration (v18+): Only hydrate components on viewport entry or interaction, leaving static sections as pure HTML with zero JS.

Q24: What is stale-while-revalidate and when to use it? Medium

A: stale-while-revalidate: Serve cached response immediately (instant!), fetch fresh copy in background for next request. User sees cached content instantly; next user gets fresh content. Perfect for: API data that can be slightly stale, CDN-cached pages, frequently accessed resources. Trade-off: User may see seconds/minutes-old data.

Q25: Explain pure pipes vs impure pipes in Angular. Easy

A: Pure pipes (default): Called ONLY when input reference changes. Memoized — same input returns cached result. Impure pipes: Called on EVERY change detection cycle. Use pure pipes 99% of the time. The async pipe is a special impure pipe. If you need impure behavior, fix your data flow (use immutable patterns) instead.

Q26: What are resource hints and how do they differ? Medium

A: dns-prefetch: Resolve DNS (cheapest). preconnect: DNS + TCP + TLS (full connection). preload: Download NOW for current page, high priority. prefetch: Download for NEXT page, low priority. modulepreload: Download + parse JS module. Use preconnect for critical third-party origins, preload for late-discovered resources (fonts, hero image).

Q27: How do you reduce CLS (Cumulative Layout Shift)? Medium

A: (1) Always set image dimensions (width/height or aspect-ratio CSS). (2) Reserve space for ads/embeds with min-height. (3) Use font-display: swap + size-adjust for web fonts. (4) Skeleton screens for dynamic content. (5) Inline critical CSS. (6) Avoid injecting content above existing content. (7) Use contain-intrinsic-size with content-visibility.

Q28: Explain passive event listeners. Medium

A: By default, browser must wait for scroll/touch handlers to finish (they might call preventDefault). With { passive: true }, you promise not to call preventDefault, allowing the browser to scroll on compositor thread immediately. Eliminates scroll jank from event listeners. Chrome defaults scroll/touch to passive, but explicit is best practice.

Q29: What is V8's hidden class optimization? Expert

A: V8 assigns "hidden classes" (shapes/maps) to objects with same structure. Same hidden class = fast property access via inline caches (O(1) fixed offset). Breaking rules causes megamorphic (dictionary lookup, slow): (1) Adding properties in different order, (2) Dynamically adding properties, (3) Deleting properties, (4) Mixing types in same function arguments.

Q30: How does scheduler.yield() differ from setTimeout(0)? Expert

A: Both yield to main thread for rendering/input. setTimeout(0) puts continuation at the BACK of task queue (low priority, 1-4ms minimum delay). scheduler.yield() maintains your task's priority at the FRONT of the user-visible queue — resumes faster while still allowing rendering. Semantically clearer about intent. Better for breaking long tasks without losing responsiveness.

S1: Your Angular app takes 5 seconds to load on mobile. How do you fix it? Hard

Answer approach:

  1. Diagnose: Run Lighthouse with mobile throttling + analyze bundle (source-map-explorer)
  2. Initial load: Lazy-load all non-critical routes. Use @defer for below-fold. Target <200KB initial bundle.
  3. Network: Enable Brotli compression. Use CDN. Preconnect to API origin. Preload LCP image.
  4. Rendering: SSR for instant FCP. Inline critical CSS. Defer non-critical CSS.
  5. Assets: WebP/AVIF images. Lazy-load below-fold images. Self-host fonts with font-display: swap.
  6. JS: Remove unused dependencies. Switch to tree-shakeable alternatives. Code-split heavy libraries.
  7. Measure: RUM monitoring to validate improvement in field. Target: FCP <1.8s, LCP <2.5s.

S2: Users report the dashboard becomes laggy after 30 minutes. What's happening? Hard

Answer: Memory leak. Investigation steps:

  1. Open Performance Monitor — watch JS heap size trend over time (saw-tooth trending up = leak)
  2. Take heap snapshots before/after repeated actions → compare
  3. Look for: growing event listener count, detached DOM nodes, growing arrays
  4. Common Angular causes: Subscriptions without unsubscribe, services holding growing arrays, router navigation leaking components, intervals/timeouts not cleared
  5. Fix: Use takeUntilDestroyed(), async pipe, clear intervals in ngOnDestroy, limit cache sizes

S3: A data table with 50,000 rows is extremely slow to scroll. Fix it. Hard

Answer:

  1. Virtual scrolling (CDK): Only render ~30 visible rows, recycle DOM on scroll
  2. Server-side pagination: Fetch only 50-100 rows at a time from backend
  3. Web Worker: Move sorting/filtering to worker thread
  4. OnPush + trackBy: Prevent unnecessary re-renders
  5. Debounce filters: Don't recompute on every keystroke (300ms debounce)
  6. Memoize: Cache filtered/sorted results (signal computed())
  7. Progressive rendering: Show first 20 rows immediately, load rest in background

S4: Your LCP is 4.5 seconds. The LCP element is a hero image. How do you fix it? Medium

Answer:

  1. <link rel="preload" as="image" href="hero.webp" fetchpriority="high">
  2. Remove loading="lazy" from hero image (above-fold should be eager)
  3. Serve optimal format: AVIF → WebP → JPEG with <picture>
  4. Serve right size (srcset) — don't send 4K to mobile
  5. Optimize TTFB: CDN, Edge SSR, Early Hints (103)
  6. Eliminate render-blocking CSS before hero image (inline critical CSS)
  7. Don't lazy-load or defer-load any resource the hero image depends on

S5: Third-party scripts (analytics, chat widget, A/B testing) are adding 2 seconds to your page load. Medium

Answer:

  1. Audit impact: Chrome DevTools → Coverage tab to see actual usage
  2. Defer non-critical: Load analytics on requestIdleCallback or after 3s timeout
  3. Facade pattern: Chat widget shows static button, loads real widget on click
  4. Self-host if possible: Eliminates DNS/TCP/TLS to third-party
  5. Use Web Workers: Partytown (run third-party scripts in worker)
  6. Reduce scripts: Remove unused ones, combine where possible
  7. Set resource hints: <link rel="preconnect"> for critical third-parties

S6: Your Angular app has CLS of 0.35 (poor). Identify and fix the causes. Medium

Answer:

  1. Debug: DevTools → Rendering panel → Layout Shift Regions (blue highlights)
  2. Images: Add width/height or aspect-ratio to all images
  3. Fonts: font-display: swap + size-adjust fallback metrics
  4. Dynamic content: Reserve space with skeleton screens (min-height)
  5. Ads/embeds: Fixed container dimensions before ad loads
  6. Late CSS: Inline critical CSS to avoid FOUC

S7: After deploying a new version, Core Web Vitals regressed. How do you investigate? Hard

Answer:

  1. Compare bundle sizes with previous build (source-map-explorer)
  2. Check RUM data segmented by page — which pages regressed?
  3. Check Chrome UX Report (CrUX) for field data confirmation
  4. Run Lighthouse on affected pages with same conditions
  5. Git diff the deployment — identify new dependencies, large assets, changed configs
  6. Profile with DevTools Performance panel — compare flame charts
  7. Check for: new render-blocking resources, removed caching headers, added synchronous scripts, larger images, removed lazy loading
  8. Rollback if severe; fix forward if minor

S8: Your Angular app's INP is 450ms. Users complain buttons feel "sluggish." Hard

Answer:

  1. Profile interactions: DevTools → Performance → record while interacting
  2. Identify bottleneck: Is it input delay (long tasks blocking), processing time (handler too slow), or presentation delay (DOM update too expensive)?
  3. Input delay fix: Break long tasks with yield(), reduce third-party scripts
  4. Processing fix: Debounce handlers, move computation to Web Worker, simplify logic
  5. Presentation fix: Reduce DOM size, use virtual scroll, OnPush + signals, CSS containment
  6. Angular-specific: Ensure OnPush everywhere, check if Zone.js is over-triggering CD, use NgZone.runOutsideAngular for non-essential handlers

S9: You need to display a chart with 1 million data points. How? Expert

Answer:

  1. Data reduction: Downsample server-side (LTTB algorithm) — 1M points → 1000 visible points
  2. Canvas/WebGL: Use Canvas2D or WebGL for rendering (not SVG/DOM for >10K points)
  3. Web Worker: Process/downsample data off main thread
  4. Level of Detail (LOD): Show aggregated data when zoomed out, detailed when zoomed in
  5. Streaming: Load data in chunks, render progressively
  6. GPU acceleration: Use WebGL-based charting (deck.gl, GPU.js)
  7. OffscreenCanvas: Render chart in Web Worker using OffscreenCanvas

S10: A colleague added a 300KB library for one utility function. How do you handle this? Medium

Answer:

  1. Identify if tree-shakeable: Can you import just the function? (lodash-es vs lodash)
  2. Check if the function is simple enough to implement in 10-20 lines (avoid the dependency)
  3. Look for smaller alternatives (date-fns vs moment.js, just-debounce vs lodash)
  4. If the library IS needed: lazy-load it (dynamic import on demand)
  5. Set up bundle budgets to catch this in CI in the future

S13: Your micro-frontend architecture has 5 Angular apps on one page. Performance is terrible. Expert

   - Link metrics to: deployments, feature flags, A/B tests
   - Segment by: page, device type, connection, geo, browser

SD2: Design a CDN strategy for a global Angular application serving 50 countries. Expert

Architecture:
1. Multi-CDN setup (Cloudflare + Akamai) for redundancy and coverage

2. Static assets:
   - Hash-based URLs → Cache-Control: immutable, max-age=1yr
   - Deployed to all edge locations simultaneously
   - Purge on deploy (only index.html)

3. Dynamic content (API):
   - Edge caching with stale-while-revalidate
   - Regional API servers (US, EU, APAC) for lower TTFB
   - GraphQL with edge-level caching per query

4. SSR at edge:
   - Cloudflare Workers / Lambda@Edge for server rendering
   - Cache rendered HTML per route (with TTL)
   - Personalization at edge (inject user data)

5. Image CDN:
   - On-the-fly optimization (Cloudinary/imgix)
   - Auto-format (AVIF/WebP) based on Accept header
   - Auto-resize based on viewport (Client Hints)

6. Failover:
   - Primary CDN down → automatic failover to secondary
   - Origin down → serve stale with stale-if-error=86400
   - Full offline → Service Worker cached version

7. Performance by region:
   - Monitor p75 TTFB per region
   - If p75 > 200ms → add edge location or move origin closer

Challenge 1: Implement debounce with cancel and flush

// Implement a debounce function that:
// 1. Delays execution by `wait` ms
// 2. Resets timer on each call
// 3. Has .cancel() to abort pending call
// 4. Has .flush() to execute immediately
// 5. Returns the result of the last invocation

function debounce(fn, wait) {
  let timer = null;
  let lastArgs = null;
  let lastResult = undefined;

  function debounced(...args) {
    lastArgs = args;
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
      lastResult = fn.apply(this, lastArgs);
      timer = null;
      lastArgs = null;
    }, wait);
    return lastResult;
  }

  debounced.cancel = () => {
    if (timer) {
      clearTimeout(timer);
      timer = null;
      lastArgs = null;
    }
  };

  debounced.flush = () => {
    if (timer) {
      clearTimeout(timer);
      timer = null;
      lastResult = fn.apply(null, lastArgs);
      lastArgs = null;
    }
    return lastResult;
  };

  return debounced;
}

// Test:
const debouncedSearch = debounce((query) => console.log('Searching:', query), 300);
debouncedSearch('h');
debouncedSearch('he');
debouncedSearch('hel');
debouncedSearch('hello'); // Only this executes (after 300ms)

Challenge 2: Implement requestIdleCallback polyfill

// Implement a polyfill for requestIdleCallback
// that schedules work during idle periods

function requestIdleCallbackPolyfill(callback, options = {}) {
  const timeout = options.timeout || Infinity;
  const start = Date.now();

  return setTimeout(() => {
    const deadline = {
      didTimeout: Date.now() - start >= timeout,
      timeRemaining: () => Math.max(0, 50 - (Date.now() - start))
    };
    callback(deadline);
  }, 1); // Schedule as macro task (after current frame)
}

// Usage: Perform non-critical work without blocking
function processInBackground(items) {
  let index = 0;

  function doWork(deadline) {
    while (index < items.length && deadline.timeRemaining() > 0) {
      processItem(items[index]);
      index++;
    }

    if (index < items.length) {
      requestIdleCallback(doWork);
    }
  }

  requestIdleCallback(doWork);
}

Challenge 3: Implement virtual scroll (simplified)

// Implement a basic virtual scroll that:
// 1. Only renders visible items
// 2. Maintains correct scroll height
// 3. Updates on scroll

class VirtualScroll {
  constructor(container, items, itemHeight, renderItem) {
    this.container = container;
    this.items = items;
    this.itemHeight = itemHeight;
    this.renderItem = renderItem;
    this.buffer = 5; // Extra items above/below viewport

    this.totalHeight = items.length * itemHeight;
    this.visibleCount = Math.ceil(container.clientHeight / itemHeight);

    this.setup();
    this.render();
  }

  setup() {
    // Create scroll container
    this.content = document.createElement('div');
    this.content.style.height = this.totalHeight + 'px';
    this.content.style.position = 'relative';
    this.container.appendChild(this.content);

    // Listen to scroll (passive!)
    this.container.style.overflow = 'auto';
    let ticking = false;
    this.container.addEventListener('scroll', () => {
      if (!ticking) {
        requestAnimationFrame(() => {
          this.render();
          ticking = false;
        });
        ticking = true;
      }
    }, { passive: true });
  }

  render() {
    const scrollTop = this.container.scrollTop;
    const startIndex = Math.max(0, Math.floor(scrollTop / this.itemHeight) - this.buffer);
    const endIndex = Math.min(
      this.items.length,
      startIndex + this.visibleCount + this.buffer * 2
    );

    // Clear and re-render visible items
    this.content.innerHTML = '';
    for (let i = startIndex; i < endIndex; i++) {
      const el = this.renderItem(this.items[i], i);
      el.style.position = 'absolute';
      el.style.top = (i * this.itemHeight) + 'px';
      el.style.height = this.itemHeight + 'px';
      el.style.width = '100%';
      this.content.appendChild(el);
    }
  }
}

// Usage:
const vs = new VirtualScroll(
  document.getElementById('list'),
  Array.from({ length: 100000 }, (_, i) => ({ id: i, name: `Item ${i}` })),
  50,
  (item) => {
    const div = document.createElement('div');
    div.textContent = item.name;
    return div;
  }
);

Challenge 4: Implement LRU Cache for API responses

// Implement an LRU (Least Recently Used) cache that:
// 1. Has max capacity
// 2. Returns cached response if available and not expired
// 3. Evicts least-recently-used entries when full
// 4. Supports TTL per entry

class LRUCache {
  constructor(maxSize = 100, defaultTTL = 60000) {
    this.maxSize = maxSize;
    this.defaultTTL = defaultTTL;
    this.cache = new Map(); // Map maintains insertion order
  }

  get(key) {
    if (!this.cache.has(key)) return null;

    const entry = this.cache.get(key);

    // Check expiration
    if (Date.now() > entry.expiry) {
      this.cache.delete(key);
      return null;
    }

    // Move to end (most recently used)
    this.cache.delete(key);
    this.cache.set(key, entry);
    return entry.value;
  }

  set(key, value, ttl = this.defaultTTL) {
    // Delete if exists (to reset position)
    if (this.cache.has(key)) {
      this.cache.delete(key);
    }

    // Evict LRU if at capacity
    if (this.cache.size >= this.maxSize) {
      const firstKey = this.cache.keys().next().value;
      this.cache.delete(firstKey); // Oldest = first in Map
    }

    this.cache.set(key, {
      value,
      expiry: Date.now() + ttl
    });
  }

  has(key) {
    return this.get(key) !== null;
  }

  clear() {
    this.cache.clear();
  }

  get size() {
    return this.cache.size;
  }
}

// Usage with HTTP interceptor:
const apiCache = new LRUCache(50, 30000); // 50 entries, 30s TTL

async function cachedFetch(url, options = {}) {
  const cacheKey = `${options.method || 'GET'}:${url}`;

  const cached = apiCache.get(cacheKey);
  if (cached) return cached;

  const response = await fetch(url, options);
  const data = await response.json();

  apiCache.set(cacheKey, data);
  return data;
}

Challenge 5: Implement task scheduler with priority and yielding

// Implement a scheduler that:
// 1. Manages tasks with priorities (high, normal, low)
// 2. Yields to main thread between tasks
// 3. Processes high-priority tasks first
// 4. Stays within frame budget (5ms per chunk)

class TaskScheduler {
  constructor() {
    this.queues = {
      high: [],
      normal: [],
      low: []
    };
    this.isRunning = false;
  }

  schedule(task, priority = 'normal') {
    this.queues[priority].push(task);
    if (!this.isRunning) this.run();
  }

  async run() {
    this.isRunning = true;

    while (this.hasTasks()) {
      const task = this.getNextTask();
      if (!task) break;

      const start = performance.now();
      await task();
      const elapsed = performance.now() - start;

      // If we used more than 5ms, yield to main thread
      if (elapsed > 5) {
        await this.yieldToMain();
      }
    }

    this.isRunning = false;
  }

  getNextTask() {
    if (this.queues.high.length) return this.queues.high.shift();
    if (this.queues.normal.length) return this.queues.normal.shift();
    if (this.queues.low.length) return this.queues.low.shift();
    return null;
  }

  hasTasks() {
    return this.queues.high.length +
           this.queues.normal.length +
           this.queues.low.length > 0;
  }

  yieldToMain() {
    return new Promise(resolve => {
      if ('scheduler' in globalThis && 'yield' in scheduler) {
        scheduler.yield().then(resolve);
      } else {
        setTimeout(resolve, 0);
      }
    });
  }
}

// Usage:
const scheduler = new TaskScheduler();

// High priority: user interaction response
scheduler.schedule(() => updateUI(), 'high');

// Normal: data processing
scheduler.schedule(() => processData(chunk), 'normal');

// Low: analytics, pre-fetching
scheduler.schedule(() => sendAnalytics(), 'low');

5. Tricky Gotcha Questions

📺 YouTube Tutorials — Common Gotchas
  • Jake Archibald: In The Loop — Event Loop & Rendering (JSConf)
  • Performance Gotchas — Steve Souders

G1: Does display: none prevent image download?

A: NO! The image still downloads. display: none only removes from render tree (no layout/paint), but the browser fetches the resource. To prevent: use loading="lazy" (only downloads near viewport), or conditionally inject the <img> via JS/Angular *ngIf.

G2: Does moving <link rel="stylesheet"> to body bottom help?

A: NO! CSS is ALWAYS render-blocking regardless of position. The browser won't paint anything until ALL CSS is parsed. Worse — CSS at bottom can cause Flash of Unstyled Content (FOUC) in some browsers. Always keep CSS in <head>. Instead: inline critical CSS and async-load the rest.

G3: Is localStorage synchronous?

A: YES! localStorage.getItem() and setItem() are synchronous and block the main thread. They also involve disk I/O. On slow devices, this can take 5-50ms. Never use localStorage in hot paths (event handlers, loops, render functions). For performance-critical caching, use IndexedDB (async) or in-memory Maps.

G4: Does async/await make code truly asynchronous?

A: The awaited Promise is async, but the code AFTER await runs as a microtask. Microtasks run BEFORE rendering! So 10 sequential awaits of CPU-heavy work still block the UI because microtasks drain completely before the browser can paint. To truly yield: await new Promise(resolve => setTimeout(resolve, 0)) or await scheduler.yield().

G5: Does will-change always improve performance?

A: NO! will-change promotes elements to their own compositor layer = more GPU memory. Too many layers = "layer explosion" = worse performance (especially on mobile with limited VRAM). Apply only to elements you're about to animate, and remove after animation completes. Never apply will-change: transform to all elements.

G6: Is HTTP/2 always faster than HTTP/1.1?

A: Usually yes, but NOT always. HTTP/2 over TCP still has head-of-line blocking at the TCP level. A single lost packet blocks ALL streams. On very lossy connections (3G mobile), multiple HTTP/1.1 connections can sometimes outperform single HTTP/2 connection because packet loss only blocks one connection. HTTP/3 (QUIC) fixes this.

G7: Does preloading everything make the page faster?

A: NO! Preloading too many resources creates bandwidth contention. High-priority preloaded resources compete with each other and with the HTML document itself. Only preload 2-3 critical resources (LCP image, critical font, key API call). Overuse actually slows down the most critical resources. Chrome DevTools will warn about excessive preloads.

G8: Is server-side rendering always better for performance?

A: NO! SSR improves FCP/LCP (user sees content faster) but can WORSEN TTI (page looks ready but isn't interactive until hydration completes). If your page is highly interactive (dashboard, editor), SSR adds complexity and server cost without much benefit. Use SSR for content-heavy pages (blogs, e-commerce products, marketing). Use CSR for app-like dashboards.

G9: Does minification significantly reduce file size?

A: After compression (Brotli/Gzip), the difference between minified and unminified is small (5-10%). Compression algorithms already eliminate repetition. However, minification still matters for: (1) Reducing parse time (fewer bytes to parse), (2) Reducing uncompressed size for Service Worker caches, (3) Small savings that add up. But don't obsess — compression does the heavy lifting.

G10: Can JavaScript affect CSSOM construction?

A: YES! If a <script> appears after a <link rel="stylesheet">, the browser waits for CSS to download before executing the script (because JS might query computed styles via getComputedStyle). This creates a dependency chain: CSS blocks JS → JS blocks DOM parsing. Solution: Use defer/async or move scripts before stylesheets if they don't depend on styles.
