2. Font Loading & Optimization

📺 YouTube Tutorials
  • Web Font Optimization — Harry Roberts (CSSConf)
  • font-display & Font Loading — Jen Simmons (Mozilla)
  • Self-Hosting Google Fonts — Kevin Powell

The Font Loading Problem

Without optimization:
1. HTML parsed → discovers @font-face in CSS
2. CSS must fully load first (render-blocking)
3. Font file download begins ONLY after CSSOM + render tree
4. Text invisible until font loads (FOIT — Flash of Invisible Text)
   OR text shown in fallback then swaps (FOUT — Flash of Unstyled Text)

Timeline:
|--CSS load--|--Font discovery--|--Font download--|--Text visible--|
0ms         200ms             250ms             800ms
             Total delay: 800ms before text is readable!

font-display Strategies

ValueBehaviorUse When
swapShow fallback immediately, swap when font loadsBody text, headings (best for performance)
blockInvisible text for 3s, then fallbackIcon fonts (prevent wrong glyphs)
fallbackInvisible 100ms, fallback, swap if loads within 3sBalance: less FOUT than swap
optionalInvisible 100ms, fallback forever (font used on NEXT visit)Slow connections, progressive enhancement
autoBrowser decides (usually = block)Never use this

Optimal Font Loading Strategy

<head>
  <!-- 1. Preconnect to font origin -->
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

  <!-- 2. Preload critical font files -->
  <link rel="preload" as="font" type="font/woff2" crossorigin
        href="/fonts/inter-var-latin.woff2">

  <!-- 3. Font-face with swap + subset -->
  <style>
    @font-face {
      font-family: 'Inter';
      src: url('/fonts/inter-var-latin.woff2') format('woff2');
      font-weight: 100 900;
      font-style: normal;
      font-display: swap;
      unicode-range: U+0000-00FF, U+0131, U+0152-0153; /* Latin subset */
    }
  </style>
</head>

Reducing CLS from Font Swap

/* size-adjust: Match fallback font metrics to web font */
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter.woff2') format('woff2');
  font-display: swap;
}

/* Adjusted fallback to prevent layout shift */
@font-face {
  font-family: 'Inter-fallback';
  src: local('Arial');
  size-adjust: 107%;        /* Match web font width */
  ascent-override: 90%;     /* Match ascender height */
  descent-override: 22%;    /* Match descender depth */
  line-gap-override: 0%;    /* Match line gap */
}

body {
  font-family: 'Inter', 'Inter-fallback', sans-serif;
}

/* Tool to generate these values: */
/* https://screenspan.net/fallback */
/* Or: npx @next/font (Next.js automatic font optimization) */

Font Optimization Checklist

  • Self-host fonts — Avoid third-party latency (no extra DNS/TCP/TLS)
  • Use WOFF2 — 30% smaller than WOFF, 50% smaller than TTF
  • Subset fonts — Only include characters you need (Latin, symbols)
  • Variable fonts — Single file for all weights/styles (vs. 6+ separate files)
  • Preload critical fonts — Start download before CSS is parsed
  • Use font-display: swap — Text visible immediately in fallback
  • Limit font families — Each family = additional download
  • Use system fonts where possible — Zero download cost
/* System font stack — instant rendering, no download */
body {
  font-family:
    -apple-system, BlinkMacSystemFont, /* macOS/iOS */
    'Segoe UI',                        /* Windows */
    'Roboto',                          /* Android */
    'Oxygen', 'Ubuntu', 'Cantarell',   /* Linux */
    'Fira Sans', 'Droid Sans',         /* Other */
    'Helvetica Neue', sans-serif;      /* Fallback */
}

Why Code Splitting Matters

Without code splitting:
  main.js = 2MB (entire app in one bundle)
  Parse time (mobile): 5 seconds
  User sees content: NEVER until 2MB downloads + parses + executes

With code splitting:
  main.js = 200KB (core app shell)
  dashboard.js = 300KB (loaded on navigation)
  admin.js = 500KB (loaded only for admin users)
  Parse time for initial load: 500ms
  User sees content: within 1-2 seconds

Types of Code Splitting

StrategyHowWhen It Loads
Route-basedLazy-loaded routesOn navigation to that route
Component-basedDynamic import of componentsWhen component is needed
Library-basedSeparate vendor chunkCached independently, less invalidation
ConditionalLoad polyfills only if neededBased on feature detection
Interaction-basedLoad on user actionOn click, hover, or viewport entry

Angular Lazy Loading (Route-Based)

// app-routing.module.ts
const routes: Routes = [
  {
    path: 'dashboard',
    loadChildren: () => import('./dashboard/dashboard.module')
      .then(m => m.DashboardModule)
    // Creates separate chunk: dashboard-dashboard-module.js
  },
  {
    path: 'admin',
    loadChildren: () => import('./admin/admin.module')
      .then(m => m.AdminModule),
    canActivate: [AdminGuard]
    // Only downloaded if user navigates to /admin
  },
  {
    path: 'reports',
    loadComponent: () => import('./reports/reports.component')
      .then(c => c.ReportsComponent)
    // Standalone component lazy loading (Angular 14+)
  }
];

// Preloading strategies
@NgModule({
  imports: [RouterModule.forRoot(routes, {
    // Load lazy routes in background after initial load
    preloadingStrategy: PreloadAllModules
  })]
})

// Custom preloading (selective)
@Injectable()
export class SelectivePreloadStrategy implements PreloadingStrategy {
  preload(route: Route, load: () => Observable<any>): Observable<any> {
    return route.data?.['preload'] ? load() : of(null);
  }
}

// Route with preload flag:
{ path: 'dashboard', loadChildren: ..., data: { preload: true } }

Component-Level Lazy Loading (Angular 17+ with @defer)

// Angular 17+ @defer blocks — built-in component lazy loading!
@Component({
  template: `
    <!-- Load heavy chart component only when visible -->
    @defer (on viewport) {
      <app-analytics-chart [data]="chartData" />
    } @placeholder {
      <div class="chart-skeleton">Loading chart...</div>
    } @loading (minimum 500ms) {
      <app-spinner />
    } @error {
      <p>Failed to load chart</p>
    }

    <!-- Load on interaction -->
    @defer (on interaction) {
      <app-comment-section />
    } @placeholder {
      <button>Show Comments</button>
    }

    <!-- Load on idle (requestIdleCallback) -->
    @defer (on idle) {
      <app-recommendations />
    }

    <!-- Load on timer -->
    @defer (on timer(3s)) {
      <app-newsletter-popup />
    }

    <!-- Prefetch: start downloading before trigger -->
    @defer (on viewport; prefetch on idle) {
      <app-heavy-widget />
    }
  `
})

4. Tree Shaking & Dead Code Elimination

📺 YouTube Tutorials
  • Tree Shaking Explained — Fireship
  • Webpack Tree Shaking Deep Dive — Sean Larkin (Webpack core)

How Tree Shaking Works

// Tree shaking = remove unused exports from bundles
// Requires: ES Modules (import/export), NOT CommonJS (require)

// math-utils.ts — exported utilities
export function add(a, b) { return a + b; }
export function subtract(a, b) { return a - b; }
export function multiply(a, b) { return a * b; }
export function complexMatrix(m) { /* 500 lines of code */ }

// app.ts — only imports what it needs
import { add, subtract } from './math-utils';
// multiply and complexMatrix are TREE-SHAKEN (removed from bundle)!

// WHY CommonJS can't be tree-shaken:
const utils = require('./math-utils'); // Imports entire module
utils.add(1, 2); // Bundler can't statically analyze which parts are used

Tree Shaking Killers (Anti-Patterns)

// 1. Side effects prevent tree shaking
// polyfills.ts
import 'zone.js';  // Side effect: modifies global scope — can't be removed
import './global-styles.css'; // Side effect: injects CSS

// 2. Barrel files (index.ts) can prevent tree shaking
// components/index.ts
export * from './button';    // If you import ANYTHING from this barrel,
export * from './modal';     // some bundlers may include EVERYTHING
export * from './table';

// FIX: Import directly from the source
import { Button } from './components/button'; // ✓ Tree-shakeable
import { Button } from './components';         // ✗ May pull in modal + table

// 3. Class properties with side effects
class MyService {
  static counter = expensiveInit(); // Side effect in static init
}
// Bundler can't remove MyService even if unused

// 4. Object pattern imports
import * as _ from 'lodash';  // Imports ENTIRE lodash (70KB+)
_.map([1,2], x => x * 2);

// FIX: Named imports from subpaths
import map from 'lodash-es/map';  // Only imports map (~2KB)

Angular-Specific Tree Shaking

// angular.json — production build enables tree shaking automatically
{
  "configurations": {
    "production": {
      "optimization": true,        // Enables tree shaking + minification
      "buildOptimizer": true,      // Angular-specific tree shaking
      "aot": true,                 // Ahead-of-time compilation (smaller bundle)
      "sourceMap": false,          // Removes source maps
      "extractLicenses": true,
      "namedChunks": false
    }
  }
}

// Mark library as side-effect-free for better tree shaking
// package.json of a library:
{
  "sideEffects": false,  // Tell bundler: no side effects, tree-shake freely
  // Or be specific:
  "sideEffects": ["*.css", "./src/polyfills.ts"]
}

// Angular's providedIn: 'root' is tree-shakeable!
@Injectable({ providedIn: 'root' })
export class UserService { }
// If no component injects UserService, it's removed from bundle!

// vs. providing in NgModule (NOT tree-shakeable)
@NgModule({
  providers: [UserService] // Always included even if unused
})

Server Configuration

# Nginx — enable Brotli (preferred) + Gzip (fallback)
# Install: nginx-module-brotli

http {
  # Brotli (static pre-compressed files)
  brotli_static on;

  # Brotli (dynamic compression)
  brotli on;
  brotli_comp_level 6;
  brotli_types text/plain text/css application/javascript
               application/json image/svg+xml;

  # Gzip fallback
  gzip on;
  gzip_comp_level 6;
  gzip_types text/plain text/css application/javascript
             application/json image/svg+xml;
  gzip_min_length 256;
}

# Angular CLI: Pre-compress at build time (best performance)
# angular.json
{
  "configurations": {
    "production": {
      "outputHashing": "all",
      // Generate .br and .gz files at build time
      // Then serve with brotli_static on;
    }
  }
}

What NOT to Compress

  • Already compressed formats: JPEG, PNG, WebP, AVIF, MP4, WOFF2, ZIP
  • Very small files (<150 bytes): Compression overhead exceeds savings
  • Binary data that's already compressed

7. HTTP Caching Deep Dive

Caching Headers Hierarchy

Request arrives → Check Cache-Control:
│
├── no-store: NEVER cache. Always fetch from server.
│   Use for: sensitive data, real-time stock prices
│
├── no-cache: Cache BUT revalidate every time (still saves bandwidth!)
│   Use for: HTML pages (check if content changed)
│
├── max-age=N: Cache for N seconds without revalidating
│   Use for: static assets with content hash
│
├── s-maxage=N: CDN/proxy cache duration (overrides max-age for shared caches)
│   Use for: API responses cached at CDN level
│
├── immutable: Never revalidate (even on reload button!)
│   Use for: hashed assets (main.a1b2c3.js)
│
├── stale-while-revalidate=N: Serve stale, revalidate in background
│   Use for: API data that can be slightly outdated
│
└── stale-if-error=N: Serve stale if origin is down
    Use for: critical content during outages

Optimal Caching Strategy for Angular Apps

# index.html — NEVER cache (user must always get latest version)
Cache-Control: no-cache
# This ensures users get new deployments immediately

# Hashed assets (main.a1b2c3.js, styles.x4y5z6.css) — cache forever
Cache-Control: public, max-age=31536000, immutable
# Hash changes = new URL = new download (cache busting)

# API responses — cache briefly, revalidate
Cache-Control: private, max-age=0, s-maxage=60, stale-while-revalidate=300
# CDN caches 60s, serves stale for 5min while revalidating

# Images (without hash) — cache with revalidation
Cache-Control: public, max-age=86400
ETag: "abc123"
# Cache 1 day, then validate with ETag

# Service Worker precached assets — immutable in SW cache
# (Handled by Angular service worker, not HTTP headers)

ETag & Conditional Requests

# First request:
GET /api/users HTTP/2
→ 200 OK
   ETag: "abc123"
   Cache-Control: no-cache
   Content-Length: 50000

# Subsequent request (revalidation):
GET /api/users HTTP/2
If-None-Match: "abc123"
→ 304 Not Modified (no body! saves bandwidth)
   # Browser uses cached copy

# If content changed:
→ 200 OK
   ETag: "def456"
   # New content sent

# Last-Modified (alternative to ETag):
Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT
→ If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT

How CDNs Improve Performance

Without CDN (origin in US-East):
  User in India → US-East: RTT = 200ms
  TCP handshake: 200ms (1 RTT)
  TLS handshake: 200ms (1 RTT)
  Request + Response: 200ms (1 RTT)
  Total for first byte: 600ms

With CDN (edge in Mumbai):
  User in India → Mumbai edge: RTT = 20ms
  TCP handshake: 20ms
  TLS handshake: 20ms
  Request + Response: 20ms (cache hit!)
  Total for first byte: 60ms = 10x improvement!

CDN Caching Strategy for SPAs

# Typical Angular deployment on CDN:

# index.html: Short TTL, always revalidated
Cache-Control: public, max-age=60, s-maxage=300
# CDN caches 5min, user gets fresh within 1min

# main.abc123.js: Long TTL (fingerprinted)
Cache-Control: public, max-age=31536000, immutable
# CDN caches forever (new hash = new URL on deploy)

# API proxy through CDN:
# CDN edge → origin only when cache misses
# Reduces load on origin servers

# Stale-while-revalidate at CDN level:
Cache-Control: public, max-age=60, stale-while-revalidate=86400
# Serve stale for 24h while fetching fresh in background
# User NEVER waits for origin response!

Edge Computing for SPAs

// Cloudflare Workers / Vercel Edge Functions / AWS Lambda@Edge

// Example: Edge-side rendering of critical data
export default {
  async fetch(request) {
    const url = new URL(request.url);

    if (url.pathname === '/index.html') {
      // Inject critical data at the edge (no client-side fetch needed!)
      const userData = await getFromKV('user-config');
      const html = await getFromCache('index.html');

      return new Response(
        html.replace('', `
          <script>window.__DATA__ = ${JSON.stringify(userData)}</script>
        `),
        { headers: { 'Content-Type': 'text/html' } }
      );
    }

    return fetch(request); // Pass through to origin
  }
};

Loading Strategies for Third-Party Scripts

<!-- 1. WORST: Synchronous (blocks everything) -->
<script src="https://third-party.com/widget.js"></script>

<!-- 2. BETTER: Async (downloads parallel, executes ASAP) -->
<script async src="https://third-party.com/analytics.js"></script>

<!-- 3. GOOD: Defer (executes after DOM parse) -->
<script defer src="https://third-party.com/widget.js"></script>

<!-- 4. BEST: Load after user interaction (facade pattern) -->
<script>
  // Load chat widget only when user clicks chat button
  document.getElementById('chat-btn').addEventListener('click', () => {
    const script = document.createElement('script');
    script.src = 'https://chat-provider.com/widget.js';
    document.head.appendChild(script);
  }, { once: true });
</script>

<!-- 5. BEST: Load on idle -->
<script>
  // Load analytics after everything else is done
  if ('requestIdleCallback' in window) {
    requestIdleCallback(() => {
      loadScript('https://analytics.com/track.js');
    });
  } else {
    setTimeout(() => {
      loadScript('https://analytics.com/track.js');
    }, 3000);
  }
</script>

Facade Pattern (YouTube Embed Example)

<!-- BAD: YouTube embed loads 800KB+ immediately -->
<iframe src="https://youtube.com/embed/..." ...></iframe>

<!-- GOOD: Facade — loads real player only on click -->
<div class="youtube-facade" data-id="VIDEO_ID" onclick="loadYouTube(this)">
  <img src="https://i.ytimg.com/vi/VIDEO_ID/hqdefault.jpg"
       loading="lazy" alt="Video thumbnail">
  <button class="play-btn" aria-label="Play video">▶</button>
</div>

<script>
function loadYouTube(facade) {
  const iframe = document.createElement('iframe');
  iframe.src = `https://youtube.com/embed/${facade.dataset.id}?autoplay=1`;
  iframe.allow = 'autoplay; encrypted-media';
  iframe.allowFullscreen = true;
  facade.replaceWith(iframe);
}
</script>

<!-- Saves: ~800KB JS, 2-3s load time until user wants to watch -->

12. Interview Questions — Phase 3

Beginner Level

  1. Q: What is lazy loading and why is it important?
    A: Lazy loading defers the loading of non-critical resources until they're needed. For images: only download when near viewport. For code: only download modules when user navigates to that route. It reduces initial page load time, saves bandwidth, and improves Core Web Vitals (especially LCP and TBT).
  2. Q: What is the difference between WebP and JPEG?
    A: WebP provides 25-35% smaller file sizes than JPEG at equivalent quality. It supports transparency (like PNG), animation (like GIF), and both lossy and lossless compression. Browser support is 97%+. AVIF is even better (50% smaller) but has less support (92%).
  3. Q: What is code splitting?
    A: Code splitting divides your JavaScript bundle into smaller chunks that load on demand. In Angular, route-based lazy loading creates separate chunks per route module. This means users only download code for features they actually use, reducing initial load time significantly.
  4. Q: Explain Cache-Control: no-cache vs no-store.
    A: no-cache: Response CAN be cached, but must revalidate with server before use (conditional request with ETag). Saves bandwidth if content hasn't changed (304 Not Modified). no-store: Response must NEVER be stored anywhere. Every request fetches fresh from server. Use for sensitive data (banking, medical records).

Intermediate Level

  1. Q: How does tree shaking work and what prevents it?
    A: Tree shaking statically analyzes ES module imports/exports to remove unused code. It works by: (1) Building a dependency graph from import statements, (2) Marking used exports, (3) Removing unmarked (dead) code. Killers: CommonJS require() (not statically analyzable), side effects in modules, barrel files re-exporting everything, dynamic imports with variable paths.
  2. Q: Explain the optimal caching strategy for a Single Page Application.
    A: (1) index.html: no-cache (always revalidate — ensures users get new deployments). (2) Hashed assets (main.abc123.js): max-age=31536000, immutable (cache forever, hash changes on update). (3) API responses: private, max-age=0, stale-while-revalidate=300 (fresh data, with stale fallback). (4) Static images: max-age=86400 with ETag revalidation. This gives instant subsequent loads while ensuring deployments are immediate.
  3. Q: What is the facade pattern for third-party embeds?
    A: Instead of loading heavy third-party embeds immediately (YouTube = 800KB, Google Maps = 600KB), show a lightweight "facade" (thumbnail + play button). Load the real embed only when user interacts. This saves hundreds of KBs on initial load and dramatically improves LCP/TBT for pages with embeds.
  4. Q: How do you determine what to preload vs prefetch vs preconnect?
    A: preconnect: Critical third-party origins (API server, CDN) — saves DNS+TCP+TLS time. preload: Critical resources discovered late by browser (fonts in CSS, images in CSS, above-fold images). prefetch: Resources for probable next navigation (next page's JS chunk). Rule: preload for current page critical path, prefetch for future pages, preconnect for third-party origins.

Advanced Level

  1. Q: Explain the 14KB rule and its significance for web performance.
    A: TCP slow start begins with a congestion window of ~10 packets (~14KB). This means on a new connection, only 14KB can be sent in the first round trip. Significance: (1) Critical CSS + HTML should fit in 14KB for fastest FCP. (2) Inline critical CSS to avoid additional round trips. (3) This is why HTTP/2 server push was valuable — prepush critical resources in the same first flight. (4) Connection reuse (keep-alive) avoids re-entering slow start.
  2. Q: How would you implement a comprehensive image loading strategy for a large e-commerce site?
    A: (1) Format: Serve AVIF → WebP → JPEG using <picture> with <source> elements. (2) Sizing: Generate 4-5 sizes per image, use srcset + sizes for responsive selection. (3) Loading: LCP hero image with fetchpriority="high" + preload. Below-fold with loading="lazy". (4) Placeholder: Use LQIP (Low Quality Image Placeholder) or blurhash. (5) CDN: Image CDN (Cloudinary, imgix) for on-the-fly transformation. (6) Angular: Use NgOptimizedImage directive for automatic best practices. (7) Compression: Quality 75-80 for lossy, AVIF quality 60-65.
  3. Q: Explain stale-while-revalidate and when to use it at CDN level.
    A: stale-while-revalidate allows the CDN to serve a cached (stale) response immediately while fetching a fresh copy from origin in the background. The user gets instant response (from cache), and the next user gets fresh content. Perfect for: API responses that can tolerate slight staleness (product catalogs, user profiles), frequently accessed pages, high-traffic endpoints where origin can't handle every request. Trade-off: User might see data that's seconds/minutes old.
  4. Q: Compare Angular's @defer blocks with route-based lazy loading. When to use each?
    A: Route-based lazy loading: Creates separate chunks per route, loaded on navigation. Best for distinct pages/features. @defer blocks (Angular 17+): Lazy-loads individual components within a page based on triggers (viewport, interaction, idle, timer). Best for: heavy components on a single page (charts, editors, comment sections). Key difference: Route-based is page-level granularity; @defer is component-level. Use both together: lazy routes for pages, @defer for heavy components within those pages.
