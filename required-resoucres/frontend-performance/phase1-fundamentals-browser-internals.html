2. Browser Architecture (Multi-Process)

📺 YouTube Tutorials
  • How Browsers Work — Inside look at modern web browser (Google)
  • Browser Architecture — Life of a Pixel (Chrome University)
  • Multi-Process Architecture in Chrome — Hussein Nasser

Chrome's Multi-Process Architecture

Modern browsers (Chromium-based) use multiple processes for security, stability, and performance:

ProcessResponsibilityCount
Browser ProcessUI (address bar, bookmarks), network requests, storage access, coordinating other processes1
Renderer ProcessParsing HTML/CSS, executing JS, painting — one per tab (site isolation)Multiple
GPU ProcessHandles GPU tasks for all tabs (compositing, WebGL, video decoding)1
Plugin ProcessRuns browser plugins (Flash-era, mostly deprecated)Per plugin
Utility ProcessNetwork service, audio service, storage serviceMultiple

Inside the Renderer Process — Threads

ThreadResponsibility
Main ThreadDOM parsing, CSS computation, JS execution, Layout, Paint — SINGLE THREADED!
Compositor ThreadComposites layers, handles scroll & zoom (can work without main thread)
Raster ThreadsConvert paint records into bitmaps (GPU rasterization)
Worker ThreadsWeb Workers, Service Workers (separate from main thread)
Key Insight: JavaScript execution, DOM manipulation, style calculations, and layout ALL happen on the same main thread. This is WHY heavy JS blocks rendering. Understanding this single fact explains most performance problems.

Site Isolation (Security + Performance)

Since Chrome 67, each site gets its own renderer process. This means:

  • A heavy tab cannot freeze other tabs
  • Spectre/Meltdown attacks are mitigated
  • Cross-origin iframes get separate processes
  • Trade-off: More memory usage (~100-150MB per process)

3. Navigation: DNS → TCP → TLS → HTTP

📺 YouTube Tutorials
  • DNS Resolution Explained — ByteByteGo
  • TCP 3-Way Handshake — Sunny Classroom
  • TLS Handshake Explained — Computerphile
  • What happens when you type a URL — Alex Xu (ByteByteGo)

When a user types a URL and presses Enter, here's the complete journey:

Step 1: URL Parsing & HSTS Check

  • Browser parses the URL (scheme, host, port, path)
  • Checks HSTS (HTTP Strict Transport Security) preload list
  • If HTTP and in HSTS list → automatically upgrades to HTTPS (307 internal redirect)

Step 2: DNS Resolution (~20-120ms)

Domain Name System translates human-readable domain to IP address:

Browser Cache → OS Cache → Router Cache → ISP DNS → Root DNS → TLD DNS → Authoritative DNS

Example: www.kyndryl.com
1. Browser DNS cache (chrome://net-internals/#dns)
2. OS resolver cache (macOS: scutil --dns)
3. Router cache
4. ISP recursive resolver
5. Root nameserver → "Go ask .com TLD"
6. .com TLD nameserver → "Go ask ns1.kyndryl.com"
7. Authoritative nameserver → "IP is 104.18.x.x"

DNS Optimization Techniques

  • <link rel="dns-prefetch" href="//api.example.com"> — Resolves DNS early
  • <link rel="preconnect" href="https://api.example.com"> — DNS + TCP + TLS early
  • Reduce DNS lookups by minimizing third-party domains
  • Use DNS over HTTPS (DoH) for privacy and sometimes speed

Step 3: TCP Three-Way Handshake (~1 RTT = 20-100ms)

Client → Server:  SYN (sequence number = x)
Server → Client:  SYN-ACK (seq = y, ack = x+1)
Client → Server:  ACK (seq = x+1, ack = y+1)

Total: 1 Round Trip Time (RTT)

TCP Optimization: Connection Reuse

  • Keep-Alive (HTTP/1.1 default): Reuse TCP connection for multiple requests
  • HTTP/2 multiplexing: Single TCP connection, multiple streams in parallel
  • TCP Fast Open (TFO): Send data in SYN packet (saves 1 RTT on repeat visits)

Step 4: TLS Handshake (~1-2 RTT = 40-200ms)

TLS 1.2 (2 RTT):
Client → Server:  ClientHello (supported ciphers, random)
Server → Client:  ServerHello + Certificate + ServerHelloDone
Client → Server:  ClientKeyExchange + ChangeCipherSpec + Finished
Server → Client:  ChangeCipherSpec + Finished

TLS 1.3 (1 RTT — modern):
Client → Server:  ClientHello + KeyShare
Server → Client:  ServerHello + KeyShare + {Certificate} + Finished
Client → Server:  Finished

TLS 1.3 0-RTT (resumption):
Client sends early data with PSK (pre-shared key from previous session)
Performance Tip: TLS 1.3 saves a full RTT compared to TLS 1.2. For users 200ms away (mobile in India), this is a 200ms improvement on every new connection.

Step 5: HTTP Request/Response

GET /index.html HTTP/2
Host: www.kyndryl.com
Accept: text/html
Accept-Encoding: gzip, br, zstd

HTTP/2 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Content-Length: 45230
Cache-Control: public, max-age=31536000, immutable

HTTP/2 vs HTTP/1.1 vs HTTP/3

FeatureHTTP/1.1HTTP/2HTTP/3
MultiplexingNo (6 connections max)Yes (single TCP connection)Yes (QUIC/UDP)
Header CompressionNoHPACKQPACK
Server PushNoYes (deprecated)No
Head-of-Line BlockingYes (per connection)Yes (TCP level)No (per stream)
TransportTCPTCPQUIC (UDP)
0-RTT ConnectionNoNoYes

Complete Timeline Example

t=0ms     URL entered
t=2ms     HSTS check, URL parsed
t=22ms    DNS resolved (cached: 0ms, cold: 50-200ms)
t=52ms    TCP handshake complete (+1 RTT = 30ms)
t=82ms    TLS 1.3 handshake complete (+1 RTT = 30ms)
t=85ms    HTTP GET sent

t=146ms   HTML parsing begins → triggers more resource requests

4. Critical Rendering Path (CRP)

📺 YouTube Tutorials
  • Critical Rendering Path — Google Chrome Developers
  • How the Browser Renders a Web Page — Traversy Media
  • Browser Rendering Optimization — Udacity (Google)

The Critical Rendering Path is the sequence of steps the browser takes to convert HTML, CSS, and JavaScript into pixels on the screen.

The 5 Steps of CRP

HTML → DOM → CSSOM → Render Tree → Layout → Paint → Composite
         ↑                ↑
         |                |
    JavaScript        JavaScript
   (can modify)     (can modify)
  1. DOM Construction — Parse HTML bytes → Characters → Tokens → Nodes → DOM Tree
  2. CSSOM Construction — Parse CSS bytes → Characters → Tokens → Nodes → CSSOM Tree
  3. Render Tree — Combine DOM + CSSOM (only visible elements)
  4. Layout (Reflow) — Calculate exact position and size of each element
  5. Paint — Fill in pixels (text, colors, images, borders, shadows)
  6. Composite — Draw layers in correct order on GPU

Render-Blocking Resources

These BLOCK the Critical Rendering Path:

ResourceBlocksWhy
CSS (all)RenderBrowser won't paint until CSSOM is complete (avoid FOUC)
JS (without async/defer)DOM parsingParser stops to download + execute JS
JS (async)DOM parsing brieflyDownloads async, but executes immediately (pauses parser)
JS (defer)NothingDownloads async, executes after DOM is parsed
FontsText renderText invisible until font loads (FOIT)

Script Loading Strategies

<!-- Parser-blocking: stops parsing until downloaded AND executed -->
<script src="app.js"></script>

<!-- Async: download in parallel, execute ASAP (blocks parser during execution) -->
<script async src="analytics.js"></script>

<!-- Defer: download in parallel, execute AFTER DOM parsed (in order) -->
<script defer src="app.js"></script>

<!-- Module: deferred by default -->
<script type="module" src="app.mjs"></script>
Best Practice: Use defer for your main application bundle. Use async only for independent scripts that don't depend on DOM (analytics, ads). Never put <script> in <head> without async/defer.

Optimizing the Critical Rendering Path

  1. Minimize critical resources — Reduce number of render-blocking CSS/JS files
  2. Minimize critical bytes — Compress, minify, reduce CSS/JS size
  3. Minimize critical path length — Reduce round trips (inline critical CSS)
  4. Defer non-critical CSS — Use media attribute or load async
  5. Inline critical CSS — First 14KB of HTML should contain above-the-fold styles

Critical CSS Inlining Example

<head>
  <!-- Critical CSS inlined -->
  <style>
    body { font-family: sans-serif; margin: 0; }
    .header { background: #1a1a2e; color: white; padding: 16px; }
    .hero { min-height: 400px; display: flex; align-items: center; }
  </style>

  <!-- Non-critical CSS loaded async -->
  <link rel="preload" href="styles.css" as="style" onload="this.onload=null;this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="styles.css"></noscript>
</head>

5. HTML Parsing & DOM Construction

📺 YouTube Tutorials
  • HTML Parser & DOM Tree — Web Dev Simplified
  • How the DOM is Built — Google Chrome Developers

The Parsing Pipeline

Bytes (from network)
  → Characters (via encoding, e.g., UTF-8)
    → Tokens (via tokenizer: StartTag, EndTag, Character, Comment)
      → Nodes (via tree construction algorithm)
        → DOM Tree (in memory)

Speculative Parsing (Preload Scanner)

When the main parser is blocked (e.g., by a synchronous script), the browser uses a preload scanner to look ahead and find resources to fetch:

  • Scans ahead for <img>, <link>, <script> tags
  • Initiates downloads in parallel while main parser is blocked
  • Does NOT build DOM — only fetches resources
  • This is why you should use standard HTML tags — the preload scanner can't parse JS-generated URLs
Anti-pattern: Dynamically injecting scripts via JS defeats the preload scanner. The browser won't discover these resources until JS executes. 
// BAD: Invisible to preload scanner
const script = document.createElement('script');
script.src = 'important-lib.js';
document.head.appendChild(script);

// GOOD: Visible to preload scanner
// <script defer src="important-lib.js"></script>

DOM Tree Size Impact

DOM NodesImpact
<800Excellent — fast style recalculation, layout, paint
800–1,500Good — typical for well-structured pages
1,500–3,000Warning — style recalculation becoming expensive
>3,000Critical — significant performance issues, especially on mobile

Why Large DOM is Slow

  • Style Recalculation: Browser must check every CSS rule against every DOM node
  • Layout: More nodes = more geometry calculations
  • Memory: Each node ≈ 0.5-1KB in memory
  • querySelector: Slower traversal with more nodes
  • GC Pressure: More objects for garbage collector to track

6. CSSOM Construction

📺 YouTube Tutorials
  • CSSOM & Render-Blocking CSS — Google Chrome Developers
  • CSS Containment & Performance — Una Kravets (Chrome)

Why CSS is Render-Blocking

The browser MUST construct the complete CSSOM before painting anything because:

  • CSS rules cascade — later rules override earlier ones
  • A rule at the end of CSS could change everything above
  • Without complete CSSOM, the browser might show wrong styles (Flash of Unstyled Content - FOUC)

CSS Specificity Calculation Performance

Selector matching is RIGHT to LEFT:

/* Browser reads: find all <a> → filter those inside .nav → filter inside .header */
.header .nav a { color: blue; }

/* More efficient selectors */
.nav-link { color: blue; }  /* Direct class — O(1) lookup */

Selector Performance (Fastest → Slowest)

  1. #id — Hash map lookup, O(1)
  2. .class — Hash map lookup, O(1)
  3. tag — Hash map lookup, O(1)
  4. .parent .child — Requires ancestor traversal
  5. .parent > .child — Only checks immediate parent (better than descendant)
  6. * — Matches everything (avoid)
  7. [attr=value] — Attribute lookup
  8. :nth-child() — Requires counting siblings
Modern Reality: CSS selector performance rarely matters unless you have 10,000+ nodes AND complex selectors. Focus on reducing CSS size and avoiding forced reflows instead.

CSS Containment

contain property tells browser what optimizations it can make:

.card {
  contain: layout;     /* Layout of this element is independent of the rest */
  contain: paint;      /* Descendants won't paint outside this box */
  contain: size;       /* Element's size is independent of children */
  contain: style;      /* Counters/quotes scoped to this subtree */
  contain: content;    /* = layout + paint + style (most common) */
  contain: strict;     /* = layout + paint + size + style (strongest) */
}

/* content-visibility: auto — HUGE performance win for off-screen content */
.below-fold-section {
  content-visibility: auto;
  contain-intrinsic-size: 0 500px; /* Estimated height for layout stability */
}

7. Render Tree, Layout & Paint

📺 YouTube Tutorials
  • Layout & Reflow — Chrome DevTools (Paul Irish)
  • Rendering Performance — Google Chrome Developers

Render Tree Construction

The Render Tree combines DOM + CSSOM, containing ONLY visible elements:

  • display: none → NOT in render tree (no layout, no paint)
  • visibility: hidden → IN render tree (takes space, no paint)
  • opacity: 0 → IN render tree (takes space, composited layer)
  • <head>, <script>, <meta> → NOT in render tree
  • Pseudo-elements (::before, ::after) → IN render tree

Layout (Reflow) — The Expensive Step

Layout calculates the exact position and size of every element in the render tree.

What Triggers Layout

  • First page load (initial layout)
  • Window resize
  • DOM changes (add/remove nodes)
  • CSS changes that affect geometry (width, height, margin, padding, position, font-size)
  • Reading layout properties (getBoundingClientRect, offsetWidth, scrollTop)
  • Content changes (text, images loading)

Layout Thrashing (Forced Synchronous Layout)

// BAD: Layout thrashing — read/write/read/write pattern
for (let i = 0; i < elements.length; i++) {
  const height = elements[i].offsetHeight;     // READ → forces layout
  elements[i].style.height = height + 10 + 'px'; // WRITE → invalidates layout
}
// Result: N forced layouts in a single frame!

// GOOD: Batch reads, then batch writes
const heights = elements.map(el => el.offsetHeight); // All reads first
elements.forEach((el, i) => {
  el.style.height = heights[i] + 10 + 'px';        // All writes after
});
// Result: Only 1 forced layout + 1 recalculation

Paint — Filling Pixels

Paint converts the render tree into actual pixels. Two types:

  • Full Paint: Repaint the entire page (expensive, rare after initial load)
  • Incremental Paint: Only repaint "dirty" rectangles (regions that changed)

Properties That Trigger Only Paint (No Layout)

/* These cause REPAINT only (cheaper than reflow) */
color, background-color, background-image,
border-color, border-style, border-radius,
outline, visibility, box-shadow, text-decoration,
filter (some), opacity (if not on own layer)

Properties That Trigger Layout + Paint (Expensive)

/* These cause REFLOW + REPAINT (expensive!) */
width, height, min-*, max-*,
margin, padding, border-width,
position, top, left, right, bottom,
display, float, clear,
font-size, font-family, font-weight,
line-height, text-align, vertical-align,
overflow, white-space

8. Compositing & GPU Acceleration

📺 YouTube Tutorials
  • GPU Compositing & Layers — Surma (Chrome DevRel)
  • Compositing in Blink & Chrome — Chrome University

Layer Promotion

The browser promotes elements to their own compositor layers when:

  • Element has transform: translateZ(0) or will-change: transform
  • Element has opacity less than 1 with animation
  • Element has position: fixed
  • Element overlaps another composited layer
  • Element has hardware-accelerated CSS (3D transforms, filters)

The Compositor's Advantage

Without Compositing (everything on main thread):
  JS → Style → Layout → Paint → Display
  [-------- ALL ON MAIN THREAD --------]

With Compositing (GPU layers):
  JS → Style → Composite → Display
  [main]        [compositor thread — no main thread needed!]

Properties Handled by Compositor ONLY (Cheapest)

/* These ONLY trigger COMPOSITE — no layout, no paint! */
transform (translate, scale, rotate, skew)
opacity
filter (on promoted layer)
The Golden Rule of 60fps Animations:
Only animate transform and opacity. These run on the compositor thread and don't touch the main thread at all. This means animations stay smooth even if JS is busy.

will-change Property

/* Hint to browser: "I'm going to animate this" */
.animated-element {
  will-change: transform, opacity;
}

/* Use sparingly! Each layer = GPU memory */
/* Remove after animation completes */
element.addEventListener('transitionend', () => {
  element.style.willChange = 'auto';
});
Warning: Don't apply will-change to everything! Each composited layer uses GPU memory (mobile GPUs have limited VRAM). Too many layers = "layer explosion" = worse performance.

9. Core Web Vitals (LCP, INP, CLS)

📺 YouTube Tutorials
  • Core Web Vitals — Google Chrome Developers
  • INP Explained — web.dev
  • Optimize LCP — Google I/O
  • Fix CLS Issues — web.dev (Annie Sullivan)

Core Web Vitals are Google's official metrics for user experience, directly impacting SEO rankings.

LCP — Largest Contentful Paint

What it measures: Time until the largest visible content element finishes rendering.

ScoreThresholdRating
Good≤ 2.5 seconds🟢
Needs Improvement2.5 – 4.0 seconds🟡
Poor> 4.0 seconds🔴

What counts as LCP element?

  • <img> elements
  • <image> inside SVG
  • <video> poster image
  • Background image via url() (on block-level elements)
  • Block-level text elements (<h1>, <p>, etc.)

How to Optimize LCP

  1. Eliminate render-blocking resources — Defer non-critical CSS/JS
  2. Optimize server response time — CDN, caching, server-side rendering
  3. Preload LCP resource — <link rel="preload" as="image" href="hero.webp">
  4. Optimize image size — Serve right size, use modern formats (WebP, AVIF)
  5. Reduce client-side rendering — SSR or pre-rendering for content-heavy pages
  6. Avoid lazy-loading LCP image — Above-fold images should load eagerly
<!-- Preload the LCP image -->
<link rel="preload" as="image" href="hero-banner.webp"
      fetchpriority="high"
      type="image/webp">

<!-- fetchpriority attribute -->
<img src="hero-banner.webp" fetchpriority="high" alt="Hero">
<img src="below-fold.webp" loading="lazy" fetchpriority="low" alt="...">

INP — Interaction to Next Paint (Replaced FID in March 2024)

What it measures: The latency of ALL interactions throughout the page lifecycle, reported as the worst interaction (at the 98th percentile).

ScoreThresholdRating
Good≤ 200ms🟢
Needs Improvement200 – 500ms🟡
Poor> 500ms🔴

INP Breakdown

User clicks button
  |
  ├── Input Delay (time waiting for main thread to be free)
  │     └── Caused by: long tasks, heavy JS, event handlers from other interactions
  │
  ├── Processing Time (time running event handlers)
  │     └── Caused by: complex logic in handlers, synchronous operations
  │
  └── Presentation Delay (time for browser to render the update)
        └── Caused by: large DOM updates, forced reflows, expensive paint
  |
Next frame painted → User sees response

How to Optimize INP

  1. Break long tasks — Use scheduler.yield() or setTimeout(0)
  2. Reduce input delay — Minimize third-party scripts blocking main thread
  3. Debounce expensive handlers — Don't recalculate on every keystroke
  4. Use requestAnimationFrame — Batch DOM updates to next frame
  5. Virtualize long lists — Don't render 10,000 DOM nodes
  6. Use CSS containment — Limit style/layout recalculation scope
// Breaking long tasks with scheduler.yield()
async function processLargeData(items) {
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);

    // Yield to main thread every 5 items
    if (i % 5 === 0) {
      await scheduler.yield(); // Let browser handle pending interactions
    }
  }
}

// Fallback for browsers without scheduler.yield()
function yieldToMain() {
  return new Promise(resolve => setTimeout(resolve, 0));
}

CLS — Cumulative Layout Shift

What it measures: Sum of all unexpected layout shifts during the page lifecycle.

ScoreThresholdRating
Good≤ 0.1🟢
Needs Improvement0.1 – 0.25🟡
Poor> 0.25🔴

CLS Calculation Formula

Layout Shift Score = Impact Fraction × Distance Fraction

Impact Fraction = % of viewport affected by the shift
Distance Fraction = how far the elements moved (as % of viewport)

Example: An element covering 50% viewport moves 25% down
Score = 0.5 × 0.25 = 0.125

Common CLS Causes & Fixes

CauseFix
Images without dimensionsAlways set width/height or use aspect-ratio
Ads/embeds without reserved spaceUse min-height on containers
Dynamically injected contentReserve space with skeleton screens
Web fonts causing FOIT/FOUTUse font-display: swap + size-adjust
Late-loading CSS changing layoutInline critical CSS, preload rest
<!-- Always specify dimensions -->
<img src="photo.webp" width="800" height="600" alt="...">

<!-- Or use aspect-ratio in CSS -->
<style>
  .responsive-img {
    width: 100%;
    aspect-ratio: 16 / 9;
    object-fit: cover;
  }
</style>

<!-- Reserve space for dynamic content -->
<div class="ad-slot" style="min-height: 250px;">
  <!-- Ad loads here -->
</div>

Long Tasks

A Long Task is any task on the main thread that takes >50ms. During a long task:

  • The page feels frozen/unresponsive
  • User interactions are delayed
  • Animations jank
  • The browser can't paint new frames
// Detect Long Tasks with PerformanceObserver
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.warn('Long Task detected:', {
      duration: entry.duration,
      startTime: entry.startTime,
      name: entry.name
    });
  }
});
observer.observe({ type: 'longtask', buffered: true });

13. Interview Questions — Phase 1

Beginner Level

  1. Q: What is the Critical Rendering Path?
    A: The CRP is the sequence of steps the browser takes to convert HTML, CSS, and JavaScript into pixels on screen: DOM construction → CSSOM construction → Render Tree → Layout → Paint → Composite.
  2. Q: What is the difference between async and defer in script tags?
    A: Both download scripts asynchronously. async executes immediately upon download (pauses HTML parsing), with no guaranteed order. defer waits until HTML parsing is complete, then executes in document order. Use defer for app scripts, async for independent analytics scripts.
  3. Q: What are Core Web Vitals?
    A: Google's three key metrics for user experience: LCP (loading performance, ≤2.5s), INP (interactivity, ≤200ms), and CLS (visual stability, ≤0.1). They directly impact SEO rankings.
  4. Q: Why is CSS render-blocking?
    A: CSS is render-blocking because the browser must construct the complete CSSOM before painting. Without it, the page might flash with wrong/no styles (FOUC). CSS rules cascade, so the browser can't safely paint until all CSS is parsed.
  5. Q: What is TTFB?
    A: Time to First Byte — the time from the browser making an HTTP request to receiving the first byte of the response. It includes DNS resolution, TCP connection, TLS handshake, and server processing time. Good TTFB is ≤800ms.

Intermediate Level

  1. Q: Explain the difference between reflow, repaint, and composite.
    A: Reflow (Layout): Recalculates geometry of elements (position, size) — most expensive. Repaint: Fills in pixels for visual changes (color, background) without geometry change. Composite: Draws pre-painted layers together — cheapest, runs on GPU. Changing width triggers all three; changing color triggers repaint + composite; changing transform triggers only composite.
  2. Q: What is layout thrashing and how do you fix it?
    A: Layout thrashing occurs when you alternate between reading layout properties (offsetWidth, getBoundingClientRect) and writing style changes in a loop. Each read forces the browser to synchronously recalculate layout. Fix: Batch all reads first, then batch all writes. Or use requestAnimationFrame to schedule writes.
  3. Q: How does HTTP/2 improve performance over HTTP/1.1?
    A: HTTP/2 provides: (1) Multiplexing — multiple requests over single TCP connection instead of 6 parallel connections, (2) Header compression (HPACK), (3) Stream prioritization, (4) Server push (deprecated). Main limitation: TCP-level head-of-line blocking, solved by HTTP/3 (QUIC/UDP).
  4. Q: What is the preload scanner and why does it matter?
    A: The preload scanner is a secondary parser that runs when the main HTML parser is blocked (by synchronous JS). It looks ahead in the HTML for resource URLs (img, link, script) and initiates downloads early. It's why we should use standard HTML elements for resources instead of dynamically creating them in JS.
  5. Q: Explain dns-prefetch vs preconnect vs preload vs prefetch.
    A: dns-prefetch: Resolve DNS only. preconnect: DNS + TCP + TLS (full connection setup). preload: Download resource needed for current page with high priority. prefetch: Download resource for future navigation with low priority. Use preconnect for critical third-party origins, preload for critical above-fold resources.

Advanced Level

  1. Q: How does the browser decide which elements get their own compositor layer?
    A: Browsers promote elements to compositor layers when they have: 3D transforms, will-change: transform/opacity, animated opacity/transform, position: fixed, hardware-accelerated filters, or overlap with another composited layer (overlap promotion). Each layer uses GPU memory, so excessive promotion causes "layer explosion" and hurts performance.
  2. Q: Explain INP in detail — how is it different from FID?
    A: FID measured only the input delay of the FIRST interaction. INP measures the full latency (input delay + processing time + presentation delay) of ALL interactions throughout the page lifetime, reporting the worst at the 98th percentile. INP is a better measure because: (1) it covers all interactions not just the first, (2) it includes processing + render time not just input delay, (3) it reflects real user experience across the entire session.
  3. Q: What is content-visibility: auto and how does it improve performance?
    A: content-visibility: auto tells the browser to skip rendering (style, layout, paint) of off-screen elements until they're near the viewport. It's like built-in virtualization. Combined with contain-intrinsic-size (to maintain scroll height), it can reduce initial rendering time by 50%+ for long pages. The browser still creates the DOM but skips the rendering pipeline for off-screen sections.
  4. Q: Explain the TCP slow start and its impact on web performance.
    A: TCP slow start is a congestion control mechanism where the initial congestion window (cwnd) starts small (typically 10 segments = ~14KB) and doubles with each ACK. This means on a cold connection, you can only send 14KB in the first round trip. This is why: (1) critical CSS should fit in ~14KB, (2) connection reuse (keep-alive, HTTP/2) is important, (3) CDNs help by being physically closer (smaller RTT). After ~4 RTTs, the connection reaches full speed.
  5. Q: How would you investigate a performance regression in production?
    A: (1) Check Real User Monitoring (RUM) data for specific metrics degradation (LCP, INP, CLS). (2) Correlate with deployment timeline. (3) Segment by device, geography, connection type. (4) Use Chrome UX Report (CrUX) for field data. (5) Reproduce in lab with DevTools Performance panel + CPU/network throttling. (6) Use PerformanceObserver to instrument specific events. (7) Check for regressions in bundle size (source maps), third-party scripts, or server TTFB.

Tricky/Gotcha Questions

  1. Q: Does display: none prevent an image from downloading?
    A: NO! The image still downloads. display: none only removes the element from the render tree (no layout/paint), but the browser still fetches the resource. To prevent download, use loading="lazy" or conditionally inject the <img> element via JS.
  2. Q: Does moving CSS to the bottom of the page help?
    A: NO! Unlike JS, CSS position in the document doesn't change its render-blocking behavior. The browser won't paint ANYTHING until all CSS is parsed (regardless of position). Worse — putting CSS at the bottom can cause FOUC in some browsers. Always keep CSS in <head>.
  3. Q: Can JavaScript affect CSSOM construction?
    A: YES! If a <script> tag appears after a <link rel="stylesheet">, the browser must wait for CSS to download before executing the script (because JS might query computed styles). This means CSS indirectly blocks JS, and JS blocks DOM parsing — creating a chain of blocking.
