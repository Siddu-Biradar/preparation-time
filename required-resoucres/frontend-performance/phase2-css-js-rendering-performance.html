CSS File Optimization

1.1 Unused CSS Removal

Typical websites ship 60-90% unused CSS. Every byte of unused CSS:

  • Increases download time
  • Increases CSSOM construction time (parser still processes every rule)
  • Delays First Contentful Paint

CSS Animations vs JavaScript Animations

/* CSS Animation — runs on compositor thread (smooth!) */
.slide-in {
  animation: slideIn 300ms ease-out forwards;
}
@keyframes slideIn {
  from { transform: translateX(-100%); opacity: 0; }
  to   { transform: translateX(0); opacity: 1; }
}

/* CSS Transition — also compositor-friendly */
.card {
  transition: transform 200ms ease, opacity 200ms ease;
}
.card:hover {
  transform: scale(1.05);
  opacity: 0.9;
}
Rule: CSS animations using only transform and opacity are promoted to the compositor thread and run at 60fps even when the main thread is busy. JS animations using the Web Animations API can also be compositor-promoted for these properties.

CSS Containment & content-visibility (Advanced)

/* contain: tells browser what it can optimize */
.independent-widget {
  contain: layout style paint;
  /* Browser knows:
     - Layout of this element won't affect rest of page
     - Styles are scoped (counters, quotes)
     - Nothing paints outside this box */
}

/* content-visibility: auto — SKIP rendering for off-screen elements */
.page-section {
  content-visibility: auto;
  contain-intrinsic-size: 0 500px; /* Placeholder height for scroll */
}

/* Performance impact on a page with 20 sections:
   Without content-visibility: Render all 20 sections (~200ms)
   With content-visibility: Render only 3 visible sections (~30ms)
   = 85% reduction in initial rendering time */

V8 Engine Pipeline (Chrome/Node.js)

Source Code (JavaScript/TypeScript transpiled)
  │
  ├── Parser → AST (Abstract Syntax Tree)
  │     ├── Pre-parser (lazy parsing for unused functions)
  │     └── Full parser (for immediately invoked code)
  │
  ├── Ignition (Interpreter) → Bytecode
  │     └── Fast startup, slower execution
  │
  ├── Sparkplug (Baseline Compiler) → Slightly optimized machine code
  │     └── Quick compile, modest speedup
  │
  ├── Maglev (Mid-tier Compiler) → Better optimized code
  │     └── Moderate compile time, good performance
  │
  └── TurboFan (Optimizing Compiler) → Highly optimized machine code
        ├── Uses type feedback from Ignition
        ├── Speculative optimizations (assumes types stay same)
        └── Deoptimization if assumptions break!

Why This Matters for Performance

  • Monomorphic code is fastest: Functions called with same argument types get optimized
  • Megamorphic code is slowest: Functions called with many different types cause deoptimization
  • Hidden Classes: Objects with same property order share hidden class (fast property access)
  • Inline Caches: Repeated property access at same site gets cached
// GOOD: Monomorphic — always same shape
function process(point) {
  return point.x + point.y;
}
process({ x: 1, y: 2 });  // Shape A
process({ x: 3, y: 4 });  // Shape A (same!)
// V8 creates an inline cache for this shape → FAST

// BAD: Megamorphic — different shapes
process({ x: 1, y: 2 });        // Shape A
process({ x: 1, y: 2, z: 3 }); // Shape B
process({ y: 2, x: 1 });        // Shape C (different order!)
process({ x: "1", y: "2" });    // Shape D (different types!)
// V8 gives up on inline caching → SLOW (generic lookup)

Hidden Classes (Shapes/Maps)

// GOOD: Always add properties in the same order
class Point {
  constructor(x, y) {
    this.x = x;  // Hidden class C0 → C1
    this.y = y;  // Hidden class C1 → C2
  }
}
const p1 = new Point(1, 2); // Shape: {x, y}
const p2 = new Point(3, 4); // Same shape! Shares hidden class

// BAD: Adding properties in different orders
const obj1 = {}; obj1.a = 1; obj1.b = 2; // Shape: a→b
const obj2 = {}; obj2.b = 2; obj2.a = 1; // Shape: b→a (DIFFERENT!)
// These have different hidden classes → can't share optimized code

// BAD: Adding properties after construction
const obj3 = { a: 1, b: 2 };
obj3.c = 3;  // Transitions to new hidden class!
// Every dynamic property addition = new hidden class = deoptimization risk

JavaScript Parsing Cost

Parsing JS is expensive — roughly 1MB of JS = 100ms parse time on mobile:

Bundle Size (gzipped)Parse Time (mobile)Parse Time (desktop)
100KB~250ms~50ms
200KB~500ms~100ms
500KB~1.2s~250ms
1MB~2.5s~500ms
Real Impact: A typical Angular app ships 300-500KB (gzipped) of JavaScript. On a mid-range mobile phone (Moto G Power), that's 750ms–1.2s just for parsing, BEFORE any execution. This is why code splitting and lazy loading are critical.

The Complete Event Loop Cycle

┌─────────────────────────────────────────────────┐
│                  EVENT LOOP                       │
│                                                   │
│  1. Pick oldest task from Task Queue              │
│     (setTimeout, setInterval, I/O, UI events)     │
│                                                   │
│  2. Execute task to completion                    │
│     (cannot be interrupted!)                      │
│                                                   │
│  3. Execute ALL microtasks                        │
│     (Promise.then, queueMicrotask,                │
│      MutationObserver, async/await continuations)  │
│     ↳ If microtask adds more microtasks,          │
│       keep draining until empty!                   │
│                                                   │
│  4. If it's time for rendering (~16.6ms):         │
│     a. Run requestAnimationFrame callbacks        │
│     b. Style recalculation                        │
│     c. Layout                                     │
│     d. Paint                                      │
│     e. Composite                                  │
│                                                   │
│  5. If idle: run requestIdleCallback              │
│                                                   │
│  6. Go to step 1                                  │
└─────────────────────────────────────────────────┘

Task Queue Priority

QueuePriorityExamples
MicrotasksHighest (drains completely)Promise.then, queueMicrotask, MutationObserver
User InteractionHighclick, keydown, input events
Animation (rAF)Before renderrequestAnimationFrame callbacks
TimerNormalsetTimeout, setInterval
IdleLowestrequestIdleCallback

Performance Implications

// DANGER: Microtask starvation — blocks rendering
async function starveMainThread() {
  for (let i = 0; i < 1000000; i++) {
    await Promise.resolve(); // Each creates a microtask
    // Microtasks drain BEFORE rendering!
    // Page is frozen for this entire loop
  }
}

// SOLUTION: Yield to macro-task queue periodically
async function cooperativeWork() {
  for (let i = 0; i < 1000000; i++) {
    doWork(i);
    if (i % 1000 === 0) {
      // Yield to main thread — allows rendering + user input
      await new Promise(resolve => setTimeout(resolve, 0));
    }
  }
}

// MODERN: scheduler.yield() (Chrome 115+)
async function modernCooperativeWork() {
  for (let i = 0; i < 1000000; i++) {
    doWork(i);
    if (i % 1000 === 0) {
      await scheduler.yield(); // Yields but keeps priority
    }
  }
}

Execution Order Quiz (Interview Favorite!)

console.log('1. Script start');

setTimeout(() => console.log('2. setTimeout'), 0);

Promise.resolve().then(() => {
  console.log('3. Promise 1');
}).then(() => {
  console.log('4. Promise 2');

// 7. Script end

// 6. queueMicrotask  (microtask)

4. Memory Management & Garbage Collection

📺 YouTube Tutorials
  • JavaScript Memory Management — Google Chrome Developers
  • Garbage Collection in V8 — Peter Marshall (V8 team)

JavaScript Memory Model

┌────────────────────────────────────────────────────┐
│                    V8 HEAP                          │
├────────────────────────────────────────────────────┤
│  Young Generation (New Space) — 1-8MB              │
│  ├── Semi-space A (active)                         │
│  └── Semi-space B (inactive/swap)                  │
│  GC: Scavenge (Minor GC) — fast, frequent          │
│       Copies surviving objects to other semi-space  │
├────────────────────────────────────────────────────┤
│  Old Generation (Old Space) — up to 1.5GB          │
│  ├── Old Pointer Space (objects with references)   │
│  └── Old Data Space (objects without references)   │
│  GC: Mark-Sweep-Compact (Major GC) — slow, rare   │
│       Marks reachable objects, sweeps unreachable   │
├────────────────────────────────────────────────────┤
│  Large Object Space (>256KB objects)               │
│  Code Space (compiled code)                        │
│  Map Space (hidden classes)                        │
└────────────────────────────────────────────────────┘

GC Impact on Performance

  • Minor GC (Scavenge): 1-10ms, frequent — causes micro-jank
  • Major GC (Mark-Sweep): 50-200ms, rare — causes visible jank/freeze
  • Incremental GC: Splits Major GC into chunks to reduce pauses
  • Concurrent GC: Runs GC on background thread (V8's Orinoco)

Reducing GC Pressure

// BAD: Creates new object every frame → GC pressure
function animate() {
  const position = { x: element.offsetLeft, y: element.offsetTop }; // NEW object!
  // ... use position ...
  requestAnimationFrame(animate);
}

// GOOD: Reuse object (object pooling)
const position = { x: 0, y: 0 }; // Allocated once
function animate() {
  position.x = element.offsetLeft;
  position.y = element.offsetTop;
  // ... use position ...
  requestAnimationFrame(animate);
}

// BAD: String concatenation in hot path
function buildMessage(items) {
  let result = '';
  for (const item of items) {
    result += item.name + ', '; // Creates new string each iteration!
  }
  return result;
}

// GOOD: Use array join
function buildMessage(items) {
  return items.map(item => item.name).join(', ');
}

5. Common Memory Leaks & Detection

📺 YouTube Tutorials
  • Finding Memory Leaks with Chrome DevTools — Google Chrome Developers
  • 4 Types of Memory Leaks in JavaScript — Academind

The 7 Common Memory Leak Patterns

1. Forgotten Event Listeners

// LEAK: Listener on global/long-lived element references component data
class MyComponent {
  constructor() {
    this.data = new Array(10000).fill('x');
    // This listener keeps `this` alive even after component is destroyed!
    window.addEventListener('resize', this.onResize.bind(this));
  }

  onResize() { /* uses this.data */ }

  // FIX: Remove listener on destroy
  destroy() {
    window.removeEventListener('resize', this.boundResize);
  }
}

2. Detached DOM Nodes

// LEAK: Reference to removed DOM node keeps it in memory
let detachedNode;
function createAndRemove() {
  const div = document.createElement('div');
  div.innerHTML = '<p>Large content...</p>'.repeat(1000);
  document.body.appendChild(div);
  document.body.removeChild(div);
  detachedNode = div; // LEAK! div is removed from DOM but still in memory
}

// FIX: Null out references
function createAndRemove() {
  const div = document.createElement('div');
  document.body.appendChild(div);
  document.body.removeChild(div);
  // Don't store reference to removed element
}

3. Closures Holding Large Data

// LEAK: Closure captures entire scope including largeData
function processData() {
  const largeData = new Array(1000000).fill({});
  const id = largeData[0].id;

  return function callback() {
    // Only uses `id` but closure captures entire `largeData`!
    console.log(id);
  };
}
const leakyCallback = processData(); // largeData is never GC'd

// FIX: Extract only what you need before closure
function processData() {
  const largeData = new Array(1000000).fill({});
  const id = largeData[0].id;
  // largeData goes out of scope after this function returns
  return function callback() {
    console.log(id); // Only captures `id`
  };
}

4. Timers & Intervals

// LEAK: setInterval runs forever, holding reference to large object
const heavyObject = { data: new Array(1000000) };
setInterval(() => {
  console.log(heavyObject.data.length); // heavyObject never GC'd
}, 1000);

// FIX: Clear intervals when done
const intervalId = setInterval(() => { /* ... */ }, 1000);
// When component/page is done:
clearInterval(intervalId);

5. RxJS Subscriptions (Angular-specific)

// LEAK: Subscription never unsubscribed
@Component({ /* ... */ })
export class LeakyComponent implements OnInit {
  ngOnInit() {
    this.http.get('/api/data').subscribe(data => {
      this.data = data; // If HTTP completes after destroy, `this` is leaked
    });

    this.someObservable$.subscribe(value => {
      // Runs forever if observable never completes
    });
  }
}

// FIX: Multiple patterns
@Component({ /* ... */ })
export class SafeComponent implements OnInit, OnDestroy {
  private destroy$ = new Subject<void>();

  ngOnInit() {
    // Pattern 1: takeUntil
    this.someObservable$.pipe(
      takeUntil(this.destroy$)
    ).subscribe(value => { /* ... */ });

    // Pattern 2: take(1) for one-shot
    this.http.get('/api/data').pipe(
      take(1)
    ).subscribe(data => { this.data = data; });

    // Pattern 3: async pipe in template (auto-unsubscribes)
    // {{ data$ | async }}
  }

  ngOnDestroy() {
    this.destroy$.next();
    this.destroy$.complete();
  }
}

6. WeakRef & FinalizationRegistry (Modern Solutions)

// Use WeakRef for caches that shouldn't prevent GC
class ImageCache {
  private cache = new Map<string, WeakRef<ImageBitmap>>();
  private registry = new FinalizationRegistry((key: string) => {
    // Called when cached object is GC'd
    this.cache.delete(key);
  });

  set(key: string, image: ImageBitmap) {
    this.cache.set(key, new WeakRef(image));
    this.registry.register(image, key);
  }

  get(key: string): ImageBitmap | undefined {
    const ref = this.cache.get(key);
    return ref?.deref(); // undefined if GC'd
  }
}

Detecting Memory Leaks with DevTools

Steps:
1. Open DevTools → Memory tab
2. Take Heap Snapshot (baseline)
3. Perform the action suspected of leaking (navigate, open modal, etc.)
4. Undo the action (go back, close modal)
5. Force GC (trash can icon)
6. Take another Heap Snapshot
7. Compare snapshots: look for objects that shouldn't exist

Key indicators:
- Growing heap over time (saw-tooth pattern that trends upward)
- Detached DOM nodes in snapshot
- Growing # of event listeners (Performance Monitor panel)
- Objects surviving in Old Generation that shouldn't

6. Animation Performance & 60fps

The Frame Budget

60fps = 16.67ms per frame
120fps = 8.33ms per frame (modern high-refresh displays)

Frame budget breakdown (16.67ms):
├── JavaScript: ~4ms (execute handlers, compute)
├── Style calculation: ~2ms
├── Layout: ~3ms
├── Paint: ~3ms
├── Composite: ~1ms
└── Browser overhead: ~3ms
    = You get ~10ms for your code!

The Pixel Pipeline

Full pipeline (worst case - layout change):
  JS → Style → Layout → Paint → Composite
  [~~~~~~~~~~~~~~~~~16.67ms~~~~~~~~~~~~~~~~~]

Paint-only (color/background change):
  JS → Style → Paint → Composite
  [~~~~~~~~~~~~12ms~~~~~~~~~~~~]

Composite-only (transform/opacity):
  JS → Composite
  [~~~~4ms~~~~]  ← BEST CASE! Runs on compositor thread

Achieving 60fps Animations

/* GOOD: Compositor-only properties — runs on GPU */
.animated {
  /* These NEVER trigger layout or paint */
  transform: translateX(100px);
  transform: scale(1.2);
  transform: rotate(45deg);
  opacity: 0.5;
  filter: blur(2px); /* on composited layer */
}

/* BAD: Triggers layout + paint every frame */
.animated-bad {
  left: 100px;     /* Layout! */
  top: 50px;       /* Layout! */
  width: 200px;    /* Layout! */
  height: 100px;   /* Layout! */
  margin-left: 10px; /* Layout! */
}

/* Example: Slide animation */
/* BAD */
@keyframes slideIn-bad {
  from { left: -100%; }
  to { left: 0; }
}

/* GOOD */
@keyframes slideIn-good {
  from { transform: translateX(-100%); }
  to { transform: translateX(0); }
}

FLIP Animation Technique

First, Last, Invert, Play — for layout animations at 60fps:

function flipAnimate(element, targetRect) {
  // FIRST: Get initial position
  const first = element.getBoundingClientRect();

  // LAST: Move element to final position (in DOM/CSS)
  element.classList.add('final-position');
  const last = element.getBoundingClientRect();

  // INVERT: Calculate the difference and apply inverse transform
  const deltaX = first.left - last.left;
  const deltaY = first.top - last.top;
  const deltaW = first.width / last.width;
  const deltaH = first.height / last.height;

  element.style.transform = `translate(${deltaX}px, ${deltaY}px) scale(${deltaW}, ${deltaH})`;
  element.style.transformOrigin = 'top left';

  // PLAY: Animate from inverted position to final (transform → identity)
  requestAnimationFrame(() => {
    element.style.transition = 'transform 300ms ease-out';
    element.style.transform = '';
  });
}

// Why this works:
// - Layout change happens instantly (no animation)
// - Visual animation uses only transform (compositor-only!)
// - Result: Layout-like animation at 60fps

7. requestAnimationFrame Deep Dive

📺 YouTube Tutorials
  • requestAnimationFrame Explained — Steve Griffith

Why rAF > setTimeout for Animations

// BAD: setTimeout — fires regardless of frame timing
// - Can fire mid-frame → visual glitch
// - Runs in background tabs → wastes CPU
// - Not synced with display refresh
setInterval(() => {
  element.style.transform = `translateX(${x++}px)`;
}, 16); // Approximate, not synchronized

// GOOD: requestAnimationFrame
// - Fires exactly once per frame, before paint
// - Pauses in background tabs (saves battery)
// - Synced with display refresh rate (60Hz, 120Hz, etc.)
function animate() {
  element.style.transform = `translateX(${x++}px)`;
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

rAF Patterns

// Pattern: Delta-time animation (frame-rate independent)
let lastTime = 0;
function animate(currentTime) {
  const deltaTime = currentTime - lastTime;
  lastTime = currentTime;

  // Move 100px per second regardless of frame rate
  const speed = 100; // pixels per second
  position += speed * (deltaTime / 1000);

  element.style.transform = `translateX(${position}px)`;
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

// Pattern: Batching DOM reads/writes with rAF
function batchedUpdate(elements, newValues) {
  // Read phase (causes 1 forced layout at most)
  const measurements = elements.map(el => el.getBoundingClientRect());

  // Write phase (in rAF — before next paint)
  requestAnimationFrame(() => {
    elements.forEach((el, i) => {
      el.style.transform = `translateY(${newValues[i]}px)`;
    });
  });
}

8. Scroll Performance

📺 YouTube Tutorials
  • Scroll Performance & Passive Listeners — Jake Archibald
  • IntersectionObserver — Kevin Powell

Why Scroll Can Be Janky

  • Scroll handlers run on main thread (by default)
  • Browser doesn't know if handler will call preventDefault()
  • Must wait for handler to finish before scrolling
  • Heavy handlers → scroll jank (missed frames)

Passive Event Listeners

// BAD: Browser must wait for handler (might call preventDefault)
document.addEventListener('scroll', handleScroll); // Default: passive = false
document.addEventListener('touchmove', handleTouch); // Same problem

// GOOD: Passive listener — tells browser "I won't prevent default"
document.addEventListener('scroll', handleScroll, { passive: true });
document.addEventListener('touchmove', handleTouch, { passive: true });
// Browser can scroll immediately on compositor thread!

// Note: Chrome now defaults scroll/touch listeners to passive
// But explicitly setting it is best practice for clarity

// Angular: Template binding
// <div (scroll)="onScroll($event)"> — NOT passive by default
// Use HostListener with options or manual addEventListener

Scroll-linked Effects

// BAD: Heavy work on every scroll event (fires 60+ times/sec)
window.addEventListener('scroll', () => {
  // Reading scrollTop forces layout
  const scrolled = document.documentElement.scrollTop;
  header.style.opacity = 1 - scrolled / 500; // Style change
  parallax.style.transform = `translateY(${scrolled * 0.5}px)`; // Layout...
});

// GOOD: Debounced + rAF batched
let ticking = false;
window.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => {
      const scrolled = window.scrollY;
      header.style.opacity = 1 - scrolled / 500;
      parallax.style.transform = `translateY(${scrolled * 0.5}px)`;
      ticking = false;
    });
    ticking = true;
  }
}, { passive: true });

// BEST: IntersectionObserver (no scroll handler at all!)
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      entry.target.classList.add('visible');
    }
  });
}, { threshold: 0.1 });
observer.observe(element);

// MODERN: CSS Scroll-Driven Animations (Chrome 115+)
@keyframes fadeIn {
  from { opacity: 0; transform: translateY(50px); }
  to { opacity: 1; transform: translateY(0); }
}
.animated-section {
  animation: fadeIn linear both;
  animation-timeline: view();
  animation-range: entry 0% cover 40%;
}

9. DOM Manipulation Performance

📺 YouTube Tutorials
  • Efficient DOM Manipulation — Steve Griffith
  • Virtual DOM vs Real DOM — Fireship

Why DOM is Slow

DOM operations cross the JavaScript → C++ bridge. Each crossing has overhead:

JavaScript World (V8)          C++ World (Blink/WebKit)
┌──────────────┐               ┌──────────────────┐
│  JS object   │ ←── bridge ──→ │  DOM node (C++)  │
│  reference   │   (expensive!) │  Style data      │
└──────────────┘               │  Layout data     │
                               └──────────────────┘

Each DOM operation:
1. Cross bridge to C++ (overhead)
2. Potentially invalidate style/layout
3. Return to JS

Efficient DOM Manipulation Patterns

// BAD: Multiple DOM operations (multiple bridge crossings + reflows)
for (let i = 0; i < 1000; i++) {
  const div = document.createElement('div');
  div.textContent = `Item ${i}`;
  container.appendChild(div); // 1000 DOM insertions = 1000 potential reflows
}

// GOOD: DocumentFragment (single DOM insertion)
const fragment = document.createDocumentFragment();
for (let i = 0; i < 1000; i++) {
  const div = document.createElement('div');
  div.textContent = `Item ${i}`;
  fragment.appendChild(div); // Fragment is in-memory, no reflow
}
container.appendChild(fragment); // Single reflow!

// GOOD: innerHTML for large batches (even faster)
const html = Array.from({ length: 1000 },
  (_, i) => `<div>Item ${i}</div>`
).join('');
container.innerHTML = html; // Single parse + single reflow

// BETTER for Angular: Use trackBy in *ngFor
// This prevents Angular from destroying/recreating DOM nodes
@Component({
  template: `
    <div *ngFor="let item of items; trackBy: trackById">
      {{ item.name }}
    </div>
  `
})
export class ListComponent {
  trackById(index: number, item: Item): number {
    return item.id; // Angular reuses DOM nodes with same ID
  }
}

When to Use Web Workers

Transferable Objects (Zero-Copy)

// Normal postMessage: COPIES data (slow for large arrays)
worker.postMessage(largeArrayBuffer); // Copies entire buffer

// Transferable: MOVES ownership (instant, zero-copy)
worker.postMessage(largeArrayBuffer, [largeArrayBuffer]);
// largeArrayBuffer is now empty in main thread!
// Worker owns the memory — no copy needed

// Works with: ArrayBuffer, MessagePort, OffscreenCanvas,
//             ImageBitmap, ReadableStream, WritableStream

// Example: Processing image data
const canvas = document.querySelector('canvas');
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]);
// Worker can now paint to canvas without main thread!

SharedArrayBuffer & Atomics

// Shared memory between main thread and workers (no copying!)
const sharedBuffer = new SharedArrayBuffer(1024);
const sharedArray = new Int32Array(sharedBuffer);

// Main thread
worker.postMessage({ buffer: sharedBuffer });
sharedArray[0] = 42; // Worker can see this immediately!

// Worker
addEventListener('message', ({ data }) => {
  const view = new Int32Array(data.buffer);
  console.log(view[0]); // 42 — shared memory!

  // Atomic operations for thread safety
  Atomics.add(view, 0, 1);      // Atomic increment
  Atomics.wait(view, 1, 0);     // Wait until value changes
  Atomics.notify(view, 1, 1);   // Wake waiting thread
});

12. Interview Questions — Phase 2

Beginner Level

  1. Q: What is the event loop?
    A: The event loop is the mechanism that coordinates JavaScript execution. It continuously: (1) picks a task from the task queue, (2) executes it to completion, (3) drains all microtasks, (4) renders if needed, (5) repeats. JavaScript is single-threaded — the event loop enables async behavior without threads.
  2. Q: What is the difference between microtasks and macrotasks?
    A: Macrotasks (setTimeout, setInterval, I/O): One executed per event loop iteration, then rendering can happen. Microtasks (Promise.then, queueMicrotask, MutationObserver): ALL drained after each macrotask, before rendering. This means microtasks can starve rendering if they keep adding more microtasks.
  3. Q: Why should you use requestAnimationFrame for animations?
    A: rAF fires exactly once per frame, synchronized with the display refresh rate. It pauses in background tabs (saving battery), guarantees code runs before paint (no visual glitch), and adapts to the display's refresh rate (60Hz, 120Hz). setTimeout(fn, 16) is an approximation that can drift and waste CPU.
  4. Q: What causes memory leaks in JavaScript?
    A: Common causes: (1) Forgotten event listeners on global objects, (2) References to detached DOM nodes, (3) Closures capturing large scopes, (4) Uncleared intervals/timeouts, (5) Unsubscribed observables/subscriptions, (6) Global variables, (7) Console.log references in development.

Intermediate Level

  1. Q: Explain layout thrashing and how to fix it in a real-world scenario.
    A: Layout thrashing occurs when JS reads a layout property, then writes a style, then reads again — each read forces synchronous layout recalculation. Example: In a list of cards, reading each card's height to set its sibling's height. Fix: (1) Batch reads using getComputedStyle before any writes, (2) Use rAF to separate read/write phases, (3) Use a library like fastdom that queues reads and writes separately.
  2. Q: How do Web Workers improve performance? What are their limitations?
    A: Web Workers run JavaScript on a separate thread, preventing heavy computation from blocking the UI. Limitations: (1) No DOM access, (2) Communication via postMessage (serialization cost), (3) No access to window, document, or parent scope, (4) Separate memory space (except SharedArrayBuffer), (5) Additional download cost for worker script. Best for: sorting, data processing, image manipulation, crypto.
  3. Q: What is the FLIP technique and when would you use it?
    A: FLIP (First, Last, Invert, Play) enables layout animations at 60fps. You: (1) Record initial position (First), (2) Apply final layout (Last), (3) Calculate difference and apply inverse transform (Invert), (4) Animate transform to identity (Play). This works because the actual layout change happens instantly, and the visual animation uses only compositor-friendly transforms.
  4. Q: Explain passive event listeners and their performance impact.
    A: By default, the browser doesn't know if a scroll/touch event handler will call preventDefault(). So it must wait for the handler to finish before scrolling. With { passive: true }, you promise not to call preventDefault, allowing the browser to scroll immediately on the compositor thread. Impact: Eliminates scroll jank from event listeners. Chrome now defaults scroll/touch to passive, but explicitly setting it is best practice.

Advanced Level

  1. Q: Explain V8's hidden classes and how they affect performance.
    A: V8 assigns "hidden classes" (shapes/maps) to objects with the same structure. Objects sharing a hidden class use the same optimized property access code (inline caches). Performance impact: (1) Always initialize properties in the same order, (2) Never add properties dynamically after construction, (3) Don't delete properties (changes hidden class), (4) Keep function arguments consistent in type/shape. Breaking these rules causes "megamorphic" property access — generic, slow dictionary lookup instead of fast fixed-offset access.
  2. Q: How would you handle rendering a list of 100,000 items performantly?
    A: (1) Virtual Scrolling (CDK Virtual Scroll in Angular): Only render visible items (~20-30 DOM nodes), recycling as user scrolls. (2) Pagination: Show items in pages of 50-100. (3) Infinite Scroll with recycling: Load more as user scrolls, remove far-away items. (4) Web Worker for filtering/sorting. (5) content-visibility: auto for sections. (6) RequestIdleCallback for progressive rendering. (7) trackBy to prevent DOM recreation on data changes.
  3. Q: Explain Transferable Objects and when to use them.
    A: Normal postMessage copies data between threads (structured clone algorithm) — O(n) for large arrays. Transferable Objects (ArrayBuffer, OffscreenCanvas, ImageBitmap) transfer ownership instead of copying — O(1), instant. After transfer, the buffer is neutered in the sender (becomes zero-length). Use when passing large binary data to/from workers: image processing, audio processing, large dataset operations. For shared access without transfer, use SharedArrayBuffer with Atomics.
  4. Q: What is scheduler.yield() and how does it differ from setTimeout(0)?
    A: Both yield to the main thread, allowing browser to handle higher-priority work. Differences: (1) setTimeout(0) puts your continuation at the BACK of the task queue (low priority). (2) scheduler.yield() keeps your continuation at the FRONT of the user-visible task queue (maintains priority). (3) setTimeout has a 1-4ms minimum delay. (4) scheduler.yield() is semantically clear about intent. Result: With scheduler.yield(), your code resumes faster while still allowing rendering and user input to happen.

Scenario-Based Questions

  1. Q: Your Angular app's dashboard is dropping frames during scroll. How do you debug and fix it?
    A: (1) Record Performance profile → identify long tasks during scroll. (2) Check for non-passive scroll listeners (search codebase). (3) Enable "Paint Flashing" in Rendering panel to see what's repainting. (4) Check for layout thrashing (forced synchronous layouts in flame chart). (5) Look for heavy change detection (use OnPush strategy). (6) Consider content-visibility for off-screen sections. (7) Implement virtual scrolling for long lists. (8) Move heavy computation to requestAnimationFrame or Web Worker.
  2. Q: Users report your SPA becomes slow after 30+ minutes of use. What's likely happening?
    A: Memory leak. Investigation: (1) Open Performance Monitor panel — watch JS heap size over time. (2) Take heap snapshots before/after repeated actions. (3) Check for: unsubscribed observables, uncleaned event listeners, detached DOM nodes (DOM leak), growing caches without eviction. (4) Look for growing number of event listeners in Performance Monitor. (5) Use allocation timeline to find what's growing. Common Angular causes: subscriptions without takeUntil, services holding growing arrays, router navigation leaking components.
