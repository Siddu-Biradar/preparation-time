Service Worker Lifecycle

Registration → Install → Activate → Fetch (intercept requests)

1. REGISTER (main thread):
   navigator.serviceWorker.register('/sw.js')

2. INSTALL (first time or update detected):
   - Download SW script
   - Parse & execute
   - Pre-cache critical assets (install event)
   - WAIT (if previous SW is still active)

3. ACTIVATE (after old SW releases control):
   - Clean up old caches
   - Take control of clients

4. FETCH (intercept every network request):
   - Apply caching strategy
   - Return cached/network response

// Angular PWA: All this is handled automatically!
// ng add @angular/pwa

Caching Strategies

StrategyHow It WorksUse ForTrade-off

Network FirstTry network → if fails → fallback to cacheAPI data that must be freshSlow on bad network
Stale While RevalidateServe from cache immediately → fetch update in backgroundContent that can be slightly staleBest UX, eventual consistency

Implementing Strategies (Raw SW)

// sw.js — Stale While Revalidate
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.open('dynamic-v1').then(async (cache) => {
      const cachedResponse = await cache.match(event.request);

      // Fetch fresh in background
      const networkFetch = fetch(event.request).then(response => {
        if (response.ok) {
          cache.put(event.request, response.clone());
        }
        return response;
      }).catch(() => cachedResponse); // Offline fallback

      // Return cached immediately (or wait for network if no cache)
      return cachedResponse || networkFetch;
    })
  );
});

// Cache First with expiration
self.addEventListener('fetch', (event) => {
  if (event.request.url.includes('/static/')) {
    event.respondWith(
      caches.match(event.request).then(cached => {
        return cached || fetch(event.request).then(response => {
          const clone = response.clone();
          caches.open('static-v1').then(cache => cache.put(event.request, clone));
          return response;
        });
      })
    );
  }
});

Navigation Preload (Critical for Performance)

// Problem: Service Worker startup adds latency to navigation requests
// The browser must wake up the SW before it can fetch from network
// This adds 50-200ms to navigation!

// Solution: Navigation Preload starts the network request WHILE SW boots
self.addEventListener('activate', (event) => {
  event.waitUntil(
    self.registration.navigationPreload?.enable()
  );
});

self.addEventListener('fetch', (event) => {
  if (event.request.mode === 'navigate') {
    event.respondWith(
      (async () => {
        // Use the preloaded response (already fetching in parallel!)
        const preloadResponse = await event.preloadResponse;
        if (preloadResponse) return preloadResponse;

        // Fallback to cache
        const cached = await caches.match(event.request);
        return cached || fetch(event.request);
      })()
    );
  }
});

Performance Timeline API

// PerformanceObserver — the unified way to observe performance entries
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    switch (entry.entryType) {
      case 'navigation':
        // Page load timing
        console.log('DOM Interactive:', entry.domInteractive);
        console.log('DOM Complete:', entry.domComplete);
        console.log('Load Event:', entry.loadEventEnd);
        break;
      case 'resource':
        // Individual resource timing
        console.log(`${entry.name}: ${entry.duration}ms`);
        break;
      case 'longtask':
        // Tasks > 50ms
        console.log(`Long task: ${entry.duration}ms`);
        break;
      case 'largest-contentful-paint':
        console.log(`LCP: ${entry.startTime}ms`, entry.element);
        break;
      case 'layout-shift':
        if (!entry.hadRecentInput) {
          console.log(`CLS shift: ${entry.value}`);
        }
        break;
      case 'first-input':
        console.log(`FID: ${entry.processingStart - entry.startTime}ms`);
        break;
      case 'event':
        // INP tracking
        console.log(`Interaction: ${entry.duration}ms`);
        break;
    }
  }
});

// Observe multiple types
observer.observe({ type: 'navigation', buffered: true });
observer.observe({ type: 'resource', buffered: true });
observer.observe({ type: 'longtask', buffered: true });
observer.observe({ type: 'largest-contentful-paint', buffered: true });
observer.observe({ type: 'layout-shift', buffered: true });

resources.forEach(r => {

      body,
      keepalive: true

}

Performance Regression Detection

// Custom CI script to detect performance regressions:
// compare-bundles.js
const fs = require('fs');
const path = require('path');

function getBundleSizes(distPath) {
  const files = fs.readdirSync(distPath);
  return files
    .filter(f => f.endsWith('.js') || f.endsWith('.css'))
    .map(f => ({
      name: f.replace(/\.[a-f0-9]+\./, '.*.'),
      size: fs.statSync(path.join(distPath, f)).size
    }));
}

const current = getBundleSizes('./dist/current');
const previous = getBundleSizes('./dist/previous');

// Alert if any bundle grew by more than 10%
current.forEach(file => {
  const prev = previous.find(p => p.name === file.name);
  if (prev) {
    const growth = ((file.size - prev.size) / prev.size) * 100;
    if (growth > 10) {
      console.error(`⚠️  ${file.name} grew by ${growth.toFixed(1)}%!`);
      process.exit(1);
    }
  }
});

Streaming SSR

// Traditional SSR:
// Server renders ENTIRE page → sends complete HTML (slow TTFB)

// Streaming SSR:
// Server sends HTML in chunks as it's ready
// Browser can start rendering while server is still working!

// Angular 18+ supports streaming:
// Server streams the app shell immediately
// Heavy data-dependent sections stream when ready

// Timeline:
// Traditional SSR:
// [--server renders entire page--]→[---send all HTML---]→[user sees page]
// 0ms                            500ms                  700ms

// Streaming SSR:
// [--shell ready--]→[send shell]→[user sees shell!]→[rest streams in]
// 0ms              100ms        200ms               500ms (progressive)
// User sees content 500ms earlier!

Partial Hydration & Islands

// Full Hydration (Angular default):
// Server sends HTML → Client downloads ALL JS → hydrates EVERYTHING
// Even static content that never changes gets hydrated

// Partial/Incremental Hydration (Angular 18+):
// Only hydrate interactive components on demand
// Static HTML stays as-is (no JS needed!)

// Angular @defer with hydration triggers:
@defer (hydrate on viewport) {
  <app-interactive-chart />
  // Only hydrates when visible in viewport
}

@defer (hydrate on interaction) {
  <app-comment-form />
  // Only hydrates when user clicks/focuses
}

@defer (hydrate never) {
  <app-static-footer />
  // NEVER hydrated — pure HTML, zero JS!
}

// Impact: Instead of hydrating 50 components (500KB JS executing):
// Only hydrate 5 interactive ones (50KB JS) → 10x less work!

HTTP/3 & QUIC

// HTTP/3 advantages over HTTP/2:
// 1. Built on QUIC (UDP) — no TCP head-of-line blocking
// 2. 0-RTT connection resumption
// 3. Connection migration (WiFi → cellular without reconnect)
// 4. Per-stream flow control

// Impact on performance:
// - Faster connection establishment (0-1 RTT vs 2-3 RTT)
// - No packet loss cascading (one lost packet doesn't block all streams)
// - Better on mobile (connection migration)
// - Especially important for users with packet loss (3G, poor WiFi)

// Enable in your server (example: Nginx with QUIC)
// listen 443 quic reuseport;
// listen 443 ssl;
// add_header Alt-Svc 'h3=":443"; ma=86400';

Early Hints (103 Status Code)

// Problem: While server is processing the request (database query, etc.),
// the browser is IDLE — wasting time.

// Solution: 103 Early Hints — server sends resource hints BEFORE the response
// Browser can start downloading critical resources while server is still working

// Server timeline:
// t=0ms:  Request received
// t=5ms:  Send 103 Early Hints (preload critical CSS, JS, fonts)
// t=5ms:  Browser starts downloading hinted resources!
// t=200ms: Server finishes processing
// t=200ms: Send 200 OK with HTML
// t=200ms: Browser already has CSS/JS/fonts downloaded!
//          → Faster FCP because resources were prefetched during server think time

// Example 103 response:
// HTTP/1.1 103 Early Hints
// Link: </styles/main.css>; rel=preload; as=style
// Link: </scripts/app.js>; rel=preload; as=script
// Link: </fonts/inter.woff2>; rel=preload; as=font; crossorigin
//
// (server continues processing...)
//
// HTTP/1.1 200 OK
// Content-Type: text/html
// ... (full response)

Request Prioritization

// Browsers assign priority to requests:
// Highest: Main document HTML
// High: CSS, Fonts, Preloaded resources
// Medium: Scripts (in viewport), Images (in viewport)
// Low: Scripts (deferred), Images (below fold), Prefetch

// You can influence priority:
<link rel="preload" href="critical.css" as="style" fetchpriority="high">
<img src="hero.webp" fetchpriority="high">      <!-- Boost priority -->
<img src="carousel.webp" fetchpriority="low">    <!-- Lower priority -->
<script src="analytics.js" fetchpriority="low"></script>

// HTTP/2 Priority Hints header:
// Priority: u=0 (highest urgency)
// Priority: u=7 (lowest urgency)
// Priority: u=3, i (incremental — can be rendered progressively)

Speculative Loading

// Speculation Rules API (Chrome 109+)
// Tell browser what pages user is likely to visit next
// Browser can prerender them in background!

<script type="speculationrules">
{
  "prerender": [
    {
      "urls": ["/dashboard", "/profile"],
      "eagerness": "moderate"
    }
  ],
  "prefetch": [
    {
      "urls": ["/settings", "/help"],
      "eagerness": "conservative"
    }
  ]
}
</script>

// Eagerness levels:
// "immediate": Start right away
// "eager": Start quickly, high confidence needed
// "moderate": Start on hover over link (most common)
// "conservative": Start on pointer down (just before click)

// With moderate eagerness:
// User hovers over "Dashboard" link → browser starts prerendering
// User clicks → page appears INSTANTLY (already rendered!)
// This gives sub-50ms navigation for SPAs!

// Using WASM in Angular:
// Example: Image processing with wasm-based library

// 1. Load WASM module
async function loadImageProcessor() {
  const wasm = await import('./image-processor.wasm');
  await wasm.default(); // Initialize
  return wasm;
}

// 2. Use in Angular service
@Injectable({ providedIn: 'root' })
export class ImageService {
  private wasm: any;

  async init() {
    this.wasm = await loadImageProcessor();
  }

  // Process image off main thread using WASM in Web Worker
  async processImage(imageData: ImageData): Promise<ImageData> {
    const worker = new Worker(new URL('./image.worker', import.meta.url));
    return new Promise((resolve) => {
      worker.onmessage = (e) => resolve(e.data);
      worker.postMessage(imageData, [imageData.data.buffer]); // Transfer
    });
  }
}

// image.worker.ts
import init, { apply_filter } from './image-processor.wasm';

addEventListener('message', async ({ data }) => {
  await init();
  const result = apply_filter(data.data, data.width, data.height);
  postMessage(new ImageData(result, data.width, data.height));
});

How Accessibility Overlaps with Performance

  • Reduced motion: Fewer animations = less GPU work = better battery
  • Semantic HTML: Less JS needed for accessibility = smaller bundle
  • Font sizing: System fonts = no font download latency
  • Image alt text: Proper dimensions prevent CLS
  • Skip navigation: Reduces DOM traversal for screen readers
  • Reduced data usage: prefers-reduced-data media query
/* Respect user's motion preferences */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

/* Respect data-saving preferences */
@media (prefers-reduced-data: reduce) {
  .hero-video { display: none; }
  .hero-image { content: url('hero-low-res.webp'); }
}

/* In Angular: */
@Component({

   - Performance-aware code reviews

   - Celebrate wins (X% improvement in LCP!)
   - Keep up with platform improvements

12. Interview Questions — Phase 5

Beginner Level

  1. Q: What is a Service Worker and how does it improve performance?
    A: A Service Worker is a script that runs in the background (separate thread), intercepting network requests. It improves performance by: (1) Caching assets for instant subsequent loads, (2) Enabling offline functionality, (3) Serving cached responses while fetching fresh data in background (stale-while-revalidate), (4) Pre-caching critical resources on install. In Angular, @angular/pwa provides automatic service worker setup.
  2. Q: What is the difference between RUM and synthetic monitoring?
    A: RUM (Real User Monitoring) collects performance data from actual users in production — reflects real devices, networks, and conditions but is noisy and hard to reproduce. Synthetic monitoring runs automated tests in controlled environments (Lighthouse, WebPageTest) — consistent and reproducible but doesn't reflect real-world conditions. Use both: synthetic for pre-deploy testing and debugging, RUM for monitoring production reality.
  3. Q: What are performance budgets?
    A: Performance budgets are limits set on metrics (bundle size, load time, Core Web Vitals) that trigger warnings or errors when exceeded. Examples: "Initial JS bundle must be under 400KB", "LCP must be under 2.5s". They're enforced in CI pipelines to prevent performance regressions. Angular supports budgets natively in angular.json.

Intermediate Level

  1. Q: Explain Service Worker caching strategies and when to use each.
    A: (1) Cache First: Check cache, fallback to network — for static assets (JS, CSS, images). (2) Network First: Try network, fallback to cache — for API data that must be fresh. (3) Stale While Revalidate: Serve cache immediately, refresh in background — best UX for content that can be slightly stale. (4) Network Only: Always fetch — for real-time data, POST requests. (5) Cache Only: Only from pre-cache — for app shell, critical assets that never change.
  2. Q: How do you implement performance monitoring in an Angular production application?
    A: (1) Install web-vitals library and measure CWV on every page load. (2) Use PerformanceObserver for Long Tasks and resource timing. (3) Track route change performance with User Timing API (mark start/end of navigation). (4) Send metrics via sendBeacon (reliable on page unload). (5) Include context: page URL, device memory, connection type, Angular version. (6) Build a dashboard showing p75 CWV metrics per page. (7) Set up alerts for regressions. (8) Use Chrome UX Report (CrUX) for field data without instrumentation.
  3. Q: Explain rendering patterns: CSR vs SSR vs SSG. When to use each?
    A: CSR (Client-Side): JS renders everything in browser. Best for: dashboards, authenticated apps. Downsides: slow FCP/LCP, poor SEO. SSR (Server-Side): Server renders HTML per request. Best for: dynamic content that changes per user/request. Trade-off: higher server cost, complex setup. SSG (Static Site Generation): HTML generated at build time. Best for: blogs, docs, marketing pages — content that rarely changes. Fastest possible delivery from CDN. In Angular: Use SSG for static pages, SSR for dynamic personalized content, CSR for fully interactive dashboards.

Advanced Level

  1. Q: Explain HTTP/3 and QUIC — how do they improve web performance?
    A: HTTP/3 uses QUIC (UDP-based protocol) instead of TCP. Improvements: (1) 0-RTT connection resumption (instant reconnection to known servers). (2) No head-of-line blocking — lost packet on one stream doesn't block others (unlike HTTP/2 over TCP). (3) Connection migration — switching from WiFi to cellular doesn't break connections (based on connection ID, not IP). (4) Built-in TLS 1.3 — always encrypted, no separate handshake. Impact: Most significant on mobile with unreliable networks (India, developing markets). Reduces connection establishment by 1-2 RTT and eliminates cascade failures from packet loss.
  2. Q: What is the Speculation Rules API and how does it differ from prefetch/prerender?
    A: Speculation Rules API (Chrome 109+) is a declarative way to tell the browser what navigations are likely, enabling it to prefetch or prerender pages in advance. Unlike link rel="prefetch" (which only downloads resources), speculation rules can PRERENDER (full page render in hidden tab). It supports eagerness levels (immediate, moderate on hover, conservative on mousedown). It replaces the deprecated link rel="prerender" with a more powerful and controllable API. Combined with Angular's router, it can make route transitions appear instant (<50ms).
  3. Q: How would you design a performance strategy for a global enterprise Angular application serving users in 50+ countries?
    A: (1) CDN with edge nodes in all regions (Cloudflare, Akamai). (2) SSR at the edge (Cloudflare Workers / Lambda@Edge) — render close to user. (3) Adaptive loading: detect connection quality → serve appropriate tier. (4) Image CDN with on-the-fly format/size optimization. (5) Critical CSS inlined, fonts self-hosted on CDN. (6) Performance budgets enforced per region (stricter for slower markets). (7) Route-based code splitting + smart preloading (viewport/hover based). (8) Service Worker for offline + cache-first strategy. (9) RUM segmented by country/device/connection to identify regional issues. (10) HTTP/3 enabled for mobile-heavy markets. (11) Consider ISR for pages with mixed static/dynamic content.
  4. Q: Explain partial/incremental hydration and its performance benefits over full hydration.
    A: Full hydration: Server renders HTML, client downloads ALL JS, executes ALL component logic, and attaches ALL event listeners — even for static content that never changes. This means TTI is delayed until ALL JS executes. Partial/Incremental hydration (Angular 18+): Only hydrate components that need interactivity, and only when they're visible or interacted with. Static sections remain as pure HTML with zero JS. Benefits: (1) Dramatically reduces JS execution on load (from 500KB → 50KB). (2) Faster TTI (only interactive components need JS). (3) Lower memory usage. (4) Better mobile performance. In Angular: @defer (hydrate on viewport/interaction/never) controls granularity.

System Design: Performance

  1. Q: Design a performance monitoring and alerting system for a large-scale frontend application.
    A: Architecture: (1) Collection Layer: web-vitals SDK in app → sendBeacon to ingestion endpoint. (2) Ingestion: Edge function validates and enriches data (adds region, page category). (3) Storage: Time-series DB (InfluxDB/TimescaleDB) for metrics, S3 for raw events. (4) Processing: Streaming aggregation (p50, p75, p95 per page per hour). (5) Dashboard: Grafana/custom UI showing CWV trends, distributions, regressions. (6) Alerting: Alert when p75 of any CWV crosses threshold for 30+ minutes. (7) Correlation: Link performance data to deploys (detect regression source). (8) Budget enforcement: CI integration that fails builds exceeding budgets. Segmentation: by page, device type, connection, geography.
