1. The Testing Pyramid

Beginner

//
//              /\
//             /  \         E2E Tests (Few — 5-10%)
//            / E2E\        Slow, brittle, expensive
//           /──────\       Test critical user journeys
//          /        \
//         /Integration\    Integration Tests (15-25%)

//      /                \

//   /──────────────────────\ Test logic in isolation
//

// ═══ TEST CONFIDENCE FORMULA ═══

// Unit: High speed, low confidence per test (but coverage compounds)

    Sentry.addBreadcrumb({ category, message, level: 'info' });
  }
}

7. Memory Leak Debugging

Critical

Theory: Common Memory Leak Sources in Angular

Memory leaks happen when your app holds references to objects that should be garbage-collected. In SPAs, users don't refresh — so leaks accumulate over hours, eventually crashing the tab.

// ═══ TOP 5 MEMORY LEAK SOURCES IN ANGULAR ═══
//
// 1. UNSUBSCRIBED OBSERVABLES (RxJS)
//    - Subscribing in ngOnInit without unsubscribing in ngOnDestroy
//    - Interval/timer observables that run forever
//    - WebSocket connections never closed
//
// 2. EVENT LISTENERS NOT REMOVED
//    - window.addEventListener('scroll', ...) without removeEventListener
//    - Renderer2.listen() without calling the unlisten function
//
// 3. DETACHED DOM NODES
//    - Component removed from DOM but JS still references its elements
//    - closures capturing DOM references that prevent GC
//
// 4. CLOSURES CAPTURING LARGE OBJECTS
//    - Event handlers closing over entire component instances
//    - Callbacks in services holding references to destroyed components
//
// 5. GROWING DATA STRUCTURES
//    - Arrays/Maps that grow unbounded (never pruned)
//    - Cached data without eviction policy

// ═══ FIX PATTERNS ═══

// ❌ LEAK: Subscription never cleaned up
@Component({ ... })
export class LeakyComponent implements OnInit {
  ngOnInit() {
    this.dataService.stream$.subscribe(data => {
      this.items = data; // This closure prevents GC of entire component!
    });
  }
}

// ✅ FIX 1: takeUntilDestroyed (Angular 16+, BEST approach)
@Component({ ... })
export class FixedComponent {
  private destroyRef = inject(DestroyRef);
  
  ngOnInit() {
    this.dataService.stream$.pipe(
      takeUntilDestroyed(this.destroyRef)
    ).subscribe(data => this.items = data);
  }
}

// ✅ FIX 2: Use signals + toSignal (auto-cleanup)
@Component({ ... })
export class SignalComponent {
  items = toSignal(this.dataService.stream$, { initialValue: [] });
  // toSignal automatically unsubscribes when component is destroyed!
}

// ✅ FIX 3: async pipe in template (auto-cleanup)
// <div *ngFor="let item of items$ | async">{{ item.name }}</div>

// ❌ LEAK: Event listener never removed
ngOnInit() {
  window.addEventListener('resize', this.onResize);
}
// ✅ FIX:
private resizeListener = this.onResize.bind(this);
ngOnInit() { window.addEventListener('resize', this.resizeListener); }
ngOnDestroy() { window.removeEventListener('resize', this.resizeListener); }

DevTools Memory Profiling (Step-by-Step)

// ═══ HOW TO FIND MEMORY LEAKS WITH CHROME DEVTOOLS ═══
//
// STEP 1: Take baseline heap snapshot
//   → DevTools → Memory tab → "Take heap snapshot"
//   → This is your baseline (Snapshot 1)
//
// STEP 2: Perform the leaky action
//   → Navigate to a page, open a modal, scroll through a list
//   → Navigate AWAY (back to previous page)
//   → Repeat 3-5 times to accumulate leaks
//
// STEP 3: Force garbage collection
//   → Click the trash can icon (🗑) in DevTools Memory tab
//   → This ensures only TRULY leaked objects remain
//
// STEP 4: Take second snapshot
//   → Take Snapshot 2
//
// STEP 5: Compare snapshots
//   → Select Snapshot 2 → Change view to "Comparison"
//   → Compare against Snapshot 1
//   → Sort by "# Delta" or "Size Delta" (descending)
//   → Look for: Detached HTMLDivElement, Object, Array growing
//
// ═══ WHAT TO LOOK FOR ═══
// • "Detached" prefix = DOM nodes no longer in page but still referenced
// • Growing array/object counts between snapshots
// • Component class names still present after navigation
// • EventListener objects growing in count
//
// ═══ ALLOCATION TIMELINE (Finding WHEN leak happens) ═══
// → Memory tab → "Allocation instrumentation on timeline"
// → Start recording → perform actions → stop
// → Blue bars = memory allocated during that time
// → Blue bars that DON'T turn gray = LEAKED (not garbage collected)
// → Click blue bar to see what objects were allocated

// ═══ PERFORMANCE.MEMORY API (Programmatic detection) ═══
// Monitor memory usage over time:
setInterval(() => {
  if (performance.memory) {
    const used = performance.memory.usedJSHeapSize / 1024 / 1024;
    const total = performance.memory.totalJSHeapSize / 1024 / 1024;
    console.log(`Heap: ${used.toFixed(1)}MB / ${total.toFixed(1)}MB`);
    
    // Alert if growing beyond threshold:
    if (used > 200) {
      console.warn('MEMORY WARNING: Heap exceeds 200MB!');
      // Send to monitoring service
    }
  }
}, 30000); // Check every 30s

// ═══ DETACHED DOM NODE DETECTION ═══
// In DevTools Console:
// 1. Type: getEventListeners(document) — see ALL listeners
// 2. Heap snapshot → filter "Detached" → trace retainer path
// 3. The "Retaining path" shows you EXACTLY what's holding the reference

Real-World Memory Leak Case Studies

// ═══ CASE 1: Router Navigation Leak ═══
// Problem: Component subscribes to router events, never unsubscribes
// Each navigation creates new subscription → linear memory growth
// Fix: takeUntilDestroyed() on ALL router subscriptions

// ═══ CASE 2: Third-Party Library Leak ═══
// Problem: Chart library (Chart.js) creates canvas context
// Angular destroys component, but chart instance stays in memory
// Fix: Call chart.destroy() in ngOnDestroy()

ngOnDestroy() {
  this.chartInstance?.destroy(); // Releases canvas + internal data
}

// ═══ CASE 3: Closure Leak in Services ═══
// Problem: Service stores callbacks from components:
@Injectable({ providedIn: 'root' })
export class NotificationService {
  private listeners: Function[] = []; // GROWS FOREVER!
  
  onNotification(cb: Function) {
    this.listeners.push(cb);
  }
}
// Fix: Return unsubscribe function:
onNotification(cb: Function): () => void {
  this.listeners.push(cb);
  return () => { // Return cleanup function
    this.listeners = this.listeners.filter(l => l !== cb);
  };
}

// ═══ CASE 4: WebSocket Connection Leak ═══
// Problem: Each route change creates new WebSocket, old one not closed
// Fix: Manage connection lifecycle in a singleton service with cleanup
Interview Pattern When asked "How do you detect and fix memory leaks?", structure your answer: (1) Detect: Chrome DevTools heap snapshots, compare before/after navigation. (2) Identify: Look for "Detached" DOM nodes and growing object counts. (3) Common causes: unsubscribed observables, event listeners, third-party library cleanup, growing caches. (4) Angular fixes: takeUntilDestroyed(), toSignal(), async pipe, ngOnDestroy cleanup.

Q: Your Angular SPA gets slower after 30 minutes of use. How do you diagnose and fix it? (Amazon, Google, Flipkart)

Answer: This screams memory leak. Steps: (1) Open DevTools Memory tab → take heap snapshot as baseline. (2) Use the app for 10 min (navigate pages, open/close modals). (3) Force GC → take second snapshot. (4) Compare snapshots — sort by "Size Delta". (5) Look for Detached DOM nodes (component removed but referenced) and growing arrays. (6) Trace retainer path to find the root cause. Common fixes: add takeUntilDestroyed() to all subscriptions, destroy third-party libraries in ngOnDestroy, add LRU eviction to caches, ensure event listeners are removed.

8. Logging & Analytics

// ═══ STRUCTURED FRONTEND LOGGING ═══
@Injectable({ providedIn: 'root' })
export class LogService {
  private readonly LOG_LEVELS = { debug: 0, info: 1, warn: 2, error: 3 };
  private level = environment.production ? 'warn' : 'debug';
  
  info(message: string, data?: any) { this.log('info', message, data); }
  warn(message: string, data?: any) { this.log('warn', message, data); }
  error(message: string, data?: any) { this.log('error', message, data); }
  
  private log(level: string, message: string, data?: any) {
    if (this.LOG_LEVELS[level] < this.LOG_LEVELS[this.level]) return;
    
    const entry = {
      timestamp: new Date().toISOString(),
      level,
      message,
      data,
      url: window.location.href,
      userAgent: navigator.userAgent
    };
    
    // In production: send to backend logging service
    if (environment.production) {
      this.sendToBackend(entry);
    } else {
      console[level](message, data);
    }
  }
  
  private sendToBackend(entry: any) {
    // Use beacon for reliability (sends even on page unload):
    navigator.sendBeacon('/api/logs', JSON.stringify(entry));
  }
}

// ═══ ANALYTICS (Event Tracking) ═══
@Injectable({ providedIn: 'root' })
export class AnalyticsService {
  trackEvent(event: string, properties?: Record<string, any>) {
    // Google Analytics 4:
    (window as any).gtag('event', event, properties);
    
    // Or custom:
    navigator.sendBeacon('/api/analytics', JSON.stringify({
      event,
      properties,
      timestamp: Date.now(),
      sessionId: this.sessionId,
      page: window.location.pathname
    }));
  }
  
  trackPageView(page: string) {
    this.trackEvent('page_view', { page_path: page });
  }
}

// Auto-track route changes:
constructor(private router: Router, private analytics: AnalyticsService) {
  this.router.events.pipe(
    filter(event => event instanceof NavigationEnd)
  ).subscribe((event: NavigationEnd) => {
    this.analytics.trackPageView(event.urlAfterRedirects);
  });
}

8. Performance Monitoring (RUM)

Advanced 
// RUM = Real User Monitoring (actual user performance data)
// vs Synthetic = Lighthouse/WebPageTest (lab conditions)

// ═══ WEB VITALS COLLECTION ═══
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

@Injectable({ providedIn: 'root' })
export class PerformanceMonitorService {
  constructor() {
    if (environment.production) this.init();
  }
  
  private init() {
    onLCP(metric => this.report(metric));
    onINP(metric => this.report(metric));
    onCLS(metric => this.report(metric));
    onFCP(metric => this.report(metric));
    onTTFB(metric => this.report(metric));
    
    // Custom metrics:
    this.observeLongTasks();
    this.observeResourceTiming();
  }
  
  private report(metric: any) {
    const body = {
      name: metric.name,
      value: metric.value,
      delta: metric.delta,
      id: metric.id,
      page: location.pathname,
      connection: (navigator as any).connection?.effectiveType,
      deviceMemory: (navigator as any).deviceMemory,
      viewport: `${innerWidth}x${innerHeight}`
    };
    navigator.sendBeacon('/api/performance', JSON.stringify(body));
  }
  
  private observeLongTasks() {
    const observer = new PerformanceObserver(list => {
      for (const entry of list.getEntries()) {
        if (entry.duration > 100) { // Only report > 100ms
          this.report({ name: 'long-task', value: entry.duration });
        }
      }
    });
    observer.observe({ type: 'longtask', buffered: true });
  }
  
  private observeResourceTiming() {
    const observer = new PerformanceObserver(list => {
      for (const entry of list.getEntries() as PerformanceResourceTiming[]) {
        if (entry.duration > 1000) { // Slow resources (> 1s)
          this.report({
            name: 'slow-resource',
            value: entry.duration,
            resource: entry.name
          });
        }
      }
    });
    observer.observe({ type: 'resource', buffered: true });
  }
}

9. Feature Flags

Intermediate 
// ═══ WHY FEATURE FLAGS? ═══
// • Deploy code without releasing features (decouple deploy from release)
// • Canary releases: enable for 5% of users first
// • A/B testing: show variant A vs B
// • Kill switch: instantly disable broken feature
// • Beta programs: enable for specific user segments

// ═══ ANGULAR FEATURE FLAG SERVICE ═══
@Injectable({ providedIn: 'root' })
export class FeatureFlagService {
  private flags = signal<Record<string, boolean>>({});
  
  constructor(private http: HttpClient) {
    // Fetch flags on app init:
    this.http.get<Record<string, boolean>>('/api/features')
      .subscribe(flags => this.flags.set(flags));
  }
  
  isEnabled(flag: string): boolean {
    return this.flags()[flag] ?? false;
  }
  
  // For templates:
  enabled = (flag: string) => computed(() => this.flags()[flag] ?? false);
}

// Structural Directive:
@Directive({ selector: '[featureFlag]', standalone: true })
export class FeatureFlagDirective {
  private ff = inject(FeatureFlagService);
  private vcr = inject(ViewContainerRef);
  private templateRef = inject(TemplateRef);
  
  @Input() set featureFlag(flag: string) {
    if (this.ff.isEnabled(flag)) {
      this.vcr.createEmbeddedView(this.templateRef);
    } else {
      this.vcr.clear();
    }
  }
}

// Usage:
<div *featureFlag="'new-checkout'">
  <app-new-checkout />
</div>

// Route guard with feature flag:
export const featureFlagGuard = (flag: string): CanActivateFn => () => {
  return inject(FeatureFlagService).isEnabled(flag);
};

const routes: Routes = [
  {
    path: 'beta-dashboard',
    loadComponent: () => import('./beta-dashboard.component'),
    canActivate: [featureFlagGuard('beta-dashboard')]
  }
];

12. Interview Questions (Previously Asked)

Q1: What's your testing strategy for a large Angular application? (All companies)

Answer: Testing pyramid: 70% unit, 20% integration, 10% E2E. Unit: all services, pipes, validators, reducers (fast, isolated). Integration: components with TestBed or Angular Testing Library (template + bindings + child components). E2E: Playwright for critical user journeys (login, checkout, search). Visual regression: Chromatic/Playwright screenshots for component library. Coverage: 80%+ on business logic, not chasing 100%. CI: all tests run on every PR, E2E on staging before deploy.

Q2: How do you monitor frontend errors in production? (Amazon, Microsoft, Google)

Answer: Stack: Sentry for error tracking + Web Vitals for performance. Setup: (1) Global ErrorHandler sends to Sentry with user context. (2) HTTP interceptor catches API errors with request/response details. (3) Source maps uploaded during build for readable stack traces. (4) Session replay on errors for reproduction. (5) Alerts: Slack/PagerDuty on error rate spike, new error types, affected user count. (6) Dashboard: errors by route, by browser, by release. (7) Release tracking: tag deploys to correlate errors with code changes.

Q3: How do you implement feature flags? What about cleanup? (Amazon, Flipkart)

Answer: Implementation: (1) Service fetches flags from backend (LaunchDarkly/Unleash/custom). (2) Structural directive *featureFlag="'name'" for template conditional. (3) Route guards for feature-gated routes. (4) Interceptor adds feature context to API calls. Strategies: percentage rollout, user segment targeting, kill switch. Cleanup: critical! (1) Set expiry dates on flags. (2) Automated linting to detect stale flags. (3) After 100% rollout for 2 weeks → remove flag + dead code. (4) Track active flags in dashboard. Tech debt accumulates fast without cleanup.

Q4: How would you set up a CI/CD pipeline for a frontend monorepo with 5 apps? (Senior level)

Answer: Nx monorepo: (1) affected command — only test/build changed apps + their dependents. (2) Distributed caching (Nx Cloud) — skip unchanged tasks across team. (3) Pipeline: lint → type-check → unit test → build → E2E (parallel where possible). (4) Per-app budgets (fail if any app exceeds). (5) PR previews per app (Vercel/Cloudflare). (6) Canary deploys: deploy to 5% first, monitor errors for 30min, then full. (7) Rollback: instant via CDN (point to previous build). (8) Shared library changes trigger all consuming apps.

Q5: Explain Real User Monitoring vs Synthetic Monitoring. Which metrics do you track? (Google, Microsoft)

Answer: Synthetic (Lab): Lighthouse, WebPageTest — controlled conditions, consistent, catches regressions in CI. RUM (Field): actual user data — varying devices, networks, geographies. Track both! Metrics: CWV (LCP, INP, CLS) at p50/p75/p95. Custom: time-to-interactive per route, API response times, long tasks, JS errors. Segment by: device type, connection speed (4G/3G), geography, browser. Dashboard: per-route performance, release comparison. Alerts: p75 LCP exceeds 2.5s for 5 minutes → PagerDuty.
