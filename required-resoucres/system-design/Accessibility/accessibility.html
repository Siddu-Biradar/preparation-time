Accessibility — From 0 to Advanced (Frontend Edition)

A complete, interview-grade accessibility guide for Frontend SDE2/SDE3 roles. Covers WCAG, ARIA, keyboard, focus, screen readers, testing, and the questions interviewers actually ask — with code, gotchas, and patterns from the WAI-ARIA Authoring Practices Guide.

1. Why Accessibility Matters Beginner

  • Users: ~16% of the world (1.3 billion+) lives with a disability. Add temporary (broken arm) and situational (sun glare, noisy room) impairments and you cover almost everyone.
  • Legal: ADA (US), Section 508, EAA (EU 2025), AODA (Ontario), Equality Act (UK). Lawsuits target inaccessible sites — Domino's, Target, Beyoncé, Netflix have all been sued.
  • Business: SEO benefits (semantic HTML & alt text), bigger market, lower bounce rates, higher trust.
  • Engineering: Accessible code is more maintainable; semantic HTML maps better to design systems.
Senior framing At SDE2/SDE3 level interviewers want to hear "a11y is a quality bar I bake in from day one, not a remediation pass at the end". Talk about lint rules, design tokens for contrast, ESLint plugin jsx-a11y, axe in CI.

2. POUR Principles Beginner

WCAG is built on four principles. Memorise the acronym — it shows up in interviews verbatim.

PrincipleMeaningExample
PerceivableInformation must be presentable via senses the user has.Alt text on images, captions on videos, sufficient contrast.
OperableInterface must be usable via the input the user has.Keyboard accessible, no time limits, no seizure-inducing flashing.
UnderstandableContent & UI must be understandable.Predictable navigation, clear errors, consistent labels.
RobustContent must work with current and future assistive tech.Valid HTML, proper ARIA, no reliance on quirks.

3. WCAG 2.1 / 2.2 — A, AA, AAA Beginner

  • Level A: bare minimum. If you fail this, the site is unusable for some.
  • Level AA: the legal & industry standard. Always target this.
  • Level AAA: highest. Often impractical for entire sites; aim for it on critical flows.

WCAG 2.2 (Oct 2023) adds 9 new criteria: focus appearance, focus not obscured, dragging movements (24 px target), consistent help, redundant entry, accessible authentication, etc. These come up in 2025+ interviews.

WCAG 3 (Silver) Still in draft. It will replace pass/fail with a scored model. Don't bring it up unless asked, but mention you're tracking it.

4. Color & Contrast Intermediate

ContentWCAG AAWCAG AAA
Normal text (< 18pt or < 14pt bold)4.5:17:1
Large text (≥ 18pt or ≥ 14pt bold)3:14.5:1
UI components & graphical objects3:1—
Focus indicator (WCAG 2.2)3:1 against adjacent colors—

Don't rely on color alone

Required fields, error states, chart series — always pair color with an icon, pattern, or text label. ~8% of men & ~0.5% of women are colorblind.

/* Bad — only color */
.error { color: red; }

/* Good — color + icon + label */
.error::before { content: "⚠ "; }
.error[role="alert"] { color: var(--danger); }
Tools Chrome DevTools color picker shows AA/AAA inline. Use Stark, Polypane, axe-DevTools, or npm:wcag-contrast. New APCA algorithm (likely WCAG 3) accounts for font weight better.

5. Alternative Text & Images Beginner

  • Informative image: describe the meaning, not the appearance. "Quarterly sales chart showing 30% growth" — not "image of a chart".
  • Decorative image: alt="" (empty but PRESENT). Screen reader skips it.
  • Functional image (icon-only button): describe the action. <button aria-label="Close"><svg ...></svg></button>
  • Complex image: short alt + long description nearby (or aria-describedby, or a linked transcript).
  • Text in image: avoid. If unavoidable, repeat the text in alt verbatim.
<!-- Decorative -->
<img src="curl.svg" alt="" role="presentation">

<!-- Informative -->
<img src="ceo.jpg" alt="Sundar Pichai speaking at Google I/O 2025">

<!-- Functional -->
<a href="/cart" aria-label="View cart, 3 items">
  <svg aria-hidden="true">...</svg> <span>3</span>
</a>

<!-- SVG inline (preferred) -->
<svg role="img" aria-labelledby="logoTitle">
  <title id="logoTitle">Acme Corp</title>
  <path d="..."/>
</svg>
Gotchas
  • Missing alt entirely → screen readers read the filename ("IMG_4523.jpg").
  • Don't start alt with "image of" — screen readers already announce "graphic".
  • Background-image SVGs (CSS) are inaccessible — assistive tech can't see them.
  • Captions on charts ≠ alt text. Both serve different audiences.

6. Semantic HTML First Beginner

The most important a11y practice. Native elements come with built-in roles, keyboard support, focus, and AT integration that you'd otherwise rebuild (poorly).

Don'tDo
<div onclick><button>
<span class="link"><a href>
<div class="header"><header>
<div> for lists<ul>/<ol>/<li>
Custom dropdown<select> when possible
Custom modal<dialog> with showModal()
Custom accordion<details>/<summary>
First Rule of ARIA Don't use ARIA if a native HTML element does the job. No ARIA is better than bad ARIA. <button> > <div role="button" tabindex="0">.

7. ARIA — Roles, States, Properties Intermediate

The 5 Rules of ARIA

  1. If you can use a native element, use it.
  2. Don't change native semantics unless you really must.
  3. All interactive ARIA controls must be keyboard accessible.
  4. Don't use role="presentation" or aria-hidden="true" on focusable elements.
  5. All interactive elements must have an accessible name.

Three categories

  • Roles — what something is: button, dialog, tab, tabpanel, menu, tree, grid, alert, status.
  • States — current condition: aria-expanded, aria-selected, aria-checked, aria-disabled, aria-busy, aria-pressed.
  • Properties — relationships & descriptions: aria-label, aria-labelledby, aria-describedby, aria-controls, aria-owns, aria-current.

Accessible name resolution (priority)

  1. aria-labelledby (wins over everything)
  2. aria-label
  3. Native label (<label for>, <legend>, <caption>, alt)
  4. Inner text content
  5. title attribute (last resort)
<!-- Toggle button with state -->
<button aria-pressed="false" aria-label="Mute audio">
  <svg aria-hidden="true">...</svg>
</button>

<!-- Disclosure -->
<button aria-expanded="false" aria-controls="menu1">Menu</button>
<ul id="menu1" hidden> ... </ul>

<!-- Tabs -->
<div role="tablist" aria-label="Settings">
  <button role="tab" aria-selected="true"  aria-controls="p1" id="t1">Profile</button>
  <button role="tab" aria-selected="false" aria-controls="p2" id="t2" tabindex="-1">Billing</button>
</div>
<div role="tabpanel" id="p1" aria-labelledby="t1">...</div>
<div role="tabpanel" id="p2" aria-labelledby="t2" hidden>...</div>
Common ARIA mistakes
  • role="button" on an <a href> — confusing for AT. Pick one.
  • aria-label on a non-interactive <div> — ignored by most ATs.
  • Forgetting to update aria-expanded/aria-selected after the state changes.
  • Putting aria-hidden="true" on a focusable element creates a "ghost" — visible, focusable, invisible to AT. Either hide visually too or remove from tab order.
  • role="presentation" doesn't remove children's roles for <table>/<ul> structures (implicit semantics still apply for required children).

8. Landmarks & Page Structure Intermediate

Landmarks let screen-reader users jump between sections like sighted users skim. NVDA's D and VoiceOver's VO+U rotor depend on these.

ElementImplicit Role
<header> (top-level)banner
<nav>navigation
<main>main
<aside>complementary
<footer> (top-level)contentinfo
<form aria-label>form
<section aria-label>region
role="search"search

Rules

  • Exactly one <main>.
  • Multiple <nav>s? Differentiate with aria-label="Primary", aria-label="Footer".
  • All content should live inside a landmark.
  • Use headings (h1–h6) in logical order — they form a parallel navigation system.

9. Live Regions & Announcements Advanced

How you tell screen readers about content that changes asynchronously (toast, search results count, chat message).

ValueBehaviorUse for
aria-live="polite"Announce when AT is idleStatus updates, "5 results found"
aria-live="assertive"Interrupt current speechErrors, time-critical
role="status"Implicit politeLoading, progress text
role="alert"Implicit assertiveForm errors, warnings
role="log"Polite, append-only historyChat, console
<!-- The container must exist on initial render. -->
<div role="status" aria-live="polite" id="toast"></div>

<script>
function announce(msg) {
  const el = document.getElementById('toast');
  el.textContent = '';                  // re-trigger announcement
  setTimeout(() => { el.textContent = msg; }, 50);
}
announce('Profile saved');
</script>

Other attributes

  • aria-atomic="true" — announce the entire region, not just the diff.
  • aria-relevant="additions text" — what changes are announced (default is good).
  • aria-busy="true" — pause announcements while doing batch updates.
Gotchas
  • The live region must exist in the DOM at initial paint; adding it AND content together often fails to announce.
  • Repeating the same string won't re-announce — clear & re-set.
  • Don't overuse assertive — it interrupts users mid-task.

10. The Accessibility Tree Advanced

The browser builds a parallel tree from the DOM that exposes name, role, state, and value to AT. display: none, visibility: hidden, and aria-hidden="true" remove nodes from it. Position-off-screen (.sr-only) keeps them in the tree (use this for visually-hidden labels). 

/* Visually-hidden but accessible to AT */
.sr-only {
  position: absolute;
  width: 1px; height: 1px;
  padding: 0; margin: -1px; overflow: hidden;
  clip: rect(0,0,0,0); white-space: nowrap; border: 0;
}

Inspect with Chrome DevTools → Elements → Accessibility tab. Firefox has the same plus a tree view.

11. Keyboard Navigation Basics Intermediate

KeyAction
Tab / Shift+TabMove focus forward / backward
EnterActivate links and submit forms
SpaceActivate buttons, toggle checkboxes
ArrowsWithin composite widgets (radio, tabs, menu, grid)
EscClose dialog/menu, cancel
Home / EndFirst / last item in a widget or grid row
PageUp / PageDownScroll big chunks (sliders, listboxes)

tabindex values

  • 0 — natural document order, focusable.
  • -1 — focusable via JS only, not in tab order. Use for items inside roving-tabindex widgets and for receiving focus on programmatic dialogs.
  • positive numbers — almost always wrong. Breaks natural order, hard to maintain.

Skip link (must-have)

<a href="#main" class="skip-link">Skip to main content</a>
<!-- ... lots of nav ... -->
<main id="main" tabindex="-1">...</main>

The tabindex="-1" on main ensures focus actually lands there in some browsers (Safari quirk).

12. Focus Management Intermediate

  • Visible focus ring — never outline: none without a replacement. Use :focus-visible to show only on keyboard focus.
  • SPA route changes: after navigation, focus the new page's <h1> (with tabindex="-1") and announce the new title in a live region.
  • Async actions: after deletion, move focus to the next sensible item (sibling, parent, or "Undo" toast).
  • Modals/dialogs: store the trigger before opening; restore focus to it on close.
/* Show focus ring only when keyboard-focused */
button:focus { outline: none; }
button:focus-visible { outline: 3px solid #2a5bd7; outline-offset: 2px; }
// SPA route change
useEffect(() => {
  document.title = `${page.title} — Acme`;
  pageH1Ref.current?.focus();
  announce(`Navigated to ${page.title}`);
}, [pageId]);

13. Focus Trapping (Modals & Dialogs) Advanced

The native way (preferred)

const dlg = document.querySelector('dialog');
openBtn.addEventListener('click', () => dlg.showModal()); // traps focus + ESC + backdrop
closeBtn.addEventListener('click', () => dlg.close());

The manual way (when you can't use <dialog>)

const FOCUSABLE = 'a[href], button:not([disabled]), input:not([disabled]),' +
  ' textarea:not([disabled]), select:not([disabled]), [tabindex]:not([tabindex="-1"])';

function trap(container) {
  const focusables = container.querySelectorAll(FOCUSABLE);
  const first = focusables[0];
  const last  = focusables[focusables.length - 1];

  container.addEventListener('keydown', (e) => {
    if (e.key !== 'Tab') return;
    if (e.shiftKey && document.activeElement === first) {
      e.preventDefault(); last.focus();
    } else if (!e.shiftKey && document.activeElement === last) {
      e.preventDefault(); first.focus();
    }
  });
}

Modal a11y checklist

  • role="dialog" + aria-modal="true"
  • aria-labelledby="dialog-title" (or aria-label)
  • Initial focus on the dialog (often the first focusable, or the dialog container itself)
  • Trap Tab inside
  • Close on Esc and on backdrop click
  • Restore focus to the trigger on close
  • Mark page background aria-hidden="true" or inert while open
<!-- Use the new `inert` attribute (2024+) on background -->
<div id="page" inert> ...rest of app... </div>
<dialog open>...</dialog>

14. Roving Tabindex Pattern Advanced

Composite widgets (toolbars, menus, tabs, listboxes, grids, trees) should be a single tab stop. Once focused, arrow keys move within the widget. This is the roving tabindex pattern. 

// Only ONE child has tabindex=0 at any time
<div role="toolbar" aria-label="Format">
  <button tabindex="0">Bold</button>
  <button tabindex="-1">Italic</button>
  <button tabindex="-1">Underline</button>
</div>

// JS: arrow keys move tabindex AND focus
toolbar.addEventListener('keydown', (e) => {
  const items = [...toolbar.querySelectorAll('button')];
  const i = items.indexOf(document.activeElement);
  let next = i;
  if (e.key === 'ArrowRight') next = (i + 1) % items.length;
  if (e.key === 'ArrowLeft')  next = (i - 1 + items.length) % items.length;
  if (next !== i) {
    items[i].tabIndex = -1;
    items[next].tabIndex = 0;
    items[next].focus();
    e.preventDefault();
  }
});

Alternative: aria-activedescendant — focus stays on the container, ARIA points to the active child. Used by many comboboxes.

15. Custom Keyboard Shortcuts Advanced

  • Don't override platform shortcuts (Cmd+L, Cmd+T, screen reader keys).
  • Provide a way to remap or disable shortcuts (WCAG 2.1.4 — character key shortcuts).
  • Document them in a "?" help dialog.
  • Don't trigger shortcuts while typing in inputs unless modified.
  • Use aria-keyshortcuts="Control+K" to advertise to AT.
document.addEventListener('keydown', (e) => {
  const inField = ['INPUT','TEXTAREA','SELECT'].includes(e.target.tagName);
  if (e.key === 'k' && (e.metaKey || e.ctrlKey)) {
    e.preventDefault(); openCommandPalette();
  } else if (e.key === '/' && !inField) {
    e.preventDefault(); focusSearch();
  }
});

16. Accessible Forms Intermediate

The non-negotiables

  • Every input has a visible <label>. Placeholder is not a label.
  • Use <fieldset> + <legend> for radio/checkbox groups.
  • Use the right input type — mobile keyboards adapt (email/tel/number/search).
  • Use autocomplete tokens (email, given-name, postal-code, current-password, one-time-code) — required by WCAG 2.2 AA.
  • Required fields: visible asterisk + required + aria-required="true" if needed for legacy AT.
  • Don't disable the submit button — let users submit and show errors.
<form novalidate>
  <label for="email">Email</label>
  <input id="email" name="email" type="email"
         autocomplete="email" required
         aria-describedby="emailHelp emailError"
         aria-invalid="false">
  <p id="emailHelp" class="help">We'll never share it.</p>
  <p id="emailError" class="error" role="alert" hidden></p>
</form>

17. Error Handling & Validation Advanced

  • On submit with errors: focus the first invalid field and announce a summary.
  • Tie error text to the input via aria-describedby.
  • Set aria-invalid="true" only AFTER the user has interacted (avoid screaming on first paint).
  • Inline errors should appear in a role="alert" region or live region for AT users.
  • Provide concrete fix instructions, not "Invalid input".
function submit(form) {
  const invalids = [...form.querySelectorAll(':invalid')];
  if (invalids.length) {
    invalids[0].focus();
    summaryRegion.textContent =
      `${invalids.length} error${invalids.length>1?'s':''} found. Please fix them.`;
    return;
  }
  form.submit();
}

19. Accessible Data Grids Critical

Most failed in interviews. A true grid is a single tab stop with 2D arrow navigation, like a spreadsheet.

  • role="grid" on the table; role="row"; role="columnheader"; role="gridcell".
  • Arrow keys move between cells; Home/End first/last in row; Ctrl+Home/Ctrl+End first/last cell.
  • Sort buttons in headers expose aria-sort="ascending|descending|none".
  • Resizable columns: announce new size via live region.
  • Use roving tabindex on cells.
<table role="grid" aria-label="Employees" aria-rowcount="500">
  <thead>
    <tr role="row">
      <th role="columnheader" aria-sort="ascending">
        <button>Name</button>
      </th>
      <th role="columnheader" aria-sort="none">
        <button>Role</button>
      </th>
    </tr>
  </thead>
  <tbody>
    <tr role="row" aria-rowindex="2">
      <td role="gridcell" tabindex="0">Sid</td>
      <td role="gridcell" tabindex="-1">SDE3</td>
    </tr>
  </tbody>
</table>
If it's just data display Use a regular <table> with scope="col/row" and <caption>. Don't add grid semantics unless it actually behaves like a grid (cell focus, edit-in-place, etc.).

20. Motion, Animation & Reduced Motion Intermediate

  • WCAG 2.3.1 — no content flashes more than 3× per second (seizure risk).
  • WCAG 2.3.3 — pause/stop/hide for animation triggered by interaction (AAA).
  • Respect prefers-reduced-motion for vestibular disorders.
  • Avoid parallax, big translate/scale animations, autoplaying carousels.
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

Also check matchMedia('(prefers-reduced-motion: reduce)').matches from JS to short-circuit framer-motion / Lottie animations.

21. Internationalization & RTL Intermediate

  • <html lang="en"> on every page; lang on inline foreign-language spans.
  • Use logical CSS properties: margin-inline-start instead of margin-left, so RTL flips automatically.
  • dir="auto" on <input>/<textarea> for user-generated content.
  • Don't bake text into images.
  • Avoid date/number formatting via string concatenation — use Intl.DateTimeFormat, Intl.NumberFormat.

22. Mobile & Touch a11y Intermediate

  • Target size WCAG 2.5.5 (AAA) ≥ 44×44 CSS px; WCAG 2.2 (AA) 24×24 minimum spacing.
  • Allow zoom — don't set user-scalable=no in viewport meta.
  • Support landscape AND portrait (WCAG 1.3.4).
  • Use OS gestures sparingly; provide alternatives (WCAG 2.5.1).
  • VoiceOver (iOS) and TalkBack (Android) work with the same ARIA you ship for desktop.

23. Cognitive Accessibility Intermediate

  • Plain language; aim for grade-8 reading level on consumer apps.
  • Consistent navigation across pages (WCAG 3.2.3).
  • Don't auto-log-out without warning.
  • Provide undo for destructive actions.
  • Avoid CAPTCHAs that rely on visual puzzles — offer alternatives (WCAG 2.2: Accessible Authentication).
  • Break long forms into steps with clear progress.

25. Automated Testing — axe, Lighthouse, ESLint Intermediate

Automated tools catch ~30–50% of issues. Necessary but not sufficient.

ESLint plugin

npm i -D eslint-plugin-jsx-a11y
// .eslintrc
{ "extends": ["plugin:jsx-a11y/recommended"] }

axe-core in unit tests (Jest + RTL)

import { render } from '@testing-library/react';
import { axe, toHaveNoViolations } from 'jest-axe';
expect.extend(toHaveNoViolations);

test('login is accessible', async () => {
  const { container } = render(<Login />);
  expect(await axe(container)).toHaveNoViolations();
});

axe in Playwright / Cypress

// Playwright
import AxeBuilder from '@axe-core/playwright';
const { violations } = await new AxeBuilder({ page }).analyze();
expect(violations).toEqual([]);

Lighthouse

Built into Chrome DevTools. Audits color contrast, ARIA validity, headings, link names. Score > 95 in CI is a good gate.

Browser extensions

  • axe DevTools (Deque) — most thorough.
  • WAVE (WebAIM) — visual overlays.
  • Accessibility Insights (Microsoft) — guided manual + automated.
  • ARC Toolkit — quick checks.

26. Manual Testing Checklist Intermediate

  • Unplug your mouse — can you reach every control with Tab?
  • Is focus always visible?
  • Tab order matches visual order?
  • Can you submit / cancel / close from the keyboard?
  • Zoom to 200% — does the layout still work? No horizontal scroll? (WCAG 1.4.10 reflow at 320 px)
  • Disable CSS — is the content still in a logical order?
  • Disable images — are alt texts meaningful?
  • Use a screen reader to read each interactive element.
  • Toggle prefers-reduced-motion — animations stop?
  • Force prefers-color-scheme: dark — contrast still passes?

27. Remediating 100s of Violations — Batch Approach Critical

This is a real SDE3-level scenario. You inherit a codebase with hundreds of axe violations. The wrong answer is "fix them one by one".

  1. Audit & categorize — run axe sitewide, group by rule (e.g., "230 missing-alt", "120 color-contrast", "60 button-name"). Most violations cluster around < 10 root causes.
  2. Fix at the root — one design-system fix often kills hundreds:
    • Update <Button> to require children or aria-label.
    • Add a token system that enforces contrast at compile time.
    • Wrap all <Modal> instances with focus trap + dialog role.
  3. Add CI gates — block new violations even before you fix the old ones (delta budget).
  4. ESLint + axe in CI as the foundation.
  5. Triage by impact: critical/serious first, by traffic-weighted page.
  6. Track in a dashboard (axe-watcher, Sentry, in-house). Communicate weekly progress.
  7. Pair with design on contrast / focus tokens — a11y is co-owned.
  8. Bring in a screen reader user for usability testing — automated tools won't catch awkward UX.
Resume bullet (real) "Reduced WCAG 2.1 AA violations from 120+ to 0 across a 200-screen Angular dashboard by introducing axe-CI gates, refactoring 7 design-system components, and standardizing focus management; cut accessibility-related production tickets by 80%."

28. Best Practices Checklist Intermediate

Structure
  • One <h1>, ordered headings.
  • Landmarks: header/nav/main/footer.
  • Skip-link as first focusable.
  • lang on <html>.
Forms
  • Visible labels for every input.
  • autocomplete tokens.
  • Tie errors with aria-describedby + role="alert".
  • Focus first invalid on submit.
Keyboard / Focus
  • Visible focus, only via :focus-visible.
  • Trap focus in modals; restore on close.
  • Roving tabindex on composite widgets.
  • Never tabindex>0.
ARIA & SR
  • Native first; ARIA only when needed.
  • Live region for async announcements.
  • Test with NVDA + VoiceOver.
  • Run axe in CI.

29. Top Interview Questions Advanced

Q1. What is WCAG and what are its principles?
Web Content Accessibility Guidelines, maintained by the W3C. Built on POUR: Perceivable, Operable, Understandable, Robust. Three conformance levels — A, AA, AAA — with AA being the legal/industry standard.
Q2. Difference between aria-label, aria-labelledby, and aria-describedby?
aria-label: provides an accessible name as a string.
aria-labelledby: accessible name from another element's id(s); wins over aria-label.
aria-describedby: extra description (announced after the name); used for hints, errors.
Q3. Why is semantic HTML preferred over ARIA?
Native elements come with built-in role, keyboard support, focus, and AT integration. No ARIA is better than bad ARIA. Use ARIA only to fill semantic gaps not covered by HTML.
Q4. How do you make a custom dropdown accessible?
Use the WAI-ARIA combobox or listbox pattern: role="combobox" on the input, aria-expanded, aria-controls pointing to the listbox, aria-activedescendant on the input pointing to the focused option. Arrow keys move within options, Enter selects, Esc closes. Trap focus inside.
Q5. What's a focus trap and how do you build one?
A focus trap keeps Tab cycling within a container (a modal). Find first & last focusable elements; on Tab from last → focus first; on Shift+Tab from first → focus last. Use the native <dialog> with showModal() for free trapping.
Q6. What's the roving tabindex pattern?
Used for composite widgets (toolbars, tabs, listboxes). Only one child has tabindex="0" at a time; the rest are -1. Arrow keys move focus AND swap the tabindex. Result: a single tab stop into the widget, then arrow keys inside.
Q7. What is the accessibility tree?
A parallel tree built from the DOM that exposes role, name, state, and value to assistive tech. display:none, visibility:hidden, and aria-hidden=true remove nodes. Visually hiding without removing means using .sr-only CSS.
Q8. How do you announce dynamic content changes (toasts, search results)?
Use a live region (aria-live="polite" or role="status" for non-urgent; aria-live="assertive" or role="alert" for urgent). The container must exist on initial paint; updating its text content triggers the announcement.
Q9. What contrast ratio does WCAG AA require?
4.5:1 for normal text, 3:1 for large text (≥18pt or ≥14pt bold), 3:1 for UI components and graphical objects. WCAG 2.2 also requires 3:1 for the focus indicator.
Q10. How do you handle focus in a single-page app on route change?
After navigation, focus the new page's heading (often <h1 tabindex="-1">) and announce the title in a live region. Update document.title. Don't leave focus on the old (now-detached) link.
Q11. <button> vs <div onClick> — what do you lose?
Buttons are focusable, keyboard-operable (Enter/Space), announced as "button", submit forms, support :disabled, and respect form/fieldset disabling. Divs need tabindex, role="button", key handlers, and still don't behave the same for AT.
Q12. What does aria-hidden="true" do? Common pitfall?
Removes an element (and descendants) from the accessibility tree. Pitfall: applying it to a focusable element makes it visible & tabbable but invisible to AT — a confusing "ghost". Combine with tabindex="-1" or use inert.
Q13. Difference between aria-disabled and disabled?
disabled removes the element from the tab order, makes it non-interactive, and excludes it from form submission. aria-disabled="true" communicates the state to AT but the element remains focusable — useful when you want users to focus the disabled control to learn why it's disabled.
Q14. How would you make an icon-only button accessible?
Add aria-label describing the action. Mark the SVG aria-hidden="true" so its content doesn't double-announce. Ensure 44×44 px target size and 3:1 contrast with surroundings.
Q15. How do you test accessibility?
Layered approach: ESLint jsx-a11y while coding → axe-core in unit/E2E tests in CI → Lighthouse audit → manual keyboard test → screen reader (NVDA + VoiceOver) → user testing with disabled users.
Q16. What is the difference between role="alert" and role="status"?
Both are live regions. alert = assertive (interrupts current speech) — use for errors. status = polite (waits for idle) — use for non-critical updates like "Saved".
Q17. What is the "first rule of ARIA"?
"If you can use a native HTML element with the semantics and behavior you require already built in, instead of repurposing an element and adding ARIA, do so."
Q18. How would you make a modal accessible?
Use <dialog> + showModal() if possible. Otherwise: role="dialog" + aria-modal="true" + aria-labelledby; trap focus inside; mark background inert; close on Esc; restore focus to the trigger on close; initial focus on the dialog (or first input).
Q19. Explain skip-links.
A link as the first focusable element that jumps focus past repeated nav directly to the main content. Hidden visually until focused. Required for WCAG 2.4.1 (Bypass Blocks).
Q20. What's prefers-reduced-motion?
A CSS media query / JS matchMedia that reflects the user's OS preference for reduced motion. Use it to short-circuit animations that may trigger vestibular disorders.
Q21. What is the inert attribute?
A modern boolean attribute that makes an element & its subtree unfocusable AND ignored by AT — perfect for hiding background content under a modal. Replaces verbose aria-hidden + tabindex="-1" recursion.
Q22. Walk me through making a tab component accessible.
role="tablist" on container; each role="tab" with aria-selected and aria-controls="panelId"; matching role="tabpanel" with aria-labelledby="tabId". Roving tabindex on tabs. Arrow Right/Left moves between tabs (and activates them in the "automatic" pattern), Home/End jump to first/last. Hide inactive panels with hidden.
Q23. How do you handle a long list of dynamically-loaded items for AT users?
Announce additions via a polite live region ("10 more results loaded"). Use aria-busy="true" while loading. For "infinite scroll", offer a "Load more" button as an alternative — auto-loading is hostile to keyboard/AT users.
Q24. What's the difference between visibility: hidden, display: none, opacity: 0, and .sr-only?
display:none + visibility:hidden → removed from a11y tree.
opacity:0 → still in a11y tree, still focusable.
.sr-only (clip/positioned offscreen) → in a11y tree but not visible. Use for visually-hidden labels and skip-links.
Q25. You've inherited a project with 120+ a11y violations. How do you approach it?
See §27 in this guide — audit, group by rule, fix at the root in the design system, gate new violations in CI, triage by impact, track and communicate progress weekly, and finish with screen reader user testing.

30. Real-World Scenarios Advanced

Scenario A — "Build a fully accessible autocomplete"

  • Use the WAI-ARIA combobox pattern (1.2 spec).
  • role="combobox" on input, aria-expanded, aria-controls="listbox", aria-autocomplete="list".
  • aria-activedescendant updates as user arrows through results — focus stays in the input.
  • Live region announces "X results, use up and down arrows".
  • Esc clears or closes; Enter selects.

Scenario B — "Login form keeps failing accessibility"

  • Inputs probably lack <label for> — placeholder isn't enough.
  • Missing autocomplete tokens (username, current-password).
  • Errors not announced — wrap in role="alert".
  • Submit button disabled while invalid → users can't trigger the error announcement; let them submit.
  • Password show/hide button missing aria-label & aria-pressed.

Scenario C — "Toast notifications aren't read by screen readers"

  • Confirm a single live region exists at app root with role="status".
  • Toast renders into THAT region, not a fresh one each time.
  • Clear text before re-setting if the same message repeats.
  • Don't auto-dismiss too fast — give AT time to announce.

Scenario D — "Make a complex data table accessible"

  • Decide: simple <table> (just data) vs role="grid" (interactive cells).
  • Use <caption> + scope="col/row".
  • Sort buttons with aria-sort.
  • For grids: roving tabindex, arrow nav, Home/End/PgUp/PgDn.
  • Announce row count and current cell coordinates in a live region as user navigates.

31. Rapid-Fire Gotchas Advanced

  • Placeholder ≠ label. Always use <label>.
  • Never tabindex>0. Use 0 or -1 only.
  • outline: none without a replacement = WCAG fail.
  • Auto-playing carousels violate WCAG 2.2.2 unless pausable.
  • Click handlers on divs miss keyboard support entirely.
  • Headings for styling (h3 because it "looks right") break document outline.
  • Modals without focus trap let users Tab to background content.
  • Modal opens but background still scrolls — set inert on background and lock body scroll.
  • aria-hidden on focusable elements = ghost element.
  • SVG without title/aria-label when used as standalone graphic.
  • Decorative SVG needs aria-hidden="true" or role="presentation".
  • Disabled submit button swallows error announcements — let users submit.
  • Live region added after announcement won't fire — must exist in DOM first.
  • Same string twice in a live region → no re-announce.
  • Color-only indicators (red border for error) fail WCAG 1.4.1.
  • Missing lang attribute → AT mispronounces.
  • Toast that disappears in 2 seconds too fast for AT & cognitive disabilities.
  • Custom checkbox without aria-checked updating → state lost.
  • Image inside button needs alt OR button needs aria-label, not both.
  • Modal with Escape only — also need a visible Close button.
  • title attribute for accessible name is fragile (mobile, keyboard-only); don't rely on it.
  • Skip-link must be visible on focus — common to forget the :focus style.
  • Toast/snackbar with action — that action must be keyboard reachable before dismiss.
  • SPA route change without focus management leaves AT confused.
  • Drag-and-drop without keyboard alternative = WCAG fail (2.5.7 in WCAG 2.2).
