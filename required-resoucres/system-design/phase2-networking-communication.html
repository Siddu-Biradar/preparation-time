1. HTTP Fundamentals

Beginner

Theory: HTTP Protocol

HTTP (HyperText Transfer Protocol) is a request-response protocol. The client sends a request, the server returns a response. It's stateless — each request is independent (no memory of previous requests).

HTTP/1.1 vs HTTP/2 vs HTTP/3

FeatureHTTP/1.1HTTP/2HTTP/3
TransportTCPTCPQUIC (UDP-based)
Multiplexing❌ (one request per connection)✅ (multiple streams per connection)✅ (+ no head-of-line blocking)
Header Compression❌HPACKQPACK
Server Push❌✅✅
Connection SetupTCP + TLS (3 RTT)TCP + TLS (2-3 RTT)0-1 RTT (QUIC)
Head-of-line blockingTCP levelTCP level (shared)❌ (per-stream)
// HTTP/1.1 problem: 6 connections per origin limit
// Browser opens max 6 TCP connections to same domain
// If you have 20 resources → queuing!

// HTTP/2 solution: Multiplexing
// Single TCP connection handles ALL requests simultaneously
// Each request is a "stream" with a unique ID
// No need for domain sharding, CSS sprites, or resource inlining!

// HTTP/3 with QUIC:
// Built on UDP, handles packet loss per-stream
// If stream 3 loses a packet, streams 1,2,4 continue unblocked
// 0-RTT reconnection for returning visitors

HTTP Methods (Semantic Meaning)

MethodSemanticIdempotentSafeBody
GETRetrieve resourceYesYes❌
POSTCreate resourceNoNo✅
PUTReplace entire resourceYesNo✅
PATCHPartial updateNo*No✅
DELETERemove resourceYesNoOptional
OPTIONSCORS preflight / capabilitiesYesYes❌
HEADGET without body (headers only)YesYes❌

HTTP Status Codes (Must Know)

// 2xx — Success
200 OK           // Standard success
201 Created      // Resource created (POST)
204 No Content   // Success, no body (DELETE)

// 3xx — Redirection
301 Moved Permanently  // Resource moved (cacheable)
302 Found              // Temporary redirect
304 Not Modified       // Use cached version (conditional GET)

// 4xx — Client Errors
400 Bad Request        // Malformed request
401 Unauthorized       // No/invalid auth credentials
403 Forbidden          // Auth valid, but no permission
404 Not Found          // Resource doesn't exist
409 Conflict           // State conflict (duplicate, version mismatch)
422 Unprocessable      // Valid syntax, invalid semantics
429 Too Many Requests  // Rate limited

// 5xx — Server Errors
500 Internal Server Error  // Unexpected server failure
502 Bad Gateway            // Upstream server error
503 Service Unavailable    // Server overloaded/maintenance
504 Gateway Timeout        // Upstream didn't respond in time

2. REST API Design

Beginner

Theory: REST Principles

REST (Representational State Transfer) is an architectural style with constraints:

  1. Client-Server: Separate UI from data storage
  2. Stateless: Each request contains all info needed (no server-side session)
  3. Cacheable: Responses must define if they're cacheable
  4. Uniform Interface: Resources identified by URIs, manipulated via representations
  5. Layered System: Client can't tell if connected to server directly or via proxy

RESTful URL Design

// GOOD — Resource-based URLs:
GET    /api/v1/products              // List all products
GET    /api/v1/products/123          // Get specific product
POST   /api/v1/products              // Create product
PUT    /api/v1/products/123          // Replace product
PATCH  /api/v1/products/123          // Partial update
DELETE /api/v1/products/123          // Delete product

// Nested resources:
GET    /api/v1/products/123/reviews  // Reviews for product 123
POST   /api/v1/products/123/reviews  // Add review to product 123

// Filtering, sorting, pagination:
GET    /api/v1/products?category=electronics&sort=-price&page=2&limit=20

// BAD — Action-based URLs (not RESTful):
POST   /api/getProducts          ❌
POST   /api/deleteProduct/123    ❌
GET    /api/fetchUserData        ❌

Angular HTTP Client Patterns

// ═══ Service Layer Pattern ═══
@Injectable({ providedIn: 'root' })
export class ProductService {
  private readonly baseUrl = '/api/v1/products';
  
  constructor(private http: HttpClient) {}

  // GET with params
  getProducts(filters: ProductFilters): Observable<PaginatedResponse<Product>> {
    const params = new HttpParams()
      .set('category', filters.category || '')
      .set('page', filters.page.toString())
      .set('limit', filters.limit.toString())
      .set('sort', filters.sortBy || '-createdAt');
    
    return this.http.get<PaginatedResponse<Product>>(this.baseUrl, { params });
  }

  // POST with body
  createProduct(product: CreateProductDto): Observable<Product> {
    return this.http.post<Product>(this.baseUrl, product);
  }

  // PUT (full replace)
  updateProduct(id: string, product: Product): Observable<Product> {
    return this.http.put<Product>(`${this.baseUrl}/${id}`, product);
  }

  // PATCH (partial update)
  patchProduct(id: string, changes: Partial<Product>): Observable<Product> {
    return this.http.patch<Product>(`${this.baseUrl}/${id}`, changes);
  }

  // DELETE
  deleteProduct(id: string): Observable<void> {
    return this.http.delete<void>(`${this.baseUrl}/${id}`);
  }
}

// ═══ HTTP Interceptor for Auth ═══
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const authService = inject(AuthService);
  const token = authService.getToken();
  
  if (token) {
    req = req.clone({
      setHeaders: { Authorization: `Bearer ${token}` }
    });
  }
  
  return next(req).pipe(
    catchError((error: HttpErrorResponse) => {
      if (error.status === 401) {
        authService.logout();
        inject(Router).navigate(['/login']);
      }
      return throwError(() => error);
    })
  );
};

4. WebSockets & Real-Time Communication

Intermediate

Theory: WebSocket Protocol

WebSocket provides full-duplex, persistent communication over a single TCP connection. Unlike HTTP's request-response model, either side can send messages at any time.

// WebSocket Handshake (HTTP Upgrade):
// Client → Server:
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

// Server → Client:
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

// After handshake: bidirectional message frames (no HTTP overhead!)

┌──────────┐                  ┌──────────┐
│  Client  │ ═══WebSocket═══  │  Server  │
│          │ ←── message ──── │          │
│          │ ──── message ──→ │          │
│          │ ←── message ──── │          │
│          │ ──── message ──→ │          │
└──────────┘                  └──────────┘
  Messages flow in BOTH directions at ANY time

Angular WebSocket Implementation

// ═══ Robust WebSocket Service with Reconnection ═══
@Injectable({ providedIn: 'root' })
export class WebSocketService {
  private socket$ = new ReplaySubject<WebSocket>(1);
  private messages$ = new Subject<any>();
  private reconnectAttempts = 0;
  private maxReconnectAttempts = 5;
  private reconnectInterval = 1000; // starts at 1s, doubles each retry

  connect(url: string): Observable<any> {
    this.createConnection(url);
    return this.messages$.asObservable();
  }

  private createConnection(url: string) {
    const ws = new WebSocket(url);

    ws.onopen = () => {
      console.log('WebSocket connected');
      this.reconnectAttempts = 0; // Reset on successful connect
      this.socket$.next(ws);
    };

    ws.onmessage = (event) => {
      try {
        const data = JSON.parse(event.data);
        this.messages$.next(data);
      } catch(e) {
        this.messages$.next(event.data);
      }
    };

    ws.onclose = (event) => {
      if (!event.wasClean && this.reconnectAttempts < this.maxReconnectAttempts) {
        // Exponential backoff reconnection
        const delay = this.reconnectInterval * Math.pow(2, this.reconnectAttempts);
        this.reconnectAttempts++;
        console.log(`Reconnecting in ${delay}ms (attempt ${this.reconnectAttempts})`);
        setTimeout(() => this.createConnection(url), delay);
      }
    };

    ws.onerror = (error) => {
      console.error('WebSocket error:', error);
    };
  }

  send(message: any) {
    this.socket$.pipe(take(1)).subscribe(ws => {
      if (ws.readyState === WebSocket.OPEN) {
        ws.send(JSON.stringify(message));
      }
    });
  }

  disconnect() {
    this.socket$.pipe(take(1)).subscribe(ws => ws.close());
  }
}

// Usage in component:
export class ChatComponent implements OnInit, OnDestroy {
  messages: ChatMessage[] = [];
  private destroy$ = new Subject<void>();

  constructor(private ws: WebSocketService) {}

  ngOnInit() {
    this.ws.connect('wss://api.example.com/chat')
      .pipe(takeUntil(this.destroy$))
      .subscribe(msg => this.messages.push(msg));
  }

  sendMessage(text: string) {
    this.ws.send({ type: 'chat', text, timestamp: Date.now() });
  }

  ngOnDestroy() {
    this.destroy$.next();
    this.ws.disconnect();
  }
}

Use Cases for WebSockets

  • Chat applications (WhatsApp Web, Slack)
  • Live notifications (email, social media)
  • Collaborative editing (Google Docs, Figma)
  • Live sports scores / stock tickers
  • Online gaming (multiplayer state sync)

// ═══ SSE Implementation ═══

// Backend (Node.js):
app.get('/api/events', (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive'
  });

  // Send events:
  const sendEvent = (data, event = 'message') => {
    res.write(`event: ${event}\n`);
    res.write(`data: ${JSON.stringify(data)}\n`);
    res.write(`id: ${Date.now()}\n\n`);  // Last-Event-ID for reconnection
  };

  sendEvent({ status: 'connected' }, 'open');
  
  const interval = setInterval(() => {
    sendEvent({ price: Math.random() * 100 }, 'stock-update');
  }, 1000);

  req.on('close', () => clearInterval(interval));
});

// Frontend (Angular):
@Injectable({ providedIn: 'root' })
export class SseService {
  private zone = inject(NgZone);

  getEvents(url: string): Observable<MessageEvent> {
    return new Observable(observer => {
      const eventSource = new EventSource(url);

      eventSource.onmessage = (event) => {
        this.zone.run(() => observer.next(event));
      };

      eventSource.addEventListener('stock-update', (event: any) => {
        this.zone.run(() => observer.next(event));
      });

      eventSource.onerror = (error) => {
        // EventSource automatically reconnects!
        // Last-Event-ID header sent on reconnection
        console.warn('SSE error, reconnecting...', error);
      };

      return () => eventSource.close();
    });
  }
}

// When to use SSE vs WebSocket:
// SSE: Notifications, live feeds, stock prices, build logs (server→client only)
// WebSocket: Chat, gaming, collab editing (need bidirectional)

6. Polling Strategies

Beginner

Theory: Short Polling vs Long Polling

// ═══ SHORT POLLING ═══
// Client repeatedly asks server at fixed intervals
// Simple but wasteful (many empty responses)

// Angular implementation:
pollOrders(): Observable<Order[]> {
  return interval(5000).pipe(             // Every 5 seconds
    startWith(0),                          // Immediately on subscribe
    switchMap(() => this.http.get<Order[]>('/api/orders')),
    distinctUntilChanged((a, b) => JSON.stringify(a) === JSON.stringify(b)),
    retry(3)
  );
}

// ═══ LONG POLLING ═══
// Client sends request, server HOLDS it open until new data or timeout
// More efficient than short polling (fewer empty responses)

// Server (holds connection until data available):
app.get('/api/updates', async (req, res) => {
  const lastId = req.headers['last-event-id'] || 0;
  const timeout = setTimeout(() => res.json({ data: null }), 30000);
  
  // Wait for new data...
  const data = await waitForNewData(lastId);
  clearTimeout(timeout);
  res.json({ data, id: data.id });
});

// Angular:
longPollUpdates(): Observable<Update> {
  const poll = (): Observable<Update> => {
    return this.http.get<{data: Update, id: string}>('/api/updates').pipe(
      tap(res => { if(res.data) this.lastId = res.id; }),
      filter(res => res.data !== null),
      map(res => res.data),
      // Immediately start next long poll after response:
      concatMap(data => merge(of(data), poll()))
    );
  };
  return poll();
}

// ═══ COMPARISON ═══
// Short Polling: Simple, but network waste. Use for: dashboards, status checks
// Long Polling: Efficient, but complex. Use for: chat (before WebSocket era)
// SSE: Best for server→client streams. Use for: notifications, live feeds
// WebSocket: Best for bidirectional real-time. Use for: chat, gaming, collab

7. CORS Deep Dive

Intermediate

Theory: Same-Origin Policy & CORS

Same-Origin Policy (SOP) prevents scripts on one origin from accessing resources on another origin. An origin = scheme + host + port.

// Same origin:
https://app.example.com/page1  ↔  https://app.example.com/page2  ✅

// Different origin (port differs):
https://app.example.com        ↔  https://app.example.com:8080   ❌

// Different origin (subdomain differs):
https://app.example.com        ↔  https://api.example.com        ❌

// CORS = Server says "I allow this origin to access me"
// Server sends response headers:
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400  // Cache preflight for 24h

Preflight Requests (OPTIONS)

// Browser automatically sends OPTIONS preflight for "complex" requests:
// Complex = non-GET/POST, custom headers, or non-simple content types

// Step 1: Browser sends OPTIONS:
OPTIONS /api/products HTTP/1.1
Origin: https://myapp.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

// Step 2: Server responds:
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400

// Step 3: If allowed, browser sends actual PUT request

// OPTIMIZATION: Set Max-Age to reduce preflight requests!
// Without Max-Age: EVERY complex request triggers OPTIONS first (2x latency)

Angular Dev Proxy (bypass CORS locally)

// proxy.conf.json — development only!
{
  "/api": {
    "target": "http://localhost:3000",
    "secure": false,
    "changeOrigin": true,
    "pathRewrite": { "^/api": "" }
  }
}

// angular.json:
"serve": {
  "options": {
    "proxyConfig": "proxy.conf.json"
  }
}
// Now: http://localhost:4200/api/products → http://localhost:3000/products
// No CORS issues in development!

8. HTTP Caching

Intermediate

Theory: Cache Hierarchy

┌──────────────────────────────────────────────────────────┐
│  Request flow (checks each cache layer):                 │
│                                                          │
│  Browser Memory Cache (fastest, per-tab, volatile)       │
│       ↓ miss                                             │
│  Browser Disk Cache (persistent, shared across tabs)     │
│       ↓ miss                                             │
│  Service Worker Cache (programmatic, offline support)    │
│       ↓ miss                                             │
│  CDN / Edge Cache (geographically distributed)           │
│       ↓ miss                                             │
│  Origin Server (generates fresh response)                │
└──────────────────────────────────────────────────────────┘

Cache-Control Headers

// ═══ IMMUTABLE ASSETS (JS, CSS with hash in filename) ═══
// main.abc123.js — filename changes when content changes
Cache-Control: public, max-age=31536000, immutable
// Cache for 1 year! Browser NEVER revalidates (filename = cache key)

// ═══ HTML (must always revalidate) ═══
Cache-Control: no-cache
// Forces browser to ALWAYS check with server (conditional GET)
// If content unchanged, server responds 304 Not Modified (no body!)

// ═══ API RESPONSES ═══
// Dynamic data that changes frequently:
Cache-Control: private, no-store
// Never cache (user-specific, sensitive)

// Data that changes but can be stale briefly:
Cache-Control: private, max-age=60, stale-while-revalidate=600
// Use cached version for 60s, then serve stale for 600s while revalidating in background

// ═══ CONDITIONAL REQUESTS (ETag) ═══
// First response:
HTTP/1.1 200 OK
ETag: "abc123"
Cache-Control: no-cache

// Subsequent request:
GET /api/user HTTP/1.1
If-None-Match: "abc123"

// If unchanged:
HTTP/1.1 304 Not Modified  // No body! Saves bandwidth

// If changed:
HTTP/1.1 200 OK
ETag: "def456"
{new data...}

Angular Caching Strategy

// HTTP Interceptor for Caching API responses:
const cache = new Map<string, { response: any; timestamp: number }>();
const CACHE_TTL = 30000; // 30 seconds

export const cacheInterceptor: HttpInterceptorFn = (req, next) => {
  // Only cache GET requests
  if (req.method !== 'GET') {
    // Invalidate cache on mutations
    cache.forEach((_, key) => {
      if (key.startsWith(req.url.split('?')[0])) cache.delete(key);
    });
    return next(req);
  }

  const cached = cache.get(req.urlWithParams);
  if (cached && Date.now() - cached.timestamp < CACHE_TTL) {
    return of(new HttpResponse({ body: cached.response }));
  }

  return next(req).pipe(
    tap(event => {
      if (event instanceof HttpResponse) {
        cache.set(req.urlWithParams, { response: event.body, timestamp: Date.now() });
      }
    })
  );
};

9. CDN Architecture

Intermediate

Theory: How CDNs Work

A CDN (Content Delivery Network) is a geographically distributed network of servers that cache and serve content closer to users.

// Without CDN:
User (Mumbai) ──────── 200ms ────────→ Origin (US-East)

// With CDN:
User (Mumbai) ──── 20ms ────→ CDN Edge (Mumbai) ──cache hit──→ Response!
                                    │ cache miss
                                    └──── 200ms ────→ Origin (US-East)
                                                         │
                                    ←──── cache + serve ──┘

// CDN Decision Flow:
// 1. User request hits nearest CDN edge (DNS-based routing)
// 2. Edge checks if cached copy exists and is fresh
// 3. If FRESH → serve immediately (cache HIT)
// 4. If STALE → serve stale + revalidate in background (stale-while-revalidate)
// 5. If MISS → fetch from origin, cache, serve

CDN Strategies for Angular Apps

// Deploy strategy:
// 1. Static assets (JS/CSS/images) → CDN with immutable caching
// 2. index.html → CDN with no-cache (always revalidate)
// 3. API → NOT on CDN (or CDN with short TTL + vary headers)

// Cloudflare/AWS CloudFront config:
{
  "patterns": [
    { "path": "*.js", "cache": "1y", "immutable": true },
    { "path": "*.css", "cache": "1y", "immutable": true },
    { "path": "*.woff2", "cache": "1y", "immutable": true },
    { "path": "index.html", "cache": "no-cache" },
    { "path": "/api/*", "cache": "bypass" }
  ]
}

// Cache Invalidation:
// Angular uses content-hashed filenames (main.abc123.js)
// On deploy: new hash = new URL = CDN treats as new resource
// Old files: CDN expires naturally (no manual purge needed!)
// index.html: Points to new hashed files → cache busted automatically

10. Service Workers & Offline Support

Advanced

Theory: Service Worker Lifecycle

// Service Worker sits between browser and network:
┌──────────┐     ┌─────────────────┐     ┌──────────┐
│  Browser │ ←→  │  Service Worker │ ←→  │  Network │
│  (Page)  │     │  (Proxy/Cache)  │     │  (Server)│
└──────────┘     └─────────────────┘     └──────────┘

// Lifecycle:
// 1. Register → 2. Install (cache assets) → 3. Activate (claim clients)
// 4. Idle (listening for fetch/push events)
// 5. Update (new SW found → install → waiting → activate)

// Caching Strategies:
// ┌─────────────────────────────────────────────────────┐
// │ Cache First (Static assets)                         │
// │ Request → Cache → [Hit? Serve!] [Miss? Network]     │
// ├─────────────────────────────────────────────────────┤
// │ Network First (API calls)                           │
// │ Request → Network → [OK? Serve + Cache] [Fail? Cache]│
// ├─────────────────────────────────────────────────────┤
// │ Stale While Revalidate (Semi-dynamic)               │
// │ Request → Cache (serve stale) + Network (update cache)│
// └─────────────────────────────────────────────────────┘

Angular PWA (@angular/pwa)

12. AbortController & Request Cancellation

Critical

Theory: Why Request Cancellation Matters

Without cancellation, your app suffers from race conditions: user types "ang", "angu", "angul" → 3 requests fire, but response for "ang" may arrive AFTER "angul" response, overwriting correct results with stale data.

// ═══ PROBLEM: Race Condition Without Cancellation ═══
// User types: a → an → ang → angu
// Requests:   GET /search?q=a    (200ms)
//             GET /search?q=an   (150ms)  ← arrives first!
//             GET /search?q=ang  (300ms)
//             GET /search?q=angu (100ms)  ← arrives second!
// Without cancellation: UI shows results for "a" (last to resolve)
// With cancellation: Only "angu" request is active, others aborted

AbortController API

// ═══ NATIVE AbortController ═══
const controller = new AbortController();
const signal = controller.signal;

// Pass signal to fetch:
fetch('/api/search?q=angular', { signal })
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => {
    if (err.name === 'AbortError') {
      console.log('Request cancelled'); // Expected, not an error
    } else {
      throw err; // Real error
    }
  });

// Cancel the request:
controller.abort(); // Immediately cancels the in-flight request

// ═══ AbortSignal.timeout() — Auto-cancel after timeout ═══
fetch('/api/slow-endpoint', {
  signal: AbortSignal.timeout(5000) // Cancel if no response in 5s
});

// ═══ AbortSignal.any() — Cancel from multiple sources ═══
const userCancel = new AbortController();
const combinedSignal = AbortSignal.any([
  userCancel.signal,
  AbortSignal.timeout(10000)
]);
fetch('/api/data', { signal: combinedSignal });

Angular: Cancellation with RxJS switchMap

// ═══ RxJS switchMap = AUTOMATIC cancellation ═══
// switchMap unsubscribes from previous inner observable when new value arrives
// This AUTOMATICALLY cancels the previous HTTP request

@Injectable({ providedIn: 'root' })
export class SearchService {
  private http = inject(HttpClient);
  private searchTerms$ = new Subject<string>();

  results$ = this.searchTerms$.pipe(
    debounceTime(300),           // Wait 300ms after last keystroke
    distinctUntilChanged(),      // Don't search if same term
    switchMap(term =>           // ← CANCELS previous request automatically
      term.length < 2
        ? of([])
        : this.http.get<Result[]>(`/api/search?q=${term}`)
    )
  );

  search(term: string) {
    this.searchTerms$.next(term);
  }
}

// ═══ Cancel on route change (takeUntilDestroyed) ═══
@Component({ ... })
export class DataComponent {
  private destroyRef = inject(DestroyRef);

  ngOnInit() {
    this.http.get('/api/heavy-data').pipe(
      takeUntilDestroyed(this.destroyRef) // Cancel if user navigates away
    ).subscribe(data => this.data = data);
  }
}

// ═══ Manual cancellation with AbortController in Angular ═══
@Component({ ... })
export class UploadComponent {
  private abortController: AbortController | null = null;

  upload(file: File) {
    this.abortController = new AbortController();
    
    // Angular HttpClient doesn't natively support AbortController,
    // but unsubscribing from the observable cancels the XHR:
    this.uploadSub = this.http.post('/api/upload', file).subscribe({
      next: () => console.log('Done'),
      error: (err) => console.error(err)
    });
  }

  cancelUpload() {
    this.uploadSub?.unsubscribe(); // This cancels the underlying XHR!
  }
}
Common Mistake Using mergeMap instead of switchMap for search/autocomplete. mergeMap runs all requests in parallel — you get race conditions. Always use switchMap when only the latest result matters.
Interview Tip switchMap = only latest (search, autocomplete)
exhaustMap = ignore new until current finishes (form submit, login)
concatMap = queue in order (sequential file uploads)
mergeMap = all parallel (analytics events, logging)

Q: How do you prevent stale API responses from overwriting current data? (Google, Amazon, Flipkart)

Answer: Three approaches: (1) switchMap in RxJS — automatically cancels previous HTTP request when new one fires. (2) AbortController — explicitly cancel fetch with signal. (3) Request ID tracking — attach monotonically increasing ID to each request, ignore responses where ID < latest sent ID. In Angular, switchMap is the idiomatic solution. For fetch-based code, AbortController.abort() sends TCP RST, saving bandwidth.

13. Rate Limiting & Retry Logic

Advanced

Theory: Client-Side Rate Limiting

Even though rate limiting is typically a server concern, smart frontends implement client-side rate limiting to avoid hitting server limits, improve UX, and reduce unnecessary network usage.

StrategyHow It WorksUse Case
DebounceWait N ms after last event before firingSearch input, resize handler
ThrottleFire at most once per N msScroll handler, mouse move, analytics
Token BucketN tokens refill per second; each request costs 1 tokenAPI call limiting (prevent abuse)
Sliding WindowMax N requests in last T secondsProtecting against burst traffic
Queue + DrainQueue requests, process N per intervalBatch uploads, bulk operations
// ═══ TOKEN BUCKET Rate Limiter (Client-Side) ═══
class TokenBucketRateLimiter {
  private tokens: number;
  private lastRefill: number;

  constructor(
    private maxTokens: number = 10,
    private refillRate: number = 2 // tokens per second
  ) {
    this.tokens = maxTokens;
    this.lastRefill = Date.now();
  }

  private refill() {
    const now = Date.now();
    const elapsed = (now - this.lastRefill) / 1000;
    this.tokens = Math.min(this.maxTokens, this.tokens + elapsed * this.refillRate);
    this.lastRefill = now;
  }

  canProceed(): boolean {
    this.refill();
    if (this.tokens >= 1) {
      this.tokens -= 1;
      return true;
    }
    return false; // Rate limited — show "slow down" UI
  }
}

// ═══ Angular Interceptor: Respect Server Rate Limits (HTTP 429) ═══
export const rateLimitInterceptor: HttpInterceptorFn = (req, next) => {
  return next(req).pipe(
    catchError((error: HttpErrorResponse) => {
      if (error.status === 429) {
        // Parse Retry-After header
        const retryAfter = error.headers.get('Retry-After');
        const delayMs = retryAfter ? parseInt(retryAfter) * 1000 : 5000;
        
        // Show user feedback
        console.warn(`Rate limited. Retrying in ${delayMs}ms`);
        
        // Retry after the specified delay
        return timer(delayMs).pipe(
          switchMap(() => next(req))
        );
      }
      return throwError(() => error);
    })
  );
};

Exponential Backoff with Jitter

// ═══ PRODUCTION-GRADE Retry with Exponential Backoff + Jitter ═══

export const retryWithBackoff: HttpInterceptorFn = (req, next) => {
  const MAX_RETRIES = 3;
  const BASE_DELAY = 1000; // 1 second

  return next(req).pipe(
    retry({
      count: MAX_RETRIES,
      delay: (error: HttpErrorResponse, retryCount: number) => {
        // DON'T retry client errors (4xx) — those won't fix themselves
        if (error.status >= 400 && error.status < 500) {
          return throwError(() => error);
        }
        
        // DON'T retry non-idempotent requests (POST, DELETE) without idempotency key
        if (!req.headers.has('Idempotency-Key') && 
            ['POST', 'DELETE', 'PATCH'].includes(req.method)) {
          return throwError(() => error);
        }

        // Exponential backoff: 1s, 2s, 4s
        const exponentialDelay = BASE_DELAY * Math.pow(2, retryCount - 1);
        
        // Add jitter (±25%) to prevent thundering herd
        const jitter = exponentialDelay * 0.25 * (Math.random() * 2 - 1);
        const finalDelay = Math.round(exponentialDelay + jitter);
        
        console.log(`Retry ${retryCount}/${MAX_RETRIES} in ${finalDelay}ms`);
        return timer(finalDelay);
      }
    })
  );
};

// ═══ WHY JITTER? — Thundering Herd Problem ═══
// Without jitter: Server goes down, comes back up
//   All 10,000 clients retry at exactly 1s, 2s, 4s → overwhelming the server again!
// With jitter: Retries are spread out: 0.8s, 1.1s, 0.9s, 1.3s...
//   Server can recover gradually

// ═══ IDEMPOTENCY KEY — Safe retries for mutations ═══
// Problem: User clicks "Pay" → network timeout → retry → DOUBLE CHARGE!
// Solution: Attach unique key, server deduplicates
const payment$ = this.http.post('/api/pay', payload, {
  headers: { 'Idempotency-Key': crypto.randomUUID() }
});
// Server: if same key seen before, return cached response (no re-processing)

Circuit Breaker Pattern (Frontend)

// ═══ CIRCUIT BREAKER — Stop retrying when service is clearly down ═══
// States: CLOSED (normal) → OPEN (failing) → HALF-OPEN (testing recovery)

enum CircuitState { CLOSED, OPEN, HALF_OPEN }

@Injectable({ providedIn: 'root' })
export class CircuitBreakerService {
  private state = CircuitState.CLOSED;
  private failureCount = 0;
  private lastFailureTime = 0;
  
  private readonly FAILURE_THRESHOLD = 5;  // Open after 5 failures
  private readonly RECOVERY_TIMEOUT = 30000; // Try again after 30s

  canRequest(): boolean {
    if (this.state === CircuitState.CLOSED) return true;
    if (this.state === CircuitState.OPEN) {
      // Check if recovery timeout has passed
      if (Date.now() - this.lastFailureTime > this.RECOVERY_TIMEOUT) {
        this.state = CircuitState.HALF_OPEN;
        return true; // Allow ONE test request
      }
      return false; // Circuit is open, show fallback UI
    }
    return true; // HALF_OPEN — allow test request
  }

  recordSuccess() {
    this.failureCount = 0;
    this.state = CircuitState.CLOSED;
  }

  recordFailure() {
    this.failureCount++;
    this.lastFailureTime = Date.now();
    if (this.failureCount >= this.FAILURE_THRESHOLD) {
      this.state = CircuitState.OPEN;
      // Show fallback UI: "Service temporarily unavailable"
    }
  }
}
Interview Critical Always mention idempotency keys when discussing retry logic for payment/order APIs. Without them, retries can cause double-charges. This shows you understand real production systems.

14. Streaming & ReadableStream

Advanced

Theory: What is HTTP Streaming?

Traditional HTTP: Request → wait → receive ENTIRE response. Streaming: receive response in chunks as they're generated. Critical for large payloads, AI responses (ChatGPT-like UX), and progressive rendering.

TypeDirectionProtocolUse Case
Chunked TransferServer → ClientHTTP/1.1 Transfer-Encoding: chunkedProgressive HTML, AI text generation
ReadableStreamServer → ClientFetch API + streamsFile downloads, real-time logs
WritableStreamClient → ServerFetch API + upload streamingLarge file uploads
TransformStreamPipeJS Streams APIDecompression, parsing on-the-fly
// ═══ READING A STREAM (ChatGPT-like progressive text) ═══
async function streamAIResponse(prompt: string) {
  const response = await fetch('/api/ai/chat', {
    method: 'POST',
    body: JSON.stringify({ prompt }),
    headers: { 'Content-Type': 'application/json' }
  });

  // Get the ReadableStream from response body
  const reader = response.body!.getReader();
  const decoder = new TextDecoder();
  let fullText = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    
    // Decode chunk and append to display
    const chunk = decoder.decode(value, { stream: true });
    fullText += chunk;
    updateUI(fullText); // Progressive rendering!
  }
}

// ═══ ANGULAR: Streaming with HttpClient (reportProgress) ═══
// Angular HttpClient supports download progress but not streaming text natively.
// For streaming text, use fetch() directly:

@Injectable({ providedIn: 'root' })
export class StreamingService {
  private ngZone = inject(NgZone);
  
  streamChat(prompt: string): Observable<string> {
    return new Observable(observer => {
      const controller = new AbortController();
      
      fetch('/api/ai/stream', {
        method: 'POST',
        body: JSON.stringify({ prompt }),
        signal: controller.signal,
        headers: { 'Content-Type': 'application/json' }
      }).then(async response => {
        const reader = response.body!.getReader();
        const decoder = new TextDecoder();
        
        while (true) {
          const { done, value } = await reader.read();
          if (done) { observer.complete(); break; }
          
          const chunk = decoder.decode(value, { stream: true });
          this.ngZone.run(() => observer.next(chunk)); // Trigger CD
        }
      }).catch(err => observer.error(err));
      
      // Cleanup: abort stream on unsubscribe
      return () => controller.abort();
    });
  }
}

// Usage in component:
text = signal('');
ngOnInit() {
  this.streamingService.streamChat('Explain CORS')
    .subscribe(chunk => this.text.update(t => t + chunk));
}

// ═══ NDJSON STREAMING (Newline-Delimited JSON) ═══
// Server sends one JSON object per line, progressively:
// {"id":1,"status":"processing"}\n
// {"id":1,"status":"done","result":"..."}\n

async function* parseNDJSON(response: Response) {
  const reader = response.body!.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop()!; // Keep incomplete line in buffer
    
    for (const line of lines) {
      if (line.trim()) yield JSON.parse(line);
    }
  }
}

// ═══ BACKPRESSURE — When consumer is slower than producer ═══
// ReadableStream handles this automatically:
// If reader doesn't call .read(), the stream pauses (backpressure signal)
// The server stops sending chunks until client catches up
// This prevents memory overflow from buffering too much data
When to Use Streaming
  • AI/LLM responses — show text as it generates (like ChatGPT)
  • Large file downloads — show progress, allow cancellation
  • Real-time logs — tail -f style in browser
  • SSR streaming — send HTML head immediately, body streams in (faster TTFB)
  • Large JSON responses — parse progressively with NDJSON

Q: How would you implement a ChatGPT-like streaming response in Angular? (Google, startups)

Answer: Use native fetch() with ReadableStream (not HttpClient, which buffers the full response). Create an Observable wrapper: fetch with POST, get response.body.getReader(), loop with reader.read() yielding chunks via observer.next(). Use AbortController for cancellation on unsubscribe. Run inside NgZone to trigger change detection. For NDJSON, split on newlines and JSON.parse each line progressively. Show streaming text with a blinking cursor CSS animation.

13. Interview Questions (Previously Asked)

Q1: How would you design a real-time chat application's frontend? (Meta, Google, Flipkart)

Answer: WebSocket for bidirectional messaging. Connection management: reconnect with exponential backoff, heartbeat pings every 30s. Messages: optimistic UI (show immediately, confirm async). State: normalized message store (Map by messageId), conversation index. Offline: queue messages in IndexedDB, sync on reconnect with server-side ordering (vector clocks or timestamps). Typing indicators via lightweight WS events. Read receipts as background events. Pagination: cursor-based for history loading.

Q2: Explain HTTP caching strategy for a production Angular app. (Amazon, Microsoft)

Answer: index.html: no-cache (always revalidate, tiny file). JS/CSS bundles: immutable, max-age=1year (content-hashed filenames). Fonts: max-age=1year (rarely change). API responses: varies — user-specific data (private, no-store), product listings (stale-while-revalidate=60s), static configs (max-age=1h). Service Worker adds offline layer: Cache First for static assets, Network First for API. CDN handles geographic distribution with same cache rules.

Q3: What's the difference between WebSocket, SSE, and Long Polling? When to use each? (All companies)

Answer: WebSocket: Full duplex, persistent TCP connection, both sides send anytime. Use for: chat, gaming, collaboration. SSE: Server-to-client only, built on HTTP, auto-reconnection. Use for: notifications, live feeds, dashboards. Long Polling: Client holds request open, server responds when data available. Use for: legacy systems, simple notifications. Decision: Need bidirectional? → WebSocket. Server push only? → SSE (simpler). Firewall/proxy issues? → Long Polling (safest).

Q4: How do you handle API failures gracefully in a frontend app? (Amazon, Flipkart, Swiggy)

Answer: Layered approach: (1) Retry with exponential backoff for transient failures (5xx, timeout). (2) Circuit breaker pattern: after N failures, stop trying and show fallback UI. (3) Optimistic UI: show success immediately, rollback on failure. (4) Error boundaries: catch rendering errors, show degraded UI not white screen. (5) Offline queue: for mutations, store in IndexedDB, sync when online. (6) Stale data: show cached version with "last updated" indicator. (7) User feedback: toast notifications with retry button.

Q5: Design the networking layer for a food delivery app (Swiggy/Zomato). (Swiggy, PhonePe, Flipkart)

Answer: REST for CRUD (menu, orders). WebSocket for real-time order tracking (driver location every 3s). SSE for order status changes (placed → preparing → out → delivered). Caching: restaurant menus cached 5min (stale-while-revalidate), user location cached in memory. Offline: Service Worker caches last viewed restaurants. Retry: exponential backoff on payment APIs (idempotency key!). Rate limiting awareness: queue non-critical calls. BFF pattern: separate APIs for customer app vs restaurant app vs driver app.

Q6: Explain CORS. Why does it exist? How do you handle it? (All companies)

Answer: CORS (Cross-Origin Resource Sharing) is a security mechanism. Same-Origin Policy prevents malicious scripts from reading data across origins. CORS is how a server explicitly allows specific origins. Handling: (1) Server sets Access-Control-Allow-Origin header. (2) For complex requests (PUT, custom headers), browser sends preflight OPTIONS. (3) Set Access-Control-Max-Age to cache preflight. (4) Development: use Angular proxy (proxy.conf.json). (5) Never use Access-Control-Allow-Origin: * with credentials! (6) Cookies need: withCredentials + explicit origin + Allow-Credentials: true.
