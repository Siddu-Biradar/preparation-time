1. Core Web Vitals (CWV)

Critical

Theory: What Google Measures

Core Web Vitals are Google's standardized metrics for user experience. They directly impact SEO ranking and are the common language for performance discussions in interviews.

MetricFull NameMeasuresGoodNeeds WorkPoor
LCPLargest Contentful PaintLoading speed (when main content appears)≤ 2.5s2.5-4s> 4s
INPInteraction to Next PaintResponsiveness (delay between user input and visual update)≤ 200ms200-500ms> 500ms
CLSCumulative Layout ShiftVisual stability (unexpected movement of content)≤ 0.10.1-0.25> 0.25
// ═══ LCP — What counts as "largest contentful paint"? ═══
// - <img> elements
// - <video> poster images
// - Background images via url()
// - Block-level text elements (<h1>, <p>, etc.)
// LCP is the LAST such element to render above the fold

// Common LCP killers:
// 1. Large hero images not optimized
// 2. Render-blocking CSS/JS in <head>
// 3. Web fonts causing invisible text (FOIT)
// 4. Server response time (slow TTFB)
// 5. Client-side rendering (JS must execute first)

// ═══ INP — Interaction to Next Paint ═══
// Measures the WORST interaction latency across the page session
// Includes: click, tap, keypress (NOT scroll, hover)
// Breakdown: Input Delay + Processing Time + Presentation Delay
//
// Input Delay: Time between user click and handler starting
//   → Caused by: long tasks blocking main thread
// Processing Time: How long the event handler takes
//   → Caused by: expensive computation in handler
// Presentation Delay: Time from handler finish to next paint
//   → Caused by: complex layout/paint triggered by handler

// ═══ CLS — Cumulative Layout Shift ═══
// Measures visual instability — elements moving unexpectedly
// Layout shift score = impact fraction × distance fraction
//
// Common CLS killers:
// 1. Images without width/height (browser doesn't know size until loaded)
// 2. Ads/embeds injected without reserved space
// 3. Web fonts causing reflow (different metrics than fallback)
// 4. Dynamic content injected above existing content
// 5. Late-loading CSS that rearranges layout

How to Fix Each CWV

// ═══ FIX LCP ═══
// 1. Preload LCP image:
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">

// 2. Use SSR/SSG for immediate content (no JS dependency)
// 3. Optimize server response time (TTFB < 800ms)
// 4. Inline critical CSS (above-the-fold styles)
// 5. Use responsive images with srcset:
<img srcset="hero-400.webp 400w, hero-800.webp 800w, hero-1200.webp 1200w"
     sizes="(max-width: 600px) 400px, (max-width: 1000px) 800px, 1200px"
     src="hero-800.webp" alt="Hero" fetchpriority="high" />

// ═══ FIX INP ═══
// 1. Break long tasks (yield to main thread):
async function processLargeList(items) {
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);
    if (i % 100 === 0) {
      await scheduler.yield();  // Let browser handle user input
    }
  }
}

// 2. Move expensive work to Web Worker
// 3. Use requestIdleCallback for non-urgent work
// 4. Debounce/throttle frequent event handlers
// 5. Use CSS containment to limit paint scope

// ═══ FIX CLS ═══
// 1. Always set explicit dimensions:
<img width="800" height="600" src="..." alt="...">
// Or use aspect-ratio:
img { aspect-ratio: 4/3; width: 100%; }

// 2. Reserve space for dynamic content:
.ad-slot { min-height: 250px; }

// 3. Use font-display: optional (no layout shift):
@font-face {
  font-family: 'MyFont';
  src: url('/font.woff2') format('woff2');
  font-display: optional;  // Uses fallback if font loads late
}

// 4. Use transform for animations (not top/left/width/height):
.modal { transform: translateY(100%); } // No layout shift!

2. Rendering Performance (Browser Pipeline)

Intermediate

Theory: The Rendering Pipeline

// Browser rendering pipeline (every frame):
// ┌───────────┐   ┌───────────┐   ┌────────┐   ┌───────┐   ┌───────────┐
// │ JavaScript│ → │   Style   │ → │ Layout │ → │ Paint │ → │ Composite │
// │           │   │  (CSS)    │   │        │   │       │   │           │
// └───────────┘   └───────────┘   └────────┘   └───────┘   └───────────┘
//    ~4ms             ~2ms           ~2ms        ~2ms          ~1ms
//
// Total budget per frame at 60fps: 16.67ms (1000/60)
// Actual available: ~10ms (browser overhead)
//
// KEY INSIGHT: If you only change COMPOSITE properties (transform, opacity),
// browser skips Layout and Paint entirely! (GPU accelerated)

// ═══ LAYOUT THRASHING (Forced Reflow) ═══
// PROBLEM: Interleaving reads and writes forces browser to recalculate layout

// BAD — Forces layout recalculation on every iteration:
elements.forEach(el => {
  const height = el.offsetHeight;        // READ (triggers layout)
  el.style.height = height * 2 + 'px';  // WRITE (invalidates layout)
  // Next read triggers ANOTHER layout!
});

// GOOD — Batch reads, then batch writes:
const heights = elements.map(el => el.offsetHeight); // All READS first
elements.forEach((el, i) => {
  el.style.height = heights[i] * 2 + 'px';          // All WRITES
});
// Only ONE layout recalculation!

CSS Properties & Their Pipeline Cost

TriggersPropertiesCostUse When
Layout + Paint + Compositewidth, height, margin, padding, top, left, font-size🔴 Most expensiveOnly if necessary, never in animations
Paint + Compositecolor, background, box-shadow, border-radius🟡 ModerateOK for state changes, avoid in 60fps animations
Composite onlytransform, opacity, filter (GPU)🟢 CheapestALWAYS use for animations!
// ═══ will-change (Promote to compositor layer) ═══
// Tells browser to optimize element for future animation
.card-will-animate {
  will-change: transform;  // Browser creates GPU layer ahead of time
}
// WARNING: Don't overuse! Each layer = GPU memory
// Apply just before animation, remove after

// ═══ contain (Isolation for rendering) ═══
.widget {
  contain: layout style paint;  // OR: contain: content;
  // Tells browser: changes inside this element
  // do NOT affect anything outside it
  // Browser can skip recalculating ancestors!
}
// Use for: independent widgets, cards, chat messages

3. JavaScript Performance

Intermediate

Theory: Long Tasks & Main Thread

// A "Long Task" = any task taking > 50ms on the main thread
// During a long task: NO user interaction is processed! (page feels frozen)

// ═══ BREAKING LONG TASKS ═══

// Method 1: setTimeout (yields to main thread)
function processLargeArray(items) {
  let index = 0;
  function chunk() {
    const end = Math.min(index + 100, items.length);
    while (index < end) {
      processItem(items[index++]);
    }
    if (index < items.length) {
      setTimeout(chunk, 0);  // Yield, then resume
    }
  }
  chunk();
}

// Method 2: requestIdleCallback (runs during idle time)
function backgroundWork(deadline) {
  while (deadline.timeRemaining() > 0 && tasks.length > 0) {
    performTask(tasks.shift());
  }
  if (tasks.length > 0) {
    requestIdleCallback(backgroundWork);
  }
}
requestIdleCallback(backgroundWork);

// Method 3: scheduler.yield() (modern — Chrome 129+)
async function processItems(items) {
  for (const item of items) {
    doWork(item);
    await scheduler.yield();  // Lets higher-priority work run
  }
}

// ═══ DEBOUNCE vs THROTTLE ═══
// Debounce: Wait until user STOPS doing action (search input)
function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

// Throttle: Execute at most once per interval (scroll, resize)
function throttle(fn, limit) {
  let inThrottle = false;
  return (...args) => {
    if (!inThrottle) {
      fn(...args);
      inThrottle = true;
      setTimeout(() => inThrottle = false, limit);
    }
  };
}

Memory Management

// ═══ COMMON MEMORY LEAKS IN ANGULAR ═══

// 1. Unsubscribed Observables:
// BAD:
ngOnInit() {
  this.service.getData().subscribe(data => this.data = data);
  // If component is destroyed, subscription still runs!
}

// GOOD — Options:
// a) takeUntilDestroyed (Angular 16+):
data$ = this.service.getData().pipe(takeUntilDestroyed());

// b) async pipe (auto-unsubscribes):
// template: {{ data$ | async }}

// c) DestroyRef:
constructor(private destroyRef: DestroyRef) {
  this.service.getData().pipe(
    takeUntilDestroyed(this.destroyRef)
  ).subscribe(data => this.data = data);
}

// 2. Event listeners not removed:
ngOnInit() {
  this.handler = () => { /* ... */ };
  window.addEventListener('resize', this.handler);
}
ngOnDestroy() {
  window.removeEventListener('resize', this.handler);  // MUST clean up!
}

// 3. Closures holding large data:
function createHandler(largeDataSet) {
  // 'largeDataSet' is captured in closure — never GC'd while handler exists!
  return () => console.log(largeDataSet.length);
}
// Fix: Only capture what you need, or set to null when done

// 4. Detached DOM nodes:
let cachedElement = document.querySelector('.modal');
document.body.removeChild(cachedElement);
// cachedElement still holds reference! DOM node can't be GC'd
cachedElement = null;  // Fix: release reference

4. Bundle Optimization

Intermediate

Theory: What Makes Bundles Large?

// Angular production build output:
// main.js      — App code + framework (~200-500KB)
// polyfills.js — Browser compatibility (~30KB)
// runtime.js   — Webpack/esbuild runtime (~2KB)
// styles.css   — Global styles
// lazy-*.js    — Lazy-loaded route chunks

// TOP BUNDLE SIZE KILLERS:
// 1. Lodash (full import: 72KB) vs lodash-es (tree-shakable)
// 2. Moment.js (300KB with locales!) → use date-fns (5KB per function)
// 3. RxJS operators (import specific, not 'rxjs')
// 4. Material/PrimeNG full imports vs individual components
// 5. Unneeded polyfills (zone.js = 40KB, might not need all)

// ═══ ANALYZE BUNDLE ═══
ng build --stats-json
npx webpack-bundle-analyzer dist/my-app/stats.json

// OR with source-map-explorer:
ng build --source-map
npx source-map-explorer dist/my-app/main.*.js

Optimization Techniques

// 1. TREE SHAKING (Dead Code Elimination):
// BAD:
import * as _ from 'lodash';     // Imports ALL of lodash (72KB)
_.debounce(fn, 300);

// GOOD:
import { debounce } from 'lodash-es';  // Only debounce function (~1KB)

// 2. LAZY LOADING ROUTES:
const routes: Routes = [
  {
    path: 'reports',
    loadComponent: () => import('./reports/reports.component')
      .then(m => m.ReportsComponent)
    // Only downloaded when user navigates to /reports
  }
];

// 3. DEFER BLOCKS (Angular 17+):
@Component({
  template: `
    @defer (on viewport) {
      <app-heavy-chart />  <!-- Separate chunk, loaded when visible -->
    } @placeholder {
      <div style="height:400px"></div>  <!-- Reserve space (no CLS!) -->
    }
  `
})

// 4. DIFFERENTIAL LOADING (Angular handles automatically):
// Modern browsers get ES2020+ (smaller, native async/await)
// Old browsers get ES5 (larger, with polyfills)

// 5. COMPRESSION:
// Brotli (20-30% smaller than gzip for text):
// nginx config:
// brotli on;
// brotli_types text/html text/css application/javascript;

// 6. ANGULAR BUDGETS (fail build if too large):
"budgets": [
  { "type": "initial", "maximumWarning": "300kB", "maximumError": "500kB" },
  { "type": "anyComponentStyle", "maximumWarning": "4kB" }
]

@Injectable({ providedIn: 'root' })
export class OnDemandPreloadStrategy implements PreloadingStrategy {
  private preloadSubject = new Subject<string>();
  
  preload(route: Route, load: () => Observable<any>) {
    return this.preloadSubject.pipe(
      filter(path => route.path === path),
      take(1),
      switchMap(() => load())
    );
  }
  
  startPreload(path: string) { this.preloadSubject.next(path); }
}

7. Virtual Scrolling (Large Lists)

Advanced

Theory: Why Virtual Scrolling?

Rendering 10,000 DOM elements causes: huge memory consumption, slow initial render, janky scroll. Virtual scrolling only renders the visible items (~20-50) and recycles DOM nodes as user scrolls.

// ═══ Angular CDK Virtual Scroll ═══
import { ScrollingModule } from '@angular/cdk/scrolling';

@Component({
  imports: [ScrollingModule],
  template: `
    <cdk-virtual-scroll-viewport itemSize="50" class="list-viewport">
      <div *cdkVirtualFor="let item of items; trackBy: trackById" class="item">
        {{ item.name }}
      </div>
    </cdk-virtual-scroll-viewport>
  `,
  styles: [`
    .list-viewport { height: 500px; }
    .item { height: 50px; }  /* Must match itemSize */
  `]
})
export class VirtualListComponent {
  items = Array.from({ length: 100000 }, (_, i) => ({ id: i, name: `Item ${i}` }));
  trackById = (index: number, item: any) => item.id;
}

// For VARIABLE height items:
// Use experimental autosize or custom VirtualScrollStrategy

// ═══ Infinite Scroll + Virtual Scroll ═══
@Component({
  template: `
    <cdk-virtual-scroll-viewport itemSize="80" (scrolledIndexChange)="onScroll($event)">
      <app-product-card *cdkVirtualFor="let product of products" [product]="product" />
    </cdk-virtual-scroll-viewport>
  `
})
export class InfiniteScrollComponent {
  products: Product[] = [];
  private page = 1;
  private loading = false;
  
  onScroll(index: number) {
    // Load more when near the end
    if (index > this.products.length - 20 && !this.loading) {
      this.loading = true;
      this.productService.getProducts(++this.page).subscribe(more => {
        this.products = [...this.products, ...more];
        this.loading = false;
      });
    }
  }
}

8. Angular Change Detection Optimization

Critical

Theory: How Angular Change Detection Works

// Angular uses Zone.js to patch ALL async APIs:
// setTimeout, addEventListener, fetch, Promise.then, etc.
// After ANY async operation completes → Zone.js triggers change detection

// DEFAULT strategy: Check EVERY component top-to-bottom
// Component tree: A → B → C → D (all checked even if no changes!)

// ═══ OPTIMIZATION 1: OnPush Strategy ═══
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush
  // Only checks this component when:
  // 1. @Input() reference changes (new object, not mutation!)
  // 2. Event handler fires IN this component
  // 3. Async pipe receives new value
  // 4. Manual markForCheck() called
})

// ═══ OPTIMIZATION 2: Signals (Angular 16+) ═══
@Component({
  template: `
    <h1>{{ title() }}</h1>       <!-- Signal read -->
    <p>Count: {{ count() }}</p>
    <p>Double: {{ double() }}</p> <!-- Computed signal -->
  `
})
export class CounterComponent {
  title = input.required<string>();     // Signal-based input
  count = signal(0);                     // Writable signal
  double = computed(() => this.count() * 2); // Derived (memoized)
  
  increment() { this.count.update(c => c + 1); }
}
// Signals enable FINE-GRAINED reactivity:
// Only the specific template binding is updated, not the whole component!
// No Zone.js dependency → future: zoneless Angular

// ═══ OPTIMIZATION 3: trackBy ═══
// Without trackBy: *ngFor destroys and recreates ALL DOM on any change
// With trackBy: Angular reuses existing DOM elements

// BAD:
<div *ngFor="let item of items">{{ item.name }}</div>

// GOOD:
<div *ngFor="let item of items; trackBy: trackById">{{ item.name }}</div>
trackById = (_: number, item: Item) => item.id;

// ═══ OPTIMIZATION 4: Pure Pipes (Memoized) ═══
@Pipe({ name: 'filter', pure: true })  // pure is default
export class FilterPipe implements PipeTransform {
  transform(items: Item[], searchTerm: string) {
    return items.filter(i => i.name.includes(searchTerm));
  }
  // Only re-executes when input REFERENCE changes (not on every CD cycle)
}

// ═══ OPTIMIZATION 5: runOutsideAngular ═══
constructor(private ngZone: NgZone) {}

ngOnInit() {
  // Animation/timer that doesn't need CD:
  this.ngZone.runOutsideAngular(() => {
    this.animationFrame = requestAnimationFrame(this.animate.bind(this));
    // This won't trigger change detection!
  });
}

10. Animation Performance (rAF & FLIP)

Advanced

Theory: Why Animations Jank

Browser renders at 60fps (16.67ms per frame). If your animation work takes longer than 16ms, frames are dropped → jank (stuttering). The key is to only animate properties that the GPU can handle WITHOUT triggering layout/paint.

// ═══ THE RENDERING COST OF CSS PROPERTIES ═══
// 
// CHEAP (Compositor-only, GPU handles it):
//   transform: translate(), scale(), rotate()
//   opacity
//   → These NEVER trigger Layout or Paint. ~0ms cost.
//
// MODERATE (Triggers Paint, not Layout):
//   color, background-color, box-shadow, border-radius
//   → Repaints affected pixels. Avoid on large elements.
//
// EXPENSIVE (Triggers Layout → Paint → Composite):
//   width, height, top, left, margin, padding, font-size
//   → Recalculates ALL element positions. NEVER animate these!
//
// ═══ RULE: Only animate transform and opacity ═══

requestAnimationFrame (rAF)

// ═══ requestAnimationFrame — Sync with browser's render cycle ═══
// DON'T: setInterval(() => moveElement(), 16) ← not synced, drops frames
// DO: requestAnimationFrame ← called right before next paint

function smoothScroll(element: HTMLElement, target: number) {
  const start = element.scrollTop;
  const distance = target - start;
  const duration = 300; // ms
  let startTime: number;

  function step(timestamp: number) {
    if (!startTime) startTime = timestamp;
    const elapsed = timestamp - startTime;
    const progress = Math.min(elapsed / duration, 1);
    
    // Easing function (ease-out cubic)
    const eased = 1 - Math.pow(1 - progress, 3);
    
    element.scrollTop = start + distance * eased;
    
    if (progress < 1) {
      requestAnimationFrame(step); // Schedule next frame
    }
  }
  
  requestAnimationFrame(step);
}

// ═══ Angular: Run animations OUTSIDE NgZone ═══
// rAF fires 60 times/second — you don't want change detection each time!
@Component({ ... })
export class AnimatedComponent {
  private ngZone = inject(NgZone);
  private animationId: number;

  startAnimation() {
    this.ngZone.runOutsideAngular(() => { // ← Critical!
      const animate = () => {
        // Update positions, transforms, etc.
        this.animationId = requestAnimationFrame(animate);
      };
      this.animationId = requestAnimationFrame(animate);
    });
  }

  stopAnimation() {
    cancelAnimationFrame(this.animationId);
  }
}

FLIP Technique (First, Last, Invert, Play)

// ═══ FLIP — Animate layout changes smoothly ═══
// Problem: You can't animate 'width' or 'top' smoothly (triggers layout)
// Solution: FLIP — calculate the change, then animate with transform

// F = First:  Record element's initial position/size
// L = Last:   Apply the DOM change (element jumps to new position)
// I = Invert: Use transform to VISUALLY put it back at First position
// P = Play:   Remove the transform with a transition → smooth animation!

function flipAnimate(element: HTMLElement, callback: () => void) {
  // F — FIRST: Record current position
  const first = element.getBoundingClientRect();
  
  // L — LAST: Apply DOM change (element jumps instantly)
  callback(); // e.g., reorder list, expand card, etc.
  
  // L — Record new position
  const last = element.getBoundingClientRect();
  
  // I — INVERT: Calculate difference and apply inverse transform
  const deltaX = first.left - last.left;
  const deltaY = first.top - last.top;
  const deltaW = first.width / last.width;
  const deltaH = first.height / last.height;
  
  element.style.transform = `translate(${deltaX}px, ${deltaY}px) scale(${deltaW}, ${deltaH})`;
  element.style.transformOrigin = 'top left';
  
  // P — PLAY: Remove transform with animation
  requestAnimationFrame(() => {
    element.style.transition = 'transform 300ms ease-out';
    element.style.transform = '';
    
    element.addEventListener('transitionend', () => {
      element.style.transition = '';
      element.style.transformOrigin = '';
    }, { once: true });
  });
}

// ═══ REAL USE CASES FOR FLIP ═══
// • Reordering a list (items slide to new positions)
// • Expanding a card to fullscreen (shared element transition)
// • Moving elements between containers
// • Angular CDK Drag&Drop uses FLIP internally!

// ═══ Web Animations API (Modern Alternative) ═══
element.animate([
  { transform: 'translateY(0)', opacity: 1 },
  { transform: 'translateY(-20px)', opacity: 0 }
], {
  duration: 300,
  easing: 'ease-out',
  fill: 'forwards'  // Keep final state
});

// Benefits over CSS transitions:
// • Programmatic control (pause, reverse, cancel, onfinish)
// • Can animate between computed values
// • Better performance profiling in DevTools
// • Composable (multiple animations on same element)
Performance Trap will-change creates a new GPU compositing layer. Each layer uses GPU memory. On mobile, creating 50+ layers can cause OOM crashes. Use will-change ONLY just before the animation starts, and remove it after the animation ends. Never set it permanently in CSS for dozens of elements.
Debugging Jank Chrome DevTools → Performance tab → Record → look for red triangles (dropped frames). Enable "Rendering" → check "Paint flashing" (green rectangles show what's being repainted). If your animation causes green flashing, you're triggering paint. Switch to transform/opacity.

Q: An element animates from one position to another but stutters. How do you debug and fix it? (Google, Meta)

Answer: (1) Open DevTools Performance tab, record the animation. (2) Look at Main thread — if frames exceed 16ms, identify what's causing it. (3) Check if animating layout-triggering properties (top, left, width) — switch to transform: translate(). (4) Enable "Paint flashing" — if element causes repaint, add will-change: transform before animation, remove after. (5) If JS-driven, ensure using requestAnimationFrame (not setInterval) and running outside NgZone. (6) For complex layout transitions, use FLIP technique: measure → apply change → invert with transform → animate removal.

11. Browser Rendering Engine Internals

Critical

Theory: The Complete Rendering Pipeline

Understanding what happens between receiving HTML and pixels on screen is what separates senior engineers from everyone else.

// ═══ FULL CRITICAL RENDERING PATH (Detailed) ═══
//
// 1. PARSE HTML → DOM Tree
//    • Tokenizer breaks HTML into tokens (start tag, text, end tag)
//    • Tree builder constructs DOM tree from tokens
//    • BLOCKED BY: <script> without async/defer (parser-blocking)
//    • Speculative parsing: browser pre-scans for resources to fetch
//
// 2. PARSE CSS → CSSOM Tree
//    • Parses all stylesheets (inline, external, user agent)
//    • Resolves cascade: specificity → origin → order
//    • RENDER-BLOCKING: No painting until ALL CSS is parsed
//    • That's why Critical CSS should be inlined in <head>
//
// 3. COMBINE → Render Tree
//    • DOM + CSSOM = Render Tree (only visible elements)
//    • display: none elements are NOT in render tree
//    • visibility: hidden IS in render tree (takes space)
//    • ::before, ::after pseudo-elements ARE in render tree
//
// 4. LAYOUT (Reflow)
//    • Calculates exact position and size of every element
//    • Box model: content + padding + border + margin
//    • Starts from root, cascades down (parent affects children)
//    • EXPENSIVE: Changing one element can affect many others
//    • Layout thrashing: read → write → read → write (forced sync layout)
//
// 5. PAINT
//    • Converts render tree to pixels (rasterization)
//    • Draws: text, colors, borders, shadows, images
//    • Paint order: background → border → children → outline
//    • Creates PAINT RECORDS (instruction list for each layer)
//
// 6. COMPOSITE
//    • Combines painted layers in correct order (z-index, stacking)
//    • GPU-accelerated: each layer is a texture
//    • Properties that create new layers:
//      • will-change: transform/opacity
//      • position: fixed
//      • transform: translateZ(0) (hack — avoid)
//      • <video>, <canvas>, CSS animations
//    • Compositor thread: runs INDEPENDENTLY of main thread!
//      That's why transform/opacity animations never jank

// ═══ VISUAL PIPELINE ═══
// 
//  HTML → DOM ─┐
//              ├→ Render Tree → Layout → Paint → Composite → PIXELS
//  CSS → CSSOM┘
//
// Changing 'width':     Layout → Paint → Composite (EXPENSIVE)
// Changing 'color':     Paint → Composite (MODERATE)
// Changing 'transform': Composite ONLY (CHEAP — GPU only!)

Layout Thrashing & Forced Synchronous Layout

// ═══ LAYOUT THRASHING — The #1 performance killer in DOM manipulation ═══
//
// BAD: Interleaving reads and writes forces browser to recalculate layout
// EACH read after a write triggers a "forced synchronous layout"

// ❌ BAD — Forces layout recalculation N times:
const items = document.querySelectorAll('.item');
items.forEach(item => {
  const height = item.offsetHeight;        // READ (forces layout!)
  item.style.height = height * 2 + 'px';   // WRITE (invalidates layout)
  // Next iteration's READ will force ANOTHER layout calculation
});

// ✅ GOOD — Batch reads, then batch writes:
const items = document.querySelectorAll('.item');
// Phase 1: Read ALL values
const heights = Array.from(items).map(item => item.offsetHeight);
// Phase 2: Write ALL values
items.forEach((item, i) => {
  item.style.height = heights[i] * 2 + 'px';
});
// Only ONE layout recalculation!

// ═══ Properties that trigger FORCED LAYOUT when read: ═══
// offsetTop, offsetLeft, offsetWidth, offsetHeight
// scrollTop, scrollLeft, scrollWidth, scrollHeight
// clientTop, clientLeft, clientWidth, clientHeight
// getComputedStyle(), getBoundingClientRect()
// innerText (requires layout to determine text)

// ═══ CSS CONTAINMENT — Limit layout recalculation scope ═══
.widget {
  contain: layout;    // Layout changes inside don't affect outside
  contain: paint;     // Painting is clipped to element boundary
  contain: size;      // Element's size isn't affected by children
  contain: strict;    // All of the above (maximum isolation)
  content-visibility: auto; // Skip rendering off-screen content entirely
}
// content-visibility: auto → browser skips layout+paint for off-screen
// Can save 100-400ms on pages with lots of below-fold content!

Stacking Contexts & Compositing Layers

// ═══ STACKING CONTEXT — When z-index creates new layers ═══
// A new stacking context is created by:
// • position: relative/absolute/fixed + z-index (not auto)
// • opacity < 1
// • transform (any value except none)
// • filter (any value except none)
// • will-change: transform, opacity
// • mix-blend-mode, isolation: isolate
//
// PROBLEM: Elements in a stacking context can NEVER appear
// between layers of a different stacking context.
// This is why z-index: 99999 sometimes doesn't work!

// ═══ GPU COMPOSITING LAYERS — Memory considerations ═══
// Each compositing layer = GPU texture = MEMORY
// 
// Check layers: DevTools → More Tools → Layers
// You'll see each GPU layer, its memory cost, and why it was created
//
// PROBLEM: "Layer explosion" — too many layers on mobile:
// • Each 1000x1000px layer @ 4 bytes/pixel = 4MB GPU memory
// • Mobile GPUs have limited memory (256-512MB shared)
// • 50 unnecessary layers = potential OOM crash
//
// SOLUTION:
// 1. Use will-change sparingly (only during animation)
// 2. Avoid position: fixed on many elements
// 3. Use DevTools Layers panel to audit
// 4. Prefer one scrollable container over many fixed layers
Interview Must-Know "What happens when you change the width of a div?"
Answer: Triggers Layout (recalculates all affected element positions) → Paint (repaint affected areas) → Composite. If many elements are affected, this can take 50-100ms, causing visible jank. Solution: Animate transform: scaleX() instead — compositor-only, ~0ms, GPU-handled.

Q: Explain the critical rendering path. How would you optimize it for a content-heavy page? (Google, Amazon, Meta)

Answer: CRP: HTML parsing→DOM, CSS parsing→CSSOM, merge→Render Tree, Layout, Paint, Composite. Optimizations: (1) Inline critical CSS (~14KB above-fold styles) in <head> to avoid render-blocking stylesheet fetch. (2) Async/defer non-critical JS (parser-blocking scripts delay DOM construction). (3) Preload LCP resource (image/font) with fetchpriority=high. (4) Use font-display: swap (avoid invisible text during font load). (5) Reduce DOM depth (layout calculation is O(n) on DOM nodes). (6) Use content-visibility: auto for below-fold sections (browser skips layout/paint). (7) Speculative preloading with <link rel="preload"> for critical resources.

13. Interview Questions (Previously Asked)

Q1: What are Core Web Vitals? How would you improve LCP for an Angular e-commerce app? (Google, Amazon, Flipkart)

Answer: CWV are Google's metrics: LCP (loading), INP (interactivity), CLS (stability). For LCP: (1) SSR the product page (immediate HTML). (2) Preload hero image with fetchpriority="high". (3) Inline critical CSS. (4) Use NgOptimizedImage with priority flag. (5) Reduce TTFB with CDN + edge caching. (6) Eliminate render-blocking JS (defer non-critical). Target: LCP ≤ 2.5s on 4G mobile.

Q2: Your Angular app's main bundle is 2MB. How do you reduce it? (All companies)

Answer: (1) Run source-map-explorer to find culprits. (2) Lazy load ALL routes except landing. (3) Replace moment.js with date-fns or Angular's DatePipe. (4) Use tree-shakable providers (providedIn: 'root'). (5) Switch to standalone components (better tree-shaking). (6) Import specific Angular Material modules, not entire library. (7) Use @defer for heavy below-fold components. (8) Set budgets (300KB initial warning, 500KB error). (9) Verify production mode enabled. (10) Consider dropping Zone.js with Signals.

Q3: Explain Angular's change detection. How does OnPush work? When would you use Signals? (All Angular interviews)

Answer: Default CD: Zone.js patches async APIs → after any async, checks ALL components top-down. OnPush: Only checks when @Input ref changes, events fire inside, or async pipe emits. Signals (16+): fine-grained reactivity — only updates specific template bindings, no Zone.js needed. Use Signals for: new projects, performance-critical components, when migrating away from Zone.js. OnPush is sufficient for most apps with immutable data patterns.

Q4: How would you handle a list of 50,000 items without freezing the UI? (Microsoft, Google)

Answer: (1) Virtual scrolling (CDK ScrollingModule) — only render visible ~30 items. (2) trackBy for DOM reuse. (3) OnPush on list items. (4) Pagination or infinite scroll (cursor-based API). (5) If filtering/sorting is expensive → Web Worker. (6) Debounce search/filter inputs. (7) Use signals for filter state. Never render all 50K items — even with virtual scroll, pre-calculate heights.

Q5: What is layout thrashing? Give an example and how to fix it. (Google, Meta)

Answer: Layout thrashing = repeatedly reading layout properties then writing styles in a loop, forcing browser to recalculate layout on every iteration. Example: reading offsetHeight then setting height in forEach. Fix: batch all reads first, then batch all writes. Or use requestAnimationFrame to separate read/write phases. Tools: DevTools Performance panel shows "Forced reflow" warnings in purple. Also use CSS contain: layout to isolate components.

Q6: Design a performance monitoring system for a large Angular app. (Senior level — Amazon, Microsoft)

Answer: Architecture: (1) Web Vitals library collects CWV + custom metrics. (2) Performance Observer API tracks long tasks, resource timing. (3) Angular-specific: monitor CD cycles, component render time via profiler API. (4) Send to analytics backend (beacon API for page unload). (5) Dashboard with percentiles (p50, p75, p95) per route. (6) Alerts when p75 LCP exceeds budget. (7) CI integration: Lighthouse CI fails PR if regression. (8) Synthetic monitoring: scheduled Lighthouse runs. (9) RUM segmentation: by device, connection type, geography.
