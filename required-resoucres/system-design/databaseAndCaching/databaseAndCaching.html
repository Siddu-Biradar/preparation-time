Database & Caching — From 0 to Advanced (Frontend Edition)

A complete, interview-grade guide for Frontend SDE2/SDE3 roles. We cover where data lives, how it travels, how it's cached at every layer (browser → CDN → server → DB), and the patterns top engineers use to keep apps fast, offline-capable, and consistent.

1. Why Frontend Devs Need Database & Caching Beginner

Modern frontend isn't just "render the UI". It owns a meaningful share of the data plane: client storage, request caching, optimistic updates, conflict resolution, offline queues, normalized stores, and selectors. SDE2/SDE3 interviews probe whether you understand where data lives, who is the source of truth, and what happens when the network fails.

  • Performance: a request avoided is the cheapest request. Caching = fewer round trips, faster paints.
  • UX: instant interactions need optimistic updates and local persistence.
  • Reliability: Service Workers + IndexedDB enable offline-first apps.
  • Cost: a well-cached SPA cuts server load and bandwidth.
  • System design rounds: "Design Twitter / Gmail / Notion offline" — they want to hear about cache layers, conflict resolution, and storage tiers.

2. Mental Model: The Data Pipeline Beginner

Every byte rendered traveled through (potentially) all of these layers. Each is a cache opportunity:

┌────────────────────────────────────────────────────────────────────┐
│ User → React component → Selector → In-memory store (Redux/Zustand)│
│                                       ↑                            │
│                         Persisted state (IndexedDB / localStorage) │
│                                       ↑                            │
│                    HTTP cache (Browser memory + disk cache)        │
│                                       ↑                            │
│                       Service Worker / Cache Storage               │
│                                       ↑                            │
│                          CDN / Edge cache                          │
│                                       ↑                            │
│                  Origin server (in-memory + Redis)                 │
│                                       ↑                            │
│                Database (with its own buffer pool / indexes)       │
└────────────────────────────────────────────────────────────────────┘
Interview Tip Always answer "where is the source of truth?" before "where do we cache?". Caching invariably involves invalidation, and invalidation requires knowing who owns the data.

As a frontend dev you'll mostly consume APIs over HTTP. Knowing what's behind that API helps you reason about pagination shape, IDs, latency, and whether requests can be cached aggressively.

4. CAP, ACID, BASE — The 90-Second Version Intermediate

  • CAP: in a network partition you can choose Consistency or Availability, not both. Most web apps lean AP (available, eventually consistent).
  • ACID (SQL): Atomicity, Consistency, Isolation, Durability — strong guarantees per transaction.
  • BASE (NoSQL): Basically Available, Soft state, Eventual consistency — scale over strict guarantees.

Why frontend cares: optimistic UI assumes BASE-style "the server will agree eventually". You must design for rollback when it doesn't.

6. localStorage Beginner

Synchronous key-value store. Strings only. Per-origin, persists indefinitely.

// Set / get / remove
localStorage.setItem('theme', 'dark');
const theme = localStorage.getItem('theme');     // 'dark' or null
localStorage.removeItem('theme');
localStorage.clear();
localStorage.length;                              // count
localStorage.key(0);                              // key at index

// Objects → JSON
const user = { id: 1, name: 'Sid' };
localStorage.setItem('user', JSON.stringify(user));
const parsed = JSON.parse(localStorage.getItem('user') || 'null');

// Cross-tab sync (fires in OTHER tabs)
window.addEventListener('storage', (e) => {
  if (e.key === 'theme') applyTheme(e.newValue);
});

Best practices

  • Always JSON.parse inside try/catch — corrupt data shouldn't crash the app.
  • Namespace keys: app:user:settings to avoid collisions.
  • Version your schema: { v: 2, data: ... } so you can migrate.
  • Wrap in a thin abstraction so you can swap to IndexedDB later.
// Tiny safe wrapper
export const storage = {
  get(key, fallback = null) {
    try { return JSON.parse(localStorage.getItem(key)) ?? fallback; }
    catch { return fallback; }
  },
  set(key, value) {
    try { localStorage.setItem(key, JSON.stringify(value)); return true; }
    catch (e) {
      if (e.name === 'QuotaExceededError') evictOldest();
      return false;
    }
  },
  remove: (k) => localStorage.removeItem(k),
};
Gotchas
  • Synchronous — large reads/writes block the main thread. Don't store MBs.
  • Stores strings only. setItem('x', 1) stores "1".
  • Throws QuotaExceededError when full (especially in private/incognito).
  • Accessible to any JS on the page → NEVER store JWTs, secrets, PII here. XSS = total compromise.
  • storage event fires only in other tabs — same-tab listener won't fire.
  • SSR (Next/Nuxt): localStorage is undefined on server — guard with typeof window !== 'undefined'.
  • Disabled in cross-origin iframes when third-party storage is blocked (Safari ITP, Chrome partitioning).

7. sessionStorage Beginner

Same API as localStorage but scoped to the tab/window and cleared when it closes.

sessionStorage.setItem('checkout:step', '2');
sessionStorage.getItem('checkout:step');

When to use it

  • Multi-step forms / wizards where reload should preserve progress, but new tab should start fresh.
  • Temporary auth challenges (CSRF challenge, OTP attempt counters per session).
  • "Came from page X" tracking for the current journey only.
Gotchas
  • A duplicated tab inherits sessionStorage at the moment of duplication, then diverges. Don't assume uniqueness.
  • Closing a tab clears it; refresh does not.
  • Each iframe has its own sessionStorage if origin differs.

8. Cookies Intermediate

The oldest browser storage. Tiny (~4 KB), but uniquely sent with every same-origin HTTP request — which is both their power and their risk.

Anatomy of a cookie

Set-Cookie: sid=abc123;
            Domain=example.com;
            Path=/;
            Expires=Wed, 09 Jun 2027 10:18:14 GMT;
            Max-Age=31536000;
            Secure;             // HTTPS only
            HttpOnly;           // not readable from JS
            SameSite=Lax;       // CSRF protection
            Partitioned;        // CHIPS — partitioned per top-site

SameSite values

ValueSent on cross-site requests?Use case
StrictNeverBanking, sensitive apps
Lax (default)Only on top-level GET navigationMost apps
NoneAlways (requires Secure)Cross-site embeds, OAuth
// JS access (only NON HttpOnly cookies)
document.cookie = 'lang=en; Path=/; Max-Age=3600; SameSite=Lax';
document.cookie; // "lang=en; theme=dark"  (parse manually 😖)

// Modern API — Cookie Store (Chromium)
await cookieStore.set({ name: 'lang', value: 'en', sameSite: 'lax' });
const c = await cookieStore.get('lang');

Cookies vs localStorage for auth

HttpOnly CookielocalStorage
Readable by XSS?NoYes
Sent automatically?Yes (need CSRF protection)No (manual Authorization header)
Recommended for tokens?Yes (HttpOnly + Secure + SameSite=Lax/Strict)No
Gotchas
  • Every cookie is sent with every request to the domain → bloated headers slow APIs. Keep cookies small.
  • document.cookie API is awful — get/set strings concatenated. Use a tiny lib.
  • Setting a cookie's Domain=.example.com shares it with all subdomains. Audit carefully.
  • Third-party cookies are being phased out (Safari ITP already blocks them; Chrome is gradually). Use Partitioned (CHIPS) for embeds.
  • Without Secure, cookies are sent over HTTP and trivially stolen.

9. IndexedDB Advanced

A browser-native, asynchronous, transactional, object-oriented database. It can store almost anything: objects, blobs, files, ArrayBuffers — up to the quota (often hundreds of MB to GBs). It's the backbone of offline-first PWAs.

Concepts

  • Database — has a name + version.
  • Object Store — like a SQL table; holds keyed records.
  • Index — secondary lookup on a field.
  • Transaction — readonly or readwrite over one or more stores; auto-commits.
  • Cursor — iterate large result sets.

Raw IndexedDB (verbose)

const req = indexedDB.open('shop', 2);

req.onupgradeneeded = (e) => {
  const db = e.target.result;
  if (!db.objectStoreNames.contains('products')) {
    const store = db.createObjectStore('products', { keyPath: 'id' });
    store.createIndex('by_category', 'category', { unique: false });
  }
};

req.onsuccess = () => {
  const db = req.result;
  const tx = db.transaction('products', 'readwrite');
  const store = tx.objectStore('products');
  store.put({ id: 1, name: 'Pen', category: 'office' });
  tx.oncomplete = () => console.log('saved');
};

Use a wrapper (recommended): idb by Jake Archibald

import { openDB } from 'idb';

const db = await openDB('shop', 2, {
  upgrade(db, oldV, newV, tx) {
    if (oldV < 1) {
      const s = db.createObjectStore('products', { keyPath: 'id' });
      s.createIndex('by_category', 'category');
    }
    if (oldV < 2) {
      db.createObjectStore('cart', { keyPath: 'id', autoIncrement: true });
    }
  },
});

await db.put('products', { id: 1, name: 'Pen', category: 'office' });
const item = await db.get('products', 1);
const office = await db.getAllFromIndex('products', 'by_category', 'office');

// Transaction across stores
const tx = db.transaction(['cart', 'products'], 'readwrite');
await tx.objectStore('cart').add({ productId: 1, qty: 2 });
await tx.done;

Realistic frontend use cases

  • Offline cache for large lists (Gmail-style: thousands of messages).
  • Draft documents (Google Docs, Notion offline editor).
  • Asset cache: PDFs, audio, videos for offline playback.
  • Encryption keys (with WebCrypto), background sync queues.
  • Embedded SQLite (sql.js / wa-sqlite) backed by IndexedDB or OPFS.
Gotchas
  • Transactions auto-commit the moment the event loop yields without an active request — never await non-IDB promises mid-transaction.
  • Schema changes require bumping the version and handling onupgradeneeded. Old tabs block upgrades — listen to onversionchange and reload.
  • Safari has historically had quirky IDB bugs; test on iOS.
  • No SQL — design key paths and indexes carefully; you can't ad-hoc query.
  • Storage may be evicted under pressure unless you call navigator.storage.persist().

10. Cache Storage API (Service Worker) Advanced

A separate storage area for full HTTP Request/Response pairs. Mostly used by Service Workers to enable offline.

// Inside a Service Worker
self.addEventListener('install', (e) => {
  e.waitUntil(
    caches.open('shell-v3').then(cache =>
      cache.addAll(['/', '/app.js', '/styles.css', '/offline.html'])
    )
  );
});

self.addEventListener('fetch', (e) => {
  e.respondWith(
    caches.match(e.request).then(hit => hit || fetch(e.request))
  );
});

Different from localStorage/IndexedDB: this stores actual HTTP responses including headers — perfect for static assets and API GETs you want to serve offline.

11. OPFS & FileSystem Access Advanced

Origin Private File System — a sandboxed, high-performance filesystem per origin. Used for SQLite-in-the-browser (wa-sqlite, SQLite WASM), large file editing, and DAW/photo tools. 

// In a Worker (recommended for sync handles)
const root = await navigator.storage.getDirectory();
const file = await root.getFileHandle('app.db', { create: true });
const sync = await file.createSyncAccessHandle();
sync.write(new TextEncoder().encode('hello'));
sync.close();

Compared to IndexedDB, OPFS gives near-native I/O speeds — Notion, Figma, and SQL.js v3 use it where available.

12. Quota, Eviction & Persistence Intermediate

const { quota, usage } = await navigator.storage.estimate();
console.log(`${usage} / ${quota} bytes`);

const persisted = await navigator.storage.persist(); // ask to be non-evictable
const isPersisted = await navigator.storage.persisted();
  • Each origin gets a quota (often ~60% of free disk).
  • Browsers may evict best-effort storage under pressure.
  • persist() upgrades to "persistent" — never auto-evicted (Chrome grants silently if PWA is installed; Firefox prompts).
  • Safari aggressively evicts after 7 days of no user interaction (ITP).

13. Normalisation (Frontend State Edition) Intermediate

From databases: removing duplicate data by splitting into related tables. On the frontend, the same idea = a Redux/Zustand store keyed by ID, never nested.

Bad — nested, duplicated

{
  posts: [
    { id: 1, title: 'A', author: { id: 7, name: 'Sid' } },
    { id: 2, title: 'B', author: { id: 7, name: 'Sid' } }, // dup!
  ]
}

Good — normalized

{
  posts: {
    byId: {
      1: { id: 1, title: 'A', authorId: 7 },
      2: { id: 2, title: 'B', authorId: 7 },
    },
    allIds: [1, 2],
  },
  users: {
    byId: { 7: { id: 7, name: 'Sid' } },
    allIds: [7],
  }
}

Why frontend cares

  • Update once, reflected everywhere — no cache desync.
  • Memoized selectors (Reselect) work cleanly on flat shapes.
  • O(1) lookups instead of O(n) array scans.
  • Smaller diffs = faster re-renders + smaller serialized state.

The 3 normal forms (1NF, 2NF, 3NF) — interview cheatsheet

  • 1NF: atomic values per column (no arrays/objects).
  • 2NF: 1NF + no partial dependency on a composite key.
  • 3NF: 2NF + no transitive dependency (non-key → non-key).

Higher forms (BCNF, 4NF, 5NF) are rarely asked of frontend devs but be aware they exist.

Tooling normalizr by Paul Armstrong, Redux Toolkit's createEntityAdapter, RTK Query and Apollo's normalized cache all do this for you.

14. Denormalisation & Trade-offs Intermediate

Sometimes the opposite is correct: copy data to avoid joins/lookups.

  • Server: read-heavy reports, search indexes, precomputed feeds.
  • Frontend: derived state for rendering performance (e.g., precomputed display strings).

Cost: writes are now duplicated — keep a single source of truth and recompute selectors instead of duplicating in the store.

15. HTTP Caching (The Browser Cache) Advanced

Two cache families

  1. Strong (fresh) cache — browser doesn't even ask the server.
  2. Weak / conditional — browser asks the server "is this still valid?" with If-None-Match / If-Modified-Since; server may reply 304 Not Modified.

Headers you must know

HeaderWhat it does
Cache-Control: public, max-age=31536000, immutableCache for 1 year; never revalidate. Use for hashed assets.
Cache-Control: no-cacheCache, but always revalidate before use.
Cache-Control: no-storeDon't cache anywhere. Use for sensitive responses.
Cache-Control: privateBrowser may cache; CDNs/proxies must not.
Cache-Control: stale-while-revalidate=60Serve stale up to 60s, refresh in background.
Cache-Control: stale-if-error=86400Serve stale for a day if origin errors.
ETag: "abc123"Strong validator; sent back as If-None-Match.
Last-Modified / If-Modified-SinceWeak validator (timestamp).
Vary: Accept-Encoding, Accept-LanguageCache key includes these request headers.
AgeSeconds since the response was generated (set by caches).

Patterns by asset type

/* Hashed bundles (app.[hash].js) */
Cache-Control: public, max-age=31536000, immutable

/* HTML entry */
Cache-Control: no-cache  // always revalidate (cheap 304)

/* User-specific JSON */
Cache-Control: private, max-age=0, must-revalidate

/* CDN-able public JSON */
Cache-Control: public, s-maxage=300, stale-while-revalidate=60
Gotchas
  • Hard reload (Cmd+Shift+R) bypasses cache; normal reload still uses revalidation. This trips up "but it works locally!" debugging.
  • no-cache ≠ no-store. The first revalidates, the second never stores.
  • POST/PUT/DELETE responses are not cached (browsers also evict matching GETs after non-safe methods).
  • Vary: * effectively disables caching — use specific values.
  • Once a response with a long max-age is in the wild, you cannot recall it. Always hash filenames for static assets.

back/forward cache (bfcache)

Modern browsers snapshot the entire page when you navigate away, so back/forward is instant. Things that disable it: unload handlers, open IndexedDB transactions, Cache-Control: no-store on the document, in-flight fetches.

16. CDN & Edge Caching Intermediate

  • CDNs (Cloudflare, CloudFront, Fastly, Vercel Edge) cache shared responses close to users.
  • Use s-maxage to set a CDN-specific TTL different from max-age.
  • Cache key includes URL + Vary'd headers — beware of accidentally including Cookie in Vary (poisons the cache per user).
  • Cache busting / purging: change the URL (hash), use surrogate keys (Fastly), or call the CDN's purge API on deploy.
  • Personalized HTML? Use Edge Side Includes (ESI) or fragment caching, or render shells at edge and hydrate user data client-side.

17. Server-Side Caching Intermediate

Even if you're "frontend only", you'll work with backend engineers and need to reason about these layers in interviews:

  • In-memory app cache: Node LRU map, Java caffeine — fastest, per-process.
  • Distributed cache: Redis, Memcached — shared across servers.
  • Database buffer pool: pages held in RAM by the DB itself.
  • Materialized views: precomputed query results.

Cache patterns (must-know names)

PatternHow it worksTrade-off
Cache-aside (lazy)App reads cache; on miss, reads DB and populates cache.Stale on writes — needs invalidation.
Read-throughApp always asks cache; cache fetches from DB on miss.Cache is the abstraction.
Write-throughWrites go to cache + DB synchronously.Slower writes, fresh reads.
Write-behindWrites go to cache; flushed to DB async.Fast writes; risk on crash.
Refresh-aheadCache proactively refreshes hot keys before expiry.Wasted work on cold keys.

Eviction policies

  • LRU (Least Recently Used) — most common.
  • LFU (Least Frequently Used) — better for skewed access.
  • TTL — time-based.
  • FIFO / Random — simple but rarely optimal.

Famous failure modes

  • Thundering herd / cache stampede — many requests miss the same key at once and all hit the DB. Fix: locks, request coalescing, stale-while-revalidate.
  • Cache penetration — repeated lookups for keys that don't exist. Fix: cache the negative result with short TTL or use a Bloom filter.
  • Cache avalanche — many keys expire simultaneously. Fix: jitter TTLs.

18. API Caching Strategies (Frontend) Advanced

Levels of API caching

  1. HTTP — let Cache-Control do the work for GETs (cheapest).
  2. In-memory query cache — React Query, SWR, RTK Query, Apollo.
  3. Persisted query cache — same libs + IndexedDB hydration.
  4. Service Worker — intercept fetches, return cached responses.

React Query / TanStack Query — cheat sheet

const { data, isPending, isError } = useQuery({
  queryKey: ['user', userId],
  queryFn: () => fetch(`/api/users/${userId}`).then(r => r.json()),
  staleTime: 60_000,         // fresh for 60s — no refetch on remount
  gcTime: 5 * 60_000,        // keep in cache 5 min after unused
  refetchOnWindowFocus: true,
  retry: 2,
});

// Mutation with optimistic update
const qc = useQueryClient();
const mutation = useMutation({
  mutationFn: updateUser,
  onMutate: async (next) => {
    await qc.cancelQueries({ queryKey: ['user', next.id] });
    const prev = qc.getQueryData(['user', next.id]);
    qc.setQueryData(['user', next.id], next);
    return { prev };
  },
  onError: (_err, next, ctx) => qc.setQueryData(['user', next.id], ctx.prev),
  onSettled: (_d, _e, next) => qc.invalidateQueries({ queryKey: ['user', next.id] }),
});

Caching strategies for service workers

StrategyBehaviorUse for
Cache-FirstCache, fallback to networkStatic assets, fonts, hashed JS/CSS
Network-FirstNetwork, fallback to cacheHTML shell, news content
Stale-While-RevalidateReturn cached immediately, refresh in backgroundAvatars, semi-fresh data
Network-OnlyAlways networkAuth, payments, analytics
Cache-OnlyAlways cachePre-warmed app shell

Cache invalidation strategies

  • Time-based (TTL) — simplest.
  • Event-based — invalidate on mutation (RTK Query tags, Apollo refetchQueries).
  • Manual — queryClient.invalidateQueries().
  • ETag / If-None-Match — server confirms freshness.
  • Subscriptions / WebSockets — server pushes invalidations.
"There are only two hard things in CS" Cache invalidation, naming things, and off-by-one errors. Prefer short TTL + revalidation over long TTL + perfect invalidation.

self.addEventListener('sync', (event) => {

Offline-first checklist

  • Pre-cache app shell on install.
  • Use IndexedDB for pending mutations queue.
  • Implement Background Sync to retry when online.
  • UI: show "offline" banner using navigator.onLine + online/offline events.
  • Conflict resolution policy: last-write-wins, CRDT, or server-arbitration.

20. State Management Patterns Advanced

The 5 kinds of frontend state

  1. Server cache state — fetched data (use React Query/RTK Query).
  2. Global UI state — theme, modals, sidebar (Zustand/Redux/Context).
  3. Local component state — input values, hover (useState).
  4. URL state — filters, pagination, tab (useSearchParams, router).
  5. Form state — React Hook Form / Formik.

Most state-management pain comes from putting type 1 in a tool meant for type 2. "I store API responses in Redux" is a common SDE2 anti-pattern; React Query / RTK Query exist for that.

Common architectural patterns

  • Flux / Redux — unidirectional, single store, pure reducers.
  • Atom-based — Recoil, Jotai — fine-grained reactivity.
  • Proxy-based — Valtio, MobX — mutable feel, signals.
  • Selector-based — Zustand, Redux Toolkit + Reselect.
  • Server-state-as-cache — React Query, SWR, Apollo, URQL, Relay.

21. Redux / Zustand / RTK Query / React Query Advanced

Zustand (minimal)

import { create } from 'zustand';
import { persist } from 'zustand/middleware';

const useCart = create(persist(
  (set) => ({
    items: [],
    add: (item) => set((s) => ({ items: [...s.items, item] })),
    clear: () => set({ items: [] }),
  }),

));

Redux Toolkit + RTK Query

import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

export const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['User'],
  endpoints: (b) => ({
    getUser: b.query({
      query: (id) => `users/${id}`,
      providesTags: (_r, _e, id) => [{ type: 'User', id }],
    }),
    updateUser: b.mutation({
      query: (u) => ({ url: `users/${u.id}`, method: 'PUT', body: u }),
      invalidatesTags: (_r, _e, u) => [{ type: 'User', id: u.id }],
    }),
  }),
});

22. Real-time Sync & Conflict Resolution Advanced

  • Polling — simple, wasteful.
  • Long polling — server holds request open until update.
  • Server-Sent Events (SSE) — one-way push from server.
  • WebSockets — bidirectional persistent.
  • WebRTC DataChannels — peer-to-peer.

Conflict resolution strategies

  • Last-Write-Wins (LWW) — simplest, can lose updates.
  • Version vectors / OCC — server rejects stale writes; client retries.
  • Operational Transform (OT) — Google Docs.
  • CRDTs (Yjs, Automerge) — mathematically mergeable; great for offline collaborative.

23. Security & Privacy Intermediate

  • Never store secrets (JWT, refresh tokens, API keys) in localStorage / sessionStorage / IndexedDB. XSS = total compromise.
  • Auth tokens belong in HttpOnly + Secure + SameSite cookies.
  • Treat all client storage as user-readable and user-editable. Validate everything server-side.
  • For sensitive caches (medical, banking), use Cache-Control: no-store.
  • Wipe storage on logout: localStorage.clear(), delete IndexedDB databases, unregister service workers.
  • Encrypt sensitive cached data with WebCrypto when storage is unavoidable.
  • Be aware of storage partitioning in modern browsers (cookies/storage keyed by top-frame origin too).
  • GDPR/CCPA: cookies and local storage often need consent banners.

24. Performance & Memory Advanced

  • Don't read/write huge JSON to localStorage on every keystroke — debounce.
  • Move heavy IndexedDB work to a Web Worker; it's async but JSON deserialization on main thread isn't.
  • Use structuredClone to copy without circular ref issues.
  • Memoize selectors (reselect, useMemo) so derived state recomputes only when inputs change.
  • Use Map/Set for hot lookups instead of objects when keys are non-strings.
  • Tree-shake state libraries — import { create }, not the entire package.
  • Watch storage event listeners — they fire on EVERY change in other tabs; unsubscribe on unmount.
  • Profile with DevTools → Application → Storage and Memory tab → Snapshots.

25. Best Practices Checklist Intermediate

Storage
  • Pick the right tier (cookie/local/session/IDB).
  • Namespace + version your keys.
  • Wrap raw APIs behind a typed module.
  • Handle QuotaExceededError gracefully.
HTTP Caching
  • Hash filenames + immutable.
  • no-cache on the HTML entry.
  • Use stale-while-revalidate on JSON.
  • Set Vary precisely.
State
  • Server data → React Query / RTK Query.
  • UI state → Zustand / Context.
  • Normalize entities; memoize selectors.
  • Optimistic updates with rollback.
Security
  • Tokens in HttpOnly cookies, never in localStorage.
  • Wipe storage on logout.
  • no-store for sensitive responses.
  • Treat client data as untrusted.

26. Top Interview Questions Advanced

Q1. localStorage vs sessionStorage vs cookies vs IndexedDB?
  • Cookies — ~4 KB, sent with every request, configurable expiry, HttpOnly for auth.
  • localStorage — ~5–10 MB, sync, persists forever, per origin, JS readable.
  • sessionStorage — same as local but per tab, cleared on close.
  • IndexedDB — async, transactional, MB→GB, structured data, blobs.
Use cookies for auth, IDB for offline data, localStorage for small UI prefs.
Q2. Why is localStorage considered insecure for tokens?
It's accessible to any JS that runs on the page. A single XSS exfiltrates every token. HttpOnly cookies are not exposed to JS, so XSS can't directly read them — pair with SameSite to prevent CSRF.
Q3. Difference between Cache-Control: no-cache and no-store?
no-cache = cache it, but always revalidate before use (cheap 304s). no-store = never cache anywhere. Use no-store for sensitive data like banking.
Q4. Explain ETag and conditional requests.
Server sends ETag: "v1". Browser sends back If-None-Match: "v1" on the next request. Server replies 304 Not Modified with no body if unchanged, saving bandwidth.
Q5. What is stale-while-revalidate?
A Cache-Control directive: serve cached response immediately even if stale, and revalidate in the background for next time. Massive UX win for "fresh enough" data.
Q6. How would you implement an offline-first app?
App shell precached via Service Worker. Data in IndexedDB. Mutations queued in IDB. Background Sync flushes the queue when online. UI uses optimistic updates with rollback. Conflict resolution via version vectors or CRDTs.
Q7. What is normalization in frontend state?
Storing entities in a flat {byId, allIds} shape so updates happen in one place. Avoids inconsistencies when the same entity is referenced from multiple lists. Used by Redux Toolkit's createEntityAdapter, Apollo's normalized cache, etc.
Q8. Cache-aside vs write-through caching?
Cache-aside: app reads cache, fetches DB on miss, populates cache. Stale on writes.
Write-through: every write goes to cache + DB synchronously. Slower writes but cache always fresh.
Q9. What is a thundering herd / cache stampede? How do you fix it?
When a hot cache key expires, many concurrent requests miss and stampede the DB. Fix: distributed lock so only one request fetches; others wait. Or use stale-while-revalidate. Or refresh-ahead before expiry.
Q10. Why use React Query over Redux for server data?
React Query is purpose-built for async server state: caching, deduping, background refetch, stale time, optimistic updates, retries — all out of the box. Redux requires you to hand-roll all of that.
Q11. How do you invalidate caches across tabs?
BroadcastChannel, storage event, or a shared SharedWorker. React Query's broadcastQueryClient-experimental uses BroadcastChannel.
Q12. Difference between Cache Storage and IndexedDB?
Cache Storage stores Request/Response pairs (HTTP-shaped) — perfect for offline assets. IndexedDB stores arbitrary structured data with indexes and queries. Use both: assets in Cache, data in IDB.
Q13. Explain the Critical Rendering Path's relationship with caching.
Cached HTML/CSS/JS skip TTFB and download. Inline critical CSS to avoid the round trip. Use preload/preconnect hints. Service Workers can return responses without ever hitting the network → instant LCP on repeat visits.
Q14. How do you handle race conditions in optimistic updates?
(a) Cancel in-flight queries before applying optimistic state (queryClient.cancelQueries).
(b) Snapshot previous state for rollback.
(c) On error, restore snapshot.
(d) On settle, refetch the canonical value.
(e) For ordered ops, attach a client-generated ID + timestamp, and let server order.
Q15. What's a CRDT and why does it matter?
Conflict-free Replicated Data Type — data structures (counters, sets, sequences) that can be merged from multiple replicas without conflict. Used in Figma, Linear, Notion-like apps for real-time multi-device editing.
Q16. SameSite cookies — explain Lax vs Strict vs None.
Strict: never sent on cross-site requests (highest CSRF protection but breaks "logged in" link clicks).
Lax (default): sent on top-level GET navigation (e.g., clicking a link) but not on POST/iframe/img.
None: always sent — must be combined with Secure; for cross-site embeds.
Q17. How do you migrate IndexedDB schema?
Bump the version number. In onupgradeneeded, branch on oldVersion to apply incremental migrations. Listen to onversionchange on existing connections to close them so the upgrade can proceed.
Q18. CDN vs browser cache — when does each apply?
CDN caches shared responses for many users at the edge. Browser cache is per-user. Use s-maxage (CDN) and max-age (browser) to set them independently. Cache-Control: private tells CDNs not to cache.
Q19. Design an offline-capable Twitter-like timeline.
- Service Worker for app shell (Cache-First).
- IndexedDB store for tweets, normalized by id.
- On open: render from IDB instantly, then fetch newer tweets and merge.
- Compose tweet → write to IDB pending store + queue Background Sync.
- Use cursor-based pagination (since_id / max_id) to merge cleanly.
- Conflict resolution: server is the truth; client retries with idempotency key.
Q20. What happens to localStorage in private/incognito mode?
It exists but is cleared when the session ends. Quotas may be smaller. Some browsers throw QuotaExceededError earlier. Always wrap writes in try/catch.

27. Real-World Scenarios (whiteboard ready) Advanced

Scenario A — "Make this dashboard load instantly on revisit"

  • Hash & immutable-cache static bundles.
  • no-cache the HTML so deploys take effect.
  • Precache shell via Service Worker.
  • Persist React Query cache to IndexedDB; hydrate on boot.
  • Show last-known data instantly, refetch in background (SWR pattern).

Scenario B — "Users complain stale data after deploy"

  • Check Cache-Control on HTML — should be no-cache.
  • Hash filenames so new bundles are new URLs.
  • Service Worker: bump cache name, skipWaiting() + clients.claim().
  • Notify in UI: "new version available, reload" pattern.

Scenario C — "Implement a draft autosave"

  • Debounced writes to IndexedDB on edit.
  • Conflict marker: store updatedAt on server response.
  • On reconnect: send draft if local is newer.

Scenario D — "Logout but data lingers"

  • localStorage.clear() + sessionStorage.clear().
  • indexedDB.databases() → delete each.
  • caches.keys() → caches.delete().
  • navigator.serviceWorker.getRegistrations() → unregister.
  • Server-side: invalidate refresh token.

28. Rapid-Fire Gotchas Advanced

  • localStorage stores only strings. Numbers, booleans, objects all become strings.
  • localStorage blocks the main thread — never store MBs of data.
  • storage event fires in other tabs only.
  • IndexedDB transactions auto-commit when the microtask queue is empty — never await a non-IDB promise inside one.
  • Cookies sent with every request → keep them tiny.
  • Vary: * effectively disables caching.
  • no-cache ≠ no-store (the former still caches, just revalidates).
  • POST responses are not cached by default.
  • bfcache restoration is broken by unload handlers and open IDB transactions.
  • Storage may be evicted unless you call navigator.storage.persist().
  • Safari ITP clears storage after 7 days of no first-party interaction.
  • Cross-origin iframes get partitioned storage in modern browsers.
  • Service Worker scope = the path it's served from. /sw.js controls everything; /foo/sw.js only /foo/*.
  • A new SW waits until all controlled tabs close — use skipWaiting() + clients.claim() to take over immediately.
  • fetch uses the HTTP cache by default; pass {cache: 'no-store'} to bypass.
  • React Query's staleTime: 0 (default) refetches on every mount — set it explicitly.
  • Always handle QuotaExceededError — it WILL happen on iOS.
  • Don't put React Query data in Redux. Don't put forms in Redux either.
  • Selectors that return new array/object literals every call defeat memoization → wrap with createSelector.
  • JSON.parse can throw — always try/catch around storage reads.
  • indexedDB.databases() isn't supported in Firefox; track DB names yourself if you need to enumerate.
  • Service Worker registrations survive page reload — use DevTools → Application → "Update on reload" while developing.

Master these layers and you can confidently answer "where does the data live, how is it cached, and what happens when the network dies?" — the heart of any senior frontend interview.
