1. What is Frontend System Design?

Beginner

Definition

Frontend System Design (FSD) is the practice of designing the client-side architecture of web applications at scale. Unlike backend system design that focuses on databases, servers, and distributed systems, FSD focuses on:

  • How the user interface is structured and rendered
  • How data flows through the client
  • How the application communicates with backend services
  • How performance, accessibility, and reliability are maintained at scale
  • How teams collaborate on the same codebase without stepping on each other

Why Companies Ask FSD in Interviews

CompanyWhy They AskWhat They Evaluate
GoogleScale (billions of users)Component design, performance budgets, a11y
MetaComplex UIs (News Feed, Messenger)State management, real-time updates, data normalization
AmazonConversion-critical UIsPerformance, progressive loading, error handling

Flipkart/SwiggyMobile-first, flaky networksPWA, caching, optimistic UI, SSR

Non-Functional Requirements Checklist

Always mention these — they differentiate senior from junior candidates:

  • Performance: Core Web Vitals (LCP < 2.5s, INP < 200ms, CLS < 0.1)
  • Accessibility: WCAG 2.1 AA compliance, keyboard navigation, screen reader support
  • Internationalization (i18n): RTL support, pluralization, date/number formatting
  • Responsiveness: Mobile-first, adaptive layouts, touch targets ≥ 44px
  • SEO: SSR/SSG for public pages, structured data, meta tags
  • Offline support: Service Workers, background sync
  • Error handling: Graceful degradation, error boundaries, retry logic
  • Security: XSS prevention, CSP, CORS, auth token management
  • Testing: Unit, integration, E2E, visual regression
  • Monitoring: RUM, error tracking, performance budgets
Interview Insight At companies like Flipkart/Swiggy, they specifically look for: "What happens on a 2G connection?" and "How does the app work offline?" — always address network resilience.

3. Client-Server Architecture

Beginner

Theory: How the Web Works

When a user types a URL and presses Enter:

  1. DNS Resolution: Browser looks up IP address (DNS cache → OS cache → resolver → root → TLD → authoritative)
  2. TCP Handshake: 3-way handshake (SYN → SYN-ACK → ACK)
  3. TLS Handshake: For HTTPS — certificate exchange, key agreement (adds 1-2 RTT)
  4. HTTP Request: Browser sends GET / with headers (User-Agent, Accept, Cookie, etc.)
  5. Server Response: HTML document returned (200 OK)
  6. HTML Parsing: DOM tree construction begins (top to bottom)
  7. Resource Discovery: Parser encounters CSS, JS, images → fires new requests
  8. CSSOM Construction: CSS parsed into CSSOM tree
  9. JavaScript Execution: Blocks parsing (unless async/defer)
  10. Render Tree: DOM + CSSOM merged → layout → paint → composite
┌──────────┐          ┌─────────────────────────────────────┐
│  Browser │          │            Server                   │
│ (Client) │          │  ┌─────────────────────────────┐    │
│          │──DNS────→│  │  Load Balancer (Nginx/ALB)  │    │
│          │←──IP─────│  └──────────────┬──────────────┘    │
│          │          │                 │                    │
│          │──TCP────→│  ┌──────────────▼──────────────┐    │
│          │──TLS────→│  │  Application Server (Node)  │    │
│          │──HTTP───→│  └──────────────┬──────────────┘    │
│          │←─HTML────│                 │                    │
│          │←─CSS─────│  ┌──────────────▼──────────────┐    │
│          │←─JS──────│  │    Database / Cache / CDN    │    │
│          │←─Assets──│  └─────────────────────────────┘    │
└──────────┘          └─────────────────────────────────────┘

Critical Rendering Path

The sequence of steps the browser must complete to render the first pixel:

HTML → DOM Tree
                  ↘
                    Render Tree → Layout → Paint → Composite
                  ↗
CSS  → CSSOM Tree

JavaScript can BLOCK both DOM and CSSOM construction!

Key facts for interviews:

  • CSS is render-blocking (browser won't paint until CSSOM is ready)
  • <script> without defer/async blocks HTML parsing
  • <script defer> downloads in parallel, executes after DOM ready (in order)
  • <script async> downloads in parallel, executes immediately (no order guarantee)
  • <link rel="preload"> hints browser to fetch resources early
  • <link rel="preconnect"> establishes connection to third-party origin early
Common Mistake Placing <script> tags in <head> without defer blocks the entire page render. Always use defer for non-critical scripts or place them before </body>.

Deep Dive: Client-Side Rendering (CSR)

// How Angular works by default (CSR)
// 1. Browser downloads empty HTML shell
// 2. Downloads main.js bundle
// 3. Angular bootstraps, creates DOM
// 4. User sees content ONLY after JS executes

// Timeline:
// [blank screen]──[download JS]──[parse/execute JS]──[render]──[interactive]
//                                                     ↑ FCP      ↑ TTI
// Problem: Large gap between navigation and FCP

Pros: Simple deployment (static files on CDN), rich interactivity, no server needed for rendering

Cons: Poor SEO (crawlers may not execute JS), slow FCP on slow devices, large JS bundles

Deep Dive: Server-Side Rendering (SSR)

// Angular Universal (SSR) — how it works:
// 1. Request hits Node.js server
// 2. Angular renders component tree to HTML STRING on server
// 3. Sends fully-formed HTML to browser
// 4. Browser shows content immediately (FCP ✓)
// 5. JS bundle downloads and "hydrates" — attaches event listeners
// 6. App becomes interactive (TTI)

// angular.json — enabling SSR:
// ng add @angular/ssr

// server.ts (simplified):
import { renderApplication } from '@angular/platform-server';
import { AppComponent } from './app/app.component';

// Server renders full HTML:
const html = await renderApplication(AppComponent, {
  document: indexHtml,
  url: req.url
});
res.send(html);

Hydration in Angular 16+:

// app.config.ts
import { provideClientHydration } from '@angular/platform-browser';

export const appConfig = {
  providers: [
    provideClientHydration()  // Enables non-destructive hydration
  ]
};

// What hydration does:
// 1. Server sends HTML + serialized state (TransferState)
// 2. Client Angular reuses existing DOM nodes (doesn't destroy & recreate)
// 3. Attaches event listeners to existing elements
// 4. Result: No content flickering, faster TTI
Angular 17+ Tip Angular 17 introduced partial hydration via @defer blocks. Components inside @defer are not hydrated until their trigger condition is met (viewport, interaction, idle, timer).

SSG & ISR (Not native to Angular but important to know)

// SSG: Pre-render pages at BUILD time
// Angular Prerendering (angular.json):
{
  "prerender": {
    "routesFile": "routes.txt"  // List of routes to pre-render
  }
}
// Result: Static HTML files served from CDN — fastest possible TTFB

// ISR: Frameworks like Next.js/Nuxt support this natively
// Concept: Serve stale cached page → regenerate in background
// Angular equivalent: Use SSR + CDN caching with stale-while-revalidate headers
// Cache-Control: public, s-maxage=60, stale-while-revalidate=600

5. SPA vs MPA (Single Page vs Multi Page)

Beginner

Theory

AspectSPA (Angular, React)MPA (Traditional)
NavigationClient-side routing (no full page reload)Full page reload on every navigation
Initial LoadHeavier (downloads entire app shell + route)Lighter per page
Subsequent NavigationInstant (only data fetched)Full reload each time
SEONeeds SSR/prerenderingNaturally SEO-friendly
ComplexityHigher (state, routing, auth, caching)Lower per page, higher at scale
User ExperienceApp-like, smooth transitionsPage flashes on navigation
ExamplesGmail, Figma, NotionWikipedia, Amazon (mostly), eBay

How Angular Router Works (SPA Navigation)

// When user clicks a link in Angular SPA:
// 1. Router intercepts click (prevents default navigation)
// 2. URL updates via History API (pushState)
// 3. Router matches URL to route config
// 4. Lazy-loaded module downloaded (if not cached)
// 5. Component rendered in <router-outlet>
// 6. Guards/resolvers execute if configured
// 7. No full page reload — only DOM update!

// Route configuration:
const routes: Routes = [
  { path: '', component: HomeComponent },
  { 
    path: 'dashboard',
    loadComponent: () => import('./dashboard/dashboard.component')
      .then(m => m.DashboardComponent),  // Lazy loaded!
    canActivate: [AuthGuard]
  },
  { path: '**', component: NotFoundComponent }
];

Hybrid Approaches (Modern Trend)

Modern apps combine both:

  • Marketing pages: SSG/MPA (SEO, fast load)
  • App shell: SPA (rich interactivity)
  • Example: Amazon — product listing (SSR) + checkout flow (SPA-like)

Theory: Atomic Design

Brad Frost's methodology for building component hierarchies:


┌─────────────────────────────────────────────────────────────┐
│  PAGES (full screens)                                       │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  TEMPLATES (page layouts with placeholders)           │  │
│  │  ┌─────────────────────────────────────────────────┐  │  │

│  │  │  │  MOLECULES (groups of atoms)             │   │  │  │
│  │  │  │  ┌───────────────────────────────────┐   │   │  │  │
│  │  │  │  │  ATOMS (buttons, inputs, labels)  │   │   │  │  │
│  │  │  │  └───────────────────────────────────┘   │   │  │  │
│  │  │  └──────────────────────────────────────────┘   │  │  │
│  │  └─────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘

Examples:
  Atoms     → Button, Input, Icon, Badge, Avatar
  Molecules → SearchBar (Input + Button + Icon), FormField (Label + Input + Error)
  Organisms → Header (Logo + Nav + SearchBar + UserMenu), ProductCard
  Templates → DashboardLayout (Header + Sidebar + Content area)
  Pages     → DashboardPage (Template + real data)

Angular Component Design Principles

// ═══ SMART vs DUMB COMPONENTS ═══

// DUMB (Presentational) Component — Pure UI, no side effects
@Component({
  selector: 'app-product-card',
  template: `
    <div class="card">
      <img [src]="product.image" [alt]="product.name">
      <h3>{{ product.name }}</h3>
      <p>{{ product.price | currency }}</p>
      <button (click)="addToCart.emit(product)">Add to Cart</button>
    </div>
  `,
  changeDetection: ChangeDetectionStrategy.OnPush  // ← Key for performance!
})
export class ProductCardComponent {
  @Input() product!: Product;
  @Output() addToCart = new EventEmitter<Product>();
}

// SMART (Container) Component — Handles logic, state, API calls
@Component({
  selector: 'app-product-list',
  template: `
    <app-product-card
      *ngFor="let product of products$ | async"
      [product]="product"
      (addToCart)="onAddToCart($event)"
    />
  `
})
export class ProductListComponent {
  products$ = this.store.select(selectProducts);
  
  constructor(private store: Store) {}
  
  onAddToCart(product: Product) {
    this.store.dispatch(addToCart({ product }));
  }
}

7. Design Patterns for Frontend

Intermediate

Theory: Patterns You MUST Know

1. Observer Pattern (RxJS)

// Foundation of Angular's reactive programming
// Observable = data source that emits values over time
// Observer = subscriber that reacts to emitted values

import { Subject, BehaviorSubject } from 'rxjs';

// NotificationService — global event bus
@Injectable({ providedIn: 'root' })
export class NotificationService {
  private notifications$ = new BehaviorSubject<Notification[]>([]);
  
  getNotifications() { return this.notifications$.asObservable(); }
  
  addNotification(n: Notification) {
    const current = this.notifications$.value;
    this.notifications$.next([...current, n]);
  }
  
  dismiss(id: string) {
    const filtered = this.notifications$.value.filter(n => n.id !== id);
    this.notifications$.next(filtered);
  }
}

2. Singleton Pattern (Services)

// Angular services with providedIn: 'root' are singletons
@Injectable({ providedIn: 'root' })  // ← ONE instance for entire app
export class AuthService {
  private currentUser$ = new BehaviorSubject<User | null>(null);
  
  // Every component that injects AuthService gets the SAME instance
  // This ensures consistent state across the app
}

3. Strategy Pattern (Dynamic behavior)

// Different validation strategies based on context
interface ValidationStrategy {
  validate(value: string): ValidationResult;
}

class EmailValidation implements ValidationStrategy {
  validate(value: string) {
    const valid = /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value);
    return { valid, error: valid ? null : 'Invalid email format' };
  }
}

class PhoneValidation implements ValidationStrategy {
  validate(value: string) {
    const valid = /^\+?[\d\s-]{10,}$/.test(value);
    return { valid, error: valid ? null : 'Invalid phone number' };
  }
}

// Usage in component:
class FormFieldComponent {
  @Input() strategy!: ValidationStrategy;
  
  onBlur(value: string) {
    const result = this.strategy.validate(value);
    this.showError(result);
  }
}

4. Facade Pattern (Simplify complex subsystems)

// Hide complexity behind a clean interface
@Injectable({ providedIn: 'root' })
export class CheckoutFacade {
  // Internally uses multiple services:
  constructor(
    private cartService: CartService,
    private paymentService: PaymentService,
    private inventoryService: InventoryService,
    private notificationService: NotificationService,
    private analyticsService: AnalyticsService
  ) {}

  // Exposes simple API to components:
  async checkout(order: Order): Promise<CheckoutResult> {
    const available = await this.inventoryService.checkStock(order.items);
    if (!available) throw new OutOfStockError();
    
    const payment = await this.paymentService.processPayment(order.total);
    if (!payment.success) throw new PaymentFailedError();
    
    await this.cartService.clear();
    this.notificationService.show('Order placed!');
    this.analyticsService.track('purchase', order);
    
    return { orderId: payment.orderId, status: 'confirmed' };
  }
}

5. Decorator Pattern (Angular's @ decorators)

// @Component, @Injectable, @Input — all decorators
// Custom decorator for caching:
function Cacheable(ttlMs: number = 60000) {
  return function(target: any, key: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    const cache = new Map<string, { value: any; timestamp: number }>();
    
    descriptor.value = function(...args: any[]) {
      const cacheKey = JSON.stringify(args);
      const cached = cache.get(cacheKey);
      
      if (cached && Date.now() - cached.timestamp < ttlMs) {
        return of(cached.value);  // Return cached Observable
      }
      
      return original.apply(this, args).pipe(
        tap(result => cache.set(cacheKey, { value: result, timestamp: Date.now() }))
      );
    };
    return descriptor;
  };
}

// Usage:
@Cacheable(30000)  // Cache for 30 seconds
getProducts(): Observable<Product[]> {
  return this.http.get<Product[]>('/api/products');
}

9. Build Tools & Bundlers

Intermediate

Theory: Why Bundlers Exist

Browsers can load ES modules natively, but bundlers are still essential for:

  • Code Splitting: Break one large bundle into smaller chunks loaded on demand
  • Tree Shaking: Remove unused code (dead code elimination)
  • Minification: Reduce file size (remove whitespace, shorten variable names)
  • Transpilation: Convert TypeScript/modern JS to browser-compatible code
  • Asset Optimization: Compress images, inline critical CSS, hash filenames for caching
  • Dev Experience: Hot Module Replacement, source maps, dev server

Angular's Build System

Angular VersionBundlerKey Feature
Angular ≤ 16WebpackMature, plugin ecosystem, slower
Angular 17+esbuild + Vite10-80x faster builds, native ESM dev server

Code Splitting Strategies

// 1. ROUTE-BASED splitting (most common in Angular)
const routes: Routes = [
  {
    path: 'admin',
    loadChildren: () => import('./admin/admin.routes')
      .then(m => m.ADMIN_ROUTES)
    // Creates separate chunk: admin-HASH.js
  }
];

// 2. COMPONENT-BASED splitting (Angular 17+ @defer)
@Component({
  template: `
    @defer (on viewport) {
      <app-heavy-chart [data]="chartData" />
    } @placeholder {
      <div class="skeleton"></div>
    } @loading (minimum 200ms) {
      <app-spinner />
    } @error {
      <p>Failed to load chart</p>
    }
  `
})
// heavy-chart component is in its OWN chunk, loaded only when visible!

// 3. SERVICE-BASED splitting
async loadPdfGenerator() {
  const { PdfService } = await import('./services/pdf.service');
  const pdfService = new PdfService();
  return pdfService.generate(this.data);
}

11. Micro-Frontends

Advanced

Theory: When & Why

Micro-frontends apply microservices principles to the frontend. Each team owns a vertically sliced feature — from UI to API.

When to use:

  • Multiple teams (5+) working on one product
  • Teams need independent deploy cycles
  • Legacy migration (incrementally replace old app)
  • Different tech stacks per team (rarely ideal but sometimes necessary)

When NOT to use:

  • Small team (≤3 devs) — overhead outweighs benefits
  • Simple application — monolith is faster to develop
  • Shared state is critical between features

12. Islands Architecture & Server Components

Advanced

Theory: The Problem with Full-Page Hydration

Traditional SSR sends full HTML, then hydrates the entire page with JavaScript. This means the browser downloads, parses, and executes JS for components that are STATIC (header, footer, text content). Wasteful!

// ═══ THE SPECTRUM OF RENDERING ARCHITECTURES ═══
//
// Traditional CSR:    □□□□□□□□□□□  (all JS, no HTML until JS runs)
// Traditional SSR:    ████████████  (HTML sent, ALL re-hydrated)
// Islands:            ██░░██░░░██  (HTML sent, only interactive parts hydrated)
// Server Components:  ██░░░░░░░░░  (most stays server-rendered, never hydrated)
//
// █ = Interactive (hydrated with JS)
// ░ = Static (pure HTML, ZERO JS cost)
// □ = Empty (waiting for JS)

// ═══ ISLANDS ARCHITECTURE (Astro, Fresh, 11ty) ═══
//
// Page is mostly STATIC HTML (the "sea")
// Interactive widgets are "islands" that hydrate independently
//
// ┌──────────────────────────────────────────────────┐
// │  Static Header (HTML only — 0 JS)                │
// ├──────────────────────────────────────────────────┤
// │  Static Content      │  [Interactive   ]         │
// │  (article text,      │  [ Search Bar  ]  ← Island│
// │   images, etc.)      │  [_____________]         │
// │                      │                           │
// │  More static text    │  [Interactive   ]         │
// │  ...                 │  [ Comment Box ]  ← Island│
// │                      │  [_____________]         │
// ├──────────────────────────────────────────────────┤
// │  Static Footer (HTML only — 0 JS)                │
// └──────────────────────────────────────────────────┘
//
// BENEFIT: Page with 50KB of JS only loads ~5KB (just the islands)
// IDEAL FOR: Content-heavy sites (blogs, docs, marketing, e-commerce)

Angular's Approach: Partial Hydration with @defer

// ═══ Angular 17+ — PARTIAL HYDRATION ═══
// Angular's answer to Islands Architecture:
// Components wrapped in @defer DON'T hydrate until triggered

@Component({
  template: `
    <!-- This hydrates immediately (critical interactive content) -->
    <app-search-bar />

    <!-- This is server-rendered HTML, hydrated ONLY when visible -->
    @defer (on viewport) {
      <app-comments [postId]="postId" />
    } @placeholder {
      <div class="comment-skeleton">Loading comments...</div>
    }

    <!-- This hydrates ONLY when user interacts -->
    @defer (on interaction) {
      <app-rich-editor />
    } @placeholder {
      <div class="fake-editor" tabindex="0">Click to edit...</div>
    }

    <!-- This never hydrates until idle time -->
    @defer (on idle) {
      <app-recommendations />
    }
  `
})
// Result: Only search-bar JS loads immediately
// Comments JS loads when scrolled into view
// Editor JS loads on first click
// Recommendations JS loads when browser is idle

// ═══ Angular 19+ — EVENT REPLAY ═══
// Problem: User clicks a @defer placeholder before it hydrates
// Solution: Angular records the click, replays it after hydration
// User doesn't notice any delay!

React Server Components (RSC) — Concept for Angular Devs

// ═══ SERVER COMPONENTS — What Angular devs should know ═══
// (Even though Angular doesn't have RSC yet, interviewers may ask)
//
// KEY CONCEPT:
// Server Components = components that ONLY run on the server
// They NEVER ship JS to the client (not even for hydration!)
//
// React splits components into:
// • Server Components (default): Run on server, render to HTML, no JS shipped
// • Client Components ("use client"): Traditional — JS shipped + hydrated
//
// BENEFITS:
// • Zero JS for data-fetching components (fetch in component, render HTML)
// • Direct database access from component (no API layer needed!)
// • Large dependencies (markdown parser, syntax highlighter) stay on server
//
// ANGULAR EQUIVALENT (upcoming):
// • @defer (on viewport/interaction) achieves similar "no JS until needed"
// • Angular SSR + signals is moving toward fine-grained reactivity
// • Angular team is exploring "server-only components" for future versions
//
// INTERVIEW ANSWER: "Angular achieves similar benefits through partial hydration
// with @defer blocks and provideClientHydration(). While not architecturally 
// identical to RSC, the practical outcome is the same: reduced client JS,
// faster TTI, and progressive interactivity."
Interview Q&A

Q: What are Islands Architecture and Server Components? How does Angular handle this? (Google, Meta, startups)

Answer: Islands Architecture treats a page as mostly static HTML with isolated "islands" of interactivity that hydrate independently. Server Components (React) are components that only execute on the server and ship zero JS. Angular's equivalent is @defer blocks with partial hydration: SSR renders the full page, but deferred components don't hydrate until their trigger fires (viewport, interaction, idle). This achieves similar JS savings without architectural complexity. Angular 19+ adds event replay so clicks on unhydrated regions are captured and replayed after hydration.

Tree Shaking — Deep Mechanics

// ═══ WHY TREE SHAKING SOMETIMES FAILS ═══
//
// Tree shaking works by analyzing ES module import/export STATICALLY.
// It CANNOT shake code that has SIDE EFFECTS.

// ❌ SIDE EFFECT — can't be tree-shaken:
import './polyfills';  // No export, just executes code
// The file might modify globals — bundler can't remove it safely

// ❌ BARREL FILE TRAP:
// libs/shared/index.ts:
export * from './button';    // 50KB
export * from './table';     // 200KB  
export * from './chart';     // 500KB
// If you import { Button } from '@shared' → bundler MAY include all 750KB!
// WHY: barrel re-exports can create side-effect chains

// ✅ FIX: Import directly from the source:
import { Button } from '@shared/button';  // Only 50KB

// ═══ sideEffects field in package.json ═══
// Tell bundler which files are safe to tree-shake:
{
  "sideEffects": false  // NONE of our files have side effects — shake freely
}
// Or specify which files DO have side effects:
{
  "sideEffects": ["./src/polyfills.ts", "**/*.css"]
}

// ═══ Angular-specific: providedIn: 'root' IS tree-shakable ═══
// Services with providedIn: 'root' are ONLY included if injected somewhere
// Services registered in module providers: [] are ALWAYS included
@Injectable({ providedIn: 'root' }) // ✅ Tree-shakable
export class AnalyticsService { }
// If no component injects AnalyticsService → it's removed from bundle!
Interview Tip When asked "How would you reduce bundle size?", mention: (1) Lazy-load routes, (2) @defer for heavy components, (3) Import directly (not from barrel files), (4) Check sideEffects in package.json of dependencies, (5) Use Angular budgets to fail CI if bundle exceeds threshold, (6) Analyze with source-map-explorer.

14. Edge Computing & Edge SSR

Advanced

Theory: What is "The Edge"?

Edge computing = running code at CDN nodes closest to the user (200+ locations worldwide), rather than at a central origin server. This reduces latency from 200-500ms to 10-50ms.

// ═══ TRADITIONAL vs EDGE ARCHITECTURE ═══
//
// TRADITIONAL (Origin-only):
// User (Mumbai) → CDN (static only) → Origin (US-East) → Response
// Latency: 200-400ms for dynamic content
//
// EDGE SSR:
// User (Mumbai) → Edge Node (Mumbai) → Renders HTML at edge → Response  
// Latency: 10-50ms! (code runs in Mumbai, not US)
//
// ═══ EDGE PLATFORMS ═══
// • Cloudflare Workers: V8 isolates, 200+ locations, $0 for first 100K req/day
// • Vercel Edge Functions: Built into Vercel, runs Middleware at edge
// • AWS CloudFront Functions / Lambda@Edge
// • Deno Deploy: Deno runtime at edge
// • Fastly Compute@Edge: WASM-based
//
// ═══ WHAT CAN RUN AT THE EDGE? ═══
// ✅ SSR rendering (generate HTML per-request)
// ✅ Authentication checks (validate JWT, redirect if expired)
// ✅ A/B testing (select variant, no client-side flicker!)
// ✅ Geolocation (show local prices, language)
// ✅ Personalization (different content per user segment)
// ✅ API routing / rewriting
// ❌ Database queries (DB is still at origin — use read replicas)
// ❌ Heavy computation (edge has limited CPU/memory)

// ═══ ANGULAR AT THE EDGE ═══
// Angular SSR can run at edge with Cloudflare Workers:
// 1. Build Angular with SSR: ng build --configuration production
// 2. Deploy server bundle to Cloudflare Workers
// 3. HTML is rendered at the nearest edge node
//
// Analog.js (Angular meta-framework) supports:
// • Cloudflare Pages (edge SSR)
// • Vercel Edge
// • Netlify Edge Functions
//
// ═══ STALE-WHILE-REVALIDATE at Edge ═══
// Edge caches SSR'd HTML for 60s:
// Request 1: Edge renders HTML, caches it (100ms)
// Request 2-100: Served from edge cache (5ms!)
// After 60s: Serve stale cache + background revalidate
// Perfect for: product pages, blog posts, dashboards
Edge Limitations Edge functions have constraints: limited memory (128MB), limited execution time (50ms on Cloudflare, 30s on Vercel), no filesystem access, limited Node.js APIs. Don't try to run heavy computation or database connections directly at edge — use it for rendering + lightweight logic.

Q: What is Edge SSR and when would you use it vs traditional SSR? (Google, Vercel-funded startups, senior roles)

Answer: Edge SSR renders HTML at CDN nodes (200+ locations) closest to the user, reducing TTFB from 200-400ms to 10-50ms. Use it for: content that varies by geography (prices, language), authenticated pages (check JWT at edge), A/B tests (no client flicker). Use traditional SSR when: you need database access, heavy computation, or long-running operations. Angular supports this via Analog.js deployed to Cloudflare Pages or Vercel Edge. Trade-off: edge has limited CPU/memory, so complex pages might be slower at edge than a powerful origin server.

13. Interview Questions (Previously Asked)

Q1: What's the difference between CSR, SSR, and SSG? When would you use each? (Google, Amazon, Flipkart)

Answer: CSR renders entirely in the browser — good for dashboards/internal tools but poor SEO (Googlebot CAN render JS but slower crawl budget, potential soft 404s) and slow FCP. SSR renders on the server per request — ideal for dynamic content needing SEO (e-commerce, social media). SSG pre-renders at build time — fastest TTFB, perfect for static content (blogs, docs). ISR (Incremental Static Regeneration) — serve static, revalidate in background (not native Angular, but achievable with edge caching + stale-while-revalidate). Modern apps use hybrid: SSG for marketing, SSR for product pages, CSR for authenticated dashboard. Angular supports all three: default CSR, Angular Universal for SSR, and prerendering for SSG.

Q2: How would you structure a large Angular application with 50+ developers? (Microsoft, Kyndryl, TCS)

Answer: Nx monorepo with strict module boundaries. Feature libraries per domain (orders, products, users). Shared UI library with Storybook. Each team owns a slice: feature lib + data-access lib + API. Enforce boundaries via Nx's eslint rule. CI uses affected-only builds (nx affected:build). Shared state via NgRx with feature stores. Code generation via Nx generators for consistency. PR reviews enforced per-library CODEOWNERS. Bundle budgets per lazy route.

Q3: Explain the critical rendering path and how you'd optimize it. (Google, Meta)

Answer: CRP: HTML → DOM + CSS → CSSOM → Render Tree → Layout → Paint → Composite. Optimizations: (1) Minimize render-blocking CSS — inline critical CSS, defer non-critical. (2) Use font-display: swap to avoid invisible text. (3) Preload LCP image/fonts. (4) Defer non-critical JS with async/defer. (5) Reduce DOM depth/complexity. (6) Use contain: layout for isolated components. (7) Avoid layout thrashing (batch DOM reads then writes).

Q4: What are micro-frontends? When would you NOT use them? (Amazon, Flipkart, Atlassian)

Answer: Micro-frontends are independently developed, deployed, and maintained frontend applications composed into one user experience. Implementation: Module Federation, Single-SPA, or route-based. I would NOT use them for: small teams (≤3 devs), simple apps, apps needing heavy shared state, when consistent UX is critical (shared design system is harder). Overhead includes: increased bundle size (shared deps), complex CI/CD, harder debugging across boundaries, potential version conflicts.

Q5: Design the component architecture for a reusable data table. (Microsoft, Salesforce, Google)

Answer: Atomic design: Table (organism) composed of: Header (molecule: sort + filter), Row (molecule: cells + actions), Cell (atom: text/link/badge), Pagination (molecule), Toolbar (molecule: search + bulk actions). API: @Input() columns (column config array), @Input() data, @Input() pageable, @Output() rowClick, @Output() sort, @Output() filter. Virtual scrolling via CDK for 10K+ rows. OnPush change detection. Signals for column visibility state. Content projection for custom cell templates.

Q6: Explain Angular's change detection and how you optimize it. (All companies)

Answer: Default: Angular checks EVERY component on every event (Zone.js patches async APIs). Tree traversal top→bottom. Optimizations: (1) OnPush strategy — only checks when @Input reference changes or event fires in component. (2) trackBy in *ngFor — prevents re-creating DOM for unchanged items. (3) Signals (Angular 16+) — fine-grained reactivity without Zone.js. (4) Detach change detector for static views. (5) Pure pipes (memoized). (6) NgZone.runOutsideAngular() for animations/timers that don't need CD.

Q7: What is hydration in Angular? Explain partial hydration. (Google, modern Angular interviews)

Answer: Hydration: After SSR sends HTML, client Angular "hydrates" — it reuses existing DOM nodes and attaches event listeners instead of destroying and recreating the DOM. Angular 16+ uses non-destructive hydration (provideClientHydration()). Partial hydration (Angular 17+): Only hydrate components that need interactivity. @defer blocks with on interaction/on viewport triggers delay hydration of heavy components until needed. Result: faster TTI, less JS executed upfront.

Q8: How does tree shaking work? Why does Angular use ES modules? (Intermediate+)

Answer: Tree shaking = dead code elimination. Bundler (esbuild/webpack) statically analyzes import/export statements, removes unused exports. Works because ES modules have static structure (imports at top level, no conditional imports). Angular uses ESM so unused services, components, and utilities are removed from final bundle. CommonJS can't be tree-shaken because require() is dynamic. Best practice: use named exports, avoid barrel files that re-export everything, use providedIn: 'root' (tree-shakable providers).
