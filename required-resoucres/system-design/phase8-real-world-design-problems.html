Phase 8: Real-World Design Problems

The final boss. Full system design walkthroughs using the RADIO framework. Practice structuring your answer for 45-minute interviews. Each problem covers architecture, data flow, performance, and trade-offs.

RADIO Framework (Your Interview Structure)

Critical 
// ═══ RADIO = How to STRUCTURE your FSD interview answer ═══
// Spend ~5 min on each step in a 30-45 min interview

R — REQUIREMENTS  (Clarify scope, features, constraints)
    "What are the core features? What can I deprioritize?"
    "How many concurrent users? What devices?"
    "Offline support needed? Real-time updates?"

A — ARCHITECTURE  (High-level system design)
    Component tree, data flow direction, rendering strategy
    Draw boxes: Client → BFF → Services
    Key technology choices and WHY

D — DATA MODEL    (State shape, API contracts, storage)
    Client state structure (normalized entities)
    API endpoints and response shapes
    Caching strategy, storage (memory/localStorage/IndexedDB)

I — INTERFACE     (Component API, key components)
    Smart vs Dumb components
    Key component inputs/outputs
    Routing structure

O — OPTIMIZATIONS (Performance, edge cases, trade-offs)
    Performance: lazy loading, virtualization, caching
    Accessibility, error handling, offline
    What trade-offs did you make and why?

// ═══ TIME ALLOCATION ═══
// 0-5 min:  Requirements (ASK questions, don't assume)
// 5-15 min: Architecture + Data Model (draw diagrams)
// 15-30 min: Interface + key implementation details
// 30-40 min: Optimizations + trade-offs
// 40-45 min: Questions from interviewer
Interview Pro Tip Always START by asking clarifying questions. "Should I focus on mobile or desktop?" "Do we need offline support?" "What's the scale — thousands or millions of users?" This shows maturity and prevents you from designing the wrong thing.

Problem 1: Design Google Search Frontend

Critical

Requirements

  • Search input with autocomplete suggestions (debounced)
  • Search results page with pagination
  • Different result types: web, images, videos, news
  • Recent searches / search history
  • Performance: instant feel (LCP < 1.5s)
R — Requirements Clarification: "Is voice search in scope? Do we need personalization? What's the expected QPS for autocomplete? Should results be SSR or CSR?"
A — Architecture: 
┌─────────────────────────────────────────────────────────┐
│                    ARCHITECTURE                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌──────────────┐     ┌───────────────┐                │
│  │  Search Bar  │ ──→ │ Autocomplete  │                │
│  │  Component   │     │   Service     │                │
│  └──────┬───────┘     └───────┬───────┘                │
│         │                     │                         │
│         │ submit         GET /suggestions?q=...         │
│         ↓                     ↓                         │
│  ┌──────────────┐     ┌───────────────┐                │
│  │  Results     │ ←── │  Search API   │                │
│  │  Page (SSR)  │     │  (BFF layer)  │                │
│  └──────────────┘     └───────────────┘                │
│         │                                               │
│    ┌────┴────┬──────────┬─────────┐                    │
│    ↓         ↓          ↓         ↓                    │
│  Web      Images      Video     News                   │
│  Results  Grid        Cards     Feed                   │
│                                                         │
└─────────────────────────────────────────────────────────┘

Rendering: SSR for results page (SEO + fast LCP)
CSR for autocomplete (interactive, no SEO needed)
D — Data Model: 
// Autocomplete API:
GET /api/suggestions?q=ang&limit=8
Response: { suggestions: ["angular", "angular material", "angularjs"] }

// Search API:
GET /api/search?q=angular+tutorial&type=web&page=1
Response: {
  results: [
    { id, title, url, snippet, favicon, timestamp },
    ...
  ],
  totalResults: 1500000,
  relatedSearches: ["angular docs", "angular vs react"],
  spelling: { corrected: null }
}

// Client State:
{
  query: string,
  suggestions: string[],
  results: SearchResult[],
  activeTab: 'web' | 'images' | 'video' | 'news',
  page: number,
  loading: boolean,
  recentSearches: string[]  // localStorage
}
I — Interface (Key Components): 
// Component Tree:
SearchPage
├── SearchBar (input + suggestions dropdown)
│   ├── Input (debounced, keyboard nav for suggestions)
│   └── SuggestionsList (highlighted matching text)
├── TabBar (web | images | video | news)
├── ResultsList
│   ├── WebResult (title, URL, snippet)
│   ├── ImageGrid (masonry layout)
│   ├── VideoCard (thumbnail, duration)
│   └── NewsCard (source, time)
├── Pagination
└── RelatedSearches
O — Optimizations:
  • Debounce autocomplete: 300ms delay, cancel on new keystroke
  • Cache recent suggestion results (in-memory Map, LRU)
  • SSR results page for SEO + fast LCP
  • Prefetch first result's page on hover
  • Virtual scroll for image grid (thousands of results)
  • URL state: /search?q=...&type=web&page=2 (shareable, back works)
  • Keyboard a11y: Arrow keys navigate suggestions, Enter selects

Problem 2: Design Twitter/X Feed

Advanced

Requirements

  • Infinite scroll feed with tweets (text, images, videos)
  • Real-time new tweet notifications ("5 new tweets" banner)
  • Like, retweet, reply (optimistic UI)
  • Compose tweet (with media upload)
  • Handle millions of concurrent users
A — Architecture: 
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  ┌─────────────┐    ┌──────────────┐    ┌───────────────┐   │
│  │  Feed Page   │    │ WebSocket    │    │   REST API    │   │
│  │  (CSR/SPA)   │ ←─ │  Service     │    │  (BFF)        │   │
│  └──────┬───────┘    └──────────────┘    └───────────────┘   │
│         │                                                    │
│    ┌────┴────┬──────────────────┐                           │
│    ↓         ↓                  ↓                           │
│  TweetCard  ComposeBox       Sidebar                        │
│  (virtual)  (rich text)      (trends)                       │
│                                                              │
│  State: Normalized tweet entities (Map by ID)               │
│  Feed: Ordered array of tweet IDs                           │
│  WebSocket: New tweet IDs pushed, prepend to feed           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
D — Data Model: 
// Normalized state:
{
  entities: {
    tweets: {
      "t1": { id: "t1", text: "...", authorId: "u1", likes: 42, 
              retweetCount: 5, replyCount: 3, mediaIds: ["m1"],
              timestamp: 1700000000, liked: false, retweeted: false },
    },
    users: {
      "u1": { id: "u1", name: "Sid", handle: "@sid", avatar: "..." }
    },
    media: {
      "m1": { id: "m1", type: "image", url: "...", width: 800, height: 600 }
    }
  },
  feed: {
    ids: ["t5", "t4", "t3", "t2", "t1"],  // Ordered
    cursor: "abc123",                       // For pagination
    hasMore: true,
    newTweetIds: ["t8", "t7", "t6"]        // Buffered (not shown yet)
  }
}

// API: Cursor-based pagination
GET /api/feed?cursor=abc123&limit=20
// WebSocket event: { type: "new_tweet", tweetId: "t8" }
O — Optimizations:
  • Virtual scroll: Only render visible tweets (~10-15 in viewport)
  • Optimistic likes: Increment immediately, revert on API failure
  • Image lazy loading: IntersectionObserver, progressive JPEG
  • New tweets banner: Buffer in state, show count, load on click (don't auto-scroll)
  • Normalized entities: Update user avatar in one place → reflected in all tweets
  • Connection-aware: Reduce image quality on slow connections
  • Offline: Cache last 50 tweets in IndexedDB, show on revisit

Problem 3: Design E-commerce Product Detail Page

Critical

Requirements

  • Product images (gallery with zoom), title, price, variants (size, color)
  • Add to cart with quantity selector
  • Reviews section (ratings, text, images)
  • Related products carousel
  • SEO-critical (must be indexable)
A — Architecture: 
// Rendering: SSR (Angular Universal) for SEO + fast LCP
// Hydration: Full hydration for interactivity

// Component Hierarchy:
ProductDetailPage (SSR)
├── Breadcrumbs
├── ImageGallery (lazy load non-visible images)
│   ├── MainImage (LCP element — preload!)
│   ├── ThumbnailStrip
│   └── ZoomOverlay (@defer on interaction)
├── ProductInfo
│   ├── Title + Rating summary
│   ├── Price (with discount display)
│   ├── VariantSelector (size/color matrix)
│   ├── QuantitySelector
│   └── AddToCartButton (sticky on mobile)
├── ProductTabs
│   ├── Description (HTML from CMS)
│   ├── Specifications (table)
│   └── Reviews (@defer on viewport — below fold)
│       ├── RatingSummary (bar chart)
│       ├── ReviewFilters
│       └── ReviewList (paginated)
└── RelatedProducts (@defer on idle — carousel)
D — Data Model: 
// API (single request for above-fold data):
GET /api/products/123
{
  id: "123",
  title: "Premium Headphones",
  price: { amount: 2999, currency: "INR", mrp: 4999, discount: 40 },
  images: [{ url, alt, width, height }],  // First image = LCP
  variants: [
    { type: "color", options: [{ value: "black", stock: 15 }, ...] },
    { type: "size", options: [{ value: "M", stock: 0 }, ...] }  // stock:0 = disabled
  ],
  rating: { average: 4.3, count: 1284 },
  inStock: true,
  deliveryEstimate: "Dec 15-17"
}

// Lazy-loaded (separate requests):
GET /api/products/123/reviews?page=1&sort=recent
GET /api/products/123/related?limit=12
O — Optimizations:
  • SSR: Full HTML for SEO + LCP (product title + image immediately visible)
  • Preload LCP image: <link rel="preload" as="image" fetchpriority="high">
  • @defer reviews: Only load when user scrolls to reviews section
  • Image CDN: srcset with responsive sizes, AVIF/WebP with fallback
  • Variant selection: Disable out-of-stock combinations, URL state for selected variant
  • Add to cart: Optimistic, sticky button on mobile, quantity validation
  • Schema.org: Structured data for rich Google snippets (price, rating, availability)

Problem 4: Design a Chat Application (WhatsApp Web)

Advanced

Requirements

  • 1:1 and group chats, message history (scroll to load older)
  • Real-time messaging (instant delivery)
  • Typing indicators, read receipts, online status
  • Media messages (images, files)
  • Offline support (queue messages, sync on reconnect)
A — Architecture: 
┌───────────────────────────────────────────────────────────────┐
│  WebSocket (persistent) for:                                  │
│  • Message delivery/receive                                   │
│  • Typing indicators                                          │
│  • Online/offline status                                      │
│  • Read receipts                                              │
│                                                               │
│  REST API for:                                                │
│  • Message history (paginated)                                │
│  • Media upload (presigned S3 URLs)                           │
│  • User search / contacts                                     │
│  • Conversation list                                          │
│                                                               │
│  IndexedDB for:                                               │
│  • Cached messages (offline access)                           │
│  • Message queue (send when online)                           │
│  • Media thumbnails                                           │
└───────────────────────────────────────────────────────────────┘

Components:
ChatApp
├── ConversationList (virtual scroll — could have 1000s)
│   └── ConversationItem (last msg, unread count, avatar)
├── ChatWindow
│   ├── ChatHeader (name, status, actions)
│   ├── MessageList (virtual scroll, load older on scroll up)
│   │   ├── MessageBubble (text/image/file/system)
│   │   ├── DateSeparator
│   │   └── TypingIndicator
│   └── MessageInput (text, emoji, file attach)
└── Sidebar (user profile, settings)
D — Data Model: 
// Normalized state:
{
  conversations: {
    "c1": { id: "c1", type: "1:1", participantIds: ["u1","u2"],
            lastMessageId: "m50", unreadCount: 3 }
  },
  messages: {
    "m50": { id: "m50", conversationId: "c1", senderId: "u2",
             text: "Hey!", timestamp: 1700000000, 
             status: "delivered" /* sent|delivered|read */,
             type: "text" }
  },
  users: {
    "u2": { id: "u2", name: "Alice", avatar: "...", online: true,
            lastSeen: 1700000000 }
  },
  typing: { "c1": ["u2"] },  // Users currently typing in each conversation
  offlineQueue: [
    { id: "temp-1", conversationId: "c1", text: "Hi!", timestamp: ... }
  ]
}

// WebSocket events:
{ type: "message", data: { conversationId, message } }
{ type: "typing", data: { conversationId, userId, isTyping } }
{ type: "status", data: { userId, online, lastSeen } }
{ type: "receipt", data: { messageId, status: "read" } }
O — Optimizations:
  • Virtual scroll: Both conversation list AND message list
  • WebSocket reconnection: Exponential backoff + fetch missed messages on reconnect
  • Optimistic send: Show message immediately with "sending..." status
  • IndexedDB: Cache last 100 messages per conversation (instant load on open)
  • Throttle typing: Send typing event max once per 3 seconds
  • Image upload: Show thumbnail immediately, upload in background, replace with final URL
  • E2E encryption: Signal protocol for message content
  • Multi-tab: SharedWorker for single WebSocket across tabs

Problem 5: Design an Analytics Dashboard

Intermediate

Requirements

  • Multiple widgets: charts, KPIs, tables, maps
  • Date range filter (affects all widgets)
  • Real-time data updates for some widgets
  • Customizable layout (drag & rearrange widgets)
  • Export to PDF/CSV
A — Architecture: 
// Key decisions:
// 1. Each widget fetches its OWN data (independent loading)
// 2. Shared date range filter triggers all widgets to refetch
// 3. Real-time widgets use SSE (server → client, unidirectional)
// 4. Layout persisted per user (API or localStorage)

DashboardPage
├── FilterBar (date range, comparison mode)
├── WidgetGrid (CSS Grid + CDK Drag&Drop)
│   ├── KpiWidget (signal-based, small payload)
│   ├── LineChartWidget (D3/ng2-charts)
│   ├── BarChartWidget
│   ├── DataTableWidget (virtual scroll, sortable)
│   ├── MapWidget (@defer — heavy library)
│   └── ActivityFeedWidget (SSE real-time)
└── ExportMenu (PDF via html2canvas, CSV via blob)

// Each widget is self-contained:
@Component({ selector: 'widget-kpi' })
export class KpiWidget {
  config = input.required<WidgetConfig>();
  dateRange = input.required<DateRange>();
  // Fetches own data when dateRange changes:
  data = computed(() => /* HTTP call based on dateRange */);
}
O — Optimizations:
  • Parallel data fetching: Each widget independent (one slow widget doesn't block others)
  • Skeleton per widget: Show widget shape while loading
  • @defer heavy chart libraries (only load when widget visible)
  • Memoized computations: Don't recalculate chart data if inputs unchanged
  • Web Worker: Process large datasets (10K+ rows) off main thread
  • Export: Generate in Web Worker → Blob → download link
  • Auto-refresh: SSE for live widgets, polling interval for others (configurable)

  • Comments section with nested replies

// Streaming: HLS (HTTP Live Streaming)
// Video split into 2-10 second segments at multiple qualities
// Player dynamically switches quality based on bandwidth
// m3u8 manifest → segment files (.ts)
O — Optimizations:
  • Preload first segment: Start playback while downloading rest

  • Thumbnail preview: Sprite sheet loaded on first hover over seekbar

Problem 7: Design a Collaborative Document Editor

Advanced

Requirements

  • Rich text editing (bold, italic, headings, lists, tables)
  • Multiple users editing simultaneously (real-time sync)
  • Cursor positions of other users visible
  • Conflict resolution (two users edit same paragraph)
  • Version history (undo, view older versions)
A — Architecture: 
// Conflict resolution approach: OT or CRDT
// OT (Operational Transform): Google Docs approach
//   - Transform operations against each other
//   - Server is source of truth (central)
//   - Complex but battle-tested
//
// CRDT (Conflict-free Replicated Data Types): Figma approach
//   - Data structure that automatically merges
//   - No central server needed (P2P possible)
//   - Growing ecosystem (Yjs, Automerge)

// Recommended: Yjs (CRDT library) + WebSocket

EditorPage
├── Toolbar (formatting buttons, undo/redo)
├── Editor (ProseMirror/TipTap + Yjs binding)
│   ├── ContentEditable (rich text rendering)
│   ├── RemoteCursors (colored cursors of other users)
│   └── SelectionHighlights
├── CollaboratorAvatars (who's viewing)
├── CommentsPane (annotations on text ranges)
└── VersionHistory (timeline of changes)

// Data flow:
// Local edit → Yjs Doc (local CRDT) → WebSocket → Server
// Server → broadcast to other clients → Yjs merges automatically
// No conflicts! CRDT guarantees eventual consistency
O — Optimizations:
  • Yjs: CRDT handles conflict resolution automatically
  • Awareness protocol: Lightweight cursor/selection sharing (separate from doc changes)
  • Throttle syncs: Batch local changes, send every 100ms (not per keystroke)
  • Offline: Edit locally, CRDT merges when reconnected (no conflicts!)
  • Version history: Store snapshots at intervals, not every keystroke
  • Large documents: Split into blocks, only sync visible portion
  • Undo: Local undo stack (don't undo other users' changes)

Critical

│  ├── HomePage                                                  │
│  │   ├── LocationBar (geolocation / address)                  │
│  │   ├── SearchBar (debounced, recent searches)               │
│  │   ├── BannerCarousel                                        │
│  │   ├── CategoryChips (quick filters)                        │
│  │   └── RestaurantGrid (virtual scroll, infinite load)       │
│  ├── RestaurantPage                                            │
│  │   ├── Header (name, rating, delivery time, offers)         │
│  │   ├── MenuCategories (sticky sidebar)                      │
│  │   └── MenuItems (with add/customize)                       │
│  ├── CartPage                                                  │
│  │   ├── ItemList (qty adjust, remove)                        │
│  │   ├── CouponInput                                           │
│  │   └── OrderSummary + PlaceOrder                             │
│  └── OrderTrackingPage                                         │
│      ├── StatusTimeline (SSE updates)                          │
│      ├── MapView (Leaflet + driver marker via WebSocket)       │
│      └── DeliveryPartnerInfo                                   │
│                                                                │
└────────────────────────────────────────────────────────────────┘
D — Data Model: 
// Restaurant list (paginated, filtered):
GET /api/restaurants?lat=12.97&lng=77.59&cuisine=indian&sort=rating&page=1

// Menu (grouped by category):
GET /api/restaurants/456/menu
{ categories: [{ name: "Starters", items: [{ id, name, price, veg, customizations }] }] }

// Cart (client-side signal, persisted to sessionStorage):
{
  restaurantId: "456",
  items: [
    { menuItemId: "i1", name: "Paneer Tikka", price: 249, qty: 2,
      customizations: [{ name: "Extra Cheese", price: 30 }] }
  ],
  coupon: null,
  deliveryFee: 40,
  total: 568
}

// Order tracking:
WebSocket: { type: "location", lat: 12.98, lng: 77.60, bearing: 45 }
SSE: { type: "status_change", status: "out_for_delivery", eta: "8 min" }
O — Optimizations:
  • Location-based caching: Cache restaurant list per location (stale-while-revalidate)
  • Image CDN: Responsive food images, AVIF with fallback, low-quality placeholder
  • Menu scroll spy: Category sidebar highlights current visible section
  • Cart persistence: sessionStorage (don't lose cart on refresh)
  • Map optimization: @defer map component (heavy), throttle marker updates to 1fps
  • Service Worker: Cache restaurant pages (offline browsing of previously viewed menus)
  • Payment retry: Idempotency key prevents double-charging on network retry
  • Multi-restaurant: Warn user if adding from different restaurant (clear or keep both?)

Interview Tips & Common Mistakes

Critical
DO
  • Ask clarifying questions before designing (shows maturity)
  • Think out loud — interviewer wants to hear your thought process
  • Draw diagrams — even rough boxes and arrows help
  • Discuss trade-offs — "I chose X over Y because..."
  • Mention real tools — "I'd use CDK virtual scroll" not "I'd optimize the list"
  • Cover non-functional requirements — accessibility, error handling, offline
  • Prioritize — "For MVP, I'd start with... then add..."
DON'T
  • Jump into implementation without understanding requirements
  • Over-engineer — don't add microservices for a todo app
  • Ignore scale — always ask "how many users?"
  • Forget error states — what happens when API fails? Network drops?
  • Skip accessibility — always mention keyboard nav, screen readers
  • Say "React" when interviewing for Angular role (know your framework!)
  • Design backend in a frontend interview — stay frontend-focused
