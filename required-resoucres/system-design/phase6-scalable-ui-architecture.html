1. Design Systems

Critical

Theory: What is a Design System?

A Design System is a collection of reusable components, design tokens, guidelines, and patterns that ensure visual/behavioral consistency across an entire product suite.

2. Component API Design

// ═══ PRINCIPLES OF GOOD COMPONENT APIs ═══

// 1. SINGLE RESPONSIBILITY: One component = one job
// BAD: <user-profile-card-with-edit-modal />
// GOOD: <user-card /> + <edit-profile-modal />

// 2. CLEAR INPUTS/OUTPUTS:
@Component({ selector: 'ui-select' })
export class SelectComponent<T> {
  // Inputs: what parent provides
  options = input.required<SelectOption<T>[]>();
  value = input<T | null>(null);
  placeholder = input('Select...');
  disabled = input(false);
  searchable = input(false);
  multiple = input(false);
  
  // Outputs: what parent listens to
  valueChange = output<T>();
  searchChange = output<string>();
  opened = output<void>();
  closed = output<void>();
}

// 3. CONTENT PROJECTION for flexibility:
@Component({
  selector: 'ui-card',
  template: `
    <div class="card">
      <div class="card-header">
        <ng-content select="[card-title]" />
        <ng-content select="[card-actions]" />
      </div>
      <div class="card-body">
        <ng-content />
      </div>
      <div class="card-footer">
        <ng-content select="[card-footer]" />
      </div>
    </div>
  `
})
export class CardComponent {}

// Usage:
<ui-card>
  <h3 card-title>Order #123</h3>
  <button card-actions>Edit</button>
  <p>Card body content here...</p>
  <span card-footer>Last updated: 5m ago</span>
</ui-card>

// 4. SMART vs DUMB COMPONENTS:
// DUMB (Presentational): Only @Input/@Output, no services, reusable
// SMART (Container): Injects services, manages state, orchestrates

// DUMB:
@Component({ selector: 'product-card' })
export class ProductCardComponent {
  product = input.required<Product>();
  addToCart = output<string>();  // Emits product ID
}

// SMART:
@Component({ template: `
  @for (p of products(); track p.id) {
    <product-card [product]="p" (addToCart)="onAddToCart($event)" />
  }
`})
export class ProductListComponent {
  private store = inject(ProductStore);
  products = this.store.filteredProducts;
  onAddToCart(id: string) { this.store.addToCart(id); }
}

// ═══ ANGULAR THEME SERVICE ═══
@Injectable({ providedIn: 'root' })
export class ThemeService {
  private theme = signal<'light' | 'dark'>(
    (localStorage.getItem('theme') as 'light' | 'dark') || 'light'
  );
  
  readonly currentTheme = this.theme.asReadonly();
  
  constructor() {
    // Apply on init:
    effect(() => {
      document.documentElement.setAttribute('data-theme', this.theme());
      localStorage.setItem('theme', this.theme());
    });
    
    // Respect system preference:
    const prefersDark = window.matchMedia('(prefers-color-scheme: dark)');
    if (!localStorage.getItem('theme') && prefersDark.matches) {
      this.theme.set('dark');
    }
  }
  
  toggle() { this.theme.update(t => t === 'light' ? 'dark' : 'light'); }
}

// ═══ CSS ARCHITECTURE APPROACHES ═══
// 1. BEM (Block-Element-Modifier):
.card {}             // Block
.card__title {}      // Element
.card--featured {}   // Modifier

// 2. Angular ViewEncapsulation (default: Emulated):
@Component({
  encapsulation: ViewEncapsulation.Emulated  // Scoped styles (default)
  // Emulated: Angular adds _ngcontent attributes for scoping
  // None: Global styles (use sparingly — resets, utilities)
  // ShadowDom: True shadow DOM (strictest isolation)
})

// 3. CSS Layers (Modern — ordering specificity):
@layer base, components, utilities;
@layer base { body { margin: 0; } }
@layer components { .btn { padding: 8px 16px; } }
@layer utilities { .mt-4 { margin-top: 16px; } }
// Utilities always win (last layer), regardless of selector specificity!

4. Responsive Design at Scale

Intermediate 
// ═══ MODERN RESPONSIVE TECHNIQUES ═══

// 1. CONTAINER QUERIES (Component-level responsiveness):
// Respond to PARENT container size, not viewport!
.card-container {
  container-type: inline-size;
  container-name: card;
}

@container card (min-width: 400px) {
  .card { display: grid; grid-template-columns: 200px 1fr; }
}
@container card (max-width: 399px) {
  .card { display: block; }
}
// Same component adapts based on WHERE it's placed, not screen size!

// 2. FLUID TYPOGRAPHY (no breakpoints needed):
h1 { font-size: clamp(1.5rem, 4vw, 3rem); }
// Minimum: 1.5rem, Scales: 4vw, Maximum: 3rem

// 3. RESPONSIVE GRID (auto-fit):
.grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: 24px;
}
// Automatically adjusts columns based on available space!

// 4. LOGICAL PROPERTIES (RTL support built-in):
.element {
  margin-inline-start: 16px;  // margin-left in LTR, margin-right in RTL
  padding-block: 8px;         // padding-top + padding-bottom
  border-inline-end: 1px solid var(--border);
}

// ═══ BREAKPOINT SERVICE (Angular) ═══
import { BreakpointObserver, Breakpoints } from '@angular/cdk/layout';

@Injectable({ providedIn: 'root' })
export class LayoutService {
  private breakpoints = inject(BreakpointObserver);
  
  isMobile$ = this.breakpoints.observe([Breakpoints.Handset])
    .pipe(map(result => result.matches));
  
  isTablet$ = this.breakpoints.observe([Breakpoints.Tablet])
    .pipe(map(result => result.matches));
    
  isDesktop$ = this.breakpoints.observe([Breakpoints.Web])
    .pipe(map(result => result.matches));
  
  // Custom breakpoints:
  columns$ = this.breakpoints.observe([
    '(min-width: 1200px)',
    '(min-width: 768px)',
  ]).pipe(
    map(result => {
      if (result.breakpoints['(min-width: 1200px)']) return 3;
      if (result.breakpoints['(min-width: 768px)']) return 2;
      return 1;
    })
  );
}

// ═══ KEY ACCESSIBILITY PATTERNS ═══

// 1. SEMANTIC HTML (First line of defense):
// BAD:
<div class="button" onclick="submit()">Submit</div>
// GOOD:
<button type="submit">Submit</button>
// Button gives you: keyboard (Enter/Space), focus, role, disabled state FREE!

// 2. ARIA ATTRIBUTES (When semantic HTML isn't enough):
// Live regions (dynamic updates announced by screen reader):
<div aria-live="polite" aria-atomic="true">
  {{ statusMessage }}  <!-- Screen reader announces changes -->
</div>

// Custom components:
<div role="tablist">

    Tab 1
  </button>
</div>
<div role="tabpanel" id="panel-0" [attr.aria-labelledby]="'tab-0'">
  Content for Tab 1
</div>

// 3. FOCUS MANAGEMENT:
// After modal opens → focus first focusable element
// After modal closes → return focus to trigger
// Skip links:
<a href="#main-content" class="skip-link">Skip to main content</a>

// Angular CDK Focus Trap (for modals/dialogs):
import { A11yModule } from '@angular/cdk/a11y';

<div cdkTrapFocus [cdkTrapFocusAutoCapture]="true">
  <!-- Focus is trapped inside this element -->
  <input placeholder="Search..." />

</div>

// 4. KEYBOARD NAVIGATION:
@HostListener('keydown', ['$event'])
onKeyDown(event: KeyboardEvent) {
  switch (event.key) {
    case 'ArrowDown': this.focusNext(); event.preventDefault(); break;
    case 'ArrowUp': this.focusPrev(); event.preventDefault(); break;
    case 'Enter':
    case ' ': this.select(); event.preventDefault(); break;
    case 'Escape': this.close(); break;
  }
}

// WCAG AA: 4.5:1 for normal text, 3:1 for large text
// WCAG AAA: 7:1 for normal text

// ═══ OVERLAY (Modals, Tooltips, Dropdowns) ═══
import { Overlay, OverlayConfig } from '@angular/cdk/overlay';
import { ComponentPortal } from '@angular/cdk/portal';

@Injectable()
export class ModalService {
  constructor(private overlay: Overlay) {}
  
  open<T>(component: Type<T>, config?: Partial<OverlayConfig>) {
    const overlayRef = this.overlay.create({
      hasBackdrop: true,
      positionStrategy: this.overlay.position()
        .global().centerHorizontally().centerVertically(),
      ...config
    });
    
    const portal = new ComponentPortal(component);
    const componentRef = overlayRef.attach(portal);
    
    // Close on backdrop click:
    overlayRef.backdropClick().subscribe(() => overlayRef.dispose());
    
    return { overlayRef, componentRef };
  }
}

8. Web Components & Shadow DOM

Advanced

Theory: What are Web Components?

Web Components are browser-native APIs for creating reusable, encapsulated custom elements. They work in ANY framework (Angular, React, Vue, vanilla JS) — making them ideal for cross-team shared components.

// ═══ WEB COMPONENTS = 3 Specifications ═══
//
// 1. CUSTOM ELEMENTS — Define your own HTML tags
// 2. SHADOW DOM — Encapsulated styles + DOM (can't leak in or out)
// 3. HTML TEMPLATES — <template> + <slot> for composability
//
// ═══ Creating a Custom Element ═══
class MyButton extends HTMLElement {
  constructor() {
    super();
    // Attach Shadow DOM (encapsulated!)
    const shadow = this.attachShadow({ mode: 'open' });
    
    shadow.innerHTML = `
      <style>
        /* These styles CANNOT leak outside this component */
        /* External styles CANNOT affect this component */
        button {
          background: var(--btn-bg, #0f9d7a);  /* CSS vars CAN penetrate! */
          color: white;
          border: none;
          padding: 8px 16px;
          border-radius: 6px;
          cursor: pointer;
        }
        button:hover { opacity: 0.9; }
      </style>
      <button>
        <slot>Default text</slot>  <!-- Content projection -->
      </button>
    `;
  }

  // Lifecycle callbacks (like Angular's lifecycle hooks):
  connectedCallback() { /* mounted to DOM */ }
  disconnectedCallback() { /* removed from DOM */ }
  attributeChangedCallback(name, old, val) { /* attribute updated */ }
  
  static get observedAttributes() { return ['disabled', 'variant']; }
}

// Register the custom element:
customElements.define('my-button', MyButton);
// Usage: <my-button variant="primary">Click me</my-button>

Shadow DOM: Encapsulation Benefits & Gotchas

// ═══ SHADOW DOM ENCAPSULATION ═══
//
// BENEFITS:
// ✅ Styles don't leak OUT (your component doesn't break page CSS)
// ✅ Styles don't leak IN (page CSS doesn't break your component)
// ✅ DOM is hidden (querySelector from outside can't reach shadow DOM)
// ✅ Perfect for: design system widgets shared across teams/frameworks
//
// GOTCHAS (Interview gold!):
// ❌ Global styles DON'T penetrate Shadow DOM
//    → font-family from body won't apply inside shadow!
//    → Solution: Use CSS Custom Properties (they DO inherit into shadow)
//
// ❌ Form participation is broken
//    → <input> inside shadow DOM doesn't participate in parent <form>
//    → Solution: ElementInternals API (modern) or event forwarding
//
// ❌ Accessibility can break
//    → aria-labelledby can't reference elements across shadow boundary
//    → Solution: Use aria-label (string) or slot elements
//
// ❌ Event retargeting
//    → Events from shadow DOM get retargeted to host element
//    → event.target = <my-button> (not the internal <button>)
//
// ═══ ANGULAR + Shadow DOM ═══
@Component({
  selector: 'app-card',
  encapsulation: ViewEncapsulation.ShadowDom,  // Uses real Shadow DOM!
  template: `
    <div class="card">
      <ng-content />
    </div>
  `,
  styles: [`
    .card { border: 1px solid var(--card-border, #e2e7f0); }
    /* These styles are truly encapsulated */
  `]
})
export class CardComponent {}

// ═══ ANGULAR VIEW ENCAPSULATION MODES ═══
// Emulated (DEFAULT): Adds _ngcontent attributes for scoping (not real shadow)
// ShadowDom: Uses native Shadow DOM (real encapsulation)
// None: No encapsulation (styles are global!)
//
// When to use ShadowDom: Shared library components used across apps
// When to use Emulated: Regular app components (simpler debugging)

Angular Elements (Web Components from Angular)

// ═══ ANGULAR ELEMENTS — Ship Angular components as Web Components ═══
// Use case: Build in Angular, consume in React/Vue/vanilla HTML

// 1. Create component normally:
@Component({
  selector: 'app-date-picker',
  standalone: true,
  template: `<input type="date" (change)="onChange($event)">`,
})
export class DatePickerComponent {
  @Input() value: string = '';
  @Output() dateChange = new EventEmitter<string>();
  onChange(e: Event) {
    this.dateChange.emit((e.target as HTMLInputElement).value);
  }
}

// 2. Register as custom element:
import { createCustomElement } from '@angular/elements';

@NgModule({ ... })
export class AppModule {
  constructor(private injector: Injector) {
    const datePickerEl = createCustomElement(DatePickerComponent, { injector });
    customElements.define('company-date-picker', datePickerEl);
  }
  ngDoBootstrap() {} // No bootstrap component
}

// 3. Use ANYWHERE (even non-Angular apps):
// <company-date-picker value="2024-01-01"></company-date-picker>
// <script src="date-picker-element.js"></script>

// ═══ WHEN TO USE ANGULAR ELEMENTS ═══
// ✅ Micro-frontends: embed Angular widget in React/Vue host
// ✅ CMS: provide interactive widgets for non-technical content editors
// ✅ Legacy: gradually migrate jQuery app → Angular components
// ❌ Full Angular apps: just use Angular normally (overhead not worth it)
Interview Answer Pattern "Web Components are great for cross-framework shared components (design system used by Angular + React teams). However, for within-framework use, native Angular components are better because: they have full DI access, better change detection integration, and simpler testing. Shadow DOM's style encapsulation is powerful but breaks design token inheritance unless you use CSS Custom Properties for everything."

9. Intersection Observer & Resize Observer

Critical

Intersection Observer — Visibility Detection

Fires a callback when an element enters/exits the viewport (or any ancestor). Replaced scroll event listeners for lazy loading, infinite scroll, and analytics.

// ═══ INTERSECTION OBSERVER — Core API ═══
const observer = new IntersectionObserver(
  (entries) => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        console.log('Element visible!', entry.target);
        console.log('Visible ratio:', entry.intersectionRatio); // 0.0 to 1.0
      }
    });
  },
  {
    root: null,            // Viewport (null = browser viewport)
    rootMargin: '100px',   // Trigger 100px BEFORE element enters viewport
    threshold: [0, 0.25, 0.5, 0.75, 1.0]  // Fire at these visibility %
  }
);

observer.observe(document.querySelector('.lazy-section'));
// Don't forget: observer.unobserve(element) or observer.disconnect()

// ═══ ANGULAR DIRECTIVE: Lazy Load on Viewport ═══
@Directive({ selector: '[appLazyLoad]', standalone: true })
export class LazyLoadDirective implements OnInit, OnDestroy {
  private el = inject(ElementRef);
  private observer!: IntersectionObserver;
  
  appLazyLoad = output<void>(); // Emits when element enters viewport

  ngOnInit() {
    this.observer = new IntersectionObserver(
      ([entry]) => {
        if (entry.isIntersecting) {
          this.appLazyLoad.emit();
          this.observer.unobserve(this.el.nativeElement); // Only fire once
        }
      },
      { rootMargin: '200px' } // Preload 200px before visible
    );
    this.observer.observe(this.el.nativeElement);
  }

  ngOnDestroy() { this.observer.disconnect(); }
}

// Usage:
// <div (appLazyLoad)="loadComments()">
//   @if (commentsLoaded) { <app-comments /> }
// </div>

// ═══ USE CASES ═══
// • Lazy loading images (loading="lazy" uses IO internally!)
// • Infinite scroll (observe sentinel element at bottom)
// • Analytics: track which sections users actually see
// • Pause videos when not visible (save bandwidth)
// • Animate-on-scroll (add CSS class when visible)
// • @defer (on viewport) — Angular uses IO internally!

// ═══ GOTCHAS ═══
// • rootMargin only works with root: null or scrollable ancestor
// • threshold: 1.0 won't fire if element is larger than viewport
// • Callback fires ASYNCHRONOUSLY (not immediately on scroll)
// • Multiple thresholds = callback fires at EACH threshold crossing
// • Observe many elements with ONE observer (not one observer per element!)

// ═══ RESIZE OBSERVER — Detect element size changes ═══
// Unlike window.resize which only fires for viewport resize,
// ResizeObserver fires when ANY element's size changes
// (e.g., sidebar collapse, content load, container query alternative)

const resizeObserver = new ResizeObserver((entries) => {
  entries.forEach(entry => {
    const { width, height } = entry.contentRect;
    console.log(`Element resized: ${width}x${height}`);
    
    // entry.borderBoxSize — includes padding + border
    // entry.contentBoxSize — content area only
    // entry.devicePixelContentBoxSize — in device pixels (canvas!)
  });
});

resizeObserver.observe(document.querySelector('.container'));

// ═══ ANGULAR: Responsive Component with ResizeObserver ═══
@Directive({ selector: '[appElementSize]', standalone: true })
export class ElementSizeDirective implements OnInit, OnDestroy {
  private el = inject(ElementRef);
  private observer!: ResizeObserver;
  
  elementWidth = output<number>();
  sizeClass = output<'sm' | 'md' | 'lg'>();

  ngOnInit() {
    this.observer = new ResizeObserver(([entry]) => {
      const width = entry.contentRect.width;
      this.elementWidth.emit(width);
      
      // Component-level responsive (like container queries!)
      if (width < 400) this.sizeClass.emit('sm');
      else if (width < 800) this.sizeClass.emit('md');
      else this.sizeClass.emit('lg');
    });
    this.observer.observe(this.el.nativeElement);
  }

  ngOnDestroy() { this.observer.disconnect(); }
}

// Usage: switch component layout based on its OWN width (not viewport):
// <div appElementSize (sizeClass)="layout = $event">
//   @switch (layout) {
//     @case ('sm') { <card-compact /> }
//     @case ('md') { <card-medium /> }
//     @case ('lg') { <card-full /> }
//   }
// </div>

// ═══ USE CASES ═══
// • Canvas resize (recalculate drawing dimensions)
// • Chart libraries (redraw chart on container resize)
// • Responsive components (adapt layout to container, not viewport)
// • Detect sidebar collapse/expand
// • Virtual scroll: recalculate visible items on container resize
// • Auto-resize textarea to content

// ═══ PERFORMANCE NOTE ═══
// ResizeObserver callbacks are called AFTER layout but BEFORE paint
// This means reads inside the callback are "free" (no forced layout)
// But WRITES will trigger another layout pass — batch them with rAF!
resizeObserver = new ResizeObserver(entries => {
  // ✅ Read entry.contentRect (free — already calculated)
  const width = entries[0].contentRect.width;
  
  // ✅ Batch DOM writes in rAF:
  requestAnimationFrame(() => {
    element.style.fontSize = width > 600 ? '16px' : '14px';
  });
});
Observer vs Polling Never use scroll/resize event listeners + getBoundingClientRect() polling. Observers are: (1) More performant (browser optimizes internally), (2) Don't cause layout thrashing, (3) Battery-friendly (no constant JS execution), (4) Automatically handle dynamic DOM changes.

Q: How would you implement "infinite scroll" in Angular? (All companies)

Answer: Place a sentinel <div> at the bottom of the list. Use IntersectionObserver with rootMargin: '200px' to detect when it's about to enter viewport. When triggered, call loadMore() which fetches next page (cursor-based pagination) and appends to the signal array. Use CDK VirtualScroll for rendering performance if the list grows to 1000+ items. Cleanup: unobserve on destroy. Alternative: CDK ScrollDispatcher provides scroll events, but IO is more performant for this pattern.

// ═══ ERROR BOUNDARY (Global Error Handler) ═══
@Injectable()
export class GlobalErrorHandler implements ErrorHandler {
  private errorService = inject(ErrorTrackingService);
  private snackbar = inject(MatSnackBar);
  
  handleError(error: any) {
    // 1. Log to error tracking (Sentry):
    this.errorService.capture(error);
    
    // 2. Show user-friendly message:
    if (error instanceof HttpErrorResponse) {
      this.handleHttpError(error);
    } else {
      this.snackbar.open('Something went wrong. Please try again.', 'Dismiss');
    }
    
    // 3. Don't re-throw (prevents white screen):
    console.error(error);
  }
  
  private handleHttpError(error: HttpErrorResponse) {
    const messages: Record<number, string> = {
      0: 'No internet connection',
      403: 'You don\'t have permission to do that',
      404: 'The requested resource was not found',
      429: 'Too many requests. Please wait.',
      500: 'Server error. We\'re working on it.',
      503: 'Service temporarily unavailable'
    };
    this.snackbar.open(messages[error.status] || 'Request failed', 'Dismiss');
  }
}

11. Interview Questions (Previously Asked)

Q1: How would you design a component library/design system for a large org? (All senior interviews)

Answer: Architecture: (1) Monorepo (Nx) with shared UI library. (2) Design tokens (JSON → CSS vars) as single source of truth. (3) Atomic Design: atoms → molecules → organisms → templates. (4) Storybook for documentation + visual testing. (5) Chromatic for visual regression CI. (6) Semantic versioning with changelog. (7) Tree-shakable (standalone components). (8) Accessibility baked in (all components meet WCAG AA). (9) Theme-able via CSS custom properties. (10) Published to private npm registry. Governance: Design system team owns library, product teams contribute via PR.

Q2: How do you ensure accessibility in a large Angular application? (Amazon, Microsoft, Google)

Answer: Multi-layer approach: (1) Semantic HTML first (buttons, headings, landmarks). (2) Angular CDK a11y utilities (FocusTrap, LiveAnnouncer, ListKeyManager). (3) ARIA attributes for custom widgets. (4) Keyboard navigation for all interactive elements. (5) Focus management (modal trap, return on close). (6) Color contrast (4.5:1 minimum). (7) Testing: axe-core in unit tests, screen reader manual testing (VoiceOver/NVDA). (8) CI: axe-linter, pa11y-ci. (9) Skip links. (10) Reduced motion: prefers-reduced-motion media query.

Q3: Explain container queries vs media queries. When to use each? (Google, Meta)

Answer: Media queries respond to VIEWPORT size — good for page layout (sidebar collapses on mobile). Container queries respond to PARENT container size — good for reusable components (card shows horizontal/vertical layout based on where it's placed). Use media queries for: overall page layout, hiding/showing sections. Use container queries for: component-level responsiveness, cards that work in sidebar AND main content, widgets in flexible grid. Container queries make components truly portable across different contexts.

Q4: How would you implement dark mode in a production Angular app? (All companies)

Answer: (1) Define all colors as CSS custom properties (design tokens). (2) [data-theme="dark"] selector overrides variables. (3) Angular service: signal-based, reads system preference (prefers-color-scheme), allows user override, persists to localStorage. (4) Effect applies data-theme attribute to document. (5) Images: provide dark variants or use CSS filter. (6) Third-party widgets: CSS mix-blend-mode or filter invert. (7) Transitions: use color-scheme CSS property for native scrollbar/form styling. (8) Test: verify contrast ratios in both themes.

Q5: How do you handle internationalization for a global app supporting 20+ languages? (Amazon, Microsoft)

Answer: Strategy: (1) Angular built-in i18n for compile-time (best performance, separate builds per locale). OR Transloco for runtime switching (better DX, larger bundle). (2) ICU message format for plurals/gender. (3) Date/number formatting: Angular pipes with locale (DatePipe, DecimalPipe). (4) RTL: CSS logical properties + [dir] attribute. (5) Translation workflow: extract → send to translators → import. (6) Lazy-load translations per route. (7) Content expansion: design for 40% text expansion (German/Finnish). (8) Testing: pseudo-localization to catch hardcoded strings.
