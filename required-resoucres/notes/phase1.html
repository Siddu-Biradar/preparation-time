01 Variables, Types & Functions

The atoms of any Go program. Coming from TypeScript, most surprises come from zero values and strict typing.

Why does this exist (and why like this)?

Go was designed at Google to fix three real problems:

  • Slow compile times in C++ → Go's grammar is small and parses in one pass.
  • Implicit type conversions in C cause bugs → Go forbids them entirely (you must explicitly cast).
  • Uninitialized memory causes nondeterministic bugs → every variable in Go has a zero value (no undefined, no null for value types).

Theory

1. Static typing, but inferred. Like TypeScript, Go infers types when it can. Unlike TS, types can never change at runtime.

2. Zero values. Every type has a default value when declared without an initializer:

TypeZero valueTS equivalent intuition
int, int64, float640 / 0.0like 0 (never NaN by default)
string"" (empty string)like "" (never undefined)
boolfalsesame
pointers, slices, maps, channels, interfaces, funcsnillike null (only for reference-y types)
structseach field's zero valuelike {} with each prop pre-initialized

3. Numeric types are explicit and many. No single number type. You pick the size.

  • int, int8, int16, int32, int64 (signed)
  • uint, uint8 (=byte), uint16, uint32, uint64
  • float32, float64 (default for decimals)
  • rune = int32 = a single Unicode code point

Syntax — 4 ways to declare

// 1. var with type, no value -> zero value
var name string           // ""
var age int              // 0

// 2. var with type and value
var city string = "Bengaluru"

// 3. var with inferred type
var country = "India"      // inferred string

// 4. short declaration (most common, only inside functions)
salary := 3000000            // inferred int
ratio  := 3.14               // inferred float64

Functions — full anatomy

// Multiple return values are idiomatic in Go (TS would use a tuple/object).
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("division by zero")
    }
    return a / b, nil
}

// Named return values (acts like pre-declared variables, optional)
func stats(nums []int) (sum, max int) {
    for _, n := range nums {
        sum += n
        if n > max { max = n }
    }
    return // "naked" return — uses sum, max as-is
}

// Variadic — accepts any number of args of same type
func total(nums ...int) int {
    s := 0
    for _, n := range nums { s += n }
    return s
}
total(1, 2, 3)               // 6
nums := []int{1,2,3}
total(nums...)               // "spread" syntax

// First-class — functions are values, can be passed/returned (closures!)
func multiplier(factor int) func(int) int {
    return func(n int) int { return n * factor }
}
double := multiplier(2)
double(5)                    // 10

When & Why use what?

  • Use := inside functions whenever you don't need a specific size. It's the idiomatic default.
  • Use var at package level (:= is illegal there) or when you want a zero-valued variable to assign later.
  • Pick int/float64 unless you have a real reason (file format, network protocol, big arithmetic). Don't prematurely optimize to int8.
  • Multiple returns are how Go does errors. Always return (value, error).
  • Named returns — useful only for short functions or when the return values need explanation. Avoid for long functions, naked returns hide bugs.

Gotchas

1. No implicit conversions. var x int = 5; var y int64 = x ❌ compile error. You must write y := int64(x). Same with int → float64.
2. Unused variables = compile error. Go forbids unused locals. Use _ (blank identifier) to discard: 
x, _ := divide(10, 2)  // ignore the error (BAD habit but legal)
3. := with multiple vars is "at least one new". x, err := foo() works even if x exists, as long as one variable on the left is new.
4. Shadowing. Inside a block, x := ... creates a NEW x, hiding the outer one. Easy to do accidentally with err in if blocks. Use linters (golangci-lint) to catch.
5. Constants are typed or untyped. Untyped consts (const Pi = 3.14) auto-fit any compatible numeric type at use site. Typed consts (const Pi float64 = 3.14) lock you to that type.

Interview Q&A

Q: What's the zero value of a struct?

Each field's individual zero value. So type User struct { Name string; Age int } → User{Name: "", Age: 0}. No constructors run automatically — Go has no constructors.

Q: Why does Go forbid unused variables?

Unused vars usually indicate a bug or stale code. Forcing removal keeps codebases clean. (Unused imports also fail to compile.)

Q: Difference between := and =?

:= declares AND assigns (only in functions). = assigns to an already-declared variable. Mix them up and you'll either shadow a variable or get a compile error.

Q: Go has int AND int32. Why?

int is platform-sized (32 bits on 32-bit systems, 64 on 64-bit). int32 is always exactly 32 bits. Use int32 when you need a fixed size (file format, RPC, binary protocols). Otherwise use int.

02 Control Flow — if / for / switch

Go has only ONE loop keyword (for) and a much more powerful switch than TS.

Why does this exist?

Go's designers stripped redundancy. Instead of for / while / do-while, there is just for in three forms. Instead of cascading if / else if, idiomatic Go uses switch for cleanliness.

Theory + Syntax

if — with optional init statement

// Init statement runs BEFORE the condition. Variable scoped to the if/else.
if err := save(); err != nil {
    log.Println(err)
    return
}
// err does NOT exist here.

// Plain if
if x > 10 {
    // ...
} else if x > 5 {
    // ...
} else {
    // ...
}
Why init? Keeps the variable's scope tight (only valid where it makes sense). This is the most common Go pattern for error handling. Memorize it.

for — the only loop

// 1. Classic C-style
for i := 0; i < 10; i++ { ... }

// 2. while-style
for x < 100 { x *= 2 }

// 3. Infinite loop (use break/return to exit)
for { ... }

// 4. range — over slice/array/map/channel/string
for i, v := range nums { ... }     // index, value
for _, v := range nums { ... }     // just value
for i := range nums { ... }        // just index
for k, v := range myMap { ... }    // map iteration (UNORDERED!)
for v := range myChannel { ... }   // receive until channel closes
for i, r := range "héllo" { ... }  // i = byte index, r = rune (Unicode!)

// 5. Go 1.22+: range over int (counts 0..n-1)
for i := range 10 { fmt.Println(i) }   // 0..9

switch — the underrated workhorse

// No fallthrough by default (opposite of C/JS!)
switch day {
case "Sat", "Sun":
    fmt.Println("weekend")
case "Mon":
    fmt.Println("meh")
default:
    fmt.Println("weekday")
}

// Switch on conditions (replaces if/else if chains)
switch {
case score >= 90: grade = "A"
case score >= 75: grade = "B"
default:           grade = "C"
}

// Type switch — runtime type checking on interfaces
switch v := i.(type) {
case int:    fmt.Println("int:", v)
case string: fmt.Println("string:", v)
default:     fmt.Println("unknown")
}

When & Why

  • switch over if/else if when you have 3+ branches. Cleaner, faster, more idiomatic.
  • Use range for iteration over collections — almost never write for i := 0; i < len(s); i++ unless you specifically need control over the index.
  • Init in if for any error/result-checking pattern.

Gotchas

1. Map iteration order is random. Go intentionally randomizes it so you don't accidentally rely on it. If order matters, sort the keys first. 
keys := make([]string, 0, len(m))
for k := range m { keys = append(keys, k) }
sort.Strings(keys)
for _, k := range keys { ... }
2. Loop variable capture (FIXED in Go 1.22+). Pre-1.22: 
// Pre-Go 1.22 — broken
for _, v := range items {
    go func() { fmt.Println(v) }()  // All print last item!
}
// Pre-1.22 fix: shadow the var
for _, v := range items {
    v := v   // new variable per iteration
    go func() { fmt.Println(v) }()
}
Go 1.22+ does this automatically. Always check what Go version your project uses.
3. switch doesn't fall through by default. Unlike C/Java/JS, you don't need break. To explicitly fall through use the fallthrough keyword (rare).
4. Range copies the value. for _, item := range items { item.Name = "x" } mutates the COPY, not the original. Use the index: items[i].Name = "x".

Interview Q&A

Q: Why no while in Go?

Simplicity. for cond { } is identical to while. Fewer keywords, same expressivity.

Q: How do you loop over Unicode characters?

for i, r := range str — i is the byte index, r is the rune (code point). If you index str[i] you get a single byte (could be mid-character for multi-byte chars). For correct Unicode iteration, always use range.

03 defer, panic & recover

Go's answer to finally, exceptions, and resource cleanup. Different model from JS/Java.

Why does this exist?

Go has no exceptions. Errors are values, returned explicitly. But you still need:

  • Cleanup guaranteed even when functions return early or fail → defer
  • Crash mechanism for unrecoverable bugs (nil pointer, out of bounds) → panic
  • Last-resort recovery at program boundaries (HTTP server, goroutine roots) → recover

Theory

defer schedules a function call to run when the surrounding function returns — whether normally or via panic.

panic stops normal flow, runs deferred funcs upward, and crashes the program if not recovered.

recover (only inside a deferred func) catches a panic and returns control to the caller.

  ┌────────────────────────────────────────────────┐
  │ func doWork() {                                │
  │     defer cleanup()      ← scheduled (LIFO)    │
  │     defer logExit()      ← scheduled           │
  │                                                │
  │     panic("boom")        ─────┐                │
  │                                ▼               │
  │     // unreachable        unwinds:             │
  │ }                          1. logExit() runs   │
  │                            2. cleanup() runs   │
  │                            3. panic propagates │
  └────────────────────────────────────────────────┘

Syntax + Code

// 1. defer for cleanup — runs when function returns (LIFO order)
func readFile(path string) ([]byte, error) {
    f, err := os.Open(path)
    if err != nil { return nil, err }
    defer f.Close()      // guaranteed to run before this function returns
    return io.ReadAll(f)
}

// 2. defers run in REVERSE order (stack)
func demo() {
    defer fmt.Println("first deferred")
    defer fmt.Println("second deferred")
    fmt.Println("normal")
}
// Output: normal / second deferred / first deferred

// 3. panic — abort with a message
func mustHaveDB() {
    if db == nil {
        panic("db connection is nil")
    }
}

// 4. recover — catch a panic in a deferred func
func safeRun(work func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r)
        }
    }()
    work()
    return nil
}

When & Why

Use caseToolWhy
Close files, DB connections, HTTP bodiesdeferGuaranteed cleanup even on early return
Unlock a mutexdefer mu.Unlock()Prevent deadlocks on panic
Log function entry/exitdeferTracing/debugging
Truly unrecoverable statepanice.g., bug detected at startup
Top of HTTP handler/goroutinerecoverDon't let one request crash the whole server
Rule of thumb: Use defer liberally. Use panic rarely (only for "this should never happen" bugs). Use recover only at process boundaries (servers, workers).

Gotchas

1. Arguments to deferred functions evaluate IMMEDIATELY. 
x := 10
defer fmt.Println(x)   // captures 10 NOW
x = 20
// Prints: 10

// To capture latest value, wrap in closure:
defer func() { fmt.Println(x) }()  // prints 20
2. defer in a loop = memory hog. Each iteration's defer queues up. Don't defer f.Close() inside a 1M-iteration loop. Wrap in a function: 
for _, name := range files {
    func() {
        f, _ := os.Open(name)
        defer f.Close()
        // process
    }()
}
3. recover only works inside a deferred function called from the panicking goroutine. recover() elsewhere returns nil. And it doesn't catch panics in other goroutines — each goroutine needs its own recover.
4. Don't use panic/recover as exception control flow. It's not try/catch. The convention is errors-as-values. recover is for crash safety, not branching logic.

Interview Q&A

Q: Order of defers?

LIFO — last deferred runs first. Stack semantics. Useful when deferred operations have dependencies (e.g., open DB → start tx → defer rollback → defer close).

Q: Will defer run if my program crashes via panic?

Yes. Defers in the panicking goroutine all run (in LIFO order) before the program exits. This is why defer mu.Unlock() is critical for safe locking.

Q: Why doesn't Go have try/catch?

Design choice. Exceptions cause invisible control flow and "exception specifications" (Java) become unmaintainable. Go forces you to handle errors at every step, making code more explicit (and verbose, yes).

04 Arrays, Slices & Maps (the BIG gotcha section)

90% of "WTF" Go moments for new devs come from slice internals. Master this, save weeks of pain.

Why both arrays AND slices?

Arrays have a fixed size baked into the type. [3]int and [4]int are different types. They live on the stack and copy on assignment.

Slices are growable views over an underlying array. They're what you'll use 99% of the time.

Slice internals (this is the key)

A slice is a 3-word struct under the hood:

  ┌──────────────────────────┐
  │ Slice header              │
  │  ┌──────────┐             │
  │  │ ptr      │ ──┐         │
  │  │ len  = 3 │   │         │
  │  │ cap  = 5 │   │         │
  │  └──────────┘   │         │
  └──────────────────┼────────┘
                     ▼
                Underlying array (in heap)
                ┌──┬──┬──┬──┬──┐
                │a │b │c │  │  │
                └──┴──┴──┴──┴──┘
                 0  1  2  3  4
                len=3 ──┘  cap=5 ─┘
  • ptr — pointer to the start of data
  • len — number of elements visible
  • cap — capacity before reallocation

When you append beyond cap, Go allocates a NEW bigger array, copies, and returns a new slice. Until then, multiple slices can share the same underlying array — this is the source of every gotcha.

Syntax + Code

// Array — fixed size
var a [3]int                   // [0 0 0]
b := [3]int{1, 2, 3}
c := [...]int{1, 2, 3}        // compiler counts → [3]int

// Slice — growable
var s []int                    // nil slice (len=0, cap=0, ptr=nil)
t := []int{1, 2, 3}              // literal
u := make([]int, 5)             // len=5, cap=5, all zeros
v := make([]int, 3, 10)           // len=3, cap=10 (perf hint)

// Append
s = append(s, 1, 2, 3)            // always reassign! append may return new slice
s = append(s, t...)               // spread another slice

// Slicing s[low:high:cap]
nums := []int{10,20,30,40,50}
sub := nums[1:4]                // [20 30 40] — shares memory!
sub2 := nums[1:4:4]              // 3-index form caps it (safer)

// Maps
m := make(map[string]int)
m["sid"] = 42
val, ok := m["foo"]               // idiomatic: value + exists?
delete(m, "sid")
len(m)                            // number of entries

When to use what

UseFor
Array [N]TRare. Fixed-size buffers, hashing, when size is part of the type contract (e.g., [16]byte for a UUID).
Slice []TDefault. All "list" use cases.
Map map[K]VLookup by key. Like JS object / TS Record. Random-access, no order.
make([]T, 0, N)When you know roughly how many items you'll append. Avoids reallocation. Big perf win.

Gotchas — READ TWICE

1. append MAY or MAY NOT mutate. 
a := []int{1,2,3}
b := append(a, 4)   // a still [1,2,3], b is [1,2,3,4] (probably new array)
// But if a had spare cap, append would mutate a's array!
// → ALWAYS reassign: x = append(x, ...)
2. Slicing aliases memory. 
orig := []int{1,2,3,4,5}
sub := orig[1:3]            // [2,3]
sub[0] = 99                 // orig is now [1,99,3,4,5] !
To break the link, copy: cp := append([]int{}, sub...) or cp := slices.Clone(sub).
3. Returning a sub-slice can leak the whole underlying array. If orig has 1M elements and you return orig[:10], the GC can't free the other 999,990 because the slice still references the array. Fix: copy explicitly.
4. Nil map vs empty map. 
var m map[string]int          // nil map
m["x"] = 1                    // PANIC: assignment to entry in nil map

m = make(map[string]int)        // must make first
m["x"] = 1                    // OK
But reading from a nil map is fine — returns zero value. Asymmetric, surprising.
5. Map values aren't addressable. m["k"].field = 1 ❌. You must read, modify, write back: v := m["k"]; v.field = 1; m["k"] = v. Or store pointers: map[string]*Foo.
6. Iterating a map while modifying it. Go allows it but new entries may or may not appear in the iteration. Don't rely on either behavior.
7. Pre-allocate when you know the size. make([]T, 0, 10000) is way faster than appending one by one and growing geometrically. Same for maps: make(map[K]V, expectedSize).

Interview Q&A

Q: Pass a slice by value or pointer?

By value is fine. The slice header (24 bytes) is cheap to copy, and both copies share the same underlying array. You only need *[]T if you need the function to change which array the caller's slice points to (e.g., reassign after a giant append).

Q: How does slice growth work?

Roughly: doubles capacity until ~256, then grows by ~25%. Implementation detail and has changed across Go versions — never depend on exact numbers.

Q: How to deep-copy a slice?

slices.Clone(s) (Go 1.21+) or cp := make([]T, len(s)); copy(cp, s). append([]T{}, s...) also works. For slices of pointers/structs with refs, you must clone each element manually.

Q: Why doesn't Go have a Set type?

Convention: use map[T]struct{} (zero-byte values). Add: set[k] = struct{}{}. Check: _, ok := set[k]. Some libs wrap this.

05 Structs, Methods & Composition

Go has no classes. Structs + methods + embedding = its alternative to OOP. Think: simpler, less ceremony.

Why no classes?

Inheritance is widely considered the worst feature of OOP — fragile base classes, deep hierarchies, "is-a" relationships that break at scale. Go embraces:

  • Composition over inheritance — embed structs to reuse
  • Implicit interfaces — no implements keyword (covered in next section)
  • Plain methods on plain structs — no virtual tables, no this magic

Theory + Syntax

// Struct = plain data record. Like a TS interface/type alias.
type User struct {
    ID        int       // exported (capital first letter)
    Name      string
    email     string    // unexported (lowercase) — private to package
    CreatedAt time.Time
}

// Construct
u1 := User{ID: 1, Name: "Sid"}        // named (preferred)
u2 := User{1, "Sid", "x@y.com", time.Now()}  // positional (fragile)
var u3 User                            // zero-valued

// Methods — functions with a receiver
func (u User) FullName() string {        // VALUE receiver — gets a copy
    return u.Name + " #" + strconv.Itoa(u.ID)
}

func (u *User) SetName(n string) {       // POINTER receiver — can mutate
    u.Name = n
}

// Embedding — the "inheritance" of Go
type Admin struct {
    User                 // no field name = embedded
    Permissions []string
}

a := Admin{User: User{Name: "root"}, Permissions: []string{"*"}}
a.FullName()         // promoted method! Calls User's FullName
a.Name              // promoted field
a.User.Name         // also valid (explicit)

When pointer receiver vs value receiver?

Use POINTER receiver when…Use VALUE receiver when…
Method modifies the receiverMethod only reads
Struct is large (avoid copy)Struct is small (int, small struct)
Struct contains a mutex / sync primitiveType is a basic value (e.g., type ID int)
Consistency: if any method needs *T, use *T for ALL methods of that type
Default rule: Use pointer receivers unless you have a strong reason not to. It's the safer default — avoids accidental copies and keeps method sets consistent.
The Method Set rule (advanced but critical):
  • The method set of type T contains all methods with VALUE receivers func (t T).
  • The method set of type *T contains methods with EITHER value or pointer receivers — pointer's method set is a SUPERSET.
Practical impact: if (*User).Save() exists (pointer receiver), then *User satisfies any interface needing Save, but User does NOT — even though you can call u.Save() on a User value (Go auto-addresses it). The auto-addressing only works for direct variables; for interface satisfaction or for non-addressable values (like map entries), the type itself must satisfy. 
type Saver interface { Save() error }
type User struct{}
func (u *User) Save() error { return nil }

var _ Saver = &User{}     // ✅ *User satisfies Saver
var _ Saver = User{}      // ❌ compile error: User does not satisfy Saver

Composition example (the "OOP replacement")

type Animal struct { Name string }
func (a Animal) Greet() string { return "hi, I'm " + a.Name }

type Dog struct {
    Animal              // embed
    Breed string
}
func (d Dog) Bark() string { return "woof" }

d := Dog{Animal: Animal{Name: "Rex"}, Breed: "Lab"}
d.Greet()        // "hi, I'm Rex"  (Animal's method)
d.Bark()         // "woof"          (Dog's method)

// Override: just declare a method with same name on Dog
func (d Dog) Greet() string { return "woof, I'm " + d.Name }

Gotchas

1. Mixing receivers is confusing. If Save() is on *User and Display() is on User, your method set differs based on whether the variable is User or *User. Pick ONE convention per type.
2. Struct comparison. Structs are ==-comparable only if all their fields are. Slices/maps/funcs in a struct → not comparable. Use reflect.DeepEqual or the cmp package.
3. Embedding is NOT inheritance. No virtual dispatch. The outer type doesn't "is-a" the inner. The inner doesn't know it's embedded.
4. Struct tags are critical for JSON/DB: 
type User struct {
    Name string `json:"name"`
    Pwd  string `json:"-"`      // don't serialize
    Age  int    `json:"age,omitempty"`  // omit if zero
}
Without tags, JSON keys default to the field name (capitalized!).

Interview Q&A

Q: How do I do "private" fields?

Lowercase first letter = unexported (package-private). Uppercase = exported. There's NO file-level or class-level privacy.

Q: Can I have constructors?

No language feature, but the convention is a function named NewX returning *X (or X): func NewUser(name string) *User { ... }.

Q: What's the difference between type Foo struct{...} and type Foo = struct{...}?

type Foo X creates a new distinct type. type Foo = X is a type alias — same type, different name. You'll mostly use the former.

06 Interfaces — the Go way

The single most important Go concept. If you only learn one thing deeply, learn this.

Why are Go interfaces different?

In Java/TS, you say class Foo implements Bar. In Go, there's no implements keyword. A type satisfies an interface automatically if it has the right methods. This is called structural / duck typing at compile time.

This unlocks two superpowers:

  • Decoupling — your library can define an interface, and any user's type can satisfy it without modifying their code.
  • Small interfaces — Go culture loves 1-method interfaces (like io.Reader). They compose perfectly.

Theory + Syntax

// Define
type Greeter interface {
    Greet() string
}

// Two types that satisfy it WITHOUT saying so
type Dog struct{ Name string }
func (d Dog) Greet() string { return "woof, " + d.Name }

type Robot struct{ ID int }
func (r Robot) Greet() string { return fmt.Sprintf("beep #%d", r.ID) }

// Use polymorphically
func SayHi(g Greeter) {
    fmt.Println(g.Greet())
}
SayHi(Dog{"Rex"})       // woof, Rex
SayHi(Robot{42})       // beep #42

Under the hood

An interface value is two words:

  ┌────────────────────┐
  │ Interface value    │
  │  ┌──────────┐      │
  │  │ type     │ ──▶ which concrete type? (Dog / Robot)
  │  │ value    │ ──▶ pointer to actual data
  │  └──────────┘      │
  └────────────────────┘

This is why a nil interface is tricky: an interface is nil only if BOTH type AND value are nil. (See gotchas below.)

When & how to design interfaces

  • Define interfaces at the consumer side, not the producer. The package that uses a dependency declares what it needs. This keeps producers free.
  • Keep them small. The std lib io.Reader has 1 method. io.Writer has 1. They compose into io.ReadWriter, io.ReadCloser, etc.
  • Accept interfaces, return structs — let callers pass any implementation, but give them a concrete type back so they can use all its methods.

Realistic example — repository pattern

// In package "user" (the consumer)
type Repository interface {
    FindByID(ctx context.Context, id int) (*User, error)
    Save(ctx context.Context, u *User) error
}

type Service struct {
    repo Repository
}

func (s *Service) Update(ctx context.Context, id int, name string) error {
    u, err := s.repo.FindByID(ctx, id)
    if err != nil { return err }
    u.Name = name
    return s.repo.Save(ctx, u)
}

// In a different package, "postgres":
type PostgresRepo struct { db *sql.DB }
func (p *PostgresRepo) FindByID(...) ...   // implementation
func (p *PostgresRepo) Save(...) ...

// In tests, an in-memory mock
type mockRepo struct { users map[int]*User }
func (m *mockRepo) FindByID(...) ...
func (m *mockRepo) Save(...) ...
// → testable without DB!

The empty interface and any

interface{} is the empty interface — every type satisfies it (it has no methods). Since Go 1.18 there's an alias any that means the same thing.

It's useful but escapes the type system, so use sparingly. Common in JSON handling and generic-ish APIs (pre-generics).

Type assertion & type switch

var i any = "hello"
s := i.(string)              // PANIC if i isn't a string
s, ok := i.(string)          // safe: ok=true if assertion succeeds

switch v := i.(type) {       // type switch
case string: /* v is string */
case int:    /* v is int */
default: /* v is interface{} */
}

Gotchas

1. The "typed nil" trap. 
type MyError struct{ Msg string }
func (e *MyError) Error() string { return e.Msg }

func do() error {
    var e *MyError      // nil pointer
    return e            // returns NON-NIL interface! (type=*MyError, value=nil)
}
if err := do(); err != nil {
    // THIS RUNS — even though "logically" we returned nil
}
Always return nil directly: return nil, not return e when e is a typed nil.
2. Pointer vs value method sets. If (*T).Foo() exists, then *T satisfies any interface needing Foo. T does NOT (you'd need to take its address). This causes "type X does not implement Y" errors.
3. Big "god" interfaces. An interface with 12 methods means you can never mock it cheaply. Split it.

Interview Q&A

Q: How do you mock dependencies for testing?

Define what you need as an interface in your service package. The real impl is in another package; the mock is in _test.go. Inject via the constructor. No mock library needed (though gomock/testify exist).

Q: Why "accept interfaces, return structs"?

Accepting interfaces makes your function flexible. Returning a struct gives the caller the full set of methods + future-proofs your API (you can add methods without breaking interface contracts).

Q: How is Go's interface different from Java's?

Java requires explicit implements. Go is implicit (structural). Result: you can satisfy interfaces from third-party libs without modifying their code, and tests are easier (less coupling).

07 Error Handling — idiomatic Go

Errors are values. No try/catch. Verbose? Yes. Reliable? Also yes.

Why errors-as-values?

Exceptions allow code to silently throw across many layers. Programmers forget what can fail. Go forces every error to be either:

  • Handled at the call site, or
  • Explicitly returned to the caller

This makes error paths visible in code review.

The basics

// error is a built-in interface:
type error interface { Error() string }

// Idiomatic pattern
result, err := doWork()
if err != nil {
    return nil, fmt.Errorf("doWork failed: %w", err)
}
// use result

Creating errors

// Simple
err := errors.New("not found")
err := fmt.Errorf("user %d not found", id)

// Sentinel — exported variables compared by identity
var ErrNotFound = errors.New("user not found")
if errors.Is(err, ErrNotFound) { ... }

// Custom error type — when you want extra data
type ValidationError struct {
    Field string
    Msg   string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("%s: %s", e.Field, e.Msg)
}

var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println(ve.Field)   // type-asserted access
}

Wrapping (Go 1.13+)

Use %w in fmt.Errorf to wrap an error, preserving the chain:

if err != nil {
    return fmt.Errorf("saving user %d: %w", id, err)
}

// Caller can later check the underlying error:
if errors.Is(err, sql.ErrNoRows) { ... }
if errors.As(err, &myType) { ... }

When to use what?

ToolUse when
errors.New / fmt.ErrorfOne-off error message
Sentinel var ErrX = errors.New(...)Caller needs to detect a specific error class
Custom struct + Error()Need to attach data (status code, field, etc.)
%w wrappingAlways when adding context as error bubbles up
errors.IsCompare to a sentinel
errors.AsExtract a typed error from the chain

Gotchas

1. Don't use == for wrapped errors. err == sql.ErrNoRows fails if someone wrapped it. Use errors.Is(err, sql.ErrNoRows).
2. Don't ignore errors. v, _ := foo() is a code smell. Acceptable only when you've reasoned about why ignoring is safe.
3. Don't double-log. Either log AND return the error (DRY violation, leads to log spam), or just return it. Pick one — the convention is "log at the boundary (handler), return everywhere else."
4. Lower-case error messages. Convention: "user not found" not "User not found.". They get composed: "saving: user not found" reads naturally.
5. The typed-nil pitfall (again). See Interfaces section. Always return nil on success.

Interview Q&A

Q: errors.Is vs errors.As?

Is = "is this error in the chain equal to X (sentinel)?". As = "is there an error in the chain whose type is T, and bind it to this var".

Q: How do you handle errors at HTTP boundaries?

Map domain errors to HTTP codes in your handler/middleware. Example: errors.Is(err, ErrNotFound) → 404. Log at the handler. Return clean JSON to the client.

Q: panic vs error?

Errors are for expected failures (file missing, bad input). Panics are for programmer bugs (nil pointer, index out of range). Library code should almost never panic.

08 Pointers & Memory

Go has pointers but is GC'd — you get safety without manual free. Coming from JS, the rules below feel new.

Why pointers exist in a GC language?

  • Mutation — pass a value to a function and let it modify the original.
  • Avoid copying — large structs are expensive to pass by value.
  • Optional values — sometimes nil means "not provided".

You'll never malloc/free manually. Go's escape analysis decides stack vs heap. The GC handles cleanup.

Syntax + Theory

x := 42
p := &x          // p is *int, points to x
fmt.Println(*p)  // 42 — dereference
*p = 100          // modifies x
fmt.Println(x)   // 100

// new allocates a zero-valued T and returns *T
q := new(int)     // q is *int, *q is 0
*q = 7

// Struct pointer
u := &User{Name: "Sid"}
u.Name           // auto-dereferenced! You don't write (*u).Name

Stack vs Heap (escape analysis)

The Go compiler decides automatically:

  • If a value's pointer never leaves the function → stack (fast, freed on return).
  • If a pointer escapes (returned, stored in a global, captured by a closure that outlives the function) → heap (GC-managed).

Inspect with go build -gcflags="-m":

func leak() *int {
    x := 42
    return &x   // "x escapes to heap"
}

When to use a pointer?

  • Need to mutate the caller's value → pointer.
  • Struct is large (rule of thumb: more than ~3-4 small fields, or contains slices/maps you don't want recopied) → pointer.
  • Need to express "optional" with nil → pointer.
  • Otherwise — pass by value. Smaller, safer, no aliasing.

Realistic example

type Counter struct{ N int }

func incVal(c Counter)  { c.N++ }   // modifies COPY, useless
func incPtr(c *Counter) { c.N++ }   // modifies original

c := Counter{N: 0}
incVal(c)        // c.N still 0
incPtr(&c)       // c.N now 1

Gotchas

1. Nil pointer dereference panics at runtime. Always check before deref: 
if u != nil { fmt.Println(u.Name) }
2. & on map values. Illegal: p := &m["k"]. Map values are not addressable. Workaround: store pointers in the map.
3. Pointer to loop variable (pre-Go-1.22) — see Control Flow gotcha.
4. Don't reach for pointers prematurely. Small structs (under ~64 bytes) often perform better as values — better cache locality, GC has less to track.

Interview Q&A

Q: Are slices pointers?

A slice contains a pointer (in its 3-word header). Passing a slice copies the header but both copies still point at the same underlying array.

Q: Does Go have pointer arithmetic?

No, intentionally. p + 1 won't compile (except via unsafe, which you almost never use). This kills a whole class of memory bugs.

Q: How does Go's GC work (briefly)?

Concurrent mark-sweep with low pause times (sub-millisecond on most workloads). It runs alongside your program. You can't trigger explicit GC easily, but GOGC and GOMEMLIMIT tune behavior.

09 Packages & Modules

How Go organizes code on disk and pulls dependencies. Modern (post-1.11) Go uses modules.

Why two concepts?

  • A package is one folder of .go files compiled together. Smallest unit of compilation.
  • A module is a versioned collection of packages, identified by a path (e.g., github.com/user/project). It's what lives in go.mod.

Folder structure

myapp/
├── go.mod                ← module name + Go version + deps
├── go.sum                ← checksums for deps (always commit)
├── main.go               ← package main (entry point)
├── internal/             ← only importable inside this module
│   └── auth/
│       └── auth.go       ← package auth
├── pkg/                  ← public, importable by others (optional convention)
│   └── parser/
│       └── parser.go     ← package parser
└── cmd/
    └── server/
        └── main.go       ← another binary (package main)

Code

// main.go
package main

import (
    "fmt"                                // stdlib
    "github.com/user/myapp/internal/auth"  // own package
    log "github.com/sirupsen/logrus"       // aliased third-party
)

func main() {
    auth.Login("sid")
    log.Info("started")
}

Visibility rule

Capitalize the first letter of an identifier to export it from a package; lowercase to keep it private. There is no public/private keyword.

Module commands (cheat-sheet)

CommandDoes
go mod init github.com/u/repoCreates go.mod
go mod tidyAdds missing & removes unused deps
go get pkg@v1.2.3Pin a dep version
go get -u ./...Upgrade all deps
go list -m allList used module versions
go mod why pkgWhy is this dep here?
go mod vendorCopy deps into vendor/ (offline / reproducible builds)

When & Why

  • Use internal/ for code you DON'T want consumed by external modules. The Go toolchain enforces this.
  • One package per folder — Go forbids two packages in the same dir. Test files (_test.go) can be in the same pkg or pkg_test.
  • Small packages > one giant package. Group by what changes together, not by tech layer.
  • Avoid cyclic imports — Go forbids them at compile time. Refactor to break cycles by introducing an interface in a shared "smaller" package.

Gotchas

1. Package name vs folder name. Doesn't have to match (e.g., folder parser/ can have package parserv2). But ergonomics suffer — keep them the same.
2. internal/ magic. Code in foo/internal/ can only be imported by code rooted at foo/. Good for hiding implementation details.
3. go get in a module folder modifies go.mod. To install a global CLI tool, use go install pkg@latest — it doesn't touch your module.
4. init() functions. Each file can have an init() that runs at import time. Useful for registration, but avoid heavy work — it makes startup slow and order tricky.

Interview Q&A

Q: go.sum — commit or ignore?

Always commit. It pins exact checksums for reproducible builds and prevents supply-chain swaps.

Q: How do you handle private repos?

Set GOPRIVATE=github.com/myorg/* so Go skips the public proxy and sumdb for those paths. Configure SSH or a personal access token via git config.
