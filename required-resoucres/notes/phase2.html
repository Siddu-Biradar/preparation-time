01 Generics (Go 1.18+)

Type parameters for functions and types. The single biggest language addition since modules.

Why did Go finally add generics?

For 10 years Go survived without them, using interface{} + type assertions, or code generation. The cost: lots of boilerplate (a Min function for every numeric type), plus runtime type assertions that the compiler couldn't check.

Generics give us:

  • Type-safe generic data structures (queues, sets, ordered maps).
  • Zero-copy abstraction — code is monomorphized/specialized at compile time.
  • Functional helpers — Map, Filter, Reduce on slices (now in slices/maps std lib).

Theory + Syntax

// Type parameter: [T any] after function name
func Max[T cmp.Ordered](a, b T) T {
    if a > b { return a }
    return b
}
Max(3, 5)              // inferred T=int
Max[float64](1.1, 2.2)   // explicit type

// Multiple type params + constraint
func Map[T, U any](in []T, f func(T) U) []U {
    out := make([]U, len(in))
    for i, v := range in { out[i] = f(v) }
    return out
}
nums := []int{1,2,3}
strs := Map(nums, func(n int) string { return strconv.Itoa(n) })

// Generic type
type Stack[T any] struct {
    items []T
}
func (s *Stack[T]) Push(x T) { s.items = append(s.items, x) }
func (s *Stack[T]) Pop() (T, bool) {
    var zero T
    if len(s.items) == 0 { return zero, false }
    n := len(s.items) - 1
    x := s.items[n]
    s.items = s.items[:n]
    return x, true
}

s := &Stack[string]{}
s.Push("a"); s.Push("b")

Constraints

A constraint is an interface that limits what types T can be. Common ones:

  • any — anything (alias for interface{}).
  • comparable — types usable with ==, != (good for map keys).
  • cmp.Ordered (Go 1.21+) — types usable with < > <= >= (numbers + strings).
  • Custom: define your own interface with method signatures or type union.
// Type union constraint
type Number interface {
    ~int | ~int64 | ~float64
}
func Sum[T Number](nums []T) T {
    var total T
    for _, n := range nums { total += n }
    return total
}

The ~int means "anything whose underlying type is int", so user-defined types like type Money int also satisfy it.

When to use generics?

Use genericsDon't use generics
Generic data structures (Stack, LRU cache, ordered set)Trivial helpers — interface might be cleaner
Functional combinators (Map, Filter, Reduce)When you'd only use 1-2 concrete types — write them out
Numeric algorithms over multiple typesJust to avoid interface{} in one place
Rob Pike's heuristic: "If your code calls methods on the type, an interface is probably better. If it just shuffles values around, generics fit."

Gotchas

1. No method type parameters (yet). You can't have func (r Repo) Find[T any](id int) T — only the receiver type can be generic. Workaround: top-level generic function.
2. Inference isn't always perfect. Sometimes you must specify Foo[int](x).
3. Generic code can be slower than expected. Go generates a "GC shape"-based dictionary at compile, not full monomorphization (like C++). Don't assume same perf as hand-written specialized code; benchmark.
4. Don't over-genericize. One concrete type? Use it. Two? Maybe duplicate. Three+ or a real abstraction? Generics earn their keep.

Interview Q&A

Q: Generic vs interface — when does each win?

Interface = behavior abstraction (call methods). Generics = container/algorithm abstraction (move values around). Sometimes you need both: func Sort[T cmp.Ordered](s []T) uses generics; func Sort(data sort.Interface) uses interface — different ergonomics.

Q: What's ~int vs int in a constraint?

int matches only int. ~int matches int AND any named type with underlying int (e.g., type Score int).

02 Context Package — the most important stdlib package

If you do nothing else right in Go server code, get context right. It's how cancellation, deadlines, and request-scoped values flow.

Why does context exist?

In a Go server, one HTTP request might fan out to: DB query, Redis call, downstream HTTP, goroutine that does background work. If the client disconnects (or the request takes too long), all of that work should stop. Without a unified mechanism, you'd have ad-hoc cancellation per call. Context is that mechanism.

The Context interface

type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done()    <-chan struct{}   // closes when canceled
    Err()     error             // why was it canceled?
    Value(key any) any      // request-scoped values
}

The key idea: contexts form a tree. Cancel a parent, and ALL children cancel. Add a deadline to a child, the child has the tighter of (parent's, its own).

  ctx (root, no deadline)
   ├── ctx1 with timeout 5s   ── derived
   │     └── ctx2 with cancel() callable
   └── ctx3 with value("requestID", "abc-123")

Creating contexts

// Root contexts — start of a request or program
ctx := context.Background()        // for main() / init
ctx := context.TODO()              // "I'll figure out the right one later"

// Derived contexts — the workhorses
ctx, cancel := context.WithCancel(parent)
defer cancel()                            // ALWAYS defer cancel!

ctx, cancel := context.WithTimeout(parent, 5*time.Second)
defer cancel()

ctx, cancel := context.WithDeadline(parent, time.Now().Add(10*time.Second))
defer cancel()

// WithDeadline use case: aligning with an external SLA
// e.g., the upstream gave you a hard deadline; pass the SAME deadline downstream
deadline, ok := req.Context().Deadline()
if ok {
    ctx, cancel = context.WithDeadline(ctx, deadline)   // honor caller's deadline
    defer cancel()
}
// Note: derived ctx takes the EARLIER of (parent's deadline, your deadline)

// Carry values (use sparingly! see gotchas)
ctx = context.WithValue(parent, requestIDKey, "abc-123")

Real usage — HTTP handler chain

func handler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()                // already canceled if client disconnects
    ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
    defer cancel()

    user, err := repo.FindUser(ctx, id)   // ctx flows down
    if err != nil {
        http.Error(w, err.Error(), 500); return
    }
    // ...
}

// In repo
func (r *Repo) FindUser(ctx context.Context, id int) (*User, error) {
    row := r.db.QueryRowContext(ctx, "SELECT ...", id)
    // ↑ if ctx is canceled, query is aborted
}

// Listening to cancellation in your own loop
for {
    select {
    case <-ctx.Done():
        return ctx.Err()       // context.Canceled or context.DeadlineExceeded
    case work := <-jobs:
        process(work)
    }
}

Rules of context

  1. Pass ctx as the FIRST argument of any function that does I/O, work, or further calls.
  2. Never store contexts in structs. They're per-call.
  3. Always defer cancel() when you derive a context. Even if you returned a value cleanly — pending timers leak otherwise.
  4. Don't pass nil ctx. Use context.TODO() if you don't have one yet.
  5. Use ctx.Value sparingly — only for request-scoped data (request ID, auth user). NEVER for optional function parameters.

Gotchas

1. Forgetting defer cancel(). A WithTimeout/WithCancel spawns a goroutine to track the deadline. Not calling cancel leaks it. Linters (govet) catch this.
2. Context value type collisions. 
// BAD: string keys collide across packages
ctx = context.WithValue(ctx, "user", u)

// GOOD: unexported type as key, scoped to your package
type ctxKey int
const userKey ctxKey = 1
ctx = context.WithValue(ctx, userKey, u)
u, _ := ctx.Value(userKey).(*User)
3. Don't ignore ctx.Done() in long loops. Even if you don't make external calls, periodically check the channel so cancellation is responsive.
4. context.Background() in HTTP handlers = bug. The request's own ctx tracks the client's connection. Use r.Context().

Interview Q&A

Q: How does the DB driver know to cancel the query?

It calls ctx.Done() in a goroutine; on close, it sends a cancel command to the DB (e.g., Postgres pg_cancel_backend). All major drivers support this.

Q: Difference between context.Canceled and context.DeadlineExceeded?

Both are sentinel errors. Canceled means someone called cancel(). DeadlineExceeded means timeout fired. Useful in handlers to map to 499 vs 504.

Q: Can I pass tracing/logging info via context?

Yes — request ID, trace ID, auth principal are textbook use cases. NOT for things like DB connections or business config.

03 JSON, Time, Strings & Stdlib Mastery

Go's standard library is a competitive moat. Know these packages cold and you'll need fewer dependencies than in any other language.

Why is the stdlib so important?

Unlike Node where npm install x for everything, the Go community prefers stdlib + minimal deps. net/http, encoding/json, database/sql, html/template, crypto/* — all production-ready. This means smaller binaries, less supply-chain risk, and stable APIs.

encoding/json

type User struct {
    ID    int    `json:"id"`
    Name  string `json:"name"`
    Email string `json:"email,omitempty"`  // drop if zero
    Pwd   string `json:"-"`                // never serialize
}

// Marshal — Go → JSON bytes
b, err := json.Marshal(u)              // compact
b, err := json.MarshalIndent(u, "", "  ")  // pretty

// Unmarshal — JSON bytes → Go struct
var u User
err := json.Unmarshal(b, &u)         // ALWAYS pass pointer!

// Streaming — Decoder/Encoder for big or io-based JSON
dec := json.NewDecoder(r.Body)
dec.DisallowUnknownFields()           // strict mode
err := dec.Decode(&u)
Custom JSON — implement MarshalJSON() / UnmarshalJSON() on your type for special formats (e.g., custom date, money). See Reflection section below.

time

now := time.Now()
later := now.Add(2 * time.Hour)
diff := later.Sub(now)               // returns Duration

// Parsing — uses the magic reference time: Mon Jan 2 15:04:05 MST 2006
t, _ := time.Parse(time.RFC3339, "2024-05-01T10:30:00Z")
t, _ := time.Parse("2006-01-02", "2024-05-01")

// Formatting
s := now.Format(time.RFC3339)         // "2024-05-15T14:32:01Z"
s := now.Format("02 Jan 2006")         // "15 May 2024"

// Timer / Ticker
<-time.After(3 * time.Second)         // blocks 3s
ticker := time.NewTicker(1 * time.Second)
defer ticker.Stop()                  // always stop tickers!
for t := range ticker.C { // every 1s }
Why 2006-01-02? Go's reference time is mnemonic: 01/02 03:04:05PM 06 -0700 = Jan 2nd, 3:04:05PM, 2006, MST. Memorize once, save hours of confusion.

strings & strconv

// strings — string manipulation
strings.Contains("hello", "ell")         // true
strings.HasPrefix("go-1.22", "go-")
strings.Split("a,b,c", ",")              // [a b c]
strings.Join([]string{"a","b"}, "-")      // "a-b"
strings.ToLower, .ToUpper, .TrimSpace, .Replace, .ReplaceAll

// strconv — string ↔ number
n, err := strconv.Atoi("42")              // "42" → 42 (int)
n, err := strconv.ParseFloat("3.14", 64)
s := strconv.Itoa(42)                    // 42 → "42"
s := strconv.FormatFloat(3.14, 'f', 2, 64)

// Builder — efficient concatenation (avoid s += s2 in loops!)
var sb strings.Builder
for i := 0; i < 100; i++ {
    sb.WriteString("x")
}
result := sb.String()

Other heavy hitters to know

PackageWhat it does
net/httpHTTP server + client. Not just for hobby — runs in production.
database/sqlSQL driver-agnostic interface. Use with pgx/mysql drivers.
encoding/json, encoding/csv, encoding/base64Common encodings.
regexpRegex (RE2 — guaranteed linear time, no catastrophic backtracking).

Gotchas

1. JSON unmarshal silently ignores unknown fields by default. Add dec.DisallowUnknownFields() if you want strict validation (always, IMO).
2. JSON tags must match the JSON exactly (case-sensitive). "name" tag won't match incoming "Name".
3. time.Time defaults to local timezone. Always t.UTC() at boundaries. Store UTC. Convert at the edge.
4. time.Sleep is not cancellable. Use select { case <-time.After(d): case <-ctx.Done(): }.
5. strings.TrimRight(s, "abc") trims any of those characters, not the suffix. For suffix removal use strings.TrimSuffix.
6. JSON numbers default to float64. Unmarshal a big int into any and you may lose precision. Use json.Number or a typed struct.

Interview Q&A

Q: Why is Go's regex package "slow" compared to PCRE?

It uses RE2, which guarantees O(n) time. It can't do backreferences or lookaheads, but it's safe against catastrophic regex inputs (security wins).

Q: How would you parse a date like "15-May-2024"?

time.Parse("02-Jan-2006", "15-May-2024") — the layout always uses the reference values.

04 io.Reader / io.Writer — the universal interfaces

Two tiny interfaces that compose into all of Go's I/O. Master these and you'll never re-implement streaming.

Why this design?

In Java/Node, file I/O, HTTP body, network socket, in-memory buffer all have different APIs. Go unifies them with two single-method interfaces, letting any source/sink plug into any consumer (compression, hashing, encryption, encoding…).

The interfaces

type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}

That's it. Read fills p with up to len(p) bytes, returns count + error. EOF is signaled via io.EOF.

Who implements these?

  Reader implementations               Writer implementations
  ──────────────────────                ─────────────────────
  *os.File           (file)             *os.File
  *bytes.Buffer      (in-memory)        *bytes.Buffer
  *strings.Reader    (string)           *strings.Builder
  net.Conn           (TCP socket)       net.Conn
  http.Request.Body  (request body)     http.ResponseWriter
  *gzip.Reader       (decompressing)    *gzip.Writer
  *cipher.StreamReader (decrypting)     *cipher.StreamWriter
  *bufio.Reader      (buffered)         *bufio.Writer

Composition examples

// Read a file, gunzip, parse JSON — all streaming, no big buffers
f, _ := os.Open("data.json.gz")
defer f.Close()
gz, _ := gzip.NewReader(f)              // gz is also an io.Reader
defer gz.Close()
var data []User
json.NewDecoder(gz).Decode(&data)

// Copy from any reader to any writer
n, err := io.Copy(dst, src)             // streaming, low memory

// Tee — read AND simultaneously write a copy
hash := sha256.New()
tee := io.TeeReader(src, hash)
io.Copy(io.Discard, tee)
fmt.Printf("%x\n", hash.Sum(nil))     // SHA of stream

// MultiReader — concatenate streams
r := io.MultiReader(file1, file2, strings.NewReader("trailer"))

// MultiWriter — write to many sinks (e.g., file + stdout)
w := io.MultiWriter(os.Stdout, logFile)
fmt.Fprintln(w, "hello")

When & Why

  • Building a function that processes data? Take an io.Reader. The caller can pass a file, an in-memory buffer (great for tests), an HTTP body, anything.
  • Returning data? Return an io.Reader for streaming, or a []byte only when the caller will need it all at once.
  • Use bufio.Reader when reading from network/file char-by-char or line-by-line — raw os.File is unbuffered.

Gotchas

1. Read may return fewer bytes than asked — that's NORMAL. Don't assume one Read = one logical message. Use io.ReadFull, bufio, or io.ReadAll for whole reads.
2. EOF is a value, not a panic. err == io.EOF means success — the stream ended cleanly. err == io.ErrUnexpectedEOF = stream cut short mid-read.
3. Always close. If you got an io.ReadCloser (like http.Response.Body), defer Close(). Forgetting leaks connections + memory.
4. io.ReadAll reads EVERYTHING into memory. Don't use it on untrusted/unbounded inputs — DoS risk. Cap with io.LimitReader.

Interview Q&A

Q: How do you stream a 10GB file processing without loading it into RAM?

Open as *os.File, wrap with bufio.NewScanner for lines or bufio.NewReader for chunks, process incrementally. Use io.Copy for pipe-throughs.

Q: How do you compute SHA of an HTTP upload while uploading to S3?

io.TeeReader(req.Body, hasher) — pass the tee to S3 client. Hash is updated as bytes flow.

05 Reflection & Custom JSON

Inspect types at runtime. Powerful, but slow and easy to misuse — use as last resort.

Why does reflection exist?

Some libraries (encoding/json, ORM, validators) need to work with arbitrary user types. They can't be hardcoded. Reflection lets them ask at runtime: "What fields does this struct have? What's their type? What tags?"

The model

Two types in reflect:

  • reflect.Type — the type metadata (name, kind, fields, methods).
  • reflect.Value — a runtime handle to a concrete value (read/set/call).
type User struct {
    Name string `json:"name" validate:"required"`
    Age  int    `json:"age"`
}

u := User{Name: "Sid", Age: 30}
t := reflect.TypeOf(u)
v := reflect.ValueOf(u)

fmt.Println(t.Name())              // "User"
fmt.Println(t.Kind())              // struct
fmt.Println(t.NumField())          // 2

for i := 0; i < t.NumField(); i++ {
    f := t.Field(i)
    fmt.Printf("%s (%s) tag=%q value=%v\n",
        f.Name, f.Type, f.Tag.Get("json"), v.Field(i))
}
// Name (string) tag="name" value=Sid
// Age (int) tag="age" value=30

Custom JSON marshaling — the pragmatic use of reflection

You usually don't write reflection yourself. You implement these interfaces:

type Money struct {
    Amount   int64     // cents
    Currency string
}

// Custom output: "$12.34"
func (m Money) MarshalJSON() ([]byte, error) {
    s := fmt.Sprintf("\"%s%.2f\"", m.Currency, float64(m.Amount)/100)
    return []byte(s), nil
}

func (m *Money) UnmarshalJSON(b []byte) error {
    var s string
    if err := json.Unmarshal(b, &s); err != nil { return err }
    // parse "$12.34" → m.Currency, m.Amount...
    return nil
}

The std lib's encoding/json package detects these methods via reflection and calls them.

When to use reflection?

  • Writing a library that handles arbitrary user types (validator, ORM, encoder).
  • Wiring DI containers, registering plugins.
  • Generating test fixtures.
  • Almost never in app code. Prefer interfaces, generics, or code generation.

Gotchas

1. Reflection is SLOW. 10-100x slower than direct field access. Don't use in hot paths. Cache reflect.Type if you must.
2. Reflection sidesteps type safety. Errors that would be compile-time become runtime panics. Test thoroughly.
3. To set a field via reflection, you need reflect.ValueOf(&u).Elem() (a settable value) and the field must be exported. Unexported fields can't be set via reflection.
4. Tag parsing is YOUR job. StructField.Tag.Get("json") returns "name,omitempty" as ONE string — split it manually.

Interview Q&A

Q: What's the alternative to reflection in modern Go?

Generics (Go 1.18+) eliminate many use cases. Code generation (go generate + stringer, genny) gives compile-time, zero-overhead specialization. Reach for reflect only when neither works.

Q: How does fmt.Println know how to print any type?

It uses reflection internally (or calls String()/Error() methods if implemented). For custom output, implement fmt.Stringer.

06 Structured Logging with slog

Built-in (Go 1.21+), structured, leveled, fast. Replaces log, logrus, zap for most needs.

Why structured?

Old-style logs (log.Println("user 42 saved in 17ms")) are unparseable strings. Structured logs are JSON/key-value — your log aggregator (Loki, ELK, Datadog) can index and query them.

slog basics

import "log/slog"

// Default text logger to stderr
slog.Info("user saved", "id", 42, "duration_ms", 17)
// time=2024-05-15T10:30:00 level=INFO msg="user saved" id=42 duration_ms=17

// JSON logger
logger := slog.New(slog.NewJSONHandler(os.Stderr, &slog.HandlerOptions{
    Level: slog.LevelDebug,
}))
slog.SetDefault(logger)

slog.Error("db query failed", "err", err, "query", q)
// {"time":"...","level":"ERROR","msg":"db query failed","err":"...","query":"..."}

Common patterns

// Levels: Debug, Info, Warn, Error
slog.Debug("raw payload", "data", payload)
slog.Warn("retrying", "attempt", n)

// Group attributes
slog.Info("http request",
    slog.Group("req",
        "method", "GET",
        "path", "/users",
    ),
    "status", 200,
)

// Loggers with persistent context (e.g., per-request)
reqLogger := slog.Default().With("requestID", id, "user", u)
reqLogger.Info("started")
reqLogger.Info("saved", "rows", 3)
// Both lines include requestID and user automatically.

// With context — for trace propagation
slog.InfoContext(ctx, "work done")

When & Why

  • Default to JSON in production, text in local dev.
  • Use slog.With at request entry to attach request/trace IDs — they automatically appear in every log line for that request.
  • Don't log secrets (passwords, tokens, PII). Build a redaction layer (custom LogValuer impl).

Gotchas

1. Key-value pairs come in PAIRS. slog.Info("x", "k1", v1, "k2") with odd args is silently mangled. Use slog.Any("k", v) typed attrs to avoid mistakes.
2. Loggers are concurrency-safe — share one. Don't create a new logger per request unless deriving with With.
3. slog is slower than zap for the absolute hottest paths. For >100k logs/sec consider zerolog/zap. Otherwise slog is plenty fast.

Interview Q&A

Q: How do you correlate logs to traces?

Inject the traceID/spanID as attrs via logger.With(...) at request entry, ideally pulled from OpenTelemetry context.

Q: When would you NOT use slog?

Pre-Go 1.21 codebases (zap/zerolog); ultra-high-throughput pipelines where allocation profile matters; specialized formats (CEF, GELF) needing existing libs.

07 Go Tooling — test, vet, build, generate

Go ships with one CLI that does ~everything. No webpack.config, no tsconfig, no jest.config.

Why a single tool?

Predictability across teams and codebases. go test ./... works the same in every Go project on earth. New hires don't need to learn 10 build tools.

Cheat-sheet

CommandPurpose
go run main.goCompile + run (dev)
go build ./...Compile every package; binary named after main package
go installBuild & place binary in $GOPATH/bin
go test ./...Run all tests
go test -race ./...With race detector (use in CI!)
go test -cover ./...Code coverage
go test -bench=. -benchmemRun benchmarks
go vet ./...Static analysis (catches common bugs)
gofmt -w . / go fmt ./...Auto-format
go mod tidySync go.mod / go.sum
go generate ./...Run generators (mocks, enums)
go doc fmt.SprintfInline docs
go envShow Go env (GOROOT, GOPATH, GOOS, etc.)
go tool pprof cpu.profProfiler UI

Testing

// file: math_test.go (must end in _test.go)
package mymath

import "testing"

func TestAdd(t *testing.T) {
    got := Add(2, 3)
    if got != 5 {
        t.Errorf("Add(2,3) = %d; want 5", got)
    }
}

// Table-driven tests — idiomatic Go style
func TestAddMany(t *testing.T) {
    cases := []struct {
        name    string
        a, b    int
        want    int
    }{
        {"both pos", 1, 2, 3},
        {"with zero", 5, 0, 5},
        {"neg", -1, -1, -2},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            if got := Add(tc.a, tc.b); got != tc.want {
                t.Errorf("got %d, want %d", got, tc.want)
            }
        })
    }
}

// Benchmark
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(1, 2)
    }
}
Run a single test: go test -run TestAdd ./pkg. Verbose: -v. One subtest: -run "TestAddMany/with_zero".

go generate

Embed compiler-driven scripts in your code:

//go:generate stringer -type=Status
type Status int
const ( Pending Status = iota; Active; Closed )
// running `go generate` produces status_string.go with String() method

Common generators: stringer, mockgen (gomock), protoc-gen-go (proto), sqlc, ent.

When & Why

  • Always run go vet + golangci-lint in CI. Catches mistakes before review.
  • Always run with -race in CI. Concurrency bugs hide for months otherwise.
  • Test files next to source (same folder, _test.go suffix). External tests use package foo_test in same folder.

Gotchas

1. Flaky tests. Most are concurrency or time-dependent. Use testing.Short for slow tests; t.Parallel() needs care if shared globals exist.
2. t.Parallel() + table-driven tests + loop var. Pre-Go 1.22, capture the test case: tc := tc before t.Run closure. Fixed in 1.22.
3. go test ./... doesn't fail on race conditions WITHOUT -race. Add it to CI.
4. Coverage gates can lie. 90% coverage means lines were executed, not that you tested all behaviors. Don't chase numbers blindly.

Interview Q&A

Q: What does go vet catch that the compiler doesn't?

Lock copies, misuses of Printf formatting, suspicious shifts, unreachable code, etc. Use golangci-lint for a superset.

Q: How do you isolate integration tests?

Use build tags: //go:build integration at top of file, run with go test -tags=integration. Or check a flag/env var and t.Skip().
