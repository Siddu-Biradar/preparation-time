01 Goroutines & the Scheduler

Lightweight, multiplexed onto OS threads by Go's runtime. Cheap to create, expensive to misuse.

Why goroutines instead of threads or async/await?

  • OS threads are expensive (~1MB stack each). You can't have millions.
  • async/await infects your codebase — every function becomes async ("function color problem").
  • Goroutines start with ~2KB stacks (grow on demand). You can have millions on one machine. Code is written like sync; the runtime parallelizes it.

The G-M-P scheduler model

  G = goroutine (your code)
  M = OS thread
  P = processor (logical CPU, count = GOMAXPROCS)

  ┌─ P0 ──────────┐   ┌─ P1 ──────────┐
  │ local queue:  │   │ local queue:  │
  │ [G3 G7 G9]    │   │ [G2 G5]       │
  │      ↓        │   │     ↓         │
  │   M0 runs G3  │   │   M1 runs G2  │
  └───────────────┘   └───────────────┘
        ↕                   ↕     work-stealing across Ps
  ┌─ Global queue (overflow): [G15 G22 G33] ─┐
  │                                          │
  │  Network poller (epoll/kqueue) hands     │
  │  ready-from-IO goroutines back to Ps     │
  └──────────────────────────────────────────┘

When a goroutine blocks on I/O, the runtime parks it and the M moves on to another G. You get C10M (ten million concurrent connections) potential, sync-style code.

Syntax

// Spawn — just prefix `go`
go handleRequest(req)

// Anonymous func
go func(id int) {
    fmt.Println("worker", id)
}(1)

// Number of logical CPUs the runtime uses
runtime.GOMAXPROCS(0)        // 0 = read current
runtime.NumGoroutine()       // for monitoring

When & Why

  • Per-request: HTTP server starts one goroutine per connection (you don't have to).
  • Background work: refresh cache, drain a queue.
  • Parallel computation: split work across cores using a worker pool.
  • Fan-out/fan-in: multiple downstream calls, gather results.

Gotchas

1. Goroutines are not free. Spawning 100K to do nothing wastes RAM. They're cheap relative to threads — not free.
2. main exiting kills all goroutines. No graceful shutdown unless you arrange one (WaitGroup, signal handling). Background work must finish or you'll lose it.
3. Fire-and-forget = leaks waiting to happen. If a goroutine blocks on a channel that nobody closes, it lives forever. See "Goroutine Leaks" section.
4. GOMAXPROCS in containers. By default Go reads the host's CPU count, not the cgroup limit. In Kubernetes, set GOMAXPROCS via env or use uber-go/automaxprocs to align with CPU limits.

Interview Q&A

Q: Are goroutines threads?

No. They're scheduled USER-SPACE by the Go runtime onto OS threads. Many goroutines per thread; threads are reused.

Q: How does the runtime know when to switch goroutines?

Cooperatively at function calls + on I/O blocks. Since Go 1.14, also preemptively (signal-based) so tight loops don't starve others.

02 Channels & Select — communicate, don't share

"Don't communicate by sharing memory; share memory by communicating." — Go's mantra.

Why channels?

Channels turn shared state into typed message passing. They eliminate most locking by design. Closer to Erlang's actor model than Java's threads.

Channel anatomy

// Unbuffered — sync handoff (sender blocks until receiver ready)
ch := make(chan int)

// Buffered — async up to capacity
ch := make(chan int, 10)

// Send / receive
ch <- 42           // send
v := <-ch          // receive
v, ok := <-ch      // receive + check if channel closed (ok=false → closed and drained)

// Close — by SENDER, signals "no more values"
close(ch)

// Range — receive until close
for v := range ch { ... }

// Direction in function signatures (compile-time enforced)
func producer(out chan<- int) { out <- 1 }    // send-only
func consumer(in <-chan int) { v := <-in }   // receive-only

Select — wait on multiple channels

select {
case v := <-ch1:
    handle(v)
case ch2 <- 5:
    log("sent")
case <-ctx.Done():
    return ctx.Err()
case <-time.After(2 * time.Second):
    return errors.New("timeout")
default:                 // non-blocking — runs if no case ready
    log("nothing ready")
}

If multiple cases are ready, select chooses one at random (intentional — prevents starvation).

  Sender ──▶ [        channel buffer          ] ──▶ Receiver
                ↑ blocks if full                ↑ blocks if empty (unless closed)
            close() = no more sends

Common patterns

// 1. Generator — produce values from a goroutine
func naturals() <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for i := 1; ; i++ { out <- i }
    }()
    return out
}

// 2. Done channel — signal completion
done := make(chan struct{})
go func() {
    defer close(done)
    work()
}()
<-done   // wait

// 3. Timeout
select {
case v := <-ch:
    handle(v)
case <-time.After(5 * time.Second):
    return errors.New("timeout")
}

Buffered vs Unbuffered?

Use unbufferedUse buffered
You want a synchronization handoff (rendezvous)You want decoupling — sender continues without waiting
Default choice when in doubtProducer is bursty, consumer is steady (queue smoothing)
Signal/done channelsWorker pools (capacity = number of workers or job batch size)

Gotchas

1. Sending on a CLOSED channel = PANIC. Receiving from closed is fine (returns zero value + ok=false). Convention: only the sender closes.
2. Closing a NIL channel = panic. Sending/receiving on nil = blocks FOREVER. The "block forever" can be useful in select to disable a case — but accidental nil channels = goroutine leak.
3. Closing a channel TWICE = panic. If multiple goroutines might want to close, use sync.Once or a single dedicated closer.
4. Don't close to signal cancellation FROM consumer to producer. The producer might still be sending and you'll panic. Use context for cancellation.
5. select with no ready cases AND no default = block forever. Add ctx.Done() case for safety.

Interview Q&A

Q: What's the difference between an unbuffered channel and a buffered channel of size 1?

Unbuffered: send blocks until a receive happens. Buffered(1): send returns immediately if empty, blocks only when buffer full. The semantic difference matters — unbuffered guarantees handoff, buffered allows the sender to move on.

Q: How do you wait for a goroutine to finish without WaitGroup?

A done channel (chan struct{}) closed by the goroutine. Receiver blocks on <-done until close.

03 sync — Mutex, WaitGroup, Once, RWMutex

When channels are overkill, classic locks are still right.

Why locks if we have channels?

Channels are great for passing data between goroutines. Locks are better for guarding shared state (in-memory caches, counters, maps). The Go community: use whichever makes the code clearest.

sync.Mutex

type Counter struct {
    mu sync.Mutex      // zero-valued mutex is ready to use
    n  int
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}
func (c *Counter) Get() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n
}

sync.RWMutex — many readers OR one writer

var mu sync.RWMutex

mu.RLock(); v := cache[k]; mu.RUnlock()    // many readers
mu.Lock();  cache[k] = v; mu.Unlock()        // one writer, blocks readers

Useful only when reads vastly outnumber writes (~10:1+). Otherwise plain Mutex is faster (no internal bookkeeping).

sync.WaitGroup — wait for N goroutines to finish

var wg sync.WaitGroup
for _, item := range items {
    wg.Add(1)
    go func(it Item) {
        defer wg.Done()
        process(it)
    }(item)
}
wg.Wait()           // blocks until counter hits 0

sync.Once — do something exactly once

var (
    once sync.Once
    db   *sql.DB
)
func getDB() *sql.DB {
    once.Do(func() {
        db, _ = sql.Open("postgres", dsn)
    })
    return db
}

Thread-safe lazy init. Concurrent callers all wait for the first one's f() to complete.

Decision tree

ScenarioUse
Pass values between goroutinesChannel
Counter / shared map / cacheMutex (or sync.Map for very specific patterns)
Read-heavy, write-rareRWMutex
Wait for N tasksWaitGroup (or errgroup if errors matter)
Lazy init / singletonsync.Once
Pure counter atomicsync/atomic (faster, no lock)

Gotchas

1. NEVER copy a sync.Mutex. Once locked, the copy has different state from the original = chaos. go vet catches this. Always use pointer receivers on types containing sync.
2. wg.Add inside a goroutine is wrong. 
// BAD — wg.Wait might fire before Add runs
go func() {
    wg.Add(1)       // race
    defer wg.Done()
    // ...
}()
Always wg.Add on the parent goroutine BEFORE spawning.
3. Forgetting to Unlock on early return. Always defer mu.Unlock() immediately after mu.Lock(). Saves you from countless bugs.
4. Deadlock from lock ordering. If goroutine A locks mu1 then mu2, and B locks mu2 then mu1 → deadlock. Always acquire locks in the same order across the codebase.
5. sync.Map is NOT a "concurrent map". It's optimized for two specific patterns (write-once-read-many, disjoint key sets per goroutine). For general use, plain map + RWMutex is faster.

Interview Q&A

Q: How do you protect a map from concurrent access?

Wrap it in a struct with a mutex. Concurrent writes (or write+read) on a built-in map = panic, detected by Go runtime. Don't trust "looks fine" — add the lock.

Q: WaitGroup vs channel for waiting?

WaitGroup if you just need "all done". Channel if you also want to collect results or errors. errgroup combines both.

04 Worker Pool & Fan-Out / Fan-In

The two patterns you'll use weekly in real backend code.

Why a worker pool?

You have N jobs (could be millions) and want to run them with bounded parallelism (e.g., 10 at a time, to avoid hammering an external API or running out of file descriptors).

Worker pool

func workerPool(ctx context.Context, jobs []Job, numWorkers int) []Result {
    jobCh := make(chan Job)
    resCh := make(chan Result, len(jobs))

    // Spawn workers
    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range jobCh {
                select {
                case <-ctx.Done(): return
                case resCh <- process(ctx, j):
                }
            }
        }()
    }

    // Feed jobs
    go func() {
        defer close(jobCh)
        for _, j := range jobs {
            select {
            case <-ctx.Done(): return
            case jobCh <- j:
            }
        }
    }()

    // Close result chan when all workers done
    go func() { wg.Wait(); close(resCh) }()

    // Drain
    results := make([]Result, 0, len(jobs))
    for r := range resCh {
        results = append(results, r)
    }
    return results
}

  jobs ──▶ jobCh ──┬──▶ Worker 1 ──┐
                    ├──▶ Worker 2 ──┼──▶ resCh ──▶ collector
                    └──▶ Worker N ──┘
   (fan-out)                          (fan-in)

Fan-out / Fan-in (distinct from pool)

Pool = fixed workers, dynamic jobs. Fan-out = one input multiplexed to many parallel goroutines. Fan-in = many goroutines' outputs merged into one channel.

// Fan-in — merge many channels into one
func merge[T any](chs ...<-chan T) <-chan T {
    out := make(chan T)
    var wg sync.WaitGroup
    wg.Add(len(chs))
    for _, c := range chs {
        go func(c <-chan T) {
            defer wg.Done()
            for v := range c { out <- v }
        }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

When & Why

  • Worker pool: scraping, image processing, bulk DB ops, calling external APIs in parallel.
  • Fan-out: parallelize independent tasks. Fan-in: collect their results.
  • Pick worker count based on bottleneck: I/O-bound → many workers (50-500). CPU-bound → ~runtime.NumCPU().

Gotchas

1. Forgetting to close jobCh = workers block forever. The feeder MUST close jobCh after sending all jobs.
2. Result channel buffer. If workers can produce faster than collector consumes, an unbuffered resCh causes workers to block. Buffer = number of jobs (if memory allows) or use the pattern shown.
3. Errors get lost. Workers must communicate errors. errgroup (next section) is built for this.
4. Order is not preserved. First in, last out — totally possible. If order matters, send (idx, result) tuples and reorder at the end.

Interview Q&A

Q: How do you bound concurrency without a worker pool?

A semaphore — buffered channel of size N: sem := make(chan struct{}, N). Each goroutine does sem <- struct{}{} before work and <-sem when done. Simple alternative.

Q: How do you handle a worker pool where work itself spawns more work (recursive)?

Tricky — naive approach deadlocks (workers block on full job queue). Solutions: unbounded job queue (slice + mutex), separate "scheduler" goroutine, or golang.org/x/sync/semaphore with weighted limits.

05 errgroup & Advanced Patterns

The 80% solution to "run N things, fail fast, propagate first error". Use it daily.

Why errgroup?

WaitGroup doesn't track errors. Channels work but boilerplate-heavy. golang.org/x/sync/errgroup wraps both with cancellation: when one task errors, the shared context is canceled and others can stop.

Basic usage

import "golang.org/x/sync/errgroup"

func fetchAll(ctx context.Context, urls []string) ([][]byte, error) {
    g, ctx := errgroup.WithContext(ctx)
    results := make([][]byte, len(urls))

    for i, u := range urls {
        i, u := i, u   // pre-Go-1.22 capture (auto in 1.22+)
        g.Go(func() error {
            req, _ := http.NewRequestWithContext(ctx, "GET", u, nil)
            res, err := http.DefaultClient.Do(req)
            if err != nil { return err }
            defer res.Body.Close()
            b, err := io.ReadAll(res.Body)
            if err != nil { return err }
            results[i] = b
            return nil
        })
    }
    if err := g.Wait(); err != nil {
        return nil, err
    }
    return results, nil
}

Bounded errgroup (Go 1.20+ in x/sync)

g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10)         // at most 10 concurrent goroutines
for _, u := range urls {
    g.Go(func() error { ... })
}
g.Wait()

When & Why

  • Anytime you'd combine WaitGroup + error channel + context cancel.
  • Service composition — call 5 backends in parallel, fail fast.
  • Bulk operations with size limit.

Gotchas

1. g.Wait() returns the FIRST error. Subsequent errors are lost. If you need all errors, collect them yourself in a slice + mutex.
2. ctx from WithContext is canceled on first error — use it inside goroutines so they exit.
3. Don't share results via a single index from the loop variable (pre-Go-1.22 issue) — capture i properly.

Interview Q&A

Q: errgroup vs sync.WaitGroup?

errgroup adds error propagation + context cancellation. WaitGroup is just a counter. For 99% of "run N things" cases, errgroup is the right call.

06 Race Detector & Go Memory Model

Concurrency bugs are the worst: nondeterministic, often invisible until production. Tools save you.

Why a memory model?

Without rules, the compiler/CPU can reorder reads and writes for performance. The Go memory model defines which orderings are guaranteed across goroutines (the "happens-before" relation).

Practical takeaway: any concurrent read+write of the same variable without synchronization is a DATA RACE — undefined behavior. The compiler is allowed to assume races don't happen, so a race can corrupt arbitrary memory.

What synchronizes?

  • Channel operations: send happens-before corresponding receive completes.
  • Closing a channel happens-before receivers see closed.
  • sync.Mutex Lock/Unlock: nth Unlock happens-before (n+1)th Lock.
  • sync.Once.Do: f() completes before any other Do returns.
  • atomic operations.

If you read & write a variable in different goroutines without one of these, → race.

Race detector

go run -race ./...
go test -race ./...
go build -race main.go

It instruments memory accesses. ~5-10x slowdown — only run in CI/dev, not in production binary.

A classic race

var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }()
}
// Final counter is NOT 1000. counter++ is read-modify-write.
// Fix: sync.Mutex or atomic.AddInt64.

Always use -race in CI

One CI job that runs go test -race ./... catches an enormous class of bugs you'd otherwise hit in production at 3am.

Gotchas

1. The race detector finds RACES YOU EXECUTE. If a code path isn't exercised, races there go undetected. Pair with good test coverage.
2. "It works on my machine" but races still exist. CPUs have different memory ordering — Intel is more forgiving than ARM. Buggy code can pass on x86 and break on M1/AWS Graviton.
3. -race false negatives are rare; false positives essentially don't exist. If it says race, fix it.

Interview Q&A

Q: Are reads of an int atomic?

No guarantee. The Go memory model treats unaligned/unsynced word reads as racy. Use atomic or a mutex.

Q: Does append need a lock if multiple goroutines append to the same slice?

Yes. Slice header writes are not atomic, and the underlying array can be reallocated mid-append. Lock or use channels to funnel appends through one goroutine.

07 sync/atomic & sync.Pool

Lock-free primitives + object pooling. The "performance toolbox".

Why atomic?

For simple operations (counter, flag, pointer swap) on a single word, atomic CPU instructions are 5-100x faster than a Mutex. The downside: only works for one variable at a time, not multi-step invariants.

atomic basics (Go 1.19+ types are nicer)

var count atomic.Int64
count.Add(1)
v := count.Load()
count.Store(100)
swapped := count.CompareAndSwap(old, new)

// atomic.Pointer for lock-free reference swap (e.g., config hot-reload)
var cfg atomic.Pointer[Config]
cfg.Store(newCfg)
c := cfg.Load()

sync.Pool — recycle objects

The GC handles allocation, but for hot paths (e.g., per-request buffers in an HTTP server), allocating + GC'ing thousands per second adds up. sync.Pool lets you reuse objects.

var bufPool = sync.Pool{
    New: func() any { return make([]byte, 1024) },
}

func handle(req string) {
    buf := bufPool.Get().([]byte)
    defer func() {
        buf = buf[:0]            // reset for reuse
        bufPool.Put(buf)
    }()
    // use buf...
}

When to use?

  • atomic — simple counters, hot-reload pointers, lock-free flags. Don't try to build complex data structures with it (you'll fail).
  • sync.Pool — objects that are expensive to allocate AND short-lived AND used in high-frequency code paths (e.g., HTTP request buffers, JSON decoders). Used internally by fmt, encoding/json, etc.

Gotchas

1. atomic for invariants over MULTIPLE variables = wrong. "If x > 0 then y must be > 0" — atomic can't enforce that. Use a Mutex.
2. sync.Pool objects can be GC'd at any time. It's a CACHE, not a guaranteed pool. Don't store anything you can't recreate.
3. ALWAYS reset pooled objects. Get + use without zeroing → leaked data from previous use. buf = buf[:0] for slices.
4. Don't use sync.Pool for cheap-to-create objects. Overhead of Get/Put can be more than allocation. Benchmark.

Interview Q&A

Q: Mutex vs atomic — which is faster?

Atomic, by 5-100x for single-variable ops. But mutex is more flexible (multi-step transactions). Profile before choosing.

Q: When does sync.Pool actually help?

High-throughput servers where allocations dominate the profile (visible in pprof). Adding Pool can drop GC pressure significantly. For low traffic, it's overhead.

08 Pipeline Pattern & Cancellation

Compose stages of channels for streaming data processing. Foundation of Go's concurrency style.

Why pipelines?

Many backend tasks are: read data → transform → filter → write. Each stage can run in parallel with the others, with backpressure naturally handled by channel capacity. Like Unix pipes but inside one process.

A pipeline = stages connected by channels

  source ──▶ stage1 ──▶ stage2 ──▶ sink
   (gen)     (filter)   (transform)  (consume)
   chan       chan       chan

Concrete example

// Stage 1: produce numbers
func gen(ctx context.Context, nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            select {
            case <-ctx.Done(): return
            case out <- n:
            }
        }
    }()
    return out
}

// Stage 2: square
func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case <-ctx.Done(): return
            case out <- n * n:
            }
        }
    }()
    return out
}

// Compose
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
for v := range square(ctx, gen(ctx, 1, 2, 3, 4)) {
    fmt.Println(v)        // 1 4 9 16
}

The cancellation contract

Each stage:

  1. Closes its output channel when input closes (use defer close(out)).
  2. Selects on ctx.Done() for every send AND the input range (range cooperates because input close propagates).
  3. Returns when context is canceled — prevents goroutine leaks if downstream stops consuming.

When to use?

  • Stream processing — log enrichment, ETL, video frame processing.
  • Multi-step backend transformations: parse → validate → enrich → save.
  • When you want backpressure for free (channel capacity = buffer size).

Gotchas

1. If the consumer stops, all upstream stages leak unless they listen to ctx.Done(). Always wire context through.
2. Buffered stage channels mask backpressure. Useful for smoothing bursty stages, but avoid huge buffers — they hide bottlenecks and use memory.
3. Don't share state between stages. Each stage should be a pure-ish function: in-channel → out-channel. State = synchronization headaches.

Interview Q&A

Q: How do you stop a pipeline early (e.g., consumer found what it wanted)?

Cancel the context. Every stage selects on ctx.Done(), drains, and exits. Upstream's defer close(out) cascades.

09 Goroutine Leaks — the #1 production concurrency bug

A goroutine that never exits = memory leak, file-descriptor leak, eventually a crash. Top interview/incident topic.

Why this section?

Most Go production incidents involving slow leaks trace to goroutines waiting forever on a channel/lock that won't be released. You should know the patterns by heart.

The 5 most common leak patterns

1. Send on a channel with no receiver. 
ch := make(chan int)
go func() { ch <- work() }()   // blocks forever if main returns
// Fix: buffered channel OR add select with ctx.Done()
2. Receive from a channel that's never closed AND never sent to. 
go func() {
    for v := range ch {  // blocks forever if no one closes ch
        use(v)
    }
}()
3. Forgetting defer cancel() on context. The internal goroutine that fires the timer leaks until process exit.
4. HTTP body not closed. 
res, _ := http.Get(url)
// forgot defer res.Body.Close() — connection leaks, response goroutine waits
5. Ignoring context in long loops. 
for {
    doWork()    // no ctx check — this goroutine never exits
}
// Fix:
for {
    select {
    case <-ctx.Done(): return
    default:
        doWork()
    }
}

Detecting leaks

// In tests — uber-go/goleak
import "go.uber.org/goleak"
func TestMain(m *testing.M) {
    goleak.VerifyTestMain(m)
}

// In production — pprof
import _ "net/http/pprof"
go http.ListenAndServe(":6060", nil)
// curl localhost:6060/debug/pprof/goroutine?debug=2 → see all goroutine stacks

If runtime.NumGoroutine() climbs steadily under steady load, you have a leak. pprof goroutine shows where.

Reading pprof goroutine?debug=2 output: Each goroutine block looks like: 
goroutine 42 [chan receive, 17 minutes]:
main.worker(...)
        /app/main.go:88
created by main.handle
        /app/main.go:120
Key fields:
  • State in brackets: chan receive (waiting on channel), chan send, select, IO wait, semacquire (mutex), runnable.
  • Duration: minutes/hours = leak suspect.
  • Top frame: where it's stuck.
  • "created by": where it was spawned (your bug origin).
Group by stack trace — 1000 goroutines stuck at the same line = found it.

Always-do checklist for any goroutine you spawn

  1. What ends this goroutine? (close of channel, context cancel, return condition)
  2. Does every blocking operation have a ctx.Done() escape?
  3. Is there a single owner who'll close the channels it sends on?
  4. If using defer cancel(), is it called on every path?

Interview Q&A

Q: How do you detect goroutine leaks in CI?

uber-go/goleak in TestMain snapshots goroutines at start, compares at end, fails the test if extras remain.

Q: Production memory grows over time but no obvious heap leak. What's likely?

Goroutine leak. Each goroutine has a stack (~2KB to 8KB+). 100K leaked goroutines = ~1 GB. Check runtime.NumGoroutine and pprof goroutine profile.

Q: Can you have too many goroutines?

Yes. Goroutines are cheap, not free. Beyond a few hundred thousand, scheduler overhead and stack memory hurt. Bound concurrency with worker pools or semaphores.

10 Graceful Shutdown — production-critical pattern

Every Go service needs this. Without it, in-flight requests are killed mid-flight on deploy/restart.

Why this matters?

Kubernetes sends SIGTERM when scaling down or rolling out. Default Go behavior on signal: process exits immediately, killing all goroutines. That means: half-written DB rows, dropped HTTP responses, lost in-flight messages from queues.

Graceful shutdown means:

  1. Stop accepting NEW work (close listener / unsubscribe consumer).
  2. Let IN-FLIGHT work finish (with a timeout).
  3. Close resources cleanly (DB, files, message broker).
  4. Exit with code 0.

The standard pattern

package main

import (
    "context"
    "errors"
    "log/slog"
    "net/http"
    "os"
    "os/signal"
    "sync"
    "syscall"
    "time"
)

func main() {
    // 1. Root context wired to OS signals
    ctx, stop := signal.NotifyContext(context.Background(),
        syscall.SIGINT, syscall.SIGTERM)
    defer stop()
    // ↑ ctx is canceled on Ctrl-C or kubelet's SIGTERM

    srv := &http.Server{
        Addr:    ":8080",
        Handler: routes(),
    }

    // 2. Run server in a goroutine so main can wait on signals
    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        slog.Info("server starting", "addr", srv.Addr)
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            slog.Error("server crashed", "err", err)
            os.Exit(1)
        }
    }()

    // 3. Block until signal
    <-ctx.Done()
    slog.Info("shutdown signal received")

    // 4. Give in-flight requests up to 30s to finish
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    if err := srv.Shutdown(shutdownCtx); err != nil {
        slog.Error("forced shutdown", "err", err)
    }

    // 5. Wait for any background goroutines (workers, etc.)
    wg.Wait()

    // 6. Close downstream resources
    // db.Close(), redis.Close(), kafka.Close(), tracer.Shutdown(), etc.

    slog.Info("clean exit")
}

  SIGTERM ──▶ ctx canceled ──▶ srv.Shutdown(ctx, 30s)
                                  │
                                  ├─ stop accepting new conns
                                  ├─ wait for in-flight handlers
                                  └─ close idle connections
                                  
   Background workers also see ctx.Done() and exit ──▶ wg.Wait() returns
                                  │
                                  └──▶ close DB/Kafka/etc ──▶ os.Exit(0)

Worker shutdown — how the workers cooperate

func runWorker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            slog.Info("worker draining")
            // Optionally: drain remaining jobs in `jobs` if buffered
            return
        case j, ok := <-jobs:
            if !ok { return }
            process(ctx, j)
        }
    }
}

Common deployment scenarios

PlatformSignalDefault grace period
KubernetesSIGTERM30s (configurable via terminationGracePeriodSeconds)
Docker (docker stop)SIGTERM10s before SIGKILL
systemdSIGTERM90s default
AWS ECSSIGTERM30s default (configurable)
Match your shutdown timeout to the orchestrator's grace period. Too short = aborts. Too long = orchestrator SIGKILLs you anyway.

Gotchas

1. Don't ignore http.ErrServerClosed. A clean Shutdown returns that error from ListenAndServe — it's NORMAL, not a failure. Use errors.Is(err, http.ErrServerClosed) to skip it.
2. signal.Notify needs buffered channel. If you build the handler manually (instead of NotifyContext), use a buffered chan os.Signal of size 1 — otherwise the signal can be missed.
3. Closing the DB BEFORE workers finish causes their final queries to fail. Order: stop input → wait for in-flight → close downstream. Reverse the startup order.
4. Long-running requests vs grace period. If a request takes 5 minutes and your grace is 30s, it WILL be killed. Either shorten the request, increase grace, or stream progress so client can resume.
5. Health-check endpoints during shutdown. Once shutdown begins, your /healthz readiness probe should fail (return 503) so the load balancer stops sending NEW traffic. livenessProbe stays OK so K8s doesn't double-kill you.

Interview Q&A

Q: How do you handle a deploy with zero downtime?

Combination: (1) graceful shutdown so existing requests finish. (2) Readiness probe flips to "not ready" before SIGTERM (in K8s, the preStop hook can sleep a few seconds). (3) Multiple replicas behind a load balancer so traffic shifts to healthy pods. (4) Database connection draining.

Q: What's signal.NotifyContext vs signal.Notify?

NotifyContext (Go 1.16+) gives you a context that's canceled on signal — fits idiomatically with the rest of context-based code. Notify is the lower-level channel API; use only if you need custom signal handling logic.

Q: Why don't you call os.Exit() in graceful shutdown?

os.Exit bypasses deferred functions — your DB connections, Kafka producers, tracers won't flush. Just return from main and let the runtime exit cleanly. Only use os.Exit(1) for unrecoverable errors during STARTUP, before deferred cleanups are needed.
