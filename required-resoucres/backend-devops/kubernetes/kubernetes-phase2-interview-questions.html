1. Core Concepts

Q1. What is a Pod, and why doesn't Kubernetes just run containers directly? EASY

A Pod is the smallest deployable unit — one or more containers sharing a network namespace (same IP, can reach each other via localhost) and optionally storage. Kubernetes schedules/manages Pods, not raw containers, because it needs an atomic unit that can bundle tightly-coupled containers (e.g. app + sidecar) that must co-locate and share networking.

Q2. Why should you use a Deployment instead of creating a Pod directly? EASY

A bare Pod that dies is gone forever — nothing recreates it. A Deployment manages a ReplicaSet that continuously ensures the desired number of Pod replicas exist, and additionally provides rolling updates and rollback history that a raw Pod/ReplicaSet doesn't.

Q3. What's the relationship between Deployment, ReplicaSet, and Pod? MEDIUM

Deployment manages ReplicaSets (creating a new one on each rollout); ReplicaSet manages Pods (ensuring the replica count matches spec via its label selector). Deployment is the layer that adds versioned rollout/rollback behavior on top of ReplicaSet's simple "keep N Pods alive" job.

Q4. How does Kubernetes know which Pods belong to which Service/ReplicaSet? MEDIUM

Purely through labels and selectors — a Service/ReplicaSet has a label selector (e.g. app: di-jfrog), and any Pod carrying matching labels is automatically included, regardless of how it was created. There's no other linkage mechanism.

2. Services & Networking

Q5. ClusterIP vs NodePort vs LoadBalancer — differences and when to use each? MEDIUM

ClusterIP (default) is only reachable inside the cluster — used for internal service-to-service calls. NodePort exposes a fixed port on every node's IP — simple external access, common for local/dev clusters. LoadBalancer provisions an external cloud load balancer with its own IP — typical production external entrypoint (often still fronted by an Ingress for HTTP routing).

Q6. Why do Pod IPs matter less than you'd think in Kubernetes? MEDIUM

Because Pods are ephemeral and their IPs change every time they're recreated (e.g. after a crash or rollout). You never hardcode a Pod IP — you always talk to a Service's stable ClusterIP/DNS name, and the Service transparently load-balances to whichever Pods currently match its selector.

Q7. What is an Ingress, and why not just create many LoadBalancer Services? MEDIUM

Ingress is an HTTP(S) layer-7 routing rule (host/path-based) sitting in front of Services, letting you route many services through ONE external entrypoint (with TLS termination), instead of provisioning a separate expensive cloud LoadBalancer per service. Requires an Ingress Controller running in the cluster to actually implement the routing.

Q8. What is kube-dns/CoreDNS used for from an app developer's perspective? EASY

It lets your app reach other services by a stable DNS name (e.g. di-jfrog-svc or fully-qualified di-jfrog-svc.dash.svc.cluster.local) instead of an IP — resolving to the Service's ClusterIP, which then load-balances to healthy backing Pods.

3. ConfigMaps & Secrets

Q9. ConfigMap vs Secret — what's actually different under the hood? MEDIUM

Functionally similar (both can be consumed as env vars or mounted files), but Secrets are intended for sensitive data and are base64-encoded in etcd — NOT encrypted by default. Both are equally "insecure" at rest unless you enable etcd encryption-at-rest or use an external secrets manager (e.g. Vault).

Q10. Your app needs different DB connection strings in dev/staging/prod — how would you handle this in Kubernetes? MEDIUM

Keep the same container image across environments, and inject environment-specific values via a ConfigMap/Secret referenced in the Deployment spec (or, in a Helm-based setup like this workspace's, via per-environment values.yaml overlays that template the ConfigMap/env vars) — never bake environment-specific config into the image itself.

Q11. If you update a ConfigMap that's mounted as a volume, does the running Pod see the change automatically? HARD

If mounted as a volume, the file content eventually updates in the Pod (kubelet syncs it periodically) — but if consumed as environment variables (envFrom/valueFrom), the Pod does NOT pick up the change until it's restarted, since env vars are only read at container start.

4. Probes & Health

Q12. Liveness vs Readiness probe — what's the practical difference in what happens on failure? MEDIUM

A failing liveness probe causes Kubernetes to RESTART the container (it assumes the process is stuck/unrecoverable). A failing readiness probe only removes the Pod from the Service's routable endpoints — traffic stops going to it, but it is NOT restarted, since it might recover on its own (e.g. waiting on a dependency).

Q13. Why is it a bad idea to make your liveness probe check downstream dependencies (e.g. database connectivity)? HARD

If the database has a temporary outage, EVERY Pod's liveness probe would fail simultaneously, causing Kubernetes to restart all of them in a loop — worsening the outage instead of just quietly waiting it out. Downstream dependency checks belong in the READINESS probe (stop routing traffic) not liveness (restart the process).

Q14. What is a startup probe for, and when do you need one? MEDIUM

For slow-starting applications (e.g. large in-memory cache warm-up) — it delays liveness/readiness checks from running until the startup probe succeeds once, preventing Kubernetes from prematurely killing a Pod that's still legitimately starting up.

5. Deployments & Rollouts

Q15. How does a rolling update achieve zero-downtime deployment? MEDIUM

The Deployment creates a new ReplicaSet with the updated Pod template and gradually scales it up while scaling the old ReplicaSet down, governed by maxSurge (how many extra Pods above desired count are allowed) and maxUnavailable (how many Pods below desired count are tolerated). Crucially, a new Pod only starts receiving traffic once its READINESS probe passes — so a broken new version won't fully replace working old Pods before it's confirmed ready.

Q16. How do you roll back a bad deployment? EASY

kubectl rollout undo deployment/<name> reverts to the previous ReplicaSet revision. You can also target a specific revision with --to-revision=N, viewable via kubectl rollout history.

Q17. What's the difference between kubectl apply and kubectl create? EASY

create fails if the resource already exists. apply is declarative — it creates the resource if it doesn't exist, or computes/applies a diff to update it if it does, which is why apply is the standard way to manage resources via version-controlled YAML/Helm templates.

Q18. What causes a rollout to get "stuck" mid-way, and how would you notice it? HARD

kubectl rollout status deployment/<name> will hang/report not-progressing if new Pods never become Ready — typically because the new image is broken, a readiness probe never passes, or there aren't enough cluster resources to schedule the surge Pods. Check kubectl describe deployment and the new ReplicaSet's Pods directly.

6. Helm

Q18b. What's the difference between an Init Container and a regular container, and between a Job and a Deployment? MEDIUM

An Init Container runs to completion BEFORE the Pod's main container(s) start (e.g. wait for a dependency, run a migration) — if it fails, the main container never starts. A Job runs a Pod to completion ONCE for a batch/one-off task (retried on failure until success or a backoff limit), whereas a Deployment keeps its Pods running continuously and restarts/replaces them if they exit. A CronJob just creates Jobs on a schedule.

Q19. What problem does Helm solve that raw YAML manifests don't? MEDIUM

It templates Kubernetes YAML so the same chart can be parameterized per environment via values.yaml overrides (image tag, replica count, resource limits, env vars), instead of maintaining separate near-duplicate YAML files per environment. It also gives you release versioning, easy rollback (helm rollback), and dependency composition (subcharts into an umbrella chart).

Q20. What is an umbrella chart with subcharts, in practical terms? MEDIUM

A parent chart (e.g. this workspace's dash-chart) that declares other charts as dependencies (e.g. one subchart per microservice — di-jfrog, di-authorization, etc.), so a single helm install deploys the entire platform as one coordinated release, while each subchart still has its own independently maintained templates/values.

Q21. How would you debug what YAML Helm is actually going to apply before running helm install? MEDIUM

helm template ./chart -f values-override.yaml renders the final manifests locally without touching the cluster — the fastest way to verify your values actually produce the YAML you expect.

7. Scenario-Based / Debugging

Q22. Your Pod shows status Pending and never starts — what do you check? HARD

kubectl describe pod and read the Events section — most commonly insufficient CPU/memory across all nodes to satisfy the Pod's resource requests, or a node selector/affinity/taint rule that no node satisfies.

Q23. Your Pod is stuck in ImagePullBackOff — what are the likely causes? MEDIUM

Wrong image name or tag (typo, or the tag was never pushed), missing/incorrect imagePullSecrets for a private registry (e.g. the JFrog Artifactory registry used across this workspace's services), or the registry being unreachable from the cluster's network.

Q24. Your Pod is in CrashLoopBackOff — walk through how you'd debug it. HARD

First kubectl logs <pod> --previous to see the crashed instance's actual error (the current instance may have just restarted with no logs yet). Then kubectl describe pod to check exit code/reason (e.g. OOMKilled) and recent Events. If needed, temporarily override the container's command to drop into a shell for manual investigation.

Q25. A Pod is Running and healthy, but the Service never routes traffic to it — what's wrong? HARD

Two likely causes: (1) the readiness probe is failing, so the Pod is excluded from the Service's endpoints even though it's "Running" — check kubectl describe pod Conditions; (2) the Service's label selector doesn't actually match the Pod's labels — check with kubectl get endpoints <svc> (empty means no match).

Q26. After a rollout, users intermittently get errors for the first few seconds — what's the likely misconfiguration? HARD

The readiness probe isn't strict/accurate enough — it's marking the new Pod "ready" before it can truly serve traffic (e.g. before a DB connection pool or cache warms up), so the rolling update routes real traffic to a Pod that isn't fully ready. Fix by making the readiness check reflect true application readiness and/or tuning initialDelaySeconds/periodSeconds.

Q27. How would you safely test a config change (e.g. a new env var) without risking the whole production Deployment? MEDIUM

Apply the change to a staging/dev namespace or a separate Helm values override first (e.g. this workspace's env-config/onprem-dev vs env-config/shared-prod), verify via kubectl logs/health checks, then promote the same change to production values once verified — never edit production values directly as a first test.

Q28. What's the difference between scaling a Deployment (kubectl scale) and a Horizontal Pod Autoscaler (HPA)? MEDIUM

kubectl scale sets a fixed, manual replica count. An HPA automatically adjusts the replica count within a min/max range based on observed metrics (commonly CPU/memory utilization, or custom metrics) — useful when load is variable and you don't want to manually scale up/down.
