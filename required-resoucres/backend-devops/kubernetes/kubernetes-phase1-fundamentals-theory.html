1. Why Kubernetes? (The Orchestration Problem)

EASY

Docker runs one container on one host. Once you have many services (this workspace has 20+ DI microservices) across many hosts, you need something to answer:

  • Which host should this container run on? (scheduling)
  • What happens if the host or container dies? (self-healing)
  • How do I run 5 copies for load, and route traffic across them? (scaling + service discovery)
  • How do I roll out a new version without downtime? (rolling updates)
  • How do I configure the same image differently per environment? (ConfigMaps/Secrets/Helm values)

Kubernetes answers all of these declaratively — you describe the desired state (e.g. "run 3 replicas of this image"), and Kubernetes continuously works to make reality match it.

2. Core Building Blocks: Cluster, Node, Pod

EASY
ObjectWhat it is
ClusterA set of machines (nodes) managed as one unit by Kubernetes.
NodeA single machine (VM or physical) in the cluster that runs Pods.
PodThe smallest deployable unit — one or more containers that always run together on the same node, sharing network namespace (same IP/localhost) and optionally volumes. Usually one container per Pod for a backend service, with a "sidecar" container as the common multi-container case.
# A minimal Pod spec for a Go backend service
apiVersion: v1
kind: Pod
metadata:
  name: di-jfrog-pod
  labels:
    app: di-jfrog
spec:
  containers:
    - name: di-jfrog
      image: kyndryl.jfrog.io/ibmcb-docker-local/dash/portal_jfrog_app:1.0.0
      ports:
        - containerPort: 8080
Interview point: You almost never create a bare Pod directly in production — you create a Deployment (next section), which creates and manages Pods for you (self-healing, scaling, rolling updates). A bare Pod that dies is gone forever; a Deployment notices and creates a replacement.

3. Deployment & ReplicaSet

MEDIUM

ReplicaSet — ensures a specified number of identical Pod replicas are always running (creates new ones if one dies, kills extras if there are too many). Deployment — a higher-level object that manages ReplicaSets for you, and is what enables rolling updates and rollbacks. You almost always write a Deployment, never a raw ReplicaSet.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: di-jfrog
spec:
  replicas: 3
  selector:
    matchLabels:
      app: di-jfrog
  template:
    metadata:
      labels:
        app: di-jfrog
    spec:
      containers:
        - name: di-jfrog
          image: kyndryl.jfrog.io/ibmcb-docker-local/dash/portal_jfrog_app:1.0.0
          ports:
            - containerPort: 8080
How it self-heals: Deployment → creates a ReplicaSet → ReplicaSet's job is only "make sure N Pods matching this label selector exist." If a Pod crashes or its node dies, the ReplicaSet controller notices the count dropped below 3 and creates a new Pod immediately — no human intervention needed.

4. Services: ClusterIP, NodePort, LoadBalancer

MEDIUM

Pods are ephemeral — their IPs change every time they're recreated. A Service gives a stable virtual IP + DNS name that automatically load-balances across all currently-matching Pods (matched via label selector, same mechanism as Deployment).

TypeReachable fromTypical use
ClusterIP (default)Only inside the clusterInternal service-to-service calls (e.g. di-application-manager calling di-authorization).
NodePortAny node's IP, on a fixed high port (30000-32767)Simple external access without a cloud load balancer (common in local/dev clusters).
LoadBalancerAn external IP provisioned by the cloud providerProduction external entrypoint (usually still fronted by an Ingress in practice).
apiVersion: v1
kind: Service
metadata:
  name: di-jfrog-svc
spec:
  selector:
    app: di-jfrog
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP
Interview point: Other Pods reach this Service simply via DNS name di-jfrog-svc (or di-jfrog-svc.namespace.svc.cluster.local fully-qualified) — Kubernetes' internal DNS resolves it to the Service's stable ClusterIP, which then load-balances to one of the healthy backing Pods. This is analogous to how Compose gives you name-based DNS between containers, but cluster-wide and load-balanced.

5. Ingress (Routing HTTP Traffic)

MEDIUM

An Ingress is an HTTP(S) routing layer sitting in front of Services — path/host-based routing, TLS termination, all through one external entrypoint instead of provisioning a LoadBalancer per service. This matches this workspace's dash-chart/templates/ingress.yaml, which is a single unified Ingress routing to all 20+ DI microservices by path (e.g. /api/jfrog/ → di-jfrog Service, /api/authorization/ → di-authorization Service).

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: dash-ingress
spec:
  rules:
    - host: dash.example.kyndryl.com
      http:
        paths:
          - path: /api/jfrog
            pathType: Prefix
            backend:
              service:
                name: di-jfrog-svc
                port:
                  number: 80
          - path: /api/authorization
            pathType: Prefix
            backend:
              service:
                name: di-authorization-svc
                port:
                  number: 80
Requires an Ingress Controller: The Ingress object itself is just a routing rule — an Ingress Controller (e.g. NGINX Ingress Controller) must actually be running in the cluster to read these rules and do the routing. Note this workspace's umbrella chart uses its OWN NGINX reverse proxy templates (dash-chart/templates/nginx/) rather than relying purely on a cluster Ingress Controller in some deployment modes.

6. ConfigMaps & Secrets

MEDIUM

Same purpose as Docker env vars/mounted config files, but cluster-native and decoupled from the container image so the same image can be deployed with different config per environment (dev/staging/prod) — exactly what bdg-sw-devx-di-deploy/deployments/env-config/ overlays are for.

ConfigMapSecret
PurposeNon-sensitive config (feature flags, URLs, JSON config)Sensitive data (passwords, tokens, TLS certs)
StoragePlain text in etcdBase64-encoded in etcd (NOT encrypted by default!)
ConsumptionEnv var or mounted file (matches MOUNT_PATH pattern used in this workspace's do_build.sh per-service settings)Env var or mounted file, same mechanisms as ConfigMap
# Mounting a ConfigMap as environment variables
envFrom:
  - configMapRef:
      name: di-jfrog-config

# Mounting a Secret as a file (common for config.json / certs)
volumes:
  - name: jfrog-secret-vol
    secret:
      secretName: di-jfrog-secret
containers:
  - name: di-jfrog
    volumeMounts:
      - name: jfrog-secret-vol
        mountPath: /etc/secrets
        readOnly: true
Common interview trap: "Are Kubernetes Secrets actually secure/encrypted?" — By default, no. They're only base64-encoded (trivially reversible, NOT encryption) at rest in etcd unless you explicitly enable encryption-at-rest or use an external secrets manager (e.g. Vault — this workspace's dash-chart/templates/_extsecrets.tpl integrates with exactly this kind of external secrets pattern).

7. Probes: Liveness, Readiness, Startup

HARD

This is one of the most important — and most commonly misunderstood — things a backend engineer must configure correctly for their own service.

ProbeQuestion it answersOn failure
Liveness"Is this process healthy, or stuck/deadlocked?"Kubernetes restarts the container.
Readiness"Is this Pod ready to receive traffic right now?"Kubernetes removes it from the Service's endpoints (stops routing traffic to it) — does NOT restart it.
Startup"Has this slow-starting app finished initializing yet?"Blocks liveness/readiness checks from running (and killing a slow-starting container) until startup succeeds once.
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 15
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
Real-world bug this explains: A service temporarily can't reach its database (e.g. Mongo restarting) — if you only define a liveness probe hitting /health which checks DB connectivity, Kubernetes will keep RESTARTING the app in a loop (making the outage worse), when what you actually want is for readiness to fail (temporarily stop routing traffic) while liveness stays healthy (the process itself is fine, just waiting on a dependency) — the app should recover once the DB is back, without needless restarts.

8. Resource Requests & Limits

MEDIUM 
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
  • requests — what the scheduler guarantees/reserves for this Pod when deciding which node to place it on. Under-setting this risks the Pod landing on an already-busy node.
  • limits — the hard ceiling. Exceeding the memory limit gets the container OOMKilled (same 137 exit code as Docker). Exceeding the CPU limit just throttles it (doesn't kill it).
Interview point: "What happens if you don't set resource requests/limits at all?" — The Pod is treated as "BestEffort" QoS class — it can use as much as is available on the node, but it's the FIRST to be evicted under node memory pressure, which is dangerous for production services with unpredictable traffic.

9. Rolling Updates & Rollbacks

MEDIUM 
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1        # can create 1 extra Pod above desired count during rollout
    maxUnavailable: 0  # never go below desired count → zero-downtime rollout
kubectl set image deployment/di-jfrog di-jfrog=...:1.1.0   # trigger a rollout
kubectl rollout status deployment/di-jfrog                  # watch progress
kubectl rollout undo deployment/di-jfrog                    # rollback to previous revision
kubectl rollout history deployment/di-jfrog                 # see revision history

How it actually works: the Deployment creates a NEW ReplicaSet (new Pod template with the new image), gradually scales it up while scaling the OLD ReplicaSet down, respecting maxSurge/maxUnavailable and readiness probes at each step — a new Pod isn't considered "up" until its readiness probe passes, so a broken new version won't fully replace working old Pods.

10. Namespaces & Labels/Selectors

EASY
  • Namespace — a logical partition within a cluster (e.g. dash namespace used by this workspace's umbrella chart) for isolating resources, RBAC, and resource quotas per team/environment.
  • Labels — arbitrary key-value tags on objects (e.g. app: di-jfrog).
  • Selectors — how Services/Deployments/ReplicaSets find the Pods they should manage or route to, by matching labels. This is the ENTIRE mechanism connecting a Service to its Pods — there's no other link.

11. Init Containers & Jobs/CronJobs

MEDIUM

Two patterns backend engineers run into constantly but that don't fit the "long-running Deployment" model:

ObjectPurpose
Init ContainerRuns and must complete SUCCESSFULLY before the Pod's main container(s) start. Common use: run a DB migration, wait for a dependency to be reachable, or fetch a config file — all before the app itself boots.
JobRuns a Pod to completion once (not continuously) — for one-off/batch tasks (e.g. a data backfill script). Kubernetes retries it if it fails, until it succeeds or hits a backoff limit.
CronJobCreates a Job on a cron schedule — e.g. a nightly cleanup task or a periodic report generator.
# Init container example — wait for Mongo to be reachable before the app starts
spec:
  initContainers:
    - name: wait-for-mongo
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z mongo 27017; do sleep 2; done']
  containers:
    - name: di-jfrog
      image: kyndryl.jfrog.io/ibmcb-docker-local/dash/portal_jfrog_app:1.0.0
apiVersion: batch/v1
kind: CronJob
metadata:
  name: di-jfrog-history-cleanup
spec:
  schedule: "0 2 * * *"   # every day at 02:00
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: cleanup
              image: kyndryl.jfrog.io/ibmcb-docker-local/dash/portal_jfrog_app:1.0.0
              command: ["./main", "--cleanup-history"]
          restartPolicy: OnFailure
Interview point: An Init Container failing blocks the Pod from ever starting its main containers (Pod stays in Init:Error/Init:CrashLoopBackOff status) — this is a distinct failure mode from the main container crashing, and is a common thing to check first if a Pod "never even starts."

12. Helm Basics

MEDIUM

Helm is a package manager for Kubernetes YAML — instead of hand-writing/duplicating YAML per environment, you template it. This workspace's bdg-sw-devx-di-deploy/dash-chart is exactly this: one umbrella chart composing 20+ subcharts (one per microservice, e.g. di-jfrog, di-authorization), with per-customer value overlays in env-config/.

ConceptPurpose
Chart.yamlChart metadata: name, version, appVersion, dependencies (subcharts).
values.yamlDefault configuration values (image repo/tag, replica count, resources, env vars) — this is what's overridden per environment.
templates/YAML manifests with Go templating ({{ .Values.xyz }}) that get rendered using values.yaml.
SubchartA nested chart (e.g. di-jfrog/ under deployments/charts/) — a microservice's own Deployment/Service/ConfigMap templates, composed into the umbrella chart.
helm install dash ./dash-chart -f env-config/shared-prod/values.yaml
helm upgrade dash ./dash-chart -f env-config/shared-prod/values.yaml
helm rollback dash 3          # roll back to revision 3
helm template ./dash-chart    # render final YAML locally without installing (great for debugging)
helm get values dash          # see the values actually in use for a release
As a backend/full-stack dev, you mostly need to: understand how your service's own values.yaml (image repo/tag, env vars, resources, replica count) maps into the rendered Deployment/Service — not necessarily author brand-new charts from scratch.

13. Daily-Driver kubectl Commands

EASY 
kubectl get pods                         # list Pods in current namespace
kubectl get pods -n dash                 # list Pods in a specific namespace
kubectl describe pod di-jfrog-abc123      # detailed status + recent Events (great for debugging)
kubectl logs -f di-jfrog-abc123           # tail logs
kubectl logs di-jfrog-abc123 --previous   # logs from the PREVIOUS (crashed) instance of the container
kubectl exec -it di-jfrog-abc123 -- sh    # shell into a running Pod
kubectl port-forward svc/di-jfrog-svc 8080:80   # tunnel a cluster Service to your local machine
kubectl apply -f deployment.yaml         # create/update from a manifest
kubectl delete pod di-jfrog-abc123        # delete a Pod (ReplicaSet will recreate it if managed)
kubectl get events --sort-by='.lastTimestamp'   # cluster-wide recent events, newest last

14. Debugging a Broken Pod — Playbook

HARD
  1. Check Pod status first: kubectl get pods — look at STATUS and RESTARTS columns.
  2. Pending — Pod hasn't been scheduled yet. Run kubectl describe pod and check Events — usually insufficient CPU/memory on any node, or an unsatisfied node selector/affinity rule.
  3. ImagePullBackOff / ErrImagePull — wrong image name/tag, private registry auth missing, or registry unreachable. Check imagePullSecrets and the exact image string.
  4. CrashLoopBackOff — the container starts then exits repeatedly. Check kubectl logs <pod> --previous (the crashed instance's logs, since the CURRENT instance may have just restarted with nothing logged yet).
  5. OOMKilled (visible in kubectl describe pod under "Last State") — container exceeded its memory limit. Either raise the limit or find/fix the memory leak.
  6. Pod is Running but Service isn't routing to it — check the readiness probe is passing (kubectl describe pod → Conditions → Ready), and that the Service's label selector actually matches the Pod's labels (kubectl get endpoints <svc-name> — empty endpoints means no Pod currently matches).
  7. Config/env var looks wrong at runtime — kubectl exec in and run env, or kubectl describe pod to confirm which ConfigMap/Secret is actually mounted, and diff against what you expect from the Helm values for that environment.
Classic scenario asked in interviews: "Your service deploys fine but users get 502s intermittently right after a rollout." — Likely cause: readiness probe isn't strict enough (marks Pod ready before the app can truly serve traffic, e.g. before a DB connection pool warms up), so the rolling update routes traffic to a Pod that isn't actually ready yet. Fix: tighten the readiness check to reflect true readiness (e.g. verify DB connectivity), and/or increase initialDelaySeconds.
