1. Why Containers? (VM vs Container)

EASY

1.0 What is an Operating System & a Kernel? (the piece everything else builds on)

Your laptop's Operating System (macOS, Windows, Linux) is the software layer that sits between physical hardware (CPU, RAM, disk, network card) and every application you run. The kernel is the core of that OS — the part with direct, privileged access to hardware. It decides which process gets CPU time next (scheduling), hands out chunks of memory to programs, and mediates every disk/network operation. Every single program on your machine — a text editor, a browser, docker itself — ultimately makes requests ("system calls") to this one kernel. This matters because both VMs and containers exist to solve the same underlying problem — "how do I run multiple isolated things on one physical machine without them interfering with each other" — but they solve it at two very different layers, which is the whole reason interviewers ask about it.

1.1 What is a Virtual Machine (VM)?

A Virtual Machine is a piece of software (running on top of a program called a hypervisor, e.g. VMware, VirtualBox, or the hypervisor built into macOS/Windows) that pretends to be an entire physical computer. It emulates virtual hardware — a virtual CPU, virtual RAM, a virtual disk, a virtual network card — and then a complete, independent guest Operating System (with its own separate kernel) is installed and booted inside that virtual hardware, exactly as if it were a real machine.

  • Hypervisor — the software that creates and manages VMs. Type 1 (bare-metal, e.g. VMware ESXi, runs directly on hardware — used in data centers/cloud) vs Type 2 (hosted, e.g. VirtualBox/Parallels, runs as an app on top of your existing OS — used on laptops).
  • Guest OS — the full operating system installed inside the VM. If your host is macOS and you spin up a VM, that VM can run a completely different OS (e.g. full Ubuntu Linux) with its own kernel, its own drivers, its own entire filesystem — the host and guest kernels do not share anything.
  • Why it's heavy — booting a VM means booting an entire second operating system from scratch (kernel init, drivers, system services) before your actual application even starts. That's why VMs take minutes to boot and consume gigabytes of disk just for the guest OS, before your app's code takes a single byte.
  • Why it's very strongly isolated — because the isolation boundary is virtual hardware, a VM has no more visibility into another VM (or the host) than a real physical computer would have into the computer sitting next to it on a desk. This is why VMs are still used when you need to run genuinely different/untrusted OSes on the same physical hardware, or need the strongest possible isolation guarantee (e.g. multi-tenant cloud infrastructure, where AWS/Azure/GCP use VMs to isolate different customers from each other at the hardware level).

1.2 What is a Container?

A Container takes a completely different approach: instead of emulating hardware and booting a second kernel, it runs as an isolated process (or group of processes) directly on the host's existing kernel — there is no guest OS, no second kernel, no virtual hardware. The "isolation" a container has is an illusion created by the host Linux kernel itself, using two built-in kernel features:

  • Namespaces — give a process its own view of the system, even though it's running on the same shared kernel as everything else. A process in a PID namespace thinks it's PID 1 on a brand-new machine, even though the host sees it as just another regular process among hundreds. Docker uses PID (process IDs), NET (network interfaces/ports), MNT (filesystem mounts), UTS (hostname), IPC (inter-process communication), and USER (user/group IDs) namespaces to give each container this illusion of "being its own machine."
  • cgroups (control groups) — limit and account for how much CPU, memory, disk I/O, etc. a process (or group of processes) is allowed to consume, so one container can't starve the others of resources on the shared host.
  • Union/overlay filesystem — stacks read-only image layers with one thin writable layer on top, so the container sees what looks like its own private, complete filesystem, without actually copying the whole OS filesystem per container.

Because there's no second kernel to boot and no hardware to emulate — a container is "born" simply by the host kernel setting up these namespaces/cgroups around a process and starting it — containers start in milliseconds and only need to ship the extra files your app actually needs (often tens of MBs), not an entire OS.

One-sentence summary to say out loud in an interview: "A VM virtualizes hardware and boots a full second OS/kernel per VM; a container virtualizes the OS — all containers share one host kernel, and Linux namespaces + cgroups create the illusion of isolation without the cost of booting a separate kernel."

2. Image vs Container vs Registry

EASY
  • Image — a read-only, immutable template (layered filesystem + metadata like default CMD/ENV). Built once from a Dockerfile.
  • Container — a running (or stopped) instance of an image, with its own writable layer on top and its own process namespace. You can run many containers from one image.
  • Registry — where images are stored/versioned/pulled from (Docker Hub, or in this workspace's case, the internal Kyndryl JFrog Artifactory Docker registry — see AFAAS_DOCKER_REGISTRY used by bdg-sw-devx-di-jfrog's build).
# Image → Container relationship
docker build -t di-jfrog:local .        # builds an IMAGE from a Dockerfile
docker run -d --name jfrog1 di-jfrog:local   # creates + starts a CONTAINER from that image
docker run -d --name jfrog2 di-jfrog:local   # a SECOND, independent container, same image
docker images                            # list images (templates)
docker ps -a                             # list containers (running instances)
Analogy interviewers like: Image = class, Container = object/instance. You compile a class once; you can instantiate it many times, each with independent state.

3. Anatomy of a Dockerfile

MEDIUM

3.0 What is a Dockerfile, actually?

A Dockerfile is just a plain text file (no extension, literally named Dockerfile) containing a list of step-by-step instructions for how to assemble an image — think of it as a recipe. Each line is one instruction (FROM, RUN, COPY, etc.), and when you run docker build, Docker executes these instructions in order, one at a time, top to bottom, and commits the filesystem result of each instruction as a new, cacheable layer stacked on top of the previous one. The final image is just the sum of all those layers. You write a Dockerfile once per service (usually committed alongside the source code); anyone can then run docker build against it to reproduce the exact same image, on any machine, without manually installing anything themselves.

A minimal but realistic Dockerfile for a Go backend service (matches the shape of bdg-sw-devx-di-jfrog / bdg-sw-devx-di-application-manager in this workspace):

FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o main .

FROM alpine:3.19
RUN adduser -D -u 1000 appuser
WORKDIR /app
COPY --from=builder /app/main .
COPY config.json .
USER appuser
EXPOSE 8080
ENTRYPOINT ["./main"]
InstructionPurpose
FROMBase image to start from (alpine = small, distroless = smaller/no shell, slim = fewer OS packages).
WORKDIRSets the working directory for subsequent instructions (and the container's default CWD).
COPYCopies files from the build context into the image.
RUNExecutes a command at build time and commits the result as a new layer (e.g. installing deps, compiling).
ENVSets environment variables baked into the image (visible at both build & run time).
ARGBuild-time-only variable (not present in the final running container unless also set via ENV).
EXPOSEDocuments which port the app listens on (does NOT actually publish it — that's -p at docker run).
USERSwitches to a non-root user for the remaining instructions/runtime (security best practice).
CMD / ENTRYPOINTDefines the default process the container runs (see next section).

4. CMD vs ENTRYPOINT vs RUN

MEDIUM

This is one of the most commonly asked Docker questions in backend interviews.

RUNCMDENTRYPOINT
When it executesBuild timeContainer start (as default)Container start (always)
Overridable?N/AYes — fully replaced by docker run image <args>No (args passed become arguments to it, unless --entrypoint is used)
Typical useInstall deps, compileDefault command/argsFixed executable that should always run
# CMD only — fully replaceable
CMD ["./main", "--port=8080"]
$ docker run myimg                 # runs: ./main --port=8080
$ docker run myimg ./main --port=9090   # CMD fully overridden

# ENTRYPOINT + CMD combo (most flexible, most common in real Dockerfiles)
ENTRYPOINT ["./main"]
CMD ["--port=8080"]                # default args, CAN be overridden
$ docker run myimg                 # runs: ./main --port=8080
$ docker run myimg --port=9090     # runs: ./main --port=9090 (only CMD part replaced)
Quick answer for interviews: "ENTRYPOINT defines the fixed executable; CMD defines default arguments to it that a caller can override at docker run. Using both together is the recommended pattern for a service that should always run the same binary but allow flag overrides."

5. Multi-Stage Builds

MEDIUM

Multi-stage builds let you use a heavy "build" image (with compilers/toolchains) and copy only the final artifact into a slim "runtime" image — dramatically reducing final image size and attack surface.

Go example (compiled binary, no runtime needed)

FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN go build -o /out/app .

FROM gcr.io/distroless/static-debian12
COPY --from=builder /out/app /app
ENTRYPOINT ["/app"]
# Final image: just the binary + distroless base — often < 20MB, no shell, no package manager

Node/Angular example (matches bdg-sw-devx-di-web-component build)

FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=builder /app/dist/mcmp-devops-overview-ui /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
# Final image: only compiled static assets + nginx — the entire node_modules/toolchain is discarded
Why interviewers ask this: It tests whether you understand that each FROM starts a fresh stage, that only COPY --from=<stage> artifacts survive into later stages, and that this is the standard way to keep production images small and secure (no compiler/toolchain shipped to prod).

6. Layer Caching & .dockerignore

MEDIUM

Each Dockerfile instruction creates a cacheable layer. Docker reuses a cached layer if the instruction AND all previous layers are unchanged. This is why dependency installation is ordered before copying full source code:

# GOOD — deps only reinstall when go.mod/go.sum actually change
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN go build -o main .

# BAD — any source change invalidates the cached "go mod download" layer too,
# forcing a full re-download on every single code edit
COPY . .
RUN go mod download
RUN go build -o main .

.dockerignore excludes files from the build context (sent to the Docker daemon before building) — same purpose as .gitignore but for builds:

.git
node_modules
dist
*.log
.env
coverage/
Interview point: A large/irrelevant build context (e.g. forgetting to exclude node_modules or .git) slows every build even if those files aren't referenced, because Docker has to transfer the whole context to the build daemon first.

7. Volumes vs Bind Mounts vs tmpfs

MEDIUM
TypeManaged byUse case
VolumeDocker (stored under /var/lib/docker/volumes)Persistent app data (e.g. a local MongoDB's data dir) — survives container removal, portable, backup-friendly.
Bind mountYou (any host path)Local development — mount your source code into the container for live-reload; mount config files from host.
tmpfsHost RAM onlySensitive temp data that should never touch disk (e.g. short-lived secrets).
# Named volume — Docker manages storage, persists across container recreation
docker run -v jfrog-mongo-data:/data/db mongo:7

# Bind mount — your local source tree lives inside the container (dev mode)
docker run -v $(pwd):/app -w /app node:20 npm start

# tmpfs — RAM-only, gone when container stops
docker run --tmpfs /run node:20
Key fact: A container's own writable layer is deleted when the container is removed (docker rm). Anything you need to keep MUST live in a volume or bind mount — this is the #1 reason a "works on my machine, lost my data after restart" bug happens.

8. Container Networking Basics

MEDIUM

8.0 Quick refresher: IP address, port, and NAT

Before container-specific networking makes sense, three plain networking terms are worth being precise about: an IP address identifies a machine (or, inside Docker, a container) on a network. A port is a number (0–65535) that lets many different services run on the same IP address without colliding — e.g. a web server on port 80 and a database on port 5432 can both run on the same machine's IP. NAT (Network Address Translation) is the technique your home router (and Docker's bridge network) uses to let many private, internal IP addresses share one public-facing IP — it rewrites packets on the way in/out so the outside world only ever sees one address, while internally traffic gets routed to the right container/device.

Docker gives every container its own private IP address on a virtual network, isolated from your host's real network by default, which is why you explicitly need -p host:container to make a container's port reachable from outside — without it, the container is only reachable from other containers on the same Docker network.

  • bridge (default) — containers get a private IP on a virtual bridge network; reach the outside world via NAT; reach each other by name only if on the same user-defined bridge network (default bridge does NOT support name-based DNS — user-defined ones do).
  • host — container shares the host's network namespace directly (no port mapping needed, but no isolation).
  • none — no networking at all.
# Publish a port: host_port:container_port
docker run -p 8080:80 nginx
# Now http://localhost:8080 on your machine reaches port 80 INSIDE the container

# User-defined network — enables container-to-container DNS by name
docker network create di-net
docker run --network di-net --name mongo mongo:7
docker run --network di-net --name jfrog-svc di-jfrog:local
# Inside jfrog-svc, connecting to "mongo:27017" resolves via Docker's embedded DNS
Interview trap: "Can two containers on the default bridge network talk to each other by container name?" — No (only by IP). Only user-defined bridge networks (or Compose, which creates one automatically) provide automatic DNS resolution by service/container name. This is exactly why Compose files just work with hostnames like mongo or redis.

9. Docker Compose for Local Dev

MEDIUM

Compose is the standard way a backend/full-stack dev spins up a service + its dependencies (DB, cache) locally with one command. Example modeled on this workspace's di-jfrog (Go + MongoDB):

version: "3.9"
services:
  jfrog-service:
    build: .
    ports:
      - "8080:8080"
    environment:
      - DATABASE_URL=mongodb://mongo:27017/jfrog
      - AFAAS_URL=https://artifactory.internal.kyndryl.com
    depends_on:
      - mongo
    volumes:
      - ./config.json:/app/config.json:ro

  mongo:
    image: mongo:7
    ports:
      - "27017:27017"
    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
docker compose up -d          # build (if needed) + start all services in background
docker compose logs -f jfrog-service   # tail logs of one service
docker compose down           # stop and remove containers (add -v to also remove volumes)
docker compose ps             # list running services in this project
Interview trap — depends_on is NOT a readiness check. It only guarantees Mongo's container starts before the app container starts — not that Mongo is actually accepting connections yet. Real apps handle this with retry/backoff connection logic in code, or a healthcheck: + condition: service_healthy in Compose.

10. Environment Variables & Secrets

EASY
  • ENV in a Dockerfile — baked into the image, visible via docker inspect. Never put real secrets here (they end up in the image layer history, readable by anyone with image access).
  • docker run -e KEY=value or Compose environment: — injected at container start, not baked into the image.
  • --env-file .env — loads many vars from a file (keep .env in .gitignore and .dockerignore).
  • Docker secrets / mounted secret files — for anything sensitive (API tokens, DB passwords), mount as a file (e.g. into /run/secrets/) rather than an env var where possible, since env vars are visible to any process in the container and can leak into logs/crash dumps more easily.
Ties back to this workspace: bdg-sw-devx-di-jfrog's build docs reference ARTIFACTORY_PASS, INIT_USER etc. as required environment variables for the build step — exactly the "inject at runtime, never bake into the image" pattern.

12. Daily-Driver CLI Commands

EASY 
docker build -t myapp:dev .              # build image from Dockerfile in current dir
docker run -d -p 8080:8080 --name app myapp:dev   # run detached, map port, name it
docker ps                                # list running containers
docker ps -a                             # include stopped containers
docker logs -f app                       # tail logs (follow)
docker exec -it app sh                   # shell into a running container
docker inspect app                       # full JSON metadata (env vars, mounts, network, etc.)
docker stop app && docker rm app         # stop then remove
docker system prune -a                   # remove all unused images/containers/networks (careful!)
docker cp app:/app/config.json ./local.json   # copy a file out of a container

13. Debugging a Broken Container — Playbook

HARD

This is the single most common real-world/interview scenario: "your container keeps exiting / won't start — what do you check?"

  1. Check exit code first: docker ps -a shows the last exit code. 0 = clean exit (often means your process finished immediately — e.g. CMD was wrong and returned right away). 137 = SIGKILL (often OOM-killed — check memory limits). 1/other = app-level crash.
  2. Read the logs: docker logs app — most crashes print a stack trace or config error here.
  3. Check if it's even trying to run the right command: docker inspect app --format '{{.Config.Cmd}} {{.Config.Entrypoint}}'.
  4. Get a shell in a similar (fresh) container to poke around: docker run -it --entrypoint sh myapp:dev (bypasses the normal ENTRYPOINT so you land in a shell instead of immediately crashing again).
  5. Check environment variables actually present: docker exec app env (only works if the container is still running — if it keeps crash-looping, use step 4 instead).
  6. Check port/network binding: is the app listening on 0.0.0.0 inside the container (not 127.0.0.1, which is invisible from outside the container even with -p mapped)?
  7. Check volume/file permissions: especially if you added a non-root USER — a common failure is the app can't write to a mounted directory owned by a different UID.
Classic gotcha asked in interviews: "My container exits immediately with code 0 even though my app should run forever." — Usually the process listens on localhost only, or the main process is a shell script that itself exits after spawning a background process (PID 1 must be the actual long-running process, or use something like tini/exec to hand off signals correctly).
