1. Core Concepts

Q1. What is the difference between an image and a container? EASY

An image is an immutable, read-only template (layered filesystem + metadata). A container is a running instance of an image with its own writable layer and process namespace. One image → many independent containers.

Q2. Is Docker a lightweight VM? EASY

No. Containers share the host kernel and are isolated via Linux namespaces (PID/NET/MNT/etc.) and cgroups (resource limits) — there's no separate guest kernel like a VM has, which is why containers start in milliseconds and are much smaller.

Q3. What happens to the container's filesystem when it stops vs when it's removed? MEDIUM

Stopping preserves the container and its writable layer (you can restart it, data is still there). Removing (docker rm) deletes the writable layer permanently — any data not in a volume/bind mount is gone.

Q4. What is the union/overlay filesystem and why does Docker use it? MEDIUM

It stacks multiple read-only image layers plus one writable container layer on top, presenting them as a single merged filesystem view. This lets images share common base layers (saving disk/network) while each container still sees an independent writable surface (copy-on-write).

2. Dockerfile & Images

Q5. CMD vs ENTRYPOINT — what's the difference and when would you use both together? MEDIUM

ENTRYPOINT is the fixed executable that always runs; CMD supplies default arguments that a caller CAN override at docker run. Using both (ENTRYPOINT ["./main"] + CMD ["--port=8080"]) gives you a fixed binary with overridable default flags — the most common real-world pattern.

Q6. COPY vs ADD — which should you prefer and why? EASY

Prefer COPY for local files — it's explicit and predictable. ADD has "magic" behavior (auto-extracts tar archives, can fetch remote URLs) that makes builds less predictable and is a common source of bugs/security issues; only use ADD when you specifically need its extraction behavior.

Q7. What is a multi-stage build and why use it? MEDIUM

It lets you use a heavy "builder" stage (with compilers/toolchain) to produce an artifact, then COPY only that artifact into a slim final stage. Result: smaller final image, no build tools/source code shipped to production, smaller attack surface.

Q8. How does Docker layer caching work, and how do you write a Dockerfile to take advantage of it? MEDIUM

Each instruction produces a layer; if an instruction and everything before it is unchanged (same instruction text + same input files' checksums), Docker reuses the cached layer instead of re-executing. Order instructions from least-frequently-changing to most-frequently-changing — e.g. copy package.json/go.mod and install deps BEFORE copying the rest of the source, so dependency installation is cached across most code edits.

Q9. How would you reduce the size of a production Docker image? MEDIUM

Use a small/minimal base image (alpine, distroless), multi-stage builds to drop build tools, combine RUN commands to reduce layer count where it matters, add a proper .dockerignore, and avoid installing unnecessary packages (no -dev tools in the final stage).

Q10. What's the purpose of .dockerignore? EASY

It excludes files/dirs from the build context sent to the Docker daemon (e.g. node_modules, .git, .env) — speeds up builds, avoids accidentally baking secrets or huge irrelevant folders into layers.

Q11. What's the difference between ENV and ARG in a Dockerfile? MEDIUM

ARG is only available during the build (e.g. to parametrize a version number) and is NOT present in the running container unless you also assign it to an ENV. ENV is baked into the image and persists into the running container, visible via docker inspect.

3. Volumes & Data Persistence

Q12. Volumes vs bind mounts — what's the difference? MEDIUM

A volume is managed entirely by Docker (stored under Docker's own directory) — portable, backup-friendly, ideal for persistent app data like a database. A bind mount maps an arbitrary host path directly into the container — typically used in local dev to live-mount your source code.

Q13. If you don't mount a volume for your database container, what happens to the data when the container is removed? EASY

It's permanently lost — the writable layer that held it is deleted with the container. This is the classic "why did my local Mongo lose all its data" bug.

Q14. When would you use tmpfs instead of a volume? HARD

When data is sensitive and short-lived and should never be written to disk at all (e.g. a decrypted secret used only during process runtime) — tmpfs lives purely in host RAM and disappears when the container stops.

4. Networking

Q15. Explain -p 8080:80. EASY

Maps host port 8080 to container port 80 — traffic hitting the host on 8080 is forwarded into the container's port 80. Format is host:container.

Q16. Can two containers on the default bridge network reach each other by container name? MEDIUM

No — the default bridge network doesn't provide automatic DNS resolution by name (only by IP). You need a user-defined bridge network (or Docker Compose, which creates one automatically per project) to resolve other containers by name.

Q17. Your app binds to 127.0.0.1 inside the container instead of 0.0.0.0 — what breaks? HARD

127.0.0.1 only accepts connections from within the same network namespace (i.e. only from inside that exact container). Even with -p port mapping, external traffic (and other containers) can't reach it, because from the container's perspective the request doesn't originate from localhost. The app must bind to 0.0.0.0 (all interfaces) to be reachable.

5. Docker Compose

Q18. Does depends_on guarantee the dependency service is ready to accept connections? MEDIUM

No — it only guarantees start ORDER of containers, not application readiness. E.g. a Mongo container might be "started" but not yet accepting connections. Use a healthcheck + condition: service_healthy, or retry/backoff logic in your app's DB connection code.

Q19. How would you run the same Compose stack with different environment values for local dev vs a shared dev environment? MEDIUM

Use an override file (e.g. docker-compose.override.yml, merged automatically) or multiple -f files (docker compose -f docker-compose.yml -f docker-compose.dev.yml up), combined with .env files for variable substitution.

6. Security Basics

Q20. Why should containers run as a non-root user? MEDIUM

If an attacker exploits the app process and it's running as root inside the container, a container-escape vulnerability could grant root on the host. Adding a dedicated USER in the Dockerfile limits the blast radius even though it doesn't eliminate escape risk entirely.

Q21. Why shouldn't you put secrets in an ENV instruction in a Dockerfile? MEDIUM

Anything set via ENV (or a build ARG that leaks into a layer) is baked into the image and visible to anyone who can pull/inspect it or view its layer history — secrets should be injected at runtime (env var at docker run/Compose, or better, a mounted secret file) rather than baked into the image itself.

Q22. What's the risk of using the latest tag in production? EASY

It's mutable and non-reproducible — the same tag can point to different content over time, making rollbacks and debugging inconsistent behavior across environments much harder. Pin explicit versions/digests in production.

7. Scenario-Based / Debugging

Q23. Your container exits immediately with code 0 right after starting — what do you check? HARD

Check whether the main process (PID 1) actually blocks/runs forever — a common bug is CMD/ENTRYPOINT running a script that spawns a background process and then exits itself, so Docker sees the foreground process finish and stops the container. Fix by making the long-running process itself PID 1 (or using exec in a shell script, or a minimal init like tini).

Q24. Your container keeps exiting with code 137 — what does that mean and how do you confirm the cause? HARD

137 = 128 + 9 (SIGKILL) — very commonly caused by the OOM killer terminating the process because it exceeded a memory limit. Confirm via docker inspect (OOMKilled: true) and check/raise memory limits or fix a memory leak.

Q25. How do you debug a container that keeps restarting so fast you can't exec into it? HARD

Override the entrypoint to drop into a shell instead of running the normal command: docker run -it --entrypoint sh myimage. This lets you inspect the filesystem/env/config without the crash loop, then manually run the original command to see the actual error.

Q26. How would you containerize a Go backend service and an Angular frontend differently, and why? MEDIUM

Go compiles to a single static binary — final image can be a minimal/distroless base with just that binary (no runtime needed). Angular builds to static HTML/JS/CSS — final image typically uses a lightweight web server (nginx/alpine) to serve the compiled dist/ output; neither ships Node.js or the Go toolchain in the final image (multi-stage build for both).

Q27. How do you pass build-time configuration (e.g. an API base URL baked into a frontend bundle) without hardcoding it in source? HARD

Use a Dockerfile ARG passed via --build-arg at build time (e.g. docker build --build-arg API_URL=https://... .), consumed by the build step (e.g. an Angular environment file generated at build time) — keeping the same Dockerfile reusable across environments without editing source.
