Terminal & Shell (Bash/Zsh) Essentials

Navigation & Files

  • pwd — print working directory.
  • ls -la — long listing with hidden files.
  • cd dir / cd .. / cd - — change directory; - toggles to previous dir.
  • mkdir -p a/b/c — create nested dirs in one shot.
  • touch f.py — create empty file / refresh mtime.
  • cp -r src/ dst/ — recursive copy.
  • mv old new — move or rename.
  • rm -rf dir/ ⚠️ — recursive force delete. Irreversible.
  • ln -s target link — symlink.

View & Search

  • cat / less / head -n 20 / tail -f — view files; tail -f streams logs.
  • grep -r "pattern" . — recursive search.
  • rg "pattern" ⭐ — ripgrep, 10× faster, respects .gitignore.
  • find . -name "*.py" — find files by pattern.
  • fzf ⭐ — interactive fuzzy finder. Pipe anything in.
  • wc -l file — count lines.
  • diff a b — line-by-line diff.

Processes & System

  • ps aux | grep python — list matching processes.
  • top / htop — live CPU/RAM monitor.
  • kill PID / kill -9 PID — terminate / force kill.
  • lsof -i :8000 — who is on port 8000? (FastAPI/Django dev server killer).
  • df -h / du -sh * — disk free / dir sizes.
  • uname -a — OS/kernel info.

Network

  • curl -X POST url -d '{}' -H "Content-Type: application/json" — test APIs.
  • curl -v url — verbose for debugging.
  • ping host / dig domain — connectivity / DNS.
  • ss -tlnp / netstat -tulpn — list listening ports.
  • ssh user@host / scp file user@host:/p — remote shell & copy.
  • jq '.key' ⭐ — JSON CLI processor.

Pipes, Redirects, Chains

  • cmd1 | cmd2 — pipe stdout into stdin.
  • cmd > f / cmd >> f — overwrite / append.
  • cmd 2>&1 — merge stderr into stdout.
  • cmd1 && cmd2 / cmd1 || cmd2 — chain on success/failure.
  • $(cmd) — command substitution.
  • xargs — turn stdin into args.

Env & Shell Config

  • export VAR=value — env var children inherit.
  • echo $PATH / which python / type cmd.
  • ~/.zshrc — aliases, exports, PATH edits.
  • source ~/.zshrc — reload config.
  • Oh My Zsh ⭐ + Powerlevel10k or Starship prompt.

Week 0 Phase 0 — Setup & Mindset

Get a clean Python environment, learn why Python dominates backend/AI, and pick your tooling stack.

Install Python the Right Way (pyenv + uv)

Never use system Python ⚠️

  • macOS/Linux ship an old Python that the OS depends on. Don't pip install there.
  • Use pyenv to install & switch versions; uv or poetry to manage projects.

pyenv (multi-version manager)

  • brew install pyenv (Mac) / curl https://pyenv.run | bash (Linux).
  • pyenv install 3.12.5 · pyenv install 3.11.9
  • pyenv global 3.12.5 — default for shell.
  • pyenv local 3.11.9 — pin per-project (writes .python-version).
  • pyenv versions — list installed.

uv ⭐ (Rust-based, ultra-fast)

  • brew install uv or curl -LsSf https://astral.sh/uv/install.sh | sh
  • uv venv — make a virtualenv (10–100× faster than python -m venv).
  • uv pip install fastapi — install (drop-in pip).
  • uv add fastapi uvicorn[standard] — manages pyproject.toml.
  • uv sync — install from lockfile (uv.lock).
  • uv run script.py — run inside project env.

Poetry (still very common)

  • pipx install poetry
  • poetry new myapp / poetry init
  • poetry add fastapi · poetry install · poetry shell · poetry run pytest
  • Locks deps in poetry.lock; uses pyproject.toml (PEP 621).

pipx — install Python CLIs globally, isolated

  • pipx install black ruff httpie pre-commit poetry
  • Each tool gets its own venv. No version conflicts.

Verify Setup

  • python --version · pip --version · which python
  • uv venv && source .venv/bin/activate · python -c "import sys; print(sys.executable)"

Pre-1 Python / pip / venv CLI — Daily Commands Reference

Memorize before Phase 1. You'll run these 50× a day. python --help and pip --help are your friends.

🎯 Goal: Know every python, pip, venv, uv, poetry subcommand and the few flags you'll use.

Python Interpreter Flags

Run code

  • python script.py — run a file.
  • python -m pkg — run a module/package as __main__ (e.g., python -m http.server, python -m pytest).
  • python -c "print(1+1)" — execute a one-liner.
  • python -i script.py — run script then drop into REPL with its globals.
  • python - — read code from stdin.

Tuning & Debug Flags

  • python -O — strip assert statements (production).
  • python -X dev ⭐ — dev mode: extra warnings, async resource tracker, faulthandler.
  • python -X faulthandler — print Python tracebacks on segfault.
  • python -W error — turn warnings into errors (CI safety).
  • python -B — don't write .pyc files.
  • python -u — unbuffered stdout (Docker logs).
  • python -v — verbose import tracing.

Useful Env Vars

  • PYTHONPATH — extra dirs to search for imports.
  • PYTHONDONTWRITEBYTECODE=1 — same as -B.
  • PYTHONUNBUFFERED=1 — same as -u; set this in every Docker image.
  • PYTHONASYNCIODEBUG=1 — asyncio debug warnings.
  • PYTHONHASHSEED=0 — deterministic hash (debug).
  • PYTHONBREAKPOINT=ipdb.set_trace — make breakpoint() open ipdb.

venv — Built-in Virtual Environments

Create / Activate

  • python -m venv .venv — create venv in .venv/.
  • source .venv/bin/activate (Mac/Linux) · .venv\Scripts\activate (Win).
  • deactivate — exit venv.
  • which python — verify points into .venv/bin/python.
  • ⭐ Always work inside a venv. Never install into system Python.

Auto-activate

  • direnv + .envrc with source .venv/bin/activate — auto-activate when you cd.
  • uv/poetry handle this implicitly via uv run/poetry run.

Recreate / Nuke

  • rm -rf .venv && python -m venv .venv — fresh start when deps go weird.

pip — Package Manager (the basics)

Install / Uninstall

  • pip install pkg · pip install pkg==1.2.3 · pip install "pkg>=1,<2"
  • pip install -e . — editable install (your code as a package; edits picked up live). ⭐
  • pip install -r requirements.txt — install from file.
  • pip install --upgrade pkg · pip uninstall pkg.
  • pip install "fastapi[all]" — extras (optional deps group).
  • pip install git+https://github.com/u/r@branch — install from VCS.

Inspect

  • pip list · pip list --outdated
  • pip show pkg — version, location, deps.
  • pip freeze > requirements.txt — pin everything (use pip-tools/uv/poetry for proper locks).
  • pip check — verify dep tree consistency.
  • pip cache purge — clear cache.

Production-Safe Installs

  • pip install --no-deps — skip transitive deps (lockfile-only installs).
  • pip install --require-hashes -r requirements.txt ⭐ — verify SHA256 hashes (supply-chain safety).
  • pip install --no-cache-dir — common in Dockerfiles to slim image.

Lockfile Tools

  • pip-tools: pip-compile requirements.in → pinned requirements.txt.
  • uv: uv lock + uv sync.
  • poetry: poetry lock + poetry install --sync.
  • pdm, hatch — alternatives.

uv — Ultra-Fast Modern Workflow ⭐

Project Lifecycle

  • uv init myapp — scaffold project (pyproject.toml + src/ + venv).
  • uv add fastapi "uvicorn[standard]" sqlalchemy
  • uv add --dev pytest ruff mypy
  • uv remove pkg
  • uv sync — install exactly what's in uv.lock (CI command).
  • uv lock --upgrade — bump lockfile.
  • uv run uvicorn app:app --reload — run inside env without manual activation.
  • uv tool install black — global CLI tool, isolated (like pipx).
  • uv python install 3.12 — install Python itself!

Weeks 5–6 Phase 3 — Async, Concurrency & the GIL

🎯 Mental model: CPython has a Global Interpreter Lock (GIL) — only one thread runs Python bytecode at a time. I/O-bound → use asyncio or threads. CPU-bound → use multiprocessing, C extensions (numpy), or sub-interpreters / free-threaded Python (3.13+ no-GIL build).

The GIL — What It Actually Does

  • Protects internal interpreter state; one bytecode thread at a time per process.
  • Releases on most blocking I/O syscalls and inside C extensions (numpy, lxml).
  • 3.12 introduced per-interpreter GIL (PEP 684); 3.13 added experimental free-threaded build (PEP 703).
  • Implication: threads for I/O, processes for CPU.

Week 13.5 Phase 5.5 — Advanced Query Tuning & DB Performance

The single biggest skill gap between mid-level and senior backend. "It works on dev" → "p99 spiked 10× in prod" is almost always a query problem.

Reading EXPLAIN (ANALYZE, BUFFERS) like a senior ⭐

  • Plan node order: read inside-out (innermost = first executed).
  • Estimated vs actual rows: gap > 10× = stale stats → run ANALYZE.
  • cost=startup..total: Postgres unit, only useful for comparison; use actual time.
  • BUFFERS: shared hit = cache; shared read = disk → cold cache or working set > shared_buffers.
  • Common red flags: Seq Scan on big table, Nested Loop with high outer rows, Sort spilling to disk (external merge Disk: NkB), Hash Join with batches > 1, Bitmap Heap Scan with high lossy.
  • Tools: explain.dalibo.com ⭐, explain.depesz.com, auto_explain for slow logs in prod.
# Run on a sample query and read top-down for hot spots
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)

FROM users u LEFT JOIN orders o ON o.user_id = u.id
WHERE u.created_at > now() - interval '30 days'
GROUP BY u.id;

CTEs, window functions & subquery cost cliffs

  • Postgres ≥12: CTEs are not always optimization fences anymore. Use WITH … AS MATERIALIZED to force; default = inlinable.
  • Prefer window functions over self-joins for ranking, running totals, gaps-and-islands.
  • Avoid correlated subqueries on hot paths — rewrite as LEFT JOIN LATERAL when row count is small.
  • EXISTS > IN (SELECT …) for big subqueries; planner is smarter with EXISTS.
-- Top-3 orders per user (window beats correlated subquery)
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY total DESC) AS rn
  FROM orders o
) t WHERE rn <= 3;

-- Gaps & islands: consecutive event runs
SELECT user_id, MIN(ts), MAX(ts), COUNT(*)
FROM (
  SELECT *, ts - INTERVAL '1 minute' * (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts)) AS grp

Locking, isolation & deadlocks

  • Default Postgres isolation = READ COMMITTED. Use REPEATABLE READ for "read consistent snapshot"; SERIALIZABLE for true serializability (with retry-on-conflict).
  • SELECT … FOR UPDATE ⭐ for "read-modify-write" — locks rows; FOR UPDATE SKIP LOCKED for queue patterns.
  • Deadlocks: always lock rows in the same order across code paths. Catch DeadlockDetected and retry with backoff.
  • Long-running transactions block VACUUM → bloat. Keep them < few seconds.

Migrations without downtime ⭐

  • Add column: NULL allowed first, backfill in batches, then add NOT NULL + default. Never ADD COLUMN … DEFAULT on a huge table pre-PG11.
  • Drop column: stop writing → ship → drop in next release.
  • Rename column: never directly. Add new, dual-write, backfill, switch reads, drop old.
  • Add index: CREATE INDEX CONCURRENTLY always. Watch invalid-index after failure.
  • Foreign keys: NOT VALID initially → VALIDATE CONSTRAINT later (no full table lock).
  • Tools: pg_repack, pg-osc, Alembic with op.execute for raw DDL.

Cache strategy under load

  • Cache stampede: 1000 reqs miss simultaneously, all hit DB → meltdown. Fix: request coalescing (lock + single fetch) or jittered TTL + probabilistic early refresh.
  • Negative caching: cache 404s for short TTL; otherwise scrapers DDoS your DB looking for non-existent keys.
  • Hot keys: shard the hot key into N suffixes (user:42:0..user:42:7) and pick at random.
  • TTL discipline: never set TTL = 0 by accident; always EX/PX on writes.
# Stampede-safe cache-aside with single-flight lock
async def get_user(uid: int):
    key = f"u:{uid}"
    if (cached := await r.get(key)): return orjson.loads(cached)
    lock_key = f"u:{uid}:lock"
    if await r.set(lock_key, "1", nx=True, ex=5):
        try:
            user = await db.fetch_user(uid)
            await r.set(key, orjson.dumps(user), ex=300 + random.randint(0, 60))
            return user
        finally:
            await r.delete(lock_key)
    # lost the race — wait briefly & retry cache
    await asyncio.sleep(0.05)
    return orjson.loads(await r.get(key))

Week 14 Phase 6 — Auth & Security

AuthN vs AuthZ — Mental Model

  • Authentication = who are you? (passwords, tokens, certs, biometrics).
  • Authorization = what can you do? (RBAC, ABAC, ReBAC).
  • Common patterns: session cookies (server-side), JWT (stateless), OAuth2 (delegation), OIDC (identity layer on OAuth2), API keys (machine-to-machine).

Password Storage — Done Right

  • Never store plaintext or fast hashes (MD5/SHA1).
  • Use argon2id (preferred) or bcrypt. Library: argon2-cffi, passlib, bcrypt.
  • Salt is automatic with these libs. Pepper (server-side secret) optional.
  • Tune work factor: target ~250–500ms hash time on prod hardware.
  • Password reset tokens: short TTL, single-use, opaque random (secrets.token_urlsafe(32)), stored hashed.

  • Structure: header.payload.signature; signed (HS256/RS256/EdDSA), not encrypted by default.

  • Pitfalls: no easy revocation, "alg: none" attacks, weak secrets, leaking PII in payload.
  • Library: PyJWT, python-jose, authlib.
  • FastAPI: OAuth2 + JWT recipe in docs.

Week 18.5 Phase 8.5 — Resilience Patterns: Don't Let One Failure Take Down Everything

Distributed = "the failure of a computer you didn't even know existed will render your own unusable." (Lamport). These are the patterns top companies will grill you on.

The Failure Modes Map

Timeouts — the most important pattern

  • Every network call needs an explicit timeout. Default = your enemy (requests blocks forever; httpx defaults to 5s).
  • Tier your timeouts: fastest tier (cache) = 50ms, DB = 1–2s, downstream API = 3–5s. Total request budget propagated via header (X-Request-Deadline or gRPC deadline).
  • Timeout < user-perceived patience (~3s p99 is the goal for OLTP APIs).
  • Connect timeout vs read timeout vs total: set all three. httpx.Timeout(connect=2.0, read=5.0, write=5.0, pool=2.0).
import httpx, asyncio

# Per-call timeout overrides client default
client = httpx.AsyncClient(
    timeout=httpx.Timeout(5.0, connect=2.0),
    limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
)

async def charge(card_id: str, amount: int, deadline_ms: int):
    # Propagate remaining budget
    async with asyncio.timeout(deadline_ms / 1000):
        return await client.post("/charge", json={"card": card_id, "amt": amount})

Retries — done wrong, you ARE the outage

  • Retry only idempotent ops (GET, PUT, DELETE; POST only with idempotency key).
  • Exponential backoff + full jitter ⭐ — never fixed delay. delay = random.uniform(0, base * 2**attempt).
  • Cap at 3 attempts; cap total elapsed time below caller's timeout.
  • Retry budget (token bucket): drop retries when budget exhausted — prevents "retry storms" amplifying load 5–10×.
  • Skip retry on 4xx (client errors); retry on 5xx + connection errors only.
# tenacity — battle-tested retry library
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

@retry(
    stop=stop_after_attempt(3),
    wait=wait_random_exponential(multiplier=0.1, max=2.0),   # jitter ⭐
    retry=retry_if_exception_type((httpx.ConnectError, httpx.ReadTimeout)),
    reraise=True,
)
async def fetch(url): return await client.get(url)
⚠ Retry-after-timeout double-charge: Network blip → server did process → client retries → 2 charges. Solution: idempotency key in request, server dedups in Redis with TTL ≥ retry window.

Circuit Breakers — fast-fail when downstream is dead ⭐

Three states: CLOSED (normal) → trips on N consecutive failures → OPEN (fast-fail for cooldown period) → after timeout → HALF-OPEN (probe single request) → CLOSED if success / OPEN if failure.

  • Per downstream not per call — one breaker per dependency.
  • Trip on: timeouts, 5xx, connection errors. Don't trip on 4xx.
  • Surface circuit-open as a clean fallback (cached response, default value, friendly error) — never a generic 500.
  • Export state as a Prometheus gauge (circuit_state{dep="payments"} = 0|1|2) for alerting.
# pybreaker — most-used Python lib
import pybreaker
from prometheus_client import Gauge

state_g = Gauge("circuit_state", "0=closed,1=half,2=open", ["dep"])

class Listener(pybreaker.CircuitBreakerListener):
    def state_change(self, cb, old, new):
        state_g.labels(dep=cb.name).set({"closed":0,"half-open":1,"open":2}[new.name])

payments_breaker = pybreaker.CircuitBreaker(
    name="payments",
    fail_max=5,           # trip after 5 consecutive failures
    reset_timeout=30,      # half-open after 30s
    exclude=[ValueError],  # business errors don't trip
    listeners=[Listener()],
)

@payments_breaker
async def charge(*a, **kw):
    return await client.post("/charge", json=kw)

try:
    res = await charge(amount=100)
except pybreaker.CircuitBreakerError:
    res = fallback_offline_charge(100)   # queue, accept-and-defer

  • Service-mesh option: Istio / Envoy outlier detection implements circuit breaking at the proxy — language-agnostic.

Bulkheads — isolate failure domains ⭐

Named after ship compartments. One leak shouldn't sink the ship. In code: separate connection pools / thread pools / semaphores per dependency so one slow downstream can't starve every other route.

# Per-dependency bulkhead via asyncio.Semaphore
payments_bh = asyncio.Semaphore(20)         # max 20 in-flight
search_bh   = asyncio.Semaphore(50)
ml_bh       = asyncio.Semaphore(5)          # slow + expensive

async def call_payments(...):
    async with payments_bh:           # waits if 20 already in flight
        return await charge(...)

# In Django / Flask sync app: use ThreadPoolExecutor per dependency
from concurrent.futures import ThreadPoolExecutor
payments_pool = ThreadPoolExecutor(max_workers=20, thread_name_prefix="pay")
search_pool   = ThreadPoolExecutor(max_workers=50, thread_name_prefix="srch")
  • HTTP clients: separate httpx.AsyncClient per downstream with own Limits.
  • Combine with timeouts + circuit breakers for full resilience triad.
  • K8s-level bulkhead: separate Deployments / HPA per critical path so checkout pods aren't starved by analytics pods.

Load Shedding & Backpressure

  • When near saturation, reject early with 503 + Retry-After instead of accepting and timing out (which wastes both sides' resources).
  • Signal: queue depth, in-flight requests, CPU > 80%. Reject lowest-priority traffic first.
  • Use concurrency limits (Little's Law: concurrency = throughput × latency) — pick a target latency, derive concurrency cap.
  • Implementations: aiometer, asyncio.Semaphore, uvicorn --limit-concurrency, Envoy/Istio adaptive concurrency, AWS ALB target-response-time metric.
# FastAPI middleware: shed when in-flight > cap
from starlette.middleware.base import BaseHTTPMiddleware

class LoadShed(BaseHTTPMiddleware):
    def __init__(self, app, cap=200):
        super().__init__(app); self.sem = asyncio.Semaphore(cap)
    async def dispatch(self, req, call_next):
        if self.sem.locked():
            return JSONResponse({"error":"overloaded"}, status_code=503,
                                headers={"Retry-After": "1"})
        async with self.sem:
            return await call_next(req)

Idempotency & Exactly-Once (in practice)

  • True exactly-once is impossible in distributed systems. Aim for at-least-once + idempotent consumer = effectively-once.
  • Stripe-style idempotency key: client sends Idempotency-Key header; server stores key + response in Redis (TTL 24h). On retry, return stored response.
  • Outbox pattern for "atomic DB write + event publish": write event to outbox table in same TX; separate worker reads & publishes (Phase 8).
  • Inbox pattern for consumers: dedup on (source, event_id) before processing.
# Server-side idempotency key (Stripe-style)
async def handle_charge(req):
    key = req.headers.get("Idempotency-Key")
    if not key: raise HTTPException(400)

    cached = await r.get(f"idem:{key}")
    if cached: return orjson.loads(cached)

    # SET NX = "create lock if absent" — only one wins
    if not await r.set(f"idem:{key}:lock", "1", nx=True, ex=30):
        return JSONResponse({"error":"in-flight"}, status_code=409)

    res = await do_charge(req.body)
    await r.set(f"idem:{key}", orjson.dumps(res), ex=86400)
    return res

Cascading Failure Analysis ⭐ (the FAANG interview favorite)

A small slowness propagates & amplifies until the entire system collapses. Classic chain:

  1. Downstream X latency rises 50ms → 500ms.
  2. Caller threads/coroutines pile up waiting → connection pool exhausts.
  3. Health checks fail → K8s kills pod → fewer pods → each gets more load.
  4. Retries amplify load 3× → downstream gets more requests, gets slower → death spiral.

The countermeasures (mnemonic T-R-C-B-L-I)

  1. Timeouts — bounded; smaller than caller's timeout.
  2. Retries — capped, jittered, with budget.
  3. Circuit breaker — fail fast when downstream sick.
  4. Bulkheads — isolate per dependency.
  5. Load shedding — refuse work near capacity.
  6. Idempotency — make retries safe.

Bonus mitigations

  • Backpressure: queue size limit; drop oldest or reject newest.
  • Health-check decoupling: liveness ≠ readiness ≠ startup. A struggling pod under load shouldn't get killed (liveness PASS) but should stop receiving traffic (readiness FAIL).
  • Graceful degradation: serve stale cache, hide non-critical features, return partial results.
  • Adaptive concurrency (Netflix concurrency-limits, Envoy adaptive): auto-tune in-flight cap based on observed latency.
  • Region failover: multi-AZ minimum; multi-region for tier-1 services.

class ResilientClient:
    def __init__(self, name: str, base_url: str):
        self.name = name
        self.client = httpx.AsyncClient(
            base_url=base_url,
            timeout=httpx.Timeout(3.0, connect=1.0),
            limits=httpx.Limits(max_connections=50),
        )
        self.bulkhead = asyncio.Semaphore(30)
        self.breaker = pybreaker.CircuitBreaker(
            name=name, fail_max=5, reset_timeout=20,
        )

    @retry(stop=stop_after_attempt(3),
           wait=wait_random_exponential(multiplier=0.1, max=2),
           retry=retry_if_exception_type((httpx.TransportError,)))
    async def _send(self, method, url, **kw):
        async with self.bulkhead:
            return await self.breaker.call_async(
                self.client.request, method, url, **kw
            )

    async def get(self, url, **kw):  return await self._send("GET", url, **kw)
    async def post(self, url, **kw): return await self._send("POST", url, **kw)

Week 26 Phase 12 — Performance, Profiling & CPython Internals

Senior backend = can debug a 10× regression and explain it.

CPython Internals (the parts that bite you)

  • Bytecode: dis.dis(func) shows ops; PEP 659 specializing adaptive interpreter (3.11+).
  • Reference counting + cyclic GC; gc.collect(), gc.disable() for latency-sensitive paths.
  • Memory: small-int cache, string interning, free lists.
  • Why dicts are fast (open addressing, compact dicts since 3.6).
  • Why lists vs tuples vs deque differ in operations.
  • Async event loop internals (selectors, futures, tasks).
  • Python 3.11/3.12 speedups (Faster CPython project).
  • Free-threaded build (3.13+, PEP 703); sub-interpreters (PEP 684).
🎥 CPython Internals⭐ Anthony Shaw
📕 Book: CPython Internals (Anthony Shaw)Real Python

Profiling Toolchain (recap + go deeper)

  • py-spy ⭐ live + flame graphs.
  • memray ⭐ memory allocations (Bloomberg) — finds leaks fast.
  • scalene CPU + memory + GPU + line-level.
  • cProfile + snakeviz.
  • line_profiler — @profile decorator.
  • pyinstrument — call-tree profiler with low overhead, great for FastAPI middleware.
  • Async-aware: aiomonitor, aiodebug.

Speed-Up Strategies

  • Avoid premature optimization; measure first.
  • Algorithmic wins beat micro-opts (O(n²) → O(n log n)).
  • Use C-backed libs: numpy, pandas, orjson/ujson (JSON), msgspec ⭐ (faster Pydantic-style validation).
  • Compile hot paths: Cython, mypyc, Numba, PyO3 (Rust extensions) ⭐.
  • PyPy for some workloads (not C-extension-heavy).
  • Async + connection pooling for I/O bound.
  • Use __slots__ / dataclasses with slots=True when you have millions of instances.
  • Batch DB writes; use COPY in Postgres for bulk loads.
  • Avoid N+1 queries (selectinload/prefetch_related).
