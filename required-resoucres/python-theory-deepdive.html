Object-Oriented Python

1. Classes & OOP basics

Theory

A class is a blueprint that bundles state (attributes) with behavior (methods). In Python everything is an object — even classes themselves (instances of type). Three method flavors:

  • Instance method — first arg self; sees instance state.
  • Class method — @classmethod, first arg cls; alternative constructors.
  • Static method — @staticmethod; no implicit first arg; namespace grouping.

Hands-on

class Account:
    bank = "HDFC"                       # class attribute (shared)

    def __init__(self, owner, balance=0):
        self.owner = owner                # instance attribute
        self._balance = balance           # single-underscore = "internal"

    def deposit(self, amt):               # instance method
        if amt <= 0: raise ValueError("positive")
        self._balance += amt

    @classmethod
    def from_dict(cls, d):                # alt constructor
        return cls(d["owner"], d.get("balance", 0))

    @staticmethod
    def validate_pan(pan: str) -> bool:   # utility, no self/cls
        return len(pan) == 10 and pan.isalnum()

    @property
    def balance(self):                    # getter
        return self._balance

    @balance.setter
    def balance(self, v):
        if v < 0: raise ValueError
        self._balance = v

When / Why / Why-not / How

Q: When should I create a class instead of a function or dict?
When data + behavior cluster together AND lifecycle / invariants matter (e.g., balance can never go negative). For pure data with no logic prefer dataclass or NamedTuple; for one-off transforms a function is better.
Q: Why use @property instead of a public attribute?
To start simple (public attr) and upgrade later without breaking callers — add validation/computation behind the same access syntax. Don't add @property pre-emptively; YAGNI.
Q: Why-not subclass everything?
Inheritance creates tight coupling. Prefer composition (hold a reference to a helper) when you only need behavior reuse, not "is-a" semantics. Reserve inheritance for true polymorphism.
Q: How do private attrs work?
Python has no real private. Conventions: _x = "internal, don't touch", __x = name-mangled to _ClassName__x (collision avoidance, not security). Don't fight the language — use _ and trust callers.

2. Inheritance, MRO & super()

Theory

Python supports multiple inheritance. MRO (Method Resolution Order) decides which parent method is called and is computed by the C3 linearization algorithm. Always use super().method() — never name parents directly — so cooperative multiple inheritance works.

Hands-on — the diamond

class A:
    def hi(self): print("A"); super().hi()
class B(A):
    def hi(self): print("B"); super().hi()
class C(A):
    def hi(self): print("C"); super().hi()
class D(B, C):
    def hi(self): print("D"); super().hi()
class Root:
    def hi(self): print("Root")
# Add Root at the end
class A(Root):
    def hi(self): print("A"); super().hi()

D().hi()                  # D B C A Root
print(D.__mro__)          # [D, B, C, A, Root, object]

Mixins (the right way to combine behavior)

class JSONMixin:
    def to_json(self):
        import json
        return json.dumps(self.__dict__)

class TimestampMixin:
    def __init__(self, *a, **kw):
        from datetime import datetime
        self.created_at = datetime.utcnow()
        super().__init__(*a, **kw)         # cooperative!

class User(TimestampMixin, JSONMixin):
    def __init__(self, name): self.name = name
    def __init__(self, *a, **kw):
        super().__init__(*a, **kw)
        self.name = a[0] if a else kw["name"]

Q&A

Q: When should I use multiple inheritance?
Almost only for mixins — small, orthogonal, stateless behaviors (logging, serialization, comparability). Avoid mixing two "real" base classes.
Q: Why super().__init__(*a, **kw) in mixins?
So calls flow through the entire MRO. If a mixin __init__ doesn't call super, classes after it never initialize.
Q: Why-not deep inheritance trees?
Behavior gets spread across N classes — debugging means walking __mro__. Rule of thumb: max 2 levels + mixins. Anything deeper → reach for composition or strategy pattern.
Q: How do abstract base classes help?
abc.ABC + @abstractmethod prevents instantiation until all abstracts are implemented — great for plugin/strategy interfaces. Or use typing.Protocol (structural / "duck typing with type checking").

3. Dunder methods & the data model

Theory

Dunder ("double-underscore") methods plug your class into Python's built-in operators and protocols. Instead of obj.equals(other) you implement __eq__ and use ==. This is what "Pythonic" really means.

Hands-on — Vector with full protocol

class Vec:
    __slots__ = ("x", "y")             # save memory + speed
    def __init__(self, x, y): self.x, self.y = x, y
    def __repr__(self):  return f"Vec({self.x},{self.y})"   # debug
    def __str__(self):   return f"({self.x}, {self.y})"      # user
    def __eq__(self, o): return isinstance(o, Vec) and (self.x, self.y) == (o.x, o.y)
    def __hash__(self): return hash((self.x, self.y))            # needed for sets/dict keys
    def __lt__(self, o): return (self.x**2+self.y**2) < (o.x**2+o.y**2)
    def __add__(self, o): return Vec(self.x+o.x, self.y+o.y)
    def __mul__(self, k): return Vec(self.x*k, self.y*k)         # Vec * 3
    def __rmul__(self, k): return self * k                       # 3 * Vec
    def __iter__(self):   return iter((self.x, self.y))         # tuple unpack
    def __len__(self):    return 2
    def __bool__(self):   return self.x != 0 or self.y != 0   # truthiness

Q&A

Q: When override __repr__?
Always on domain classes. __repr__ shows in tracebacks, debuggers, REPL — saves hours of debugging. __str__ is optional (falls back to repr).
Q: Why must I add __hash__ when I define __eq__?
Defining __eq__ auto-sets __hash__ = None → instance becomes unhashable. If equality is by value, hash must agree: hash((self.x, self.y)).
Q: Why-not override __getattribute__?
It runs on every attribute access, easy to recurse infinitely or 50× slow your class. Prefer __getattr__ (only called when normal lookup fails).
4. Dataclasses vs NamedTuple vs Pydantic vs attrs

Hands-on

from dataclasses import dataclass, field, asdict
from typing import ClassVar

@dataclass(frozen=True, slots=True)        # 3.10+ slots=True
class Point:
    x: float
    y: float
    z: float = 0.0
    tags: list[str] = field(default_factory=list)   # NEVER bare []
    PI: ClassVar[float] = 3.14159

p = Point(1.0, 2.0, tags=["a"])
# p.x = 9   # FrozenInstanceError
asdict(p)                  # {'x':1.0,...}
from typing import NamedTuple
class RGB(NamedTuple):
    r: int; g: int; b: int = 0
RGB(255, 128).r            # tuple-like + named access
from pydantic import BaseModel, Field, EmailStr
class User(BaseModel):
    id: int
    email: EmailStr
    age: int = Field(ge=0, le=150)
User.model_validate({"id": "1", "email": "a@b.com", "age": 30})  # coerces "1"->1 ⭐

Q: Why field(default_factory=list) instead of = []?
Same reason as mutable default args — every instance would share the same list. default_factory calls a fresh factory per instance.
Q: Why pick Pydantic over dataclass for FastAPI?
Pydantic does parse-don't-validate: it coerces & validates at the boundary, gives JSON schema for free, and integrates with FastAPI's docs. Dataclasses are static — no input validation.
5. Decorators

Theory

A decorator is a callable that takes a function (or class) and returns a replacement. @deco above def f is sugar for f = deco(f). They give you cross-cutting concerns (logging, caching, auth, retry) without touching business code.

Hands-on — three levels

import functools, time

# Level 1: simple decorator
def log(fn):
    @functools.wraps(fn)                        # preserves __name__/__doc__ ⭐
    def wrapper(*a, **kw):
        print(f"call {fn.__name__}")
        return fn(*a, **kw)
    return wrapper

# Level 2: decorator with args
def retry(times=3, exc=Exception):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            for i in range(times):
                try: return fn(*a, **kw)
                except exc:
                    if i == times - 1: raise
                    time.sleep(2**i)
        return wrapper
    return deco

@retry(times=5, exc=ConnectionError)
def fetch(url): ...

# Level 3: class-based decorator (keeps state)
class Counter:
    def __init__(self, fn):
        functools.update_wrapper(self, fn)
        self.fn = fn; self.count = 0
    def __call__(self, *a, **kw):
        self.count += 1
        return self.fn(*a, **kw)

@Counter
def hello(): print("hi")
hello(); hello(); print(hello.count)            # 2

Q&A

Q: When use a decorator vs a regular function call?
Use a decorator when behavior must wrap every call of a function transparently (auth, timing, retry). For one-off "do X then call Y", just call directly.
Q: Why-not @cache on instance methods?
It captures self in the cache key — preventing instance GC = memory leak. Use @cached_property, or move logic to module-level pure function.
Q: How do I stack multiple decorators?
Bottom up: @a / @b / def f = a(b(f)). Order matters: e.g. @cache @log caches the log call (bad); @log @cache logs each cache hit/miss.
Q: Why @functools.wraps?
Without it, fn.__name__ becomes "wrapper", breaks Sphinx docs, FastAPI route names, mocks, profilers. Always wrap your wrappers.
6. Generators & iterators

Theory

An iterator is any object with __iter__ (returns self) and __next__ (returns next item or raises StopIteration). A generator function uses yield — Python builds the iterator for you, with state preserved between calls. Generators are lazy: nothing runs until you ask for the next value.

Hands-on

# Generator function
def countdown(n):
    while n > 0:
        yield n           # pauses, returns n; resumes here next call
        n -= 1

for x in countdown(3): print(x)     # 3 2 1

# Generator expression — like list comp but parens, lazy
even_sq = (x*x for x in range(10**9) if x%2==0)
sum(even_sq)                            # streams, no huge list

# Pipeline: read big file lazily
def lines(path):
    with open(path) as f:
        for line in f: yield line.rstrip()
def errors(it):
    for ln in it:
        if "ERROR" in ln: yield ln
n_err = sum(1 for _ in errors(lines("app.log")))    # O(1) memory

# yield from — delegate to sub-generator
def flatten(xs):
    for x in xs:
        if isinstance(x, list): yield from flatten(x)
        else: yield x

# Generator as coroutine — send/throw/close
def averager():
    total, count = 0, 0
    while True:
        x = yield (total / count if count else 0)
        total += x; count += 1
g = averager(); next(g)
print(g.send(10), g.send(20))            # 10.0  15.0

Q&A

Q: When use a generator vs a list?
Generator when: data is large/streamed, you'll iterate once, or you want a pipeline. List when: you need len(), indexing, multiple passes, or random access.
Q: Why-not generators everywhere?
They're single-use (exhausted after one iteration), can't be pickled easily, harder to debug, and you lose len(). If a list of 10K items is fine, just build the list.
Q: How does yield from differ from a for + yield loop?
yield from also forwards send(), throw(), close(), and the sub-generator's return value (via StopIteration.value). It's the basis for old-style coroutines.
Q: How do I peek without consuming?
Use itertools.tee(it, 2), or wrap in a helper that buffers one item. Don't try to next + push back.
7. Context managers (with)

Theory

A context manager guarantees setup/teardown around a block — even on exceptions. Two protocols: class-based (__enter__/__exit__) or generator-based via @contextmanager.

Hands-on

# Class-based
class Timer:
    def __enter__(self):
        import time; self.t0 = time.perf_counter(); return self
    def __exit__(self, exc_type, exc, tb):
        import time; self.elapsed = time.perf_counter() - self.t0
        # return True to suppress exception, falsy to propagate

with Timer() as t:
    do_work()
print(t.elapsed)

# Generator-based — usually simpler
from contextlib import contextmanager

@contextmanager
def tempenv(**kw):
    import os
    old = {k: os.environ.get(k) for k in kw}
    os.environ.update({k: str(v) for k, v in kw.items()})
    try:
        yield
    finally:
        for k, v in old.items():
            if v is None: os.environ.pop(k, None)
            else: os.environ[k] = v

with tempenv(DEBUG="1"):
    run_tests()

# Multiple resources — chain them
from contextlib import ExitStack
with ExitStack() as stack:
    files = [stack.enter_context(open(p)) for p in paths]
    process(files)         # all closed even if any fail

Stdlib goodies

  • contextlib.suppress(OSError) — silence specific exceptions cleanly.
  • contextlib.closing(obj) — ensures obj.close() for non-CM objects.
  • contextlib.nullcontext() — no-op CM, useful as default param.
  • contextlib.asynccontextmanager — async version (FastAPI lifespan).

Q&A

Q: When write a CM vs try/finally?
CM when the setup/teardown is reusable across many call-sites. One-off cleanup → just use try/finally.
Q: Why return a non-self value from __enter__?
with X() as y binds y to whatever __enter__ returns. open() returns the file; a DB connection might return a cursor. Choose the most useful object.
Q: Why-not swallow exceptions in __exit__ by default?
Returning truthy from __exit__ hides errors silently — terrible debugging. Only do it deliberately (e.g. suppress).
8. Type hints & the typing module

Theory

Type hints (PEP 484) are not enforced at runtime — they're metadata for static checkers (mypy, pyright), IDEs, and Pydantic. Modern Python (3.10+) lets you write list[int] and X | None directly without importing.

Hands-on

from typing import Protocol, Iterable, Callable, TypeVar, ParamSpec, Literal, Final, Annotated, NewType

# Modern (3.10+) — no need to import List/Dict/Optional
def top(items: list[int], k: int = 5) -> list[int]:
    return sorted(items, reverse=True)[:k]

UserId = NewType("UserId", int)             # distinct from raw int at type level
def get(uid: UserId) -> "User": ...

# Generics
T = TypeVar("T")
def first(xs: Iterable[T]) -> T | None:
    for x in xs: return x
    return None

# Structural typing — duck typing checked statically
class SupportsClose(Protocol):
    def close(self) -> None: ...

def shut(x: SupportsClose) -> None: x.close()

# Literal types — exhaustive switching
Mode = Literal["r", "w", "a"]
def open_log(mode: Mode): ...

# Annotated for metadata (Pydantic / FastAPI use this heavily)
Age = Annotated[int, "0..150"]

# Decorators that preserve sig (3.10+)
P = ParamSpec("P"); R = TypeVar("R")
def log(fn: Callable[P, R]) -> Callable[P, R]:
    def wrap(*a: P.args, **kw: P.kwargs) -> R:
        return fn(*a, **kw)
    return wrap

Tooling — mypy --strict

pip install mypy
mypy --strict src/
# Catches: missing return type, untyped def, no implicit Optional, ...

Q&A

Q: When add type hints?
Always on public APIs (function signatures, dataclass fields, module-level constants). Internal local variables only when inference fails or for clarity.
Q: Why-not Any everywhere?
Any turns off checking at that point — viral. Prefer object (no operations allowed without narrowing) or a real Protocol.
Q: When use Protocol vs ABC?
Protocol = structural ("has these methods"), no inheritance needed — best for cross-cutting interfaces (e.g. anything with close()). ABC = nominal, must subclass; gives runtime isinstance checks.
Q: How do I check at runtime?
Hints aren't enforced. For runtime validation use Pydantic, typeguard, or beartype.
9. Descriptors & __slots__

Theory

A descriptor is any object defining __get__, __set__, or __delete__. They power property, classmethod, staticmethod, and ORM fields. __slots__ tells Python "instances will only have these attributes" → drops the per-instance __dict__, saving ~40-50% memory and speeding attribute access.

Hands-on — validated descriptor

class Positive:
    def __set_name__(self, owner, name):    # 3.6+ auto-binds attr name
        self.name = "_" + name
    def __get__(self, obj, objtype=None):
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0: raise ValueError(f"{self.name} must be > 0")
        setattr(obj, self.name, value)

class Order:
    qty   = Positive()
    price = Positive()
    def __init__(self, qty, price): self.qty, self.price = qty, price

Order(2, 9.99)              # ok
# Order(0, 5)               # ValueError

__slots__

class Point:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y

p = Point(1, 2)
# p.z = 3   # AttributeError ⭐
# sys.getsizeof(p) is ~50% smaller than dict-based

Q&A

Q: When write a custom descriptor?
When the same validation/computation must apply to many attributes across classes (ORM fields, units of measure, range-checked values). Otherwise @property is enough.
Q: When use __slots__?
When you create millions of small instances (game entities, parsed records, geometric points). Skip in normal app code — adds friction.
Q: Why-not __slots__?
Breaks dynamic attr addition, __dict__-based introspection, multiple inheritance with non-slot bases, and weakref unless "__weakref__" in slots. Profile before adopting.
10. Metaclasses

Theory

Classes are instances of metaclasses. Default = type. A metaclass customizes class creation — registering subclasses, enforcing structure, generating attrs (Django Models, SQLAlchemy declarative). 99% of code never needs them; modern alternatives (__init_subclass__, __set_name__, decorators) cover most cases more simply.

Hands-on

# Plugin auto-registry — modern way (no metaclass)
class Plugin:
    registry = {}
    def __init_subclass__(cls, **kw):           # 3.6+ ⭐ replaces most metaclass uses
        super().__init_subclass__(**kw)
        Plugin.registry[cls.__name__] = cls

class CSVPlugin(Plugin): ...
class JSONPlugin(Plugin): ...
print(Plugin.registry)                          # {'CSVPlugin': ..., 'JSONPlugin': ...}

# If you really need a metaclass:
class Singleton(type):
    _instances = {}
    def __call__(cls, *a, **kw):
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*a, **kw)
        return cls._instances[cls]

class Config(metaclass=Singleton):
    def __init__(self): self.values = {}
Config() is Config()                          # True

Q&A

Q: When use a metaclass?
Building a framework where users declaratively define classes that need transformation (Django ORM, SQLAlchemy, Pydantic v1, ABC). Application code: almost never.
Q: Why-not metaclass for plugin registry?
__init_subclass__ covers it with way less complexity. Reserve metaclasses for actually changing the class object's structure.
