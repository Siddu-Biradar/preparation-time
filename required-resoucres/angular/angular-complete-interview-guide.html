1. JavaScript & TypeScript Fundamentals

Angular is built on TypeScript, and TypeScript is a superset of JavaScript. Interviewers expect you to be strong in both languages before they discuss Angular.

Theory

JavaScript runs on a single-threaded event loop. Understanding this is essential — it explains why long-running synchronous code blocks the UI and why async patterns (callbacks, promises, async/await, observables) are critical. TypeScript adds a type system that catches bugs at compile time and powers Angular's dependency injection, decorators, and template type-checking.

Event loop — predict the output

console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

console.log('4');

// Output: 1, 4, 3, 2
// Why: synchronous code runs first (1, 4),
// then microtask queue (Promise → 3),
// then macrotask queue (setTimeout → 2)

Theory: Microtasks (promises, MutationObserver) run before macrotasks (setTimeout, setInterval, I/O). This is why Angular's change detection triggered by Zone.js (which patches both) can intercept async completions in a predictable order.

}

counter.increment(); // 12
counter.getCount();  // 12
// The variable 'count' survives because the returned object's methods
// close over it. This is exactly how Angular singleton services maintain state.

Interview Questions

Q: What is the difference between var, let, and const?

A: var is function-scoped, hoisted to the top of its function as undefined, and can be redeclared. let is block-scoped, hoisted but in the temporal dead zone until declaration, and cannot be redeclared. const is block-scoped like let but the binding cannot be reassigned (the value itself can still be mutated if it is an object or array).

Q: Explain closures with a real example.

A: A closure is a function that retains access to its outer scope's variables even after the outer function has returned. In Angular, every service created by a factory function is a closure — the service methods close over the injected dependencies and private state. RxJS operators like map and filter also use closures to capture the projection/predicate function.

Q: What is the difference between interface and type in TypeScript?

A: Interfaces are for object shapes — they support declaration merging, extending, and are used by Angular's DI system. Types support unions (string | number), intersections (A & B), mapped types, conditional types, and template literal types. Rule of thumb: use interfaces for API models and component contracts, use types for unions, computed types, and complex type algebra.

Q: What are generics and why do they matter?

A: Generics let you write type-safe code that works with multiple types without losing type information. Without generics, HttpClient.get() would return Observable<any> and you'd lose autocomplete and type checking. With generics, HttpClient.get<User[]>('/api/users') returns Observable<User[]> and the compiler knows exactly what properties are available.

Q: How does the JavaScript event loop work?

A: JavaScript has a single call stack. When the stack is empty, the engine checks the microtask queue first (promises, queueMicrotask), running all microtasks. Then it checks the macrotask queue (setTimeout, events, I/O) and runs one macrotask. Then it checks microtasks again. This cycle repeats. Angular's Zone.js patches both queues to detect when async work completes, triggering change detection.

2.3 Dependency Injection — deep theory

Angular's DI system is a hierarchical injector tree that mirrors the component tree. When a component requests a dependency, Angular walks up the injector tree until it finds a provider.

  • providedIn: 'root' — singleton across the entire app. Tree-shakeable.
  • providedIn: 'any' — one instance per lazy-loaded module boundary.
  • Component-level providers — new instance per component. Useful for services with component-scoped state.
  • Injection tokens — InjectionToken for non-class values (config objects, feature flags).
  • inject() function — modern alternative to constructor injection. Works in constructors, field initializers, and factory functions.

Interview Questions

Q: What is the difference between NgModule and standalone components?

A: NgModules group components, directives, pipes, and providers into cohesive blocks. Standalone components declare their own dependencies via the imports array and don't need an NgModule. Standalone is the default since Angular 17. Benefits: simpler mental model, better tree-shaking (unused standalone components are removed from the build), and easier lazy loading (individual components can be lazy-loaded, not just modules).

Q: Explain Angular's dependency injection hierarchy.

A: Angular maintains a tree of injectors that mirrors the component tree. Root injector → module injectors → component injectors. When a component requests a service, Angular searches upward. providedIn: 'root' registers at the root injector (singleton). Component-level providers creates a new instance per component instance. This hierarchy enables scoped services, component-level state, and lazy module isolation.

Q: When do you use ngOnInit vs constructor?

A: Constructor is for DI — injecting dependencies. It runs before Angular sets inputs and before the component is fully initialized. ngOnInit runs after the first ngOnChanges, meaning inputs are available. Use ngOnInit for initialization logic that depends on inputs, API calls, and setup that should only run once. In modern Angular, the inject() function in field initializers can replace some constructor patterns.

Q: What is the difference between @ViewChild and @ContentChild?

A: @ViewChild accesses elements/components defined in the component's own template. @ContentChild accesses elements/components projected via <ng-content> from the parent. @ViewChild is available in ngAfterViewInit. @ContentChild is available in ngAfterContentInit.

Q: Explain pure vs impure pipes.

A: A pure pipe (default) only re-executes when the input value reference changes — Angular caches the result. An impure pipe (pure: false) re-executes on every change detection cycle, regardless of whether inputs changed. Pure pipes are performant. Impure pipes (like async) are expensive but necessary when the pipe needs to react to changes that don't alter the reference (like array mutations).

Interview Questions

Q: When would you use a service for communication vs @Input/@Output?

A: @Input/@Output is for direct parent-child relationships. For sibling components, deeply nested components, or components in different branches of the tree, use a shared service. Services are also better when the state needs to persist across route navigations. Rule: if you are passing data through more than 2 intermediate components (prop drilling), switch to a service.

Q: What is content projection and when do you use it?

A: Content projection (<ng-content>) lets a parent component pass template content into a child component. Use it for reusable layout components — cards, modals, dialogs, panels, tabs — where the structure is fixed but the content varies. Multi-slot projection with select lets you target different content areas. It is the Angular equivalent of React's children/slots.

Q: Explain the smart/dumb (container/presentational) component pattern.

A: Smart components (containers) handle data fetching, state management, and business logic. Dumb components (presentational) receive data via @Input and emit events via @Output — they have no knowledge of services or state. Benefits: dumb components are highly reusable, easy to test, and easy to reason about. Smart components coordinate the page-level logic. This separation makes the codebase more maintainable as it grows.

4. Change Detection & Rendering

Theory

Change detection is Angular's mechanism for keeping the view in sync with the component state. Understanding how it works is one of the most common interview topics because it directly impacts performance.

4.1 How change detection works

Angular walks the component tree top-down, checking each component's template bindings. If a binding's value has changed, Angular updates the DOM. This process is triggered by Zone.js, which patches all async APIs (events, timers, HTTP) so Angular knows when to check.

4.2 Default vs OnPush strategies

FeatureDefaultOnPush
When it checksEvery change detection cycleOnly when inputs change by reference, events fire inside, or manually triggered
PerformanceConvenient but can be expensive in large treesEfficient — skips subtrees when not needed
Data patternsWorks with any mutation patternRequires immutable data / signal updates
When to useSmall apps, prototyping, leaf componentsAll components in medium-to-large apps

4.3 Signals — the future of change detection

Signals are Angular's fine-grained reactivity primitive. Instead of Zone.js triggering broad CD cycles, signals create a dependency graph where only the specific consumers that read a changed signal are updated. This is more precise and more efficient than tree-based checking.

Interview Questions

Q: What triggers change detection in Angular?

A: Zone.js patches async APIs and triggers CD when they complete: (1) DOM events (click, input, scroll), (2) Timers (setTimeout, setInterval), (3) HTTP responses, (4) Promise resolutions and microtasks. With OnPush + signals, CD still needs a trigger, but the framework can skip unchanged subtrees. Zoneless Angular relies entirely on signal-based reactivity.

Q: What is the difference between signals and observables?

A: Signals are synchronous, hold a current value, and create a dependency graph — they are for state. Observables are asynchronous streams of values over time — they are for events and async data flows. Signals auto-notify consumers when their value changes. Observables require explicit subscription. In Angular, signals are used for component state and template bindings; observables (RxJS) are used for HTTP, WebSockets, user event streams, and complex async orchestration.

5. RxJS Deep Dive

Theory

RxJS (Reactive Extensions for JavaScript) is Angular's async engine. It provides observables — lazy, composable, cancellable streams of values. Understanding RxJS is non-negotiable for Angular interviews.

5.1 Core concepts

  • Observable: a lazy collection of values over time. Does not execute until subscribed.
  • Observer: an object with next, error, complete callbacks.
  • Subscription: represents the execution of an observable. Must be cleaned up.
  • Operators: pure functions that transform, filter, combine, and control streams.
  • Subject: both observable and observer. Can multicast values to many subscribers.
  • BehaviorSubject: Subject that holds a current value and emits it to new subscribers.
  • ReplaySubject: Caches N previous values and replays them to new subscribers.

Hands-on Code

Search autocomplete — the classic RxJS interview question

@Component({
  template: `
    <input [formControl]="searchControl" placeholder="Search..." />
    @for (result of results(); track result.id) {
      <div class="result">{{ result.name }}</div>
    }
    @if (loading()) { <div class="spinner">Loading...</div> }
  `
})
export class SearchComponent {
  searchControl = new FormControl('');
  results = signal<SearchResult[]>([]);
  loading = signal(false);
  private destroyRef = inject(DestroyRef);
  private http = inject(HttpClient);

  constructor() {
    this.searchControl.valueChanges.pipe(
      debounceTime(300),           // Wait for user to stop typing
      distinctUntilChanged(),      // Skip if same value
      tap(() => this.loading.set(true)),
      switchMap(term =>            // Cancel previous request
        term && term.length > 2
          ? this.http.get<SearchResult[]>(`/api/search?q=${encodeURIComponent(term)}`).pipe(
              catchError(() => of([]))  // Handle errors gracefully
            )
          : of([])
      ),
      tap(() => this.loading.set(false)),
      takeUntilDestroyed(this.destroyRef)
    ).subscribe(results => this.results.set(results));
  }
}

Theory: This is the most commonly asked RxJS code in interviews. debounceTime prevents API calls on every keystroke. distinctUntilChanged skips duplicate values. switchMap cancels the previous request when a new term arrives — preventing race conditions. catchError returns a fallback empty array instead of breaking the stream. takeUntilDestroyed prevents memory leaks.

Interview Questions

Q: What is the difference between switchMap, mergeMap, concatMap, and exhaustMap?

A: All four map an outer value to an inner observable, but they differ in concurrency: switchMap cancels previous (use for search). mergeMap runs all concurrently (use for parallel uploads). concatMap queues sequentially (use for ordered operations). exhaustMap ignores new values while busy (use for submit buttons). Choosing wrong causes race conditions or duplicate requests.

Q: How do you prevent memory leaks with RxJS in Angular?

A: (1) Use async pipe — it auto-unsubscribes. (2) Use takeUntilDestroyed() for imperative subscriptions. (3) Use take(1) or first() for one-time operations. (4) Store subscriptions and call .unsubscribe() in ngOnDestroy. (5) Use DestroyRef with onDestroy callback. The most common leak: subscribing in a component without cleaning up when the component is destroyed.

Q: When do you use Subject vs BehaviorSubject vs ReplaySubject?

A: Subject — multicasts values to current subscribers only, no initial value. BehaviorSubject — requires initial value, emits current value to new subscribers immediately. Use for state that always has a value (current user, selected item). ReplaySubject — caches N past values and replays them, no initial value required. Use when late subscribers need historical values.

Interview Questions

Q: What is the difference between canActivate and canMatch?

A: canActivate prevents navigation to a route but the route is still matched — the user sees a redirect. canMatch prevents the route from even being considered during URL matching — useful when you want different components for the same URL based on user role (admin sees admin dashboard, user sees user dashboard).

Q: How does lazy loading work in Angular?

A: Lazy loading uses dynamic import() to defer downloading a module or component until the user navigates to that route. Angular's build system creates separate JavaScript chunks for lazy routes. On navigation, the router triggers the import, the chunk is downloaded, parsed, and the component is rendered. This reduces the initial bundle size and improves startup performance.

Q: How do you handle unsaved changes in a form when the user navigates away?

A: Use a canDeactivate guard that checks if the form is dirty and shows a confirmation dialog. The guard returns true (allow navigation), false (block), or a UrlTree (redirect). This prevents accidental data loss when users navigate away from a half-filled form.

Q: When do you choose reactive forms over template-driven?

Signal-based store (recommended for most apps)

// Cart store using signals — no library needed
@Injectable({ providedIn: 'root' })
export class CartStore {
  // Private writable state
  private _items = signal<CartItem[]>([]);

  // Public read-only selectors
  readonly items = this._items.asReadonly();
  readonly itemCount = computed(() => this._items().length);
  readonly total = computed(() =>
    this._items().reduce((sum, item) => sum + item.price * item.quantity, 0)
  );
  readonly isEmpty = computed(() => this._items().length === 0);

  // Actions
  addItem(product: Product) {
    this._items.update(items => {
      const existing = items.find(i => i.productId === product.id);
      if (existing) {
        return items.map(i =>
          i.productId === product.id
            ? { ...i, quantity: i.quantity + 1 }
            : i
        );
      }
      return [...items, { productId: product.id, name: product.name,
                          price: product.price, quantity: 1 }];
    });
  }

  removeItem(productId: string) {
    this._items.update(items => items.filter(i => i.productId !== productId));
  }

  updateQuantity(productId: string, quantity: number) {
    if (quantity <= 0) return this.removeItem(productId);
    this._items.update(items =>
      items.map(i => i.productId === productId ? { ...i, quantity } : i)
    );
  }

  clear() { this._items.set([]); }
}

Theory: This signal-based store gives you centralized state management, computed derived state (total, count, isEmpty), immutable updates, and no external library dependency. For most Angular apps with 3 years of complexity, this pattern is sufficient, scalable, and easy to test.

Interview Questions

Q: When would you introduce NgRx vs using signals + services?

A: Use signals + services when: state is shared between a few components, the team is small, and state logic is straightforward. Use NgRx when: the app has complex state transitions, you need time-travel debugging, multiple developers need strict patterns, or you need side effects orchestration (NgRx Effects). Most apps under 50 components do not need NgRx.

Q: What is the Redux pattern and how does NgRx implement it?

A: Redux pattern: single source of truth (store), state is read-only (immutable), changes via pure functions (reducers), triggered by actions. NgRx adds: Selectors (memoized state reads), Effects (side effects like API calls), and Angular DI integration. The tradeoff: more boilerplate and indirection, but very predictable state management in large teams.

12. Angular Security

Theory

Angular has built-in protections against common web vulnerabilities, but you must understand them to use them correctly.

Key security topics

  • XSS (Cross-Site Scripting): Angular auto-sanitizes template bindings. Interpolation ({{ }}) is always safe. [innerHTML] is sanitized. bypassSecurityTrustHtml skips sanitization — use with extreme caution.
  • CSRF (Cross-Site Request Forgery): Use Angular's HttpClientXsrfModule which reads a token from a cookie and sends it as a header. The server must set and validate this token.
  • Authentication: Use JWT tokens stored in HttpOnly cookies (not localStorage). Add auth interceptor to attach tokens. Handle token refresh with interceptors.
  • Authorization: Use route guards (canActivate) for page-level access. Use structural directives (*appHasPermission) for element-level access. Always enforce authorization on the server — client-side guards are UX, not security.
  • Content Security Policy (CSP): Set CSP headers to prevent inline scripts, restrict allowed origins, and block unsafe patterns.
  • Dependency vulnerabilities: Run npm audit regularly. Use tools like Snyk or Dependabot for automated vulnerability scanning.

JWT refresh interceptor

export const tokenRefreshInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);

  return next(req).pipe(
    catchError((error: HttpErrorResponse) => {
      if (error.status === 401 && !req.url.includes('/refresh')) {
        return auth.refreshToken().pipe(
          switchMap(newToken => {
            const cloned = req.clone({
              setHeaders: { Authorization: `Bearer ${newToken}` }
            });
            return next(cloned);
          }),
          catchError(() => {
            auth.logout();
            return throwError(() => error);
          })
        );
      }
      return throwError(() => error);
    })
  );
};

Interview Questions

Q: How does Angular protect against XSS?

A: Angular treats all template values as untrusted by default. Interpolation ({{ }}) escapes HTML entities. Property binding ([innerHTML]) is sanitized — dangerous tags and attributes are stripped. Only DomSanitizer.bypassSecurityTrust* disables sanitization, and it should be used only for trusted content with additional server-side validation.

Q: Where should you store JWT tokens?

A: HttpOnly cookies are the most secure — they are not accessible via JavaScript, preventing XSS-based token theft. If you must use localStorage/sessionStorage (e.g., for third-party auth), understand the XSS risk and implement strict CSP. Never store tokens in plain JavaScript variables that persist in memory longer than needed.

Complete signal-based component

@Component({
  selector: 'app-todo-list',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <h2>Todos ({{ remaining() }} remaining)</h2>

    <input #newTodo (keyup.enter)="addTodo(newTodo.value); newTodo.value = ''" />

    <select (change)="filter.set($any($event.target).value)">
      <option value="all">All</option>
      <option value="active">Active</option>
      <option value="completed">Completed</option>
    </select>

    @for (todo of filteredTodos(); track todo.id) {
      <div [class.completed]="todo.done">
        <input type="checkbox" [checked]="todo.done"
               (change)="toggleTodo(todo.id)" />
        {{ todo.text }}
        <button (click)="removeTodo(todo.id)">×</button>
      </div>
    }
  `
})
export class TodoListComponent {
  // State
  todos = signal<Todo[]>([]);
  filter = signal<'all' | 'active' | 'completed'>('all');

  // Derived state
  remaining = computed(() => this.todos().filter(t => !t.done).length);
  filteredTodos = computed(() => {
    const all = this.todos();
    switch (this.filter()) {
      case 'active': return all.filter(t => !t.done);
      case 'completed': return all.filter(t => t.done);
      default: return all;
    }
  });

  // Side effect: persist to localStorage
  constructor() {
    // Load from localStorage
    const saved = localStorage.getItem('todos');
    if (saved) this.todos.set(JSON.parse(saved));

    // Save whenever todos change
    effect(() => {
      localStorage.setItem('todos', JSON.stringify(this.todos()));
    });
  }

  addTodo(text: string) {
    if (!text.trim()) return;
    this.todos.update(list => [...list, { id: crypto.randomUUID(), text: text.trim(), done: false }]);
  }

  toggleTodo(id: string) {
    this.todos.update(list => list.map(t => t.id === id ? { ...t, done: !t.done } : t));
  }

  removeTodo(id: string) {
    this.todos.update(list => list.filter(t => t.id !== id));
  }
}

Interview Questions

Q: How do signals change Angular's reactivity model?

A: Traditional Angular uses Zone.js to detect async events and run change detection on the entire component tree. Signals create a fine-grained dependency graph — when a signal changes, only the specific computed values and effects that depend on it are recalculated. This is more precise (less wasted work) and enables zoneless Angular where CD is driven entirely by signal changes, not by async event interception.

Q: When would you use effect() and what are the gotchas?

A: Use effect() for side effects: localStorage sync, analytics logging, console debugging, DOM manipulation. Gotchas: (1) Effects run at least once on creation. (2) Don't write to signals inside effects (creates dependency loops) — use untracked() to read without tracking. (3) Effects are cleaned up when the component is destroyed. (4) Effects are not for derived state — use computed() for that.

23. Micro-Frontend Architecture

Theory

Micro-frontends extend the microservice idea to the frontend: independently deployable UI applications composed into a single user experience. At the SDE-3 level you are expected to evaluate whether your org needs micro-frontends, choose an integration strategy, and own the cross-cutting concerns (shared state, routing, design system, auth).

23.1 Integration strategies

StrategyHow it worksProsCons

23.2 Cross-cutting concerns

  • Shared shell: A host app that provides the layout, header, nav, auth context, and router. Remotes plug into named router outlets or designated DOM slots.
  • Shared dependencies: Module Federation's shared config prevents loading Angular/RxJS/CDK multiple times. Pin major versions across teams. Use a singleton: true, strictVersion: true policy for core deps.
  • Communication: Custom Events on window for loose coupling. Shared signal-based services for tighter coupling within the same runtime. Never share state via global variables.
  • Routing: Shell owns top-level routes. Each remote defines child routes. Use loadRemoteModule() in the route config. Deep-link support requires coordination on URL namespace.
  • Auth: Shell handles login and stores the token. Remotes retrieve it via a shared auth service or custom event. Never duplicate auth logic across remotes.
  • Design consistency: Publish a shared design-system library (CSS variables, Angular CDK components) consumed by all remotes.

Interview Questions

Q: When would you recommend micro-frontends vs a modular monolith?

A: Micro-frontends when: (1) multiple autonomous teams own different business domains, (2) independent deployment is a hard requirement, (3) the app is large enough that a single build takes >10 min, (4) different domains have different release cadences. Modular monolith (Nx libraries + lazy loading) when: one or two teams, shared release cycle, full type-safety is more valuable than deployment independence. In most orgs under ~50 frontend engineers, the modular monolith is simpler and faster.

Q: How do you handle version mismatches between shared Angular in micro-frontends?

A: Pin the major Angular version across all remotes using singleton: true, strictVersion: true in Module Federation's shared config. If versions mismatch, the runtime throws instead of silently loading two Angulars (which would crash). Use a monorepo or a shared package.json policy enforced in CI to keep versions aligned. Minor and patch divergence is usually safe.

Q: What are the biggest pitfalls of micro-frontends?

A: (1) Duplicate bundles if shared config is wrong — loading Angular twice is ~80KB wasted. (2) Inconsistent UX if teams don't share a design system. (3) Communication complexity — global state leaks, event naming collisions. (4) Harder E2E testing — you need to deploy all remotes to test a flow. (5) DevEx regression — local dev requires running multiple apps or using a mock shell. Evaluate the operational cost vs the autonomy benefit carefully.

Interview Questions

Q: How do you decide library boundaries in an Nx monorepo?

A: Slice by domain first (checkout, inventory, auth), then by type (feature, data-access, ui, util). A feature lib is a smart component that wires up data-access and ui libs. Data-access libs contain services and API calls. UI libs are pure presentational components. Utils are pure functions with no Angular dependency. Q: What is Nx computation caching and how does it speed up CI?

A: Nx hashes each task's inputs (source files, dependencies, env variables, config). If the hash matches a previous run, it replays the cached output instead of re-executing. Locally this avoids redundant rebuilds. With Nx Cloud, the cache is shared across CI agents and developers — if one developer builds a lib, another developer or CI gets the cached result instantly. This can reduce CI time by 50-80% in large monorepos.

Interview Questions

Q: What is the difference between useClass, useValue, useFactory, and useExisting?

A: useClass: creates a new instance of the class. useValue: provides a static value (configs, constants). useFactory: calls a factory function that can use inject() to read other providers — flexible for conditional logic. useExisting: creates an alias to another token — useful when a class implements multiple interfaces and you want the same singleton accessible via different tokens.

Q: What is the injection context and when does inject() work?

A: inject() works in: constructors of classes created by DI, field initializers of such classes, and factory functions passed to useFactory, InjectionToken, runInInjectionContext(). It does NOT work in: lifecycle hooks (ngOnInit, etc.), event handlers, setTimeout callbacks, or plain functions called outside the injection context. At SDE-3 level, you should know how to use runInInjectionContext when you need DI in places that don't naturally have it.

Q: How do multi-providers enable a plugin architecture?

A: Multi-providers let you register multiple implementations under the same token. When injected, you get an array of all implementations. This is a plugin pattern: the consuming code iterates over all plugins without knowing which ones are registered. Angular uses this internally for interceptors (HTTP_INTERCEPTORS), app initializers (APP_INITIALIZER), and route guards. You can build your own — validation plugins, analytics trackers, feature extensions — all registered via multi: true.

Custom operator — retry with exponential backoff

import { Observable, timer, throwError } from 'rxjs';
import { mergeMap, retryWhen, scan } from 'rxjs/operators';

export function retryWithBackoff<T>(
  maxRetries: number = 3,
  initialDelay: number = 1000,
  maxDelay: number = 30000
) {
  return (source: Observable<T>): Observable<T> =>
    source.pipe(
      retryWhen(errors =>
        errors.pipe(
          scan((retryCount, error) => {
            if (retryCount >= maxRetries) throw error;
            return retryCount + 1;
          }, 0),
          mergeMap(retryCount => {
            const delay = Math.min(initialDelay * Math.pow(2, retryCount - 1), maxDelay);
            console.log(`Retry #${retryCount} after ${delay}ms`);
            return timer(delay);
          })
        )
      )
    );
}

// Usage:
this.http.get<Data>('/api/unstable-endpoint').pipe(
  retryWithBackoff(3, 1000, 10000)
).subscribe(data => this.data.set(data));

import { Observable, of, shareReplay, timer, switchMap, startWith } from 'rxjs';

export function cacheWithTTL<T>(ttl: number) {
  let cache$: Observable<T> | null = null;
  let lastFetch = 0;

  return (source: Observable<T>): Observable<T> => {
    const now = Date.now();
    if (!cache$ || now - lastFetch > ttl) {
      lastFetch = now;
      cache$ = source.pipe(shareReplay(1));
    }
    return cache$;
  };
}

}

Q: How do you write a custom RxJS operator?

A: A custom operator is a function that returns (source: Observable<T>) => Observable<R>. Inside, you pipe the source through existing operators to compose new behavior. Keep operators pure — no side effects or shared mutable state (except intentional caching). Type the generics properly so the operator is reusable. Test operators independently using marble testing.

Q: What is the difference between a pipeable operator and a creation operator?

A: Pipeable operators transform an existing observable (map, filter, switchMap — used inside .pipe()). Creation operators create a new observable from scratch (of, from, interval, timer, fromEvent). Custom operators are almost always pipeable — they receive a source and return a transformed observable.

Circuit breaker pattern

@Injectable({ providedIn: 'root' })
export class CircuitBreaker {
  private failures = new Map<string, { count: number; openedAt: number }>();
  private threshold = 5;
  private resetTimeout = 30000; // 30 seconds

  canRequest(key: string): boolean {
    const state = this.failures.get(key);
    if (!state) return true;
    if (state.count < this.threshold) return true;
    // Circuit is OPEN — check if reset timeout has passed
    if (Date.now() - state.openedAt > this.resetTimeout) {
      this.failures.delete(key); // half-open: allow one request
      return true;
    }
    return false; // Circuit still open — reject
  }

  recordFailure(key: string) {
    const state = this.failures.get(key) ?? { count: 0, openedAt: 0 };
    state.count++;
    if (state.count >= this.threshold) state.openedAt = Date.now();
    this.failures.set(key, state);
  }

  recordSuccess(key: string) {
    this.failures.delete(key);
  }
}

// Usage in a service
getData(endpoint: string): Observable<Data> {
  if (!this.circuitBreaker.canRequest(endpoint)) {
    return throwError(() => new Error('Service temporarily unavailable'));
  }
  return this.http.get<Data>(endpoint).pipe(
    tap(() => this.circuitBreaker.recordSuccess(endpoint)),
    catchError(err => {
      this.circuitBreaker.recordFailure(endpoint);
      return throwError(() => err);
    })
  );
}

SDE-3 engineers are expected to lead migrations — not just write code, but plan the strategy, manage risk, and execute incrementally without breaking production.

32.1 Common migration paths

MigrationStrategyKey decisions
NgModules → StandaloneIncremental — use ng generate @angular/core:standalone schematicStart with leaf components, work upward. Can coexist — standalone components can import NgModules via importProvidersFrom

32.2 Migration principles

  • Incremental, not big-bang: Migrate one module/feature at a time. Ship to production after each increment.
  • Coexistence: Old and new patterns must work side by side during the transition.
  • Automation: Use Angular schematics for automated migrations wherever possible.
  • Testing gate: No migration PR without tests passing. Add tests for migrated code if they don't exist.
  • Rollback plan: Every migration step should be revertable with a git revert.
  • Communication: Document the migration plan, share with the team, get buy-in before starting.

Interview Questions

Q: How would you migrate a large Angular app from NgModules to standalone?

A: (1) Run the Angular schematic as a starting point. (2) Start with leaf components (no children) — they have the fewest dependencies. (3) Convert bottom-up — children before parents. (4) Use importProvidersFrom(ExistingModule) as a bridge during transition. (5) Update route configs from loadChildren to loadComponent. (6) Remove empty NgModules after all their declarations are standalone. (7) Do it in small PRs — each PR converts one module, runs full CI, and ships to production.

Q: What is the strangler fig pattern and how does it apply to frontend migration?

A: The strangler fig pattern incrementally replaces an old system by building new features alongside it, then gradually routing traffic from old to new. For AngularJS → Angular: run both frameworks in the same app (ngUpgrade) or use micro-frontends (old routes served by AngularJS, new routes by Angular). Over time, migrate route by route until AngularJS is completely removed. Never do a big-bang rewrite — it takes too long and has too much risk.

describe('SearchService', () => {
  let scheduler: TestScheduler;

  beforeEach(() => {
    scheduler = new TestScheduler((actual, expected) => {
      expect(actual).toEqual(expected);
    });
  });

  it('should debounce and deduplicate search terms', () => {
    scheduler.run(({ cold, expectObservable }) => {
      // Simulate user typing: 'a' at 0ms, 'ab' at 10ms, 'abc' at 20ms
      const input$ =    cold('a-b-c---|', { a: 'a', b: 'ab', c: 'abc' });
      const expected =  '    --------c|';  // Only 'abc' after debounce

      const result$ = input$.pipe(
        debounceTime(30, scheduler),
        distinctUntilChanged()
      );

      expectObservable(result$).toBe(expected, { c: 'abc' });
    });
  });
});

Interview Questions

Q: What is marble testing and when do you use it?

A: Marble testing is a technique for testing RxJS observables using ASCII marble diagrams that represent values over virtual time. ---a--b--| means: value 'a' at frame 3, 'b' at frame 6, complete at frame 9. It is essential for testing time-dependent operators (debounceTime, delay, timeout, switchMap) without real timers. Without marble testing, you'd need setTimeout in tests, making them slow and flaky.

Q: What are component test harnesses and why use them?

A: Test harnesses are an abstraction layer over component DOM queries. Instead of using querySelector('.product-title') (brittle — breaks when CSS changes), you use harness.getProductName() (stable API). Angular Material ships harnesses for all its components. Building harnesses for your own components lets consumers (other teams, E2E tests) interact with your components through a stable API. This is especially important in a design system consumed by multiple teams.

36. Design System & Component Library

Theory

SDE-3 engineers often lead the creation of a shared component library consumed by multiple teams. This is different from building one-off components — it requires API design, documentation, versioning, and governance.

Key principles

  • Headless / unstyled primitives: Build behavior-only components (like CDK) that consumers can style. Or provide a styled library with CSS custom properties for theming.
  • Composition over configuration: Prefer <card><card-header>...</card-header></card> over <card [title]="..." [subtitle]="..." [actions]="...">. Composition via content projection is more flexible.
  • Accessibility by default: Every component ships with proper ARIA, keyboard navigation, and focus management.
  • Storybook: Visual documentation and testing for every component variant.
  • Semantic versioning: Breaking API changes require a major version bump. Communicate deprecations early.
  • Changelog: Auto-generated from conventional commits.
  • Component test harnesses: Ship CDK harnesses so consumers can test their code without depending on your DOM structure.

37. Architecture Decision Records & Technical Leadership

Theory

At SDE-3, you are a technical leader — not just a coder. You make architecture decisions, document them, mentor juniors, and set standards for the team.

37.1 Architecture Decision Records (ADRs)

An ADR is a short document that captures a significant architectural decision, the context, the options considered, and the rationale for the chosen option.

// docs/adr/002-state-management-approach.md

# ADR-002: State Management Approach

## Status: Accepted
## Date: 2024-03-15

## Context
Our app has 40+ components sharing state across 8 feature modules.
Currently using ad-hoc services with BehaviorSubject, causing
inconsistent patterns and difficulty in debugging state changes.

## Options Considered
1. **Signal-based stores (custom)** — lightweight, Angular-native, no library
2. **NgRx Store** — Redux pattern, time-travel debugging, effects
3. **NgRx Signal Store** — signal-based, less boilerplate than NgRx Store
4. **Keep current approach** — refactor existing services

## Decision
Option 3: NgRx Signal Store

## Rationale
- Signals align with Angular's direction (zoneless future)
- Less boilerplate than classic NgRx Store (no actions/reducers)
- Built-in computed state and effects
- DevTools support for debugging
- Team already familiar with signals from recent migration
- NgRx ecosystem (effects, entity) available when needed

## Consequences
- Team needs 1-2 days of NgRx Signal Store training
- Existing BehaviorSubject services will be migrated incrementally
- New features must use Signal Store from day one

37.2 Code review leadership

  • Review for architecture, not just syntax: Is the component doing too much? Is state in the right place? Is this testable?
  • Be constructive: "Consider using switchMap here to avoid race conditions" > "This is wrong."
  • Set up review checklists: Performance (OnPush?), accessibility (semantic HTML?), testing (coverage?), security (sanitization?).
  • Automate what you can: Linting catches style issues. Bundle budgets catch size regressions. Let humans review design and logic.
  • Timebox reviews: Review within 4 hours. Don't block the team.

37.3 Mentoring patterns

  • Pair programming on complex features — share context, transfer knowledge live.
  • Architecture workshops — walk the team through system design decisions.
  • "Why" documentation — code tells you what, comments and ADRs tell you why.
  • Runbooks — how to deploy, how to rollback, how to debug common production issues.

Interview Questions

Q: How do you make technical decisions for the team?

A: (1) Identify the problem clearly — what pain are we solving? (2) List options with pros/cons. (3) Build a small proof-of-concept if the decision is high-risk. (4) Discuss with the team — get input, not just buy-in. (5) Document the decision as an ADR (Architecture Decision Record). (6) Commit to the decision — avoid revisiting without new evidence. (7) Monitor the outcome — was the predicted benefit realized? ADRs prevent "why did we choose this?" conversations 6 months later.

Q: How do you handle tech debt in a fast-moving team?

A: (1) Track tech debt like any other work — add it to the backlog with impact and effort estimates. (2) Allocate 15-20% of each sprint to debt reduction. (3) Attach debt reduction to feature work — "while building feature X, we'll also refactor the related service." (4) Prioritize debt that slows the team (brittle tests, unclear module boundaries) over cosmetic debt. (5) Never let debt accumulate silently — visibility is the first step to managing it.

Q: Describe your approach to code reviews.

A: I review for: (1) Correctness — does it do what it should? (2) Architecture — is this the right abstraction? Is state in the right place? (3) Performance — OnPush, trackBy, subscription cleanup. (4) Testability — can this be unit tested without complex setup? (5) Security — user input handling, auth checks. I automate style/lint checks so human reviews focus on design. I aim to review within 4 hours and give specific, actionable feedback with code examples.
