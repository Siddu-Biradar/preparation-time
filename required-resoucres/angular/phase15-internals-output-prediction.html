1. Angular Compiler Pipeline — Complete Deep Dive

Understanding Angular's compiler is the ultimate differentiator in senior interviews. The compiler transforms templates and TypeScript into optimized JavaScript that Angular's runtime can execute.

Compilation Phases

┌─────────────────────────────────────────────────────────────┐
│                    ANGULAR COMPILER (ngc)                     │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. PARSING PHASE                                            │
│     ├── Template Parsing → Template AST                      │
│     ├── CSS Parsing → Scoped Styles                          │
│     └── Metadata Collection (decorators → metadata)          │
│                                                              │
│  2. ANALYSIS PHASE                                           │
│     ├── Resolve imports, declarations, exports               │
│     ├── Build dependency graph (which component uses what)   │
│     ├── Semantic analysis (validate bindings, directives)    │
│     └── Detect circular dependencies                         │
│                                                              │
│  3. TYPE-CHECKING PHASE (strictTemplates)                    │
│     ├── Generate Type Check Block (TCB) per component        │
│     ├── TCB = TypeScript code representing template logic    │
│     ├── Feed TCB to TypeScript compiler                      │
│     └── Report type errors as template errors                │
│                                                              │
│  4. CODE GENERATION (EMIT) PHASE                             │
│     ├── Generate ɵcmp (component definition)                 │
│     ├── Generate ɵfac (factory function)                     │
│     ├── Generate template function (Ivy instructions)        │
│     ├── Generate ɵdir, ɵpipe, ɵmod definitions              │
│     └── Output .js + .d.ts with Angular metadata             │
│                                                              │
└──────────────────────────────────────────────────────────────┘

Type Check Block (TCB) — How Template Type-Checking Works

// Given this component:
@Component({
  template: `
    <input [value]="user.name" (input)="update($event)" />
    <app-card [title]="user.age"></app-card>
  `
})
class MyComponent {
  user = { name: 'John', age: 30 };
  update(e: Event) {}
}

// Angular generates a TCB (simplified):
function _tcb_MyComponent(ctx: MyComponent) {
  // Validates [value]="user.name" — is user.name assignable to string?
  const _binding1: string = ctx.user.name; // ✓

  // Validates (input)="update($event)" — $event is Event
  const _event: Event = null!;
  ctx.update(_event); // ✓

  // Validates [title]="user.age" — is number assignable to AppCard's title: string?
  const _cardCtx: AppCardComponent = null!;
  _cardCtx.title = ctx.user.age; // ✗ ERROR: Type 'number' is not assignable to 'string'
}

Partial Compilation (for Libraries)

// Libraries use "partial compilation" — generates INTERMEDIATE format
// that the consuming app's compiler finishes ("linking" step)

// Why? Because libraries don't know the consumer's Angular version at build time.
// Partial compilation produces version-agnostic intermediate code.

// tsconfig.json for library:
{
  "angularCompilerOptions": {
    "compilationMode": "partial"  // Only for LIBRARIES
  }
}

// At build time in the consuming app, the Angular "linker" converts
// partial declarations (ɵɵngDeclareComponent) → full definitions (ɵɵdefineComponent)

Incremental Compilation

// Angular's compiler supports incremental rebuilds:
// 1. File dependency graph tracked
// 2. On change, only affected files + their dependents recompiled
// 3. TCBs regenerated only for affected components

// How Angular determines "affected":
// - Component A uses Directive B in its template
// - If B's public API changes → A is re-type-checked
// - If B's template changes → only B is re-compiled (locality!)

// IVY LOCALITY PRINCIPLE:
// Each component can be compiled independently knowing only about
// its direct dependencies' PUBLIC API (inputs, outputs, selectors).
// This is what makes incremental compilation fast.
🎯 Interview Questions:
  • What is a Type Check Block? → TypeScript function generated from template that TypeScript compiler validates
  • What is the Ivy locality principle? → Each component compiled independently using only public API of dependencies
  • Why do libraries use partial compilation? → They don't know consumer's Angular version; linker finalizes at build time
  • How does Angular achieve incremental builds? → Dependency graph tracking; only recompile affected files and dependents
  • What happens if you disable strictTemplates? → No TCB generated; template errors only caught at runtime

2. Ivy Renderer & Instruction Set

How Templates Become DOM Instructions

// Template:
// <div class="container">
//   <h1>{{ title }}</h1>
//   <app-child [data]="items" />
// </div>

// Compiled to (simplified Ivy instructions):
function MyComponent_Template(rf: RenderFlags, ctx: MyComponent) {
  if (rf & RenderFlags.Create) {          // CREATION PHASE (runs once)
    ɵɵelementStart(0, 'div', ['class', 'container']);
      ɵɵelementStart(1, 'h1');
        ɵɵtext(2);                         // placeholder for text node
      ɵɵelementEnd();
      ɵɵelement(3, 'app-child', ['data']); // self-closing element
    ɵɵelementEnd();
  }
  if (rf & RenderFlags.Update) {          // UPDATE PHASE (runs on every CD)
    ɵɵadvance(2);                          // move cursor to text node
    ɵɵtextInterpolate(ctx.title);          // update text content
    ɵɵadvance(1);                          // move to app-child
    ɵɵproperty('data', ctx.items);         // update input binding
  }
}

Key Ivy Instructions

InstructionPurpose
ɵɵelementStart / ɵɵelementEndCreate opening/closing DOM element
ɵɵelementSelf-closing element (no children)
ɵɵtextCreate text node
ɵɵtextInterpolateUpdate text content (interpolation)
ɵɵpropertyUpdate property binding
ɵɵlistenerAttach event listener
ɵɵtemplateCreate embedded view (for *ngIf, @if)
ɵɵadvanceMove internal cursor to next element
ɵɵpipe / ɵɵpipeBindCreate/invoke pipe
ɵɵdefineComponentComponent definition with metadata

LView & TView — Runtime Data Structures

// TView (Template View) — SHARED blueprint, created once per component TYPE
// Contains: node definitions, binding indices, directive list, pipes
// Think of it as the "class" — the shape/schema

// LView (Logical View) — PER INSTANCE data array
// Contains: actual DOM nodes, binding values, directive instances
// Think of it as the "object" — the actual runtime data

// Why this matters:
// - Memory efficiency: 1000 list items share 1 TView, have 1000 LViews
// - CD checks LView[bindingIndex] === newValue for dirty checking
// - LView is a flat array (not a tree) for cache-line efficiency

// LView layout:
// [FLAGS, PARENT, TVIEW, HOST, ...DIRECTIVE_INSTANCES, ...BINDING_VALUES, ...CHILD_VIEWS]

3. afterRender & afterNextRender Hooks

Angular 16+ introduced afterRender and afterNextRender — hooks that run after Angular has rendered DOM. They replace many ngAfterViewInit + setTimeout hacks.

The 4 Render Phases

// Phases run in a specific order EVERY time Angular renders:
// 1. earlyRead  — Read DOM layout before writes (fast reads)
// 2. write      — Write to DOM (mutations, style changes)
// 3. mixedReadWrite — Legacy compatibility (avoid this)
// 4. read       — Final DOM reads after all writes complete

import { afterRender, afterNextRender, AfterRenderPhase } from '@angular/core';

@Component({ ... })
export class ChartComponent {
  private chartEl = viewChild.required<ElementRef>('chart');

  constructor() {
    // Runs ONCE after first render (replacement for ngAfterViewInit)
    afterNextRender(() => {
      this.initChart(this.chartEl().nativeElement);
    });

    // Runs EVERY render cycle (replacement for ngAfterViewChecked)
    afterRender(() => {
      this.updateChartDimensions();
    });
  }
}

// Using specific phases:
afterRender({
  earlyRead: () => {
    // Read layout metrics BEFORE any writes (avoids forced reflow)
    const rect = this.el.nativeElement.getBoundingClientRect();
    return rect; // Return value passed to write phase
  },
  write: (rect) => {
    // Now make DOM mutations based on the read
    this.tooltip.style.top = `${rect.bottom + 10}px`;
  }
});

Why Phases Matter (Layout Thrashing Prevention)

// WITHOUT phases (causes layout thrashing):
afterRender(() => {
  const height = el.offsetHeight;   // READ → triggers layout
  el.style.width = height + 'px';   // WRITE → invalidates layout
  const width = el.offsetWidth;     // READ AGAIN → forces REFLOW!
  el2.style.height = width + 'px';  // WRITE
});

// WITH phases (batched reads and writes):
afterRender({
  earlyRead: () => ({
    height: el.offsetHeight,        // All reads batched together
    width: el.offsetWidth
  }),
  write: (dims) => {
    el.style.width = dims.height + 'px';   // All writes batched
    el2.style.height = dims.width + 'px';
  }
});
// Result: Only ONE layout calculation, not multiple forced reflows

afterNextRender vs ngAfterViewInit

AspectngAfterViewInitafterNextRender
Runs on server (SSR)?YES (problematic!)NO (browser-only)
DOM guaranteed?Yes, but in Zone contextYes, truly after render
Phase control?NoYes (earlyRead, write, read)
Injection context?No (use constructor)YES (can use inject())
Works with signals?YesYes (designed for signals)
🎯 Interview Questions:
  • When would you use afterNextRender vs ngAfterViewInit? → afterNextRender is SSR-safe, has render phases, works in injection context
  • What is layout thrashing? How do render phases prevent it? → Interleaved reads/writes force multiple reflows; phases batch all reads then all writes
  • What's the difference between afterRender and afterNextRender? → afterRender runs every CD; afterNextRender runs once

4. Directive Composition API

Angular 15+ allows composing multiple directives on a host component without the consumer needing to apply them manually. This is critical for building clean component libraries.

// The Problem: Users must remember to add related directives
// <button appRipple appTooltip="Save" appLoadingState>Save</button>

// The Solution: Compose directives inside the component
@Component({
  selector: 'app-button',
  hostDirectives: [
    {
      directive: RippleDirective,
      inputs: ['rippleColor: color'],     // Expose/remap inputs
      outputs: ['rippleComplete: onRipple']
    },
    {
      directive: TooltipDirective,
      inputs: ['tooltipText: tooltip'],
    },
    LoadingStateDirective  // All inputs/outputs hidden from consumer
  ],
  template: `<ng-content />`
})
export class AppButtonComponent {}

// Usage (clean — no extra directives needed):
<app-button color="blue" tooltip="Save changes">Save</app-button>

// Key Rules:
// 1. hostDirectives must be standalone
// 2. Directive lifecycle hooks still fire (in order of declaration)
// 3. Host bindings from all directives are merged
// 4. If two directives bind the same host property, last one wins
// 5. Consumers can still add MORE directives on top

Advanced: Directive Inheritance vs Composition

// Inheritance (limited — single parent only):
@Directive({ ... })
class BaseTooltip { @Input() text = ''; show() {} hide() {} }

@Directive({ selector: '[appRichTooltip]' })
class RichTooltip extends BaseTooltip {
  // Inherits inputs + can override methods
  override show() { /* rich version */ }
}

// Composition (preferred — multiple behaviors):
@Component({
  hostDirectives: [
    FocusableDirective,      // Adds focus ring + keyboard nav
    DisableableDirective,    // Adds disabled state handling
    { directive: TooltipDirective, inputs: ['tooltipText'] }
  ]
})
class MyWidget {}

// The component AUTOMATICALLY gets all behaviors without inheritance!

5. Structural Directive Microsyntax

The microsyntax is the grammar behind *ngIf="expr", *ngFor="let x of items". Understanding it is essential for building custom structural directives.

Microsyntax Grammar

// *directive="expression" desugars to:
// <ng-template [directive]="expression">...</ng-template>

// Full grammar:
// *prefix="( :let | :expression ) (';' | ',')? ( :let | :as | :keyExp )*"
//
// :let = "let" identifier ( '=' identifier )?
// :as = identifier "as" identifier  
// :keyExp = identifier ':'? expression ( 'as' identifier )?

// Examples:

// *ngIf="condition; else elseBlock; let result"
// Desugars to:
<ng-template [ngIf]="condition" [ngIfElse]="elseBlock" let-result="ngIf">

// *ngFor="let item of items; index as i; trackBy: trackFn"
// Desugars to:
<ng-template ngFor [ngForOf]="items" let-item [ngForTrackBy]="trackFn" let-i="index">

Building a Custom Structural Directive with Context

// Custom *appRepeat="3; let i = index; let isLast = last"
interface RepeatContext {
  $implicit: number;   // Value for bare "let x"
  index: number;
  count: number;
  first: boolean;
  last: boolean;
}

@Directive({ selector: '[appRepeat]', standalone: true })
export class RepeatDirective {
  private templateRef = inject(TemplateRef<RepeatContext>);
  private vcr = inject(ViewContainerRef);

  @Input() set appRepeat(count: number) {
    this.vcr.clear();
    for (let i = 0; i < count; i++) {
      this.vcr.createEmbeddedView(this.templateRef, {
        $implicit: i,        // Available as "let x" (bare variable)
        index: i,            // Available as "let i = index"
        count,
        first: i === 0,      // Available as "let f = first"
        last: i === count - 1
      });
    }
  }
}

// Usage:
// <div *appRepeat="5; let i = index; let isLast = last">
//   Item {{ i }} {{ isLast ? '(last!)' : '' }}
// </div>

$implicit — The Magic Variable

// $implicit is the value that a bare "let x" receives
// without specifying "= propertyName"

// In ngFor: $implicit = the current item
// Template: let item    → item = context.$implicit

// In ngIf: $implicit = the condition value  
// Template: let result  → result = context.$implicit (= condition value)

// Custom directive:
this.vcr.createEmbeddedView(this.templateRef, {
  $implicit: 'hello',  // "let x" → x = 'hello'
  name: 'world'        // "let y = name" → y = 'world'
});

ngTemplateOutlet with Typed Context

// Passing context to projected templates

@Component({

Rendering Tree Structures

interface TreeNode {

@Component({

Dynamic Template Selection

// Different templates based on item type
@Component({
  template: `
    <ng-template #textTpl let-item>
      <p>{{ item.content }}</p>
    </ng-template>

    <ng-template #imageTpl let-item>
      <img [src]="item.url" [alt]="item.alt" />
    </ng-template>

    <ng-template #videoTpl let-item>
      <video [src]="item.url" controls></video>
    </ng-template>

    @for (item of items(); track item.id) {
      <ng-container
        [ngTemplateOutlet]="getTemplate(item.type)"
        [ngTemplateOutletContext]="{ $implicit: item }"
      />
    }
  `
})
export class FeedComponent {
  @ViewChild('textTpl') textTpl!: TemplateRef<any>;
  @ViewChild('imageTpl') imageTpl!: TemplateRef<any>;
  @ViewChild('videoTpl') videoTpl!: TemplateRef<any>;

  items = input.required<FeedItem[]>();

  getTemplate(type: string): TemplateRef<any> {
    const map: Record<string, TemplateRef<any>> = {
      text: this.textTpl,
      image: this.imageTpl,
      video: this.videoTpl
    };
    return map[type] || this.textTpl;
  }
}

7. View Queries — static vs dynamic Timing

// The `static` flag controls WHEN the query resolves

@ViewChild('myEl', { static: true })  elRef!: ElementRef;
// Resolved in ngOnInit (before CD runs)
// ONLY works if element is NOT inside *ngIf, @if, *ngFor, @for, etc.
// Use for: elements that are ALWAYS present in template

@ViewChild('myEl', { static: false }) elRef!: ElementRef; // DEFAULT
// Resolved in ngAfterViewInit (after first CD)
// Works with conditional/dynamic elements
// Use for: elements inside structural directives

// GOTCHA: If you need the element in ngOnInit for initial setup,
// you MUST use static: true — but the element must be unconditional.

// With Signals (Angular 17+):
el = viewChild('myEl');              // Signal<ElementRef | undefined>
el = viewChild.required('myEl');     // Signal<ElementRef> (throws if missing)

// ContentChild works the same way:
@ContentChild(HeaderDirective, { static: true }) header!: HeaderDirective;
// Available in ngOnInit if projected content is unconditional

8. forRoot / forChild Pattern Deep Dive

// PROBLEM: Lazy-loaded modules create CHILD injectors.
// If a lazy module imports a module with providers, it gets its OWN instance!

// SOLUTION: forRoot() / forChild() pattern

@NgModule({ declarations: [TooltipDirective, ModalComponent] })
export class UiModule {
  // forRoot: provides SINGLETON services (only called in AppModule)
  static forRoot(config: UiConfig): ModuleWithProviders<UiModule> {
    return {
      ngModule: UiModule,
      providers: [
        TooltipService,           // Singleton
        ModalService,             // Singleton  
        { provide: UI_CONFIG, useValue: config }
      ]
    };
  }

  // forChild: NO providers (safe for lazy modules — uses parent's singleton)
  static forChild(): ModuleWithProviders<UiModule> {
    return {
      ngModule: UiModule,
      providers: []  // Empty! Uses root providers
    };
  }
}

// AppModule:
imports: [UiModule.forRoot({ theme: 'dark' })]  // ← provides singletons

// LazyFeatureModule:
imports: [UiModule.forChild()]  // ← only gets declarations, uses root services

// IN STANDALONE WORLD (Angular 15+):
// This pattern is OBSOLETE! Use:
// - providedIn: 'root' for singletons
// - Route-level providers for scoped services
// - provideRouter(routes) instead of RouterModule.forRoot(routes)
⚠️ Common Bug: Importing a module with providers in a lazy module WITHOUT forChild() creates a SECOND instance of the service. This causes subtle bugs where lazy features have stale/different state than the rest of the app.

9. inject() Context Edge Cases

// inject() can ONLY be called in an "injection context":
// ✅ Field initializers
// ✅ Constructor body
// ✅ Factory functions (useFactory, InjectionToken factory)
// ✅ afterNextRender / afterRender callbacks
// ✅ Inside runInInjectionContext()
// ❌ ngOnInit, ngOnChanges, lifecycle hooks
// ❌ Event handlers, setTimeout callbacks
// ❌ Regular methods called later

// Example: inject() in field initializer (works!)
@Component({ ... })
class MyComponent {
  private http = inject(HttpClient);            // ✅
  private route = inject(ActivatedRoute);       // ✅
  private destroy = inject(DestroyRef);         // ✅
  
  data$ = inject(HttpClient).get('/api/data');  // ✅ (inline)
}

// Example: inject() in ngOnInit (FAILS!)
ngOnInit() {
  const http = inject(HttpClient); // ❌ ERROR: inject() must be called in injection context
}

// Workaround: runInInjectionContext
import { Injector, runInInjectionContext } from '@angular/core';

@Component({ ... })
class MyComponent {
  private injector = inject(Injector);

  laterMethod() {
    runInInjectionContext(this.injector, () => {
      const svc = inject(SomeService); // ✅ Works now!
    });
  }
}

// Common Pattern: Creating injection context in utility functions
export function injectDestroy(): Observable<void> {
  // Must be called during construction (field init or constructor)
  const destroy$ = new Subject<void>();
  inject(DestroyRef).onDestroy(() => {
    destroy$.next();
    destroy$.complete();
  });
  return destroy$.asObservable();
}

10. Output Prediction Challenges

Rules for solving Angular output questions:
  1. Lifecycle hooks fire in a SPECIFIC order (see diagram above)
  2. Parent lifecycle hooks wrap child hooks (parent init → child init → parent afterViewInit)
  3. OnPush + object mutation = NO re-render
  4. Zone.js means setTimeout/Promise triggers CD (unless runOutsideAngular)
  5. Signals are glitch-free (computed never shows intermediate state)
  6. async pipe subscribes in ngOnInit and unsubscribes in ngOnDestroy

Challenge 1: Lifecycle Hook Ordering

// What's the console output when AppComponent renders?

@Component({
  selector: 'app-child',
  template: '<p>child</p>'
})
class ChildComponent implements OnInit, AfterViewInit, AfterContentInit {
  ngOnInit() { console.log('Child OnInit'); }
  ngAfterContentInit() { console.log('Child AfterContentInit'); }
  ngAfterViewInit() { console.log('Child AfterViewInit'); }
}

@Component({
  selector: 'app-root',
  template: '<app-child />'
})
class AppComponent implements OnInit, AfterViewInit, AfterContentInit {
  ngOnInit() { console.log('Parent OnInit'); }
  ngAfterContentInit() { console.log('Parent AfterContentInit'); }
  ngAfterViewInit() { console.log('Parent AfterViewInit'); }
}
Answer 
Parent OnInit
Parent AfterContentInit
Child OnInit
Child AfterContentInit
Child AfterViewInit
Parent AfterViewInit     // ← Parent WAITS for child's view!

Rule: Parent's OnInit/AfterContentInit fire BEFORE children. But Parent's AfterViewInit fires AFTER all children's AfterViewInit (because parent's "view" includes child components).

Challenge 2: OnPush + Object Mutation

@Component({
  selector: 'app-child',
  template: '{{ user.name }}',
  changeDetection: ChangeDetectionStrategy.OnPush
})
class ChildComponent {
  @Input() user!: { name: string };
}

@Component({
  selector: 'app-root',
  template: '<app-child [user]="user" /> <button (click)="update()">Update</button>'
})
class AppComponent {
  user = { name: 'Alice' };
  
  update() {
    this.user.name = 'Bob';  // Mutation!
  }
}

// Q: After clicking "Update", what does child display?
Answer

Still displays "Alice"!

OnPush checks @Input REFERENCE. this.user.name = 'Bob' mutates the object but doesn't change the reference. The child's OnPush strategy sees the same object reference and SKIPS re-rendering.

Fix: this.user = { ...this.user, name: 'Bob' }; (new reference)

Challenge 3: async pipe + switchMap Cancellation

@Component({
  template: '{{ result$ | async }}'
})
class SearchComponent implements OnInit {
  search$ = new Subject<string>();
  result$!: Observable<string>;

  ngOnInit() {
    this.result$ = this.search$.pipe(
      switchMap(term => {
        console.log('Fetching:', term);
        return of(`Result for ${term}`).pipe(delay(1000));
      })
    );
  }

  ngAfterViewInit() {
    this.search$.next('Angular');
    setTimeout(() => this.search$.next('React'), 500);
  }
}

// Q: What gets logged? What does the template show after 1.5s?
Answer 
// Console:
"Fetching: Angular"     // t=0ms
"Fetching: React"       // t=500ms (switchMap CANCELS "Angular" request)

// Template after 1.5s:
"Result for React"      // Only this — "Angular" was cancelled by switchMap

Rule: switchMap cancels the previous inner observable when a new emission arrives. "Angular" request never completes because "React" is emitted 500ms later (before the 1000ms delay).

Challenge 4: Signal Computed Glitch-Free Guarantee

const firstName = signal('John');
const lastName = signal('Doe');
const fullName = computed(() => {
  console.log('computed runs');
  return `${firstName()} ${lastName()}`;
});

effect(() => {
  console.log('effect:', fullName());
});

// After initial run, execute:
firstName.set('Jane');
lastName.set('Smith');

// Q: How many times does "computed runs" log for the batch update?
// Q: Does effect ever see "Jane Doe" (intermediate state)?
Answer

computed runs: ONCE for the batch (when finally read)

Effect NEVER sees "Jane Doe" — Angular signals are glitch-free. Effects are scheduled, not synchronous. By the time the effect runs, both signals have their final values.

The notification is: "signals are dirty" → effect scheduled → effect runs → reads computed → computed evaluates with BOTH new values → "Jane Smith"

Challenge 6: ContentChild vs ViewChild Resolution

@Component({
  selector: 'app-wrapper',
  template: `
    <ng-content />
    <p #viewEl>View Element</p>
  `
})
class WrapperComponent implements AfterContentInit, AfterViewInit {
  @ContentChild('projectedEl') content!: ElementRef;
  @ViewChild('viewEl') view!: ElementRef;

  ngAfterContentInit() {
    console.log('Content:', this.content?.nativeElement?.textContent);
    console.log('View:', this.view?.nativeElement?.textContent);
  }
  ngAfterViewInit() {
    console.log('Content2:', this.content?.nativeElement?.textContent);
    console.log('View2:', this.view?.nativeElement?.textContent);

}

View: undefined                  // ❌ ViewChild NOT available yet!

Challenge 7: Dependency Injection Hierarchy

@Injectable()
class CounterService {

}

// Q: What numbers do the two app-child components display?
Answer

First child: 1, Second child: 2

Challenge 8: ngOnChanges vs Signal Input

// With traditional @Input + ngOnChanges:
@Component({ selector: 'app-a', template: '{{ label }}' })
class CompA implements OnChanges {
  @Input() value = 0;
  label = '';
  ngOnChanges(changes: SimpleChanges) {
    if (changes['value']) {
      this.label = `prev=${changes['value'].previousValue}, curr=${changes['value'].currentValue}`;
    }
  }
}

// With signal input:
@Component({ selector: 'app-b', template: '{{ label() }}' })
class CompB {
  value = input(0);
  label = computed(() => `value=${this.value()}`);
}

// Parent: <app-a [value]="x" /><app-b [value]="x" />
// Parent sets x = 5 (initial was 0)

// Q: What does CompA's ngOnChanges receive?
// Q: Can CompB access previousValue?
Answer

CompA: prev=0, curr=5 — ngOnChanges provides SimpleChange with previousValue/currentValue.

CompB: Can ONLY see current value value=5. Signal inputs don't track previous values. If you need previous, use effect() with a local variable or toObservable() with pairwise().

// Workaround for previous value with signals:
prevValue = signal(0);
value = input(0);
constructor() {
  effect(() => {
    const curr = this.value();
    // Access this.prevValue() for previous
    this.prevValue.set(curr); // Update after use
  });
}

Challenge 10: ExpressionChangedAfterItHasBeenChecked

@Component({
  selector: 'app-child',
  template: '{{ value }}'
})
class ChildComponent implements AfterViewInit {
  @Input() value = 0;
}

@Component({
  selector: 'app-root',
  template: '<app-child [value]="count" />'
})
class AppComponent implements AfterViewInit {
  count = 0;
  ngAfterViewInit() {
    this.count = 1;  // ← Modify in AfterViewInit!
  }
}

// Q: What error appears in dev mode? Why?
Answer

Error: ExpressionChangedAfterItHasBeenCheckedError: Expression has changed after it was checked. Previous value: '0'. Current value: '1'.

Why: Angular runs a verification pass (dev mode only) AFTER AfterViewInit. It detects that count changed from 0 to 1 between the check and verification pass. This means the DOM is out of sync — the child received 0 but parent now has 1.

Fixes:

  • setTimeout(() => this.count = 1) — pushes to next CD cycle
  • this.cdr.detectChanges() — force immediate re-check
  • Use signals (they schedule updates properly)
  • Move the logic to ngOnInit instead
