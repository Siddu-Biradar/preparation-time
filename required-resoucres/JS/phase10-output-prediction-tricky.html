1. Event Loop & Async Output Questions

📺 YouTube Tutorials
  • What the heck is the event loop? — Philip Roberts (JSConf EU)
  • JavaScript Visualized - Event Loop — Lydia Hallie
  • In The Loop — Jake Archibald (JSConf Asia)
💡 Remember the execution order:
  1. Synchronous code (call stack)
  2. Microtasks (Promise.then, queueMicrotask, MutationObserver)
  3. Macrotasks (setTimeout, setInterval, I/O, UI rendering)
Within same queue: FIFO (first in, first out). Microtasks drain completely before ANY macrotask.

Medium Q1: Promise vs setTimeout

console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

console.log("4");
Output: 1, 4, 3, 2
Why: Sync first (1, 4) → microtask queue (Promise → 3) → macrotask queue (setTimeout → 2). Even with 0ms delay, setTimeout goes to macrotask queue which runs AFTER all microtasks.

Hard Q2: Nested Promises & setTimeout

console.log("start");

setTimeout(() => {
  console.log("timeout 1");
  Promise.resolve().then(() => console.log("promise inside timeout"));
}, 0);

Promise.resolve().then(() => {
  console.log("promise 1");
  setTimeout(() => console.log("timeout inside promise"), 0);
});

Promise.resolve().then(() => console.log("promise 2"));

console.log("end");
Output: start, end, promise 1, promise 2, timeout 1, promise inside timeout, timeout inside promise
Why:
1. Sync: "start", "end"
2. Microtasks: "promise 1" (schedules new setTimeout), "promise 2"
3. Macrotask 1: "timeout 1" → schedules microtask → drain microtask: "promise inside timeout"
4. Macrotask 2: "timeout inside promise" (was scheduled later)

Hard Q3: queueMicrotask vs Promise.resolve

queueMicrotask(() => console.log("microtask 1"));

Promise.resolve()
  .then(() => console.log("promise 1"))
  .then(() => console.log("promise 2"));

queueMicrotask(() => console.log("microtask 2"));

Promise.resolve().then(() => console.log("promise 3"));
Output: microtask 1, promise 1, microtask 2, promise 3, promise 2
Why: All are microtasks queued synchronously. Order: microtask 1, promise 1 (.then#1 of chain), microtask 2, promise 3. Then the SECOND .then ("promise 2") runs because it was only queued after "promise 1" resolved.

Expert Q4: async/await desugaring

async function foo() {
  console.log("foo start");
  await bar();
  console.log("foo end");
}

async function bar() {
  console.log("bar start");
  await Promise.resolve();
  console.log("bar end");
}

console.log("script start");
foo();
console.log("script end");
Output: script start, foo start, bar start, script end, bar end, foo end
Why:
- "script start" (sync)
- foo() called → "foo start" (sync), calls bar()
- bar() called → "bar start" (sync), hits await → pauses bar, returns to foo
- foo hits await bar() → pauses foo, returns to global
- "script end" (sync done)
- Microtask: bar's await resolves → "bar end"
- Microtask: foo's await resolves → "foo end"

Expert Q5: Complex async ordering

async function async1() {
  console.log("async1 start");
  await async2();
  console.log("async1 end");
}

async function async2() {
  console.log("async2");
}

console.log("script start");

setTimeout(() => console.log("setTimeout"), 0);

async1();

new Promise((resolve) => {
  console.log("promise1");
  resolve();
}).then(() => {
  console.log("promise2");
});

console.log("script end");
Output: script start, async1 start, async2, promise1, script end, async1 end, promise2, setTimeout
Why:
1. Sync: "script start"
2. async1() → "async1 start", calls async2 → "async2", await pauses async1
3. new Promise executor (sync!): "promise1", resolve() queues .then
4. "script end"
5. Microtasks in order: async1's continuation → "async1 end", then .then → "promise2"
6. Macrotask: "setTimeout"

Hard Q6: Promise.resolve vs new Promise

Promise.resolve().then(() => console.log(1));

new Promise((resolve) => {
  resolve();
}).then(() => console.log(2));

Promise.resolve().then(() => console.log(3));

queueMicrotask(() => console.log(4));

setTimeout(() => console.log(5), 0);
Output: 1, 2, 3, 4, 5
Why: All .then() and queueMicrotask are microtasks, queued in order. All resolve synchronously (resolve() is called immediately in the executor). Microtasks run in FIFO order. setTimeout is macrotask → last.

Expert Q7: Then chain inside then

Promise.resolve()
  .then(() => {
    console.log(1);
    return Promise.resolve(2);
  })
  .then((val) => console.log(val));

Promise.resolve()
  .then(() => console.log(3))
  .then(() => console.log(4))
  .then(() => console.log(5));
Output: 1, 3, 4, 2, 5 (modern V8/Chrome 73+/Node 12+)
Why: When .then returns a native resolved Promise, modern V8 optimizes the unwrap to 1 extra microtask tick. Chain 1 logs 1 → chain 2 logs 3 (both were queued together). Chain 2's .then(4) is queued. The Promise.resolve(2) unwrap resolves → 4 runs, then 2 runs, then 5 runs.
Note: Older engines (per spec) take 2 extra ticks → output would be 1, 3, 4, 5, 2. Always state which engine you're assuming.

Hard Q8: setTimeout(0) vs setImmediate vs Promise

// Browser environment:
setTimeout(() => console.log("timeout"), 0);
requestAnimationFrame(() => console.log("rAF"));
Promise.resolve().then(() => console.log("promise"));
console.log("sync");
Output: sync, promise, timeout, rAF (or sync, promise, rAF, timeout)
Why: Sync first. Promise is microtask (before any rendering). setTimeout is macrotask. rAF runs before next paint — timing depends on when in the frame you are. In practice: promise always before timeout, rAF timing varies.

Hard Q9: Promise constructor is synchronous!

const promise = new Promise((resolve, reject) => {
  console.log(1);
  resolve("success");
  console.log(2);
  reject("error");  // Does this throw?
  console.log(3);
});

promise
  .then(val => console.log(val))
  .catch(err => console.log(err));
Output: 1, 2, 3, "success"
Why: The executor runs synchronously (1, 2, 3 all log). resolve() is called first — promise is now fulfilled. reject() is ignored (state already changed — can only transition ONCE). .then receives "success". .catch never fires.

Expert Q10: Microtask starvation

function recursiveMicrotask(count) {
  if (count > 3) return;
  Promise.resolve().then(() => {
    console.log(`microtask ${count}`);
    recursiveMicrotask(count + 1);
  });
}

setTimeout(() => console.log("timeout"), 0);
recursiveMicrotask(1);
Output: microtask 1, microtask 2, microtask 3, timeout
Why: Each microtask schedules another microtask. The microtask queue must be FULLY drained before any macrotask runs. So all recursive microtasks complete first, then setTimeout fires. If the count check was removed → infinite loop (microtask starvation, setTimeout NEVER fires).

Hard Q11: catch returns a resolved promise

Promise.reject("error")
  .catch(err => {
    console.log("caught:", err);
    return "recovered";
  })
  .then(val => console.log("then:", val))
  .catch(err => console.log("catch2:", err));
Output: caught: error, then: recovered
Why: .catch() returns a NEW resolved promise (unless it throws). The returned value "recovered" becomes the resolved value for the next .then(). The second .catch never fires because the promise chain is now in fulfilled state.

Expert Q12: finally doesn't change the value

Promise.resolve("hello")
  .finally(() => {
    console.log("finally");
    return "world"; // Does this change the resolved value?
  })
  .then(val => console.log("then:", val));

Promise.reject("oops")
  .finally(() => {
    console.log("finally2");
    // throw new Error("new error"); // This WOULD change it
  })
  .catch(err => console.log("catch:", err));
Output: finally, finally2, then: hello, catch: oops
Why: .finally() is transparent — it doesn't receive the value and doesn't change it (return is ignored). The original value passes through. Exception: if finally THROWS, it replaces the value with the error.

2. 'this' Keyword Traps

📺 YouTube Tutorials
  • 'this' in JavaScript — Akshay Saini (Namaste JS)
  • this keyword explained — Fireship
💡 Rules of 'this' (priority order):
  1. new binding → this = new object
  2. Explicit (call/apply/bind) → this = specified object
  3. Implicit (method call) → this = object before dot
  4. Default → this = globalThis (or undefined in strict mode)
  5. Arrow functions → NO own this (inherits from enclosing lexical scope)

Medium Q13: Method extraction

const obj = {
  name: "Sid",
  greet() {
    return `Hello, ${this.name}`;
  }
};

const greet = obj.greet;
console.log(obj.greet());  // ?
console.log(greet());      // ?
Output: "Hello, Sid", "Hello, undefined" (or throws in strict mode)
Why: obj.greet() → implicit binding (this = obj). greet() → default binding (this = window → window.name = undefined). In strict mode, this = undefined → TypeError.

Hard Q14: Arrow function in object

const obj = {
  name: "Sid",
  regular() {
    return this.name;
  },
  arrow: () => {
    return this.name;
  }
};

console.log(obj.regular());
console.log(obj.arrow());
Output: "Sid", undefined
Why: Arrow functions don't have their own 'this'. The arrow function's 'this' is determined at creation time from the enclosing LEXICAL scope. The enclosing scope of the object literal is the module/global scope (NOT the object itself!). So this = window/module → name is undefined.

Hard Q15: setTimeout and this

class Timer {
  constructor() {
    this.seconds = 0;
  }
  
  start() {
    // Method 1:
    setInterval(function() {
      this.seconds++;
      console.log("A:", this.seconds);
    }, 1000);
    
    // Method 2:
    setInterval(() => {
      this.seconds++;
      console.log("B:", this.seconds);
    }, 1000);
  }
}

const t = new Timer();
// t.start(); — What happens?
Output: A: NaN (repeated), B: 1, B: 2, B: 3...
Why: Method 1: regular function in setTimeout → 'this' = window (default binding). window.seconds is undefined → undefined++ = NaN. Method 2: arrow function inherits 'this' from start() → 'this' = Timer instance → works correctly.

Hard Q16: bind vs call precedence

function showThis() {
  console.log(this.name);
}

const bound = showThis.bind({ name: "Bound" });

bound();                          // ?
bound.call({ name: "Called" });   // ?
new bound();                      // ?
Output: "Bound", "Bound", undefined
Why: bind() creates a function with permanently set 'this'. call() CANNOT override bind (bind wins over explicit). BUT 'new' keyword ALWAYS wins over bind — when used with 'new', 'this' is the newly created object (which doesn't have .name).

Expert Q17: Nested functions and this

const obj = {
  name: "Sid",
  outer() {
    console.log("outer:", this.name);
    
    function inner() {
      console.log("inner:", this.name);
    }
    
    const arrowInner = () => {
      console.log("arrow:", this.name);
    };
    
    inner();
    arrowInner();
  }
};

obj.outer();
Output: outer: Sid, inner: undefined, arrow: Sid
Why: outer() is called as method → this = obj. inner() is a standalone function call inside outer → default binding → this = window. arrowInner inherits 'this' from outer's scope → this = obj.

Expert Q18: Class field arrow functions

class Animal {
  name = "Animal";
  
  speak() {
    return this.name;
  }
  
  speakArrow = () => {
    return this.name;
  };
}

class Dog extends Animal {
  name = "Dog";
}

const dog = new Dog();
const { speak, speakArrow } = dog;

console.log(dog.speak());
console.log(dog.speakArrow());
console.log(speak());
console.log(speakArrow());
Output: "Dog", "Dog", TypeError, "Dog"
Why: Classes are ALWAYS in strict mode — no exception. Extracted speak() → this = undefined (strict mode default binding) → TypeError: Cannot read properties of undefined. Class field arrow functions are created per-instance and permanently bind 'this' to the instance. So even when extracted, speakArrow's 'this' = the dog instance → "Dog".

Hard Q19: this in event handlers

const button = document.createElement("button");

button.addEventListener("click", function() {
  console.log("regular:", this === button);
});

button.addEventListener("click", () => {
  console.log("arrow:", this === button);
});

button.addEventListener("click", function() {
  console.log("regular:", this === button);
}.bind({ custom: true }));

button.click();
Output: regular: true, arrow: false, regular: false
Why: Regular function: addEventListener sets 'this' to the element. Arrow function: inherits 'this' from enclosing scope (NOT the element). bind(): overrides addEventListener's 'this' setting.

Hard Q20: Chained method calls

const calc = {
  value: 0,
  add(n) { this.value += n; return this; },
  subtract(n) { this.value -= n; return this; },
  getResult() { return this.value; }
};

console.log(calc.add(5).subtract(2).add(10).getResult());

// But what about this?
const { add } = calc;
// add(5); — What happens?
Output: 13, then TypeError (or NaN)
Why: Method chaining works because each method returns 'this' (the same object). Extracted add() has default binding → this = window → window.value is undefined → NaN, and return this → returns window (no chaining possible).

3. Closure & Scope Gotchas

📺 YouTube Tutorials
  • Closures in JS — Akshay Saini (Namaste JS)
  • Closures Explained — Fireship

Medium Q21: Classic for loop closure

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log("var:", i), 100);
}

for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log("let:", j), 100);
}
Output: var: 3, var: 3, var: 3, let: 0, let: 1, let: 2
Why: var is function-scoped — all callbacks close over the SAME 'i' (which is 3 after loop ends). let is block-scoped — each iteration creates a NEW binding of 'j'. Fix for var: use IIFE or setTimeout with third arg.

Hard Q22: Closure with reassignment

function createCounter() {
  let count = 0;
  
  return {
    increment: () => ++count,
    getCount: () => count,
    reset: () => { count = 0; }
  };
}

const counter = createCounter();
counter.increment();
counter.increment();
counter.increment();
console.log(counter.getCount());

counter.reset();
console.log(counter.getCount());
Output: 3, 0
Why: All three methods close over the SAME 'count' variable. They share the reference, not a copy. Incrementing changes the shared variable. Reset sets it back to 0. This is the module pattern.

Hard Q23: Closure vs value capture

function createFunctions() {
  const fns = [];
  
  for (var i = 0; i < 5; i++) {
    fns.push(function() {
      return i * i;
    });
  }
  
  return fns;
}

const functions = createFunctions();
console.log(functions[0]());
console.log(functions[1]());
console.log(functions[4]());
Output: 25, 25, 25
Why: All functions close over the SAME 'i' (var is function-scoped). After loop: i = 5. All functions return 5*5 = 25. Fix: use let, or IIFE: (function(j) { fns.push(() => j*j); })(i);

Hard Q24: Stale closure in React-like scenario

function useCounter() {
  let count = 0;
  
  function handleClick() {
    setTimeout(() => {
      console.log("count:", count);
    }, 3000);
  }
  
  count = 5; // Simulating state update
  handleClick();
  count = 10; // Another update before timeout fires
}

useCounter();
Output: count: 10 (after 3 seconds)
Why: The closure captures the REFERENCE to 'count', not its value at the time of creation. By the time setTimeout fires, count has been updated to 10. This is the "stale closure" problem in React hooks.

Expert Q25: Block scoping inside loops

const arr = [];
for (let i = 0; i < 3; i++) {
  for (let i = 0; i < 3; i++) { // Same variable name!
    arr.push(() => i);
  }
}
console.log(arr.map(fn => fn()));
Output: [0, 1, 2, 0, 1, 2, 0, 1, 2]
Why: The inner 'let i' creates its OWN block-scoped variable that shadows the outer 'i'. Each iteration of the inner loop creates a fresh binding. The closures capture the inner 'i' values.

Hard Q26: IIFE and closure

var result = [];
for (var i = 0; i < 3; i++) {
  result.push(
    (function(j) {
      return function() { return j; };
    })(i)
  );
}

console.log(result[0]());
console.log(result[1]());
console.log(result[2]());
Output: 0, 1, 2
Why: The IIFE creates a new scope for each iteration. 'j' is a parameter (local to the IIFE), so each returned function closes over its own 'j'. This was the classic fix before 'let' existed.

Expert Q27: Closure memory leak pattern

function outer() {
  const bigData = new Array(1000000).fill("🔥");
  
  return function inner() {
    // inner doesn't use bigData at all!
    return "hello";
  };
}

const fn = outer();
// Is bigData garbage collected?
Answer: In theory NO (bigData is in inner's closure scope). In practice: modern V8 DOES optimize this — if bigData isn't referenced in inner, V8 excludes it from the closure. But in older engines or with eval/debugger, it stays in memory. Always set large variables to null if not needed.

Hard Q28: Closure with setTimeout and let

for (let i = 0; i < 3; i++) {
  setTimeout(function timer() {
    console.log(i);
  }, i * 1000);
}

// What's the timing of outputs?
Output: 0 (at 0s), 1 (at 1s), 2 (at 2s)
Why: let creates a new binding per iteration. Each setTimeout captures its own 'i'. The delays are 0ms, 1000ms, 2000ms respectively. If this were var: 3, 3, 3 all at different times.

Medium Q29: Implicit coercion with +

console.log(1 + "2");
console.log("3" - 1);
console.log("3" + 1);
console.log(true + true);
console.log(true + "1");
console.log([] + []);
console.log({} + []);
console.log([] + {});
Output: "12", 2, "31", 2, "true1", "", "[object Object]", "[object Object]"
Why:
- 1 + "2": + with string → string concat → "12"
- "3" - 1: - only works with numbers → "3" → 3, result: 2
- "3" + 1: + with string → concat → "31"
- true + true: no string → numeric: true=1, 1+1=2
- true + "1": + with string → "true" + "1" = "true1"
- [] + []: both coerce to "" → "" + "" = ""
- {} + []: Inside console.log() (expression context), {} is always an object literal → "[object Object]". Only when `{} + []` is a standalone statement in DevTools does {} parse as a block (giving 0).
- [] + {}: "" + "[object Object]" = "[object Object]"

Hard Q30: == vs === edge cases

console.log(null == undefined);
console.log(null === undefined);
console.log(null == 0);
console.log(null == "");
console.log(null == false);
console.log(NaN == NaN);
console.log(NaN === NaN);
console.log(undefined == false);
console.log("" == false);
console.log("" == 0);
console.log(0 == false);
Output: true, false, false, false, false, false, false, false, true, true, true
Why:
- null == undefined → SPECIAL RULE: true (they're only equal to each other)
- null/undefined don't coerce to anything else with ==
- NaN is not equal to ANYTHING, including itself
- "" == false: both coerce to 0 → true
- "" == 0: "" coerces to 0 → true
- 0 == false: false coerces to 0 → true

Hard Q31: Object coercion (valueOf, toString)

const obj = {
  valueOf() { return 42; },
  toString() { return "hello"; }
};

console.log(obj + 1);
console.log(`${obj}`);
console.log(obj == 42);
console.log(String(obj));
Output: 43, "hello", true, "hello"
Why:
- obj + 1: hint is "default" (+ operator uses default hint) → valueOf() → 42 + 1 = 43
- Template literal: hint is "string" → toString() → "hello"
- obj == 42: hint is "default" → valueOf() → 42 == 42 → true
- String(obj): hint is "string" → toString() → "hello"
Note: "default" and "number" hints both try valueOf() first, then toString(). Only "string" hint reverses the order.

Medium Q32: Tricky falsy/truthy

console.log(Boolean("0"));
console.log(Boolean(0));
console.log(Boolean(""));
console.log(Boolean(" "));
console.log(Boolean([]));
console.log(Boolean({}));
console.log(Boolean(null));
console.log(Boolean(undefined));
console.log(Boolean(-0));
console.log(Boolean(NaN));

// Tricky:
console.log([] == false);
console.log([] == ![]);
console.log({} == !{});
Output: true, false, false, true, true, true, false, false, false, false, true, true, false
Key insights:
- "0" is truthy (non-empty string!)
- " " is truthy (space is a character!)
- [] is truthy, {} is truthy (all objects are truthy!)
- [] == false: [] → "" → 0, false → 0, 0==0 → true
- [] == ![]: ![] = false (object→truthy→negated), then [] == false (see above) → true
- {} == !{}: !{} = false, {} → "[object Object]" → NaN, NaN != 0 → false

Expert Q33: typeof quirks

console.log(typeof undefined);
console.log(typeof null);
console.log(typeof NaN);
console.log(typeof typeof 1);
console.log(typeof function(){});
console.log(typeof []);
console.log(typeof {});
console.log(typeof 1n);
console.log(typeof Symbol());

// This one is tricky:
let x;
console.log(typeof x);
console.log(typeof y); // y is not declared!
Output: "undefined", "object", "number", "string", "function", "object", "object", "bigint", "symbol", "undefined", "undefined"
Why:
- typeof null = "object" → FAMOUS BUG (never fixed for backward compat)
- typeof NaN = "number" → NaN is technically a number value
- typeof typeof 1 = typeof "number" = "string"
- typeof [] = "object" → arrays are objects (use Array.isArray())
- typeof undeclaredVariable → "undefined" (doesn't throw! Safe check)

Hard Q34: Number parsing gotchas

console.log(parseInt("123abc"));
console.log(parseInt("abc123"));
console.log(parseInt("0x10"));
console.log(parseInt("010", 10));
console.log(parseInt(""));
console.log(Number(""));
console.log(Number("123abc"));
console.log(Number(null));
console.log(Number(undefined));
console.log(Number(true));
console.log(Number([1]));
console.log(Number([1, 2]));
Output: 123, NaN, 16, 10, NaN, 0, NaN, 0, NaN, 1, 1, NaN
Key rules:
- parseInt: reads digits until non-digit, stops. "abc123" → starts with non-digit → NaN
- parseInt("0x10") → hex → 16
- Number(""): empty string → 0 (parseInt("") → NaN!)
- Number(null) = 0, Number(undefined) = NaN
- Number([1]) → "1" → 1. Number([1,2]) → "1,2" → NaN

Hard Q35: Comparison operators

console.log(null > 0);
console.log(null == 0);
console.log(null >= 0);
console.log(undefined > 0);
console.log(undefined < 0);
console.log(undefined == 0);
Output: false, false, true, false, false, false
Why:
- Comparisons (> < >= <=) convert null to 0: null > 0 → 0 > 0 → false
- == has SPECIAL rule: null only equals null and undefined
- null >= 0 → 0 >= 0 → true (uses numeric comparison)
- undefined always converts to NaN in comparisons → all comparisons with NaN are false
- This inconsistency (null not == 0 but >= 0) is a famous JS quirk!

Medium Q36: String comparison

console.log("2" > "12");
console.log("2" > 12);
console.log("abc" > "abd");
console.log("a" > "A");
Output: true, false, false, true
Why:
- "2" > "12": string comparison (char by char): "2" (char code 50) > "1" (char code 49) → true
- "2" > 12: mixed → numeric: 2 > 12 → false
- "abc" > "abd": char by char, "c"(99) < "d"(100) → false
- "a"(97) > "A"(65) → true (lowercase > uppercase in char codes)

5. Hoisting & TDZ

  • Hoisting in JavaScript — Akshay Saini (Namaste JS)

Medium Q37: var hoisting

console.log(a);
console.log(b);
var a = 1;
let b = 2;
Output: undefined, ReferenceError: Cannot access 'b' before initialization
Why: var declarations are hoisted and initialized to undefined. let declarations are hoisted but NOT initialized (TDZ = Temporal Dead Zone until declaration line).

Hard Q38: Function hoisting vs variable hoisting

console.log(foo);
console.log(bar);

function foo() { return "I am foo"; }
var bar = function() { return "I am bar"; };

console.log(foo());
console.log(bar());
Output: [Function: foo], undefined, "I am foo", "I am bar"
Why: Function DECLARATIONS are fully hoisted (entire function available). Function EXPRESSIONS assigned to var: only the variable declaration is hoisted (= undefined). The assignment happens at runtime.

Hard Q39: Function vs var same name

Expert Q40: TDZ in different contexts

  // console.log(x); // What would this print?
  let x = 2;

}

Hard Q41: Hoisting in conditional blocks

if (true) {
  function foo() { console.log("inside if"); }
}

// What about:

if (false) {
  function bar() { console.log("never defined?"); }
}
Output (modern V8, non-strict): TypeError: foo is not a function, then typeof bar → "undefined"
Why: In non-strict mode, function declarations inside blocks are hoisted as `var foo = undefined` (name is hoisted, but NOT the function body). The function body is only assigned when execution reaches the declaration inside the block. So calling foo() before the if-block → foo is undefined → TypeError. typeof bar → "undefined" because the if(false) block never executes.
Key point: Function declarations inside blocks have unreliable behavior. Always use function expressions: `const foo = function() {...}` in conditional blocks.

Expert Q56: try/catch/finally with return (Google/Meta favorite)

function test1() {
  try {
    return 1;
  } catch (e) {
    return 2;
  } finally {
    return 3;
  }
}

function test2() {
  try {
    throw new Error("oops");
    return 1;
  } catch (e) {
    return 2;
  } finally {
    console.log("finally");
    // No return here
  }
}

function test3() {
  let x = 1;
  try {
    return x;
  } finally {
    x = 2;
  }
}

console.log(test1());
console.log(test2());
console.log(test3());
Output: 3, "finally" then 2, 1
Why:
- test1(): finally's return ALWAYS overrides try/catch return. Even though try returned 1, finally returns 3 → 3 wins.
- test2(): throws → catch returns 2. finally logs but doesn't return → catch's return (2) is used.
- test3(): return x captures the VALUE of x (1) before finally modifies x. finally changes x to 2 but the return value was already captured. Returns 1.
Rule: finally return > catch return > try return. But finally can't modify an already-captured primitive return value.

    console.log("finally");
  }
  console.log("after try-catch");
}

Why: foo() is async — starts executing, hits await → pauses. "sync end" runs. The rejected promise is caught by catch. finally always runs. Execution continues after the try-catch block.

Medium Q58: Nullish coalescing (??) vs OR (||)

console.log(NaN ?? "default");

Output: "default", 0, "default", "", "default", "default", "default", false, NaN, "default"
Why:
- || returns RHS for ALL falsy values (0, "", false, null, undefined, NaN)
- ?? returns RHS ONLY for null and undefined — NOT for 0, "", false, NaN

Medium Q62: Logical assignment operators (??=, ||=, &&=)

let a = null;
let b = 0;
let c = "hello";
let d = undefined;
let e = "";

a ??= "default A";
b ??= "default B";
c ??= "default C";
d ||= "fallback D";
b ||= "fallback B";
e ||= "fallback E";
c &&= c.toUpperCase();
b &&= "won't run";

console.log(a, b, c, d, e);
Output: "default A", "won't run", "HELLO", "fallback D", "fallback E"
Why (step by step):
- a ??= "default A": a is null → assigns → a = "default A"
- b ??= "default B": b is 0 (NOT null/undefined) → no-op → b stays 0
- c ??= "default C": c is "hello" (NOT null/undefined) → no-op → c stays "hello"
- d ||= "fallback D": d is undefined (falsy) → assigns → d = "fallback D"
- b ||= "fallback B": b is 0 (falsy!) → assigns → b = "fallback B"
- e ||= "fallback E": e is "" (falsy) → assigns → e = "fallback E"
- c &&= c.toUpperCase(): c is "hello" (truthy) → assigns RHS → c = "HELLO"
- b &&= "won't run": b is now "fallback B" (truthy!) → assigns RHS → b = "won't run"
Key: &&= assigns the RHS when LHS is truthy. ||= assigns when LHS is falsy. ??= assigns when LHS is null/undefined only.

Hard Q65: Promise.race vs Promise.any vs Promise.allSettled

const p1 = new Promise(res => setTimeout(() => res("one"), 100));
const p2 = Promise.reject("two");
const p3 = new Promise(res => setTimeout(() => res("three"), 50));

// What order do these resolve?
Promise.race([p1, p2, p3])
  .then(v => console.log("race resolved:", v))
  .catch(e => console.log("race rejected:", e));

Promise.any([p1, p2, p3])
  .then(v => console.log("any resolved:", v))
  .catch(e => console.log("any rejected:", e));

Promise.allSettled([p1, p2, p3])
  .then(results => console.log("allSettled:", results.map(r => r.status)));
Output:
race rejected: two
any resolved: three (after 50ms)
allSettled: ["fulfilled", "rejected", "fulfilled"] (after 100ms)
Why:
- Promise.race: first to SETTLE (fulfill OR reject) wins. p2 rejects synchronously → wins immediately.
- Promise.any: first to FULFILL wins (rejections are ignored). p2 rejected → ignored. p3 fulfills at 50ms → wins.
- Promise.allSettled: waits for ALL to settle. Never rejects. Returns array of {status, value/reason}.

Expert Q67: WeakRef and FinalizationRegistry

Medium Q68: Object.freeze — shallow vs deep (asked 40%+ of interviews)

const obj = Object.freeze({ 
  a: 1, 
  nested: { b: 2 },
  arr: [1, 2, 3]
});

obj.a = 99;
obj.newProp = "hello";
delete obj.a;
obj.nested.b = 99;
obj.arr.push(4);

console.log(obj.a);
console.log(obj.newProp);
console.log(obj.nested.b);
console.log(obj.arr);
Output: 1, undefined, 99, [1, 2, 3, 4]
Why:
- obj.a = 99: silently fails (frozen — can't modify existing props)
- obj.newProp: silently fails (frozen — can't add new props)
- delete obj.a: silently fails (frozen — can't delete props)
- obj.nested.b = 99: WORKS! Object.freeze is SHALLOW — nested objects are not frozen
- obj.arr.push(4): WORKS! The array reference is frozen, but array contents are mutable

[0, "", 1, null, undefined] (undefined always sorts to end; others string-compared)
[3, 1, 2] (comparator returns 0 → no swaps → order preserved, stable sort)
Key: Default sort converts elements to STRINGS then compares UTF-16 code units. "10" < "2" because "1" < "2" char-by-char. ALWAYS provide a comparator for numbers! undefined always goes to the end regardless of comparator.

Medium Q70: Promise.all rejection behavior

Promise.all([
  Promise.resolve(1),
  Promise.reject("fail"),
  new Promise((res) => { console.log("p3 executor"); res(3); }),
  Promise.reject("second fail")
])
.then(v => console.log("resolved:", v))
.catch(e => console.log("rejected:", e));

console.log("sync");
Output: p3 executor, sync, rejected: fail
Why:
- Promise constructors/executors run SYNCHRONOUSLY → "p3 executor" logs immediately
- "sync" logs (still synchronous)
- Promise.all rejects with the FIRST rejection ("fail") — doesn't wait for others
- "second fail" is ignored (only first rejection matters)
- All promise executors still RUN (they're not cancelled!) but their results are ignored
Key: Promise.all is "fail-fast". Use Promise.allSettled if you need all results regardless of failures.

Medium Q71: for...in vs for...of (fundamental distinction)

const arr = [10, 20, 30];
arr.custom = "hello";

console.log("--- for...in ---");
for (let x in arr) console.log(x, typeof x);

console.log("--- for...of ---");
for (let x of arr) console.log(x, typeof x);

const obj = { a: 1, b: 2 };
// for (let x of obj) console.log(x); // What happens?
Output:
--- for...in ---
"0" string, "1" string, "2" string, "custom" string
--- for...of ---
10 number, 20 number, 30 number
for...of obj → TypeError: obj is not iterable
Why:
- for...in: iterates over enumerable PROPERTY KEYS (as strings!). Includes inherited and custom properties. Returns keys, not values.
- for...of: iterates over ITERABLE VALUES (Symbol.iterator). Only works on iterables (Array, String, Map, Set, generators). Does NOT include non-index properties.
- Objects are NOT iterable by default (no Symbol.iterator). Use Object.entries(obj) with for...of.
Key: Never use for...in on arrays! It includes prototype properties and custom properties.

Hard Q72: Symbol.toPrimitive (overrides valueOf/toString)

const obj = {
  [Symbol.toPrimitive](hint) {
    if (hint === "number") return 42;
    if (hint === "string") return "hello";
    return true; // "default" hint
  },
  valueOf() { return 999; },   // IGNORED!
  toString() { return "ignored"; } // IGNORED!
};

console.log(+obj);       // hint: "number"
console.log(`${obj}`);   // hint: "string"
console.log(obj + "");   // hint: "default"
console.log(obj * 2);    // hint: "number"
console.log(obj == true); // hint: "default"
Output: 42, "hello", "true", 84, true
Why:
- Symbol.toPrimitive COMPLETELY overrides valueOf and toString when present
- +obj: unary + → hint "number" → 42
- Template literal: hint "string" → "hello"
- obj + "": binary + with string → hint "default" → true → "true" (concat)
- obj * 2: multiplication → hint "number" → 42 * 2 = 84
- obj == true: == uses hint "default" → true == true → true
Priority: Symbol.toPrimitive > valueOf/toString. If no Symbol.toPrimitive: "default"/"number" → valueOf first, "string" → toString first.

Hard Q73: RegExp lastIndex stateful trap (senior-level)

const regex = /a/g;  // Note: global flag!

console.log(regex.test("abc"));
console.log(regex.lastIndex);
console.log(regex.test("abc"));
console.log(regex.lastIndex);
console.log(regex.test("abc"));

// Same with exec:
const re2 = /\d+/g;
const str = "12 and 34 and 56";
console.log(re2.exec(str)?.[0]);
console.log(re2.exec(str)?.[0]);
console.log(re2.exec(str)?.[0]);
console.log(re2.exec(str)?.[0]);
Output: true, 1, false, 0, true, "12", "34", "56", null
Why:
- With /g flag, regex.test() and regex.exec() are STATEFUL — they remember lastIndex
- First test("abc"): finds "a" at index 0 → true, lastIndex becomes 1
- Second test("abc"): starts searching from index 1 → no "a" found → false, lastIndex resets to 0
- Third test("abc"): starts from 0 again → finds "a" → true
- exec with /g: returns next match each time, null when no more matches (then resets)
Key: NEVER reuse a global regex across different strings without resetting lastIndex! Or use string.match() / string.matchAll() instead which don't have this problem.

  1. Read line by line — don't jump ahead. Execution is sequential.
  2. Identify async boundaries — what goes to microtask queue vs macrotask queue?
  3. Track 'this' — who called the function and how?
  4. Check scope — is it var (function scope) or let/const (block scope)?
  5. Coercion — is there + with a string? Which side converts?
  6. Draw the prototype chain for inheritance questions.
  7. Remember: Promise executor is sync, .then is async (microtask).
  8. ?? vs ||: ?? only cares about null/undefined. || cares about ALL falsy values.
  9. Destructuring defaults: Only trigger for undefined, NEVER for null.
  10. finally: Its return overrides everything. But can't modify already-captured primitives.
