1. Event Loop (Complete Deep Dive)

📺 YouTube Tutorials

  • Event Loop Visualized — Lydia Hallie

Theory

JavaScript is single-threaded — it has ONE call stack. But it handles asynchronous operations through the Event Loop, which coordinates between the call stack, Web APIs, and callback queues.

What Problem Does the Event Loop Solve?

Imagine you're a chef (JavaScript) working alone in a kitchen (single thread). You can only do ONE thing at a time — chop vegetables OR stir soup, never both simultaneously. Now a customer orders a dish that takes 30 minutes to bake. Without the Event Loop, you'd stand there staring at the oven for 30 minutes, unable to serve anyone else. That's what "blocking" means — your ONE thread is stuck waiting.

The Event Loop is like having kitchen assistants (Web APIs/Browser threads) who can watch the oven FOR you. You tell them "notify me when it's done," then continue chopping vegetables (executing other code). When the timer beeps, the assistant puts a note on your counter (callback queue). When you finish your current task and look at the counter (call stack is empty), you pick up the note and handle it.

This is the fundamental insight: JavaScript itself never does async work. It DELEGATES to the browser's C++ threads (timers, network, DOM events) and the Event Loop COORDINATES when those results come back to JavaScript's single thread.

How It Actually Works — Complete Mental Model

Think of the entire system as having these components working together:

  1. Call Stack — The single lane where JS code executes. Functions go in (push) and come out (pop). Only one function runs at a time.
  2. Web APIs — The browser's multi-threaded workers. When JS calls setTimeout, fetch, or adds an event listener, it's handing work OFF to these C++ threads. They run in parallel to JS.
  3. Callback Queues — Waiting rooms where completed callbacks sit until the Call Stack is free to handle them. There are TWO queues with different priorities.
  4. Event Loop — The "traffic controller" that constantly checks: "Is the call stack empty? If yes, should I move a callback from the queue to the stack?"

🔄 Event Loop — Complete Architecture Diagram

📖 Reading This Diagram — What Each Part Does:

📚 Call Stack (Red Box) — This is JavaScript's "one hand." It can only hold one task at a time. Functions stack on top of each other (like plates). The top plate (function) finishes first, gets removed, then the one below runs. When you call a() which calls b() which calls c(), the stack is: c → b → a → global. c finishes first, then b, then a.

🌐 Web APIs (Blue Box) — These are the browser's helpers that work in parallel. When JS encounters setTimeout, fetch, or an event listener, it hands the job to the browser and moves on. The browser uses its own C++ threads to count timers, make network requests, etc. — JS doesn't wait!

⚡ Microtask Queue (Green Box) — The VIP waiting room. When Promises resolve or queueMicrotask() is called, callbacks go here. Rule: EVERY callback in this room gets served before ANYONE in the regular room. Even if new VIPs arrive while serving, they also get served immediately.

📋 Macrotask Queue (Yellow Box) — The regular waiting room. setTimeout callbacks, click events, and I/O results wait here. Rule: Only ONE person from this room is served per cycle, and only after the VIP room is completely empty.

🔄 Event Loop (Purple Box) — The receptionist/traffic controller. It constantly asks: "Is the call stack empty?" If yes → first serves ALL VIPs (microtasks), then serves ONE regular customer (macrotask), then checks VIPs again. This loop never stops — it IS what keeps your app alive and responsive.

🔀 The Flow (follow the arrows):

Call Stack encounters async code (setTimeout, fetch, etc.) → delegates to Web APIs (browser handles it in background) → when done, Web API puts callback into the appropriate Queue (Microtask or Macrotask) → Event Loop waits for call stack to empty → moves callback from queue back to Call Stack to execute

🎯 Event Loop Cycle — Step by Step

1 Execute Sync Code — Run all code on the call stack until it's completely empty

🎤 Golden Rules for Interviews

1️⃣ Sync ALWAYS first — All synchronous code runs to completion before anything async
2️⃣ Microtasks beat Macrotasks — Promise.then() runs before setTimeout(fn, 0) ALWAYS
3️⃣ Drain completely — ALL microtasks execute (even newly added) before ONE macrotask
4️⃣ setTimeout(fn, 0) ≠ immediate — It means "after sync + microtasks + render opportunity"
5️⃣ Promise executor is sync — new Promise(fn) runs fn immediately, only .then() is async

🕵️ Real Trace — Watch Code Travel Through the Diagram

Code: setTimeout(() => console.log("hi"), 1000)

Call Stack JS sees setTimeout(). It does NOT start a timer itself. It calls the browser's timer API and says: "Here's a callback, call it after 1000ms." Then JS immediately moves to the next line — it doesn't wait.
Web API The browser starts a C++ timer thread counting 1000ms. Meanwhile, JS is free to run other code. After 1000ms, the browser's timer finishes and pushes the callback into the Macrotask Queue.
Macrotask Q The callback () => console.log("hi") sits in the queue waiting. It can NOT jump to the call stack until the stack is empty AND all microtasks are done.
Event Loop Keeps checking: "Call stack empty? Microtask queue empty?" When BOTH are yes → picks up our callback and pushes it onto the call stack.
Call Stack Finally executes console.log("hi"). Prints "hi". Function pops off. Done! 🎉

💡 Key Takeaway: The 1000ms is the MINIMUM wait — if the call stack is busy running a 3-second loop when the timer expires, the callback waits in the queue until that loop finishes. Total wait = 3000ms, not 1000ms!

Why This Order Matters — Step-by-Step Walkthrough

Let's trace what actually happens when the browser encounters this code:

console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
console.log("D");

Step 1: Synchronous execution begins. The engine starts reading your script top-to-bottom. The entire script is itself a macrotask (the first one).

  • console.log("A") → pushed to call stack, executes, prints "A", popped off.
  • setTimeout(..., 0) → JS calls the Web API: "Hey browser, set a timer for 0ms and here's the callback." The browser starts a timer in C++. JS moves on immediately (doesn't wait).
  • Promise.resolve().then(...) → The Promise is already resolved (instantly). The .then() callback is scheduled into the Microtask Queue. JS moves on.
  • console.log("D") → pushed to call stack, executes, prints "D", popped off.

Call stack is now empty. Current state: Microtask Queue has [() => log("C")]. The browser timer (0ms) completes and moves the callback to Macrotask Queue: [() => log("B")].

Step 2: Event Loop checks — call stack empty? Yes! Drain microtask queue.

  • Picks () => console.log("C") from microtask queue, pushes to call stack, executes, prints "C".
  • Microtask queue is now empty.

Step 3: Render opportunity. Browser may repaint if needed (skip for now).

Step 4: Pick ONE macrotask.

  • Picks () => console.log("B") from macrotask queue, pushes to call stack, executes, prints "B".

Final Output: A → D → C → B

The key insight: Microtasks (Promises) ALWAYS run before macrotasks (setTimeout), even if setTimeout has 0ms delay. The 0ms timer just means "as soon as possible after current execution + microtasks."

// Classic event loop demonstration:
console.log("1: Sync");

setTimeout(() => console.log("2: Macrotask"), 0);

Promise.resolve().then(() => console.log("3: Microtask"));

queueMicrotask(() => console.log("4: Microtask 2"));

console.log("5: Sync");

// Output ORDER:
// "1: Sync"      — synchronous
// "5: Sync"      — synchronous

🎯 Interview Questions

Hard Explain the event loop. Why does setTimeout(fn, 0) not execute immediately?

Answer: Even with 0ms delay, setTimeout places the callback in the Macrotask Queue. The event loop first completes all synchronous code, then drains ALL microtasks, then picks ONE macrotask. So setTimeout(fn, 0) means "execute after the current stack and microtasks are clear" — not "immediately." Minimum delay is typically ~4ms due to browser clamping.

2. Microtask vs Macrotask Queue

📺 YouTube Tutorials
  • Microtasks vs Macrotasks — Lydia Hallie
  • Task Queue Deep Dive — Akshay Saini

Theory

Why Two Queues? What's the Difference?

Think of it like an airport. The Macrotask Queue is the regular boarding line — one person (task) enters the plane (call stack) at a time, with breaks between each. The Microtask Queue is the VIP fast-track — between every regular passenger, ALL VIP passengers get through first, no matter how many are waiting.

Why does this priority system exist? Microtasks exist for things that need to happen IMMEDIATELY after the current operation, before the browser has a chance to do anything else (render, handle clicks, run timers). Promises use microtasks because when you .then() on a resolved Promise, you expect the callback to run NOW-ish, not after a render frame or another timer. If Promise callbacks went to the macrotask queue, you'd see visual "flickers" as the browser renders intermediate states between Promise chains.

The critical rule: After each macrotask completes, the Event Loop drains the ENTIRE microtask queue before doing anything else. If a microtask adds more microtasks, those also run immediately. This means microtasks can "starve" everything else — if they keep adding more microtasks, the browser never gets to render or handle user input.

⏱️ Execution Timeline (Middle Section) — This shows the EXACT order things run in one cycle of the Event Loop. Read it left-to-right like a train track:
• Phase 1 (Red): All your normal synchronous code (console.log, variable assignments, loops) runs FIRST, fully to completion.
• Phase 2 (Green): ALL waiting microtasks execute — every single .then(), every await continuation, every queueMicrotask(). ALL of them. Not one — ALL.
• Phase 3 (Purple): Browser MAY render the screen (recalculate styles, layout, paint pixels). This is why UI updates appear smooth — they happen between tasks.
• Phase 4 (Yellow): Exactly ONE macrotask gets to run (one setTimeout callback, or one click handler, etc.).
• Then it loops back to Phase 2 — check microtasks again!

🚰 "Drain Completely" (Bottom-Left) — Shows what happens when one microtask creates another. Microtask A runs → it creates Microtask B → B also runs immediately → B creates C → C also runs NOW. The Event Loop refuses to leave until the microtask queue is bone-dry empty. This is powerful but dangerous (see starvation warning).

☝️ Macrotask Behavior (Bottom-Right) — Shows the opposite: Macrotask A finishes → Event Loop does NOT immediately run Macrotask B. Instead it goes: check microtasks → maybe render → THEN Macrotask B. Each macrotask gets its own "turn" with microtask-checking between each one.

⚠️ Starvation Warning (Red Box) — The danger of microtasks: if they keep adding more microtasks forever (like an infinite recursive Promise chain), the macrotask queue starves — setTimeout callbacks NEVER run, the browser NEVER paints, and the page freezes completely. This is a real interview question: "Can microtasks block rendering?"— YES!

What "Drain Completely" Means in Practice

When the Event Loop starts processing microtasks, it doesn't stop until the queue is EMPTY. Even if a microtask adds a NEW microtask while processing, that new one also gets processed in the same cycle. This is fundamentally different from macrotasks where only ONE is processed per Event Loop iteration.

// Demonstrates "drain completely" behavior:
Promise.resolve().then(() => {
  console.log("Microtask 1");
  // This adds ANOTHER microtask while we're processing microtasks!
  Promise.resolve().then(() => {
    console.log("Microtask 2 (added by Microtask 1)");
    // And another one!
    Promise.resolve().then(() => console.log("Microtask 3 (added by 2)"));
  });
});
setTimeout(() => console.log("Macrotask"), 0);

// Output:
// "Microtask 1"
// "Microtask 2 (added by Microtask 1)"
// "Microtask 3 (added by 2)"
// "Macrotask"
// ALL microtasks (including dynamically added ones) run BEFORE the setTimeout!
Key Difference: After EACH macrotask, ALL pending microtasks are drained. Microtasks can starve macrotasks! If a microtask schedules more microtasks recursively, the macrotask queue (and rendering) gets blocked forever. 
// Microtask starvation example (DON'T DO THIS):
function recurse() {
  Promise.resolve().then(recurse); // Infinite microtask loop
}
recurse(); // Page freezes! Rendering never happens!

// vs. Macrotask recursion (yields to browser):
function recurse() {
  setTimeout(recurse, 0); // Yields between each call — browser can render
}

// queueMicrotask — explicit microtask scheduling
queueMicrotask(() => {
  console.log("Microtask via queueMicrotask");
});

// Practical difference:
button.addEventListener("click", () => {
  // This runs as a macrotask (event callback)
  Promise.resolve().then(() => {
    // This microtask runs BEFORE next macrotask/render
    element.style.color = "red";
  });
});

// requestAnimationFrame — BEFORE repaint
requestAnimationFrame(() => {
  // Runs right before the browser paints next frame
  // Best for visual updates, animations
  element.style.transform = `translateX(${x}px)`;
});

📺 YouTube Tutorials

Theory

How Timers Actually Work Under the Hood

setTimeout and setInterval are NOT JavaScript features — they're Web APIs provided by the browser (or Node.js runtime). When you call setTimeout(callback, 1000), here's what actually happens:

  1. JavaScript calls the browser's timer API: "Start counting 1000ms, and here's a function to call when done."
  2. The browser starts a separate C++ timer thread. JavaScript's call stack is FREE — it continues executing the next line immediately.
  3. After 1000ms, the browser's timer thread moves the callback to the Macrotask Queue.
  4. The Event Loop waits until the call stack is empty, then picks up the callback and executes it.

Critical insight: The delay (1000ms) is the MINIMUM wait time, not a guarantee. If the call stack is busy running a 2-second synchronous operation when the timer expires, the callback sits in the queue and only runs after that operation finishes (~3 seconds total). This is why setTimeout(fn, 0) doesn't mean "immediately" — it means "after the current execution and all microtasks complete."

const timerId = setTimeout(() => console.log("delayed"), 1000);
clearTimeout(timerId); // Cancel before execution

// IMPORTANT: delay is MINIMUM, not guaranteed
setTimeout(() => console.log("hello"), 100);
// If call stack is busy for 500ms, callback runs at ~500ms, not 100ms

// Why setTimeout(fn, 0) is never truly 0ms:
// 1. Browser clamps minimum delay to ~4ms (HTML spec)
// 2. Even with 0ms, callback goes to macrotask queue
// 3. Must wait for: current sync code + ALL microtasks + render
// 4. In background tabs, browsers throttle to minimum 1000ms!

// Nested setTimeout (preferred over setInterval for precise intervals)
function poll() {
  fetch("/api/status").then(data => {
    updateUI(data);
    setTimeout(poll, 5000); // Schedule AFTER previous completes
  });
}

// setInterval — execute REPEATEDLY at interval
const intervalId = setInterval(() => {
  console.log(new Date().toLocaleTimeString());
}, 1000);
clearInterval(intervalId);

// ⚠️ setInterval problems (why pros avoid it):
// 1. Callbacks can stack up if execution takes longer than interval
//    Example: setInterval(heavyTask, 100) — if heavyTask takes 150ms,
//    next callback is already queued before previous finishes!
// 2. Timer drift: intervals aren't precise, they accumulate error over time
// 3. Continues in background tabs (throttled to 1/sec, but wastes battery)
// 4. No guarantee of exact timing — same "minimum delay" issue as setTimeout

// WHY nested setTimeout is better than setInterval:
// setInterval fires every N ms REGARDLESS of whether previous callback finished
// Nested setTimeout waits for previous to FINISH, then schedules next
// This guarantees at least N ms GAP between executions (no stacking)

// requestAnimationFrame — sync with display refresh (60fps = ~16.6ms)
// Think of rAF as: "call my function right BEFORE the next screen paint"
// Your monitor refreshes ~60 times/sec. rAF syncs your code with that rhythm.
// This is why animations look smooth with rAF but janky with setTimeout —
// setTimeout fires at arbitrary times, possibly mid-frame or between frames.
let animationId;
function animate(timestamp) {

4. Callbacks & Callback Hell

📺 YouTube Tutorials
  • Callbacks — Namaste JavaScript (Akshay Saini)
  • Callback Hell — Traversy Media

Theory

What Are Callbacks and Why Do They Cause Problems?

A callback is simply a function you pass to another function, saying "call this when you're done." It's the most primitive way to handle asynchronous operations. But the real problem isn't the nesting — it's Inversion of Control.

Inversion of Control explained: When you pass a callback to a third-party library (like a payment processor), you're handing YOUR function to THEIR code and trusting them to: (1) call it exactly once, (2) call it at the right time, (3) pass the correct arguments, (4) handle errors properly. You have ZERO control over any of this. Imagine giving your house keys to a stranger and trusting they'll only enter once, at the right time, and lock up properly. That's what callbacks do with your program's control flow.

Why callback hell isn't just about ugly indentation: The real issues are: you can't use try/catch (the callback runs in a different call stack than the code that set it up), you can't return values from async operations (there's nobody to return TO), and composing multiple operations requires deeply nested callbacks where each depends on the previous. Error handling becomes repetitive and easy to forget at each level.

// Callback: function passed as argument to be called later
function fetchData(url, onSuccess, onError) {
  const xhr = new XMLHttpRequest();
  xhr.open("GET", url);
  xhr.onload = () => onSuccess(JSON.parse(xhr.response));
  xhr.onerror = () => onError(new Error("Network failure"));
  xhr.send();
}

// Callback Hell / Pyramid of Doom:
getUser(userId, (user) => {
  getOrders(user.id, (orders) => {
    getOrderDetails(orders[0].id, (details) => {
      getShipping(details.shippingId, (shipping) => {
        updateUI(shipping);
        // Error handling is nearly impossible here
      }, handleError);
    }, handleError);
  }, handleError);
}, handleError);

// Problems with callbacks:
// 1. Inversion of Control — you hand control to the callback host
// 2. No standard error handling (no try/catch)
// 3. Deep nesting reduces readability
// 4. Hard to compose or sequence
// 5. No cancellation mechanism
// 6. Can be called multiple times (or never) — no guarantees

// Solutions to callback hell:
// 1. Named functions (reduce nesting)
// 2. Promises (standardized, chainable)
// 3. async/await (readable, synchronous-looking)
// 4. RxJS Observables (Angular's preferred approach)

5. Promises (Complete Mastery)

📺 YouTube Tutorials
  • Promises — Namaste JavaScript (Akshay Saini)
  • JavaScript Promises — Web Dev Simplified
  • Promises In Depth — Fun Fun Function
  • Advanced Promises — Fireship

Theory

What a Promise Actually IS

A Promise is an object that acts as a placeholder for a value that doesn't exist yet. Think of it like ordering food at a restaurant — the waiter gives you a receipt (the Promise). That receipt isn't food, but it represents the food that will come later. You can decide now what you'll do when the food arrives (.then) and what you'll do if the kitchen says they're out (.catch).

Why Promises solve the Inversion of Control problem: With callbacks, YOU give your function to THEM. With Promises, THEY give a Promise object back to YOU. You retain control — you decide when to attach handlers, how many to attach, and you're guaranteed the Promise settles exactly once. It's like the difference between giving someone your phone vs them giving you a tracking number.

Key mental model: The executor function (the function you pass to new Promise()) runs synchronously — it executes immediately when you create the Promise. But .then() callbacks ALWAYS run asynchronously (as microtasks), even if the Promise is already resolved. This ensures predictable ordering.

Why .then() returns a NEW Promise: This is what enables chaining. Each .then() wraps your return value in a fresh Promise. If you return a plain value (like 42), the next .then() gets it immediately. If you return another Promise, the chain PAUSES and waits for it to settle. This is how you sequence async operations without nesting — each step is a flat .then() in a chain.

Promise States

// A Promise is in one of three states:
// 1. PENDING — initial state, not yet settled
// 2. FULFILLED (resolved) — operation completed successfully
// 3. REJECTED — operation failed

// Once settled (fulfilled or rejected), a Promise is IMMUTABLE — cannot change state again.

// Creating Promises:
const promise = new Promise((resolve, reject) => {
  // Executor function runs SYNCHRONOUSLY
  console.log("Executor runs immediately!"); // This is SYNC!
  
  // Async operation:
  setTimeout(() => {
    const success = Math.random() > 0.5;
    if (success) {
      resolve("Data loaded"); // Fulfills the promise
    } else {
      reject(new Error("Failed")); // Rejects the promise
    }
  }, 1000);
});

// Consuming Promises:
promise
  .then(value => {
    console.log("Success:", value);
    return value.toUpperCase(); // Return value becomes next promise's value
  })
  .then(upper => {
    console.log("Chained:", upper);
  })
  .catch(error => {
    console.error("Error:", error.message);
  })
  .finally(() => {
    console.log("Always runs — cleanup");
    // finally doesn't receive value, doesn't modify the chain
  });

Promise Chaining (Detailed)

// EVERY .then() returns a NEW Promise
// Whatever you return from .then() becomes the resolved value of that new Promise
// If you return a Promise, the chain WAITS for it

fetch("/api/users/1")
  .then(response => {
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json(); // Returns a Promise! Chain waits for it.
  })
  .then(user => {
    console.log(user.name);
    return fetch(`/api/posts?userId=${user.id}`); // Another Promise
  })
  .then(response => response.json())
  .then(posts => {
    console.log(`${posts.length} posts found`);
  })
  .catch(error => {
    // Catches ANY error in the entire chain above
    console.error("Something failed:", error.message);
  });

// Chain behavior rules:
// 1. Return a value → next .then receives it
// 2. Return a Promise → chain waits, next .then receives resolved value
// 3. Throw an error → skips to next .catch
// 4. Return nothing → next .then receives undefined
// 5. .catch returns a value → chain RESUMES (not still in error state)

Promise.resolve("start")
  .then(v => { throw new Error("oops"); })
  .then(v => console.log("skipped"))         // Skipped!
  .catch(e => {
    console.log("caught:", e.message);       // "caught: oops"
    return "recovered";                       // Recovery!
  })
  .then(v => console.log("resumed:", v));    // "resumed: recovered"

Creating Pre-Resolved/Rejected Promises

// Already resolved
Promise.resolve(42);             // Promise { 42 }
Promise.resolve(otherPromise);   // Returns otherPromise itself (if it's a thenable)

// Already rejected
Promise.reject(new Error("fail")); // Promise {  Error: fail }

// Thenable conversion (duck typing)
const thenable = {
  then(resolve) { resolve(42); }
};
Promise.resolve(thenable).then(v => console.log(v)); // 42

🎯 Interview Questions

Medium What are the three states of a Promise? Can a Promise go from rejected to fulfilled?

Answer: Pending, Fulfilled, Rejected. No — once settled (fulfilled or rejected), a Promise is immutable. It cannot transition between fulfilled and rejected. Calling resolve after reject (or vice versa) is silently ignored.

Hard What's the difference between these two?
promise.then(handleSuccess, handleError) vs promise.then(handleSuccess).catch(handleError)

Answer: With two-arg .then: handleError only catches rejection from the ORIGINAL promise, NOT errors thrown in handleSuccess. With .catch: it catches both original rejection AND errors thrown in the preceding .then. Generally prefer .catch at the end for comprehensive error handling.

const p1 = fetch("/api/users").then(r => r.json());
const p2 = fetch("/api/posts").then(r => r.json());
const p3 = fetch("/api/comments").then(r => r.json());

// Promise.all — waits for ALL to fulfill, or FAILS FAST on first rejection
try {
  const [users, posts, comments] = await Promise.all([p1, p2, p3]);
  // All three succeeded — results in order
} catch (error) {
  // If ANY one rejects, immediately rejects with that error
  // Other pending promises are NOT cancelled (still run, just ignored)
}

// Promise.allSettled — waits for ALL to settle (never rejects)
const results = await Promise.allSettled([p1, p2, p3]);
// Returns: [
//   { status: "fulfilled", value: [...users] },
//   { status: "rejected", reason: Error("...") },
//   { status: "fulfilled", value: [...comments] }
// ]
// Use when you want results regardless of individual failures

// Promise.race — resolves/rejects with the FIRST settled promise
const fastest = await Promise.race([
  fetch("/api/server1"),
  fetch("/api/server2"),
  new Promise((_, reject) => setTimeout(() => reject("timeout"), 5000))
]);
// First to settle (either fulfill or reject) wins

// Promise.any (ES2021) — resolves with FIRST fulfilled (ignores rejections)
try {
  const first = await Promise.any([
    fetch("/mirror1"),  // fails
    fetch("/mirror2"),  // fails
    fetch("/mirror3"),  // succeeds!
  ]);
  // first = result from mirror3
} catch (error) {
  // AggregateError: All promises were rejected
  console.log(error.errors); // Array of all rejection reasons
}

// Promise.withResolvers (ES2024)
const { promise, resolve, reject } = Promise.withResolvers();
// Useful when you need to resolve/reject from outside the executor
setTimeout(() => resolve("done"), 1000);
await promise; // "done"

function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    const results = [];
    let completed = 0;
    const total = promises.length;
    
    if (total === 0) return resolve([]);
    
    promises.forEach((promise, index) => {
      Promise.resolve(promise) // Handle non-promise values
        .then(value => {
          results[index] = value; // Maintain order
          completed++;
          if (completed === total) resolve(results);
        })
        .catch(reject); // First rejection rejects the whole thing
    });
  });
}

7. async/await (Complete)

📺 YouTube Tutorials
  • async/await — Web Dev Simplified
  • async/await — Fireship
  • async/await — Namaste JavaScript

Theory

What async/await Actually Does Under the Hood

async/await is syntactic sugar over Promises — it doesn't add new capability, it makes Promises easier to read and write. But understanding what happens behind the scenes is crucial for interviews:

What async does: Marking a function async means it ALWAYS returns a Promise. If you return a plain value (like "hello"), it's automatically wrapped in Promise.resolve("hello"). If you throw inside an async function, the returned Promise is rejected with that error. The function itself starts executing synchronously until it hits its first await.

What await does (the critical part): await essentially SPLITS your function into two halves. Everything before the await runs synchronously. When it hits await, it:

  1. Evaluates the expression after await (e.g., calls fetch() — this is synchronous!)
  2. Wraps the result in a Promise if it isn't one already
  3. Immediately returns from the async function (back to whoever called it)
  4. When the awaited Promise settles, the rest of the function is scheduled as a microtask
  5. The function resumes where it left off, with the resolved value of the Promise

Mental model: Think of await as saving a bookmark in your function. The function "pauses," lets other code run, and when the Promise resolves, it comes back to the bookmark and continues. The JS engine actually transforms async/await into a state machine (similar to generators) where each await is a state transition point.

Common misconception: await does NOT block the thread! It only "pauses" the async function — the Event Loop continues processing other tasks. This is why you can have multiple async functions "running" at the same time — they take turns on the call stack.

// async function ALWAYS returns a Promise
async function greet() {
  return "Hello"; // Equivalent to: return Promise.resolve("Hello")
}
greet().then(console.log); // "Hello"

// await PAUSES execution until Promise settles
async function fetchUser(id) {
  const response = await fetch(`/api/users/${id}`); // Pauses here
  // Code below runs only after fetch resolves
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const user = await response.json(); // Pauses again
  return user;
}

// What happens with await (under the hood):
async function example() {
  console.log("A");     // Sync
  await delay(1000);    // Pauses — remainder becomes microtask
  console.log("B");     // Runs as microtask after 1s
}
// Equivalent to:
function example() {
  console.log("A");
  return delay(1000).then(() => {
    console.log("B");
  });
}

// Top-level await (ES2022 — only in modules)
const config = await fetch("/config.json").then(r => r.json());
export { config };

// Sequential vs Parallel
async function sequential() {
  const user = await fetchUser(1);       // Wait 1s
  const posts = await fetchPosts(user.id); // Wait 1s more
  // Total: ~2s (one after another)
}

async function parallel() {
  const [user, posts] = await Promise.all([
    fetchUser(1),
    fetchPosts(1)
  ]);
  // Total: ~1s (both at the same time)
}

// Start parallel, await later
async function startEarly() {
  const userPromise = fetchUser(1);    // Start immediately
  const postsPromise = fetchPosts(1);  // Start immediately
  
  // Do other work here...
  
  const user = await userPromise;      // Await when needed
  const posts = await postsPromise;
}

// await in loops
async function processSequentially(urls) {
  const results = [];
  for (const url of urls) {
    const data = await fetch(url).then(r => r.json()); // One at a time
    results.push(data);
  }
  return results;
}

async function processInParallel(urls) {
  return Promise.all(urls.map(url => fetch(url).then(r => r.json())));
}

urls.forEach(async (url) => {

8. Async Error Handling Patterns

📺 YouTube Tutorials

  • Error Handling Patterns — Fireship

Theory

// Pattern 1: try/catch with async/await (most common)
async function fetchData() {
  try {
    const response = await fetch("/api/data");
    if (!response.ok) {
      throw new Error(`HTTP Error: ${response.status}`);
    }
    return await response.json();
  } catch (error) {
    if (error.name === "AbortError") {
      console.log("Request was cancelled");
    } else if (error instanceof TypeError) {
      console.log("Network error — are you offline?");
    } else {
      console.error("Unexpected:", error.message);
    }
    return null; // Graceful fallback
  }
}

// Pattern 2: Go-style [error, result] tuple
async function tryCatch(promise) {
  try {
    const result = await promise;
    return [null, result];
  } catch (error) {
    return [error, null];
  }
}

// Usage:
const [error, user] = await tryCatch(fetchUser(1));
if (error) {
  console.log("Failed:", error.message);
} else {
  console.log("User:", user);
}

// Pattern 3: .catch() on individual promises (selective handling)
async function loadDashboard() {
  const user = await fetchUser(1); // Let this throw if it fails
  const posts = await fetchPosts(1).catch(() => []); // Fallback to empty
  const notifications = await fetchNotifications().catch(() => []); // Fallback
  
  return { user, posts, notifications };
}

// Pattern 4: Retry with exponential backoff
async function fetchWithRetry(url, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      const response = await fetch(url);
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return await response.json();
    } catch (error) {
      if (attempt === maxRetries) throw error;
      const delay = Math.min(1000 * 2 ** attempt, 10000); // 1s, 2s, 4s...
      console.log(`Retry ${attempt + 1} in ${delay}ms...`);
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

// Pattern 5: Global unhandled rejection handler
window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled promise rejection:", event.reason);
  event.preventDefault(); // Prevent default error logging
  // Report to error tracking service
});

// Pattern 1: Throttled parallel execution (limit concurrency)
async function parallelLimit(tasks, limit) {
  const results = [];
  const executing = new Set();
  
  for (const [index, task] of tasks.entries()) {
    const promise = task().then(result => {
      executing.delete(promise);
      results[index] = result;
    });
    executing.add(promise);
    
    if (executing.size >= limit) {
      await Promise.race(executing); // Wait for one to finish
    }
  }
  
  await Promise.all(executing); // Wait for remaining
  return results;
}

// Usage: process 100 URLs but max 5 at a time
const urls = Array.from({length: 100}, (_, i) => `/api/item/${i}`);
const tasks = urls.map(url => () => fetch(url).then(r => r.json()));
const results = await parallelLimit(tasks, 5);

// Pattern 2: Sequential with early exit
async function findFirst(urls, predicate) {
  for (const url of urls) {
    const data = await fetch(url).then(r => r.json());
    if (predicate(data)) return data; // Early exit!
  }
  return null;
}

// Pattern 3: Parallel with timeout
async function fetchWithTimeout(urls, timeoutMs) {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), timeoutMs);
  
  try {
    const results = await Promise.all(
      urls.map(url => fetch(url, { signal: controller.signal }).then(r => r.json()))
    );
    return results;
  } finally {
    clearTimeout(timeout);
  }
}

// Pattern 4: Debounced async (search autocomplete)
function debounceAsync(fn, delay) {
  let timeoutId;
  let abortController;
  
  return async function(...args) {
    // Cancel previous
    if (abortController) abortController.abort();
    clearTimeout(timeoutId);
    
    abortController = new AbortController();
    const signal = abortController.signal;
    
    await new Promise(resolve => { timeoutId = setTimeout(resolve, delay); });
    
    if (signal.aborted) return;
    return fn(...args);
  };
}

// Pattern 5: Mutex / Lock (prevent race conditions)
class Mutex {
  #queue = [];
  #locked = false;
  
  async acquire() {
    if (this.#locked) {
      await new Promise(resolve => this.#queue.push(resolve));
    }
    this.#locked = true;
  }
  
  release() {
    if (this.#queue.length > 0) {
      const next = this.#queue.shift();
      next(); // Wake up next waiter
    } else {
      this.#locked = false;
    }
  }
}

const mutex = new Mutex();
async function criticalSection() {
  await mutex.acquire();
  try {
    // Only one execution at a time
    await updateDatabase();
  } finally {
    mutex.release();
  }
}

function cancellableSleep(ms) {
  const controller = new AbortController();

    const timerId = setTimeout(resolve, ms);
