JavaScript vs Other Languages

  • Interpreted + JIT Compiled — Not purely interpreted; modern engines (V8, SpiderMonkey) use Just-In-Time compilation
  • Single-threaded — One call stack, uses event loop for concurrency
  • Dynamically typed — Types resolved at runtime, not compile-time
  • Multi-paradigm — Supports OOP (prototype-based), functional, and imperative
  • First-class functions — Functions are objects, can be assigned to variables, passed as arguments
  • Prototype-based inheritance — No classical inheritance (classes are syntactic sugar)

What Each of These Actually Means (Deep Explanation)

1. Interpreted + JIT Compiled — What does this mean?

In old days, languages were either compiled (like C — entire source converted to machine code BEFORE running, resulting in a fast .exe file) or interpreted (like old PHP — each line read and executed one at a time, slower but instant startup). JavaScript started as purely interpreted — Brendan Eich's first engine just read each line and executed it.

Modern JS engines like V8 use a hybrid approach called JIT (Just-In-Time) compilation. Here's what happens: When your code first runs, the engine interprets it to bytecode (like a simplified instruction set) using the Ignition interpreter. This gives you fast startup. While running, the engine monitors which functions get called repeatedly ("hot" code). These hot functions are then sent to the TurboFan compiler which generates highly optimized machine code (like C would produce). The result? You get the convenience of not needing a compile step, BUT your code runs nearly as fast as compiled languages after it "warms up."

Real-world impact: The first time a function runs, it's slow (interpreted). By the 100th call, it's blazing fast (compiled). This is why benchmarks should include "warm-up" runs.

2. Single-threaded — What does this mean?

A "thread" is like a worker that can execute instructions. Languages like Java or C++ can create multiple threads (multiple workers doing tasks simultaneously). JavaScript has only ONE thread — meaning only ONE piece of code executes at any given moment. There is only ONE call stack.

So how does JS handle async operations like fetching data or timers? Through the Event Loop. When you call setTimeout or fetch, JS doesn't actually execute it itself — it hands it off to the Browser/Node.js runtime (written in C++) which handles it in a separate thread. When the async work completes, the callback is placed in a queue. The Event Loop checks: "Is the call stack empty? If yes, pick the next task from the queue and push it onto the stack."

Why single-threaded? It avoids complex bugs like race conditions and deadlocks. The tradeoff: CPU-intensive work (like image processing) blocks the UI. Solution: Web Workers (separate threads for heavy computation that can't access DOM).

3. Dynamically typed — What does this mean?

In statically typed languages (Java, TypeScript, C), you declare a variable's type and it CANNOT change: int x = 5; x = "hello"; → compile error. The compiler catches type mistakes before code runs.

In JavaScript, variables have NO fixed type. The same variable can hold a number, then a string, then an object:

let x = 42;        // x is a number right now
x = "hello";      // now x is a string — no error!
x = { age: 25 };  // now x is an object — still fine!
x = true;         // now a boolean

The type belongs to the VALUE, not the variable. The variable is just a label pointing to whatever value. Types are only checked when code actually runs (runtime), not before. This gives flexibility but also causes bugs that TypeScript solves by adding static type checking on top of JavaScript.

4. Multi-paradigm — What does this mean?

A "paradigm" is a style of programming. Most languages strongly favor one style. JavaScript supports ALL three major ones:

  • Imperative/Procedural: Step-by-step instructions. "Do this, then do that." (for loops, if statements, sequential code)
  • Object-Oriented (OOP): Organize code into objects with properties and methods. JavaScript uses prototypes (not classes under the hood — class is syntactic sugar over prototypal inheritance).
  • Functional: Treat computation as evaluation of mathematical functions. No side effects, immutable data. (map, filter, reduce, pure functions, higher-order functions)

In practice: Angular uses OOP heavily (classes, decorators, dependency injection). React leans functional (hooks, pure components). You can mix paradigms in the same project — this is JavaScript's superpower AND its chaos.

5. First-class functions — What does this mean?

"First-class" means functions are treated exactly like any other value (numbers, strings, objects). Specifically:

// 1. Assign to a variable
const greet = function(name) { return `Hello ${name}`; };

// 2. Pass as an argument to another function
function repeat(fn, times) {
  for (let i = 0; i < times; i++) fn();
}
repeat(() => console.log("Hi"), 3);

// 3. Return from another function (closure/factory)
function multiplier(factor) {
  return function(num) { return num * factor; }; // returns a function!
}
const double = multiplier(2);
double(5); // 10

// 4. Store in data structures
const actions = [
  () => console.log("action 1"),
  () => console.log("action 2"),
];
actions[0](); // "action 1"

Why this matters: This enables callbacks, Promises, higher-order functions (map/filter/reduce), closures, decorators, middleware, and event handlers. Without first-class functions, patterns like array.map(x => x * 2) or onClick={handleClick} wouldn't exist.

6. Prototype-based inheritance — What does this mean?

In Java/C++, you have classes as blueprints and create objects from them. There's a clear hierarchy: Class → Subclass → Instance.

JavaScript does NOT have real classes. It has prototypes. Every object has a hidden link (__proto__) to another object called its "prototype." When you access a property that doesn't exist on an object, JS looks UP the prototype chain until it finds it or reaches null:

const animal = { eats: true, walk() { return "walking"; } };
const dog = Object.create(animal); // dog's prototype = animal
dog.barks = true;

dog.barks;  // true (own property)
dog.eats;   // true (found on prototype — animal)
dog.walk(); // "walking" (found on prototype)
dog.fly;    // undefined (not found anywhere in chain)

// The ES6 "class" keyword:
class Dog extends Animal { }
// This is SYNTACTIC SUGAR — underneath, it still sets up
// prototype links. Dog.prototype.__proto__ === Animal.prototype

Key insight for interviews: When someone says "JavaScript classes," understand that class is just prettier syntax for prototype chain setup + constructor functions. There's no class-based instantiation like Java — it's prototypal delegation all the way down.

What Each Step Actually Does (Step-by-Step Walkthrough)

Let's trace what happens when V8 executes function add(a, b) { return a + b; } add(5, 3);:

Step 1: Scanner/Lexer (Tokenization)

The scanner reads your raw source code character by character and breaks it into meaningful chunks called tokens. Think of it like splitting a sentence into words. The code let x = 5 + 3; becomes tokens: [LET] [IDENTIFIER:"x"] [EQUALS] [NUMBER:5] [PLUS] [NUMBER:3] [SEMICOLON]. This step strips whitespace, comments, and validates that the characters form valid tokens. If you write let 123abc, the scanner catches it here.

Step 2: Parser (AST Generation)

The parser takes the flat list of tokens and builds a tree structure called an Abstract Syntax Tree (AST). The AST represents the grammatical structure of your code. For let x = 5 + 3, the AST looks like:

VariableDeclaration (let)
  └── Declarator
        ├── Identifier: "x"
        └── BinaryExpression (+)
              ├── Literal: 5
              └── Literal: 3

The parser knows that + binds 5 and 3 before assigning to x (operator precedence). If your code has a syntax error (like missing brackets), the parser throws a SyntaxError here. V8 uses "lazy parsing" — it only fully parses functions when they're actually called, not when defined (saves startup time).

Step 3: Ignition Interpreter (Bytecode Generation)

Ignition walks the AST and generates bytecode — a compact, low-level instruction set that's between source code and machine code. It's like a simplified assembly language that V8's virtual machine understands. For our add(5, 3):

// Simplified bytecode representation:
LdaSmi [5]          // Load small integer 5 into accumulator
Star r0             // Store in register 0
LdaSmi [3]          // Load 3
Add r0              // Add register 0 to accumulator
Return              // Return result (8)

Why not compile directly to machine code? Because compilation is slow. Ignition gives you fast startup — code starts executing immediately. Most code runs only once or twice (initialization, imports), so optimizing it would waste time. Only "hot" code deserves full optimization.

Step 4: Profiler/Feedback Collector

While Ignition runs bytecode, a profiler monitors execution. It tracks: How many times each function is called? What types of arguments are passed? Which branches are taken? This information is called type feedback. If add() is always called with two numbers, the profiler notes: "this function always receives Number, Number." After a function is called enough times (the "hot" threshold, typically ~1000 calls), it's flagged for optimization.

Step 5: TurboFan Optimizing Compiler

TurboFan takes the bytecode + type feedback and generates optimized machine code (actual CPU instructions: x86, ARM, etc.). Because the profiler said "add() always gets numbers," TurboFan can skip type checks and generate a single CPU ADD instruction instead of a generic "check type, coerce if needed, then add" routine. This makes hot functions run 10-100x faster than interpreted bytecode.

Step 6: Deoptimization (Bail-out)

What if TurboFan assumed add() always gets numbers, but then you call add("hello", "world")? The optimized code can't handle strings. V8 performs a deoptimization: it throws away the optimized machine code and falls back to the Ignition bytecode. The function runs correctly (but slower). The profiler starts collecting new feedback, and TurboFan may try again with broader type assumptions.

// This causes deoptimization:
function add(a, b) { return a + b; }

// First 1000 calls — all numbers, gets optimized
for (let i = 0; i < 1000; i++) add(i, i);  // TurboFan optimizes for numbers

// Then suddenly:
add("hello", "world");  // 💥 Deoptimization! Assumptions violated.
// V8 drops back to bytecode, re-profiles, may re-optimize later

// LESSON: Keep your function arguments consistent in type!

Memory Management

  • Stack — Stores primitive values and function call frames. LIFO order. Fixed size, fast access.
  • Heap — Stores objects, arrays, functions. Dynamically allocated. Managed by Garbage Collector.
  • Garbage Collection — V8 uses "Mark-and-Sweep" + "Generational GC" (Young Generation with Scavenger, Old Generation with Mark-Compact).

How Memory Actually Works in JavaScript

Stack Memory — Fast, Small, Automatic

The stack is like a notepad where JS writes temporary notes. Every time you create a primitive variable (let x = 5), the value 5 is written directly on the stack. Every time a function is called, a new "frame" (section of the notepad) is added with that function's local variables. When the function returns, that frame is erased automatically. Stack memory is fast because access is predictable (just move a pointer up/down), small (typically 1-8MB), and self-cleaning (no garbage collection needed).

Heap Memory — Large, Slow, Manual Cleanup

The heap is like a warehouse where JS stores large, complex things (objects, arrays, closures). When you write let obj = { name: "Sid" }, the object { name: "Sid" } goes to the heap, and the stack stores only a reference (a memory address like 0x7f3a2b) pointing to where the object lives in the heap. Heap access is slower because the computer must follow the pointer to find the data.

Garbage Collection — How JS Cleans Up

Since you can't manually free memory in JS (unlike C's free()), the engine must figure out what's no longer needed and clean it up automatically. V8's GC works in two generations:

Young Generation (Scavenger / Minor GC): Most objects die young (temporary variables in a loop, intermediate calculations). The young generation is a small memory space (~1-8MB). When it fills up, the Scavenger runs: it copies surviving objects to a second space and discards everything else. Objects that survive two scavenge cycles are "promoted" to the Old Generation. This runs frequently but is very fast (1-2ms).

Old Generation (Mark-Compact / Major GC): Long-lived objects (module-level data, cached values, app state). When old space fills up, Mark-and-Sweep runs: (1) Mark — start from "roots" (global object, call stack references), follow all references, mark everything reachable as "alive." (2) Sweep — anything NOT marked is garbage, free that memory. (3) Compact — defragment by moving objects together. This is slower (10-50ms) but runs infrequently.

// What causes memory leaks (GC CAN'T clean these):

// 1. Forgotten event listeners
element.addEventListener('click', handler);
// If element is removed from DOM but listener isn't removed,
// handler (and everything it references) stays in memory.

// 2. Closures holding references
function createLeak() {
  const hugeArray = new Array(1000000).fill('x');
  return function() {
    // This closure keeps hugeArray alive forever!
    console.log(hugeArray.length);
  };
}
const leak = createLeak(); // hugeArray can never be GC'd

// 3. Global variables
window.cache = fetchedData; // Lives forever until page reload

// 4. Detached DOM nodes

document.body.appendChild(div);
const ref = div;
document.body.removeChild(div);
// div is removed from DOM but `ref` still points to it → leak!
// Stack vs Heap visualization
let name = "Sid";      // "Sid" stored in STACK (primitive)
let age = 25;          // 25 stored in STACK (primitive)

let person = {         // Reference stored in STACK
  name: "Sid",         // Object stored in HEAP
  age: 25
};

let person2 = person;  // person2 gets COPY of reference (both point to same heap object)
person2.name = "Ram";
console.log(person.name); // "Ram" — both reference same object!

How the Runtime Environment Actually Works (Component by Component)

The diagram above shows the COMPLETE picture of how JavaScript runs in a browser. Let's break down each component and how they work together:

1. Call Stack — The Single Thread of Execution

The Call Stack is where JavaScript actually executes code. It's a LIFO (Last In, First Out) data structure — like a stack of plates. When you call a function, a new "frame" (execution context) is pushed ON TOP. When that function returns, its frame is popped OFF the top. Only the TOPMOST frame is actively running at any time. This is why JS is "single-threaded" — there's only ONE call stack, executing ONE function at a time.

function multiply(a, b) { return a * b; }
function square(n) { return multiply(n, n); }
function printSquare(n) { console.log(square(n)); }
printSquare(5);

// Call Stack progression:
// 1. [printSquare(5)]           — pushed
// 2. [printSquare] [square(5)]  — square pushed on top
// 3. [printSquare] [square] [multiply(5,5)] — multiply pushed
// 4. [printSquare] [square]     — multiply returns 25, popped
// 5. [printSquare]              — square returns 25, popped
// 6. []                         — printSquare done, popped

2. Memory Heap — Where Objects Live

The Heap is a large, unstructured region of memory where objects, arrays, and functions are stored. Unlike the stack (organized, fixed-size), the heap is dynamically allocated — objects can grow/shrink. The stack stores references (pointers) to heap objects. The Garbage Collector periodically scans the heap, finds objects that no variable references anymore, and frees that memory.

3. Web APIs — The Browser's Superpowers (NOT part of JavaScript!)

This is the most misunderstood part. setTimeout, fetch, DOM manipulation, localStorage — these are NOT JavaScript features. They're provided by the browser's C++ runtime. The JavaScript spec defines NONE of these. They're given to JS as "gifts" through the global window object.

When you call setTimeout(callback, 1000), here's what happens:

  1. JS calls the Web API: "Hey browser, set a timer for 1000ms, and here's a callback."
  2. The browser's timer runs in a separate thread (C++ thread, NOT JS thread).
  3. JS call stack is now FREE to continue executing other code.
  4. After 1000ms, the browser moves the callback to the Task Queue.

This is how JS appears to do async work while being single-threaded — it delegates to the multi-threaded browser runtime!

4. Task Queue (Macrotask Queue) — Waiting Room for Callbacks

When a Web API completes its work (timer expires, network response arrives, click happens), the callback function is placed in the Task Queue. It waits here until the Call Stack is completely empty. Tasks include: setTimeout/setInterval callbacks, DOM event callbacks (click, scroll), MessageChannel, I/O callbacks.

5. Microtask Queue — The VIP Fast Lane

The Microtask Queue has HIGHER PRIORITY than the Task Queue. After EACH task completes (and call stack is empty), ALL microtasks are processed before the next macrotask. Microtasks include: Promise.then()/.catch()/.finally(), queueMicrotask(), MutationObserver, async/await continuations.

6. Event Loop — The Traffic Controller

The Event Loop is a continuously running process that coordinates everything. Here's its algorithm:

// Event Loop (simplified pseudocode):
while (true) {
  // 1. Execute all synchronous code on Call Stack until stack is empty
  
  // 2. Process ALL microtasks (drain the microtask queue completely)
  while (microtaskQueue.hasItems()) {
    callStack.push(microtaskQueue.dequeue());
    execute();
  }
  
  // 3. Render/Paint if needed (requestAnimationFrame callbacks here)
  
  // 4. Pick ONE task from Task Queue (if any)
  if (taskQueue.hasItems()) {
    callStack.push(taskQueue.dequeue());
    execute();
  }
  
  // 5. Go back to step 2 (check microtasks again!)
}

Complete Example — Putting It All Together:

console.log("1: Start");                    // Synchronous → Call Stack

setTimeout(() => console.log("2: Timeout"), 0); // → Web API → Task Queue

Promise.resolve().then(() => console.log("3: Promise")); // → Microtask Queue

console.log("4: End");                      // Synchronous → Call Stack

// OUTPUT:
// "1: Start"     ← sync (executed immediately)
// "4: End"       ← sync (executed immediately)
// "3: Promise"   ← microtask (runs before ANY macrotask)
// "2: Timeout"   ← macrotask (runs last, even though timeout is 0ms!)

// WHY? After sync code finishes, Event Loop drains microtasks FIRST
// (Promise), then picks one macrotask (setTimeout).
Key Takeaway: JavaScript itself is single-threaded (one call stack). But the RUNTIME (browser/Node.js) is multi-threaded. Async operations are handled by the runtime's C++ threads. The Event Loop is just the bridge that moves completed callbacks back into JS's single thread in the right order: sync → microtasks → render → macrotask → repeat.

🎯 Interview Questions

Medium Is JavaScript interpreted or compiled?

Answer: Neither purely. Modern JS engines use JIT (Just-In-Time) compilation. Code is first interpreted to bytecode (fast startup), then hot paths are compiled to optimized machine code by TurboFan. If optimization assumptions break, it deoptimizes back to bytecode. This is called "adaptive optimization."

Hard What causes V8 deoptimization? How do you avoid it?

Answer: Deoptimization occurs when TurboFan's type assumptions are violated. Examples: (1) Changing object shape after creation (adding/deleting properties), (2) Passing different types to the same function, (3) Using `arguments` object in optimized code, (4) Using `eval()` or `with`. Avoid by: keeping object shapes consistent, using TypeScript, avoiding polymorphic functions.

Hard Explain the difference between Stack and Heap memory in JS.

Answer: Stack stores primitives and execution context frames (fixed-size, LIFO, fast). Heap stores objects/arrays/functions (dynamically sized, slower access, garbage collected). Variables holding objects store a reference (pointer) on the stack that points to the heap location. This is why object assignment copies the reference, not the value.

Theory

What is an Execution Context?

An Execution Context (EC) is the environment in which JavaScript code is evaluated and executed. It contains everything the code needs: variables, functions, scope chain, and the value of this.

Three types of Execution Context:

  1. Global Execution Context (GEC) — Created when the script first runs. Only one per program. Creates the global object (window in browser, global in Node.js) and sets this to it.
  2. Function Execution Context (FEC) — Created each time a function is invoked. Each function gets its own EC.
  3. Eval Execution Context — Created inside eval() (avoid using eval).

Two Phases of Execution Context

Phase 1: Creation Phase (Memory Allocation)

  • Creates the Variable Object (VO) / Lexical Environment
  • var declarations → allocated memory, initialized to undefined
  • let/const → allocated memory but NOT initialized (Temporal Dead Zone)
  • Function declarations → entire function stored in memory (hoisted completely)
  • Sets up Scope Chain
  • Determines value of this

Phase 2: Execution Phase (Code Execution)

  • Code executes line by line
  • Values are assigned to variables
  • Functions are invoked (creating new ECs)
// Visualizing Execution Context
var x = 10;
function greet(name) {
  var message = "Hello " + name;
  return message;
}
var result = greet("Sid");

/* 
CREATION PHASE (Global EC):
  x: undefined
  greet: [entire function]
  result: undefined
  this: window

EXECUTION PHASE:
  x = 10
  greet("Sid") → NEW Function EC created:
    CREATION PHASE (greet EC):
      name: "Sid" (argument)
      message: undefined
    EXECUTION PHASE:
      message = "Hello Sid"
      return "Hello Sid"
    → Function EC destroyed after return
  result = "Hello Sid"
*/

Call Stack (Execution Stack)

The Call Stack is a LIFO (Last-In-First-Out) data structure that keeps track of execution contexts. When a function is called, its EC is pushed onto the stack. When it returns, it's popped off.

function first() {
  console.log("first");
  second();
  console.log("first end");
}
function second() {
  console.log("second");
  third();
}
function third() {
  console.log("third");
}
first();

/* Call Stack progression:
  [1] Global EC
  [2] Global EC → first() EC
  [3] Global EC → first() EC → second() EC
  [4] Global EC → first() EC → second() EC → third() EC
  [5] Global EC → first() EC → second() EC  (third popped)
  [6] Global EC → first() EC  (second popped)
  [7] Global EC  (first popped)

  Output: "first" → "second" → "third" → "first end"
*/

Stack Overflow

// Infinite recursion causes stack overflow
function forever() {
  forever(); // keeps pushing ECs onto stack
}
forever(); // RangeError: Maximum call stack size exceeded

// Chrome default: ~15,000-16,000 frames
// Node.js: configurable via --stack-size

🎯 Interview Questions

Hard Explain the two phases of Execution Context creation in detail.

Answer: Phase 1 (Creation/Memory): Variable Object is created — var variables are allocated and set to undefined, let/const are allocated but uninitialized (TDZ), function declarations are stored entirely. Scope chain is established. 'this' binding is determined. Phase 2 (Execution): Code runs line by line, values are assigned, functions are called (creating child ECs on the stack).

Expert What is the difference between Variable Object and Lexical Environment in ES6?

Answer: In ES5 spec, each EC has a Variable Object (stores var/function declarations). In ES6+ spec, this was replaced with Lexical Environment (has Environment Record + outer reference). Two types: (1) Declarative Environment Record (for let/const/function/class) and (2) Object Environment Record (for with/global). var uses a separate VariableEnvironment component that also points to a Lexical Environment.

4. Variables: var, let, const

📺 YouTube Tutorials
  • let & const in JS — Namaste JavaScript (Akshay Saini)
  • var, let, const — Web Dev Simplified
  • Hoisting Explained — Namaste JavaScript

Theory

var (Function-scoped, ES5)

// var is function-scoped (NOT block-scoped)
function example() {
  var x = 10;
  if (true) {
    var x = 20; // SAME variable — overwrites!
    console.log(x); // 20
  }
  console.log(x); // 20 (not 10!)
}

// var is hoisted with initialization to undefined
console.log(a); // undefined (NOT ReferenceError)
var a = 5;

// var allows re-declaration
var name = "Sid";
var name = "Ram"; // No error!

// var attaches to window object in global scope
var globalVar = "hello";
console.log(window.globalVar); // "hello"

let (Block-scoped, ES6)

// let is block-scoped
function example() {
  let x = 10;
  if (true) {
    let x = 20; // DIFFERENT variable (new block scope)
    console.log(x); // 20
  }
  console.log(x); // 10
}

// let is hoisted but NOT initialized (Temporal Dead Zone)
console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 5;

// let does NOT allow re-declaration in same scope
let name = "Sid";
let name = "Ram"; // SyntaxError: Identifier 'name' has already been declared

// let does NOT attach to window
let globalLet = "hello";
console.log(window.globalLet); // undefined

const (Block-scoped, Immutable Binding, ES6)

// const must be initialized at declaration
const PI; // SyntaxError: Missing initializer in const declaration
const PI = 3.14159;

// const binding cannot be reassigned
PI = 3.14; // TypeError: Assignment to constant variable

// BUT — const objects/arrays ARE mutable (reference is constant, not value)
const person = { name: "Sid", age: 25 };
person.name = "Ram";  // ✅ Works! Object is mutable
person = {};          // ❌ TypeError: Assignment to constant variable

const arr = [1, 2, 3];
arr.push(4);    // ✅ Works! [1, 2, 3, 4]
arr = [5, 6];   // ❌ TypeError

// To make truly immutable: Object.freeze (shallow)
const frozen = Object.freeze({ name: "Sid", address: { city: "BLR" } });
frozen.name = "Ram";          // Silently fails (or TypeError in strict mode)
frozen.address.city = "MUM";  // ✅ Works! freeze is SHALLOW

Temporal Dead Zone (TDZ)

// TDZ = time between entering scope and declaration being reached
{
  // TDZ for 'x' starts here
  console.log(x); // ReferenceError (TDZ)
  console.log(typeof x); // ReferenceError (even typeof!)
  let x = 10; // TDZ ends here
  console.log(x); // 10
}

// var has NO TDZ
{
  console.log(y); // undefined (hoisted, initialized)
  var y = 20;
}

🎯 Interview Questions

Easy What is the difference between var, let, and const?

Answer: var is function-scoped, hoisted with undefined, allows re-declaration, adds to window. let is block-scoped, hoisted but in TDZ, no re-declaration. const is like let but binding cannot be reassigned (must initialize). const objects are still mutable.

Medium What is the Temporal Dead Zone?

Answer: TDZ is the period between entering a scope and the point where a let/const variable is declared. Accessing the variable during TDZ throws ReferenceError. It exists because let/const are hoisted (engine knows about them) but not initialized until the declaration line is executed.

Hard Why does the classic for-loop with var and setTimeout print the same value? How to fix it?

Answer: var is function-scoped, so there's ONE i shared across all iterations. By the time setTimeout callbacks run, the loop has finished and i=3. Fixes: (1) Use let (creates new binding per iteration), (2) IIFE: (function(i){ setTimeout(()=>console.log(i), 0) })(i), (3) setTimeout's 3rd parameter: setTimeout(console.log, 0, i).

// Everything that's not a primitive is an Object
let obj = { name: "Sid" };           // Object literal

// typeof results (tricky!)
typeof undefined    // "undefined"

typeof true         // "boolean"
typeof 42           // "number"
typeof "hello"      // "string"
typeof Symbol()     // "symbol"
typeof 10n          // "bigint"
typeof {}           // "object"
typeof []           // "object" ← use Array.isArray([])
typeof function(){} // "function" ← special case
typeof NaN          // "number" ← NaN is a number!

Pass by Value vs Pass by Reference

// Primitives: Pass by VALUE (copy)
let a = 10;
let b = a;     // b gets COPY of value
b = 20;
console.log(a); // 10 (unchanged)

// Objects: Pass by REFERENCE (shared pointer)
let obj1 = { x: 1 };
let obj2 = obj1;   // obj2 gets copy of REFERENCE
obj2.x = 99;
console.log(obj1.x); // 99 (same object!)

// Function arguments follow same rules:
function modify(prim, obj) {
  prim = 100;     // local copy changed
  obj.val = 100;  // shared object modified
}
let num = 5;
let data = { val: 5 };
modify(num, data);
console.log(num);      // 5 (unchanged)
console.log(data.val); // 100 (modified!)
Important: JavaScript does NOT have "pass by reference" for primitives. For objects, it's technically "pass by sharing" (copy of reference). You cannot reassign the original variable from inside a function: function(obj) { obj = {} } doesn't affect the original.

🎯 Interview Questions

Easy What are the primitive types in JavaScript?

Answer: 7 primitives: Number, String, Boolean, undefined, null, Symbol (ES6), BigInt (ES2020). They are immutable, compared by value, stored on the stack.

Medium Why is typeof null === "object"?

Answer: It's a bug from the first version of JavaScript (1995). In the original implementation, values were represented with a type tag and value. Objects had type tag 0, and null was represented as the NULL pointer (0x00). So typeof checks the tag and incorrectly returns "object" for null. It can never be fixed because too much code depends on it.

Hard How do you check if something is NaN reliably?

Answer: Use Number.isNaN(value) — it returns true ONLY if value is actually NaN. Do NOT use global isNaN() which coerces first: isNaN("hello") returns true (coerces to NaN). Also: value !== value is true only for NaN (exploits NaN's unique self-inequality).

// == (loose equality) — COERCES before comparing
0 == false;    // true (false → 0)
"" == false;   // true ("" → 0, false → 0)
null == undefined; // true (special rule)
null == 0;     // false (null only == undefined)
NaN == NaN;    // false (NaN never equals anything)
[] == false;   // true ([] → "" → 0, false → 0)
[] == ![];     // true! ([] → 0, ![] → false → 0)

// === (strict equality) — NO coercion
0 === false;   // false (different types)
"5" === 5;     // false

The Abstract Equality Algorithm (== rules)

/*
When x == y:
1. Same type → compare normally (=== behavior)
2. null == undefined → true
3. Number vs String → convert String to Number
4. Boolean vs anything → convert Boolean to Number first
5. Object vs Primitive → call ToPrimitive (valueOf, then toString)
6. Everything else → false
*/

// Example: [] == ![]
// Step 1: ![] → false ([] is truthy, !truthy = false)
// Now: [] == false
// Step 2: Boolean → Number: false → 0
// Now: [] == 0
// Step 3: Object → Primitive: [].valueOf() → [] (not primitive)
//         [].toString() → ""
// Now: "" == 0
// Step 4: String → Number: "" → 0
// Now: 0 == 0 → true!
Golden Rule: Always use === (strict equality). The only acceptable use of == is value == null to check both null and undefined in one check.

Object to Primitive Coercion ([Symbol.toPrimitive], valueOf, toString)

// The engine calls methods in this order:
// 1. [Symbol.toPrimitive](hint) — if defined
// 2. For "number" hint: valueOf() → toString()
// 3. For "string" hint: toString() → valueOf()

let obj = {
  [Symbol.toPrimitive](hint) {
    if (hint === "number") return 42;
    if (hint === "string") return "hello";
    return true; // default
  }
};
+obj;          // 42
`${obj}`;      // "hello"
obj + "";      // "true" (default hint)

// Classic interview trick: make (a == 1 && a == 2 && a == 3)
let a = {
  value: 1,
  valueOf() { return this.value++; }
};
console.log(a == 1 && a == 2 && a == 3); // true!

Arithmetic Operators

let x = 5;

Comparison Operators

5 == "5";   // true (loose: coerces types)
5 === "5";  // false (strict: no coercion)
5 != "5";   // false
5 !== "5";  // true
5 > 3;      // true
5 >= 5;     // true
5 < 3;      // false

// Object comparison — by reference!
{} === {};  // false (different objects in memory)
[] === [];  // false
let arr = [1];
let ref = arr;
ref === arr; // true (same reference)

Logical Operators (Short-circuit evaluation)

// && (AND) — returns first falsy OR last truthy
true && "hello";   // "hello" (both truthy → returns last)
false && "hello";  // false (first falsy → short-circuits)
"" && "hello";     // "" (falsy → stops)
1 && 2 && 3;      // 3 (all truthy → returns last)
1 && 0 && 3;      // 0 (first falsy)

// || (OR) — returns first truthy OR last falsy
false || "hello";  // "hello" (first truthy)
"" || "default";   // "default"
0 || "" || null || "found"; // "found"
0 || "" || null;   // null (all falsy → returns last)

// ?? (Nullish Coalescing, ES2020) — only null/undefined trigger fallback
0 ?? "default";    // 0 (0 is NOT null/undefined)
"" ?? "default";   // "" (NOT null/undefined)
null ?? "default"; // "default"
undefined ?? "default"; // "default"

// Difference: || vs ??
let count = 0;
count || 10;  // 10 (0 is falsy — BAD if 0 is valid!)
count ?? 10;  // 0 (0 is not null/undefined — CORRECT!)

// ?. (Optional Chaining, ES2020)
let user = { address: { city: "BLR" } };
user?.address?.city;  // "BLR"
user?.phone?.number;  // undefined (no error!)
user?.getName?.();    // undefined (safe function call)

Assignment Operators (ES2021 Logical Assignment)

let x = 10;
x += 5;   // x = x + 5 = 15
x -= 3;   // x = 12
x *= 2;   // x = 24
x /= 4;   // x = 6
x %= 4;   // x = 2
x **= 3;  // x = 8

// Logical Assignment (ES2021)
let a = null;
a ??= "default";  // a = "default" (was null)
a ??= "other";    // a = "default" (not null anymore)

let b = "";
b ||= "fallback"; // b = "fallback" (was falsy)

let c = 1;
c &&= 2;          // c = 2 (was truthy, so assign)

🎯 Interview Questions

Medium What is the difference between || and ???

Answer: || returns the right operand if the left is any falsy value (0, "", false, null, undefined, NaN). ?? returns the right operand ONLY if the left is null or undefined. Use ?? when 0 or "" are valid values you want to keep.

Medium How does short-circuit evaluation work?

Answer: && stops at first falsy (returns it), if all truthy returns last. || stops at first truthy (returns it), if all falsy returns last. The key insight: they return actual values, not booleans. 1 && "hello" returns "hello", not true.

Theory

Conditional Statements

// if / else if / else
let score = 85;
if (score >= 90) {
  console.log("A");
} else if (score >= 80) {
  console.log("B"); // ← this runs
} else if (score >= 70) {
  console.log("C");
} else {
  console.log("F");
}

// Ternary Operator
let grade = score >= 90 ? "A" : score >= 80 ? "B" : "C";

// switch (uses === for comparison)
let day = "Monday";
switch (day) {
  case "Monday":
  case "Tuesday":   // fall-through (shared case)
    console.log("Weekday start");
    break;          // without break, falls through!
  case "Friday":
    console.log("TGIF");
    break;
  default:
    console.log("Midweek");
}

// switch with expressions (pattern)
let temp = 35;
switch (true) {
  case temp > 40: console.log("Extreme heat"); break;
  case temp > 30: console.log("Hot"); break;  // ← runs
  case temp > 20: console.log("Warm"); break;
  default: console.log("Cool");
}

Loops

// 1. for loop (classic)
for (let i = 0; i < 5; i++) {
  console.log(i); // 0, 1, 2, 3, 4
}

// 2. while loop
let i = 0;
while (i < 5) {
  console.log(i);
  i++;
}

// 3. do...while (executes at least once)
let j = 10;
do {
  console.log(j); // prints 10 even though condition is false
} while (j < 5);

// 4. for...in (iterates over KEYS/indices — use for objects)
let obj = { a: 1, b: 2, c: 3 };
for (let key in obj) {
  console.log(key, obj[key]); // "a" 1, "b" 2, "c" 3
}
// ⚠️ for...in also iterates inherited properties!
// Always use hasOwnProperty check or Object.keys()

// 5. for...of (iterates over VALUES — use for iterables)
let arr = [10, 20, 30];
for (let value of arr) {
  console.log(value); // 10, 20, 30
}
// Works on: Arrays, Strings, Maps, Sets, arguments, NodeLists
// Does NOT work on plain objects! (not iterable)

// for...of with index
for (let [index, value] of arr.entries()) {
  console.log(index, value);
}

// 6. Loop control
for (let i = 0; i < 10; i++) {
  if (i === 3) continue; // skip iteration
  if (i === 7) break;    // exit loop
  console.log(i); // 0, 1, 2, 4, 5, 6
}

// Labeled statements (for nested loops)
outer: for (let i = 0; i < 3; i++) {
  for (let j = 0; j < 3; j++) {
    if (j === 1) continue outer; // skip to next i
    if (i === 2) break outer;    // exit both loops
    console.log(i, j);
  }
}

🎯 Interview Questions

Easy What is the difference between for...in and for...of?

Answer: for...in iterates over enumerable property names/keys (works on objects, gives string indices for arrays, includes inherited properties). for...of iterates over values of iterables (arrays, strings, Maps, Sets — NOT plain objects). Use for...in for objects, for...of for arrays.

Medium Why should you avoid for...in with arrays?

Answer: (1) Gives string indices ("0","1","2") not numbers, (2) iterates prototype chain properties, (3) order not historically guaranteed, (4) iterates all enumerable properties including custom ones added to Array.prototype. Use for...of, forEach, or classic for with arrays.

Theory

try / catch / finally

try {
  // Code that might throw
  let result = riskyOperation();
  console.log(result);
} catch (error) {
  // Handles the error
  console.error("Error:", error.message);
  console.error("Stack:", error.stack);
} finally {
  // ALWAYS executes (even if return/throw in try/catch)
  cleanup();
}

// finally runs even with return!
function test() {
  try {
    return "try";
  } finally {
    console.log("finally runs!"); // This executes!
    // If finally has return, it overrides try's return
  }
}
test(); // logs "finally runs!", returns "try"

Error Types

// Built-in Error types:
new Error("generic error");
new SyntaxError("invalid syntax");     // JSON.parse("{bad}")
new ReferenceError("x is not defined");// accessing undeclared var
new TypeError("x is not a function");  // wrong type operation
new RangeError("Maximum call stack");  // stack overflow, invalid array length
new URIError("URI malformed");         // decodeURI("%")
new EvalError("eval error");           // rarely used now
new AggregateError([err1, err2]);      // Promise.any (ES2021)

// Error properties:
try {
  null.property;
} catch (e) {
  console.log(e.name);       // "TypeError"
  console.log(e.message);    // "Cannot read properties of null"
  console.log(e.stack);      // full stack trace string
  console.log(e.cause);      // ES2022: chained error cause
}

Custom Errors

class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

class HttpError extends Error {
  constructor(statusCode, message) {
    super(message);
    this.name = "HttpError";
    this.statusCode = statusCode;
  }
}

// Usage
function validateAge(age) {
  if (typeof age !== "number") {
    throw new ValidationError("Age must be a number", "age");
  }
  if (age < 0 || age > 150) {
    throw new RangeError("Age must be between 0-150");
  }
}

try {
  validateAge("twenty");
} catch (e) {
  if (e instanceof ValidationError) {
    console.log(`Validation failed for ${e.field}: ${e.message}`);
  } else if (e instanceof RangeError) {
    console.log(`Range error: ${e.message}`);
  } else {
    throw e; // Re-throw unexpected errors
  }
}

// Error Cause (ES2022)
try {
  try {
    JSON.parse("{invalid}");
  } catch (parseError) {
    throw new Error("Config failed to load", { cause: parseError });
  }
} catch (e) {
  console.log(e.message);       // "Config failed to load"
  console.log(e.cause.message); // "Expected property name..."
}

Error Handling Patterns

// Pattern 1: Re-throwing
try {
  doSomething();
} catch (e) {
  if (e instanceof TypeError) {
    handleTypeError(e);
  } else {
    throw e; // Don't swallow unknown errors!
  }
}

// Pattern 2: Optional catch binding (ES2019)
try {
  JSON.parse(data);
} catch { // No (error) needed if you don't use it
  return defaultValue;
}

// Pattern 3: Async error handling
async function fetchData() {
  try {
    const response = await fetch(url);
    if (!response.ok) {
      throw new HttpError(response.status, `HTTP ${response.status}`);
    }
    return await response.json();
  } catch (error) {
    if (error instanceof HttpError && error.statusCode === 404) {
      return null; // Handle 404 gracefully
    }
    throw error; // Re-throw others
  }
}

// Pattern 4: Global error handlers
window.onerror = function(msg, src, line, col, error) {
  // Catches uncaught errors
  logToService({ msg, src, line, col, stack: error?.stack });
};
window.addEventListener("unhandledrejection", (event) => {
  // Catches unhandled Promise rejections
  logToService({ reason: event.reason });
});

10. Strict Mode

📺 YouTube Tutorials
  • Strict Mode Explained — Web Dev Simplified
  • JavaScript Strict Mode — Dcode

Theory

What is Strict Mode?

Strict mode (ES5) opts into a restricted variant of JavaScript that eliminates silent errors, fixes mistakes that make optimization difficult, and prohibits syntax likely to be defined in future ECMAScript.

// Enable for entire script
"use strict";

// Or for a single function
function strictFunc() {
  "use strict";
  // strict rules apply only here
}

// ES6 modules and classes are ALWAYS in strict mode automatically!

What Strict Mode Changes

"use strict";

// 1. Cannot use undeclared variables
x = 10; // ReferenceError: x is not defined (without strict: creates global!)

// 2. Cannot delete variables, functions, or undeletable properties
let y = 5;
delete y; // SyntaxError

// 3. Cannot duplicate parameter names
function sum(a, a, c) {} // SyntaxError: Duplicate parameter

// 4. Octal literals not allowed
let oct = 010; // SyntaxError (use 0o10 for octal)

// 5. Cannot write to read-only properties
let obj = {};
Object.defineProperty(obj, "x", { value: 42, writable: false });
obj.x = 9; // TypeError (without strict: fails silently)

// 6. Cannot add properties to non-extensible objects
let frozen = Object.freeze({ a: 1 });
frozen.b = 2; // TypeError

// 7. 'this' in functions is undefined (not window)
function getThis() {
  return this; // undefined (without strict: window)
}

// 8. Cannot use 'with' statement
with (Math) {} // SyntaxError

// 9. eval doesn't introduce variables into surrounding scope
eval("var z = 10");
console.log(z); // ReferenceError (without strict: z is accessible)

// 10. Reserved words cannot be used as variable names
let implements, interface, package; // SyntaxError
let private, protected, public;     // SyntaxError
let static, yield;                  // SyntaxError
Angular Note: TypeScript compiles with strict mode by default. All Angular code runs in strict mode since it uses ES modules. You rarely need to add "use strict" manually in modern Angular projects.

🎯 Interview Questions

Easy What is strict mode and why use it?

Answer: "use strict" enables a stricter parsing/error handling mode: turns silent errors into thrown errors, prevents accidental globals, disables confusing features (with, octal), makes eval safer, and sets 'this' to undefined in plain functions. Use it to write safer, more optimizable code.

Medium What is the value of 'this' inside a function in strict mode vs non-strict?

Answer: In strict mode: this is undefined in a regular function call. In non-strict: this is the global object (window/global). This prevents accidental modification of global state. Arrow functions inherit this from enclosing scope regardless of strict mode.
