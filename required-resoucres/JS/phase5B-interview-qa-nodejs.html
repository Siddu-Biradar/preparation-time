1. Interview Q&A: Timers

🎯 setTimeout & setInterval Questions

Easy Is setTimeout(fn, 0) truly immediate?

Answer: No. It means "schedule after current sync code + microtasks finish, with a minimum delay of ~4ms" (browsers clamp nested timeouts to 4ms after 5 levels). The 0 means "as soon as possible" not "immediately". It's still a macrotask — all microtasks run first.

Medium What's the difference between nested setTimeout and setInterval?

Answer: setInterval fires at fixed intervals regardless of how long the callback takes — if callback takes longer than interval, executions pile up. Nested setTimeout guarantees the delay is measured FROM when the previous callback finishes, preventing overlap. Nested setTimeout is always safer for non-trivial work.

// setInterval problem: if task takes 300ms and interval is 200ms,
// callbacks overlap and queue up

// Safer: nested setTimeout
function poll() {
  doExpensiveWork().then(() => {
    setTimeout(poll, 200); // 200ms AFTER work finishes
  });
}
setTimeout(poll, 200);

Hard How do background tabs affect timers?

Answer: Browsers throttle timers in background tabs: (1) setInterval/setTimeout are clamped to minimum 1000ms in Chrome background tabs. (2) requestAnimationFrame is completely paused — it only fires when the tab is visible. (3) This is why you should use document.visibilitychange event to pause/resume logic rather than relying on timer accuracy.

Medium When would you use requestAnimationFrame over setTimeout?

Answer: rAF for any visual updates (animations, DOM manipulation) because: (1) It syncs with the browser's paint cycle (60fps = 16.7ms), (2) It automatically pauses when tab is hidden (saves battery), (3) It batches DOM reads/writes preventing forced reflows, (4) Browser can optimize multiple rAF callbacks together. Use setTimeout for non-visual delays (API polling, debounce).

Expert Implement setInterval using only setTimeout.

function mySetInterval(fn, delay) {
  let cancelled = false;
  
  function tick() {
    if (cancelled) return;
    fn();
    setTimeout(tick, delay);
  }
  
  setTimeout(tick, delay);
  
  // Return cancel function
  return { clear() { cancelled = true; } };
}

// With drift correction (bonus):
function preciseInterval(fn, delay) {
  let expected = Date.now() + delay;
  let cancelled = false;
  
  function tick() {
    if (cancelled) return;
    fn();
    const drift = Date.now() - expected;
    expected += delay;
    setTimeout(tick, Math.max(0, delay - drift));
  }
  
  setTimeout(tick, delay);
  return { clear() { cancelled = true; } };
}

2. Interview Q&A: Callbacks

🎯 Callback Questions

Easy What is a callback function?

Answer: A function passed as an argument to another function, to be called (called back) at a later time — either synchronously (Array.map, forEach) or asynchronously (setTimeout, event listeners, fs.readFile). It's the simplest form of async control flow in JavaScript.

Medium What is "Callback Hell" and what's the REAL problem?

Answer: Callback Hell (Pyramid of Doom) looks like deeply nested callbacks. But nesting isn't the core issue — you can flatten callbacks with named functions. The REAL problems are: (1) Inversion of Control — you give your callback to a 3rd party and trust they'll call it correctly (once, with right args, not too early/late). (2) No standardized error handling — each callback must manually check `if (err)`. (3) Difficult composition — running parallel tasks or sequential chains is verbose and error-prone.

Hard What is "Inversion of Control" and how do Promises solve it?

Answer: With callbacks, you hand your continuation (next step) to someone else's code. You can't guarantee: (a) callback is called exactly once, (b) called with correct arguments, (c) errors are properly reported. Promises invert this back: instead of passing your callback IN, you get a promise OUT. You control when/how to react via .then(). Promises guarantee: single resolution, immutable once settled, always async (via microtask), and built-in error propagation.

3. Interview Q&A: Promise Static Methods

🎯 Promise.all / race / allSettled / any Questions

Medium What happens if one promise in Promise.all rejects?

Answer: Promise.all short-circuits immediately on the first rejection — the returned promise rejects with that error. The remaining promises still execute (can't cancel them), but their results are ignored. Use Promise.allSettled if you need all results regardless of failures.

Medium When would you use Promise.race vs Promise.any?

Answer: Promise.race settles with the first promise to settle (resolve OR reject). Promise.any settles with the first to RESOLVE — it ignores rejections until all fail (then rejects with AggregateError). Use race for timeouts (race between fetch and a timeout promise). Use any for redundancy (try multiple mirrors, take the fastest success).

// Timeout pattern with race:
const result = await Promise.race([
  fetch("/api/data"),
  new Promise((_, reject) => setTimeout(() => reject(new Error("Timeout")), 5000))
]);

// Fastest mirror with any:
const data = await Promise.any([
  fetch("https://cdn1.example.com/data"),
  fetch("https://cdn2.example.com/data"),
  fetch("https://cdn3.example.com/data"),
]);

Hard Implement Promise.allSettled from scratch.

function allSettled(promises) {
  return Promise.all(
    promises.map((p) =>
      Promise.resolve(p).then(
        (value) => ({ status: "fulfilled", value }),
        (reason) => ({ status: "rejected", reason })
      )
    )
  );
}
// Key insight: wrap each promise so it ALWAYS resolves (never rejects)
// Then Promise.all will never short-circuit

Expert What is Promise.withResolvers() and when is it useful?

Answer: Promise.withResolvers() (ES2024) returns { promise, resolve, reject } — extracting the resolve/reject handles outside the executor. Useful when the resolution logic lives in a different scope (event handlers, callback APIs, class methods). Without it, you'd use the "deferred pattern": declare let resolve/reject outside new Promise().

// Before (deferred pattern):
let resolve, reject;
const promise = new Promise((res, rej) => { resolve = res; reject = rej; });

// After (ES2024):
const { promise, resolve, reject } = Promise.withResolvers();
// Use resolve/reject anywhere!

4. Interview Q&A: async/await

🎯 async/await Questions

Easy What does async do to a function?

Answer: It makes the function always return a Promise. If you return a non-Promise value, it's wrapped in Promise.resolve(). If you throw, the returned promise rejects. It also enables using await inside the function.

Medium Does await block the main thread?

Answer: No! await only pauses the async FUNCTION, not the main thread. When execution hits await, the function suspends and returns its promise to the caller. The event loop continues processing other tasks. When the awaited value resolves, the function resumes from where it paused (scheduled as a microtask). This is why "script end" prints before "after await".

Hard What's the difference between these three?

// 1. Sequential (SLOW — each waits for previous)
const a = await fetchA();
const b = await fetchB();
const c = await fetchC();

// 2. Parallel (FAST — all start immediately)
const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);

// 3. Fire-and-forget-then-await (FAST — same as #2 but different style)
const pA = fetchA(); // Start immediately
const pB = fetchB(); // Start immediately
const pC = fetchC(); // Start immediately
const a = await pA;
const b = await pB;
const c = await pC;

Answer: #1 is sequential: total time = A + B + C. #2 and #3 are parallel: total time = max(A, B, C). In #3, all fetches start before any await — the awaits just collect results. #2 (Promise.all) is preferred because if one fails, you fail fast. In #3, if pB rejects while you're awaiting pA, the rejection might go unhandled momentarily.

Hard Why should you always use "return await" inside try/catch?

// BUG: catch doesn't fire!
async function bad() {
  try {
    return fetchData(); // Returns promise WITHOUT awaiting
  } catch (e) {
    console.log("never reached"); // rejection escapes!
  }
}

// CORRECT: catch fires on rejection
async function good() {
  try {
    return await fetchData(); // Awaits → rejection caught here
  } catch (e) {
    console.log("caught:", e); // ✓
  }
}

Answer: Without await, `return promise` immediately returns the promise without unwrapping it — the try/catch never sees the rejection. With `return await`, the promise is unwrapped, the rejection becomes a thrown error caught by the try block. ESLint rule: no-return-await is wrong in try/catch contexts!

Expert How does await work with non-Promise values (thenables)?

Answer: await calls Promise.resolve(value) internally. If the value has a .then() method (is "thenable"), Promise.resolve unwraps it by calling .then(). This means await works with any thenable — custom promise libraries, jQuery deferreds, etc. If the value is a plain value, it's wrapped in a resolved promise and the function resumes on the next microtask.

5. Interview Q&A: Concurrency Patterns

🎯 Concurrency Questions

Medium How do you limit concurrent API requests (e.g., process 100 URLs with max 5 at a time)?

Answer: Use a Promise Pool / concurrency limiter. Maintain a counter of active requests. When a request finishes, start the next one from the queue. Libraries: p-limit, p-queue. Custom: maintain an array of active promises, use Promise.race to detect when one finishes, then add the next.

async function pool(tasks, concurrency) {
  const results = [];
  const executing = new Set();

  for (const [i, task] of tasks.entries()) {
    const p = task().then((val) => { executing.delete(p); return val; });
    executing.add(p);
    results[i] = p;

    if (executing.size >= concurrency) {
      await Promise.race(executing); // Wait for one to finish
    }
  }

  return Promise.all(results);
}

Hard Implement a mutex/lock for async operations.

Answer: A mutex ensures only one async operation accesses a resource at a time. Use a queue of resolve functions:

class Mutex {
  #locked = false;
  #queue = [];

  async acquire() {
    if (!this.#locked) {
      this.#locked = true;
      return;
    }
    await new Promise((resolve) => this.#queue.push(resolve));
  }

  release() {
    if (this.#queue.length > 0) {
      this.#queue.shift()(); // Unblock next waiter
    } else {
      this.#locked = false;
    }
  }

  async runExclusive(fn) {
    await this.acquire();
    try { return await fn(); }
    finally { this.release(); }
  }
}

const dbMutex = new Mutex();
await dbMutex.runExclusive(async () => {
  // Only one operation at a time here
  await db.read();
  await db.write();
});

Expert Implement a "stale-while-revalidate" cache strategy.

function swr(fetchFn, { ttl = 5000, staleWhileRevalidate = 30000 } = {}) {
  let cache = { value: null, timestamp: 0 };

  return async function (...args) {
    const age = Date.now() - cache.timestamp;

    if (age < ttl) {
      return cache.value; // Fresh — return immediately
    }

    if (age < staleWhileRevalidate && cache.value !== null) {
      // Stale but usable — return stale, revalidate in background
      fetchFn(...args).then((val) => {
        cache = { value: val, timestamp: Date.now() };
      });
      return cache.value;
    }

    // Expired — must wait for fresh data
    const value = await fetchFn(...args);
    cache = { value, timestamp: Date.now() };
    return value;
  };
}

6. Node.js Event Loop (Phases & Differences)

Why this matters: Full-stack interviews often ask "How does Node.js event loop differ from the browser?" — knowing the 6 phases is a strong differentiator.

Node.js Event Loop Phases (in order)

┌───────────────────────────┐
│         timers            │ ← setTimeout, setInterval callbacks
├───────────────────────────┤
│     pending callbacks     │ ← I/O callbacks deferred from previous cycle
├───────────────────────────┤
│       idle, prepare       │ ← internal use only
├───────────────────────────┤
│          poll             │ ← retrieve new I/O events; execute I/O callbacks
├───────────────────────────┤
│         check             │ ← setImmediate() callbacks
├───────────────────────────┤
│     close callbacks       │ ← socket.on('close'), etc.
└───────────────────────────┘

Between EVERY phase: process ALL microtasks (Promise.then, process.nextTick)

Key Differences from Browser

FeatureBrowserNode.js
Microtask processingAfter each macrotaskBetween every phase + after each callback within a phase (since Node 11)
process.nextTickN/AHigher priority than Promise.then! Runs before any other microtask
setImmediateN/A (non-standard)Fires in "check" phase, after I/O
requestAnimationFrameBefore repaintN/A (no rendering)
MessageChannelMacrotaskAvailable but rarely used

process.nextTick vs setImmediate vs Promise.then

// Priority order in Node.js:
// 1. process.nextTick (highest — drains completely before promises!)
// 2. Promise.then / queueMicrotask
// 3. setImmediate (check phase)
// 4. setTimeout(fn, 0) (timer phase — minimum 1ms in Node)

process.nextTick(() => console.log("1 - nextTick"));
Promise.resolve().then(() => console.log("2 - promise"));
setImmediate(() => console.log("3 - immediate"));
setTimeout(() => console.log("4 - timeout"), 0);

// Output (usually): 1 - nextTick, 2 - promise, 4 - timeout, 3 - immediate
// (timeout vs immediate order is non-deterministic at top level!)

// BUT inside an I/O callback, setImmediate ALWAYS fires before setTimeout:
const fs = require("fs");
fs.readFile(__filename, () => {
  setImmediate(() => console.log("immediate"));  // Always first
  setTimeout(() => console.log("timeout"), 0);   // Always second
});

The "Starvation" Risk with nextTick

// DANGER: nextTick recursion blocks EVERYTHING (I/O, timers, everything!)
function runForever() {
  process.nextTick(runForever); // Never yields to other phases
}
// This is worse than while(true) for the event loop!
// Use setImmediate for recursive async work instead.

// SAFE: setImmediate gives other phases a chance
function safePoll() {
  setImmediate(() => {
    doWork();
    safePoll(); // Yields between iterations
  });
}

🎯 Interview Questions

Medium What's the order: setTimeout(0) vs setImmediate in Node.js?

Answer: At the top level, the order is non-deterministic (depends on process performance and when the loop starts). Inside an I/O callback, setImmediate always fires first (because after I/O, the "check" phase runs before looping back to "timers"). This is a classic Node.js trick question.

Hard Why is process.nextTick dangerous?

Answer: nextTick callbacks drain completely (recursively) before the event loop continues to the next phase. This means recursive nextTick calls can starve I/O, timers, and everything else — the system becomes unresponsive. Promise.then is safer because it's also a microtask but has lower priority. Use setImmediate for recursive patterns.

7. Race Conditions & How to Prevent Them

Real-World Impact: Race conditions are the #1 source of bugs in async frontend code. They're subtle, hard to reproduce, and interviewers love asking about them.

What is a Race Condition?

A race condition occurs when the behavior of your code depends on the timing/ordering of async operations, which isn't guaranteed. The result changes depending on which operation finishes first.

Pattern 1: Stale Response Overwriting Fresh Data

// BUG: User types "ab" then "abc"
// Request for "ab" takes 500ms, request for "abc" takes 100ms
// "abc" response arrives first (correct), then "ab" response overwrites it!

// Broken:
async function search(query) {
  const results = await fetch(`/api/search?q=${query}`).then(r => r.json());
  renderResults(results); // "ab" results overwrite "abc" results!
}

// FIX 1: Track request order with a counter
let latestRequestId = 0;

async function search(query) {
  const requestId = ++latestRequestId;
  const results = await fetch(`/api/search?q=${query}`).then(r => r.json());
  if (requestId !== latestRequestId) return; // Stale — discard
  renderResults(results);
}

// FIX 2: AbortController (cancel previous request)
let controller = null;

async function search(query) {
  controller?.abort(); // Cancel previous
  controller = new AbortController();
  try {
    const results = await fetch(`/api/search?q=${query}`, {
      signal: controller.signal
    }).then(r => r.json());
    renderResults(results);
  } catch (e) {
    if (e.name !== "AbortError") throw e; // Ignore abort, rethrow others
  }
}

Pattern 2: Stale Closure (React/Angular trap)

// BUG: Classic React stale closure
function SearchComponent() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);

  useEffect(() => {
    // query is captured at the time useEffect runs
    fetch(`/api/search?q=${query}`)
      .then(r => r.json())
      .then(data => setResults(data)); // May set stale results!
  }, [query]);

  // FIX: Use AbortController cleanup
  useEffect(() => {
    const controller = new AbortController();
    fetch(`/api/search?q=${query}`, { signal: controller.signal })
      .then(r => r.json())
      .then(data => setResults(data))
      .catch(e => { if (e.name !== "AbortError") throw e; });

    return () => controller.abort(); // Cleanup cancels stale request
  }, [query]);
}

Pattern 3: Double-Submit / Duplicate Actions

// BUG: User double-clicks "Submit Order" — two orders created!

// FIX: Disable during processing + deduplicate
class SubmitGuard {
  #pending = false;

  async submit(fn) {
    if (this.#pending) return; // Already in-flight
    this.#pending = true;
    try {
      return await fn();
    } finally {
      this.#pending = false;
    }
  }
}

const guard = new SubmitGuard();
submitBtn.addEventListener("click", () => {
  guard.submit(async () => {
    submitBtn.disabled = true;
    await placeOrder();
    submitBtn.disabled = false;
  });
});

Pattern 4: Read-Modify-Write (Concurrent Updates)

// BUG: Two tabs increment a counter simultaneously
// Tab A reads: count = 5
// Tab B reads: count = 5
// Tab A writes: count = 6
// Tab B writes: count = 6  ← Should be 7!

// FIX: Optimistic locking with version number
async function incrementCounter() {
  const { count, version } = await fetch("/api/counter").then(r => r.json());
  
  const response = await fetch("/api/counter", {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ count: count + 1, expectedVersion: version }),
  });
  
  if (response.status === 409) {
    // Conflict! Someone else updated — retry
    return incrementCounter(); // Retry with fresh data
  }
}

// FIX for frontend state: Use the mutex from concurrency section
const stateMutex = new Mutex();

🎯 Interview Questions

Medium How do you prevent stale API responses from overwriting fresh data?

Answer: Three approaches: (1) Request ID counter — increment on each request, ignore responses whose ID doesn't match the latest. (2) AbortController — cancel previous request before starting new one (preferred). (3) Timestamp comparison — only apply response if its request timestamp is newer than the last applied one.

Hard What's a stale closure and how does it cause bugs in React?

Answer: A stale closure captures an old value of a variable (like state). In React useEffect, if you start an async operation that closes over the current state, by the time it resolves the state may have changed — but the closure still has the old value. Fix: use the cleanup function with AbortController, or use useRef for mutable latest value, or use the functional updater form of setState.

Expert How would you implement idempotent operations to prevent double-submits?

Answer: Client-side: disable button + guard flag + debounce. But the real fix is server-side idempotency: (1) Generate a unique idempotency key (UUID) per operation on the client. (2) Send it with the request. (3) Server checks if it's seen this key before — if yes, return the cached response without re-executing. This handles network retries, double-clicks, and browser back/forward safely.

8. Classic Debounce & Throttle (Timer Internals)

Why here? The main Phase 5 file covers async debounce. Machine Coding Part 1 covers the full implementation. This section explains the timer mechanics — how clearTimeout/setTimeout interaction creates debounce behavior.

Debounce: Under the Hood

// "Wait until the user STOPS typing for X ms"
// Every call resets the timer. Only the last call fires.

function debounce(fn, delay, { leading = false, trailing = true } = {}) {
  let timerId = null;
  let lastArgs = null;

  function debounced(...args) {
    lastArgs = args;
    const isFirstCall = timerId === null;

    // Leading edge: fire immediately on first call
    if (leading && isFirstCall) {
      fn.apply(this, args);
    }

    // Clear previous timer (THIS is the debounce mechanism)
    clearTimeout(timerId);

    // Set new timer
    timerId = setTimeout(() => {
      timerId = null; // Reset — next call is "first" again
      if (trailing) {
        fn.apply(this, lastArgs);
      }
    }, delay);
  }

  debounced.cancel = () => { clearTimeout(timerId); timerId = null; };
  debounced.flush = () => { clearTimeout(timerId); fn.apply(null, lastArgs); timerId = null; };
  
  return debounced;
}

// HOW IT WORKS (trace for 300ms debounce):
// t=0ms:   User types "a" → clearTimeout(null), set timer for t=300ms
// t=100ms: User types "b" → clearTimeout(prev), set NEW timer for t=400ms
// t=200ms: User types "c" → clearTimeout(prev), set NEW timer for t=500ms
// t=500ms: Timer fires! → call fn("abc")  ← Only ONE call, with latest value
// KEY: clearTimeout + setTimeout = "restart the wait"

Throttle: Under the Hood

// "Fire at most once every X ms" (rate limiting)
// Unlike debounce, throttle GUARANTEES periodic calls during sustained input

function throttle(fn, limit, { leading = true, trailing = true } = {}) {
  let timerId = null;
  let lastArgs = null;
  let lastCallTime = 0;

  function throttled(...args) {
    const now = Date.now();
    const timeSinceLastCall = now - lastCallTime;
    lastArgs = args;

    if (!lastCallTime && !leading) {
      lastCallTime = now; // Skip leading call
    }

    if (timeSinceLastCall >= limit) {
      // Enough time passed — fire immediately
      lastCallTime = now;
      fn.apply(this, args);
    } else if (!timerId && trailing) {
      // Schedule trailing call for remaining time
      timerId = setTimeout(() => {
        lastCallTime = leading ? Date.now() : 0;
        timerId = null;
        fn.apply(this, lastArgs);
      }, limit - timeSinceLastCall);
    }
  }

  throttled.cancel = () => { clearTimeout(timerId); timerId = null; lastCallTime = 0; };
  return throttled;
}

// HOW IT WORKS (trace for 200ms throttle, scroll event fires every 16ms):
// t=0ms:   scroll → fire immediately (leading), lastCallTime=0
// t=16ms:  scroll → 16 < 200, schedule trailing for t=200
// t=32ms:  scroll → 32 < 200, already scheduled, skip
// ...
// t=200ms: timer fires → call fn (trailing), reset
// t=216ms: scroll → fire immediately (200ms passed since last)
// RESULT: fn fires every ~200ms during continuous scroll (not every 16ms!)

9. requestIdleCallback & Web Workers

requestIdleCallback — Non-Urgent Background Work

// requestIdleCallback runs tasks when the browser is IDLE
// (no animations, no user input, no layout work pending)

// Use case: analytics, prefetching, non-critical DOM updates
function sendAnalytics(events) {
  // Don't block main thread with analytics!
  requestIdleCallback((deadline) => {
    // deadline.timeRemaining() tells you how much time you have (usually 0-50ms)
    while (events.length > 0 && deadline.timeRemaining() > 5) {
      const event = events.shift();
      navigator.sendBeacon("/analytics", JSON.stringify(event));
    }

    // If there's more work, schedule for next idle period
    if (events.length > 0) {
      requestIdleCallback(() => sendAnalytics(events));
    }
  }, { timeout: 5000 }); // Force execution after 5s even if never idle
}

// Priority comparison:
// 1. User input / animation (rAF) — HIGHEST
// 2. Microtasks (Promise.then)
// 3. Macrotasks (setTimeout)
// 4. requestIdleCallback — LOWEST (only when nothing else to do)

// CAVEAT: Don't mutate DOM in rIC! It might trigger forced reflows.
// Instead, batch DOM changes with requestAnimationFrame:
requestIdleCallback(() => {
  const data = computeExpensiveLayout(); // OK here
  requestAnimationFrame(() => {
    applyToDOM(data); // DOM mutation in rAF
  });
});

🎯 Interview Questions

Medium When would you use requestIdleCallback vs requestAnimationFrame?

Answer: rAF for visual updates (runs before every paint at 60fps). rIC for non-urgent work (runs only when the browser is idle). Never do DOM mutations in rIC — compute in rIC, apply in rAF. rIC has a timeout option to guarantee eventual execution.

Hard What's the difference between Web Workers and Service Workers?

Answer: Web Workers: dedicated background threads for CPU work, live as long as the page is open, one-to-one with a page. Service Workers: proxy between browser and network, persist across page sessions, intercept fetch requests for caching/offline support, used for PWAs and push notifications. Both run off the main thread, neither can access DOM.
