V8 Compilation Pipeline

/*
 * V8 COMPILATION PIPELINE (2024+):
 * 
 * Source Code → Parser → AST → Ignition (Bytecode Interpreter)
 *                                    ↓
 *                              Type Feedback (IC)
 *                                    ↓
 *                         Turbofan (Optimizing JIT Compiler)
 *                                    ↓
 *                         Optimized Machine Code
 *                                    ↓
 *                     [Deoptimization if assumptions fail]
 *                                    ↓
 *                         Back to Bytecode (Ignition)
 * 
 * KEY CONCEPTS:
 * - Ignition: Interprets bytecode. Fast startup, slower execution.
 * - TurboFan: JIT compiles "hot" functions. Slow compile, FAST execution.
 * - Inline Caches (IC): Record type info at call sites for optimization.
 * - Hidden Classes (Maps): V8's internal type system for fast property access.
 * - Deoptimization: Bail out of optimized code when assumptions break.
 */

Hidden Classes (Shapes/Maps) — Critical for Performance

// ═══ HIDDEN CLASS OPTIMIZATION ═══
// V8 creates internal "Hidden Classes" (called Maps) for objects.
// Objects with the same property names in the same order share a Hidden Class.
// This enables FAST property access (like C++ structs).

// GOOD: Same shape — V8 optimizes with shared Hidden Class
function createPoint(x, y) {
  const point = {};
  point.x = x;  // Transition: HC0 → HC1
  point.y = y;  // Transition: HC1 → HC2
  return point;
}
const p1 = createPoint(1, 2); // HC2
const p2 = createPoint(3, 4); // Same HC2! V8 reuses optimized code.

// BAD: Different property order → DIFFERENT hidden classes
const a = {}; a.x = 1; a.y = 2; // HC: {x, y}
const b = {}; b.y = 2; b.x = 1; // HC: {y, x} ← DIFFERENT!
// V8 can't reuse optimized code between a and b.

// BAD: Adding properties dynamically AFTER creation
function createUser(name) {
  const user = { name };
  if (name === "admin") {
    user.role = "admin";    // Only some objects get this → POLYMORPHIC
  }
  return user;
}
// Some users have HC{name}, others have HC{name, role}
// V8 can't optimize access patterns well.

// GOOD: Always initialize ALL properties (even to undefined)
function createUserOptimized(name, role) {
  return { name, role: role || null }; // ALWAYS same shape!
}

// ═══ INTERVIEW TIP: Monomorphic vs Polymorphic vs Megamorphic ═══
// Monomorphic (1 shape): FASTEST — V8 generates specialized code
// Polymorphic (2-4 shapes): Slower — V8 checks a few shapes
// Megamorphic (5+ shapes): SLOWEST — V8 falls back to generic lookup

function getX(obj) { return obj.x; }

// Monomorphic: all calls with same shape
getX({ x: 1, y: 2 });
getX({ x: 3, y: 4 });
getX({ x: 5, y: 6 }); // All same HC → FAST

// Megamorphic: many different shapes
getX({ x: 1 });
getX({ x: 1, y: 2 });
getX({ x: 1, y: 2, z: 3 });
getX({ x: 1, a: 2 });
getX({ x: 1, b: 2 });
getX({ x: 1, c: 2 }); // 6 different HCs → SLOW generic lookup

Inline Caches (ICs) and Optimization

// V8 records type info at each property access site (Inline Cache)
// If the IC sees the same type repeatedly → optimizes to direct offset access

// FAST: Consistent types
function sum(arr) {
  let total = 0;
  for (let i = 0; i < arr.length; i++) {
    total += arr[i]; // IC: always sees Number → optimized to machine add
  }
  return total;
}
sum([1, 2, 3, 4, 5]); // All integers → V8 uses Smi (Small Integer) path

// SLOW: Type changes (causes deoptimization!)
function sumBad(arr) {
  let total = 0;
  for (let i = 0; i < arr.length; i++) {
    total += arr[i]; // IC: sees Number... then String! → DEOPT!
  }
  return total;
}
sumBad([1, 2, "3", 4]); // Mixing types causes bailout from optimized code

// ═══ V8 NUMBER REPRESENTATIONS ═══
// Smi (Small Integer): 31-bit integers stored directly in pointer. FASTEST.
// HeapNumber: All other numbers (doubles, > 2^30). Heap allocated. Slower.

const fast = 42;         // Smi — no allocation!
const slow = 42.5;      // HeapNumber — heap allocated
const overflow = 2**31;  // HeapNumber — too large for Smi

// TIP: Prefer integer operations where possible for hot loops
// Use | 0 to force integer:  (a + b) | 0

// ═══ ARRAY STORAGE MODES ═══
// V8 internal array types (from fastest to slowest):
// 1. PACKED_SMI_ELEMENTS     — dense, all small integers [1,2,3]
// 2. PACKED_DOUBLE_ELEMENTS  — dense, all doubles [1.1, 2.2]
// 3. PACKED_ELEMENTS         — dense, mixed types [1, "a", {}]
// 4. HOLEY_SMI_ELEMENTS      — sparse integers [1,,3]
// 5. HOLEY_DOUBLE_ELEMENTS   — sparse doubles [1.1,,3.3]
// 6. HOLEY_ELEMENTS          — sparse mixed [1,,"a"]
// 7. DICTIONARY_ELEMENTS     — hash table (very large sparse arrays)

// IMPORTANT: V8 NEVER transitions from a more generic to a more specific type!
const arr1 = [1, 2, 3];      // PACKED_SMI_ELEMENTS (fastest)
arr1.push(4.5);              // → PACKED_DOUBLE_ELEMENTS (can't go back!)
arr1.push("hello");          // → PACKED_ELEMENTS (can't go back!)

// AVOID creating holes:
const arr2 = [1, 2, 3];
delete arr2[1];              // → HOLEY_ELEMENTS (permanent downgrade!)

// PREFER: Pre-allocate and fill
const arr3 = new Array(1000);  // HOLEY — already degraded!
const arr4 = Array.from({ length: 1000 }, () => 0); // PACKED_SMI — good!

🎯 Interview Questions on V8 Internals

  • Q: What are Hidden Classes and why do they matter?
    A: V8 creates internal type descriptors (Maps) for objects. Same-shaped objects share a Map → enables fast property access via fixed offsets (like struct access in C). Different shapes = different Maps = slower generic access.
  • Q: What causes deoptimization?
    A: Type changes (number→string), changing object shape after creation, using arguments object in certain ways, using `delete`, using `with`, try-catch in hot functions (legacy).
  • Q: How does V8 handle arrays?
    A: Different internal representations. Dense integer arrays (PACKED_SMI) are like C arrays. Adding non-integers or creating holes permanently downgrades performance. Never use `delete` on arrays; use splice.

Generational Garbage Collection

/*
 * V8 HEAP STRUCTURE:
 * 
 * ┌────────────────────────────────────────────────────┐
 * │ NEW SPACE (Young Generation) — ~1-8 MB             │
 * │ ┌──────────────┐  ┌──────────────┐                 │
 * │ │  Semi-space  │  │  Semi-space  │                 │
 * │ │  (From)      │  │  (To)        │                 │
 * │ └──────────────┘  └──────────────┘                 │
 * │ • Scavenger (Minor GC) — FAST (~1-5ms)             │
 * │ • Objects that survive 2 GCs → promoted to Old     │
 * ├────────────────────────────────────────────────────┤
 * │ OLD SPACE (Old Generation) — ~hundreds of MB       │
 * │ • Mark-Sweep-Compact (Major GC) — SLOWER           │
 * │ • Incremental Marking (reduces pause)              │
 * │ • Concurrent Marking (off main thread)             │
 * │ • Lazy Sweeping                                    │
 * ├────────────────────────────────────────────────────┤
 * │ LARGE OBJECT SPACE — objects > 512KB               │
 * │ CODE SPACE — compiled JIT code                     │
 * │ MAP SPACE — Hidden Classes (Maps)                  │
 * └────────────────────────────────────────────────────┘
 */

// ═══ GENERATIONAL HYPOTHESIS ═══
// "Most objects die young" — so V8 optimizes for short-lived objects.
// - New Space: small, collected VERY frequently (Scavenger)
// - Old Space: large, collected LESS frequently (Mark-Sweep-Compact)

// SHORT-LIVED (stays in New Space, collected fast):
function processData(items) {
  const temp = items.map(x => x * 2); // temp array dies after function returns
  return temp.reduce((a, b) => a + b);
}
// 'temp' is allocated in New Space, collected by Scavenger on next minor GC

// LONG-LIVED (promoted to Old Space):
const cache = new Map(); // Lives forever → promoted to Old Space
function addToCache(key, value) {
  cache.set(key, value); // Each entry stays in Old Space
}

GC Algorithms Deep Dive

/*
 * 1. SCAVENGER (Minor GC) — Young Generation
 *    - Cheney's algorithm (semi-space copying)
 *    - Copies LIVE objects from "From-space" to "To-space"
 *    - Dead objects are simply abandoned (no sweep needed!)
 *    - After copy, swap From↔To
 *    - Objects surviving 2 scavenges → promoted to Old Space
 *    - Pause: ~1-5ms (very fast, runs frequently)
 * 
 * 2. MARK-SWEEP-COMPACT (Major GC) — Old Generation
 *    Step 1: MARK — Traverse from roots, mark all reachable objects
 *    Step 2: SWEEP — Reclaim memory of unmarked objects
 *    Step 3: COMPACT — Move objects to eliminate fragmentation
 *    - Pause: ~50-200ms (optimized with concurrent/incremental)
 * 
 * 3. INCREMENTAL MARKING
 *    - Instead of marking all at once (stop-the-world),
 *      mark in small chunks between JS execution
 *    - Write barrier: track objects modified during incremental mark
 * 
 * 4. CONCURRENT GC (V8 modern)
 *    - Marking and sweeping happen on BACKGROUND THREADS
 *    - Main thread only pauses briefly for "atomic" operations
 *    - Reduces pause times to ~1-5ms even for Major GC
 */

// ═══ GC ROOTS (Starting points for mark phase) ═══
// 1. Global objects (window, global)
// 2. Currently executing function's local variables (call stack)
// 3. Active closures referencing objects
// 4. Registered event listeners
// 5. Active timers (setTimeout/setInterval callbacks)

// ═══ WHEN DOES GC RUN? ═══
// - V8 uses allocation-based triggers
// - Minor GC: when New Space fills up (~1-8MB)
// - Major GC: when Old Space grows significantly
// - Idle-time GC: during browser idle periods (requestIdleCallback)
// - You CANNOT control GC timing from JavaScript (non-deterministic)

Memory-Efficient Coding Patterns

// ═══ OBJECT POOLING (avoid GC pressure) ═══
class ObjectPool {
  #pool = [];
  #factory;
  #reset;
  
  constructor(factory, reset, initialSize = 10) {
    this.#factory = factory;
    this.#reset = reset;
    // Pre-allocate objects
    for (let i = 0; i < initialSize; i++) {
      this.#pool.push(factory());
    }
  }
  
  acquire() {
    return this.#pool.length > 0 ? this.#pool.pop() : this.#factory();
  }
  
  release(obj) {
    this.#reset(obj);
    this.#pool.push(obj);
  }
}

// Usage: particle system (avoids creating/destroying thousands of objects)
const particlePool = new ObjectPool(
  () => ({ x: 0, y: 0, vx: 0, vy: 0, active: false }),
  (p) => { p.x = 0; p.y = 0; p.vx = 0; p.vy = 0; p.active = false; }
);

const particle = particlePool.acquire();
particle.x = 100; particle.y = 200; particle.active = true;
// When done:
particlePool.release(particle);

// ═══ AVOID FREQUENT ALLOCATIONS IN HOT LOOPS ═══
// BAD: Creates new object every iteration
function transformBad(points) {
  return points.map(p => ({ x: p.x * 2, y: p.y * 2 })); // N allocations!
}

// GOOD: Mutate in place (when safe)
function transformGood(points) {
  for (let i = 0; i < points.length; i++) {
    points[i].x *= 2;
    points[i].y *= 2;
  }
  return points;
}

// ═══ USE TypedArrays FOR NUMERIC DATA ═══
// Regular arrays: Each number is a heap-allocated object (HeapNumber)
const slow = [1.1, 2.2, 3.3, /* ... 10000 items */]; // 10K heap allocations

// TypedArray: Contiguous memory, no per-element overhead
const fast = new Float64Array(10000); // Single allocation, C-like performance
fast[0] = 1.1; fast[1] = 2.2;

// ═══ WEAK REFERENCES FOR CACHES ═══
// WeakMap keys don't prevent GC — perfect for caching metadata
const metadata = new WeakMap();

function addMetadata(element, data) {
  metadata.set(element, data);
  // When element is removed from DOM and GC'd,
  // the WeakMap entry is automatically cleaned up!
}

// WeakRef for expensive computed results
class ComputeCache {
  #cache = new Map();
  
  get(key, computeFn) {
    const ref = this.#cache.get(key);
    const cached = ref?.deref();
    
    if (cached !== undefined) return cached;
    
    const result = computeFn();
    this.#cache.set(key, new WeakRef(result));
    return result;
  }
}

5 Common Memory Leak Patterns + Fixes

// ═══ LEAK 1: FORGOTTEN EVENT LISTENERS ═══
// BAD: Listener keeps reference to large closure
class Component {
  #data = new Array(100000).fill("data");
  
  mount() {
    // This listener holds a reference to `this` (and #data)
    // Even after component is "destroyed", the listener keeps it alive!
    window.addEventListener("resize", this.#handleResize);
  }
  
  #handleResize = () => {
    console.log(this.#data.length);
  };
  
  // FIX: Always remove listeners on cleanup
  destroy() {
    window.removeEventListener("resize", this.#handleResize);
  }
}

// ═══ LEAK 2: CLOSURES HOLDING LARGE REFERENCES ═══
// BAD:
function createHandler() {
  const hugeData = new Array(1000000).fill("x");
  
  return function handler() {
    // handler doesn't USE hugeData, but the closure still captures it!
    // (Some engines optimize this away, but not guaranteed)
    console.log("clicked");
  };
}
document.addEventListener("click", createHandler()); // hugeData stuck in memory!

// FIX: Null out references or restructure
function createHandlerFixed() {
  let hugeData = new Array(1000000).fill("x");
  const result = processData(hugeData);
  hugeData = null; // Explicitly release!
  
  return function handler() {
    console.log("result:", result); // Only keeps small 'result'
  };
}

// ═══ LEAK 3: FORGOTTEN TIMERS ═══
// BAD:
class Poller {
  start() {
    this.intervalId = setInterval(() => {
      this.fetchData(); // Holds reference to `this` forever
    }, 5000);
  }
  // If we forget to call stop(), this object is never GC'd!
  stop() { clearInterval(this.intervalId); }
}

// ═══ LEAK 4: DETACHED DOM NODES ═══
// BAD:
let detachedNodes = [];
function addItem() {
  const li = document.createElement("li");
  li.textContent = "item";
  document.getElementById("list").appendChild(li);
  detachedNodes.push(li); // JS keeps reference!
}
function removeAll() {
  document.getElementById("list").innerHTML = "";
  // DOM nodes removed from tree BUT still in detachedNodes array!
  // They can't be GC'd → memory leak!
}
// FIX: detachedNodes = []; or use WeakRef

// ═══ LEAK 5: GROWING MAP/SET WITHOUT CLEANUP ═══
// BAD:
const sessionData = new Map();
function trackUser(userId, data) {
  sessionData.set(userId, data);
  // Map grows forever! Old sessions never cleaned up.
}

// FIX: Use LRU cache with max size, or WeakMap if possible
class BoundedCache {
  #map = new Map();
  #maxSize;
  
  constructor(maxSize = 100) { this.#maxSize = maxSize; }
  
  set(key, value) {
    if (this.#map.size >= this.#maxSize) {
      const oldestKey = this.#map.keys().next().value;
      this.#map.delete(oldestKey);
    }
    this.#map.set(key, value);
  }
  
  get(key) { return this.#map.get(key); }
}

Memory Leak Detection with DevTools

/*
 * CHROME DEVTOOLS MEMORY PROFILING:
 * 
 * 1. HEAP SNAPSHOT (Memory tab → "Take heap snapshot")
 *    - Take snapshot BEFORE action
 *    - Perform the action (e.g., open/close modal)
 *    - Force GC (click trash icon)
 *    - Take snapshot AFTER
 *    - Compare: "Objects allocated between snapshots 1 and 2"
 *    - Look for: Detached HTMLElements, growing arrays/maps
 * 
 * 2. ALLOCATION TIMELINE
 *    - Record while performing actions
 *    - Blue bars = allocated and still alive
 *    - Gray bars = allocated and GC'd (good!)
 *    - Look for blue bars that never turn gray
 * 
 * 3. ALLOCATION SAMPLING
 *    - Lower overhead than timeline
 *    - Shows which functions allocated the most memory
 *    - Good for production profiling
 * 
 * KEY METRICS:
 * - JS Heap Size: total allocated JS memory
 * - Used JS Heap: actual live objects
 * - If "Used" grows over time without stopping → LEAK
 * 
 * PROGRAMMATIC CHECK:
 */
if (performance.memory) {
  console.log("Heap size:", performance.memory.usedJSHeapSize / 1024 / 1024, "MB");
  console.log("Heap limit:", performance.memory.jsHeapSizeLimit / 1024 / 1024, "MB");
}

// Automated leak detection pattern:
function checkForLeaks(action, iterations = 100) {
  const before = performance.memory?.usedJSHeapSize;
  
  for (let i = 0; i < iterations; i++) {
    action();
  }
  
  // Force GC if available (only works with --expose-gc flag)
  if (globalThis.gc) gc();
  
  const after = performance.memory?.usedJSHeapSize;
  const growth = (after - before) / 1024;
  
  if (growth > 100) { // > 100KB growth after GC = potential leak
    console.warn(`Potential memory leak: ${growth.toFixed(0)}KB growth`);
  }
}

Long Tasks & Main Thread Blocking

// THE PROBLEM: JavaScript is single-threaded
// Any computation > 50ms blocks rendering, input, and scrolling
// Users perceive lag at > 100ms, frustration at > 300ms

// ═══ DETECTING LONG TASKS ═══
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) {
      console.warn(`Long Task detected: ${entry.duration.toFixed(0)}ms`, entry);
    }
  }
});
observer.observe({ entryTypes: ["longtask"] });

// ═══ BREAKING UP LONG TASKS ═══

// BAD: Blocks main thread for 500ms
function processLargeArrayBad(items) {
  for (let i = 0; i < items.length; i++) {
    heavyComputation(items[i]); // 500ms total!
  }
}

// GOOD: Yield to browser between chunks using scheduler.yield() (modern)
async function processLargeArrayGood(items) {
  const CHUNK_SIZE = 100;
  
  for (let i = 0; i < items.length; i += CHUNK_SIZE) {
    const chunk = items.slice(i, i + CHUNK_SIZE);
    chunk.forEach(item => heavyComputation(item));
    
    // Yield to browser — allows rendering and input processing
    await scheduler.yield?.() ?? new Promise(r => setTimeout(r, 0));
  }
}

// ALTERNATIVE: requestIdleCallback for non-urgent work
function processInIdle(items) {
  let index = 0;
  
  function processChunk(deadline) {
    // Process items while we have time budget
    while (index < items.length && deadline.timeRemaining() > 1) {
      heavyComputation(items[index]);
      index++;
    }
    
    if (index < items.length) {
      requestIdleCallback(processChunk); // Continue in next idle period
    }
  }
  
  requestIdleCallback(processChunk);
}

// ═══ requestAnimationFrame for visual updates ═══
function animateSmooth() {
  let start = null;
  
  function frame(timestamp) {
    if (!start) start = timestamp;
    const progress = timestamp - start;
    
    // Update visuals — ALWAYS use rAF for animations
    element.style.transform = `translateX(${progress * 0.1}px)`;
    
    if (progress < 2000) {
      requestAnimationFrame(frame);
    }
  }
  
  requestAnimationFrame(frame);
}

// ═══ DEBOUNCE vs THROTTLE vs rAF — When to use which ═══
// Debounce: Wait N ms after LAST event (search input, resize end)
// Throttle: Max once per N ms (scroll tracking, mousemove)
// rAF: Once per frame (~16ms) — visual updates, animations

// Production-grade throttle with trailing call
function throttle(fn, limit) {
  let inThrottle = false;
  let lastArgs = null;
  
  return function(...args) {
    if (!inThrottle) {
      fn.apply(this, args);
      inThrottle = true;
      
      setTimeout(() => {
        inThrottle = false;
        if (lastArgs) {
          fn.apply(this, lastArgs);
          lastArgs = null;
        }
      }, limit);
    } else {
      lastArgs = args; // Save for trailing call
    }
  };
}

📺 YouTube Tutorials

The Browser Rendering Pipeline

/*
 * PIXEL PIPELINE (happens every frame at 60fps = 16.67ms budget):
 * 
 * JavaScript → Style → Layout → Paint → Composite
 * 
 * 1. JAVASCRIPT: Run your code (event handlers, animations, DOM changes)
 * 2. STYLE: Compute which CSS rules apply to which elements
 * 3. LAYOUT: Calculate position and size of every element (EXPENSIVE!)
 * 4. PAINT: Fill pixels for each layer (text, colors, images, shadows)
 * 5. COMPOSITE: Combine layers in correct order (GPU-accelerated, CHEAP)
 * 
 * GOAL: Skip expensive steps whenever possible!
 * - transform/opacity → skip Layout AND Paint (only Composite)
 * - color/background → skip Layout (only Paint + Composite)
 * - width/height/margin/padding → triggers EVERYTHING (full pipeline)
 */

Layout Thrashing (Forced Reflow)

// ═══ LAYOUT THRASHING — THE #1 PERFORMANCE KILLER ═══
// When you READ layout properties, browser must compute layout first.
// If you write THEN read in a loop → forces layout on EVERY iteration!

// BAD: Read-Write-Read-Write (forces layout on each read) — O(n) layouts!
function resizeAllBad(elements) {
  elements.forEach(el => {
    const width = el.offsetWidth;        // READ → forces layout
    el.style.width = (width * 2) + "px"; // WRITE → invalidates layout
    // Next iteration's READ will force layout AGAIN!
  });
}
// With 1000 elements → 1000 forced layouts = ~500ms frame!

// GOOD: Batch reads, then batch writes — O(1) layouts!
function resizeAllGood(elements) {
  // Phase 1: Read all (single layout calculation)
  const widths = elements.map(el => el.offsetWidth);
  
  // Phase 2: Write all (layout calculated once at end)
  elements.forEach((el, i) => {
    el.style.width = (widths[i] * 2) + "px";
  });
}
// Only 1 layout calculation! ~5ms instead of ~500ms!

// ═══ PROPERTIES THAT TRIGGER LAYOUT (avoid reading in loops!) ═══
// element.offsetTop/Left/Width/Height
// element.clientTop/Left/Width/Height
// element.scrollTop/Left/Width/Height
// element.getBoundingClientRect()
// window.getComputedStyle()
// element.focus() (may trigger scroll/layout)
// window.scrollX/Y, innerWidth/Height

// ═══ USE FASTDOM PATTERN ═══
class FastDOM {
  #reads = [];
  #writes = [];
  #scheduled = false;
  
  measure(fn) {
    this.#reads.push(fn);
    this.#schedule();
  }
  
  mutate(fn) {
    this.#writes.push(fn);
    this.#schedule();
  }
  
  #schedule() {
    if (this.#scheduled) return;
    this.#scheduled = true;
    
    requestAnimationFrame(() => {
      // All reads first (single layout)
      this.#reads.forEach(fn => fn());
      this.#reads = [];
      
      // Then all writes (single style recalc)
      this.#writes.forEach(fn => fn());
      this.#writes = [];
      
      this.#scheduled = false;
    });
  }
}

const fastdom = new FastDOM();

// Usage:
fastdom.measure(() => {
  const height = element.offsetHeight;
  fastdom.mutate(() => {
    element.style.height = height * 2 + "px";
  });
});

// ═══ GPU-ACCELERATED PROPERTIES (cheapest to animate) ═══
// ONLY these properties can be composited without layout/paint:
// - transform (translate, rotate, scale, skew)
// - opacity
// - filter (blur, brightness, etc.)
// - will-change (hint to browser to promote to own layer)

// BAD: Animating layout-triggering properties
element.style.left = x + "px";   // Triggers layout + paint + composite
element.style.top = y + "px";    // Every frame!

// Force GPU layer promotion (use sparingly — costs memory):
element.style.willChange = "transform";

// 1. Compile regex ONCE, not in loops
// BAD:
function findMatchesBad(strings) {
  return strings.filter(s => /^[A-Z]/.test(s)); // New regex every call!
}

// GOOD:
const STARTS_WITH_UPPER = /^[A-Z]/; // Compiled once
function findMatchesGood(strings) {
  return strings.filter(s => STARTS_WITH_UPPER.test(s));
}

// BAD regex (exponential backtracking):
const evil = /^(a+)+$/;  // O(2^n) for "aaaaaaaaaaab"

const greedySlow = /<.*>/;      // Backtracks from end
const specificFast = /<[^>]*>/;  // No backtracking

bigString.indexOf("abc") === 0;  // O(n) worst case
/^abc/.test(bigString);          // Regex overhead but still fast for anchored

// includes vs indexOf:

bigString.indexOf("xyz") !== -1; // Same performance, less readable

8. Async Performance Patterns

// ═══ SEQUENTIAL vs PARALLEL EXECUTION ═══

// BAD: Sequential (total time = sum of all requests)
async function fetchAllSequential(urls) {
  const results = [];
  for (const url of urls) {
    const response = await fetch(url); // Waits for each!
    results.push(await response.json());
  }
  return results;
}
// 5 requests × 200ms each = 1000ms total

// GOOD: Parallel (total time = max of all requests)
async function fetchAllParallel(urls) {
  const promises = urls.map(url => fetch(url).then(r => r.json()));
  return Promise.all(promises);
}
// 5 requests in parallel = 200ms total (5x faster!)

// BEST: Parallel with concurrency limit (don't overwhelm server)
async function fetchWithLimit(urls, concurrency = 5) {
  const results = [];
  const executing = new Set();
  
  for (const url of urls) {
    const promise = fetch(url).then(r => r.json()).then(result => {
      executing.delete(promise);
      return result;
    });
    
    executing.add(promise);
    results.push(promise);
    
    if (executing.size >= concurrency) {
      await Promise.race(executing); // Wait for one to finish
    }
  }
  
  return Promise.all(results);
}
// 100 URLs, 5 concurrency → 20 batches × 200ms = 4s (vs 20s sequential!)

  get value() {
    if (!this.#computed) {
      this.#value = this.#factory();
      this.#computed = true;

    return this.#value;
  }
}

  }
}

// Simplified Comlink-like pattern:
function createWorkerProxy(workerUrl) {
  const worker = new Worker(workerUrl);
  let callId = 0;
  const pending = new Map();
  
  worker.onmessage = ({ data }) => {
    const { id, result, error } = data;
    const { resolve, reject } = pending.get(id);
    pending.delete(id);
    error ? reject(error) : resolve(result);
  };
  
  return new Proxy({}, {
    get(_, method) {
      return (...args) => new Promise((resolve, reject) => {
        const id = callId++;
        pending.set(id, { resolve, reject });
        worker.postMessage({ id, method, args });
      });
    }
  });
}

// Usage (feels like calling local functions!):

const result = await mathWorker.fibonacci(40); // Runs in worker!
const primes = await mathWorker.findPrimes(1000000);

// ═══ CUSTOM PERFORMANCE UTILITY ═══
class PerfMonitor {
  #marks = new Map();
  #metrics = [];
  
  time(label) {
    this.#marks.set(label, performance.now());
  }
  
  timeEnd(label) {
    const start = this.#marks.get(label);
    if (!start) return;
    
    const duration = performance.now() - start;
    this.#metrics.push({ label, duration, timestamp: Date.now() });
    this.#marks.delete(label);
    
    return duration;
  }
  
  // Decorator for auto-measuring function execution time
  measure(fn, label) {
    return (...args) => {
      this.time(label || fn.name);
      const result = fn(...args);
      
      if (result instanceof Promise) {
        return result.finally(() => this.timeEnd(label || fn.name));
      }
      
      this.timeEnd(label || fn.name);
      return result;
    };
  }
  
  report() {
    const grouped = {};
    this.#metrics.forEach(m => {
      if (!grouped[m.label]) grouped[m.label] = [];
      grouped[m.label].push(m.duration);
    });
    
    Object.entries(grouped).forEach(([label, durations]) => {
      const avg = durations.reduce((a, b) => a + b, 0) / durations.length;
      const max = Math.max(...durations);
      const p95 = durations.sort((a, b) => a - b)[Math.floor(durations.length * 0.95)];
      console.log(`${label}: avg=${avg.toFixed(1)}ms, max=${max.toFixed(1)}ms, p95=${p95.toFixed(1)}ms`);
    });
  }
}

🎯 Top Performance Interview Questions

  • Q: How would you debug a janky scroll?
    A: Performance tab → look for long tasks during scroll. Check for: forced reflows (layout thrashing), expensive paint (complex CSS), non-composited animations. Fix: use transform/opacity, debounce scroll handlers, use IntersectionObserver instead of scroll event calculations, add will-change for animated elements.
  • Q: Your app has a memory leak. How do you find it?
    A: Memory tab → take heap snapshots before and after the action. Force GC between snapshots. Compare → look for growing "Detached DOM" or "Array/Object" counts. Check Retainers panel for what's keeping objects alive. Common culprits: event listeners, closures, growing Maps/caches.
  • Q: How would you optimize a function called 10,000 times per second?
    A: 1) Profile with DevTools to confirm it's the bottleneck. 2) Ensure consistent object shapes (monomorphic). 3) Use TypedArrays for numeric data. 4) Avoid creating objects in the hot path (use object pooling). 5) Consider Web Worker if CPU-bound. 6) Memoize if inputs repeat.
  • Q: Explain how you'd achieve 60fps animations.
    A: 60fps = 16.67ms per frame budget. Use only composite-triggering properties (transform, opacity). Use requestAnimationFrame for timing. Avoid layout reads in animation loop. Promote animated elements to their own layer (will-change). If JS computation needed → do it in rAF callback and keep it under 10ms.
  • Q: How do you reduce bundle size?
    A: 1) Code splitting at route level (dynamic import). 2) Tree shaking (ESM named exports). 3) Replace heavy libraries (moment→dayjs, lodash→lodash-es). 4) Lazy load below-the-fold components. 5) Compress with Brotli. 6) Analyze with webpack-bundle-analyzer. 7) Remove unused CSS (PurgeCSS).
