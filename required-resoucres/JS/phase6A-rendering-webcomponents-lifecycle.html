What Is the Critical Rendering Path?

The Critical Rendering Path (CRP) is the sequence of steps the browser takes to convert HTML, CSS, and JavaScript into pixels on screen. Understanding it is fundamental to performance optimization.

Mental Model: Think of building a house. You can't paint walls (Paint) before putting them up (Layout). You can't put walls up before knowing the blueprint (Render Tree). You can't make the blueprint before knowing both the house plan (DOM) and the decoration choices (CSSOM). The CRP is the browser's construction sequence.

Architecture Flow — Complete Browser Engine Pipeline

🌐 Browser Engine Architecture — How Bytes Become Pixels

📡 Network Layer

DNS lookup → TCP handshake → TLS negotiation → HTTP request/response. Raw bytes arrive via network stream.

⚙️ Renderer Process (Main Thread)

Parses HTML/CSS, executes JS, builds trees, calculates layout, paints layers. Single-threaded — JS blocks everything!

🎮 GPU Process

Rasterizes layers into tiles, composites final image, sends to display. Handles transform/opacity animations independently.

The Preload Scanner — Browser's Secret Weapon

When the HTML parser hits a <script> tag (without async/defer), it STOPS. But the browser doesn't sit idle — it runs the Preload Scanner to find resources ahead of time.

Step 1: HTML → DOM (Document Object Model)

// Browser receives raw HTML bytes from the network
// Conversion: Bytes → Characters (encoding) → Tokens (tokenizer) → Nodes → DOM Tree

// IMPORTANT: HTML parsing is INCREMENTAL (streaming)
// Browser doesn't wait for entire HTML — it starts building DOM as bytes arrive

// But parsing CAN BE BLOCKED by:
// 1. <script> tags (parser stops, downloads & executes JS, then resumes)
// 2. <script> with document.write() — can modify the stream!

// Solutions:
// <script defer> — download in parallel, execute AFTER DOM is complete (order preserved)
// <script async> — download in parallel, execute ASAP (order NOT guaranteed)
// <script type="module"> — automatically deferred

/*
Comparison:
                    Download    Execute         Order     DOMContentLoaded
No attribute:       Blocking    Blocking        Yes       Blocks
async:              Parallel    ASAP            No        Doesn't block
defer:              Parallel    After parsing   Yes       Doesn't block (fires after)
module:             Parallel    After parsing   Yes       Doesn't block
*/

Step 2: CSS → CSSOM (CSS Object Model)

// CSS is RENDER-BLOCKING — browser won't render until ALL CSS is parsed
// WHY? To avoid "flash of unstyled content" (FOUC)

// CSSOM is built by combining:
// 1. Browser default styles (user agent stylesheet)
// 2. External stylesheets (<link rel="stylesheet">)
// 3. Inline styles (<style> blocks)
// 4. Inline element styles (style="...")

// CSS specificity cascade happens during CSSOM construction
// Every CSS property for every visible element must be resolved

// KEY INSIGHT: CSS blocks rendering but NOT DOM parsing
// The browser can continue building the DOM while waiting for CSS
// But it CANNOT build the Render Tree (Step 3) until CSSOM is ready

// Performance implications:
// - Put CSS in <head> (discovered early)
// - Minimize render-blocking CSS
// - Use media queries on <link> to make non-critical CSS non-blocking:
//   <link rel="stylesheet" href="print.css" media="print">
//   (Still downloads, but doesn't block rendering for screen)
// - Inline critical CSS for above-the-fold content
// - Use rel="preload" for critical fonts/stylesheets

Step 3: DOM + CSSOM → Render Tree

// Render Tree = only VISIBLE elements with their computed styles
// It combines DOM structure with CSSOM styles

// What's NOT in the Render Tree:
// - Elements with display: none (completely removed)
// - <head>, <script>, <meta> (non-visual elements)
// - Elements hidden by CSS inheritance

// What IS in the Render Tree but invisible:
// - visibility: hidden (takes space, just not painted)
// - opacity: 0 (takes space, can still be interacted with)
// - elements off-screen (positioned outside viewport)

// Pseudo-elements (::before, ::after) ARE in the render tree
// even though they're not in the DOM

// Angular connection: 
// Angular's ViewEncapsulation.Emulated adds _nghost/_ngcontent attributes
// These attributes are part of the DOM and affect CSSOM specificity

Step 4: Layout (Reflow)

// Layout calculates the EXACT position and size of every element
// Input: Render Tree (what to show + styles)
// Output: Box model for each element (x, y, width, height)

// Layout is EXPENSIVE because:
// 1. One element's size can affect others (float, flexbox, grid)
// 2. Changes cascade — moving a parent moves all children
// 3. Layout is computed from the viewport inward

// The viewport meta tag affects initial layout:
// <meta name="viewport" content="width=device-width, initial-scale=1">
// Without this, mobile browsers assume 980px width

// Layout calculations involve:
// - Box model (content + padding + border + margin)
// - Flow layout (block vs inline)
// - Flexbox / Grid calculations
// - Positioning (relative, absolute, fixed, sticky)
// - Float interactions
// - Table layouts (especially expensive!)
// - Text wrapping and line breaks (requires font metrics)

Step 5: Paint

// Paint fills in actual pixels: colors, borders, shadows, text, images
// It creates PAINT RECORDS — ordered instructions for what to draw

// Paint order matters! (back-to-front, like z-index):
// 1. Background color
// 2. Background image
// 3. Border
// 4. Children (in DOM order, modified by z-index)
// 5. Outline

// Paint is per-layer (see Step 6: Composite)
// Changing only paint properties (color, background, shadow) is cheaper
// than layout changes, but still costs a repaint of that layer

Step 6: Composite

// The browser splits the page into LAYERS (like Photoshop layers)
// Each layer is painted independently, then composited together by the GPU

// What creates a new layer (compositing trigger):
// - position: fixed / sticky
// - transform (even transform: translateZ(0) — the "GPU hack")
// - opacity (when animated)
// - will-change: transform / opacity
// - <video>, <canvas>, <iframe>
// - CSS filters
// - Elements that overlap a composited layer

// WHY layers matter for performance:
// If an element is on its own layer, changes to it only require:
// 1. Repaint that ONE layer (not the whole page)
// 2. Re-composite (GPU operation — very fast!)
// 
// This is why transform/opacity animations are "free":
// They ONLY trigger composite (skip Layout AND Paint entirely!)

// The CSS properties that ONLY trigger composite:
// - transform (translate, rotate, scale)
// - opacity
// These are the ONLY properties safe for 60fps animations!

// will-change: tells browser to create a layer ahead of time
.animate-soon {
  will-change: transform; /* Creates layer in advance */
}
// WARNING: Don't overuse! Each layer consumes GPU memory.

Complete CRP Optimization Checklist

// 1. Minimize Critical Resources
//    - Inline critical CSS (above-the-fold)
//    - Defer non-critical CSS with media queries
//    - Use async/defer for scripts
//    - Remove unused CSS (tree-shaking)

// 2. Minimize Critical Bytes
//    - Minify HTML, CSS, JS
//    - Enable gzip/brotli compression
//    - Optimize images (WebP, AVIF, responsive srcset)

// 3. Minimize Critical Path Length
//    - Reduce number of round trips (HTTP/2, preload, preconnect)

//    - <link rel="preload" href="/critical.css" as="style">
//    - <link rel="dns-prefetch" href="https://cdn.example.com">

// Key metrics:
// - FCP (First Contentful Paint): When first content appears
// - LCP (Largest Contentful Paint): When main content is visible
// - CLS (Cumulative Layout Shift): Visual stability
// - TBT (Total Blocking Time): How long main thread is blocked

🎯 Interview Questions

Hard Explain the Critical Rendering Path step by step.

Answer: Browser receives HTML → parses into DOM tree (streaming, but blocked by scripts). Simultaneously downloads CSS → parses into CSSOM (render-blocking). DOM + CSSOM combine into Render Tree (only visible elements). Layout calculates exact geometry (position/size of every box). Paint fills pixels (colors, text, images). Composite combines layers via GPU. JavaScript can block DOM parsing (use defer/async). CSS blocks rendering but not parsing.

Expert Why are transform/opacity animations smooth but width/height animations are janky?

Answer: The rendering pipeline is: Layout → Paint → Composite. Changing width/height triggers a FULL pipeline (Layout + Paint + Composite) — expensive, causes other elements to shift. Transform/opacity ONLY trigger Composite (GPU handles it on a separate layer) — skips Layout and Paint entirely. At 60fps you have 16.6ms per frame; layout easily exceeds this budget while compositing is nearly free.

Medium What's the difference between async and defer on script tags?

Answer: Both download in parallel without blocking HTML parsing. defer executes AFTER DOM is fully parsed, preserves script order, fires before DOMContentLoaded. async executes as soon as downloaded (interrupts parsing), no order guarantee, doesn't wait for DOM. Use defer for scripts that need DOM access or depend on each other. Use async for independent scripts like analytics.

What Triggers Reflow (Layout)?

Reflow recalculates element positions and dimensions. It's the most expensive operation because changes cascade — moving one element can affect its siblings, children, and ancestors.

// ─── TRIGGERS REFLOW (avoid in hot paths!) ──────────────────

// 1. Geometric changes:
element.style.width = "200px";
element.style.height = "100px";
element.style.padding = "10px";
element.style.margin = "20px";
element.style.border = "1px solid red";
element.style.top / left / right / bottom;
element.style.fontSize = "18px"; // Text reflow!

// 2. DOM structure changes:
parent.appendChild(child);
parent.removeChild(child);
element.innerHTML = "...";
element.textContent = "...";

// 3. CSS class changes (if they affect layout):
element.classList.add("wide-layout");

// 4. Window resize (everything reflows)
window.addEventListener("resize", handler);

// 5. READING layout properties (forces synchronous reflow!):
element.offsetWidth;    element.offsetHeight;
element.offsetTop;      element.offsetLeft;
element.clientWidth;    element.clientHeight;
element.scrollWidth;    element.scrollHeight;
element.getBoundingClientRect();
getComputedStyle(element).width;
// These FORCE the browser to calculate layout RIGHT NOW
// to give you an accurate answer

// ─── TRIGGERS ONLY REPAINT (cheaper) ────────────────────────

// Visual-only changes (no geometry shift):
element.style.color = "red";
element.style.backgroundColor = "blue";
element.style.visibility = "hidden"; // Still takes space!
element.style.boxShadow = "0 2px 4px rgba(0,0,0,.2)";
element.style.outline = "2px solid red";
element.style.borderColor = "green"; // If border-width unchanged
element.style.backgroundImage = "url(...)";

// ─── TRIGGERS ONLY COMPOSITE (cheapest!) ────────────────────

element.style.transform = "translateX(100px)";
element.style.opacity = "0.5";
// These are handled entirely by the GPU on a separate layer

CSS Containment — Performance Boundaries

// CSS contain property tells the browser: "changes inside this element
// do NOT affect anything outside." This lets browser SKIP recalculating
// the rest of the page when this element changes.

// contain: layout — element's layout is independent
// contain: paint — nothing inside paints outside bounds (like overflow:hidden + optimization)
// contain: size — element's size doesn't depend on children (YOU must set width/height)
// contain: style — counters/quotes scoped to subtree
// contain: content — shorthand for layout + paint + style (NOT size)
// contain: strict — shorthand for ALL (layout + paint + size + style)

// PRACTICAL USE: Lists, cards, off-screen sections
// .card { contain: content; }
// → When card's innerHTML changes, browser only recalculates THAT card's layout
// → Without it, browser might recalculate layout of ALL siblings

// content-visibility: auto — ULTIMATE performance optimization
// .below-fold { content-visibility: auto; contain-intrinsic-size: 0 500px; }
// → Browser skips rendering (Layout + Paint) for off-screen elements entirely!
// → Renders only when element approaches viewport
// → contain-intrinsic-size: placeholder size for scroll calculations
// → Can reduce initial render time by 50-90% for long pages!

Layout Thrashing (Forced Synchronous Layout)

// THE WORST performance pattern in DOM manipulation:
// Alternating reads and writes in a loop

// ❌ BAD: Layout Thrashing (forces layout N times!)
const boxes = document.querySelectorAll(".box");
boxes.forEach(box => {
  const width = box.offsetWidth;    // READ → forces layout calculation
  box.style.width = width + 10 + "px"; // WRITE → invalidates layout
  // Next iteration's READ forces ANOTHER layout!
});
// N elements = N forced layouts = HORRIBLE performance

// ✅ GOOD: Batch reads, then batch writes
const boxes = document.querySelectorAll(".box");
const widths = [...boxes].map(box => box.offsetWidth); // ALL reads first
boxes.forEach((box, i) => {
  box.style.width = widths[i] + 10 + "px"; // ALL writes after
});
// Only 1 forced layout (for the reads) + 1 natural layout (for writes)

// ✅ BEST: Use requestAnimationFrame to batch writes
function updateLayout() {
  // Reads (okay — layout is current from last frame)
  const height = element.offsetHeight;

  // Writes (batched with other rAF callbacks, applied before next paint)
  requestAnimationFrame(() => {
    element.style.height = height * 2 + "px";
  });
}

// Library solution: fastdom (batches reads/writes automatically)
// fastdom.measure(() => { /* reads */ });
// fastdom.mutate(() => { /* writes */ });

Performance-Optimized Animation Patterns

// ❌ WRONG: Animating top/left (triggers reflow every frame!)
function animateBad() {
  element.style.left = parseInt(element.style.left) + 1 + "px";
  requestAnimationFrame(animateBad);
}

// ✅ RIGHT: Animating transform (composite only — 60fps guaranteed)
function animateGood() {
  position += 1;
  element.style.transform = `translateX(${position}px)`;
  requestAnimationFrame(animateGood);
}

// ✅ BEST: CSS animations/transitions (browser optimizes internally)
// CSS:
// .slide { transition: transform 0.3s ease; }
// .slide.active { transform: translateX(100px); }
// JS: element.classList.add("active"); // Browser handles the rest

// FLIP technique (First, Last, Invert, Play) for layout animations:
function flipAnimate(element, targetState) {
  // FIRST: record current position
  const first = element.getBoundingClientRect();

  // Apply state change (causes layout shift)
  targetState(); // e.g., reorder DOM, toggle class

  // LAST: record final position
  const last = element.getBoundingClientRect();

  // INVERT: move element back to where it was (using transform)
  const dx = first.left - last.left;
  const dy = first.top - last.top;
  element.style.transform = `translate(${dx}px, ${dy}px)`;

  // PLAY: animate to natural position (transform: none)
  requestAnimationFrame(() => {
    element.style.transition = "transform 0.3s ease";
    element.style.transform = "";
    element.addEventListener("transitionend", () => {
      element.style.transition = "";
    }, { once: true });
  });
}

🎯 Interview Questions

Hard What is layout thrashing and how do you prevent it?

Answer: Layout thrashing is alternating DOM reads and writes in a loop. Each read (offsetWidth, getBoundingClientRect) forces the browser to synchronously recalculate layout (because the previous write invalidated it). Prevention: batch all reads first, then all writes. Or use requestAnimationFrame to defer writes to the next frame. Libraries like fastdom automate this.

Medium Which CSS properties are cheapest to animate and why?

Answer: transform and opacity — they only trigger the Composite step (GPU-only, skips Layout and Paint). All other properties either trigger Layout+Paint+Composite (width, height, top, left, font-size) or Paint+Composite (color, background, box-shadow). For 60fps animations, ONLY use transform and opacity.

Expert Explain the FLIP animation technique.

Answer: FLIP = First, Last, Invert, Play. (1) Record element's current position (First). (2) Apply the DOM/style change (element jumps to Final position). (3) Calculate the difference and apply an inverse transform to make it LOOK like it hasn't moved (Invert). (4) Remove the transform with a CSS transition — the element animates smoothly to its new position (Play). This lets you animate layout changes using only transforms (GPU-accelerated).

What Is Shadow DOM?

Shadow DOM is a browser API that lets you attach a hidden, encapsulated DOM tree to an element. Styles inside the Shadow DOM don't leak out, and external styles don't bleed in. It's the browser's native solution for component encapsulation.

Angular Connection: Angular's ViewEncapsulation.ShadowDom uses native Shadow DOM. The default ViewEncapsulation.Emulated simulates it with _nghost/_ngcontent attribute selectors. Understanding Shadow DOM explains WHY Angular styles are scoped to components. 
// Creating a Shadow DOM
const host = document.querySelector("#my-widget");
const shadow = host.attachShadow({ mode: "open" }); // "open" = accessible via host.shadowRoot

// Add content to shadow
shadow.innerHTML = `
  <style>
    /* These styles are SCOPED — only affect this shadow tree! */
    p { color: red; font-weight: bold; }
    .title { font-size: 24px; }
  </style>
  <div class="title">I'm inside Shadow DOM</div>
  <p>External styles can't touch me!</p>
`;

// External CSS "p { color: blue; }" has NO EFFECT inside shadow!
// Shadow CSS "p { color: red; }" has NO EFFECT outside shadow!

// mode: "open" vs "closed"
// open: host.shadowRoot returns the ShadowRoot (inspectable)
// closed: host.shadowRoot returns null (truly hidden — like <video> controls)

// ─── CSS CROSSING THE SHADOW BOUNDARY ─────────────────────

// 1. Inherited properties DO cross (font-family, color, etc.) — by design
// 2. CSS custom properties (variables) cross:
shadow.innerHTML = `
  <style>
    p { color: var(--text-color, black); } /* Uses external variable! */
  </style>
  <p>I use the host's --text-color</p>
`;
// External CSS: :root { --text-color: navy; } → affects shadow content

// 3. ::part() selector (explicit opt-in):
shadow.innerHTML = `
  <button part="submit-btn">Submit</button>
`;
// External CSS: my-widget::part(submit-btn) { background: green; }

// 4. :host and :host-context selectors (style from inside):
shadow.innerHTML = `
  <style>
    :host { display: block; border: 1px solid gray; }
    :host(.dark) { background: #333; color: white; }
    :host-context(.theme-blue) { border-color: blue; }
  </style>
`;

// ─── SLOTS (Content Projection) ──────────────────────────

// Slots let users inject content INTO your shadow DOM (like Angular <ng-content>)
shadow.innerHTML = `
  <style> .wrapper { border: 2px solid blue; padding: 10px; } </style>
  <div class="wrapper">
    <h2><slot name="title">Default Title</slot></h2>
    <slot>Default content goes here</slot>
  </div>
`;

// Usage in light DOM:
// <my-widget>
//   <span slot="title">Custom Title</span>
//   <p>This goes into the unnamed/default slot</p>
// </my-widget>

// Angular equivalent:
// <ng-content select="[header]"></ng-content> = <slot name="header"></slot>

Event Retargeting in Shadow DOM

// Events that originate inside Shadow DOM are RETARGETED at the shadow boundary
// Outside code sees the HOST element as the target (encapsulation preserved!)

// Inside shadow: user clicks a <button> inside shadow root
// Outside handler: event.target === hostElement (not the internal button)
// Inside handler: event.target === button (normal behavior)

// WHICH EVENTS CROSS THE SHADOW BOUNDARY?
// Events with composed: true cross (most UI events):
// - click, dblclick, mousedown/up, mousemove, mouseover/out
// - keydown, keyup, keypress
// - focus, blur (with composed: true + relatedTarget retargeted)
// - input, change
// - touchstart, touchend, touchmove

// Events that DON'T cross (composed: false):
// - Custom events (by default) — you must set composed: true manually
// - Some internal events (slotchange)

// Custom event crossing shadow boundary:
this.shadowRoot.querySelector("button").addEventListener("click", () => {
  this.dispatchEvent(new CustomEvent("card-click", {
    detail: { id: this.getAttribute("data-id") },
    bubbles: true,   // Bubbles up the DOM
    composed: true   // CROSSES shadow boundary!
  }));
});

// slotchange event — detect when slotted content changes
const slot = this.shadowRoot.querySelector("slot");
slot.addEventListener("slotchange", () => {
  const assigned = slot.assignedNodes({ flatten: true });
  console.log("Slot content changed:", assigned.length, "nodes");
});

Adopted Stylesheets — Shared Styles Efficiently

// Problem: each Shadow DOM instance duplicates <style> content in memory

🎯 Interview Questions

Hard How does Angular's ViewEncapsulation.Emulated work?

Answer: Angular generates unique attributes (_nghost-[id] on the host, _ngcontent-[id] on children). It rewrites component CSS selectors to include these attributes (e.g., .title becomes .title[_ngcontent-abc]). This scopes styles to the component without real Shadow DOM. Medium How can external styles penetrate Shadow DOM?

Answer: Three ways: (1) CSS Custom Properties (--variables) cross the boundary. (2) Inherited properties (font-family, color, line-height) cascade into shadow. (3) The ::part() selector can style elements that opt-in with the "part" attribute. Global selectors like .class or #id cannot reach inside.

What Are Web Components?

Web Components are a set of browser-native APIs that let you create reusable, encapsulated UI components without any framework. They consist of three technologies: Custom Elements, Shadow DOM, and HTML Templates.

    super();

    return ["name", "avatar", "role"];

Reactive Properties Pattern (Without Framework)

// Pattern: Make Web Components reactive (auto-render on property change)
// This is what Lit, Stencil, and other WC libraries do under the hood

class ReactiveElement extends HTMLElement {
  static observedAttributes = [];
  #renderScheduled = false;
  #props = {};

  constructor() {
    super();
    this.attachShadow({ mode: "open" });

    // Create reactive properties from observedAttributes
    for (const attr of this.constructor.observedAttributes) {
      Object.defineProperty(this, attr, {
        get: () => this.#props[attr],
        set: (value) => {
          const old = this.#props[attr];
          if (old === value) return; // No change
          this.#props[attr] = value;
          this.#scheduleRender();
        }
      });
    }
  }

  #scheduleRender() {
    if (this.#renderScheduled) return;
    this.#renderScheduled = true;
    // Batch multiple property changes into ONE render (microtask)
    queueMicrotask(() => {
      this.#renderScheduled = false;
      this.render();
    });
  }

  attributeChangedCallback(name, _, newValue) {
    this[name] = newValue; // Sync attribute → property
  }

  connectedCallback() { this.render(); }
  render() { /* Override in subclass */ }
}

// Usage:
class UserBadge extends ReactiveElement {
  static observedAttributes = ["name", "status"];

  render() {
    this.shadowRoot.innerHTML = `
      <span class="badge ${this.status}">${this.name}</span>
    `;
  }
}
customElements.define("user-badge", UserBadge);

// Setting properties triggers batched re-render:
const badge = document.querySelector("user-badge");
badge.name = "Siddu";   // Schedules render
badge.status = "online"; // Same microtask — only ONE render happens!

Complete Page Lifecycle State Machine

🔄 Page Lifecycle States — How Browsers Manage Your Page

Modern browsers (especially mobile) aggressively manage page states to save battery and memory.

State Transitions
📄 LOADING → DOMContentLoaded → ✅ ACTIVE (visible + focused) → blur → 👁️ PASSIVE (visible, no focus)
✅ ACTIVE → visibilitychange → 👻 HIDDEN (tab switched) → freeze → 🧊 FROZEN (JS suspended)
🧊 FROZEN → memory pressure → 💀 DISCARDED (dead)
👻 HIDDEN → pagehide → ⛔ TERMINATED (unloading)
🧊 FROZEN → resume → ✅ ACTIVE (must restore state!)
State Descriptions
ACTIVE — Visible + has input focus
PASSIVE — Visible, another window focused
HIDDEN — Not visible (tab switched/minimized)
FROZEN — JS execution suspended (mobile!)
DISCARDED — Unloaded from memory (tab shell remains)
TERMINATED — Page being closed/navigated away
⚠️ Key Insight

Mobile browsers AGGRESSIVELY freeze/discard hidden tabs!

Your code MUST handle freeze → resume gracefully. Save state on visibilitychange (hidden), restore on resume. Use sendBeacon for analytics on page close.

Document Loading Events

// ─── LOADING PHASE EVENTS (in order) ─────────────────────

// 1. DOMContentLoaded — HTML fully parsed, DOM ready
//    CSS may still be loading, images not loaded
document.addEventListener("DOMContentLoaded", () => {
  console.log("DOM ready — safe to query elements");

window.addEventListener("load", () => {
  console.log("All resources loaded — including images");
  // Good for: measuring image dimensions, removing loading spinners
});

// 3. beforeunload — User about to leave (chance to warn)
window.addEventListener("beforeunload", (e) => {
  if (hasUnsavedChanges) {

// visibilitychange — user switches tab, minimizes window
document.addEventListener("visibilitychange", () => {

    pauseBackgroundWork();
    saveProgress(); // Use sendBeacon for network requests here

    resumeBackgroundWork();
    refreshData();
  }
});

window.addEventListener("pagehide", (e) => {
  if (e.persisted) {
    // Page is being stored in bfcache (back/forward cache)
    // Will be restored on browser back/forward
  } else {
    // Page is truly being unloaded
  }
});

window.addEventListener("pageshow", (e) => {

// Pages are NOT eligible for bfcache if they have:

// document.readyState: "loading" → "interactive" → "complete"
// "interactive" = DOM parsed (same as DOMContentLoaded)
// "complete" = all resources loaded (same as window.load)

if (document.readyState === "loading") {
  document.addEventListener("DOMContentLoaded", init);
} else {
  init(); // DOM already ready
}

// - Asynchronous, non-blocking

Freeze & Resume — Handling Browser Suspension

// On mobile (and increasingly desktop), browsers FREEZE hidden tabs
// Your timers, intervals, and animations STOP
// When resumed, they don't "catch up" — they just continue

// freeze event — tab is being suspended (Chrome 68+)
document.addEventListener("freeze", () => {
  // MUST complete synchronously! No async allowed.
  // 1. Stop all timers/intervals
  clearInterval(pollingInterval);
  // 2. Close WebSocket/EventSource connections (they'd be broken anyway)
  socket.close();
  // 3. Release IndexedDB locks
  db.close();
  // 4. Save state to sessionStorage (survives freeze)
  sessionStorage.setItem("appState", JSON.stringify(getState()));
});

// resume event — tab is being un-suspended
document.addEventListener("resume", () => {
  // 1. Restore state
  const saved = JSON.parse(sessionStorage.getItem("appState"));
  if (saved) restoreState(saved);
  // 2. Reconnect WebSocket
  connectWebSocket();
  // 3. Restart timers
  pollingInterval = setInterval(poll, 30000);
  // 4. Refresh stale data
  refreshDataIfStale();
});

// Detect if page was discarded (tab is re-created from scratch)
if (document.wasDiscarded) {
  // Page was killed by browser (memory pressure) and is being recreated
  // All JS state is GONE — restore from sessionStorage/IndexedDB
  restoreFromStorage();
}

Idle Detection & Background Throttling

// requestIdleCallback — run work when browser is idle (low priority tasks)
requestIdleCallback((deadline) => {
  // deadline.timeRemaining() → ms left before browser needs to do other work
  while (deadline.timeRemaining() > 5 && workQueue.length > 0) {
    processNextItem(workQueue.shift());
  }
  // If work remains, schedule another idle callback
  if (workQueue.length > 0) {
    requestIdleCallback(processWork);
  }
}, { timeout: 5000 }); // Force run within 5s even if not idle

// Use cases for requestIdleCallback:
// - Analytics reporting
// - Prefetching resources
// - Pre-rendering off-screen components
// - Non-critical DOM updates
// - IndexedDB cleanup

// ─── BACKGROUND THROTTLING (browser behavior) ─────────────

// When a tab is HIDDEN, browsers throttle:
// - setTimeout/setInterval: minimum 1000ms delay (not your specified delay!)
// - requestAnimationFrame: suspended entirely (0 fps)
// - fetch/XHR: may be delayed (lower priority)
// - WebSocket: keep-alive only (no custom messages in some browsers)

// EXCEPT when:
// - Tab is playing audio (getUserMedia, Web Audio with output)
// - Tab has an active WebSocket/WebRTC connection
// - Tab is running a Service Worker

// Timer Throttling Example:
// setInterval(fn, 100) in background tab:
//   Chrome: fires every 1000ms (not 100ms!)
//   Firefox: similar
//   Safari: may suspend entirely after 30s

// To handle this gracefully:
let lastTick = Date.now();
setInterval(() => {
  const now = Date.now();
  const elapsed = now - lastTick;
  lastTick = now;
  if (elapsed > 2000) {
    // We were throttled/frozen — refresh stale data
    syncState();
  }
  doWork();
}, 1000);

Wake Lock API — Prevent Screen Sleep

// Prevent device from sleeping (e.g., video player, recipe app, navigation)
let wakeLock = null;

async function requestWakeLock() {
  try {
    wakeLock = await navigator.wakeLock.request("screen");
    console.log("Wake lock acquired");

    wakeLock.addEventListener("release", () => {
      console.log("Wake lock released");
    });
  } catch (err) {
    // Fails if: tab hidden, low battery, browser doesn't support
    console.error("Wake lock failed:", err);
  }
}

// Re-acquire on visibility change (wake lock auto-releases when tab hidden)
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "visible" && !wakeLock) {
    requestWakeLock();
  }
});

// Release when no longer needed:
await wakeLock.release();
wakeLock = null;

🎯 Interview Questions

Medium What's the difference between DOMContentLoaded and window.load?

Answer: DOMContentLoaded fires when HTML is fully parsed and DOM tree is built — CSS stylesheets, images, and subframes may still be loading. window.load fires only when ALL resources (images, CSS, fonts, iframes) are completely loaded. Use DOMContentLoaded for DOM-dependent JS (or defer scripts). Use load only when you need image dimensions or full page resources.

Hard What is bfcache and why does having an 'unload' listener break it?

Answer: bfcache (back/forward cache) stores a complete snapshot of the page in memory for instant back/forward navigation. The 'unload' event was designed to mean "page is being destroyed," which conflicts with bfcache's goal of preserving the page. Browsers disable bfcache for pages with 'unload' listeners because they can't guarantee the listener's semantics. Use 'pagehide' with the 'persisted' property instead.

Hard What happens to timers and animations when a tab is hidden?

Answer: Browsers throttle hidden tabs: setTimeout/setInterval minimum delay becomes 1000ms (regardless of your specified delay). requestAnimationFrame is completely suspended (0 fps). Fetch requests may be deprioritized. This is intentional to save CPU/battery. Handle it by checking elapsed time on each tick and syncing state when the discrepancy is large. Use visibilitychange event to pause/resume work properly.

Medium How would you reliably send analytics data when the user leaves?

Answer: Use navigator.sendBeacon() in the visibilitychange event (when state becomes "hidden"). sendBeacon is fire-and-forget: it queues the request and guarantees delivery even as the page unloads. Unlike fetch in beforeunload (which browsers cancel), sendBeacon survives page close. Limited to POST, can't read response, body must be string/Blob/FormData.

Expert Explain the full page lifecycle state machine.

Answer: States: Active (visible + focused) → Passive (visible, not focused) → Hidden (tab switched) → Frozen (JS suspended, mobile) → Discarded (memory freed, tab shell remains) → Terminated (page closing). Transitions: visibilitychange (active↔hidden), freeze/resume (hidden↔frozen), pageshow/pagehide (for bfcache). Mobile browsers freeze aggressively — code must save state on freeze, restore on resume. document.wasDiscarded tells if page was previously killed.

How SPA Routing Works

Single Page Applications don't reload the page when navigating. They use the History API to update the URL and manage navigation state without server round-trips. This is what Angular Router, React Router, and Vue Router all use under the hood.

← Back Button → popstate event fires → Read location.pathname → Render Previous

// ─── History API Basics ───────────────────────────────────

// Push a new entry to history (URL changes, no reload)
history.pushState(
  { page: "about", scrollY: 0 },  // state object (serializable)
  "",                               // title (ignored by most browsers)
  "/about"                          // URL to display
);

// Replace current entry (no new history entry)
history.replaceState({ page: "home" }, "", "/home");

// Navigate back/forward
history.back();     // Same as browser back button
history.forward();  // Same as browser forward button
history.go(-2);     // Go back 2 entries
history.length;     // Number of entries in history stack

// ─── Listening for Navigation ─────────────────────────────

// popstate fires when user clicks back/forward (or history.back()/forward())
// Does NOT fire on pushState/replaceState!
window.addEventListener("popstate", (e) => {
  console.log("Navigated to:", location.pathname);
  console.log("State:", e.state); // The state object from pushState
  renderRoute(location.pathname);
});

// ─── Building a Mini SPA Router ───────────────────────────

class Router {
  #routes = new Map();
  #outlet = null;

  constructor(outlet) {
    this.#outlet = document.querySelector(outlet);
    window.addEventListener("popstate", () => this.#resolve());
    document.addEventListener("click", (e) => this.#handleClick(e));
  }

  route(path, handler) {
    this.#routes.set(path, handler);
    return this; // Chainable
  }

  navigate(path, state = {}) {
    history.pushState(state, "", path);
    this.#resolve();
  }

  #resolve() {
    const path = location.pathname;
    const handler = this.#routes.get(path) || this.#routes.get("*");
    if (handler) {
      this.#outlet.innerHTML = ""; // Clear
      handler(this.#outlet, history.state);
    }
  }

  #handleClick(e) {
    const link = e.target.closest("a[data-route]");
    if (!link) return;
    e.preventDefault();
    this.navigate(link.getAttribute("href"));
  }

  start() {
    this.#resolve(); // Render current route on init
  }
}

// Usage:
const router = new Router("#app");
router
  .route("/", (el) => { el.innerHTML = "<h1>Home</h1>"; })
  .route("/about", (el) => { el.innerHTML = "<h1>About</h1>"; })
  .route("/contact", (el) => { el.innerHTML = "<h1>Contact</h1>"; })
  .route("*", (el) => { el.innerHTML = "<h1>404 Not Found</h1>"; })
  .start();

// Links: <a href="/about" data-route>About</a>

// HASH ROUTING: example.com/#/about

Route Parameters & URL Parsing

// Routers need to extract dynamic segments from URLs
// e.g., /users/123/posts/456 → { userId: "123", postId: "456" }

// URL pattern matching with regex:
function matchRoute(pattern, path) {
  // Convert "/users/:id/posts/:postId" to regex
  const paramNames = [];
  const regexStr = pattern.replace(/:([^/]+)/g, (_, name) => {
    paramNames.push(name);
    return "([^/]+)"; // Capture group for the value
  });

  const match = path.match(new RegExp(`^${regexStr}$`));
  if (!match) return null;

  const params = {};
  paramNames.forEach((name, i) => {
    params[name] = decodeURIComponent(match[i + 1]);
  });
  return params;
}

// Usage:
matchRoute("/users/:id", "/users/123");
// → { id: "123" }

matchRoute("/users/:userId/posts/:postId", "/users/42/posts/7");
// → { userId: "42", postId: "7" }

Scroll Restoration

// By default, browsers restore scroll position on back/forward
// But SPAs often need to control this manually

// Disable browser's automatic scroll restoration:
if ("scrollRestoration" in history) {
  history.scrollRestoration = "manual"; // "auto" is default
}

// Manual scroll management:
class ScrollManager {
  #positions = new Map();

  savePosition(path) {
    this.#positions.set(path, {
      x: window.scrollX,
      y: window.scrollY
    });
  }

  restorePosition(path) {
    const pos = this.#positions.get(path);
    if (pos) {
      // Use requestAnimationFrame to ensure DOM has rendered
      requestAnimationFrame(() => {
        window.scrollTo(pos.x, pos.y);
      });
    } else {
      window.scrollTo(0, 0); // New page — scroll to top
    }
  }
}

// After navigate: scrollManager.restorePosition(newPath);

Route Guards Pattern (Pre-navigation Checks)

// Route guards determine if navigation should proceed
// Common in Angular (CanActivate, CanDeactivate)
// Here's the vanilla JS equivalent:

class GuardedRouter {
  #routes = new Map();
  #guards = { before: [], canLeave: [] };
  #currentRoute = null;

  // Guard that runs BEFORE entering a route
  beforeEach(guardFn) {
    this.#guards.before.push(guardFn);
  }

  // Guard that runs BEFORE leaving a route (unsaved changes?)
  beforeLeave(guardFn) {
    this.#guards.canLeave.push(guardFn);
  }

  async navigate(path) {
    // 1. Check canLeave guards (e.g., unsaved form?)
    for (const guard of this.#guards.canLeave) {
      const canLeave = await guard(this.#currentRoute, path);
      if (!canLeave) return false; // Block navigation!
    }

    // 2. Check before guards (e.g., auth check)
    for (const guard of this.#guards.before) {
      const result = await guard(path);
      if (result === false) return false;
      if (typeof result === "string") {
        // Redirect
        return this.navigate(result);
      }
    }

    // 3. Proceed with navigation
    history.pushState(null, "", path);
    this.#currentRoute = path;
    this.#resolve(path);
    return true;
  }
}

// Usage:
const router = new GuardedRouter();

// Auth guard:
router.beforeEach(async (path) => {
  if (path.startsWith("/admin") && !isLoggedIn()) {
    return "/login"; // Redirect to login
  }
  return true; // Allow
});

// Unsaved changes guard:
router.beforeLeave(async (from, to) => {
  if (formIsDirty()) {
    return confirm("You have unsaved changes. Leave anyway?");
  }
  return true;
});

Navigation API (Modern — Chrome 102+)

// The Navigation API is a modern replacement for the History API
// Solves many pain points (no popstate on pushState, no intercept hooks)

// navigation.navigate() — replaces pushState + manual rendering
navigation.navigate("/about", { state: { fromClick: true } });

// Intercept ALL navigations (link clicks, form submits, back/forward):
navigation.addEventListener("navigate", (event) => {
  // Skip external navigations
  if (!event.canIntercept) return;

  const url = new URL(event.destination.url);

  // Only handle same-origin navigations
  if (url.origin !== location.origin) return;

  event.intercept({
    // This function handles rendering — scroll happens automatically after
    async handler() {
      const content = await fetchPageContent(url.pathname);
      document.querySelector("#app").innerHTML = content;
    },
    // Focus management (accessibility):
    focusReset: "after-transition",
    // Scroll behavior:
    scroll: "after-transition" // Auto scroll-to-top or restore position
  });
});

// Benefits over History API:
// 1. ONE event for ALL navigations (pushState, link clicks, back/forward, form submit)
// 2. Built-in scroll restoration
// 3. Transition tracking: event.signal (AbortSignal for interrupted navigations)
// 4. navigation.currentEntry.getState() — typed state access
// 5. navigation.entries() — full history stack access (unlike history.length)
// 6. navigation.canGoBack / navigation.canGoForward

// Note: Not yet in Firefox/Safari (2024). Use progressively or with polyfill.
// Angular 16+ experimentally uses Navigation API when available.

🎯 Interview Questions

Medium How do SPAs handle routing without page reloads?

Answer: SPAs use the History API (history.pushState) to change the URL without triggering a page reload. When user navigates, the router intercepts link clicks (preventDefault), pushes new state to history, and renders the appropriate component. The popstate event handles browser back/forward buttons. Server must be configured to serve index.html for all routes.

Hard What's the difference between hash and history routing? When would you use each?

Answer: Hash routing (#/path) uses the URL fragment — never sent to server, so no server config needed. History routing (/path) uses pushState — clean URLs but requires server to return index.html for all paths (otherwise 404 on refresh). Use hash when: you can't control server config, need static hosting (S3), or legacy browser support. Use history (default in Angular) when: you have server control, need clean URLs for SEO, or use SSR.

Expert Why doesn't pushState trigger the popstate event?

Answer: By design, pushState/replaceState only modify the history stack — they don't trigger popstate. Only actual navigation (back/forward buttons, history.back(), history.go()) triggers popstate. This lets you update the URL programmatically and handle rendering directly (after calling pushState, you call your own renderRoute function). If pushState triggered popstate, you'd get double rendering.
