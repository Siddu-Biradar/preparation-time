What is the DOM? (Foundation)

The DOM (Document Object Model) is an API that represents an HTML/XML document as a tree of objects. It is NOT the HTML source code — it's the browser's in-memory representation that JavaScript can interact with.

Key Insight: The DOM can differ from your HTML source because: (1) The browser auto-fixes invalid HTML (adds missing <html>, <head>, <body>). (2) JavaScript can modify the DOM after load. (3) The browser normalizes whitespace and adds text nodes between elements. 
// ─── What the DOM IS and IS NOT ───────────────────────────

// DOM IS:
// - A tree-structured API for HTML/XML documents
// - Created by the browser from parsing HTML
// - The "live" representation that JS interacts with
// - An interface specification (defined by W3C/WHATWG)

// DOM IS NOT:
// - The HTML source code (view-source shows the original)
// - The rendered pixels on screen (that's after Layout + Paint)
// - Part of JavaScript itself (it's a Web API the browser provides)
// - The same as what you see in DevTools (DevTools shows a pretty-printed version)

// ─── How the DOM is Built ─────────────────────────────────

// 1. Browser receives HTML bytes over network
// 2. Bytes → Characters (decode using charset, usually UTF-8)
// 3. Characters → Tokens (tokenizer identifies tags, attributes, text)
// 4. Tokens → Nodes (each token becomes a Node object)
// 5. Nodes → DOM Tree (parent-child relationships established)

// This happens INCREMENTALLY (streaming) — browser doesn't wait for full HTML

DOM Tree Structure

// Browser parses HTML → builds DOM tree → renders pixels

Node Types (Complete Reference)

// Every item in the DOM tree is a Node
// Nodes have a .nodeType property (numeric constant)

// Node types (nodeType property):
// 1  = ELEMENT_NODE       (div, p, span — HTML tags)
// 3  = TEXT_NODE           (text content, whitespace counts!)
// 8  = COMMENT_NODE       (<!-- comments -->)
// 9  = DOCUMENT_NODE      (the document itself)
// 10 = DOCUMENT_TYPE_NODE (<!DOCTYPE html>)
// 11 = DOCUMENT_FRAGMENT_NODE (lightweight container)

// Node vs Element — THE key distinction:
// Node: ANY node in the DOM tree (text, comment, element, document)
// Element: SPECIFIC type of Node that represents an HTML tag
// All Elements are Nodes, but NOT all Nodes are Elements!

const div = document.querySelector("div");
div.nodeType;     // 1 (Element)
div.nodeName;     // "DIV" (uppercase for elements)
div.nodeValue;    // null (elements don't have a value — text nodes do)

const text = div.firstChild; // Might be a Text node
text.nodeType;    // 3
text.nodeName;    // "#text"
text.nodeValue;   // "the actual text content"

// ─── childNodes vs children (CRITICAL difference) ─────────

div.childNodes;   // NodeList — includes ALL node types (text, comments, elements)
div.children;     // HTMLCollection — ONLY Element nodes

// Example showing why this matters:
// HTML: <ul>  <li>A</li>  <li>B</li>  </ul>
// 
// ul.childNodes → [Text(" "), li, Text(" "), li, Text(" ")]  — 5 nodes!
// ul.children   → [li, li]                                   — 2 elements
// 
// Whitespace between tags creates Text nodes!
// This is the #1 gotcha when using childNodes

// ─── Checking node types ─────────────────────────────────

// Modern: instanceof checks
element instanceof HTMLElement;      // true for any HTML element
element instanceof HTMLDivElement;   // true only for <div>
element instanceof HTMLInputElement; // true only for <input>
element instanceof Text;             // true for text nodes
element instanceof Comment;          // true for comment nodes

// Old way: nodeType checks
if (node.nodeType === Node.ELEMENT_NODE) { /* it's an element */ }
if (node.nodeType === Node.TEXT_NODE) { /* it's text */ }

🎯 Interview Questions

Easy What is the DOM?

Answer: The DOM (Document Object Model) is a tree-structured API the browser creates by parsing HTML. It represents the document as objects that JavaScript can read and modify. It's NOT the HTML source — it's the browser's live in-memory representation. Changes to the DOM are reflected on screen (after layout + paint).

Medium What's the difference between childNodes and children?

Answer: childNodes returns a live NodeList of ALL child nodes (elements, text nodes, comments — including whitespace text nodes). children returns a live HTMLCollection of only Element children (skips text and comments). Use children in most cases to avoid whitespace text node surprises.

Hard How does the DOM differ from the HTML source?

Answer: The DOM can differ because: (1) Browser auto-corrects invalid HTML (adds missing body/html tags, fixes unclosed elements). Why This Matters

Before you can modify any element, you must first find it in the DOM tree. JavaScript provides multiple selection methods — each with different performance characteristics, return types, and liveness. Choosing the right one matters for both performance and correctness.

Selection Methods (Complete)

// ─── Modern Methods (use these by default) ────────────────

// querySelector — returns FIRST match or null
document.querySelector(".card");           // First element with class "card"
document.querySelector("#app");            // Element with id "app"
document.querySelector("div.card > h2");   // Complex CSS selector
document.querySelector("[data-id='123']"); // Attribute selector

// querySelectorAll — returns ALL matches (static NodeList)
document.querySelectorAll("div.card");     // All matching elements
document.querySelectorAll("input:checked"); // Pseudo-selectors work!

// getElementById — fastest selector (hash map lookup)
document.getElementById("app");            // Returns element or null
// NOTE: Don't include # — it's NOT a CSS selector

// ─── Older Methods (still valid, have unique behaviors) ────

document.getElementsByClassName("card");   // Live HTMLCollection
document.getElementsByTagName("div");      // Live HTMLCollection
document.getElementsByName("email");       // Live NodeList (for name attribute)

// ─── Scoped Selection (search within a subtree) ──────────

// You can call querySelector on ANY element (not just document)
const container = document.querySelector("#sidebar");
const link = container.querySelector("a.active"); // Searches only within #sidebar
const allLinks = container.querySelectorAll("a"); // Only links inside sidebar

Static vs Live Collections (CRITICAL)

// This is the #1 source of bugs when working with DOM collections!

// STATIC (snapshot) — querySelectorAll returns this
const staticList = document.querySelectorAll(".item");
// Captured at that moment — adding/removing .item elements later has NO effect
// Safe to iterate while modifying DOM

// LIVE (auto-updating) — getElementsBy* returns this
const liveList = document.getElementsByClassName("item");
// AUTOMATICALLY updates when DOM changes!
// ⚠️ DANGEROUS: iterating while modifying can cause infinite loops or skips

// Demo of the danger:
const items = document.getElementsByClassName("highlight");
// ❌ BUG: as you remove the class, the collection shrinks, skipping elements!
for (let i = 0; i < items.length; i++) {
  items[i].classList.remove("highlight"); // Collection shrinks! i++ skips next
}
// ✅ FIX: iterate backwards or convert to array first
for (let i = items.length - 1; i >= 0; i--) {
  items[i].classList.remove("highlight");
}
// or: [...items].forEach(el => el.classList.remove("highlight"));

// closest() — traverse UP to find matching ancestor (or self)
// INCREDIBLY useful for event delegation!
const card = clickedElement.closest(".card"); // Find parent card

// Returns null if no match found (searched all way to document)

// matches() — check if element matches a CSS selector
element.matches(".active");        // true/false
element.matches("div.card:hover"); // Complex selectors work

// contains() — check parent/child relationship
parent.contains(child);   // true if child is anywhere inside parent
document.body.contains(element); // true if element is in the page

// ─── Practical Traversal Patterns ────────────────────────

// Find all siblings:
function getSiblings(el) {
  return [...el.parentElement.children].filter(child => child !== el);
}

// Find all ancestors matching a selector:
function getAncestors(el, selector) {
  const ancestors = [];
  let current = el.parentElement;
  while (current) {
    if (current.matches(selector)) ancestors.push(current);
    current = current.parentElement;
  }
  return ancestors;
}

// Walk all descendants (depth-first):
function walkDOM(node, callback) {
  callback(node);
  node = node.firstElementChild;
  while (node) {
    walkDOM(node, callback);
    node = node.nextElementSibling;
  }
}

// ─── NodeList (from querySelectorAll) ─────────────────────

nodeList.forEach(p => { });     // ✅ Has forEach

// ❌ No .map(), .filter(), .reduce() — NOT a full array!

// ─── HTMLCollection (from getElementsBy*) ─────────────────

collection.length;               // ✅ Has length

// ─── Converting to Array (unlocks full array methods) ─────

const arr2 = [...nodeList];           // Spread (cleaner)
const arr3 = Array.prototype.slice.call(collection); // Old school

// Now you can use map, filter, reduce, find, etc:
const texts = [...document.querySelectorAll("p")].map(p => p.textContent);
const visible = [...document.querySelectorAll(".item")]

🎯 Interview Questions

Medium What's the difference between querySelector and getElementById? Which is faster?

Answer: getElementById only selects by ID — it's the fastest because browsers maintain a hash map of IDs (O(1) lookup). querySelector accepts any CSS selector but must parse and traverse — slightly slower. getElementById returns null if not found. Use getElementById for IDs, querySelector for everything else.

Hard Explain the difference between a static NodeList and a live HTMLCollection. When would the "live" behavior cause bugs?

Answer: Static NodeList (from querySelectorAll) is a snapshot — DOM changes after the query don't affect it. Live HTMLCollection (from getElementsBy*) auto-updates when the DOM changes. Bug scenario: iterating a live collection while removing matching elements — the collection shrinks mid-loop, skipping elements. Fix: iterate backwards or convert to an array first.

Medium What does element.closest() do and where is it most useful?

Answer: closest(selector) traverses UP from the element (including itself) and returns the first ancestor that matches the CSS selector, or null. Most useful in event delegation — when a click happens on a nested element (like a span inside a button inside a card), you use e.target.closest(".card") to find the relevant container regardless of what exact child was clicked.

🎯 Interview Questions

Medium What is a DocumentFragment and why is it useful for performance?

Answer: A DocumentFragment is a lightweight DOM container that exists only in memory (not part of the active DOM tree). When you append elements to a fragment, no reflows/repaints occur. When you insert the fragment into the DOM, all its children are moved in ONE operation (one reflow). The fragment itself disappears — it's just a transport mechanism for batching DOM insertions.

Hard What is layout thrashing and how do you prevent it?

Answer: Layout thrashing is alternating DOM reads (offsetWidth, getBoundingClientRect) and writes (style changes) in a loop. Each read forces a synchronous layout calculation because the previous write invalidated the layout. Prevention: batch ALL reads first, then ALL writes. Or use requestAnimationFrame to defer writes to the next frame. Libraries like fastdom automate read/write batching.

Easy How do you safely add user-generated content to the DOM?

Answer: Use textContent (escapes HTML entities) or document.createTextNode(). NEVER use innerHTML with user input — it executes embedded scripts (XSS attack). For rich HTML content, sanitize with a library like DOMPurify. In Angular, use property binding [textContent]="data" or rely on built-in sanitization.

Theory

/*
Event Propagation (3 phases):

Phase 1: CAPTURING (top → target)
window → document → html → body → div → button

Phase 2: TARGET
button (the element that was clicked)

Phase 3: BUBBLING (target → top)
button → div → body → html → document → window
*/

// addEventListener with capture option:
element.addEventListener("click", handler, { capture: true }); // Capture phase
element.addEventListener("click", handler, { capture: false }); // Bubble phase (default)
element.addEventListener("click", handler, true); // Shorthand for capture: true

// Event object properties:
element.addEventListener("click", (e) => {
  e.target;          // Element that triggered the event (deepest)
  e.currentTarget;   // Element the listener is attached to (=this)
  e.type;            // "click"
  e.timeStamp;       // When event occurred
  e.bubbles;         // Does this event bubble?
  e.eventPhase;      // 1=capturing, 2=target, 3=bubbling

  e.preventDefault();       // Prevent default browser behavior
});

Event Emitter (Pub/Sub Pattern)

// For non-DOM communication (services, state management, modules)
// This is what Angular's EventEmitter and RxJS Subject do under the hood

class EventEmitter {
  #listeners = new Map();
  
  on(event, callback) {
    if (!this.#listeners.has(event)) {
      this.#listeners.set(event, new Set());
    }
    this.#listeners.get(event).add(callback);
    return () => this.off(event, callback); // Return unsubscribe function
  }
  
  off(event, callback) {
    this.#listeners.get(event)?.delete(callback);
  }
  
  emit(event, ...args) {
    this.#listeners.get(event)?.forEach(cb => cb(...args));
  }
  
  once(event, callback) {
    const wrapper = (...args) => {
      callback(...args);
      this.off(event, wrapper);
    };
    this.on(event, wrapper);
  }

  // Clear all listeners (cleanup — like Angular ngOnDestroy)
  removeAllListeners(event) {
    if (event) {
      this.#listeners.delete(event);
    } else {
      this.#listeners.clear();
    }
  }

  // Get listener count (debugging)
  listenerCount(event) {
    return this.#listeners.get(event)?.size || 0;
  }
}

// Usage:
const bus = new EventEmitter();
const unsub = bus.on("data", (payload) => console.log(payload));

Medium What's the difference between CustomEvent and Event?

Answer: CustomEvent extends Event and adds a detail property for passing data to listeners. With new Event("name") you can only signal that something happened. With new CustomEvent("name", { detail: data }) listeners access the data via e.detail. Both support bubbles/cancelable/composed options.

Hard How would you implement cross-component communication without a framework?

Answer: Three main patterns: (1) Custom Events on document — dispatch from anywhere, listen from anywhere; events bubble so ancestors catch them naturally; good for DOM-based components. Medium Why is it important to unsubscribe from event listeners? How do you prevent memory leaks?

Answer: If a component is destroyed but its listener still references it, the garbage collector can't free that memory. Prevention: (1) Return unsubscribe functions from on() and call them on cleanup. (2) Use WeakRef or WeakMap for listener storage. (3) Use AbortController with addEventListener's signal option: addEventListener("x", fn, { signal: controller.signal }) — then controller.abort() removes all listeners at once. (4) In Angular, unsubscribe in ngOnDestroy or use takeUntilDestroyed().

Multi-Step Form Pattern

// Multi-step form (wizard) — common interview question
class FormWizard {
  #steps;
  #currentStep = 0;
  #data = {};

  constructor(formElement) {
    this.#steps = [...formElement.querySelectorAll("[data-step]")];
    this.showStep(0);
  }

  showStep(index) {
    this.#steps.forEach((step, i) => {
      step.style.display = i === index ? "block" : "none";
    });
    this.#currentStep = index;
  }

  next() {
    if (this.validateCurrentStep()) {
      this.saveStepData();
      this.showStep(this.#currentStep + 1);
    }
  }

  prev() {
    this.showStep(this.#currentStep - 1);
  }

  validateCurrentStep() {
    const step = this.#steps[this.#currentStep];
    const inputs = step.querySelectorAll("input, select, textarea");
    return [...inputs].every(input => input.reportValidity());
  }

  saveStepData() {
    const step = this.#steps[this.#currentStep];
    const formData = new FormData(step.closest("form"));
    for (const [key, value] of formData) {
      this.#data[key] = value;
    }
  }

  getData() { return { ...this.#data }; }
}

function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

    const res = await fetch(`/api/search?q=${encodeURIComponent(query)}`);
    const data = await res.json();
    results.innerHTML = data.map(item =>
      `<div class="result">${item.title}</div>`
    ).join("");
  } catch (err) {
    results.innerHTML = '<div class="error">Search failed</div>';
  }
}, 300);

// (viewport by default). No scroll event listeners needed!

// ─── Creating an IntersectionObserver ─────────────────────

const observer = new IntersectionObserver(callback, options);

// callback receives an array of IntersectionObserverEntry objects
// options configures what "intersection" means

// ─── Options Explained ───────────────────────────────────

const options = {
  root: null,              // null = viewport. Or a specific scrollable element
  rootMargin: "100px 0px", // Expand/shrink the root bounds (CSS margin format)
                           // "100px" = start triggering 100px BEFORE element is visible
  threshold: [0, 0.25, 0.5, 0.75, 1]
  // Array of visibility ratios at which to trigger
  // 0 = as soon as 1px is visible
  // 0.5 = when 50% visible
  // 1 = when 100% visible
  // Multiple values = callback fires at each threshold crossing
};

// ─── Entry Object Properties ─────────────────────────────

const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    entry.target;              // The observed DOM element
    entry.isIntersecting;      // Boolean: is it currently visible?
    entry.intersectionRatio;   // 0-1: how much is visible (0.5 = 50%)
    entry.boundingClientRect;  // Element's position/size
    entry.intersectionRect;    // Visible portion's position/size
    entry.rootBounds;          // Root container bounds
    entry.time;                // Timestamp of the intersection change
  });
});

🎯 Interview Questions

Medium Why is IntersectionObserver better than scroll event listeners for lazy loading?

Answer: Scroll events fire at high frequency (potentially 60+ times/sec), run on the main thread, and require manual throttling/debouncing. IntersectionObserver is async, browser-optimized, batches callbacks, and only fires when intersection state actually changes. It also works for nested scroll containers without extra code, and the browser can optimize the actual intersection checks internally.

Hard What's the difference between IntersectionObserver, MutationObserver, and ResizeObserver?

Answer: IntersectionObserver: watches element VISIBILITY (entering/leaving viewport or a container). MutationObserver: watches DOM CHANGES (children added/removed, attributes modified, text changed). ResizeObserver: watches element SIZE changes (width/height). All three are async and non-blocking. Use intersection for lazy loading/infinite scroll, mutation for detecting third-party DOM changes, resize for responsive components.

Medium How would you implement lazy loading images? Show two approaches.

Answer: (1) Native: <img loading="lazy"> — zero JS, browser handles it, limited control. (2) IntersectionObserver: set images to data-src, observe them, when isIntersecting swap data-src to src, unobserve. Advantages of Observer: control rootMargin (preload distance), add animations, handle error states, works for background images and iframes too.

// SameSite=Strict → CSRF protection (don't send on cross-site requests)
// Secure        → only sent over HTTPS

// ─── Reading Cookies (awkward API!) ──────────────────────

// document.cookie returns ALL cookies as one string: "key1=val1; key2=val2"
const cookies = Object.fromEntries(

// ─── Cookie Security Attributes (CRITICAL for interviews) ─

// HttpOnly — NOT accessible via document.cookie (server-only)
//            Prevents XSS from stealing auth tokens
//            Can ONLY be set by the server (Set-Cookie header)

// Secure — Only sent over HTTPS connections
//          Prevents network sniffing

// SameSite — CSRF protection
//   Strict: Never sent on cross-site requests (safest, may break some flows)
//   Lax:    Sent on top-level navigation GET (default in modern browsers)
//   None:   Always sent (requires Secure flag too — for cross-site cookies)

// Domain — Which domains receive the cookie
//   domain=example.com → sent to example.com AND all subdomains
//   No domain → only exact domain (most restrictive)

// Path — Which URL paths receive the cookie
//   path=/ → all pages
//   path=/admin → only /admin and below

🎯 Interview Questions

Easy What's the difference between localStorage and sessionStorage?

Answer: Same API, different lifetime and scope. localStorage persists forever (until manually cleared) and is shared across all tabs of the same origin. sessionStorage is cleared when the tab closes and is isolated to that specific tab (even same-origin tabs don't share it). Both store only strings (use JSON.stringify/parse for objects).

Hard Where should you store auth tokens? localStorage vs cookies?

Answer: Cookies with HttpOnly+Secure+SameSite are safest for auth tokens. localStorage is accessible by ANY JavaScript on the same origin — if an XSS attack injects a script, it can read all tokens. HttpOnly cookies are invisible to JavaScript (document.cookie can't see them). Best practice: short-lived access tokens in memory (JS variable), refresh tokens in HttpOnly Secure cookies. Never store secrets in localStorage.

Medium How does the 'storage' event enable cross-tab communication?

Answer: When localStorage changes in one tab, the 'storage' event fires in ALL OTHER same-origin tabs (not the tab that made the change). This enables real-time sync: logout in one tab → all tabs detect the token removal and redirect. The event provides: key, oldValue, newValue, url, and storageArea. Only works with localStorage (sessionStorage is tab-isolated).

What is fetch()?

fetch() is the modern browser API for making HTTP requests (replacing XMLHttpRequest). It returns a Promise that resolves to a Response object. It's the foundation of all network communication in frontend JavaScript.

Critical Gotcha: fetch does NOT reject on HTTP errors (404, 500)! It only rejects on network failures (offline, DNS error, CORS block, abort). You MUST check response.ok manually. This is the #1 fetch mistake.

Basic Usage

response.body;       // ReadableStream (for streaming)

Error Handling Patterns

// ─── Comprehensive fetch wrapper ─────────────────────────

async function api(url, options = {}) {
  const { timeout = 10000, retries = 0, ...fetchOptions } = options;

  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      const response = await fetch(url, {
        ...fetchOptions,
        signal: AbortSignal.timeout(timeout)
      });

      if (!response.ok) {
        const error = new Error(`HTTP ${response.status}`);
        error.status = response.status;
        error.response = response;
        throw error;
      }

      const contentType = response.headers.get("content-type");
      if (contentType?.includes("application/json")) {
        return await response.json();
      }
      return await response.text();

    } catch (err) {
      if (err.name === "AbortError") throw err;     // Don't retry timeouts
      if (attempt === retries) throw err;            // Last attempt
      await new Promise(r => setTimeout(r, 1000 * 2 ** attempt)); // Exponential backoff
    }
  }
}

Easy Why does fetch not reject on 404 or 500 errors?

Answer: CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks JavaScript from reading responses from a different origin (protocol + domain + port). It prevents malicious sites from reading your API data using your cookies. The SERVER must send Access-Control-Allow-Origin headers. "Preflight" OPTIONS requests happen for non-simple requests (custom headers, PUT/DELETE). Fixes: server adds CORS headers, or use a proxy (Angular: proxy.conf.json in dev).

JavaScript is single-threaded — heavy computation (image processing, data parsing, complex calculations) blocks the main thread, making the UI freeze. Service Workers act as a network proxy between your app and the server, enabling offline support, caching, and push notifications.

// ─── What Service Workers Do ─────────────────────────────
// They sit BETWEEN your app and the network
// Can intercept ALL fetch requests and decide how to respond:
// - Serve from cache (offline support)
// - Serve from network (online)
// - Serve stale + revalidate in background (fast + fresh)
// - Show offline fallback page

// ─── Lifecycle ───────────────────────────────────────────

// 1. Register → 2. Install → 3. Activate → 4. Idle/Fetch
// Registration (in main.js):
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js")
    .then(reg => console.log("SW registered:", reg.scope))
    .catch(err => console.error("SW registration failed:", err));

// sw.js — Service Worker file
// INSTALL: Pre-cache static assets
self.addEventListener("install", (e) => {
  e.waitUntil(
    caches.open("v1").then(cache => 
      cache.addAll(["/", "/index.html", "/style.css", "/app.js", "/offline.html"])
    )
  );
  self.skipWaiting(); // Activate immediately (don't wait for old SW to die)
});

// ACTIVATE: Clean up old caches
self.addEventListener("activate", (e) => {
  e.waitUntil(
    caches.keys().then(keys => 
      Promise.all(
        keys.filter(key => key !== "v1").map(key => caches.delete(key))
      )
    )
  );
  self.clients.claim(); // Take control of all pages immediately
});

// FETCH: Intercept network requests
self.addEventListener("fetch", (e) => {
  e.respondWith(
    caches.match(e.request).then(cached => {
      // Cache-first strategy: serve cache, fallback to network
      return cached || fetch(e.request).then(response => {
        // Cache the new response for next time
        const clone = response.clone();
        caches.open("v1").then(cache => cache.put(e.request, clone));
        return response;
      });
    }).catch(() => {
      // Network failed AND not in cache → show offline page
      return caches.match("/offline.html");
    })
  );
});

      return cache.match(e.request).then(cached => {
        const fetchPromise = fetch(e.request).then(response => {
          cache.put(e.request, response.clone()); // Update cache

Exercise: Offload heavy computation to a Web Worker:

// Problem: Find all prime numbers up to N (blocks main thread for large N)
// Solution: Move to a worker

// primes-worker.js
self.onmessage = (e) => {
  const max = e.data;
  const primes = [];
  
  for (let n = 2; n <= max; n++) {
    let isPrime = true;
    for (let i = 2; i <= Math.sqrt(n); i++) {
      if (n % i === 0) { isPrime = false; break; }
    }
    if (isPrime) primes.push(n);
    
    // Report progress every 10000 numbers
    if (n % 10000 === 0) {
      self.postMessage({ type: "progress", value: (n / max * 100).toFixed(1) });
    }
  }
  
  self.postMessage({ type: "result", primes });
};

// main.js
const worker = new Worker("primes-worker.js");
worker.postMessage(1000000); // Find primes up to 1 million

worker.onmessage = (e) => {
  if (e.data.type === "progress") {
    document.querySelector("#progress").textContent = `${e.data.value}%`;
  } else if (e.data.type === "result") {
    console.log(`Found ${e.data.primes.length} primes`);
    worker.terminate(); // Clean up
  }
};
// UI stays completely responsive during computation!

🎯 Interview Questions

Hard What's the difference between Web Workers and Service Workers?

Answer: Web Workers: background thread for CPU-heavy tasks, created per page, dies with the page, communicate via postMessage, can't intercept network requests. Service Workers: network proxy between app and server, persists independent of page (lifecycle-based: install→activate→fetch), intercepts ALL fetch requests, enables offline/caching/push notifications, one per scope (shared across tabs). Both have no DOM access.

Medium Why can't Web Workers access the DOM?

Answer: The DOM is not thread-safe — it was designed for single-threaded access. If multiple threads could modify the DOM simultaneously, you'd get race conditions (two threads moving the same element, conflicting style changes). Workers communicate via postMessage which safely copies data between threads. The main thread is the only thread that can touch the DOM.

Expert What are Transferable objects and when would you use them?

Answer: Normally postMessage copies data (structured clone) which is slow for large buffers. Transferable objects (ArrayBuffer, ImageBitmap, OffscreenCanvas) can be TRANSFERRED — ownership moves to the worker with zero-copy (instant, regardless of size). After transfer, the sender can no longer access the data (byteLength becomes 0). Use for: large binary data (images, audio), video frame processing, any case where copying would be too slow.
