HTTP Methods — Purpose, Idempotency, Safety

Every REST API call uses an HTTP method (verb). Knowing the exact semantics — especially idempotency and safety — is essential for design and interviews.

POSTCreate a resource❌ No❌ NoYesCreate user, submit order
PUTReplace entire resource❌ No✅ YesYesFull update of a record

Idempotent = Calling the endpoint N times produces the same result as calling it once. Example: DELETE /users/1 — whether you call it once or 10 times, the user is gone. Safe = The call does not change server state. GET is safe — reading data never modifies it.

🎯 Interview Questions

Easy What is the difference between PUT and PATCH?

Answer: PUT replaces the entire resource — you must send all fields. If you omit a field, it gets set to null/default. PATCH partially updates — only send the fields you want to change. PUT is idempotent by design (same call, same result). PATCH may or may not be idempotent depending on implementation (e.g., "increment count by 1" is not idempotent).

Medium What is the difference between 401 and 403?

Answer: 401 means "I don't know who you are" — missing/invalid authentication credentials. 403 means "I know who you are, but you're not allowed to do this." Example: 401 = no JWT token sent. 403 = valid JWT token, but the user role is "viewer" not "admin." Some APIs return 404 instead of 403 to hide whether a resource exists (security through obscurity).

Medium What does idempotent mean? Which HTTP methods are NOT idempotent?

Answer: An operation is idempotent if calling it N times produces the same result as calling it once. POST is NOT idempotent — calling POST /orders 3 times creates 3 orders. PATCH may not be — depends on the operation. GET, PUT, DELETE, HEAD, OPTIONS are idempotent. This matters for retry logic: safe to retry idempotent requests on timeout, dangerous to retry POST.

Theory: REST Constraints

REST (Representational State Transfer) is an architectural style defined by Roy Fielding in his 2000 PhD thesis. An API is "RESTful" when it satisfies 6 constraints:

  1. Client-Server — Separation of concerns. Client manages UI, server manages data.
  2. Stateless — Each request contains all information needed to process it. Server stores no session state. Enables horizontal scaling.
  3. Cacheable — Responses must define whether they are cacheable. GET responses should be cacheable.
  4. Uniform Interface — Resource identification via URIs, manipulation via representations, self-descriptive messages, HATEOAS.
  5. Layered System — Client can't tell if it's talking directly to a server or a load balancer/proxy/cache.
  6. Code on Demand (optional) — Server can send executable code (e.g., JavaScript) to client.

🎯 Interview Questions

Medium What makes an API "RESTful"? What's the most important constraint?

Answer: The 6 REST constraints. The most important for scalability is Statelessness — each request is self-contained. The server never stores client session state between requests. All context the server needs (auth token, user ID) must be in each request. This enables horizontal scaling — any server in the cluster can handle any request.

Medium How would you version a REST API? What approach do you prefer and why?

Answer: URL path versioning (/api/v1/) is most common and pragmatic — it's explicit, easy to route, visible in logs, and simple to test with curl. Header versioning is cleaner per REST theory but harder to debug. I'd use URL versioning for public APIs and internal microservices both. The rule: never make breaking changes to an existing version; create v2 instead.

3. Building with net/http (Go Stdlib)

📺 YouTube Tutorials
  • net/http Server — Anthony GG
  • Go 1.22 New Router — Alex Edwards

Theory

Go's net/http package is a production-ready HTTP server in the standard library. Unlike Node.js where you need Express, Go's stdlib handles routing (Go 1.22+), middleware, timeouts, and TLS natively. Always learn stdlib before frameworks — frameworks are just wrappers.

Minimal HTTP Server

package main

import (
    "encoding/json"
    "log"
    "net/http"
)

// Always write handlers with this exact signature
func helloHandler(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusOK) // set status BEFORE writing body
    json.NewEncoder(w).Encode(map[string]string{"message": "hello"})
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /api/hello", helloHandler) // Go 1.22+: method in pattern

    server := &http.Server{
        Addr:         ":8080",
        Handler:      mux,
        ReadTimeout:  15 * time.Second,  // ALWAYS set timeouts
        WriteTimeout: 15 * time.Second,
        IdleTimeout:  60 * time.Second,
    }

    log.Println("Server running on :8080")
    log.Fatal(server.ListenAndServe())
}
⚠️ Never use http.ListenAndServe() directly in production: It has no timeouts. A slow client can hold a connection open forever, exhausting your goroutine pool. Always create an http.Server struct with explicit timeout values.

Reading & Writing JSON (The Core Pattern)

type CreateUserRequest struct {
    Name  string `json:"name"`
    Email string `json:"email"`
    Age   int    `json:"age"`
}

type UserResponse struct {
    ID    string `json:"id"`
    Name  string `json:"name"`
    Email string `json:"email"`
}

// Standard handler pattern used in ALL real Go APIs
func createUser(w http.ResponseWriter, r *http.Request) {
    // 1. Limit body size (prevent 1GB attack bodies)
    r.Body = http.MaxBytesReader(w, r.Body, 1_048_576) // 1MB limit

    // 2. Decode JSON body
    var req CreateUserRequest
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields() // reject extra fields (strict mode)
    if err := dec.Decode(&req); err != nil {
        http.Error(w, "invalid JSON: "+err.Error(), http.StatusBadRequest)
        return
    }

    // 3. Validate
    if req.Name == "" {
        http.Error(w, "name is required", http.StatusBadRequest)
        return
    }
    if req.Age < 0 || req.Age > 150 {
        http.Error(w, "age must be between 0 and 150", http.StatusUnprocessableEntity)
        return
    }

    // 4. Business logic (call service layer)
    user, err := userService.Create(r.Context(), req)
    if err != nil {
        log.Printf("create user error: %v", err)
        http.Error(w, "internal server error", http.StatusInternalServerError)
        return
    }

    // 5. Write response
    w.Header().Set("Content-Type", "application/json")
    w.Header().Set("Location", "/api/v1/users/"+user.ID) // 201 best practice
    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode(UserResponse{
        ID: user.ID, Name: user.Name, Email: user.Email,
    })
}

// ─── Helper: write JSON response (use this everywhere) ─────────────
func writeJSON(w http.ResponseWriter, status int, v any) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    if err := json.NewEncoder(w).Encode(v); err != nil {
        log.Printf("writeJSON error: %v", err)
    }
}

🎯 Interview Questions

Medium Why must you call w.WriteHeader() before writing the body?

Answer: HTTP protocol requires status line and headers to be sent before the body. In Go's http.ResponseWriter, the first call to Write() implicitly sends the status line (200) if you haven't called WriteHeader() yet. Once the status is sent, it can't be changed. If you set headers after writing, they're silently ignored. Order: set headers → WriteHeader → write body.

Hard What happens if you don't set timeouts on your HTTP server in Go?

Answer: Without timeouts, a slow client or slow upstream can hold a goroutine and connection open indefinitely. This causes goroutine leaks and eventually exhausts memory. In production, attackers use "slow loris" attacks — sending HTTP headers one byte per second to tie up all connections. ReadTimeout kills connections that take too long to send the request. WriteTimeout kills connections where response writing is too slow. Always set both.

Theory

Chi is a lightweight, idiomatic Go router that builds directly on net/http. It adds: method+path routing, URL parameters, middleware chaining, sub-routers, and route grouping — all with zero external dependencies beyond itself.

Chi Router Setup

package main

import (
    "net/http"
    "github.com/go-chi/chi/v5"
    "github.com/go-chi/chi/v5/middleware"
)

func main() {
    r := chi.NewRouter()

    // ── Global middleware (runs for every request) ──
    r.Use(middleware.RequestID)    // adds X-Request-Id header
    r.Use(middleware.RealIP)       // sets RemoteAddr from X-Forwarded-For
    r.Use(middleware.Logger)       // structured access logs
    r.Use(middleware.Recoverer)    // catches panics, returns 500
    r.Use(middleware.Timeout(60 * time.Second)) // request timeout

    // ── Route groups with shared middleware ──
    r.Route("/api/v1", func(r chi.Router) {
        r.Use(AuthMiddleware) // JWT validation for all /api/v1 routes

        r.Route("/users", func(r chi.Router) {
            r.Get("/", listUsers)           // GET  /api/v1/users
            r.Post("/", createUser)         // POST /api/v1/users

            r.Route("/{userID}", func(r chi.Router) {
                r.Use(LoadUserCtx)          // load user from DB into context
                r.Get("/", getUser)         // GET    /api/v1/users/{userID}
                r.Put("/", updateUser)      // PUT    /api/v1/users/{userID}
                r.Patch("/", patchUser)     // PATCH  /api/v1/users/{userID}
                r.Delete("/", deleteUser)   // DELETE /api/v1/users/{userID}
            })
        })

        r.Route("/applications", func(r chi.Router) {
            r.Get("/", listApplications)
            r.Post("/", createApplication)
            r.Get("/{appID}", getApplication)
            r.Patch("/{appID}", updateApplication)
            r.Delete("/{appID}", deleteApplication)
        })
    })

    http.ListenAndServe(":8080", r)
}

    // ...

type contextKey string
const userKey contextKey = "user"

func LoadUserCtx(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        userID := chi.URLParam(r, "userID")
        user, err := db.GetUser(r.Context(), userID)
        if err != nil {
            http.Error(w, "user not found", http.StatusNotFound)
            return
        }
        ctx := context.WithValue(r.Context(), userKey, user)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

Theory: Consistent Response Envelope

Production APIs use a consistent response envelope so clients know exactly where to find data, errors, and metadata regardless of the endpoint.

Standard Response Envelope

// Standard API response envelope — use this pattern consistently
type APIResponse[T any] struct {
    Data    T           `json:"data,omitempty"`
    Error   *APIError   `json:"error,omitempty"`
    Meta    *Meta       `json:"meta,omitempty"`   // pagination info
}

type APIError struct {
    Code    string `json:"code"`
    Message string `json:"message"`
    Details any    `json:"details,omitempty"` // field-level validation errors
}

type Meta struct {
    Total  int `json:"total"`
    Offset int `json:"offset"`
    Limit  int `json:"limit"`
}

// ─── Success responses ────────────────────────────────
// Single resource:
// { "data": { "id": "1", "name": "John" } }

// List with pagination:
// { "data": [...], "meta": { "total": 100, "offset": 0, "limit": 20 } }

// ─── Error responses ─────────────────────────────────
// { "error": { "code": "VALIDATION_ERROR", "message": "...", "details": {...} } }

// Usage
func writeSuccess[T any](w http.ResponseWriter, status int, data T, meta *Meta) {
    writeJSON(w, status, APIResponse[T]{Data: data, Meta: meta})
}

func writeError(w http.ResponseWriter, status int, code, msg string) {
    writeJSON(w, status, APIResponse[any]{
        Error: &APIError{Code: code, Message: msg},
    })
}

Input Validation Pattern

// Use github.com/go-playground/validator/v10
import "github.com/go-playground/validator/v10"

var validate = validator.New()

type CreateApplicationRequest struct {
    Name        string `json:"name"        validate:"required,min=2,max=100"`
    Description string `json:"description" validate:"omitempty,max=500"`
    Environment string `json:"environment" validate:"required,oneof=dev staging prod"`
    Priority    int    `json:"priority"    validate:"min=1,max=5"`
}

func createApplication(w http.ResponseWriter, r *http.Request) {
    var req CreateApplicationRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "INVALID_JSON", err.Error())
        return
    }

    // Validate struct tags
    if err := validate.Struct(req); err != nil {
        // Convert validation errors to human-readable map
        errors := make(map[string]string)
        for _, e := range err.(validator.ValidationErrors) {
            errors[e.Field()] = e.Tag() + "=" + e.Param()
        }
        writeJSON(w, http.StatusBadRequest, APIResponse[any]{
            Error: &APIError{
                Code:    "VALIDATION_ERROR",
                Message: "request validation failed",
                Details: errors,
            },
        })
        return
    }
    // ... continue with business logic
}

🎯 Interview Questions

Medium How do you handle an unknown JSON field in a Go request body?

Answer: By default, json.Decoder silently ignores unknown fields. To reject them, use dec.DisallowUnknownFields(). This prevents clients from sending garbage data or typos ("naem" instead of "name") that would silently be ignored, making debugging harder. For public APIs, it's better to be permissive (ignore unknowns) for forward compatibility; for strict internal APIs, reject them.

Hard Why should you limit request body size? How do you do it in Go?

Answer: Without a body size limit, a client can send a 10GB request body, buffering it into memory and causing OOM. Use r.Body = http.MaxBytesReader(w, r.Body, 1<<20) (1MB limit). When exceeded, json.Decoder.Decode() returns a *http.MaxBytesError. For file uploads, set a higher limit. This is a basic DoS protection measure.

Theory: The Middleware Pattern

Middleware is a function that wraps an HTTP handler to add cross-cutting behaviour (logging, auth, rate limiting) without touching business logic. In Go, middleware has a single signature: it takes an http.Handler and returns an http.Handler.

// The middleware signature — memorize this
type Middleware func(http.Handler) http.Handler

// Every middleware looks like this:
func MyMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // PRE-processing (runs BEFORE the handler)
        log.Println("Request started:", r.Method, r.URL.Path)

        next.ServeHTTP(w, r) // call the next handler in the chain

        // POST-processing (runs AFTER the handler)
        log.Println("Request finished")
    })
}

// Chaining multiple middleware (manual, without Chi)
handler := LoggingMiddleware(AuthMiddleware(RateLimitMiddleware(myHandler)))
// Execution order: Logging → Auth → RateLimit → myHandler → RateLimit → Auth → Logging

func CORSMiddleware(next http.Handler) http.Handler {

// ─── 4. Recovery (Panic Handler) Middleware ───────────────────────
func Recovery(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                // Log the stack trace
                buf := make([]byte, 2048)
                n := runtime.Stack(buf, false)
                slog.Error("panic recovered",
                    "error", err,
                    "stack", string(buf[:n]),
                )
                http.Error(w, "internal server error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

🎯 Interview Questions

Medium How does Go middleware work? Why does order matter?

Answer: Middleware wraps handlers in a chain. Each middleware calls next.ServeHTTP(w, r) to pass to the next link. Order matters because each middleware runs both before AND after the next. Logging middleware should be outermost (runs first, captures total time). Auth middleware should run before business logic but after logging (so you log unauthorized attempts). Recovery should be outermost of all (catches panics from all other middleware).

Hard What is the difference between CORS simple request and preflight request?

Answer: A simple request (GET/POST with standard headers) doesn't trigger preflight — the browser sends it directly and checks CORS headers in the response. A preflight is an OPTIONS request the browser sends first to check if the actual request is allowed (required for custom headers like Authorization, non-simple methods like DELETE, or cross-origin POSTs with JSON). If your server doesn't handle OPTIONS with correct CORS headers, the browser blocks the actual request. Always handle OPTIONS in your router.

Theory

Go has no exceptions. Errors are values. For REST APIs, you need a disciplined error strategy that translates internal Go errors into appropriate HTTP responses without leaking internal details to clients.

Domain Error → HTTP Status Mapping

// Define domain-level errors — never expose DB/internal errors to client
type AppError struct {
    Code    string // machine-readable code: "USER_NOT_FOUND"
    Message string // human-readable message for clients
    Status  int    // HTTP status code
    Err     error  // wrapped internal error (for logging only, NOT sent to client)
}

func (e *AppError) Error() string { return e.Message }
func (e *AppError) Unwrap() error { return e.Err }

// Sentinel constructors
func ErrNotFound(resource, id string) *AppError {
    return &AppError{
        Code:    "NOT_FOUND",
        Message: fmt.Sprintf("%s with id %s not found", resource, id),
        Status:  http.StatusNotFound,
    }
}
func ErrConflict(msg string) *AppError {
    return &AppError{Code: "CONFLICT", Message: msg, Status: http.StatusConflict}
}
func ErrValidation(msg string) *AppError {
    return &AppError{Code: "VALIDATION_ERROR", Message: msg, Status: http.StatusBadRequest}
}
func ErrForbidden(msg string) *AppError {
    return &AppError{Code: "FORBIDDEN", Message: msg, Status: http.StatusForbidden}
}
func ErrInternal(err error) *AppError {
    return &AppError{
        Code:    "INTERNAL_ERROR",
        Message: "an unexpected error occurred",
        Status:  http.StatusInternalServerError,
        Err:     err, // logged server-side, NOT returned to client
    }
}

// Central error handler — use in every handler
func handleError(w http.ResponseWriter, err error) {
    var appErr *AppError
    if errors.As(err, &appErr) {
        if appErr.Err != nil {
            slog.Error("application error", "internal_error", appErr.Err)
        }
        writeJSON(w, appErr.Status, map[string]any{
            "error": map[string]string{
                "code":    appErr.Code,
                "message": appErr.Message,
            },
        })
        return
    }
    // Unknown error — log full details, return generic message
    slog.Error("unexpected error", "error", err)
    writeJSON(w, http.StatusInternalServerError, map[string]any{
        "error": map[string]string{
            "code":    "INTERNAL_ERROR",
            "message": "an unexpected error occurred",
        },
    })
}

// Usage in a handler:
func getUser(w http.ResponseWriter, r *http.Request) {
    id := chi.URLParam(r, "id")
    user, err := svc.GetUser(r.Context(), id)
    if err != nil {
        handleError(w, err) // one line handles everything
        return
    }
    writeJSON(w, http.StatusOK, user)
}
⚠️ NEVER do this: http.Error(w, err.Error(), 500) — this leaks internal error messages (DB connection strings, file paths, stack traces) to the client. Always log the internal error server-side and return a generic message to the client.

🎯 Interview Questions

Hard How do you prevent leaking internal errors to API clients?

Answer: Define a domain error type with both an internal error (for logging) and a public message (for clients). Use errors.As() to check if an error is a domain error. If yes, use its public message and status code. If it's an unknown error type, log the full details and return a generic "internal server error" message. Never use err.Error() directly in HTTP responses — it may contain DB queries, file paths, or stack traces.

Medium When should you use 422 vs 400?

Answer: 400 (Bad Request) = the request is malformed — unparseable JSON, wrong content-type, missing required headers. 422 (Unprocessable Entity) = the request is syntactically valid but semantically wrong — the JSON parsed fine, but a field value violates a business rule (negative price, start date after end date, invalid enum value). Some APIs use 400 for both; using both is more precise for clients.

type PaginationParams struct {
    Offset int `json:"offset"`
    Limit  int `json:"limit"`
}

func parsePagination(r *http.Request) (PaginationParams, error) {
    offsetStr := r.URL.Query().Get("offset")
    limitStr  := r.URL.Query().Get("limit")
    
    offset := 0
    if offsetStr != "" {
        var err error
        offset, err = strconv.Atoi(offsetStr)
        if err != nil || offset < 0 {
            return PaginationParams{}, fmt.Errorf("invalid offset parameter")
        }
    }
    
    limit := 20 // default
    if limitStr != "" {
        var err error
        limit, err = strconv.Atoi(limitStr)
        if err != nil || limit <= 0 {
            return PaginationParams{}, fmt.Errorf("invalid limit parameter")
        }
        if limit > 100 { limit = 100 } // cap maximum
    }
    
    return PaginationParams{Offset: offset, Limit: limit}, nil
}

// Response with pagination metadata
type PaginatedResponse[T any] struct {
    Data   []T  `json:"data"`
    Total  int  `json:"total"`
    Offset int  `json:"offset"`
    Limit  int  `json:"limit"`
    HasMore bool `json:"has_more"`
}

type ApplicationFilter struct {

func parseFilter(r *http.Request) (ApplicationFilter, error) {
    f := ApplicationFilter{
        Name:   r.URL.Query().Get("name"),
        Status: r.URL.Query().Get("status"),
        Sort:   r.URL.Query().Get("sort"),
        Order:  r.URL.Query().Get("order"),
    }
    
    // Validate sort field against allowlist (CRITICAL — prevents SQL injection)
    allowedSort := map[string]bool{"name": true, "created_at": true, "updated_at": true}
    if f.Sort != "" && !allowedSort[f.Sort] {
        return ApplicationFilter{}, fmt.Errorf("invalid sort field: %s", f.Sort)
    }
    
    // Validate order direction
    if f.Order != "" && f.Order != "asc" && f.Order != "desc" {
        return ApplicationFilter{}, fmt.Errorf("order must be asc or desc")
    }
    if f.Order == "" { f.Order = "asc" }
    
    return f, nil
}

🎯 Interview Questions

Hard Why is offset pagination slow at large page numbers? How does cursor-based pagination solve this?

Answer: With LIMIT 20 OFFSET 100000, the database must scan and discard 100,000 rows before returning your 20. Even with indexes, this is O(n) in offset size. Cursor-based uses WHERE id > last_seen_id LIMIT 20 — the DB can use the index to jump directly to the cursor position and return the next 20 rows in O(log n). At offset=0 they're identical; at offset=1,000,000 the difference can be 1000x. Cursor pagination also handles insertions/deletions between pages gracefully — offset pagination skips rows or shows duplicates when data changes.

10. JWT Authentication Middleware

📺 YouTube Tutorials
  • JWT Auth in Go — Anthony GG
  • JWT REST API Complete — TechSchool

Theory

JWT (JSON Web Token) is the standard auth mechanism for REST APIs. A JWT is a base64-encoded, signed string containing claims (user ID, roles, expiry). The server validates the signature — no DB lookup needed on every request.

JWT Structure

// JWT = Header.Payload.Signature
// Example: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.signature

// Header (base64 decoded):
{ "alg": "HS256", "typ": "JWT" }

// Payload/Claims (base64 decoded):
{
  "sub": "user-uuid-here",      // subject (user ID)
  "email": "user@example.com",
  "role": "admin",
  "iat": 1719792000,            // issued at (Unix timestamp)
  "exp": 1719795600             // expires at (issued + 1 hour)
}

// Signature = HMAC-SHA256(base64(header) + "." + base64(payload), secret_key)

JWT Middleware in Go

import "github.com/golang-jwt/jwt/v5"

type Claims struct {
    UserID string `json:"sub"`
    Email  string `json:"email"`
    Role   string `json:"role"`
    jwt.RegisteredClaims
}

type contextKey string
const claimsKey contextKey = "claims"

func JWTMiddleware(secretKey []byte) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            // 1. Extract token from Authorization header
            authHeader := r.Header.Get("Authorization")
            if authHeader == "" {
                writeError(w, http.StatusUnauthorized, "MISSING_TOKEN", "authorization header required")
                return
            }
            
            parts := strings.SplitN(authHeader, " ", 2)
            if len(parts) != 2 || parts[0] != "Bearer" {
                writeError(w, http.StatusUnauthorized, "INVALID_TOKEN_FORMAT", "use Bearer ")
                return
            }
            tokenStr := parts[1]
            
            // 2. Parse & validate token
            var claims Claims
            token, err := jwt.ParseWithClaims(tokenStr, &claims, func(t *jwt.Token) (any, error) {
                // CRITICAL: validate the signing method
                if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
                    return nil, fmt.Errorf("unexpected signing method: %v", t.Header["alg"])
                }
                return secretKey, nil
            })
            
            if err != nil || !token.Valid {
                writeError(w, http.StatusUnauthorized, "INVALID_TOKEN", "token is invalid or expired")
                return
            }
            
            // 3. Store claims in context for downstream handlers
            ctx := context.WithValue(r.Context(), claimsKey, &claims)
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}

// Helper to extract claims in handlers
func ClaimsFromContext(ctx context.Context) *Claims {
    c, _ := ctx.Value(claimsKey).(*Claims)
    return c
}

// Role-based authorization middleware
func RequireRole(role string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            claims := ClaimsFromContext(r.Context())
            if claims == nil || claims.Role != role {
                writeError(w, http.StatusForbidden, "FORBIDDEN", "insufficient permissions")
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}

// Usage with Chi:
r.Route("/api/v1/admin", func(r chi.Router) {
    r.Use(JWTMiddleware(secretKey))
    r.Use(RequireRole("admin"))
    r.Get("/users", listAllUsers)

🎯 Interview Questions

Medium How does JWT work? What's in the payload?

Answer: JWT = 3 base64-encoded parts: Header (algorithm), Payload (claims: user ID, roles, expiry), Signature (HMAC of header+payload with server secret). Server validates the signature without any DB lookup — if the signature is valid and the token hasn't expired, the user is authenticated. Claims should include: sub (user ID), iat (issued at), exp (expiry). Never put passwords or sensitive data in JWT — it's base64 encoded, not encrypted.

Hard Why must you validate the signing algorithm in JWT middleware?

Answer: This is a critical security vulnerability. An attacker can forge a JWT by changing the header algorithm to "alg": "none" — some naive JWT libraries accept unsigned tokens if not explicitly checked. Also, an RS256 public key attack: if your code accepts both HS256 and RS256, an attacker can sign with the public key using HS256. Always use jwt.ParseWithClaims with a KeyFunc that explicitly rejects unexpected algorithms: if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok { return nil, error }.

Expert What are the security considerations of storing JWT in localStorage vs cookies?

Answer: localStorage: Vulnerable to XSS — any JavaScript injected into your app can read it. Simple to implement. HttpOnly cookie: Immune to XSS — JavaScript can't read HttpOnly cookies. But vulnerable to CSRF — another site can make requests with your cookies. Mitigate CSRF with SameSite=Strict cookies or CSRF tokens. Best practice for AI/SaaS apps: Store access token in memory (JavaScript variable), use HttpOnly cookie for refresh token. This limits XSS exposure (access token expires quickly) while protecting the long-lived refresh token from XSS.

    body := OpenAIRequest{
        Model:    "gpt-4o",
        Messages: []Message{{Role: "user", Content: prompt}},
    }

    bodyBytes, err := json.Marshal(body)
    if err != nil {
        return nil, fmt.Errorf("marshal request: %w", err)
    }

    // Create request WITH context — ctx carries timeout + cancellation
    req, err := http.NewRequestWithContext(ctx, http.MethodPost,
        "https://api.openai.com/v1/chat/completions",
        bytes.NewReader(bodyBytes),
    )
    if err != nil {
        return nil, fmt.Errorf("create request: %w", err)
    }

    req.Header.Set("Content-Type", "application/json")
    req.Header.Set("Authorization", "Bearer "+os.Getenv("OPENAI_API_KEY"))

    resp, err := apiClient.Do(req)
    if err != nil {
        // Distinguish timeout from other errors
        if errors.Is(err, context.DeadlineExceeded) {
            return nil, fmt.Errorf("openai timeout: %w", err)
        }
        return nil, fmt.Errorf("openai request failed: %w", err)
    }
    defer resp.Body.Close() // ALWAYS close body — prevents connection leak

    // Read with size limit (LLM responses can be large but not infinite)
    limitedBody := io.LimitReader(resp.Body, 10<<20) // 10MB max

    if resp.StatusCode != http.StatusOK {
        var errBody map[string]any
        json.NewDecoder(limitedBody).Decode(&errBody)
        return nil, fmt.Errorf("openai error %d: %v", resp.StatusCode, errBody)
    }

    var result OpenAIResponse
    if err := json.NewDecoder(limitedBody).Decode(&result); err != nil {
        return nil, fmt.Errorf("decode response: %w", err)
    }

    return &result, nil
}

🎯 Interview Questions

Medium Why should you never use http.DefaultClient in production?

Answer: http.DefaultClient has no timeout — a slow or unresponsive server will hang your goroutine forever, eventually exhausting the goroutine pool. Always create a custom &http.Client{Timeout: 30 * time.Second}. Also, the default transport has low MaxIdleConnsPerHost (2), which is too low for high-throughput services. Hard How do you test code that makes HTTP calls to external services?

Answer: Three approaches: (1) httptest.NewServer — spin up a real local HTTP server in your test, inject its URL into your client. Full fidelity, tests real HTTP. (2) Interface abstraction — define an HTTPDoer interface with Do(*http.Request) (*http.Response, error); mock it in tests. (3) testify/mock + RoundTripper — implement a custom http.RoundTripper that returns preset responses. Always use approach 1 or 2 for unit tests; use real API in integration tests with a separate environment.

Complete SSE Implementation

// ─── SSE Handler — streams LLM tokens to browser ─────────────────

type ChatRequest struct {
    Message string `json:"message" validate:"required"`
}

func (h *ChatHandler) StreamChat(w http.ResponseWriter, r *http.Request) {
    // 1. Parse request body
    var req ChatRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        http.Error(w, "invalid JSON", http.StatusBadRequest)
        return
    }

    // 2. Check browser supports SSE (optional but good practice)
    if r.Header.Get("Accept") != "" && 
       !strings.Contains(r.Header.Get("Accept"), "text/event-stream") {
        http.Error(w, "client must accept text/event-stream", http.StatusNotAcceptable)
        return
    }

    // 3. Get the Flusher interface — MUST check this
    flusher, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "streaming not supported", http.StatusInternalServerError)
        return
    }

    // 4. Set SSE headers — ORDER MATTERS: headers before WriteHeader
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    w.Header().Set("X-Accel-Buffering", "no") // disable nginx response buffering
    w.Header().Set("Access-Control-Allow-Origin", "*") // CORS for SSE

    // 5. Start LLM call in a goroutine, send tokens on channel
    tokenChan := make(chan string, 10) // buffered to avoid blocking LLM goroutine
    errChan   := make(chan error, 1)

    go func() {
        defer close(tokenChan)
        err := h.llmClient.StreamCompletion(r.Context(), req.Message, tokenChan)
        if err != nil {
            errChan <- err
        }
    }()

    // 6. SSE write loop — runs on main goroutine
    for {
        select {
        case token, ok := <-tokenChan:
            if !ok {
                // Channel closed — stream ended normally
                fmt.Fprintf(w, "data: [DONE]\n\n") // final event
                flusher.Flush()
                return
            }
            // SSE event format: "data: \n\n"
            // For structured data, use JSON in data field
            payload, _ := json.Marshal(map[string]string{"token": token})
            fmt.Fprintf(w, "data: %s\n\n", payload)
            flusher.Flush() // push to client immediately

        case err := <-errChan:
            // Send error as SSE event
            errPayload, _ := json.Marshal(map[string]string{
                "error": err.Error(),
            })
            fmt.Fprintf(w, "event: error\ndata: %s\n\n", errPayload)
            flusher.Flush()
            return

        case <-r.Context().Done():
            // Client disconnected (closed browser tab / navigated away)
            slog.Info("SSE client disconnected", "path", r.URL.Path)
            return // goroutine and LLM call cancelled via r.Context()
        }
    }
}

// Allowed MIME types — allowlist, not blocklist
var allowedMIMETypes = map[string]bool{
    "application/pdf":  true,
    "image/jpeg":       true,
    "image/png":        true,
    "audio/mpeg":       true,  // mp3
    "audio/wav":        true,
    "text/plain":       true,
}

const (
    maxUploadSize = 50 << 20  // 50MB
    maxMemory     = 10 << 20  // 10MB held in memory; rest spills to temp disk
)

func (h *FileHandler) UploadDocument(w http.ResponseWriter, r *http.Request) {
    // 1. Limit total request size BEFORE parsing
    r.Body = http.MaxBytesReader(w, r.Body, maxUploadSize)

    // 2. Parse multipart form (uses temp files for large uploads)
    if err := r.ParseMultipartForm(maxMemory); err != nil {
        if strings.Contains(err.Error(), "too large") {
            writeError(w, http.StatusRequestEntityTooLarge, "FILE_TOO_LARGE",
                fmt.Sprintf("file must be under %dMB", maxUploadSize>>20))
            return
        }
        writeError(w, http.StatusBadRequest, "INVALID_FORM", err.Error())
        return
    }
    defer r.MultipartForm.RemoveAll() // clean up temp files

    // 3. Get the file from the form field named "file"
    file, header, err := r.FormFile("file")
    if err != nil {
        writeError(w, http.StatusBadRequest, "MISSING_FILE", "field 'file' required")
        return
    }
    defer file.Close()

    // 4. Validate MIME type by reading file magic bytes
    //    (NEVER trust r.Header.Get("Content-Type") or file extension alone — trivially faked)
    buf := make([]byte, 512)
    n, _ := file.Read(buf)
    mimeType := http.DetectContentType(buf[:n])

    if !allowedMIMETypes[mimeType] {
        writeError(w, http.StatusUnsupportedMediaType, "INVALID_FILE_TYPE",
            fmt.Sprintf("file type %s not allowed", mimeType))
        return
    }

    // 5. Reset file position after reading magic bytes
    if seeker, ok := file.(io.Seeker); ok {
        seeker.Seek(0, io.SeekStart)
    }

    // 6. Generate a unique storage key (never use the original filename directly!)
    ext := filepath.Ext(header.Filename)
    storageKey := fmt.Sprintf("uploads/%s/%s%s",
        userIDFromContext(r.Context()),
        uuid.New().String(),
        ext,
    )

    // 7. Stream to S3 (don't read entire file into []byte)
    uploadResult, err := h.s3Client.PutObject(r.Context(), &s3.PutObjectInput{
        Bucket:      aws.String(h.bucket),
        Key:         aws.String(storageKey),
        Body:        file,             // io.Reader — streams directly
        ContentType: aws.String(mimeType),
        ContentLength: aws.Int64(header.Size),
        // Server-side encryption
        ServerSideEncryption: types.ServerSideEncryptionAes256,
    })
    if err != nil {
        slog.Error("s3 upload failed", "error", err, "key", storageKey)
        writeError(w, http.StatusInternalServerError, "UPLOAD_FAILED", "storage error")
        return
    }

    // 8. Persist metadata to DB and queue ingestion job
    doc := Document{
        ID:          uuid.New().String(),
        UserID:      userIDFromContext(r.Context()),
        Filename:    header.Filename,
        StorageKey:  storageKey,
        ContentType: mimeType,
        SizeBytes:   header.Size,
        Status:      "pending",
    }
    if err := h.docRepo.Create(r.Context(), doc); err != nil {
        writeError(w, http.StatusInternalServerError, "DB_ERROR", "failed to save document")
        return
    }

    // 9. Queue async ingestion job
    if err := h.queue.Enqueue(r.Context(), "ingest_document", doc.ID); err != nil {
        slog.Error("failed to queue ingestion", "docID", doc.ID, "error", err)
        // Don't fail the upload — job can be retried later
    }

    // 10. Return 202 Accepted (async processing)
    writeJSON(w, http.StatusAccepted, map[string]string{
        "document_id": doc.ID,
        "status":      "processing",
        "message":     "document uploaded, ingestion started",
    })
}

16. Graceful Shutdown & Health Checks

📺 YouTube Tutorials

Theory

In K8s, pods receive SIGTERM before being terminated (scaling down, deployment update). Without graceful shutdown, in-flight requests are cut mid-response — breaking active AI streams. Graceful shutdown: stop accepting new connections, finish current requests, then exit.

Complete Graceful Shutdown

func main() {
    r := chi.NewRouter()
    // ... add routes
    
    // Health endpoints — register BEFORE the server starts
    r.Get("/health", healthHandler)
    r.Get("/ready", readinessHandler)
    r.Get("/live", livenessHandler)

    server := &http.Server{
        Addr:         ":8080",
        Handler:      r,
        ReadTimeout:  15 * time.Second,
        WriteTimeout: 60 * time.Second, // higher for SSE streaming endpoints
        IdleTimeout:  120 * time.Second,
    }

    // Start server in goroutine (non-blocking)
    go func() {
        slog.Info("server started", "addr", server.Addr)
        if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            slog.Error("server error", "error", err)
            os.Exit(1)
        }
    }()

    // Block until OS signal received
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM) // Ctrl+C and K8s kill
    sig := <-quit

    slog.Info("shutdown signal received", "signal", sig)

    // Give in-flight requests time to complete (K8s waits terminationGracePeriodSeconds)
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    if err := server.Shutdown(shutdownCtx); err != nil {
        slog.Error("forced shutdown", "error", err)
        os.Exit(1)
    }

    // Clean up other resources
    db.Close()
    redisClient.Close()
    slog.Info("server shut down cleanly")
}

🎯 Interview Questions

Medium What's the difference between liveness and readiness probes in K8s?

Answer: Liveness: "Is this container alive?" — if it fails, K8s kills and restarts the pod. Use a lightweight check (no DB ping — you don't want K8s restarting a healthy pod just because DB is temporarily down). Readiness: "Is this container ready to serve traffic?" — if it fails, K8s removes the pod from the load balancer but doesn't restart it. Use for dependency checks (DB, Redis). During startup, readiness prevents traffic hitting a pod that hasn't loaded its config yet. During DB maintenance, readiness marks pods as not-ready, routing traffic to healthy pods.

  • slog Structured Logging — Flo Woelki

Theory

In microservices, a single user action triggers requests across multiple services. Without a trace ID attached to every log line, debugging is impossible. A Request ID (also called Correlation ID or Trace ID) is a UUID generated at the gateway and passed through the entire call chain via headers and context.

Request ID Middleware + Logger Setup

// ─── Request ID Middleware ────────────────────────────────────────
const requestIDHeader = "X-Request-ID"
type requestIDKey struct{}

func RequestIDMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // Use client-provided ID (from upstream), or generate a new one
        requestID := r.Header.Get(requestIDHeader)
        if requestID == "" {
            requestID = uuid.New().String()
        }

        // Echo back so client can correlate their request
        w.Header().Set(requestIDHeader, requestID)

        // Store in context for handlers and downstream HTTP calls
        ctx := context.WithValue(r.Context(), requestIDKey{}, requestID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func RequestIDFromContext(ctx context.Context) string {
    id, _ := ctx.Value(requestIDKey{}).(string)
    return id
}

// ─── Structured Logger with Request ID ───────────────────────────
func RequestLogger(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        ww := wrapResponseWriter(w)

        next.ServeHTTP(ww, r)

        requestID := RequestIDFromContext(r.Context())
        slog.Info("http request",
            "request_id", requestID,
            "method",     r.Method,
            "path",       r.URL.Path,
            "query",      r.URL.RawQuery,
            "status",     ww.Status(),
            "duration_ms", time.Since(start).Milliseconds(),
            "ip",         r.RemoteAddr,
            "user_agent", r.UserAgent(),
        )
    })
}

// ─── Propagate Request ID to outgoing HTTP calls ──────────────────
func callDownstreamService(ctx context.Context, url string) (*http.Response, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return nil, err
    }

    // Forward request ID to downstream — this is how you trace across services
    if requestID := RequestIDFromContext(ctx); requestID != "" {
        req.Header.Set(requestIDHeader, requestID)
    }

    return apiClient.Do(req)
}

// ─── Handler: use request-scoped logger ──────────────────────────
func createApplication(w http.ResponseWriter, r *http.Request) {
    requestID := RequestIDFromContext(r.Context())
    log := slog.With("request_id", requestID, "handler", "createApplication")

    var req CreateApplicationRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        log.Warn("invalid request body", "error", err)
        writeError(w, http.StatusBadRequest, "INVALID_JSON", err.Error())
        return
    }

    app, err := appSvc.Create(r.Context(), req)
    if err != nil {
        log.Error("failed to create application", "error", err) // has request_id automatically
        handleError(w, err)
        return
    }

    log.Info("application created", "app_id", app.ID)
    writeJSON(w, http.StatusCreated, app)
}

Theory: 3-Layer Architecture

Clean architecture separates your code into 3 layers with strict rules: each layer only depends on the layer below it. This makes every layer independently testable and replaceable.

19. Webhooks — Receiving & Verifying

📺 YouTube Tutorials
  • Webhook Signature Verification in Go

Theory

Webhooks are HTTP callbacks — external services (GitHub, Stripe, Slack) call your API when events happen. You cannot use JWT auth for webhooks (you don't control the caller). Instead, senders include an HMAC signature in a header — you verify it to confirm the request is genuine and hasn't been tampered with.

Webhook Handler with HMAC Verification

// ─── GitHub webhook example (works same way for Stripe, Slack, etc.) ─────

func (h *WebhookHandler) HandleGitHubEvent(w http.ResponseWriter, r *http.Request) {
    // 1. Read the ENTIRE body first (needed for signature verification)
    body, err := io.ReadAll(io.LimitReader(r.Body, 1<<20)) // 1MB limit
    if err != nil {
        http.Error(w, "failed to read body", http.StatusBadRequest)
        return
    }

    // 2. Verify HMAC-SHA256 signature
    // GitHub sends: X-Hub-Signature-256: sha256=
    sigHeader := r.Header.Get("X-Hub-Signature-256")
    if sigHeader == "" {
        http.Error(w, "missing signature", http.StatusUnauthorized)
        return
    }

    if !verifyHMACSignature(body, sigHeader, h.webhookSecret) {
        http.Error(w, "invalid signature", http.StatusUnauthorized)
        return
    }

    // 3. Parse event type
    eventType := r.Header.Get("X-GitHub-Event")

    // 4. Respond 200 FAST (within 5s) — queue for async processing
    // Webhook providers retry on non-200 or timeout
    w.WriteHeader(http.StatusOK)

    // 5. Process asynchronously
    go h.processEvent(context.Background(), eventType, body)
}

func verifyHMACSignature(body []byte, sigHeader, secret string) bool {
    // Strip "sha256=" prefix
    parts := strings.SplitN(sigHeader, "=", 2)
    if len(parts) != 2 || parts[0] != "sha256" {
        return false
    }
    receivedSig, err := hex.DecodeString(parts[1])
    if err != nil {
        return false
    }

    // Compute expected HMAC
    mac := hmac.New(sha256.New, []byte(secret))
    mac.Write(body)
    expected := mac.Sum(nil)

    // Use constant-time comparison to prevent timing attacks
    return hmac.Equal(receivedSig, expected)
}

Hard How do you secure webhook endpoints? Why can't you use JWT?

Answer: You can't use JWT because you don't control the webhook sender (GitHub, Stripe, etc.) — they don't have your users' JWT tokens. Instead: (1) HMAC signature — you share a secret with the provider; they sign the payload with HMAC-SHA256 and include it in a header; you verify it. (2) IP allowlisting — only accept requests from the provider's published IP ranges (fragile, IPs change). (3) Replay attack prevention — check the timestamp in the signature header and reject requests older than 5 minutes (prevents captured webhooks from being replayed later). Always use constant-time comparison (hmac.Equal) to prevent timing attacks.

HTTP & REST Fundamentals

🎯 Core Questions

Easy What are the HTTP methods? Which are safe and which are idempotent?

Answer: GET (safe + idempotent), HEAD (safe + idempotent), OPTIONS (safe + idempotent), DELETE (idempotent, not safe), PUT (idempotent, not safe), POST (neither), PATCH (depends on implementation).

Easy What is the difference between authentication and authorization?

Answer: Authentication = "Who are you?" — verifying identity (login with JWT). Authorization = "What are you allowed to do?" — checking permissions (role-based access). Authentication happens first; authorization requires a valid identity.

Medium What is CORS and why does it exist?

Answer: Cross-Origin Resource Sharing. Browsers block cross-origin requests by default (Same-Origin Policy) to prevent malicious websites from making requests to other sites using your credentials. CORS is the server's way of relaxing this — by setting Access-Control-Allow-Origin, the server says "I allow this other origin to read my responses." Without it, your Angular app on localhost:4200 can't call your Go API on localhost:8080. Preflight (OPTIONS) checks permission before the actual request.

Medium What is idempotency key and when do you need it?

Answer: For non-idempotent POST operations (like payment processing), clients include a unique Idempotency-Key: uuid header. The server stores the result of the first request keyed by that UUID. If the client retries (due to timeout), the server returns the stored result instead of processing again. This makes POST effectively idempotent — prevents double charges or duplicate orders. Critical for payment APIs and any "create" operation where retrying has side effects.

Hard How would you design rate limiting for an AI API endpoint where different users have different limits?

Answer: Use a token bucket algorithm stored in Redis, keyed by user ID (not IP — IPs change). Each user has a bucket with capacity = their plan's limit (e.g., free: 10 req/min, pro: 100 req/min). On each request: get bucket from Redis, try to consume a token (WATCH + MULTI/EXEC for atomicity or Lua script), return 429 with Retry-After header if empty. For AI specifically, rate limit by tokens not requests (a 10-token prompt and a 10,000-token response have very different costs). Store token usage in Redis with a sliding window: INCRBY user:123:tokens {tokens_used}; EXPIRE user:123:tokens 60.

Hard How do you handle versioning when you have breaking changes in a REST API?

Answer: Never remove or change v1 endpoints — create v2. Run both versions simultaneously with separate route groups. Deprecate v1 by adding a Deprecation header and announcement. After a sunset period (e.g., 6-12 months with advance notice), shut down v1. For additive changes (new fields, new endpoints), no new version needed. Breaking changes: field removal, type change, semantic meaning change, auth requirement change — these require a new version. Internally, v1 and v2 handlers can share the same service layer; only the transport representation differs.

Hard Explain the OWASP Top 10 vulnerabilities relevant to a Go REST API.

Answer: Key ones: (1) Broken Access Control — missing auth checks on endpoints, check authorization per resource not just per role. (2) Injection — use parameterized queries (sqlc/pgx) not string concatenation; validate/sanitize inputs. (3) Security Misconfiguration — set timeouts, disable debug endpoints in prod, use TLS. (4) Broken Authentication — validate JWT algorithm, short expiry, token rotation. (5) Security Logging failures — log all auth attempts. (6) For AI APIs specifically: prompt injection — user inputs manipulating your system prompt, sanitize and validate before sending to LLM.

🎯 Go Implementation Questions

Medium How do you gracefully shut down a Go HTTP server?

Answer: Use server.Shutdown(ctx) which stops accepting new connections and waits for in-flight requests to complete before closing. Pattern: listen for os.Signal (SIGTERM, SIGINT) in a goroutine, call Shutdown when signal received. Pass a context with timeout so if requests don't finish in 30 seconds, they're forcibly closed. This is essential in K8s where pods receive SIGTERM on scale-down — without graceful shutdown, active AI streaming responses are cut mid-stream.

Medium What is the http.Handler interface? What's the difference between http.Handler and http.HandlerFunc?

Answer: http.Handler is an interface: type Handler interface { ServeHTTP(ResponseWriter, *Request) }. Any type implementing this method is an HTTP handler. http.HandlerFunc is a function type that implements the Handler interface: type HandlerFunc func(ResponseWriter, *Request) — its ServeHTTP just calls itself. This is the adapter pattern — it lets you use a plain function as an http.Handler without creating a struct.

Hard How do you share data between middleware and handler in Go without using global variables?

Answer: Use context.WithValue(). Middleware stores data in the request context: ctx := context.WithValue(r.Context(), key, value); next.ServeHTTP(w, r.WithContext(ctx)). Handler retrieves it: value := r.Context().Value(key). Best practices: use a private type for context keys (not string) to prevent collisions — type ctxKey string; const userIDKey ctxKey = "userID". Only store request-scoped data: auth claims, request ID, loaded resources. Never store mutable shared state in context.

Hard How would you implement streaming LLM responses from a Go server to a browser?

Answer: Use Server-Sent Events (SSE). Set headers: Content-Type: text/event-stream, Cache-Control: no-cache, X-Accel-Buffering: no (disables nginx buffering). Get the flusher: flusher, ok := w.(http.Flusher). In a goroutine, receive tokens from the LLM streaming channel and write: fmt.Fprintf(w, "data: %s\n\n", token); flusher.Flush(). On context cancellation (user closed browser), stop the LLM call. Use select { case token := <-tokenChan: ...; case <-r.Context().Done(): return }. Send a final data: [DONE]\n\n event. This is how ChatGPT's streaming works.
