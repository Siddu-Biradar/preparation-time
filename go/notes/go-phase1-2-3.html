    1. Variables, Types & Zero Values

    📺 YouTube Tutorials
    • Go Variables & Types — NerdCademy
    • Zero Values Explained — Golang Dojo

    Theory

    Go is statically typed — every variable has a fixed type known at compile time. Unlike JavaScript, you cannot reassign a different type to the same variable. Every declared variable has a zero value — Go never leaves memory uninitialised.

    🧠 Why Static Typing? The Design Philosophy

    Go's designers came from C and C++, where type bugs cause security vulnerabilities and production crashes. They chose static typing for three concrete reasons:

    1. Compiler catches bugs before runtime. If you pass a string where an int is expected, Go refuses to compile. In JavaScript or Python, that bug lives until the exact line executes in production. In a backend service handling thousands of requests, a type error discovered at compile time costs 0 seconds of downtime; discovered in production it costs user trust.

    2. Code is self-documenting. When you read func GetUser(id string) (*User, error) you immediately know: this function takes a string ID and returns either a User pointer or an error. No runtime guessing. This matters enormously in large codebases with multiple engineers.

    3. IDE tooling becomes powerful. Static types enable autocomplete, refactoring, and "find all usages" to work correctly. Go's tooling (gopls) can tell you exactly every place a type is used across your entire codebase.

    🔍 Why Zero Values? The Safety Principle

    In C, an uninitialised variable holds whatever garbage was in that memory location — a notorious source of security bugs and crashes. Go eliminated this entire class of bugs: every variable is always initialised.

    The zero value isn't just a default — it's designed to be useful. A sync.Mutex with its zero value is immediately ready to use (no constructor needed). A var count int is immediately safe to increment. A var buf bytes.Buffer can be written to immediately. This "zero value usability" is a deliberate API design goal in the Go standard library.

    Real-world impact: You never write if user == undefined or if list != null for nil pointer checks the way you do in other languages — Go's zero values make structs and slices predictably safe to use immediately after declaration.

    ✅ When to Use var vs :=

    Use := inside functions for brevity — it's the 90% case. Use var when: (1) at package level (outside functions, where := is not allowed), (2) you need an explicit type that differs from what would be inferred (var timeout time.Duration = 5 * time.Second), (3) you want a nil slice or nil pointer explicitly (var items []string gives nil, not empty), or (4) declaring multiple variables in a block for readability.

    🎯 Interview Questions

    Easy What is a zero value in Go? Why does it matter?

    Answer: Every variable in Go is initialised to its zero value when declared without an explicit value: 0 for numbers, "" for strings, false for bools, nil for pointers/slices/maps/channels/interfaces. This means Go programs never have uninitialised memory. It matters because you can declare a var count int and safely call count++ without initialising it first. A var mu sync.Mutex is immediately usable. Reduces bugs from forgotten initialisations.

    Medium What is the difference between var x int and x := 0?

    Answer: Both declare an int variable with value 0. Differences: (1) := can only be used inside functions; var works at package level too. (2) := infers the type; var x int is explicit. (3) := must have at least one new variable on the left side. Style: use := inside functions for brevity; use var when type must be explicit (e.g., var b []byte to get a nil slice, not b := []byte{} which is non-nil).

    Medium What is the difference between a nil slice and an empty slice?

    Answer: var s []int → nil slice: s == nil is true, len(s) == 0. s := []int{} or make([]int, 0) → empty slice: s == nil is false, len(s) == 0. Both are safe to range over and append to. Difference matters in JSON: nil slice marshals as null, empty slice marshals as []. Use nil slice when "no data" and empty slice when "empty collection exists."

    2. Functions, Multiple Returns & Closures

    📺 YouTube Tutorials
    • Go Functions Deep Dive — Golang Dojo
    • Closures in Go — Anthony GG

    Theory

    Functions are first-class values in Go — they can be assigned to variables, passed as arguments, and returned from other functions. Go's signature feature is multiple return values, which enables the idiomatic value, err pattern without exceptions.

    🧠 Why First-Class Functions?

    In languages without first-class functions, to customise behaviour you need objects, classes, and strategy patterns. In Go, you just pass a function. This enables an enormous range of patterns with minimal ceremony:

    Middleware: An HTTP middleware is just a function that takes a handler and returns a handler — func(http.Handler) http.Handler. No class hierarchy needed. Callbacks: Sorting with a custom comparator — slices.SortFunc(users, func(a, b User) int { return strings.Compare(a.Name, b.Name) }). Factories: A function that returns a function — creates specialised versions with captured configuration.

    🔍 How Closures Actually Capture Variables

    A closure is a function bundled together with references to its surrounding scope. The key insight: closures capture the variable itself, not its value at creation time. This is why the classic loop-goroutine bug occurs: all goroutines share a reference to the same i variable, not copies of it.

    When a function "closes over" a variable, that variable is moved from the stack to the heap so it can outlive the enclosing function. The garbage collector keeps it alive as long as the closure is reachable. This is why closures enable patterns like counters, memoisation, and generators — the captured variable persists between calls.

    🔍 Why Multiple Return Values Instead of Exceptions?

    Go's designers studied the problems with exceptions in Java and C++: (1) exceptions create hidden control flow paths — any line can throw and exit your function unexpectedly, (2) in Java, checked exceptions pollute every function signature, (3) developers habitually write empty catch blocks, silently swallowing errors. Multiple return values force explicit handling — you must deal with the error or consciously choose to ignore it. Every failure mode in a function is visible in its signature.

    ✅ When to Use Each Function Pattern

    Named functions: the default — testable, reusable, has a clear name in stack traces. Anonymous functions: short callbacks or goroutine launchers where naming adds no value. Closures: when the function needs state that persists across calls (counter, cache, rate limiter). Named returns: only in very short functions (<5 lines) where they clearly improve readability — avoid in long functions where naked returns hide what's being returned.

// Multiple return values — the idiom

    🎯 Interview Questions

    Medium What is a closure? Give a real-world use case.

    Answer: A closure is a function that captures (closes over) variables from its surrounding scope. The function and the captured variables form a "closed" unit. Real-world uses: (1) HTTP middleware — a closure captures config/dependencies and wraps a handler. (2) Memoisation — a closure captures a cache map. (3) Counters/accumulators — a closure captures a running total. (4) Callbacks that need access to outer state.

    Hard What happens when multiple goroutines close over the same loop variable?

    Answer: Before Go 1.22, loop variables were shared across iterations — all goroutines would capture the same memory address, and by the time they run, the loop is done and the variable holds its final value. Fix: pass the variable as a function argument (creates a copy) or assign to a local variable inside the loop body. Go 1.22 changed this — each loop iteration now has its own variable, so the bug no longer applies in newer code.

    3. Control Flow — if, for, switch, range

    📺 YouTube Tutorials
    • Control Flow in Go — NerdCademy

    Theory

    Go has no while or do-while — only for. No ternary operator. No break needed in switch cases. These simplifications reduce cognitive load.

    🧠 Why Only One Loop Keyword?

    Go's designers made a deliberate choice: when there are multiple ways to express the same thing, beginners spend time deciding which to use and code reviewers spend time arguing about consistency. By having only for, there is one right answer for every looping situation. A for with only a condition is a while loop. A for {} is an infinite loop. The simplicity is intentional.

    Similarly, Go has no ternary operator (condition ? a : b) because it leads to hard-to-read nested expressions. Go's style: explicit if/else is always clear. Same with switch — no automatic fallthrough means each case is completely independent and less error-prone than C's switch.

    🔍 How range Actually Works

    When you write for i, v := range slice, Go evaluates the slice expression once before the loop begins and captures the length at that moment. Adding elements to the slice inside the loop does not change how many iterations happen. The variable v is a copy of the element — modifying v does NOT modify the original slice element. To modify in place, use slice[i].

    For maps, range iterates in a randomised order intentionally (the Go runtime adds randomness to prevent hash-collision attacks and to prevent code from accidentally depending on map iteration order — since map order is implementation-defined and can change). For strings, range decodes UTF-8 runes, so the index advances by 1-4 bytes per iteration, not always by 1.

    ✅ When to Use if init-statement

    if err := doSomething(); err != nil scopes err to just the if block. Use this when the variable is only needed for the check — it prevents err from polluting the outer scope. This is the most idiomatic Go pattern and appears in virtually every production codebase.

    // ── if — can have an init statement ──────────────────────────────
if err := doSomething(); err != nil {
    return err
    // `err` scoped to this if block only — idiomatic Go
}

// ── for — only loop keyword in Go ────────────────────────────────
// C-style
for i := 0; i < 10; i++ { fmt.Println(i) }

// While-style
for condition { ... }

// Infinite loop
for { ... }  // break when done

// Range over slice
for i, v := range []int{1,2,3} {
    fmt.Println(i, v)   // i=index, v=copy of value
}
for _, v := range slice { ... }  // ignore index
for i := range slice   { ... }  // ignore value

// Range over map (random order!)
for k, v := range myMap { fmt.Println(k, v) }

// Range over string → iterates RUNES (Unicode code points), not bytes!
for i, r := range "héllo" {
    fmt.Printf("%d: %c (%d)\n", i, r, r)
    // i = byte position (not rune position!), r = rune
}

// ── switch — no fallthrough by default ───────────────────────────
switch x {
case 1, 2:       fmt.Println("one or two")
case 3:          fmt.Println("three")
default:         fmt.Println("other")
}

// Switch with init

case v > 0:      fmt.Println("small")
default:         fmt.Println("non-positive")
}

    switch v := i.(type) {
    case int:     return fmt.Sprintf("int: %d", v)

    default:      return fmt.Sprintf("unknown: %T", v)

    🎯 Interview Questions

    Easy Does Go have a while loop?

    Answer: No. Go has only for. It acts as a while loop when used with just a condition: for condition { }. Infinite loop: for { } with a break or return inside. This is intentional — fewer loop keywords means fewer ways to write the same thing.

    Medium What does range over a string iterate over — bytes or characters?

    Answer: Runes (Unicode code points), not bytes. The index is the byte offset, not the rune index. For a string like "héllo", the é is 2 bytes (UTF-8), so the next character has index 3, not 2. To iterate bytes: for i := 0; i < len(s); i++ { b := s[i] }. len(s) always returns byte count, not rune count. Use utf8.RuneCountInString(s) for rune count.

    4. defer, panic & recover

    📺 YouTube Tutorials
    • defer Explained — Anthony GG
    • Defer, Panic, Recover — Official Go Blog

    Theory

    defer schedules a function call to run when the surrounding function returns. Arguments to the deferred function are evaluated immediately (at the defer statement), not when it runs. Multiple defers run in LIFO (Last In, First Out) order.

    🧠 Why LIFO Order? Why Does defer Exist?

    The purpose of defer is resource cleanup. Without it, every early return requires duplicating the cleanup code. With defer, you write cleanup once, immediately after acquiring the resource, and it runs no matter how the function exits — normal return, early return, or panic.

    LIFO order mirrors how resources are typically acquired: you open A, then B, then C. When closing, you must close C first (it may depend on B), then B (may depend on A), then A. Defers are pushed onto a stack — the last deferred call runs first — which naturally implements the correct teardown order.

    Real-world example: In a database transaction, you begin a transaction, defer a rollback, then do work, then explicitly commit. If the commit succeeds, the rollback is still called but does nothing (since the transaction is already committed). If any step fails and you return early, the defer automatically rolls back. This pattern makes your cleanup logic impossible to forget.

    🔍 How defer Works Internally

    When the Go compiler encounters a defer statement, it adds the function call to a per-goroutine defer chain (a linked list of deferred calls on the goroutine's stack). When the function returns — for any reason — the runtime walks this chain in reverse order and executes each deferred call.

    Arguments are evaluated at the defer line and stored in the defer record. This is why defer fmt.Println(x) prints the value of x at the defer line, not its value when the function returns. To capture the latest value, use a closure: defer func() { fmt.Println(x) }() — the closure captures the variable by reference.

    🔍 panic vs error — When to Use Each

    Use error return for: any expected failure — file not found, network timeout, invalid input, DB constraint violation. These are normal operating conditions your callers should handle.

    Use panic for: programming errors that should never happen in correctly written code — nil pointer dereference, index out of bounds, invariant violations. The rule: if a caller can trigger this condition by passing bad input, use an error. If it can only be triggered by a bug in your own code, panic is acceptable. In production, panic should be caught at the HTTP handler level by a recovery middleware and converted to a 500 response — never let a panic crash your entire server.

    ✅ When to Use defer

    Always defer: file.Close(), rows.Close(), mutex.Unlock(), span.End(), cancel() after context creation, wg.Done(). Don't use defer: inside tight loops (it adds overhead per iteration, and defers inside loops accumulate but only execute when the function returns — not when the loop iteration ends), or when you need to check the return value of Close (use explicit close and check the error).

    // ── defer: LIFO order ─────────────────────────────────────────────
func example() {
    defer fmt.Println("third")  // runs last
    defer fmt.Println("second")
    defer fmt.Println("first")  // runs first (LIFO)
    fmt.Println("executing")
}
// Output: executing → first → second → third

// ── defer: argument evaluated at defer time ───────────────────────
func deferArg() {
    x := 5
    defer fmt.Println(x) // captures x=5 NOW, not when it runs
    x = 10
    // prints 5, not 10
}

// ── defer: resource cleanup (ALWAYS do this) ─────────────────────
func readFile(path string) ([]byte, error) {
    f, err := os.Open(path)
    if err != nil { return nil, err }
    defer f.Close()          // guaranteed to run, even on early return
    return io.ReadAll(f)
}

func queryDB(ctx context.Context) {
    rows, err := db.QueryContext(ctx, "SELECT ...")
    if err != nil { return }
    defer rows.Close()       // ALWAYS defer rows.Close() after checking err
    for rows.Next() { ... }
}

// ── panic: for truly unrecoverable errors ────────────────────────
// panic stops normal execution, runs deferred functions, then crashes
// Use ONLY for: programming errors (nil dereference, out-of-bounds)
// NEVER use panic for expected errors (use error return instead)
func mustParse(s string) int {
    n, err := strconv.Atoi(s)
    if err != nil { panic(fmt.Sprintf("mustParse: invalid input %q", s)) }
    return n
}

// ── recover: catch panics ─────────────────────────────────────────
// MUST be called inside a deferred function to have any effect
func safeExecute(fn func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered panic: %v", r)
        }
    }()
    fn()
    return nil
}

// HTTP middleware pattern using recover (most common use case)
func Recovery(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                log.Printf("panic: %v\n%s", err, debug.Stack())
                http.Error(w, "internal server error", 500)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

    🎯 Interview Questions

    Medium When are deferred function arguments evaluated?

    Answer: Arguments are evaluated immediately when the defer statement is executed, not when the deferred function runs. Example: defer fmt.Println(x) captures the value of x at that line. If x changes later, the deferred call still uses the original value. Exception: if the argument is a function call that itself returns a value, that function is called at defer-time. To capture the "latest" value, use a closure: defer func() { fmt.Println(x) }() — the closure references x by address, so it sees the latest value.

    Hard Can recover() catch a panic from another goroutine?

    Answer: No. recover() only catches panics from the same goroutine. A panic in goroutine A cannot be caught by a deferred recover() in goroutine B. Each goroutine must have its own recovery mechanism. This is a common pitfall: if you launch a goroutine that panics without its own recover, the entire program crashes. Always add a deferred recover to goroutines that run user-provided code or call external APIs.

    Hard Explain the performance implications of defer.

    Answer: In early Go versions, defer had a ~200ns overhead per call (heap allocation for the defer record). Go 1.14 introduced "open-coded defers" — for simple cases (≤8 defers, no loops), defers are compiled inline with zero overhead. Defers inside loops still allocate. Rule of thumb: don't avoid defer for correctness reasons — the overhead is usually negligible. Only avoid in ultra-hot paths (tight loops called millions of times per second).

    5. Arrays, Slices & Maps — Internals

    📺 YouTube Tutorials
    • Slices Explained (gotchas!) — Golang Dojo
    • Slices: Usage & Internals — Official Go Blog
    • Maps in Go — Anthony GG

    Theory

    A slice is a three-word header: pointer to array, length, capacity. Multiple slices can share the same underlying array — mutations through one slice affect the other.

    🧠 Why Slices Exist (Instead of Just Arrays)

    Arrays in Go are fixed size — once declared as [3]int, they can never grow. They're also value types — passing an array to a function copies all its elements. For a 10,000-element array, that's 10,000 copies on every function call. Slices solve both problems: they're dynamically-sized views into an underlying array, and passing a slice copies only the 3-word header (24 bytes on 64-bit systems), regardless of how many elements the slice contains.

    🔍 The 3-Word Header — Step by Step

    Every slice is a struct with exactly 3 fields:

    • ptr — a pointer to the first element in the backing array
    • len — the number of elements you can currently access (s[0] through s[len-1])
    • cap — the total number of elements in the backing array from ptr's position onward

    When you write s := make([]int, 3, 5): a backing array of 5 integers is allocated, the pointer points to the first, len=3 (you can access 3), cap=5 (room for 5 without reallocation). When you call append(s, 4) and len < cap, no new allocation happens — Go just increments len and writes to the backing array. When len == cap, Go allocates a new, larger backing array (roughly 2x), copies all elements, and returns a new slice header pointing to the new array.

    The aliasing consequence: s2 := s[1:3] creates a new header pointing into the same backing array. Mutating s2[0] mutates s[1]. This is efficient (no copy) but dangerous if you don't expect it. After an append that triggers reallocation, the new slice no longer shares memory — they're independent.

    🔍 How Maps Work Internally

    A Go map is a hash table: keys are hashed to determine which bucket they belong to. Each bucket holds a small array of key-value pairs. Lookup is O(1) average — hash the key, go to the bucket, scan the small array. Collisions are handled by chaining overflow buckets.

    Map iteration order is deliberately randomised per-run (Go adds a random seed at program startup). This prevents code from accidentally relying on hash order — which can change between Go versions and CPU architectures. It also prevents hash-flooding attacks where an attacker crafts inputs that all hash to the same bucket, degrading performance to O(n).

    Maps are NOT safe for concurrent access. Two goroutines writing to the same map — or one writing while another reads — is a data race. Go will detect this and panic at runtime (it added a concurrent map access detector). Use sync.RWMutex or sync.Map for concurrent access.

    ✅ When to Pre-size

    If you know the approximate number of elements, pre-size with make([]T, 0, n) for slices and make(map[K]V, n) for maps. This reduces reallocations during growth. For slices, append amortises to O(1) per element, but each reallocation copies all previous elements — if you know you'll add 10,000 elements, pre-size to 10,000.

    // ── Arrays — fixed size, value type ──────────────────────────────
var a [3]int           // [0, 0, 0]
b := [3]int{1, 2, 3}
c := [...]int{4,5,6}   // compiler counts elements
// arrays are COPIED on assignment (value semantics)
x := b
x[0] = 99              // b[0] is still 1

// ── Slice internals ───────────────────────────────────────────────
// A slice header: { ptr *T, len int, cap int }
s := make([]int, 3, 5) // len=3, cap=5
// s[0..2] are accessible; s[3..4] exist in backing array but not accessible yet

s2 := s[1:3]           // shares backing array! len=2, cap=4
s2[0] = 99             // ALSO changes s[1]!

// ── Append — may or may not allocate ─────────────────────────────
// If len < cap: appends to existing array, returns same backing array
// If len == cap: allocates NEW backing array (2x growth), no aliasing
s = append(s, 10)      // safe — always use the returned slice

// ── Common gotchas ────────────────────────────────────────────────
// 1. Slice of slice shares memory
original := []int{1,2,3,4,5}
sub := original[1:3]     // shares memory!
sub = append(sub, 99)    // if cap allows, overwrites original[3]!

// Safe: use full slice expression to limit capacity
sub2 := original[1:3:3]  // cap = 3-1 = 2; append will always allocate new array

// 2. Modifying slice elements vs replacing slice
func badAppend(s []int) {
    s = append(s, 99)  // s is a copy of the header — caller's slice unchanged
}
func goodAppend(s *[]int) {
    *s = append(*s, 99) // modify through pointer
}

// ── Maps ─────────────────────────────────────────────────────────
m := make(map[string]int)     // initialised, ready to use
m2 := map[string]int{         // map literal
    "alice": 25,
    "bob":   30,
}

// Read with comma-ok to distinguish missing key from zero value
val, ok := m["key"]
if !ok { fmt.Println("key not found") }

// Delete
delete(m, "key")

// Iterate (order is RANDOM — by design)
for k, v := range m { fmt.Println(k, v) }

// CRITICAL: Never write to a nil map
var bad map[string]int
bad["key"] = 1   // panic: assignment to entry in nil map

// Maps are NOT safe for concurrent use
// Use sync.Map or protect with sync.Mutex
    ⚠️ 3 Critical Slice Gotchas for Interviews:
    1. Slice aliases share memory until append triggers a new allocation
    2. Passing a slice to a function copies the header (ptr/len/cap), not the data — the function can mutate elements but not grow the caller's slice
    3. len(m) on map = number of keys; not pre-allocatable (use make(map[K]V, hint) for performance)

    🎯 Interview Questions

    Hard Explain the internal structure of a slice. What happens when you append beyond capacity?

    Answer: A slice header is a 3-field struct: { ptr *T, len int, cap int }. ptr points to the first element in the backing array. When append is called and len == cap, Go allocates a new backing array (typically 2x the old capacity for small slices, less for large ones), copies all elements to the new array, and returns a new slice header pointing to the new array. The old array is left for GC. This means after a capacity-exceeding append, the new slice no longer shares memory with any previous slice pointing to the old array.

    Medium What is the zero value of a map and what happens if you read/write to it?

    Answer: The zero value of a map is nil. Reading from a nil map is safe — it returns the zero value of the value type (same as if the key was absent). Writing to a nil map causes a panic: "assignment to entry in nil map." Always initialise maps with make() or a map literal before writing.

    6. Structs, Methods & Composition

    📺 YouTube Tutorials
    • Structs & Methods — Golang Dojo
    • Struct Embedding / Composition — Anthony GG

    Theory

    Go has no classes. Behaviour is attached to types via methods. Inheritance is replaced by embedding (composition). Struct tags control JSON/DB serialisation.

    🧠 Why No Classes? Go's Composition Philosophy

    Classical inheritance creates tight coupling between parent and child classes — change the parent and you risk breaking all subclasses. Deep inheritance hierarchies become notoriously hard to understand and modify. The Go designers, having worked on large C++ and Java codebases, deliberately excluded inheritance. Instead, they chose composition: build complex types by combining simpler ones.

    This aligns with a principle from "Effective Java" and "Design Patterns": favour composition over inheritance. Go just makes that the only option. Embedding promotes fields and methods without the "is-a" relationship — it's purely syntactic convenience for delegation.

    🔍 Pointer Receiver vs Value Receiver — The 5 Rules

    This is asked in nearly every Go interview. Here are the rules, in priority order:

    Rule 1: If the method mutates the receiver, use a pointer receiver. func (u *User) SetEmail(e string) — only pointer receivers can modify the original. Value receivers work on a copy.

    Rule 2: If the struct contains a sync primitive (Mutex, WaitGroup), always use pointer receivers — copying a Mutex breaks it. go vet will catch this.

    Rule 3: If the struct is large, use pointer receiver to avoid copying on every method call (performance).

    Rule 4: Be consistent. If any method on a type uses a pointer receiver, all methods should use pointer receivers. Mixed pointer/value receivers confuse which method set satisfies an interface.

    Rule 5: Interface satisfaction requires matching receivers. If io.Writer needs Write, and your type implements Write with a pointer receiver, only *YourType satisfies the interface — YourType (value) does not.

    🔍 Struct Tags — Purpose and Purpose

    Struct tags are string metadata attached to fields, read at runtime via reflection. They're used by: encoding/json (controls JSON field names and omitempty), database/sql and ORMs (maps struct fields to DB columns), validation libraries (validate:"required,email"), and XML/YAML decoders. They have no effect on the compiled binary size — they're stripped in production binaries. The format is key:"value" with multiple tags space-separated.

    ✅ When to Use Anonymous Structs

    Anonymous structs (struct{ Name string; Age int }{}) are useful for: test case definitions (table-driven tests), one-off API response shapes, JSON decoding of external APIs where you don't want a named type, and configuration objects in main.go. They communicate "this type is only used here" — don't make it globally visible.

    // ── Struct definition ─────────────────────────────────────────────
type User struct {
    ID        string    `json:"id"         db:"id"`
    Name      string    `json:"name"       db:"name"`
    Email     string    `json:"email"      db:"email"`
    CreatedAt time.Time `json:"created_at" db:"created_at"`
    password  string    // unexported — not in JSON, not accessible outside package
}

// ── Value receiver vs Pointer receiver ───────────────────────────
// Value receiver: works on a COPY — safe for read-only, immutable types
func (u User) String() string {
    return fmt.Sprintf("%s <%s>", u.Name, u.Email)
}

// Pointer receiver: works on the ORIGINAL — use when:
// 1. You need to mutate the receiver
// 2. The struct is large (avoids copying)
// 3. The type has a mutex (must be passed by pointer)
func (u *User) SetEmail(email string) {
    u.Email = email  // mutates original
}

// RULE: Be consistent — if ANY method has a pointer receiver,
// ALL methods should have pointer receivers

// ── Embedding (composition, not inheritance) ──────────────────────
type Admin struct {
    User           // embedded — promotes User's methods and fields
    Permissions []string
}

a := Admin{User: User{Name: "Alice"}, Permissions: []string{"read", "write"}}
fmt.Println(a.Name)     // promoted from User — no need for a.User.Name
fmt.Println(a.String()) // promoted method from User

// Embedding with interface implementation
type Logger struct { prefix string }
func (l Logger) Log(msg string) { fmt.Printf("[%s] %s\n", l.prefix, msg) }

type Service struct {
    Logger                 // Service now has a Log() method
    db *sql.DB
}

// ── Anonymous struct (for tests, one-off types) ───────────────────
config := struct {
    Host string
    Port int
}{"localhost", 8080}

// ── Struct tags ───────────────────────────────────────────────────
type APIRequest struct {
    Name  string `json:"name"            validate:"required,min=2"`
    Email string `json:"email"           validate:"required,email"`
    Age   int    `json:"age,omitempty"`  // omit if zero value
}

    🎯 Interview Questions

    Hard When should you use a pointer receiver vs a value receiver?

    Answer: Use a pointer receiver when: (1) the method mutates the receiver, (2) the struct is large (copying is expensive), (3) the struct contains a mutex or other synchronisation primitive (must never be copied), (4) you want to allow the method to be called on a nil receiver. Use a value receiver when: the method is read-only AND the struct is small. Key rule: be consistent — if a type has any pointer receiver method, all its methods should be pointer receivers, because the method set differs (pointer type has all methods; value type has only value receiver methods).

    Medium What is struct embedding? Is it inheritance?

    Answer: Struct embedding includes one struct inside another, promoting the inner type's fields and methods to the outer type's method set. It is not inheritance — there's no polymorphism, no "is-a" relationship, no virtual dispatch. It's syntactic sugar for composition. The embedded type is still a distinct field (you can access it as outer.Inner). If both types have a method with the same name, the outer type's method takes precedence (shadowing).

    7. Interfaces — The Go Way

    📺 YouTube Tutorials
    • Interfaces Explained — Anthony GG
    • Accept interfaces, return structs — Flo Woelki

    Theory

    Interfaces in Go are implicitly satisfied — no implements keyword. If a type has all the methods an interface requires, it implements that interface automatically. This enables loose coupling without explicit declaration.

    🧠 Why Implicit Satisfaction? The Design Decision

    In Java, you declare class File implements Writer. This means: (1) you must know about the interface at the time you write the class, (2) if Writer is defined in a third-party package, you can't make File implement it without modifying File, (3) the class is tightly coupled to the interface definition.

    Go's approach — structural typing — means any type that happens to have the right methods automatically satisfies the interface. os.File satisfies io.Writer because it has a Write([]byte)(int,error) method. The io package and os package don't need to know about each other. You can define your own interfaces that existing types already satisfy — without modifying those types. This is why Go is so composable.

    🔍 How Interface Values Work Internally (2-word pair)

    An interface value is a pair of two pointers: { type *itab, value unsafe.Pointer }. The type (itab) points to a structure containing the concrete type information and a table of method pointers. The value points to the actual data (or contains it inline for small values).

    A nil interface means both pointers are nil. A "typed nil" is when the type pointer is set (pointing to, say, *MyError) but the value pointer is nil. This is why (*MyError)(nil) != nil as an error interface — the interface pair is {*MyError, nil}, which is NOT the zero interface {nil, nil}. This is Go's most notorious gotcha.

    🔍 Go Proverbs on Interfaces

    • "The bigger the interface, the weaker the abstraction." — Rob Pike. Small, focused interfaces (1–2 methods) are more widely satisfied and more useful. io.Reader has 1 method — thousands of types satisfy it. A 20-method interface is barely better than using the concrete type directly.
    • "Accept interfaces, return structs." Functions that accept interfaces are flexible (accept any implementation). Functions that return concrete structs give callers full access to all methods without type assertions.
    • "Don't design interfaces, discover them." Define interfaces where you need them (at the call site), not upfront. Let the real usage patterns reveal what abstraction is actually needed.

    ✅ When to Define an Interface

    Define an interface when: (1) you have two or more concrete types that share behaviour and you want to write code that works with either, (2) you need to mock a dependency for testing (the most common reason), (3) you're designing a plugin system where implementations come from outside your codebase. Don't define an interface for every struct upfront — in Go, interfaces emerge from usage, not from design documents.

    // ── Interface definition ──────────────────────────────────────────
type Writer interface {
    Write(p []byte) (n int, err error)
}

type Stringer interface {
    String() string
}

// Compose interfaces from smaller interfaces
type ReadWriter interface {
    io.Reader  // embedded interface
    io.Writer
}

// ── Implicit satisfaction ─────────────────────────────────────────
type File struct { name string }
func (f *File) Write(p []byte) (int, error) { /* ... */ return len(p), nil }
// *File now satisfies io.Writer — no declaration needed

var w io.Writer = &File{} // valid because *File has Write method

// ── The typed nil trap (CRITICAL interview topic) ─────────────────
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func getError() error {
    var err *MyError = nil      // typed nil pointer
    return err                  // BUG: returns non-nil interface!
}

err := getError()
fmt.Println(err == nil) // FALSE — interface has a type even though value is nil

// Interface value = { type, value }
// nil interface = { nil, nil } → err == nil is true
// typed nil  = { *MyError, nil } → err == nil is FALSE

// ── Fix: always return untyped nil ───────────────────────────────
func getErrorFixed() error {
    var err *MyError = nil
    if err == nil { return nil } // return untyped nil
    return err
}

// WRONG: large interface that forces mocking every method

    // ... 20 more methods

    🎯 Interview Questions

    Hard Explain the typed nil interface bug. How do you avoid it?

    Answer: An interface value has two components: a dynamic type and a dynamic value. A nil interface means both are nil. A "typed nil" is an interface where the type is set but the value is nil pointer. When a function returns *MyError(nil) as an error, the interface's type field is *MyError — so the interface is not nil even though the underlying pointer is. Fix: always return the interface type directly as nil (not a typed nil pointer). Use if somePointer == nil { return nil } before assigning to the interface return type.

    Medium What is the empty interface any / interface{}? When should you use it?

    Answer: any (alias for interface{}) is an interface with zero methods — every type satisfies it. Use it sparingly: for container types that must hold any value (like JSON decoding into map[string]any), for functions like fmt.Println that accept any type, or when you have no choice. Avoid it in domain logic — lose type safety and need type assertions at runtime. Go 1.18+ generics are often a better alternative: instead of func Process(v any), use func Process[T any](v T).

    8. Error Handling — Idiomatic Go

    📺 YouTube Tutorials
    • Error Handling in Go — Anthony GG
    • Working with Errors in Go 1.13 — Official Blog

    Theory

    Go has no exceptions. Errors are values — functions return (T, error) and callers check explicitly. This forces you to think about every failure mode.

    🧠 Why Errors as Values? Problems with Exceptions

    Go's designers observed several problems with exception-based error handling in Java, C++, and Python:

    Hidden control flow. In Java, any method can throw. When you write user.save(), you don't know if it throws unless you check the documentation or source code. With Go's user, err := save(ctx), the error is right there in the function signature — impossible to miss.

    Ignored errors. In Java, checked exceptions are so verbose that developers write empty catch blocks. In Python, many developers don't check return values. In Go, if you don't use the err return value, the compiler warns you (with linters). The explicit pattern makes ignoring errors a conscious, visible decision.

    Exception overhead. Throwing an exception unwinds the call stack, which is expensive. Go error values are just values — returning and checking them has zero overhead beyond the normal return path.

    The Go philosophy: errors are expected, predictable outcomes. A file might not exist. A network might timeout. A user might not be found. These aren't "exceptional" — they're normal operating conditions. Treat them as values, handle them explicitly.

    🔍 How Error Wrapping Creates a Chain

    Before Go 1.13, you had to choose: return the original error (losing context) or create a new error string (losing the original). With fmt.Errorf("context: %w", err), you do both: the new error's message includes context, and errors.Unwrap() lets you access the original. This creates a chain:

    // Error chain: HTTP handler error
//   └─ service error
//       └─ repository error
//           └─ postgres error (pgconn.PgError)
err = fmt.Errorf("handler: %w",
    fmt.Errorf("service: %w",
        fmt.Errorf("repository: %w", pgErr)))

    errors.Is(err, pgErr) traverses the entire chain. errors.As(err, &target) traverses the chain and extracts the first matching type. This means your top-level handler can check the root cause without knowing the intermediate wrapping layers.

    ✅ When to Use Each Error Pattern

    Sentinel errors (var ErrNotFound = errors.New("not found")): when callers need to check for a specific condition with errors.Is. Keep the set small — too many sentinels become an API burden. Custom error types (type ValidationError struct{}): when callers need structured data from the error (field name, status code, retry info). Wrapped errors (fmt.Errorf("%w")): almost always — add context at every layer crossing. panic: only for programmer errors that represent bugs, never for expected conditions.

    // ── The error interface ───────────────────────────────────────────
type error interface {
    Error() string
}

// ── Sentinel errors (simple, comparable) ─────────────────────────
var ErrNotFound  = errors.New("not found")
var ErrForbidden = errors.New("forbidden")

// Check with ==
if err == ErrNotFound { /* ... */ }
// Better: use errors.Is (works through wrapping chain)
if errors.Is(err, ErrNotFound) { /* ... */ }

// ── Custom error types ────────────────────────────────────────────
type ValidationError struct {
    Field   string
    Message string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation error: %s — %s", e.Field, e.Message)
}

// Wrap to add context while preserving original error
func getUser(id string) (*User, error) {
    user, err := db.QueryUser(id)
    if err != nil {
        return nil, fmt.Errorf("getUser %s: %w", id, err)  // %w wraps!
    }
    return user, nil
}

errors.Is(err, ErrNotFound) // true — unwraps chain until found

// errors.As: extracts a specific error type from the chain

if errors.As(err, &valErr) {
    fmt.Println("field:", valErr.Field)  // access typed fields
}

// ── Wrapping with %w ──────────────────────────────────────────────
// ALWAYS wrap errors with context when crossing package boundaries
func processRequest(r *Request) error {
    if err := validate(r); err != nil {
        return fmt.Errorf("processRequest: %w", err) // add callsite context
    }
    if err := save(r); err != nil {
        return fmt.Errorf("processRequest: save: %w", err)
    }
    return nil
}

// ── Don't wrap when you're the origin ────────────────────────────
// Wrong: return fmt.Errorf("error: %w", errors.New("not found"))
// Right: return fmt.Errorf("getUser: %w", ErrNotFound)

// ── Sentinel pattern for Go 1.13+ ────────────────────────────────
// In packages, define typed errors — callers use errors.As to check
// Don't export error strings — export error types or sentinels

    🎯 Interview Questions

    Medium What is the difference between errors.Is and errors.As?

    Answer: errors.Is(err, target) checks whether target appears anywhere in the error chain (using Unwrap() to traverse). It compares by value for sentinel errors, or uses the error's own Is() method if defined. errors.As(err, &target) traverses the chain looking for an error that can be assigned to target — used when you need to extract type-specific fields from a custom error type. Use Is to check "did this specific error occur?". Use As to "give me the typed error so I can read its fields."

    Hard What does %w do in fmt.Errorf? How does it affect the error chain?

    Answer: %w wraps the error — it creates a new error that contains the original as a "cause". The new error implements Unwrap() error, returning the wrapped error. This lets errors.Is and errors.As traverse the chain. %v also formats an error but does NOT wrap it — the chain is lost. Always use %w when you want callers to be able to inspect the underlying error. Use %v when you intentionally want to break the chain (e.g., at API boundaries where you don't want internal errors leaking).

    9. Pointers & Memory

    📺 YouTube Tutorials
    • Pointers Explained — Anthony GG

    Theory

    A pointer holds the memory address of a value. Pointers allow functions to modify the original value, avoid copying large structs, and represent optional values (nil = not present).

    🧠 Why Pointers? The Memory Model

    When you pass a value to a function in Go, Go makes a complete copy. For a small int, this is free. For a 500-field struct, this means copying hundreds of bytes on every call. Pointers solve this: instead of passing the whole struct, you pass its address (8 bytes on 64-bit systems), and the function can read and write the original data.

    Pointers also enable mutation: the only way a function can change a caller's variable is through a pointer. And they represent optional values: a *string can be nil ("not set"), which is different from an empty string ("explicitly empty"). This distinction matters in APIs: was the field absent in the request, or was it explicitly set to empty?

    🔍 Stack vs Heap — Where Does Memory Go?

    The Go compiler performs escape analysis to decide whether each variable lives on the stack (fast, automatic cleanup when function returns) or the heap (slower, managed by garbage collector). A variable "escapes to the heap" when it might outlive the function that created it: you return its address, store it in a heap-allocated struct, or assign it to an interface.

    Practical impact: A local variable in a tight loop that doesn't escape costs nothing in GC pressure. A variable returned as a pointer is heap-allocated and must be GC'd. This is why sync.Pool exists — to reuse heap-allocated objects and reduce GC pressure. Check escape analysis with go build -gcflags="-m" ./....

    🔍 Go Automatically Dereferences Pointers to Structs

    When you have p := &Point{1, 2} and write p.X, Go automatically dereferences the pointer for you — you don't need to write (*p).X. This applies to method calls too: if a method has a pointer receiver, Go automatically takes the address: user.SetEmail("x") is equivalent to (&user).SetEmail("x"). This syntactic convenience makes pointer usage feel natural.

    ✅ When to Use Pointers

    Use pointers when: (1) the function must modify the caller's value, (2) the struct is large (>3-4 fields is a common threshold), (3) the struct contains a sync primitive, (4) you need to distinguish "not present" from "zero value" (optional fields). Don't use pointers when: the struct is small and read-only, you want value semantics (copying is intentional), or for basic types like int, string, bool — these are always passed by value.

    // ── Basics ────────────────────────────────────────────────────────
x := 42
p := &x           // p is *int, holds address of x
fmt.Println(*p)   // dereference: 42
*p = 99           // mutate through pointer
fmt.Println(x)    // 99 — x was changed

// ── Pointer to struct ─────────────────────────────────────────────
type Point struct{ X, Y int }
p := &Point{1, 2}
p.X = 10          // Go auto-dereferences (*p).X — no need for (*p).X

// ── When to use pointers ──────────────────────────────────────────
// 1. Mutation: function must modify the caller's value
func increment(n *int) { *n++ }
n := 5; increment(&n); fmt.Println(n) // 6

// 2. Large structs: avoid copying on every function call
func process(cfg *Config) { /* 100-field struct passed by pointer */ }

// 3. Optional values: *T can be nil (Go has no Option type)
type User struct {
    Name string
    Age  *int // nil = age not provided
}

// 4. Shared mutable state (sync patterns)
type Counter struct { mu sync.Mutex; n int }
func (c *Counter) Inc() { c.mu.Lock(); c.n++; c.mu.Unlock() }
// Must use pointer receiver — copying a Mutex panics

// ── Escape analysis: stack vs heap ────────────────────────────────
// Go compiler decides: does this variable need to outlive the function?
// Stack: fast, auto-reclaimed. Heap: GC-managed.
// A variable "escapes to heap" when:
// - its address is returned or stored in a long-lived structure
// - it's passed to an interface (unknown size at compile time)
// - it's too large for the stack
func makeUser() *User {
    u := User{Name: "Sid"} // u escapes to heap — returned pointer
    return &u              // safe: heap-allocated, GC will collect when no refs
}

    🎯 Interview Questions

    Medium What is the difference between passing a struct by value vs by pointer?

    Answer: By value: Go creates a complete copy of the struct. The function operates on the copy — mutations don't affect the original. By pointer: the function receives the memory address. Mutations affect the original. Performance: passing large structs by value is expensive (copying many bytes); by pointer is 8 bytes (a pointer) regardless of struct size. Choose by pointer for: mutation, large structs, types with sync primitives (mutex). Choose by value for: small read-only structs, immutable data, when you want caller's data protected.

    12. Generics (Go 1.18+)

    📺 YouTube Tutorials
    • Generics in Go — Anthony GG
    • Generics Deep Dive — Flo Woelki

    Theory

    Generics allow you to write functions and types that work with any type satisfying a constraint, eliminating code duplication while keeping type safety.

    🧠 Why Generics Were Added (the Problem They Solve)

    Go had no generics from 2009 until 2022 (Go 1.18). During that time, developers worked around the limitation in two ways: (1) write separate functions for each type (MinInt, MinFloat64, MinString), or (2) use interface{} and type assertions at runtime (losing compile-time type safety, adding runtime overhead and potential panics).

    The Go team resisted generics for years because they add language complexity. The decisive argument was: certain fundamental patterns — generic data structures (queues, stacks, sets), generic algorithms (map, filter, sort), type-safe container types — simply cannot be expressed cleanly without generics. The cost of code duplication or unsafe interfaces became too high as the ecosystem matured.

    🔍 When to Use Generics vs Interface

    Use interfaces when: you want runtime polymorphism (different implementations called through the same interface), the behaviour is what varies, you have an existing ecosystem of types that already implement the interface.

    Use generics when: you want the same algorithm to work on multiple data types while preserving type safety, the type itself is the variable (not just behaviour), you're building reusable data structures or utility functions. Rule of thumb: if you find yourself writing func(v any) and immediately type-asserting inside, generics are the right tool.

    🔍 Constraints — What They Mean

    A constraint is an interface that a type parameter must satisfy. any (the weakest) means no constraints — only operations available to every type (assignment, comparison with == for comparable types). constraints.Ordered allows <, >. ~int means "any type whose underlying type is int" — this includes type UserID int. Without ~, a custom type like UserID wouldn't satisfy int even though it's built on it.

    ✅ When NOT to Use Generics

    Don't use generics for: types that are truly runtime-polymorphic (use interfaces), simple functions that already work fine with a concrete type, cases where the added syntax complexity outweighs the benefit. The Go team recommends: write the concrete version first, wait until you see the duplication pattern emerge, then generalise. "Make it work first, then abstract."

    // ── Type parameters ───────────────────────────────────────────────
// Syntax: func FuncName[T constraint](arg T) T

// Before generics — separate functions or type assertions
func MinInt(a, b int) int { if a < b { return a }; return b }
func MinFloat(a, b float64) float64 { if a < b { return a }; return b }

// With generics — one function, any ordered type
func Min[T constraints.Ordered](a, b T) T {
    if a < b { return a }
    return b
}
Min(3, 5)         // int
Min(3.14, 2.71)   // float64
Min("apple","b")  // string

// ── Type constraints ──────────────────────────────────────────────
// constraints.Ordered = all types that support < > <= >=
// any = interface{} — no constraint

// Custom constraint
type Number interface {
    ~int | ~int64 | ~float64  // ~ means "any type whose underlying type is"
}

func Sum[T Number](nums []T) T {
    var total T
    for _, n := range nums { total += n }
    return total
}

// ── Generic data structures ───────────────────────────────────────
type Stack[T any] struct {
    items []T
}
func (s *Stack[T]) Push(item T)     { s.items = append(s.items, item) }
func (s *Stack[T]) Pop() (T, bool) {
    var zero T
    if len(s.items) == 0 { return zero, false }
    item := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return item, true
}

s := Stack[int]{}
s.Push(1); s.Push(2)
val, _ := s.Pop() // 2

// Map — transform a slice
func Map[T, U any](s []T, fn func(T) U) []U {
    result := make([]U, len(s))
    for i, v := range s { result[i] = fn(v) }
    return result
}

// Filter

    var result []T
    for _, v := range s { if fn(v) { result = append(result, v) } }
    return result
}

// Ptr — helper to take address of any value (common in tests)
func Ptr[T any](v T) *T { return &v }

    13. Context Package — Timeouts & Cancellation

    📺 YouTube Tutorials
    • Context Package — Anthony GG
    • Advanced Context Patterns — Sameer Ajmani

    Theory

    context.Context is Go's mechanism for propagating cancellation, timeouts, and request-scoped values across API boundaries and goroutine chains. It is in every production function signature in Go.

    🧠 Why Context Exists — The Problem It Solves

    Before context, there was no standard way to cancel an in-progress operation. If a user's HTTP request timed out, the handler returned — but any goroutines spawned by that handler (DB queries, external API calls) kept running, consuming resources for a response that nobody would ever read. In a high-traffic service, this leads to goroutine accumulation and resource exhaustion.

    Context solves this by providing a cancellation tree: when you cancel a parent context, every child context derived from it is also cancelled. A goroutine that respects context can detect cancellation and return early, freeing its resources immediately. This is how Go services achieve backpressure and avoid resource leaks under load.

    🔍 The Context Tree — How Propagation Works

    Every context has a parent. Cancelling a parent cancels all children, but cancelling a child does NOT cancel the parent. This forms a tree:

    • Background is the root — never cancelled, used at the top of call chains (main, HTTP handlers, goroutine entry points)
    • WithTimeout(parent, 5s) creates a child that auto-cancels after 5 seconds (or when parent cancels, whichever comes first)
    • WithCancel(parent) creates a child with a manual cancel function
    • WithValue(parent, key, val) creates a child carrying a key-value pair — values are inherited by all children

    When you call cancel(), the context's Done channel is closed. Every goroutine watching <-ctx.Done() unblocks and can return. Deferred cancel() ensures the context is always cancelled even if the function returns early.

    🔍 Why Context Is Always the First Parameter

    This is a Go convention enforced by the community and linters. Why first? Because it needs to be passed to every function that does I/O or could be cancelled. Putting it first makes the pattern immediately recognisable: any function whose first parameter is ctx context.Context is context-aware and can be cancelled. It also makes tool analysis simpler — the Go context checker knows to look at position 0.

    ✅ When to Use Each Context Function

    context.Background(): at the start of every call chain — main function, HTTP handler, goroutine entry point. Never deep inside business logic. WithTimeout: for any external call with a known maximum acceptable duration (DB query, HTTP call, LLM API call). WithCancel: when you need to cancel based on a condition (user disconnected, error occurred in a sibling goroutine). WithValue: only for request-scoped metadata — request ID, auth token, trace ID. Never use it to pass function parameters or configuration (use explicit arguments instead).

    // ── Context tree ──────────────────────────────────────────────────
//          Background
//              │
//    WithCancel(background)
//              │
//    WithTimeout(cancel, 5s)
//              │
//   WithValue(timeout, key, val)

// ── Background: the root context ─────────────────────────────────
ctx := context.Background() // never cancelled, used at top of call chain

// ── WithTimeout: auto-cancel after duration ───────────────────────
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // ALWAYS defer cancel — prevents goroutine/resource leak

req, _ := http.NewRequestWithContext(ctx, "GET", "https://api.openai.com/...", nil)
resp, err := http.DefaultClient.Do(req)
if err != nil {
    if errors.Is(err, context.DeadlineExceeded) {
        fmt.Println("request timed out")
    }
}

// ── WithCancel: manual cancellation ──────────────────────────────
ctx, cancel := context.WithCancel(context.Background())
go func() {
    // Some goroutine that should stop when parent cancels
    for {
        select {
        case <-ctx.Done():
            fmt.Println("goroutine stopping:", ctx.Err())
            return
        default:
            doWork()
        }
    }
}()
cancel() // signal cancellation — goroutine will exit on next iteration

// ── WithValue: request-scoped data ───────────────────────────────
// ONLY for request-scoped data: request IDs, auth claims, trace IDs
// Do NOT store function parameters or optional arguments in context
type ctxKey string
const requestIDKey ctxKey = "requestID"

ctx = context.WithValue(ctx, requestIDKey, "req-uuid-123")
requestID := ctx.Value(requestIDKey).(string)

// ── ctx.Done() channel ────────────────────────────────────────────
// Returns a channel that is closed when the context is cancelled/timed out
// Check in long-running operations:
func processItems(ctx context.Context, items []Item) error {
    for _, item := range items {
        select {
        case <-ctx.Done():
            return ctx.Err() // context cancelled — stop processing
        default:
            if err := process(ctx, item); err != nil {
                return err
            }
        }
    }
    return nil
}

// ── Rule: context is always the FIRST parameter ───────────────────
// CORRECT:
func GetUser(ctx context.Context, id string) (*User, error)
// WRONG:
func GetUser(id string, ctx context.Context) (*User, error)
    ⚠️ Always call cancel(): Every WithCancel, WithTimeout, and WithDeadline returns a cancel function. If you don't call it, resources are leaked until the parent context is done. Always defer cancel() immediately after the context creation.

    🎯 Interview Questions

    Hard What is context.Context? Why is it the first parameter by convention?

    Answer: Context carries: (1) a cancellation signal — so you can stop in-flight operations when a request is cancelled or times out, (2) a deadline — the absolute time after which the context is cancelled, (3) key-value pairs for request-scoped data (auth claims, trace IDs). It's the first parameter by convention so tools, linters, and humans can consistently identify context-aware functions. Putting it first also makes chaining calls readable.

    Hard What happens if you forget to call cancel() after WithTimeout?

    Answer: A goroutine internal to the context package keeps a timer and a goroutine alive to send the cancellation signal at the deadline. If you never call cancel(), this goroutine and its resources leak until the parent context is done. In a long-running server handling thousands of requests, this creates a goroutine leak that grows over time. defer cancel() immediately after the context creation guarantees cleanup regardless of how the function exits.

    Expert How do you propagate cancellation through a pipeline of goroutines?

    Answer: Pass the context down through every goroutine. Each goroutine selects on ctx.Done() alongside its work channel. When the root context is cancelled, ctx.Done() is closed, and all goroutines in the pipeline unblock from their select and return. Parent cancels child — child passes its context to grandchild — cancellation cascades. Pattern: select { case result := <-workChan: process(result); case <-ctx.Done(): return ctx.Err() }.

    16. io.Reader / io.Writer — The Go I/O Model

    📺 YouTube Tutorials
    • io.Reader / Writer — JustForFunc

    Theory

    io.Reader and io.Writer are the two most important interfaces in the Go standard library. Everything that reads or writes data implements one of them — files, HTTP bodies, strings, network connections, gzip streams.

    🧠 Why These Two Interfaces Are the Core of Go's I/O Model

    The fundamental insight: what you read from or write to shouldn't matter to the code doing the reading or writing. A JSON decoder doesn't need to know if it's reading from a file, a network socket, a string in memory, or a compressed gzip stream. It just needs something that implements Read([]byte)(int, error).

    This is why Go's I/O model is so composable. You can wrap a reader with another reader to transform data on-the-fly: wrap a file reader with a gzip reader to decompress while reading, wrap that with a limited reader to cap the size, all without any of these components knowing about each other.

    🔍 How io.Reader Works — The Contract

    Read(p []byte) reads up to len(p) bytes into p and returns the number of bytes read and any error. A return of n, io.EOF signals end of input. A return of n, nil means "read n bytes, more data may be available." Callers must not assume all len(p) bytes are filled — multiple Read calls may be needed. Use io.ReadFull or io.ReadAll when you need exactly N bytes or all bytes.

    🔍 Streaming vs Buffering — When It Matters

    io.ReadAll reads everything into a []byte in memory. For a 1GB response body, that allocates 1GB of RAM. io.Copy uses a 32KB buffer and streams — memory usage is constant regardless of data size. For LLM streaming responses, AI document uploads, and large file processing, streaming is essential. The Go HTTP server's http.ResponseWriter implements io.Writer, so you can stream directly to the client without buffering the whole response.

    ✅ When to Use Each io Helper

    io.ReadAll: small, bounded data (JSON API responses, config files). io.Copy: any large or unbounded data (file uploads, streaming HTTP responses, LLM output). io.LimitReader: always wrap untrusted input to prevent DoS (a client sending 10GB request body). strings.NewReader: testing — use a string as an io.Reader. bytes.Buffer: accumulate writes then convert to string/bytes once at the end.

    type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }

// Files, HTTP bodies, network connections, buffers, string readers

}

    17. Goroutines — Lightweight Threads

    📺 YouTube Tutorials
    • Go Concurrency Patterns — Rob Pike (Google I/O)
    • Goroutines Explained — TechWorld with Nana

    Theory

    A goroutine is a lightweight thread managed by the Go runtime scheduler, not the OS. They start with a 2KB stack (vs 1–8MB for OS threads) and can run millions concurrently. The scheduler multiplexes M goroutines onto N OS threads (M:N threading).

    🧠 Why Goroutines? The Problem with OS Threads

    Traditional servers handle concurrency with OS threads. The problem: each OS thread costs 1–8MB of memory (the default stack size), and creating/destroying them involves expensive kernel system calls. A server with 10,000 concurrent connections needs 10,000 threads — that's potentially 80GB of memory just for stacks.

    Goroutines start with a 2KB stack (4000x smaller than OS threads) and grow dynamically as needed (Go copies the stack to a larger space when it fills — called "stack copying" or "segmented stacks"). You can run millions of goroutines on a modern machine. Creating a goroutine costs a few microseconds; creating an OS thread costs milliseconds.

    🔍 The GMP Scheduler — How Go Manages Goroutines

    Go uses an M:N threading model: M goroutines multiplexed onto N OS threads. The three components:

    • G (Goroutine): The unit of work. Each has its own stack and instruction pointer. Goroutines are cheap to create and are managed entirely by the Go runtime.
    • M (Machine — OS Thread): The actual OS thread that runs code on the CPU. There are typically as many M's as GOMAXPROCS (number of logical CPUs), though more can be created when goroutines block on syscalls.
    • P (Processor — Logical CPU): Holds a queue of runnable goroutines and connects an M to run Go code. There are exactly GOMAXPROCS P's. Each M needs a P to run Go code.

    When a goroutine blocks on I/O (network, file), its M doesn't block waiting — it detaches from the P, another M picks up the P, and continues running other goroutines. When the I/O completes, the original goroutine is put back on a P's run queue. This is why Go can handle 10,000 concurrent network connections with only 4–8 OS threads.

    🔍 GOMAXPROCS — What It Controls

    GOMAXPROCS controls how many goroutines can run simultaneously (on different CPU cores). Default is the number of logical CPUs. Setting it to 1 means all goroutines are scheduled onto a single OS thread — concurrency but no parallelism. In containers, the default GOMAXPROCS sees the host's CPU count, not the container's CPU limit — use uber-go/automaxprocs to fix this automatically.

    ✅ When to Launch Goroutines — and When Not To

    Launch goroutines for: independent, concurrent I/O operations (fetch from 3 APIs simultaneously), background jobs that must not block the caller, long-running services (HTTP server, event consumer). Don't launch goroutines for: work that must be sequential (order matters), work that returns an error you need immediately, simple synchronous operations where goroutine overhead exceeds benefit. And always: ensure every goroutine has a clear termination path — context cancellation, closed channel, or function return.

    // ── Launching goroutines ──────────────────────────────────────────

    fmt.Println("running in a goroutine")
}()

go doWork(args) // pass function by name

// ── Goroutine lifecycle ───────────────────────────────────────────
// A goroutine runs until its function returns.
// Goroutines are NOT garbage collected — they must exit naturally.

// ── The goroutine leak (critical interview topic) ─────────────────
// A goroutine that never terminates = memory leak
func leaky() {
    ch := make(chan int)
    go func() {
        val := <-ch  // blocked forever — no one sends, goroutine never exits
        fmt.Println(val)
    }()
    // ch goes out of scope — goroutine is stuck forever
}

        case val := <-ch:
            fmt.Println(val)

            return
        }

    🎯 Interview Questions

    Hard What is a goroutine leak? How do you detect and prevent it?

    Answer: A goroutine leak is a goroutine that is created but never terminates — it stays alive holding memory, file descriptors, or database connections indefinitely. Common causes: (1) blocked channel read/write with no sender/receiver, (2) infinite loop without a termination signal, (3) waiting for a network call that never completes. Detection: runtime.NumGoroutine() growing over time; tools like goleak in tests. Prevention: always provide a cancellation path (context), use buffered channels to avoid blocking, ensure every goroutine has a ctx.Done() case in its select.

    Expert Explain Go's M:N threading model (GMP scheduler).

    Answer: The GMP model: G = Goroutines (user code), M = Machine threads (OS threads), P = Processors (logical CPU, holds a run queue). There are GOMAXPROCS P's. Each M needs a P to run Go code. Each P has a local run queue of goroutines. When a goroutine blocks on I/O, its M is released (M parks), the P is reused by another M with pending goroutines — so blocking I/O doesn't waste OS threads. This lets thousands of goroutines run on a few OS threads efficiently.

    18. Channels & Select

    📺 YouTube Tutorials
    • Channels & Select — Anthony GG
    • Channel Patterns — Rob Pike

    Theory

    "Do not communicate by sharing memory; share memory by communicating." — Go Proverb. Channels are typed conduits for values between goroutines.

    🧠 Why Channels? The Shared Memory Problem

    Traditional multi-threaded programming shares data between threads via shared memory (global variables, shared heap objects), protected by mutexes. This works but is error-prone: forget a lock and you have a data race; hold two locks in different orders and you have a deadlock; lock too coarsely and you eliminate parallelism.

    Channels offer an alternative: instead of sharing a variable and protecting it, you send copies of data through a channel. Only one goroutine owns the data at any time — when you send it, you give it up. This eliminates the sharing problem by design. The proverb "share memory by communicating" is the inverse of the traditional approach.

    When to use channels vs mutexes: Use channels when passing ownership of data between goroutines, coordinating goroutine lifecycles (start/stop signals), or building pipelines. Use mutexes when protecting a shared data structure that multiple goroutines need to access (a cache, a counter, a map). Don't dogmatically prefer one — use the right tool.

    🔍 How Channels Work Internally

    A channel is implemented as a circular buffer (for buffered channels) plus two goroutine queues: one for blocked senders (when buffer is full) and one for blocked receivers (when buffer is empty). When a goroutine sends to a full buffered channel, it's parked in the sender queue and the Go scheduler runs another goroutine. When space becomes available, the parked goroutine is woken up and its value is placed in the buffer.

    Unbuffered channels have no buffer — a send directly transfers the value to a waiting receiver (or parks if none). This makes unbuffered channels a synchronisation point: both goroutines must be at the channel simultaneously for the transfer to happen.

    🔍 Closing Channels — The Rules

    Closing signals to receivers that no more values will be sent. Rules: (1) Only the sender closes a channel — never the receiver (a sender knows it's done sending; a receiver doesn't know if there are other senders). (2) Never close a channel that another goroutine might still send to — sending to a closed channel panics. (3) Reading from a closed channel returns buffered values first, then zero values. Use the comma-ok form to detect closure: v, ok := <-ch. (4) Closing a nil channel panics.

    ✅ When to Use select

    select is essential for: combining multiple input channels (fan-in), implementing timeouts (with time.After), responding to context cancellation (with ctx.Done()), and non-blocking channel operations (with default). Without select, a goroutine waiting on one channel is blocked even if another channel becomes ready. Select is what makes Go concurrency composable.

    // ── Channel operations ────────────────────────────────────────────
ch := make(chan int)       // unbuffered — send blocks until receive (and vice versa)
ch <- 42                  // send (blocks if no receiver)
val := <-ch               // receive (blocks if no sender)
close(ch)                 // close — signals no more values

// Buffered channels
bch := make(chan int, 10)  // send doesn't block until buffer is full

// ── Channel directions ────────────────────────────────────────────
// Restrict to send-only or receive-only in function signatures
func producer(out chan<- int) { out <- 42 }    // send-only
func consumer(in <-chan int) { val := <-in; _ = val } // receive-only

// ── Range over channel ────────────────────────────────────────────
// Loops until channel is closed
for val := range ch {
    fmt.Println(val) // exits loop when ch is closed
}

// ── select: multiplex channels ────────────────────────────────────
// Like switch, but for channel operations
select {
case v1 := <-ch1:
    fmt.Println("received from ch1:", v1)
case v2 := <-ch2:
    fmt.Println("received from ch2:", v2)
case ch3 <- value:
    fmt.Println("sent to ch3")
case <-time.After(5 * time.Second):
    fmt.Println("timeout")
case <-ctx.Done():
    return ctx.Err() // context cancelled
default:
    fmt.Println("non-blocking — nothing ready") // remove for blocking select
}

    doWork()

}()

    sem <- struct{}{} // acquire

}()

    🎯 Interview Questions

    Hard What is the difference between a buffered and unbuffered channel?

    Answer: Unbuffered: both sender and receiver must be ready simultaneously — send blocks until a receiver is ready; receive blocks until a sender is ready. Acts as a synchronisation point. Buffered: has a queue of capacity N. Send only blocks when the buffer is full; receive only blocks when the buffer is empty. A buffered channel of size 1 is often used as a semaphore for mutual exclusion. Rule of thumb: start with unbuffered (forces you to reason about synchronisation); add buffer only when you have a measured performance reason.

    Hard What happens when you read from a closed channel?

    Answer: Reading from a closed channel immediately returns the zero value of the channel's type and false for the "comma ok" form: val, ok := <-ch. If there are still values buffered in the channel, they're returned first; after the buffer is drained, you get zero values. Writing to a closed channel panics. Closing a closed channel panics. Pattern: only the sender should close a channel, never the receiver.

    19. sync Package — Mutex, WaitGroup, Once

    📺 YouTube Tutorials
    • Mutex & RWMutex — Anthony GG

    Theory

    The sync package provides synchronisation primitives for coordinating goroutines that access shared memory. It's the toolkit for the "sharing memory" approach to concurrency, complementing channels.

    🧠 Why sync Primitives Exist — The Shared State Problem

    Sometimes channels aren't the right tool. A cache accessed by hundreds of goroutines, a connection pool, a configuration store — these are naturally shared data structures where ownership doesn't transfer. Making each access go through a channel would be awkward and slow. Mutexes provide a simpler model: lock before reading/writing, unlock after, guaranteed exclusive access.

    🔍 How Mutex Works Internally

    A sync.Mutex has a zero value that is ready to use (no constructor). Internally it's a state machine using atomic operations: unlocked (0) and locked (various states for waiting goroutines). When a goroutine calls Lock() on an already-locked mutex, it is parked by the Go scheduler — it doesn't spin-wait (burn CPU). When the holder calls Unlock(), one waiting goroutine is woken up and given the lock.

    RWMutex allows multiple concurrent readers (RLock/RUnlock) but exclusive writers (Lock/Unlock). A write lock blocks until all readers release. If readers hold the lock continuously, writers can starve — Go's RWMutex prevents writer starvation by blocking new readers once a writer is waiting.

    🔍 WaitGroup — Purpose and Pattern

    WaitGroup solves a simple problem: "I launched N goroutines; tell me when they're all done." The counter is incremented with Add(1) before launching each goroutine, decremented with Done() when it finishes, and Wait() blocks until the counter reaches zero. Always call Add in the parent goroutine before launching children (never inside the goroutine itself) — otherwise the child might complete and call Done before Add is called, making the counter go negative and panicking.

    🔍 sync.Once — Lazy Initialisation

    sync.Once ensures a function runs exactly once, regardless of how many goroutines call it concurrently. The first goroutine to call Do(fn) runs fn; all concurrent goroutines block until fn completes; subsequent calls to Do return immediately without calling fn. Purpose: lazy singleton initialisation — initialise a resource on first use, not at startup. This is safer than package-level init() because you can handle errors and defer the (potentially expensive) initialisation until it's actually needed.

    ✅ When to Use Which sync Primitive

    Mutex: protecting a shared data structure (map, struct, counter). RWMutex: read-heavy shared data (cache, config). WaitGroup: waiting for a batch of goroutines to finish. Once: lazy singleton initialisation. Pool: reusing frequently allocated objects to reduce GC pressure. sync.Map: specific pattern: many goroutines, each writing to disjoint keys (otherwise use Mutex + map).

    import "sync"

// ── sync.Mutex — mutual exclusion ────────────────────────────────
type SafeCounter struct {
    mu sync.Mutex
    count int
}
func (c *SafeCounter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock() // ALWAYS unlock with defer — protects against panic
    c.count++
}

// ── sync.RWMutex — multiple readers, one writer ───────────────────
type Cache struct {
    mu    sync.RWMutex
    items map[string]string
}
func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()         // multiple goroutines can read simultaneously
    defer c.mu.RUnlock()
    v, ok := c.items[key]
    return v, ok
}
func (c *Cache) Set(key, val string) {
    c.mu.Lock()          // exclusive write — blocks all readers
    defer c.mu.Unlock()
    c.items[key] = val
}

    wg.Add(1)
    go func(item Item) {
        defer wg.Done() // ALWAYS defer Done to handle panics
        process(item)
    }(item)
}

    instance *DB
    once     sync.Once

        instance = connectDB() // called exactly once, even with concurrent callers
    })

}

// - many goroutines reading, rare writes (read-heavy)

    🎯 Interview Questions

    Hard What is a data race? How do you detect and fix it?

    Answer: A data race occurs when two goroutines access the same memory location concurrently without synchronisation, and at least one is a write. Data races cause undefined behaviour — random crashes, corrupted data, silent wrong results. Detection: run with -race flag: go test -race ./... or go run -race main.go. Fix with: (1) sync.Mutex/sync.RWMutex around shared data, (2) channels to pass data between goroutines (communication, not shared memory), (3) sync/atomic for simple counters/flags.

    Medium When would you use sync.RWMutex over sync.Mutex?

    Answer: When reads are much more frequent than writes. RWMutex allows unlimited concurrent readers (via RLock()) but requires exclusive access for writes (via Lock()). For a read-heavy cache (100 reads per write), RWMutex can significantly improve throughput. For write-heavy or balanced workloads, the overhead of RWMutex (it's heavier than Mutex) makes it slower. Rule: measure first, optimise second.

    20. Worker Pool & Fan-Out / Fan-In

    📺 YouTube Tutorials
    • Worker Pool Pattern — Anthony GG
    • Fan-Out Fan-In — Rob Pike (Go Concurrency Patterns)

    Theory

    Worker pools bound the number of concurrent goroutines — preventing resource exhaustion. Fan-out distributes work; fan-in merges results.

    // ── Worker Pool ───────────────────────────────────────────────────
func workerPool(ctx context.Context, jobs <-chan Job, numWorkers int) <-chan Result {
    results := make(chan Result, numWorkers)

    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case job, ok := <-jobs:
                    if !ok { return } // channel closed — no more jobs
                    result := processJob(ctx, job)
                    results <- result
                case <-ctx.Done():
                    return
                }
            }
        }()
    }

    // Close results when all workers are done
    go func() {
        wg.Wait()
        close(results)
    }()

    return results
}

// ── Fan-Out: distribute work to N goroutines ──────────────────────
func fanOut[T any](in <-chan T, n int) []<-chan T {
    outs := make([]<-chan T, n)
    for i := range outs {
        ch := make(chan T)
        outs[i] = ch
        go func() {
            defer close(ch)
            for v := range in { ch <- v }
        }()
    }
    return outs
}

// ── Fan-In: merge N channels into one ─────────────────────────────
func fanIn[T any](ctx context.Context, channels ...<-chan T) <-chan T {
    merged := make(chan T)
    var wg sync.WaitGroup

    for _, ch := range channels {
        wg.Add(1)
        go func(c <-chan T) {
            defer wg.Done()
            for {
                select {
                case v, ok := <-c:
                    if !ok { return }
                    merged <- v
                case <-ctx.Done():
                    return
                }
            }
        }(ch)
    }

    go func() { wg.Wait(); close(merged) }()
    return merged
}

    Hard How does errgroup differ from sync.WaitGroup?

    📺 YouTube Tutorials

    Theory: Pipeline Pattern

    A pipeline is a series of stages where each stage takes input from a channel, processes it, and sends results to the next channel. Cancellation propagates backward through the pipeline via context.

    // ── RAG document pipeline: read → chunk → embed → store ──────────

// Stage 1: read documents from DB
func readDocuments(ctx context.Context, docIDs []string) <-chan Document {
    out := make(chan Document)
    go func() {
        defer close(out)
        for _, id := range docIDs {
            doc, err := db.GetDocument(ctx, id)
            if err != nil { continue }
            select {
            case out <- doc:
            case <-ctx.Done(): return // cancelled
            }
        }
    }()
    return out
}

// Stage 2: split documents into chunks
func chunkDocuments(ctx context.Context, docs <-chan Document) <-chan Chunk {
    out := make(chan Chunk)
    go func() {
        defer close(out)
        for doc := range docs {
            for _, chunk := range splitIntoChunks(doc.Text, 500) {
                select {
                case out <- Chunk{DocID: doc.ID, Text: chunk}:
                case <-ctx.Done(): return
                }
            }
        }
    }()
    return out
}

// Stage 3: embed chunks (parallel — multiple workers)
func embedChunks(ctx context.Context, chunks <-chan Chunk, workers int) <-chan EmbeddedChunk {
    out := make(chan EmbeddedChunk, workers)
    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for chunk := range chunks {
                embedding, err := callEmbeddingAPI(ctx, chunk.Text)
                select {
                case out <- EmbeddedChunk{Chunk: chunk, Embedding: embedding, Err: err}:
                case <-ctx.Done(): return
                }
            }
        }()
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

// Stage 4: store in pgvector
func storeEmbeddings(ctx context.Context, embedded <-chan EmbeddedChunk) error {
    for ec := range embedded {
        if ec.Err != nil { log.Println("embed error:", ec.Err); continue }
        if err := vectorDB.Insert(ctx, ec); err != nil {
            return fmt.Errorf("store: %w", err)
        }
    }
    return nil
}

// ── Wire the pipeline ─────────────────────────────────────────────
func ingestDocuments(ctx context.Context, docIDs []string) error {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Minute)
    defer cancel()

    docs     := readDocuments(ctx, docIDs)
    chunks   := chunkDocuments(ctx, docs)
    embedded := embedChunks(ctx, chunks, 10) // 10 parallel embedding workers

    return storeEmbeddings(ctx, embedded)
}

// When context is cancelled:
// storeEmbeddings returns (no more input from embedded)
// embedChunks workers exit (ctx.Done() fires)
// chunkDocuments goroutine exits
// readDocuments goroutine exits
// All channels close in cascade → complete teardown

    🎯 Interview Questions

    Expert Describe how you would build a concurrent document processing pipeline in Go. How do you handle cancellation?

    Answer: I'd use a pipeline of stages connected by channels. Each stage is a goroutine that reads from an input channel, processes, and writes to an output channel. Cancellation via context: pass the context to every goroutine; each goroutine uses select { case <-in: ...; case <-ctx.Done(): return }. When the root context is cancelled (timeout, user abort), all goroutines unblock from their selects and exit. Each stage closes its output channel when done — downstream stages detect this via range exhaustion. For the parallel embedding stage, a worker pool with sync.WaitGroup ensures all workers finish before the output channel closes.

    24. Type Assertions & Type Switches

    📺 YouTube Tutorials
    • Type Assertions & Type Switches — Anthony GG

    Theory

    A type assertion extracts the concrete value held inside an interface. A type switch tests multiple types in sequence. Both are critical for working with interface{} / any values.

    // ── Type Assertion ─────────────────────────────────────────────────
// Syntax: value, ok := interfaceVar.(ConcreteType)
var i interface{} = "hello"

// Single-value form — PANICS if wrong type
s := i.(string)         // safe: s = "hello"
n := i.(int)            // PANIC: interface holds string, not int

// Comma-ok form — NEVER panics
s, ok := i.(string)     // ok=true,  s="hello"
n, ok := i.(int)        // ok=false, n=0 (zero value)
if !ok {
    fmt.Println("not an int")
}

// ── When to use ────────────────────────────────────────────────────
// 1. Checking if an interface implements an optional sub-interface
var w io.Writer = os.Stdout
if flusher, ok := w.(http.Flusher); ok {
    flusher.Flush()  // only available if the concrete type supports it
}

// 2. Checking if error is a specific type
if err != nil {
    var netErr *net.OpError
    if errors.As(err, &netErr) {
        fmt.Println("network operation:", netErr.Op)
    }
}

// ── Type Switch ────────────────────────────────────────────────────
// Tests a value against multiple types — cleaner than chained type assertions
func process(v any) string {
    switch val := v.(type) {  // val has the concrete type inside each case
    case int:
        return fmt.Sprintf("int: %d (doubled: %d)", val, val*2)
    case string:
        return fmt.Sprintf("string: %q (len: %d)", val, len(val))
    case bool:
        return fmt.Sprintf("bool: %t", val)
    case []int:
        return fmt.Sprintf("[]int with %d elements", len(val))
    case nil:
        return "nil value"
    default:
        return fmt.Sprintf("unknown type: %T", val)
    }
}

// ── Real-world: JSON value inspection ──────────────────────────────
var data map[string]any
json.Unmarshal(jsonBytes, &data)

for key, val := range data {
    switch v := val.(type) {
    case float64:  // JSON numbers are float64 in Go
        fmt.Printf("%s = %g\n", key, v)
    case string:
        fmt.Printf("%s = %q\n", key, v)
    case bool:
        fmt.Printf("%s = %t\n", key, v)
    case map[string]any:
        fmt.Printf("%s = nested object\n", key)
    case []any:
        fmt.Printf("%s = array[%d]\n", key, len(v))
    case nil:
        fmt.Printf("%s = null\n", key)
    }
}
    ⚠️ Always use comma-ok form unless you are 100% certain of the type. A failing type assertion panics at runtime — this crashes your server. In handler code, HTTP middleware, or any code processing untrusted data, always use val, ok := x.(Type).

    🎯 Interview Questions

    Medium What is a type assertion? What happens if it fails?

    Answer: A type assertion extracts the concrete value stored in an interface: val := iface.(ConcreteType). Single-value form panics if the assertion fails (wrong type). Two-value "comma-ok" form: val, ok := iface.(ConcreteType) — never panics; ok is false and val is the zero value if the type doesn't match. Always use comma-ok in production code where the type isn't guaranteed.

    Medium What is a type switch? How does it differ from a regular switch?

    Answer: A type switch checks the dynamic type of an interface value: switch v := x.(type) { case int: ... case string: ... }. Unlike a regular switch (which compares values), a type switch compares types. The bound variable v in each case has the concrete type of that case — so you get type-safe access to the value without further assertions. Used heavily for JSON processing, error inspection, and plugin systems.

    Hard How do you check if a concrete type implements an optional interface at runtime?

    Answer: Use a type assertion with the comma-ok form: flusher, ok := w.(http.Flusher). If ok is true, the concrete type behind the w interface also implements http.Flusher. This is how Go implements optional capabilities without forcing all types to implement every method. Example: http.ResponseWriter might or might not implement http.Flusher depending on the concrete type — check at runtime before calling Flush().

    📺 YouTube Tutorials

    Theory

    Go strings are immutable byte slices encoded in UTF-8. This distinction between bytes (8-bit) and runes (Unicode code points, up to 32-bit) is one of the most commonly asked Go topics in interviews.

    // ── String = immutable []byte (UTF-8 encoded) ─────────────────────

// len() returns BYTES, not characters!
fmt.Println(len(s))   // 13 (not 9!) — "世" and "界" are 3 bytes each in UTF-8

// Indexing gives BYTES, not characters
fmt.Println(s[0])     // 72 (byte value of 'H')
fmt.Println(s[7])     // 228 (first byte of '世', not the character)

// ── rune = int32 = Unicode code point ────────────────────────────
r := '世'
fmt.Printf("%T %v\n", r, r)  // int32 19990

// ── Correct iteration: range over string gives runes ──────────────
for i, r := range s {
    fmt.Printf("byte pos %d: %c (U+%04X)\n", i, r, r)
}
// byte pos 0: H
// byte pos 7: 世    ← byte position jumps by 3 (3 bytes for this rune)
// byte pos 10: 界

// ── Count runes (not bytes) ───────────────────────────────────────
import "unicode/utf8"
fmt.Println(utf8.RuneCountInString(s))  // 9 (the actual character count)
fmt.Println(len([]rune(s)))             // 9 (convert to rune slice — less efficient)

// ── Convert string to []rune for character-level manipulation ─────
runes := []rune(s)
runes[7] = '地'          // modify individual characters
s2 := string(runes)

// ── strings.Builder: efficient string construction ────────────────
// WRONG: += in a loop is O(n²) — allocates new string every iteration
var result string
for _, r := range words { result += r + " " }  // slow!

// CORRECT: strings.Builder
var b strings.Builder
b.Grow(estimatedSize)  // pre-allocate if you know approximate size

    b.WriteString(r)

}

// ── Common string operations ──────────────────────────────────────
// Check if valid UTF-8
utf8.ValidString(s)

// Iterate bytes (if you know it's ASCII)
for i := 0; i < len(s); i++ {
    b := s[i]  // byte
}

s3 := s      // cheap: copies the string header (pointer + len), NOT the bytes

    🎯 Interview Questions

    Hard What does len(s) return for a Go string? How do you get the character count?

    Answer: len(s) returns the number of bytes, not characters. For ASCII strings they're equal, but for multi-byte UTF-8 characters (Chinese, Arabic, emoji), bytes > characters. To get character (rune) count: utf8.RuneCountInString(s) or len([]rune(s)). Difference: "Hello, 世界" has len=13 bytes but 9 runes.     Medium Why are Go strings immutable? What does that mean for performance?

    Answer: Strings are immutable byte sequences — you cannot modify individual bytes. String assignment is cheap (copies an 8/16-byte header: pointer + length), not a full copy. Concatenation with + or += creates a new allocation each time — O(n²) in a loop. For building strings: use strings.Builder (single allocation at end), fmt.Sprintf (slower but convenient), or bytes.Buffer. Converting string ↔ []byte always copies (necessary since one is mutable, one isn't).

    import "reflect"

// ── The two main functions ─────────────────────────────────────────
// reflect.TypeOf(v)  — returns the reflect.Type  (describe the type)
// reflect.ValueOf(v) — returns the reflect.Value (inspect/modify the value)

// ── TypeOf: inspect type metadata ────────────────────────────────
type User struct {
    Name  string `json:"name"  validate:"required"`
    Email string `json:"email" validate:"email"`
    Age   int    `json:"age"`
}
u := User{Name: "Sid", Email: "sid@example.com", Age: 25}

t := reflect.TypeOf(u)

fmt.Println(t.Kind())        // struct

for i := 0; i < t.NumField(); i++ {
    field := t.Field(i)
    fmt.Printf("Field: %s  Type: %s  Tag: %s\n",
        field.Name, field.Type, field.Tag.Get("json"))
}
// Field: Name   Type: string  Tag: name
// Field: Email  Type: string  Tag: email
// Field: Age    Type: int     Tag: age

// ── ValueOf: inspect and set values ──────────────────────────────
v := reflect.ValueOf(u)
fmt.Println(v.Field(0).String())  // "Sid"
fmt.Println(v.Field(2).Int())     // 25

vp := reflect.ValueOf(&u).Elem()   // Elem() dereferences the pointer

fmt.Println(u.Name) // "Ram" — original struct modified!

// ── Kinds: the fundamental type categories ─────────────────────────
// reflect.Kind: Bool Int Float64 String Struct Slice Map Ptr Func Interface Chan...
switch v.Kind() {
case reflect.Struct:  fmt.Println("it's a struct")
case reflect.Slice:   fmt.Println("it's a slice")
case reflect.Ptr:     fmt.Println("it's a pointer")
}

// ── Practical example: generic struct-to-map converter ────────────
func StructToMap(s any) map[string]any {
    result := make(map[string]any)
    v := reflect.ValueOf(s)
    t := reflect.TypeOf(s)

    if t.Kind() == reflect.Ptr {
        v = v.Elem()
        t = t.Elem()
    }
    if t.Kind() != reflect.Struct {
        return result
    }

    for i := 0; i < t.NumField(); i++ {
        field := t.Field(i)
        if !field.IsExported() { continue } // skip unexported fields
        tag := field.Tag.Get("json")
        if tag == "" || tag == "-" { continue }
        key := strings.Split(tag, ",")[0]
        result[key] = v.Field(i).Interface()
    }
    return result
}

    27. sync/atomic & Go Memory Model

    📺 YouTube Tutorials
    • sync/atomic in Go — Anthony GG
    • The Go Memory Model — Official Reference

    Theory: sync/atomic — Lock-Free Operations

    Atomic operations are CPU-level instructions that are indivisible — they complete without interruption. No lock needed, lower overhead than Mutex for simple counters and flags.

    import (
    "sync/atomic"
    "runtime"
)

// ── Atomic integer operations ─────────────────────────────────────
var counter int64

// Add: returns the NEW value after adding
new := atomic.AddInt64(&counter, 1)    // increment
atomic.AddInt64(&counter, -1)           // decrement

// Load/Store: safe concurrent reads and writes
val := atomic.LoadInt64(&counter)       // safe read (no torn reads)
atomic.StoreInt64(&counter, 0)          // safe write (no torn writes)

// CompareAndSwap (CAS): the foundation of lock-free algorithms
// Only stores newVal if *addr == oldVal, returns whether swap happened
swapped := atomic.CompareAndSwapInt64(&counter, 0, 1)
// Used to implement: spinlocks, lock-free queues, optimistic concurrency

// ── Go 1.19+: typed atomics (cleaner API) ─────────────────────────
var flag  atomic.Bool    // zero value = false
var count atomic.Int64
var ptr   atomic.Pointer[MyStruct]

flag.Store(true)
if flag.Load() { /* ... */ }
count.Add(1)
count.Store(0)
old := count.Swap(42)         // store 42, return old value

// ── When to use atomic vs Mutex ───────────────────────────────────
// atomic:  single variable, simple operations (incr, compare-swap)
//          Higher performance, no blocking, no deadlock possible
// Mutex:   multiple variables that must change together atomically
//          Complex state that requires read-modify-write across multiple fields

// Example: use atomic for a simple hit counter
var hits atomic.Int64
func recordHit() { hits.Add(1) }

// Example: use Mutex for updating multiple fields together
type Stats struct {
    mu           sync.Mutex
    hits         int64
    latencyTotal int64
    errors       int64
}
func (s *Stats) record(latency int64, err bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.hits++                  // all 3 must change atomically together
    s.latencyTotal += latency
    if err { s.errors++ }
}

// ── Go Memory Model — Happens-Before ─────────────────────────────
// The Go Memory Model defines when one goroutine is guaranteed to
// see writes made by another goroutine.

// Rule: A write W is guaranteed to be seen by read R if:
// W "happens-before" R in the happens-before ordering.

// Happens-before relationships:
// - Package init() completes before main() starts
// - Goroutine launch: code before "go f()" happens-before f() starts
// - Channel send "happens-before" the corresponding channel receive completes
// - Mutex unlock "happens-before" the next mutex lock
// - sync.Once: the first call to Do happens-before any return from Do

// WRONG: no synchronisation — race condition
var data string
var ready bool

go func() {
    data = "hello"   // write 1
    ready = true     // write 2 — NOT guaranteed to be seen after write 1!
}()
for !ready {}       // read ready — may never see true, or see true before "hello"
fmt.Println(data)   // may print ""

// CORRECT: use channel to establish happens-before
go func() {
    data = "hello"
    ch <- struct{}{} // send establishes happens-before
}()
<-ch                 // receive: now data = "hello" is guaranteed visible
fmt.Println(data)   // safe: always prints "hello"

    🎯 Interview Questions

    Hard When should you use sync/atomic instead of a Mutex?

    Answer: Use atomic when: (1) you're updating a single primitive value (counter, flag, pointer), (2) you want lock-free performance (no thread blocking, no deadlock risk), (3) the operation is a single read, write, or compare-and-swap. Use Mutex when: multiple variables must change together consistently, or the operation requires multiple steps that must be atomic as a unit. Atomics are lower-level — easier to get wrong. Prefer Mutex for clarity unless you've measured a performance bottleneck.

    Expert What is the Go Memory Model? Why does it matter?

    Answer: The Go Memory Model defines when a write in one goroutine is guaranteed to be visible to a read in another. Without synchronisation, there is no guarantee — the Go compiler and CPU can reorder instructions for optimisation. The "happens-before" relationship is established by: channel operations, mutex lock/unlock, sync.Once, goroutine creation/start. Without happens-before, two goroutines can observe writes in different orders. This is why you need synchronisation even for seemingly simple cases like setting a boolean flag from one goroutine and reading it in another.

    Master Interview Question Bank (40+ Q&A)

    How to use this section: Questions are ordered Easy → Expert within each category. In a real interview, you'll get 5–10 of these. Know every Easy/Medium cold. Have a clear, concise answer for Hard. Expert questions signal senior-level depth.

    🎯 Category 1 — Types, Variables & Memory

    Easy What is a zero value? List 5 examples.

    Answer: Every variable declared without explicit value gets its zero value. int → 0, string → "", bool → false, *T → nil, []T → nil slice, map[K]V → nil map, chan T → nil channel, interface{} → nil, struct → all fields zeroed.

    Easy What is the difference between var x int and x := 0?

    Answer: Both declare an int with value 0. Differences: := can only be used inside functions (not package level), infers the type automatically, and requires at least one new variable on the left. var works everywhere, requires explicit type or value. Style preference: use := inside functions for brevity; use var when type must be explicit (e.g., var b []byte gives a nil slice, not b := []byte{} which is non-nil empty).

    Medium What is the difference between make and new?

    Answer: new(T): allocates zeroed T, returns *T. Works for any type. make(T, ...): creates and initialises slices, maps, and channels only (these need internal initialisation before use). new returns a pointer; make returns the type. In practice: use make for slices/maps/channels; use struct literals for structs; rarely use new.

    Medium What is a nil slice vs empty slice? When does the difference matter?

    Answer: Nil slice: var s []int — s == nil is true, len=0, safe to append/range. Empty slice: s := []int{} — s == nil is false, len=0. Both safe to use. Difference matters in JSON: nil slice marshals to null, empty slice to []. Also in tests: reflect.DeepEqual treats them as different.

    Hard Explain escape analysis. How does the Go compiler decide stack vs heap?

    Answer: Escape analysis determines at compile time whether a variable's lifetime extends beyond the function that creates it. If yes, it "escapes to heap" (GC-managed). A variable escapes when: its address is returned or stored in a heap-allocated structure, passed to an interface, or the compiler can't prove it won't outlive the function. Stack is faster (no GC), heap is necessary for long-lived data. Check with go build -gcflags="-m". Implication: if your hot-path code has unexpected allocations, use sync.Pool or avoid taking addresses of local variables.

    Hard What is the difference between int, int32, and int64?

    Answer: int is platform-dependent (64-bit on 64-bit systems, 32-bit on 32-bit systems). int32 and int64 are always fixed size. Rule: use int for loop counters, array indices, and general integers. Use int64 for values that must be exactly 64-bit (timestamps, file sizes, DB IDs). Never mix them implicitly — Go requires explicit conversion: int64(myInt).

    🎯 Category 2 — Interfaces & Polymorphism

    Easy How does Go implement interfaces? Do you need an explicit "implements" declaration?

    Answer: No. Go uses structural typing (duck typing) — if a type has all the methods an interface requires, it implicitly implements that interface. No implements keyword. Advantage: you can make third-party types satisfy your interfaces without modifying them. Example: os.File implements io.Writer because it has a Write([]byte)(int,error) method — no explicit declaration.

    Medium What is the empty interface any? When would you use it vs generics?

    Answer: any (alias for interface{}) is satisfied by every type. Use it when you truly don't know the type at compile time (JSON decoding into unknown structure, plugin systems, fmt functions). Use generics when the type is unknown but constrained — generics give compile-time type safety without reflection overhead. Example: instead of func Map(s []any, fn func(any)any)[]any (requires type assertions), use func Map[T,U any](s []T, fn func(T)U)[]U.

    Hard Explain the typed-nil interface bug. How do you reproduce it and fix it?

    Answer: An interface value has two components: {type, value}. A nil interface = {nil, nil}. A "typed nil" = {*MyError, nil} — the type is set, so the interface is NOT nil even though the pointer is nil. Reproduce: func f() error { var e *MyError; return e } — f() == nil is false. Fix: always return untyped nil: if e == nil { return nil }. Common in code that builds errors conditionally — wrap checks before returning.

    Hard What is the "accept interfaces, return structs" principle?

    Answer: Functions should accept interface parameters (for flexibility and testability) but return concrete structs (so callers can access all methods without type assertions). Accepting an interface: callers can pass any compatible type, enabling mocking. Returning a struct: callers get the full concrete type. Returning an interface forces callers to type-assert and is an anti-pattern unless the return type is genuinely polymorphic (like io.Reader). Exception: error is always returned as interface by convention.

    🎯 Category 3 — Error Handling

    Easy How do you handle errors in Go? Why doesn't Go have exceptions?

    Answer: Functions return (T, error) and callers check explicitly: if err != nil { return err }. Go avoids exceptions because: (1) exceptions can escape from unexpected places, making code flow hard to reason about, (2) checked exceptions (Java) are verbose and often ignored, (3) treating errors as values forces developers to think about every failure. The explicit check is verbose but unambiguous.

    Medium What is error wrapping? Show the difference between %v and %w.

    Answer: fmt.Errorf("context: %w", err) wraps err — the new error implements Unwrap() returning the original. errors.Is(wrapped, err) returns true. %v formats the error message but does NOT create the Unwrap chain — errors.Is can't find the original. Rule: always use %w when crossing package boundaries so callers can inspect the root cause. Use %v to intentionally break the chain (e.g., at API response boundaries to not expose internal errors).

    Hard Design an error handling strategy for a multi-layer Go service (handler → service → repository).

    Answer: (1) Repository layer: return domain-typed errors — ErrNotFound, ErrDuplicate, wrapped with context: fmt.Errorf("GetUser(%s): %w", id, ErrNotFound). (2) Service layer: translate and wrap further: fmt.Errorf("UserService.GetUser: %w", err). (3) Handler layer: use errors.Is/errors.As to map to HTTP status codes — ErrNotFound → 404, validation errors → 422. Never return raw DB errors to the client. Log the full chain server-side; send only the public message to clients.

    🎯 Category 4 — Concurrency (Most Asked)

    Easy How do you create a goroutine? What is the difference between a goroutine and an OS thread?

    Answer: go fn(args) creates a goroutine. Goroutine: ~2KB initial stack (grows on demand), managed by Go runtime, thousands can coexist. OS thread: 1–8MB stack, managed by OS kernel, expensive to create/context-switch. Go multiplexes M goroutines onto N OS threads (M:N model). Creating 100,000 goroutines is normal; creating 100,000 threads would exhaust memory.

    Medium What is a channel? What is the difference between buffered and unbuffered?

    Answer: A channel is a typed conduit for communication between goroutines. Unbuffered: synchronous — sender blocks until receiver is ready (and vice versa). Acts as a rendezvous point. Buffered(n): sender only blocks when buffer is full; receiver only blocks when empty. Use unbuffered for synchronisation; use buffered to decouple sender and receiver speed.

    Medium What is a data race? How do you detect it?

    Answer: Two goroutines access the same memory location concurrently, at least one is a write, and there's no synchronisation. Results in undefined behaviour — random crashes, corrupted state. Detect with go test -race ./... or go run -race. Fix: add sync.Mutex, use channels, or use sync/atomic for simple values.

    Hard What is a goroutine leak? Name 3 common causes and how to fix each.

    Answer: A goroutine leak = goroutine that never exits, holding resources forever. (1) Blocked receive on unmatched channel: sender exits without closing or sending — fix: always close channels when done, or add a done signal. (2) Infinite loop without exit: for { doWork() } — fix: add case <-ctx.Done() in select. (3) Blocked HTTP call without timeout: fix: use http.Client{Timeout} and http.NewRequestWithContext. Detect with runtime.NumGoroutine() trending up, or goleak in tests.

    Hard When would you use select? How does it handle multiple ready channels?

    Answer: select waits on multiple channel operations — whichever is ready first executes. If multiple are ready simultaneously, Go picks one at random (uniform pseudo-random). Common uses: timeout (case <-time.After(5s)), cancellation (case <-ctx.Done()), non-blocking check with default, multiplexing multiple input channels. The random selection when multiple are ready prevents starvation — no channel is always chosen over another.

    Hard Explain sync.WaitGroup. What happens if you call Add after Wait?

    Answer: WaitGroup waits for a collection of goroutines to finish. Add(n) increments the counter; Done() decrements (always defer it); Wait() blocks until counter reaches 0. Calling Add after Wait has started is a race condition — the counter may increment after Wait has already observed 0 and returned. Always call Add before launching the goroutine (in the parent, not inside the goroutine).

    Expert Explain the GMP scheduler model in Go.

    Answer: GMP = G (goroutines) + M (machine OS threads) + P (processor, logical CPU). There are GOMAXPROCS P's. Each P has a local run queue. Each M needs a P to run Go code. When a goroutine blocks on I/O or a syscall, its M releases the P so another M (or a newly spawned M) can use it — keeping all P's busy. Goroutines are cooperatively preempted at function call points (and since 1.14, also preemptively via signals for goroutines in tight loops). Work-stealing: idle P's steal goroutines from other P's local queues to keep all CPUs busy.

    Expert How does Go garbage collection interact with concurrency?

    Answer: Go uses a concurrent tricolor mark-and-sweep GC. GC runs concurrently with application goroutines (not fully stop-the-world like old GCs). STW (stop-the-world) pauses are very short (typically <1ms) — only for marking roots and a final sweep phase. The write barrier prevents GC from missing writes during marking. Implications: (1) more goroutines = more GC root scanning = longer GC pauses. (2) Reducing allocations (escape analysis, sync.Pool) reduces GC pressure. (3) GOMEMLIMIT (Go 1.19) lets you set a soft memory limit so GC runs more aggressively before OOM.

    🎯 Category 5 — Advanced Go (Senior Roles)

    Hard What are generics constraints? What is the ~ operator?

    Answer: A constraint defines what operations are allowed on a type parameter. constraints.Ordered allows <, >, <=, >=. ~int means "any type whose underlying type is int" — this includes user-defined types like type UserID int. Without ~, int only matches exactly int. Example: type Number interface { ~int | ~int64 | ~float64 } — this constraint matches int, int64, float64, AND any type built on them.

    Hard What is init()? When does it run? Can there be multiple?

    Answer: init() is a special function that runs automatically after package-level variables are initialised, before main(). Each package can have multiple init() functions (even in the same file). They run in the order they appear. Import order determines which package's init runs first. Use for: registering DB drivers (_ "github.com/lib/pq"), loading config defaults, registering codec implementations. Avoid: side effects that are hard to test, expensive operations, modifying global state in complex ways.

    Hard What is GOMAXPROCS? When would you change it?

    Answer: GOMAXPROCS is the number of OS threads that can execute Go code simultaneously. Default: number of logical CPUs. Increase for CPU-bound workloads with many goroutines. Decrease for I/O-bound services running in containers where you want to limit CPU usage (set to container CPU limit). In Kubernetes: GOMAXPROCS defaults to the host CPU count, NOT the container CPU limit — this causes over-scheduling. Use uber-go/automaxprocs library to set it correctly from cgroup limits.

    Expert Explain the build tag system. How do you conditionally compile code for different OS?

    Answer: Build tags are constraints placed at the top of a Go file (before the package declaration): //go:build linux && amd64. The file is only included when all constraints are met. Constraint expressions: && (AND), || (OR), ! (NOT). Also: //go:build integration for test tags. File naming convention: server_linux.go is automatically included only on Linux; server_windows.go on Windows. Use for: OS-specific syscalls, CPU architecture optimisations, feature flags, separating unit and integration tests.

    Expert How do you do dependency injection in Go without a framework?

    Answer: Define interfaces for all dependencies. Use constructor functions: func NewUserService(repo UserRepository, cache Cache) *UserService. Wire everything in main.go (the composition root). Benefits over frameworks: explicit, compile-time checked, no magic, easy to trace. For large apps: Google Wire generates the wiring code at compile time from dependency graphs defined in Go. Uber Fx uses reflection-based DI at runtime. Both are valid; start with manual wiring until complexity justifies a framework.

    Expert What is sync.Once? How does it differ from a global variable initialisation?

    Answer: sync.Once ensures a function executes exactly once regardless of how many goroutines call it concurrently. It blocks all callers until the first call completes. Difference from package-level init: Once is lazy (runs on first call, not at program start), handles concurrency safely, and can be used conditionally or in tests. Use for: lazy singletons (DB connection pools, config loading), one-time setup that might fail and needs to be retried.

    🎯 Category 6 — Real-World Scenarios (System Design + Go)

    Hard How would you implement a thread-safe LRU cache in Go?

    Answer: Combine a list.List (doubly-linked list for O(1) move-to-front) with a map[string]*list.Element for O(1) lookup. Wrap with a sync.RWMutex. On Get: RLock → lookup map → if found, move element to front (requires write lock), return value. On Set: Lock → if key exists, update and move to front; if at capacity, remove last element from list and map; add to front. Or use golang.org/x/tools/container/lru or github.com/hashicorp/golang-lru.

    Hard How do you implement a timeout for a slow database query?

    Answer: Pass a context with timeout to the DB call: ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second); defer cancel(); rows, err := db.QueryContext(ctx, query). The DB driver respects context cancellation — it sends a cancel signal to the DB when the context expires. Check the error: if errors.Is(err, context.DeadlineExceeded) to distinguish timeout from other errors. Always use QueryContext / ExecContext, never Query / Exec in production.

    Expert You have a Go service handling 10,000 concurrent requests that call an external LLM API. How do you prevent overloading the LLM API (which allows only 100 concurrent calls)?

    Answer: Use a semaphore: sem := make(chan struct{}, 100). Each goroutine acquires before calling LLM: sem <- struct{}{}; releases after: defer func() { <-sem }(). Pair with a context timeout so requests don't wait forever for a semaphore slot. For rate limiting by requests/second (not concurrency), use golang.org/x/time/rate.Limiter. For retry on 429: exponential backoff with jitter. For per-user token budgets: Redis sliding window with Lua script for atomicity.
