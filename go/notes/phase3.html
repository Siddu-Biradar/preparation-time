Goroutines & Scheduler

Theory

What is a Goroutine?

  • Lightweight thread managed by Go runtime (not OS)
  • Initial stack ~2KB (grows as needed)
  • go f() — starts a goroutine
  • Multiplexed onto OS threads (M:N threading)
  • Can run millions concurrently

G-M-P Model

  • G — Goroutine (the task)
  • M — OS Thread (the worker)
  • P — Processor (the scheduler, has a run queue)
  • GOMAXPROCS Ps running at once (default = # CPUs)
  • Work-stealing: idle P steals from busy P's queue

GOMAXPROCS

  • Max OS threads running Go code simultaneously
  • Defaults to runtime.NumCPU()
  • In containers: reads wrong CPU count — set manually!
  • GOMAXPROCS=4 env or runtime.GOMAXPROCS(4)
  • Use automaxprocs library for containers
Code Examples
// ── Basic goroutine ───────────────────────────────
go func() {
    fmt.Println("running in goroutine")
}()

// ── Don't fire-and-forget without WaitGroup ───────
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func(n int) {
        defer wg.Done()
        fmt.Println("goroutine", n)
    }(i) // pass i as argument — avoid loop-var capture
}
wg.Wait() // blocks until all goroutines finish

// ── Container k8s gotcha ──────────────────────────
import _ "go.uber.org/automaxprocs" // auto-detects container CPU quota
// OR:
func main() {
    runtime.GOMAXPROCS(runtime.NumCPU())
}
⚠️ Gotchas
Goroutines are NOT free — each has stack overhead. Thousands are fine; leaking millions will OOM. Always ensure goroutines can exit.
main() exits = all goroutines killed — if main returns before goroutines finish, the program exits without letting them complete. Use WaitGroup or channel to block main.
GOMAXPROCS in containers — Kubernetes containers may show the host CPU count, not the container's limit. Use go.uber.org/automaxprocs.
Goroutines share memory — concurrent access to shared state causes data races. Use channels or sync primitives to coordinate.
Interview Q&A
What is the difference between a goroutine and an OS thread?
OS threads are heavy (~1-8MB stack, expensive context switch managed by the OS kernel). Goroutines are lightweight (~2KB initial stack, managed by Go runtime's M:N scheduler). Millions of goroutines can exist simultaneously. The runtime multiplexes goroutines onto a small pool of OS threads using the G-M-P scheduler.
What does GOMAXPROCS control?
The number of OS threads that can execute Go code simultaneously. It equals the number of P (Processor) schedulers. Default is runtime.NumCPU(). In containers, this may report the host CPU count rather than the container's CPU limit — use automaxprocs to fix this.

Channels & Select

Theory

Channels

  • Typed conduit for goroutine communication
  • Unbuffered: send blocks until receiver ready
  • Buffered: send blocks only when buffer full
  • make(chan T) / make(chan T, n)
  • close(ch) — signals no more sends
  • Receive from closed: returns zero val + ok=false

Direction

  • chan T — bidirectional
  • chan<- T — send-only
  • ->chan T — receive-only (typo-safe in func sigs)
  • Enforce at function boundaries for clarity

select

  • Wait on multiple channel operations
  • Picks a ready case at random (if multiple)
  • default: — non-blocking
  • Use with ctx.Done() for cancellation
  • Empty select select{} blocks forever
Code Examples
// ── Unbuffered channel — synchronization ──────────
ch := make(chan int)
go func() { ch <- 42 }() // blocks until received
v := <-ch                 // blocks until sent
fmt.Println(v)            // 42

// ── Buffered channel ──────────────────────────────
ch := make(chan string, 3) // capacity=3, won't block until full
ch <- "a"; ch <- "b"; ch <- "c"
// ch <- "d" would block now

// ── Range over channel (drain until closed) ───────
gen := func(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out) // MUST close to end range loop
        for _, n := range nums { out <- n }
    }()
    return out
}
for n := range gen(2, 3, 5, 7) { fmt.Println(n) }

// ── select with timeout ───────────────────────────
select {
case result := <-ch:
    fmt.Println("got:", result)
case <-time.After(3 * time.Second):
    fmt.Println("timeout")
case <-ctx.Done():
    fmt.Println("cancelled:", ctx.Err())
}

// ── Non-blocking with default ─────────────────────
select {
case v := <-ch:
    process(v)
default:
    // channel empty, don't block
}
⚠️ Gotchas
Sending on a closed channel panics — only the sender should close. Never close from the receiver side or from multiple goroutines.
Receiving from a nil channel blocks forever — a nil channel in a select case is never selected. Useful trick: set a channel to nil after close to disable that case.
Forgetting to close causes range deadlock — if you range over a channel and never close it, the range loop blocks forever.
time.After leaks in long-running loops — each call creates a new timer that can't be GC'd until it fires. Use time.NewTimer + timer.Reset() instead.
Interview Q&A
What is the difference between buffered and unbuffered channels?
Unbuffered: send blocks until a receiver is ready — provides synchronization (both sides must be ready simultaneously). Buffered: send only blocks when the buffer is full — decouples producer and consumer speed. Use unbuffered for synchronization, buffered for queuing/pipelining.
What happens when you receive from a closed channel?
You receive the remaining buffered values first, then zero values of the channel's type. The comma-ok idiom tells you: v, ok := <-ch — ok is false when the channel is closed and empty. range automatically stops when the channel closes.

sync Package

Theory

sync.Mutex

  • Mutual exclusion — only one goroutine in critical section
  • mu.Lock() / mu.Unlock()
  • Always defer mu.Unlock() after Lock
  • Zero value is valid (don't copy after first use)
  • Never embed by value if copied elsewhere

sync.RWMutex

  • Multiple readers OR one writer
  • RLock/RUnlock for readers
  • Lock/Unlock for writers
  • Use when reads >> writes
  • Writer starvation possible — benchmark!

sync.WaitGroup

  • Wait for a collection of goroutines to finish
  • wg.Add(n) — before launching goroutines
  • wg.Done() — in each goroutine (defer it)
  • wg.Wait() — blocks until count reaches 0
  • Don't copy a WaitGroup

sync.Once

  • Executes a function exactly once
  • Even with concurrent callers
  • Use for: lazy init, singletons
  • once.Do(func)
  • Panics in Do don't reset the once
Code Examples
// ── Mutex — safe counter ──────────────────────────
type SafeCounter struct {
    mu    sync.Mutex
    value int
}
func (c *SafeCounter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.value++
}
func (c *SafeCounter) Get() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.value
}

// ── RWMutex — read-heavy cache ────────────────────
type Cache struct {
    mu    sync.RWMutex
    items map[string]string
}
func (c *Cache) Get(k string) (string, bool) {
    c.mu.RLock(); defer c.mu.RUnlock()
    v, ok := c.items[k]; return v, ok
}
func (c *Cache) Set(k, v string) {
    c.mu.Lock(); defer c.mu.Unlock()
    c.items[k] = v
}

// ── sync.Once — singleton init ────────────────────
var (
    instance *DB
    once     sync.Once
)
func GetDB() *DB {
    once.Do(func() {
        instance = &DB{} // runs exactly once
    })
    return instance
}

// ── sync.WaitGroup ────────────────────────────────
var wg sync.WaitGroup
results := make([]int, 10)
for i := 0; i < 10; i++ {
    wg.Add(1)
    go func(idx int) {
        defer wg.Done()
        results[idx] = idx * idx // safe: each goroutine writes different index
    }(i)
}
wg.Wait()
⚠️ Gotchas
Never copy a Mutex after first use — copying a locked mutex copies the lock state. Embed mutex by value in a struct, but never copy the struct that contains it.
Deadlock: locking twice in same goroutine — Go's Mutex is NOT reentrant. Calling Lock() twice in the same goroutine without Unlock will deadlock forever.
RLock + Lock in same goroutine = deadlock — a goroutine holding RLock cannot also acquire Lock (would wait for itself).
sync.Map is not a drop-in replacement — use sync.Map only for specific patterns (infrequent writes, disjoint key sets per goroutine). For most cases, a regular map + sync.Mutex is faster and more readable.
Interview Q&A
When should you use channels vs mutexes?
Channels: communicate data between goroutines, pipeline patterns, fan-out, signalling. Mutexes: protect shared state (counters, caches, maps). Rob Pike's rule: "Don't communicate by sharing memory; share memory by communicating." But both are valid — use whichever makes the code clearer.
What is the difference between sync.Mutex and sync.RWMutex?
Mutex: exclusive lock — only one goroutine (reader or writer) at a time. RWMutex: multiple concurrent readers allowed, but only one exclusive writer. Use RWMutex when reads vastly outnumber writes (e.g., config cache, read-heavy in-memory store).

Worker Pool & Fan-Out/Fan-In

Theory

Worker Pool

  • Fixed number of goroutines processing from a shared job queue
  • Bounds concurrency — prevents resource exhaustion
  • Pattern: input channel → N workers → output channel
  • Alternative: buffered channel as semaphore

Fan-Out

  • One input distributed to multiple goroutines
  • Parallelizes CPU-bound or I/O-bound work
  • Each worker gets a copy of the same input OR different items

Fan-In (merge)

  • Merge multiple channels into one
  • One goroutine per input channel, all send to merged channel
  • Close merged when all inputs done (WaitGroup)
  • Result order not guaranteed
Code Examples
// ── Worker Pool ───────────────────────────────────
func workerPool(jobs <-chan int, results chan<- int, workers int) {
    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for job := range jobs {
                results <- heavyWork(job) // process job
            }
        }()
    }
    go func() {
        wg.Wait()
        close(results)
    }()
}

jobs := make(chan int, 100)
results := make(chan int, 100)
workerPool(jobs, results, 5) // 5 workers

for j := 0; j < 100; j++ { jobs <- j }
close(jobs) // signal no more jobs

for r := range results { fmt.Println(r) }

// ── Semaphore pattern (simpler) ───────────────────
sem := make(chan struct{}, 10) // max 10 concurrent
for _, url := range urls {
    sem <- struct{}{}          // acquire
    go func(u string) {
        defer func() { <-sem }() // release
        fetch(u)
    }(url)
}
// drain semaphore
for i := 0; i < 10; i++ { sem <- struct{}{} }

// ── Fan-In (merge) ────────────────────────────────
func merge(cs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(cs))
    for _, c := range cs {
        go func(ch <-chan int) {
            defer wg.Done()
            for v := range ch { out <- v }
        }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

errgroup & Advanced Patterns

Theory & Code

golang.org/x/sync/errgroup — run goroutines, collect first error, cancel on failure. Replaces WaitGroup when you need error propagation. 

// ── Basic errgroup ────────────────────────────────
g, ctx := errgroup.WithContext(context.Background())

g.Go(func() error { return fetchA(ctx) })
g.Go(func() error { return fetchB(ctx) })
g.Go(func() error { return fetchC(ctx) })

if err := g.Wait(); err != nil {
    log.Fatal(err) // first error from any goroutine
}
// ctx is cancelled automatically when any goroutine returns error

// ── With SetLimit (Go 1.21+) ──────────────────────
g.SetLimit(5) // max 5 goroutines at a time

for _, url := range urls {
    url := url
    g.Go(func() error { return fetch(ctx, url) })
}
g.Wait()

// ── Collect all errors with errors.Join ──────────
var mu sync.Mutex
var errs []error
var wg sync.WaitGroup
for _, task := range tasks {
    task := task
    wg.Add(1)
    go func() {
        defer wg.Done()
        if err := task.Run(ctx); err != nil {
            mu.Lock(); errs = append(errs, err); mu.Unlock()
        }
    }()
}
wg.Wait()
if len(errs) > 0 { return errors.Join(errs...) }
⚠️ Gotchas
errgroup cancels context on FIRST error — all other goroutines should check ctx.Done(). This is a fail-fast model. If you need all errors, collect them manually with errors.Join.
Loop variable capture — in Go <1.22, you must shadow loop variables inside the goroutine: url := url.

Race Detector & Memory Model

Theory

Race Condition

  • Two goroutines access same memory concurrently
  • At least one is a write
  • No synchronization between them
  • Result: undefined behaviour, random crashes
  • Often reproduces rarely — hard to debug

Race Detector

  • go test -race ./...
  • go run -race main.go
  • ~2x CPU, 5-10x memory overhead
  • Reports goroutine stacks at conflict point
  • Run in CI on every PR

Memory Model

  • Happens-before: guarantee A's writes visible to B
  • Established by: channel ops, mutex lock/unlock, goroutine start, sync.Once
  • Without happens-before, read may see stale data
  • Don't assume sequential consistency across goroutines
Code Examples
// ── Race condition example ─────────────────────────
var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }() // DATA RACE: concurrent writes
}
// counter value is undefined

// Fix with Mutex:
var mu sync.Mutex
var counter int
for i := 0; i < 1000; i++ {
    go func() { mu.Lock(); counter++; mu.Unlock() }()
}

// Fix with atomic:
var counter int64
for i := 0; i < 1000; i++ {
    go func() { atomic.AddInt64(&counter, 1) }()
}

// ── Run race detector ─────────────────────────────
// go test -race ./...
// go build -race -o app && ./app

// ── goleak in tests ───────────────────────────────
import "go.uber.org/goleak"

func TestFoo(t *testing.T) {
    defer goleak.VerifyNone(t) // fails if goroutines leaked
    // test code...
}
⚠️ Gotchas
Race detector can't catch all races — it's dynamic: only detects races that actually occur in a given run. A race that requires specific timing might not appear every run.
Not all concurrent reads are races — concurrent reads of the same value with no writes are safe. Only concurrent read+write or write+write are races.

Goroutine Leaks

5 Leak Patterns & Fixes

1. Blocked send on unbuffered channel

  • Goroutine sends but receiver never starts / exits early
  • Fix: use buffered channel or ensure receiver always runs

2. Blocked receive — channel never closes

  • Goroutine waits on channel that sender never closes
  • Fix: always close channels from sender side when done

3. No context cancellation

  • Goroutine runs forever, ignores ctx.Done()
  • Fix: always check ctx.Done() in long-running goroutines

4. Goroutine stuck on mutex

  • Mutex never unlocked — waiter blocked forever
  • Fix: always defer Unlock immediately after Lock

5. Timer/ticker not stopped

  • time.After in a loop allocates a new timer each iteration
  • Fix: use time.NewTimer and call timer.Stop() + timer.Reset()
Detection & Code
// ── Detect leaks with pprof ───────────────────────
// In your HTTP server:
import _ "net/http/pprof"
// curl http://localhost:6060/debug/pprof/goroutine?debug=2

// Count goroutines:
fmt.Println(runtime.NumGoroutine())

// ── goleak in tests ───────────────────────────────
func TestMyFunc(t *testing.T) {
    defer goleak.VerifyNone(t)
    // any leaked goroutines will fail the test
}

// ── Context-aware goroutine ───────────────────────
func longRunning(ctx context.Context) error {
    ticker := time.NewTicker(time.Second)
    defer ticker.Stop() // prevents timer leak
    for {
        select {
        case <-ctx.Done(): return ctx.Err()
        case <-ticker.C:   doWork()
        }
    }
}

sync/atomic & sync.Pool

Theory & Code

sync/atomic

  • Lock-free operations on primitive types
  • Faster than mutex for simple counters/flags
  • atomic.AddInt64(&n, 1)
  • atomic.LoadInt64(&n)
  • atomic.StoreInt64(&n, v)
  • atomic.CompareAndSwapInt64(&n, old, new)
  • Go 1.19+: typed atomic.Int64 struct

sync.Pool

  • Reuse temporary objects — reduces GC pressure
  • Pool is cleared between GC cycles
  • pool.Get() — returns any or calls New
  • pool.Put(v) — return object to pool
  • Use for: buffers, byte slices, struct allocations
  • Always reset object state before Put
// ── atomic.Int64 (Go 1.19+) ───────────────────────
var hits atomic.Int64
hits.Add(1)
fmt.Println(hits.Load())

// ── sync.Pool — bytes.Buffer pool ─────────────────
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func encode(data any) ([]byte, error) {
    buf := bufPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()     // clear before returning
        bufPool.Put(buf)
    }()
    if err := json.NewEncoder(buf).Encode(data); err != nil {
        return nil, err
    }
    return append([]byte{}, buf.Bytes()...), nil // copy out before return
}
⚠️ Gotchas
sync.Pool objects can be GC'd anytime — never store objects you need to persist. Pool is a cache, not a store.
Must copy data before returning buffer to pool — if you Put a buffer back and still hold a reference to its bytes, the next Get may overwrite them.

Pipeline Pattern

Theory & Code
Pipeline: A series of stages where each stage receives data from upstream via a channel, transforms it, and sends results downstream. Each stage runs in its own goroutine. 
// ── 3-stage pipeline: generate → square → print ───

// Stage 1: generate numbers
func generate(ctx context.Context, nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            select {
            case out <- n:
            case <-ctx.Done(): return // cancellation contract
            }
        }
    }()
    return out
}

// Stage 2: square each number
func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case out <- n * n:
            case <-ctx.Done(): return
            }
        }
    }()
    return out
}

// Wire pipeline:
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

c := generate(ctx, 2, 3, 4, 5)
sq := square(ctx, c)
for n := range sq { fmt.Println(n) } // 4, 9, 16, 25
⚠️ Gotchas
Cancellation contract — every stage must handle ctx.Done() and close its output channel. If a downstream stage exits early, upstream may block forever without cancellation.
Backpressure — an unbuffered pipeline only processes at the speed of the slowest stage. Use buffered channels between stages to add slack and improve throughput.
Interview Q&A
How do you handle early exit/cancellation in a pipeline?
Each stage should select on both its input channel and ctx.Done(). When ctx is cancelled, the stage stops sending/receiving and closes its output channel. This cascades downstream, allowing all goroutines to exit cleanly without leaking.
