P1

Variables, Types & Functions

Theory

Variable Declaration

  • var x int = 5 — full form (package or function scope)
  • x := 5 — short declaration (function scope only)
  • var x int — zero value (0 for int)
  • Multiple: var a, b int = 1, 2
  • var block groups related declarations

Basic Types

  • bool — true / false
  • int, int8/16/32/64, uint
  • float32, float64
  • complex64, complex128
  • string — immutable UTF-8 bytes
  • byte = uint8, rune = int32

Functions

  • Multiple return values: func f() (int, error)
  • Named returns: func f() (x int) — naked return
  • Variadic: func sum(nums ...int)
  • First-class: assign to vars, pass as args
  • No default param values in Go

Zero Values

  • int → 0
  • float64 → 0.0
  • bool → false
  • string → ""
  • pointer/slice/map/chan/func → nil
Syntax & Code
package main

import "fmt"

// Multiple return values — idiomatic Go
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, fmt.Errorf("division by zero")
    }
    return a / b, nil
}

// Named return values (avoid in long funcs — hurts readability)
func minMax(arr []int) (min, max int) {
    min, max = arr[0], arr[0]
    for _, v := range arr {
        if v < min { min = v }
        if v > max { max = v }
    }
    return // naked return
}

// Variadic function
func sum(nums ...int) int {
    total := 0
    for _, n := range nums { total += n }
    return total
}

func main() {
    // Short declaration
    x := 42
    s := "hello"

    // Type conversion (no implicit casting in Go)
    var f float64 = float64(x)

    // Type inference
    y := 3.14 // Go infers float64

    result, err := divide(10, 3)
    if err != nil {
        fmt.Println("error:", err)
    }

    fmt.Println(x, s, f, y, result)
    fmt.Println(sum(1, 2, 3, 4))       // 10
    fmt.Println(sum([]int{1,2,3}...))  // spread slice
}
⚠️ Gotchas
1. No implicit type conversion — var x int = 3.14 won't compile. Must use float64(x).
2. := only inside functions — package-level must use var.
3. Unused variables = compile error — Go refuses to compile if a declared local var is never used. Imports too.
4. Named returns are often a smell — good for short doc-like funcs; in longer funcs they shadow outer vars and hurt readability.
5. int size is platform-dependent — 32-bit on 32-bit systems, 64-bit on 64-bit. Don't assume 64-bit.
Interview Q&A
What is the difference between var x int and x := 0?
Both declare an int initialized to 0. var works at package and function scope; := is shorthand only inside functions. var is preferred when the zero value is intentional (makes intent explicit).
Why does Go have multiple return values instead of exceptions?
Go favors explicit error handling over exceptions. Multiple returns force callers to handle errors at each call site. This makes control flow obvious — no hidden exception paths, no try/catch complexity.
What is a rune and when would you use it over byte?
rune is int32 — represents a Unicode code point. Use rune when iterating over a string with non-ASCII characters (emoji, CJK). for i, r := range "héllo" gives runes. []byte("héllo") gives raw UTF-8 bytes.
Can you re-assign a variable with := if it already exists?
Yes, if at least one variable on the left side is new. x, err := f() then y, err := g() — err is re-assigned, y is new. If ALL variables already exist, use =.

Control Flow

Theory

for — only loop in Go

  • C-style: for i := 0; i < n; i++
  • While-style: for x < 10
  • Infinite: for { ... }
  • Range: for i, v := range slice
  • No while or do-while keywords

if

  • No parentheses required
  • Init statement: if x := f(); x > 0
  • Init var scoped to the if/else block
  • No ternary operator in Go

switch

  • No break needed — cases don't fall through by default
  • Use fallthrough to explicitly fall through
  • No-condition switch = clean if-else chain
  • Type switch: switch v := x.(type)
  • Cases can be comma-separated: case 1, 2, 3:

range

  • Slice/array: i, v — index + copy of value
  • Map: k, v — iteration order NOT guaranteed
  • String: i, r — byte position + rune
  • Channel: v — receives until closed
  • Discard with _: for _, v := range s
Code Examples
// ── for loops ──────────────────────────────────────
for i := 0; i < 5; i++ { fmt.Println(i) }     // C-style
for n < 100 { n *= 2 }                         // while-style
for { /* break or return to exit */ }           // infinite

// range — canonical
s := []string{"a", "b", "c"}
for i, v := range s { fmt.Println(i, v) }
for _, v := range s { fmt.Println(v) }          // ignore index

m := map[string]int{"a": 1, "b": 2}
for k, v := range m { fmt.Println(k, v) }       // random order!

// ── if with init ───────────────────────────────────
if err := doSomething(); err != nil {
    log.Fatal(err)
}
// 'err' not accessible here — scoped to if/else block

// ── switch ─────────────────────────────────────────
switch os := runtime.GOOS; os {
case "linux":   fmt.Println("Linux")
case "darwin":  fmt.Println("macOS")
default:        fmt.Println("Other:", os)
}

// no-condition switch (replaces long if-else)
switch {
case score >= 90: fmt.Println("A")
case score >= 80: fmt.Println("B")
default:          fmt.Println("C or below")
}

// fallthrough (explicit)
switch x {
case 1:
    fmt.Println("one")
    fallthrough
case 2:
    fmt.Println("one or two") // runs if x==1 too
}
⚠️ Gotchas
range gives a copy of the value — modifying v in a range loop does NOT modify the original slice element. Use index: s[i] = ...
Map iteration order is random — deliberately randomized in Go runtime. Never rely on order. Sort keys first if needed.
Loop variable capture (pre-Go 1.22) — in goroutines inside loops, all goroutines shared the same loop var. Fixed in Go 1.22. Pre-1.22: copy with v := v.
switch cases don't fall through by default — unlike C/Java. Use fallthrough keyword explicitly (rare in practice).
Interview Q&A
How do you iterate over a string character by character in Go?
for i, r := range "héllo" — gives Unicode code points (runes). Using s[i] directly gives bytes. For multi-byte characters (emoji, accented chars), always use range.
Why is there no while loop in Go?
Go's designers wanted one loop construct. for covers all cases: C-style (init; cond; post), while-style (just condition), and infinite (for {}). Less syntax, same power.
What is the difference between a type switch and a regular switch?
A regular switch compares values. A type switch (switch v := x.(type)) checks the dynamic type of an interface value. Each case tests whether the interface holds a specific concrete type.

defer, panic & recover

Theory

defer

  • Pushes a function call onto a stack — runs when surrounding function returns
  • Arguments evaluated immediately, execution deferred
  • LIFO order (last deferred runs first)
  • Runs even if function panics
  • Use for: cleanup, unlock mutex, close file/conn

panic

  • Stops normal execution — unwinds the stack
  • Deferred functions still run during unwind
  • Reaches top of goroutine → program crashes
  • Only for truly unrecoverable situations
  • NOT a substitute for error handling

recover

  • Catches a panic — must be called inside a deferred function
  • Returns the value passed to panic()
  • Returns nil if no panic is happening
  • Only recovers panics in the same goroutine
  • Use to build resilient server middleware
Code Examples
// ── defer basics ──────────────────────────────────
func copyFile(src, dst string) error {
    f, err := os.Open(src)
    if err != nil { return err }
    defer f.Close() // guaranteed cleanup

    // work with f...
    return nil
}

// LIFO order
func lifo() {
    defer fmt.Println("first defer")  // runs LAST
    defer fmt.Println("second defer") // runs SECOND
    defer fmt.Println("third defer")  // runs FIRST
    fmt.Println("function body")
}
// Output: function body → third → second → first

// ── Argument evaluation is IMMEDIATE ─────────────
x := 0
defer fmt.Println(x) // captures x=0 right now, prints 0
x = 42               // does NOT affect the deferred call

// ── panic + recover ───────────────────────────────
func safeDiv(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r)
        }
    }()
    return a / b, nil // panics if b == 0
}

// ── HTTP middleware pattern ───────────────────────
func panicMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                http.Error(w, "Internal Server Error", 500)
                log.Printf("panic: %v\n%s", rec, debug.Stack())
            }
        }()
        next.ServeHTTP(w, r)
    })
}
⚠️ Gotchas
Args evaluated immediately — defer fmt.Println(x) captures x's value NOW, not when the defer runs. Use a closure to capture later: defer func() { fmt.Println(x) }()
defer in a loop is dangerous — each iteration pushes onto stack. Can exhaust memory. Use an inner function instead.
recover only works in direct deferred function — calling recover in a function called by a deferred function does NOT catch the panic.
panic across goroutines — recover cannot catch a panic from a different goroutine. Each goroutine must have its own recovery mechanism.
Interview Q&A
When are deferred function arguments evaluated?
Immediately when the defer statement is executed — not when the deferred function runs. So defer fmt.Println(x) captures the current value of x. To defer evaluation, wrap in a closure: defer func() { fmt.Println(x) }().
Can you modify a named return value inside a deferred function?
Yes. Named return values are accessible by the deferred function via closure. This is how you can change the return value even after a panic is recovered. Example: func f() (err error) { defer func() { if r := recover(); r != nil { err = fmt.Errorf(...) } }() ... }
What is the order of deferred calls?
LIFO — last deferred runs first. Think of it as a stack. The last defer statement in source code is the first to execute when the function returns.

Slices, Maps & Arrays

Theory

Slice Internals

  • 3-field header: pointer, length, capacity
  • Pointer → backing array (may be shared!)
  • len(s) — elements accessible
  • cap(s) — from ptr to end of array
  • make([]T, len, cap) — allocate
  • nil slice: len=0, cap=0, ptr=nil

Arrays vs Slices

  • Array: fixed size, value type (copied on assignment)
  • Slice: dynamic, reference type (shares backing array)
  • [3]int{} vs []int{}
  • Arrays rarely used directly; slices everywhere
  • Array size is part of its type: [3]int ≠ [4]int

Maps

  • Hash table — O(1) average ops
  • Key must be comparable (no slices, maps as keys)
  • Unordered iteration
  • Zero value is nil — must make before writing
  • Delete: delete(m, key)
  • Check: v, ok := m[key]

append semantics

  • If cap has room → extends len, same backing array
  • If cap full → allocates new array (usually 2x), copies, returns new slice header
  • Always: s = append(s, x) — reassign!
  • Append can cause aliasing bugs silently
Code Examples
// ── Arrays ───────────────────────────────────────
var a [3]int          // [0, 0, 0]
b := [3]int{1, 2, 3}
c := [...]int{1, 2, 3} // compiler counts

// ── Slices ────────────────────────────────────────
s := []int{1, 2, 3}
s = append(s, 4, 5)
fmt.Println(len(s), cap(s)) // 5, 6 (grew)

// Slice of a slice — shares backing array!
x := []int{1, 2, 3, 4, 5}
y := x[1:3] // [2, 3], cap=4
y[0] = 99   // also changes x[1]!

// Safe copy
dst := make([]int, len(src))
copy(dst, src)

// nil vs empty slice
var ns []int       // nil, len=0, cap=0
es := []int{}      // NOT nil, len=0, cap=0
fmt.Println(ns == nil) // true
fmt.Println(es == nil) // false

// 2D slice
matrix := make([][]int, rows)
for i := range matrix { matrix[i] = make([]int, cols) }

// ── Maps ──────────────────────────────────────────
m := map[string]int{"a": 1, "b": 2}
m["c"] = 3
delete(m, "a")

v, ok := m["x"] // ok=false if key missing, v=0 (zero val)

// Writing to nil map panics!
var bad map[string]int
// bad["key"] = 1 // panic: assignment to entry in nil map
good := make(map[string]int)
good["key"] = 1  // safe
⚠️ 7 Critical Gotchas
1. Slice aliasing — b := a[1:3] shares the backing array. Modifying b modifies a. Use copy() to avoid.
2. append after slice — data corruption — if capacity allows, append to a sub-slice overwrites elements of the original. Pre-Go: use full-slice expression a[1:3:3] to cap capacity.
3. Writing to nil map panics — reading from nil map is safe (returns zero value). Writing panics. Always make before write.
4. Map iteration is random — never write code that depends on map iteration order.
5. Maps are NOT safe for concurrent use — concurrent reads are fine, but concurrent writes (or write + read) cause data races. Use sync.RWMutex or sync.Map.
6. Always reassign from append — append(s, x) may return a different backing array. If you ignore the return, you may be mutating the old slice.
7. range gives a copy — for _, v := range s — v is a copy. Modifying v doesn't modify s. Use index s[i] to modify in place.
Interview Q&A
Explain the internal structure of a Go slice.
A slice is a 3-field struct: (pointer to backing array, length int, capacity int). Multiple slices can point to the same backing array — this is how sub-slicing works. append grows the slice; if cap is exceeded, a new backing array is allocated.
What happens when you append to a slice that was created from another slice?
If capacity is available, append modifies the shared backing array — which can corrupt the original slice's data. Use s[low:high:max] (3-index slice) to limit capacity, or copy() to get an independent slice.
Is it safe to read from a nil map?
Yes. Reading from a nil map returns the zero value for the value type (0 for int, "" for string, false for bool, nil for pointers). Writing to a nil map causes a runtime panic. Always initialize maps with make before writing.

Structs, Methods & Composition

Theory

Structs

  • Named collection of fields — Go's class equivalent
  • Value type — copied on assignment
  • Zero value: all fields at their zero values
  • Anonymous structs for one-off data
  • Struct tags for JSON, DB, validation

Methods

  • Function with a receiver: func (r T) Method()
  • Value receiver — operates on a copy
  • Pointer receiver — can modify the original
  • Methods can be defined on any named type (not just structs)
  • Be consistent: if any method has pointer receiver, all should

Embedding (Composition)

  • Go has NO inheritance — uses composition
  • Embed a type: its fields/methods promoted to outer struct
  • type Admin struct { User }
  • Access as admin.User.Name or admin.Name
  • Outer struct can override embedded methods

Struct Tags

  • Metadata string for reflection tools
  • json:"name,omitempty" — JSON encoding
  • db:"created_at" — sqlc/GORM column name
  • validate:"required,min=3" — go-playground/validator
  • Key:"value" pairs, backtick string literal
Code Examples
type User struct {
    ID       int
    Name     string   `json:"name"`
    Email    string   `json:"email,omitempty"`
    password string   // unexported — not marshalled
}

// Value receiver — works on a copy
func (u User) String() string {
    return fmt.Sprintf("%s <%s>", u.Name, u.Email)
}

// Pointer receiver — can modify the original
func (u *User) SetName(name string) {
    u.Name = name // modifies the original
}

// Methods on non-struct types
type Celsius float64
func (c Celsius) ToFahrenheit() float64 { return float64(c)*9/5 + 32 }

// ── Embedding ─────────────────────────────────────
type Animal struct { Name string }
func (a Animal) Speak() string { return a.Name + " speaks" }

type Dog struct {
    Animal        // embedded — promotes Name and Speak()
    Breed  string
}

d := Dog{Animal: Animal{Name: "Rex"}, Breed: "Husky"}
fmt.Println(d.Speak()) // promoted method
fmt.Println(d.Name)    // promoted field

// Dog can override Speak:
func (d Dog) Speak() string { return d.Name + " barks!" }

// ── Anonymous struct ──────────────────────────────
config := struct {
    Host string
    Port int
}{"localhost", 8080}

// ── Struct comparison ─────────────────────────────
p1 := Point{1, 2}
p2 := Point{1, 2}
fmt.Println(p1 == p2) // true — comparable if all fields are
⚠️ Gotchas
Value receiver can't modify — using a value receiver on a struct and expecting to mutate it won't work. Changes are on the copy. Use pointer receiver for mutation.
Inconsistent receivers cause issues — if a type has both value and pointer receivers, it can't satisfy an interface requiring pointer methods via value variable.
Struct with unexported fields — cannot be copied from a different package directly. Provide a constructor function instead.
Embedding != inheritance — there is no polymorphism. The outer type IS-A inner type is NOT true in Go. Use interfaces for polymorphism.
Interview Q&A
When should you use a pointer receiver vs a value receiver?
Use pointer receiver when: (1) the method needs to modify the receiver, (2) the struct is large and you want to avoid copying, (3) you need consistent behavior with other methods that use pointer receivers. Use value receiver for small read-only structs, or when the method shouldn't modify the original.
How does Go achieve code reuse without inheritance?
Through struct embedding (composition). Embedding promotes fields and methods of the embedded type to the outer struct. Combined with interfaces, this gives polymorphic behaviour without class hierarchies. It's more flexible than inheritance — you can embed multiple types.

Interfaces

Theory

Implicit Satisfaction

  • No implements keyword
  • A type satisfies an interface if it has all the methods
  • Checked at compile time
  • Decouples definition from usage
  • Small interfaces preferred: io.Reader, io.Writer

Interface Values

  • Two-field header: (type, value) pair
  • nil interface: both type and value are nil
  • Typed nil: type is set, value is nil — NOT nil!
  • Interface == nil only when BOTH are nil
  • Calling method on nil interface → panic

Empty Interface (any)

  • interface{} = any (Go 1.18+ alias)
  • Every type satisfies it — holds any value
  • Used by fmt.Println(a ...any)
  • Prefer generics over any for typed collections
  • Type-assert to get concrete value back

Design Rules

  • "Accept interfaces, return concrete types"
  • Define interfaces on the consumer side (not producer)
  • Keep interfaces small — 1-2 methods ideal
  • Don't preemptively abstract — extract when needed
  • Use interfaces for testing (mock the dependency)
Code Examples
// ── Basic interface ───────────────────────────────
type Animal interface {
    Sound() string
    Name() string
}

type Dog struct{ name string }
func (d Dog) Sound() string { return "Woof" }
func (d Dog) Name() string  { return d.name }

type Cat struct{ name string }
func (c Cat) Sound() string { return "Meow" }
func (c Cat) Name() string  { return c.name }

// Both satisfy Animal implicitly
func describe(a Animal) {
    fmt.Printf("%s says %s\n", a.Name(), a.Sound())
}

// ── Typed-nil trap ────────────────────────────────
func getError() error {
    var p *MyError = nil
    return p  // NOT nil! interface has type=*MyError, val=nil
}
err := getError()
fmt.Println(err == nil) // false — common bug!

// Fix: return untyped nil
func getErrorFixed() error {
    return nil // both type and val are nil
}

// ── Interface composition ─────────────────────────
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }
type ReadWriter interface { Reader; Writer } // composed

// ── Compile-time interface check ──────────────────
var _ Animal = Dog{}    // fails at compile time if Dog doesn't implement Animal
var _ Animal = (*Dog)(nil) // for pointer receivers

// ── Repository pattern ────────────────────────────
type UserRepository interface {
    FindByID(ctx context.Context, id int) (*User, error)
    Save(ctx context.Context, u *User) error
}
// Service depends on interface — easy to mock in tests
type UserService struct { repo UserRepository }
⚠️ Gotchas
Typed-nil trap — returning a typed pointer as an interface value is NOT nil, even if the pointer is nil. Always return untyped nil for error/interface returns.
Interface on value vs pointer — if a method has a pointer receiver, only *T satisfies the interface, not T. Conversely, value receiver methods are in the method set of both T and *T.
Empty interface loses type info — once stored as any, you must type-assert to recover the original type. Prefer generics for typed operations.
Interview Q&A
What is the typed-nil trap in Go interfaces?
An interface value is nil only when BOTH its type and value fields are nil. If you return a nil pointer of a concrete type as an interface, the interface stores the type info — making it non-nil. Classic bug: var p *MyError = nil; return p — the returned error interface is not nil.
Why does Go prefer small interfaces?
Small interfaces (1-2 methods) are easier to implement, compose, and mock. io.Reader has just one method — any type with a Read() method satisfies it. Large interfaces create tight coupling and make mocking harder. This is known as the Interface Segregation Principle.
What is the difference between interface{} and any?
They are identical. any is a type alias for interface{} introduced in Go 1.18 for readability. Both hold a value of any type. Prefer any in new code.

Error Handling

Theory

Error Interface

  • type error interface { Error() string }
  • Any type with Error() string is an error
  • errors.New("msg") — simple sentinel
  • fmt.Errorf("ctx: %w", err) — wrap with context

Sentinel Errors

  • Package-level var ErrNotFound = errors.New("not found")
  • Check with errors.Is(err, ErrNotFound)
  • Works through wrapping chain
  • Export if callers need to check: ErrXxx

Custom Error Types

  • Struct implementing error interface
  • Carries extra context (status code, field, etc.)
  • Extract with errors.As(err, &myErr)
  • Use pointer receiver on Error() for consistency

Wrapping (Go 1.13+)

  • fmt.Errorf("op failed: %w", err) wraps err
  • errors.Is — checks value (sentinel)
  • errors.As — checks type (custom errors)
  • errors.Unwrap — get the wrapped error
  • Chain: errors.Join (Go 1.20+)
Code Examples
// ── Sentinel error ────────────────────────────────
var ErrNotFound = errors.New("not found")

func FindUser(id int) (*User, error) {
    if id == 0 { return nil, ErrNotFound }
    return &User{}, nil
}

u, err := FindUser(0)
if errors.Is(err, ErrNotFound) {
    // handle not found
}

// ── Custom error type ─────────────────────────────
type ValidationError struct {
    Field   string
    Message string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation failed: %s — %s", e.Field, e.Message)
}

func validate(age int) error {
    if age < 0 { return &ValidationError{Field: "age", Message: "must be >= 0"} }
    return nil
}

var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println("field:", ve.Field) // extract structured info
}

// ── Wrapping for context ──────────────────────────
func loadConfig(path string) error {
    data, err := os.ReadFile(path)
    if err != nil {
        return fmt.Errorf("loadConfig: %w", err) // wrap with context
    }
    _ = data
    return nil
}

// errors.Is unwraps the chain:
if errors.Is(err, os.ErrNotExist) { ... } // works even if wrapped

// ── errors.Join (Go 1.20) ─────────────────────────
err1 := errors.New("db failed")
err2 := errors.New("cache failed")
combined := errors.Join(err1, err2)
errors.Is(combined, err1) // true
⚠️ Gotchas
Never use == to compare wrapped errors — use errors.Is(). Direct comparison breaks if the error was wrapped with %w.
errors.As needs a pointer to pointer — errors.As(err, &ve) where ve is *ValidationError. Passing the wrong type silently fails.
Don't wrap and log — either wrap with context and propagate, OR log and handle. Doing both causes duplicate log entries and confusing traces.
%w vs %v — %v embeds the error message as a string (unwrappable chain broken). %w wraps it in the chain. Always use %w when propagating.
Interview Q&A
What is the difference between errors.Is and errors.As?
errors.Is checks if any error in the chain matches a specific value (sentinel comparison). errors.As checks if any error in the chain matches a specific type and extracts it. Use Is for sentinel errors, As for custom error types that carry additional data.
How do you add context to an error without losing the original?
Use fmt.Errorf("context: %w", err). The %w verb wraps the error, preserving the chain. Callers can then use errors.Is and errors.As to inspect the original error through the wrapping layers.
When should you use panic vs returning an error?
Return errors for expected failure cases (file not found, invalid input, network timeout). Use panic only for truly unrecoverable situations (programmer errors like nil pointer dereference, invalid array index, or startup failures that make the program unable to function).

Pointers & Memory

Theory

Pointers

  • *T — pointer to T value
  • &x — address of x (takes address)
  • *p — dereference (value at address)
  • Zero value: nil
  • No pointer arithmetic (unlike C)

Stack vs Heap

  • Stack: function-local vars, fast allocation/deallocation
  • Heap: long-lived allocations managed by GC
  • Go decides automatically via escape analysis
  • Variable "escapes" to heap when it outlives its function
  • Returning a pointer to a local var is safe in Go (unlike C)

Escape Analysis

  • go build -gcflags="-m" — see escape analysis
  • Variables taken by address often escape to heap
  • Interfaces often cause escape (dynamic dispatch)
  • Heap allocation = more GC pressure
  • Don't over-optimize — profile first

new() builtin

  • new(T) allocates zeroed T, returns *T
  • Rarely used — struct literals preferred
  • new(int) = &int(0) essentially
  • make() for slices, maps, channels (initializes structure)
  • new() just zeros memory, no internal init
Code Examples
// ── Pointer basics ────────────────────────────────
x := 42
p := &x          // p is *int
fmt.Println(*p)  // 42 — dereference
*p = 100         // modifies x through pointer
fmt.Println(x)   // 100

// ── Returning pointer to local is SAFE ────────────
func newPoint(x, y int) *Point {
    p := Point{x, y} // local variable
    return &p        // safe: Go compiler moves p to heap
}

// ── new() builtin (rarely needed) ─────────────────
p1 := new(int)       // *int, value is 0
p2 := &int(0)        // equivalent (can't do this syntax exactly)
p3 := new(User)      // *User, all fields zeroed

// Prefer struct literal:
u := &User{Name: "Alice"} // allocates on heap, sets Name

// ── Nil pointer dereference panic ─────────────────
var p *int
// fmt.Println(*p) // PANIC: nil pointer dereference
if p != nil { fmt.Println(*p) } // safe guard

// ── When to use *T ────────────────────────────────
// ✅ Need to modify the value
// ✅ Large struct (avoid copying)
// ✅ Nil has semantic meaning (optional value)
// ❌ Don't use *T for small immutable data — just copy it

// ── Escape analysis check ─────────────────────────
// go build -gcflags="-m" 2>&1 | grep "escapes"
⚠️ Gotchas
Nil pointer dereference — most common Go panic. Always check if p != nil before dereferencing pointers from external sources.
Pointer to loop variable (pre-Go 1.22) — all goroutines share the same loop variable address. Fixed in 1.22; in older code, copy: v := v.
No pointer arithmetic — you cannot do p++ to walk through memory like in C. Use slices for sequential access.
GC doesn't mean no memory management — creating many small heap allocations still causes GC pressure. Use value types and sync.Pool for hot paths.
Interview Q&A
Is it safe to return a pointer to a local variable in Go?
Yes, unlike C. Go's escape analysis detects that the variable's address is returned and automatically moves it to the heap. The GC manages its lifetime. func newPoint() *Point { p := Point{1,2}; return &p } is perfectly safe.
What is escape analysis and why does it matter?
Escape analysis determines at compile time whether a variable can live on the stack or must be allocated on the heap. Stack allocation is much faster (no GC). Variables that "escape" (address taken and returned, stored in interface, etc.) go to heap. Use go build -gcflags="-m" to see what escapes.

Packages & Modules

Theory

Packages

  • Unit of code organization — directory = package
  • Exported: starts with uppercase letter
  • Unexported: lowercase — package-private
  • Package name ≠ import path (but conventionally same)
  • package main + func main() = executable

Modules (go.mod)

  • go mod init module/path — creates go.mod
  • go.mod declares: module path, Go version, dependencies
  • go.sum: cryptographic checksums for security
  • go mod tidy — sync go.mod with actual imports
  • Module path = how others import your code

internal/ package

  • Code in internal/ can only be imported by parent and sibling packages
  • Prevents external packages from importing your internals
  • Standard pattern: pkg/internal/store/
  • Enforced by the compiler — not just convention

init() function

  • Runs automatically when package is first imported
  • Cannot be called manually
  • Multiple init() in same file/package allowed
  • Used for: registering drivers, setting defaults
  • Blank import: import _ "pkg" — side effects only
Code Examples
// ── Package visibility ────────────────────────────
package user

type User struct {          // exported
    Name  string            // exported field
    email string            // unexported — only accessible in user package
}

func NewUser(name, email string) *User {
    return &User{Name: name, email: email} // constructor pattern
}

// ── go.mod example ────────────────────────────────
// module github.com/myorg/myapp
//
// go 1.22
//
// require (
//     github.com/gin-gonic/gin v1.9.1
//     github.com/jackc/pgx/v5 v5.5.0
// )

// ── Import aliases ────────────────────────────────
import (
    "fmt"
    rand "math/rand"     // alias
    _ "github.com/lib/pq" // blank import (register pq driver)
    . "math"              // dot import (unqualified access — avoid)
)

// ── init() ────────────────────────────────────────
func init() {
    // runs once when package is imported
    // common use: validate config, register things
    if os.Getenv("DB_URL") == "" {
        log.Fatal("DB_URL is required")
    }
}

// ── Cyclic imports ────────────────────────────────
// Package A imports B, B imports A → COMPILE ERROR
// Fix: extract shared types to a third package C
//      A → C, B → C (no cycle)
⚠️ Gotchas
Cyclic imports compile error — Go forbids A → B → A. Restructure: extract shared types to a common package.
Package name vs import path — import "github.com/foo/bar/v2" → the package is accessed as bar.Something(), not v2.Something().
init() order is deterministic within a package but depends on import order across packages. Avoid relying on complex init() ordering.
Dot import is an anti-pattern — import . "math" puts all exported names in current scope. Makes code hard to read and can cause name collisions.
Interview Q&A
How does Go enforce API boundaries within a project?
Through the internal/ package convention enforced by the compiler. Code in internal/ can only be imported by code in the parent directory tree. This lets you have internal helpers without exposing them as public API, even within the same module.
What is the difference between go.mod and go.sum?
go.mod declares your module path, Go version, and required dependencies with version constraints. go.sum contains cryptographic hashes of every module version used. go.sum is used to verify downloads haven't been tampered with. Both should be committed to version control.
