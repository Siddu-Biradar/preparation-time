Phase 0 Getting Started — Installation & Setup

Before writing any code, you need MongoDB installed and running. This phase walks you through everything: what each tool is, how to install it, and how to verify it's working.

What is MongoDB? (The 30-Second Version)

  • MongoDB = A database that stores JSON-like documents instead of rows/columns
  • Not a spreadsheet — It's optimized for flexible, nested data (perfect for modern applications)
  • Not SQL — Different query syntax, but same core concepts (find, filter, group)
  • Open source — You can run it yourself or use MongoDB's cloud service

MongoDB Flavors Explained

The Three Tools:

  • mongod = The MongoDB server (the actual database process)
    → This runs in background and stores your data
    → You interact with it via mongosh
    → On macOS: brew services start mongodb-community
  • mongosh = Modern interactive shell (what you use to write queries)
    → Type commands like: db.users.find()
    → The recommended MongoDB shell (2022 onwards)
    → On macOS: mongosh to launch
  • mongo = Old deprecated shell (don't use this anymore)
    → Replaced by mongosh in 2022
    → If someone tells you to use "mongo", they're outdated — use "mongosh" instead

MongoDB Editions:

  • Community = Open source, free, runs on your machine
    → Perfect for learning, dev, and production (no cost)
    → What you'll use for this guide
  • Enterprise = Commercial, paid, includes support + security features
    → Used by companies that need support contracts
    → Not needed for learning
  • Atlas = MongoDB cloud-managed (SaaS)
    → MongoDB runs servers FOR you in the cloud (AWS, GCP, Azure)
    → Free tier (M0): 512MB storage, great for learning
    → Pay as you grow when you need more

Phase 1 MongoDB Fundamentals — The Mental Model Shift

Everything you build later depends on getting this right. You MUST internalize the MongoDB way of thinking before any query makes sense.

SQL to MongoDB Mapping

  • Database → Database (same)
  • Table → Collection
  • Row → Document
  • Column → Field
  • Primary Key → _id (auto-generated ObjectId if not provided)
  • Schema → Flexible (no fixed columns)
  • JOIN → Embedding OR $lookup in aggregation

Document Structure

MongoDB documents are JSON-like objects:

{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "Sid Rameshwar",
  "age": 28,
  "email": "sid@example.com",
  "tags": ["golang", "backend"],
  "address": {
    "city": "San Francisco",
    "zip": "94105"
  },
  "createdAt": ISODate("2024-01-15T10:30:00Z")
}

BSON Types (Not Just JSON)

  • ObjectId — 12-byte unique ID, sortable, contains timestamp
  • String — UTF-8 encoded text
  • Int32, Int64, Double, Decimal128 — number types
  • Boolean — true/false
  • Date — milliseconds since Unix epoch
  • Array — ordered list of values
  • Object — nested document
  • Null — missing/empty field
  • Binary — raw bytes (images, files)

Why MongoDB? (Real Reasons)

  • Flexible Schema: Each microservice in your codebase stores different data shapes in the same collection. SQL requires ALTER TABLE; MongoDB allows it.
  • Horizontal Scaling: Sharding spreads data across machines. Your services grow without buying bigger hardware.
  • Document Shape Matches APIs: JSON request → JSON document → JSON response. No mapping layer needed.
  • Aggregation: Complex data transformations are native operations, not application logic.
  • Embedded Documents: Related data in one place. No JOIN overhead for common queries.

Key Interview Questions

Q: Why use MongoDB instead of PostgreSQL?
A: MongoDB excels when: (1) schema evolves frequently (microservices with different data shapes), (2) horizontal scaling is needed (shard across machines), (3) data is naturally hierarchical (nested documents), (4) you need JSON-native APIs. PostgreSQL is better for relational data with fixed schemas and complex JOINs.
Q: Explain ObjectId. Why does it matter?
A: ObjectId is a 12-byte value: 4-byte timestamp + 5-byte machine ID + 3-byte counter. (1) It's unique globally across all machines. (2) It's sortable (ordered by creation time). (3) It contains the creation timestamp without a separate timestamp field. (4) In your codebase, ObjectIds are used as document IDs across all services.
Q: Is MongoDB schema-less? Can you enforce structure?
A: MongoDB is schema-less by default — any document can have any fields. But you CAN enforce a schema using $jsonSchema validation at the collection level. Best practice: enforce in DB ($jsonSchema) + application layer (Go struct tags). Your sonarqube service uses Go struct marshaling for validation.
GOTCHA: null in MongoDB and missing field are different. A query { age: null } matches documents where age=null OR age field doesn't exist. Use { $exists: false } to match only missing fields.
PRODUCTION: Your jfrog service stores artifact metadata with varying fields per repository type. SQL would require separate tables; MongoDB handles it with flexible documents. Your sonarqube service stores scan results from different languages—each has different analysis fields. MongoDB's flexibility is essential here.

Phase 2 CRUD Operations — The Foundation of Everything

60% of what you do in production is CRUD. Master these to perfection. You should be able to write all 4 operations without opening documentation.

CREATE: Insert

Shell:
// Insert one document
db.users.insertOne({ name: "Sid", age: 28 })

// Insert many (one network round-trip, not N)
db.users.insertMany([
  { name: "Alice", age: 25 },
  { name: "Bob", age: 30 }
])

// Returns: { insertedId: ObjectId(...) }
Go Driver:
// Single insert
result, err := col.InsertOne(ctx, bson.M{
  "name": "Sid",
  "age": 28,
})
// err = nil if successful, result.InsertedID is the _id

// Batch insert
results, err := col.InsertMany(ctx, []interface{}{
  bson.M{"name": "Alice", "age": 25},
  bson.M{"name": "Bob", "age": 30},
})
// results.InsertedIDs is []interface{} of all IDs
  • MongoDB auto-creates _id if not provided
  • You CAN provide your own _id (must be unique)
  • Collection is auto-created on first insert
  • Use InsertMany for batch operations (1 network call vs N)

READ: Find

Shell:
// Find all documents
db.users.find()

// Find with filter
db.users.find({ age: 28 })

// Find one (returns first match or null)
db.users.findOne({ email: "sid@example.com" })

// With projection (select fields)
db.users.find({}, { name: 1, email: 1, _id: 0 })

// With sort, limit, skip
db.users.find().sort({ createdAt: -1 }).limit(10).skip(20)
Go Driver:
// Find one
var result bson.M
err := col.FindOne(ctx, bson.M{"email": "sid@example.com"}).Decode(&result)
if err == mongo.ErrNoDocuments {
  // No match found (not a real error)
}

// Find many (returns cursor)
cursor, err := col.Find(ctx, bson.M{"age": bson.M{"$gte": 25}})
defer cursor.Close(ctx)

// Decode all results
var results []bson.M
err = cursor.All(ctx, &results)

// Or iterate
for cursor.Next(ctx) {
  var doc bson.M
  cursor.Decode(&doc)
}
  • Find returns a cursor (lazy evaluation)
  • FindOne fetches just one document
  • Always check for mongo.ErrNoDocuments in Go
  • Projections reduce network bandwidth
  • Order: filter → sort → skip → limit

UPDATE: Modify Existing

Shell:
// Update one document
db.users.updateOne(
  { email: "sid@example.com" },
  { $set: { age: 29, updated: new Date() } }
)

// Update many matching
db.users.updateMany(
  { status: "inactive" },
  { $set: { active: false } }
)

// Find and update (returns the doc)
db.users.findOneAndUpdate(
  { _id: ObjectId("...") },
  { $set: { lastLogin: new Date() } },
  { returnDocument: "after" }
)
Go Driver:
// Update one
result, err := col.UpdateOne(ctx,
  bson.M{"email": "sid@example.com"},
  bson.M{"$set": bson.M{"age": 29}},
)
// result.ModifiedCount tells you how many docs were updated

// Find and update (returns the doc)
var updated bson.M
err := col.FindOneAndUpdate(ctx,
  bson.M{"_id": id},
  bson.M{"$set": bson.M{"lastLogin": time.Now()}},
  options.FindOneAndUpdate().SetReturnDocument(options.After),
).Decode(&updated)
  • $set modifies only specified fields
  • replaceOne replaces entire document (dangerous!)
  • Always use $set in production (safer than replace)
  • ModifiedCount can be 0 if no documents matched

DELETE: Remove Data

Shell:
// Delete one document
db.users.deleteOne({ email: "sid@example.com" })

// Delete many matching
db.users.deleteMany({ status: "deleted" })

// Delete entire collection
db.users.drop()

// Before deletion: always preview with find
db.users.find({ status: "deleted" }).count()
Go Driver:
// Delete one
result, err := col.DeleteOne(ctx, bson.M{"email": "sid@example.com"})
// result.DeletedCount

// Delete many
result, err := col.DeleteMany(ctx, bson.M{"status": "deleted"})
// result.DeletedCount
  • Deletion is immediate — no trash bin
  • Safety rule: Always run find() with same filter first
  • DeletedCount can be 0 if no match
  • Cannot delete individual array elements easily; use $pull update instead

Interview Questions: CRUD

Q: Difference between updateOne and updateMany?
A: updateOne updates the first matching document. updateMany updates all matching documents. Always sure which one you want — accidental updateMany is a common bug.
Q: What does InsertMany do vs individual InsertOne calls?
A: InsertMany sends all inserts in one network round-trip. 1000 individual InsertOne calls = 1000 round-trips (slow). One InsertMany with 1000 docs = 1 round-trip (fast). Your jfrog service uses this for bulk artifact inserts.
Q: What is findOneAndUpdate and when would you use it?
A: findOneAndUpdate atomically updates a document and returns it (original or updated, your choice). Useful when you need to know the final state immediately. Your nwayfw service uses this pattern for inventory updates.
GOTCHA: db.find() does NOT return an array — it returns a Cursor. In Go, you must call cursor.All(ctx, &results) to get an array. Not calling All() means you're iterating lazily, which is fine for large datasets but not if you expect a complete list.
GOTCHA: FindOne with no match returns mongo.ErrNoDocuments. This is NOT a real error — it's an expected result. Always check if err == mongo.ErrNoDocuments separately from other errors.
PRODUCTION: Your sonarqube service batch-inserts 1000s of scan results. It uses InsertMany, not individual inserts. Similarly, your jfrog service bulk-updates artifacts with upsert=true, hitting multiple documents in one call via BulkWrite.

Phase 3 Query Operators — Expressing Complex Filters

Basic find({ age: 25 }) only works for exact matches. Real queries use operators: greater than, in a list, regular expressions, etc. These are used constantly in your codebase.

Comparison Operators

Common operators:
// $eq: equal (same as plain field: value)
{ age: { $eq: 25 } }

// $ne: not equal
{ status: { $ne: "deleted" } }

// $gt, $gte, $lt, $lte: greater/less than
{ age: { $gt: 25, $lt: 65 } }

// $in: field value is in an array
{ status: { $in: ["active", "pending"] } }

// $nin: field value is NOT in an array
{ role: { $nin: ["admin", "root"] } }
  • $in is very common in your code (sonarqube, jfrog)
  • $nin = NOT in list (opposite of $in)
  • $eq is rarely needed (plain object is cleaner)

Logical Operators

Combine conditions:
// $and: ALL conditions must be true
{ $and: [
  { age: { $gt: 18 } },
  { status: "active" }
] }

// $or: ANY condition must be true
{ $or: [
  { role: "admin" },
  { department: "DevOps" }
] }

// $not: negate a condition
{ age: { $not: { $gt: 65 } } }

// $nor: NONE of the conditions are true
{ $nor: [
  { deleted: true },
  { archived: true }
] }
  • $and is implicit when you write { a: 1, b: 2 }
  • $or requires explicit syntax
  • $nor = NOT ($or)

Element Operators

Check field existence/type:
// $exists: field exists (or doesn't)
{ phone: { $exists: true } }
{ phone: { $exists: false } }  // missing field

// $type: field is a specific BSON type
{ age: { $type: "int" } }
{ email: { $type: "string" } }
  • Used in your jfrog service for artifact field validation
  • $exists: false differs from $eq: null (latter matches null values too)

Array Operators

Query array fields:
// $all: array contains ALL these values
{ tags: { $all: ["go", "backend"] } }

// $size: array has exactly N elements
{ tags: { $size: 3 } }

// $elemMatch: at least one element matches ALL conditions
{ comments: { $elemMatch: { 
    author: "Sid",
    score: { $gte: 5 }
  }
}}
  • $all is used in your sonarqube service for tag filtering
  • $size cannot be used with other operators on the same field

Text & Regex Operators

Pattern matching:
// $regex: pattern match (like LIKE in SQL)
{ name: { $regex: "^Sid", $options: "i" } }  // case-insensitive

// $text: full-text search (requires text index)
{ $text: { $search: "mongodb golang" } }

// $where: JavaScript (AVOID in production)
{ $where: "this.age > 25" }  // SLOW!
  • $regex is common but not as fast as indexed fields
  • $text requires a text index first
  • $where executes JavaScript per document — never use in production

Go Driver: Query Examples

Go code:
// Find users where age > 25 AND status = "active"
filter := bson.M{
  "age": bson.M{"$gt": 25},
  "status": "active",
}
cursor, _ := col.Find(ctx, filter)

// Find where role is in ["admin", "dev"]
filter := bson.M{
  "role": bson.M{"$in": []string{"admin", "dev"}},
}

// Find where tags array contains both "go" and "backend"
filter := bson.M{
  "tags": bson.M{"$all": []string{"go", "backend"}},
}

Interview Questions: Query Operators

Q: When should you use $in vs $eq with multiple values?
A: { role: { $in: ["admin", "dev"] } } is cleaner than { $or: [{ role: "admin" }, { role: "dev" }] }. Always prefer $in for checking if a field is one of several values.
Q: How do $or and $and combine? Is there an implicit AND?
A: Yes, fields at the top level have an implicit AND. { age: 25, status: "active" } means age=25 AND status="active". To use OR, you must be explicit: { $or: [...] }.
Q: What is the difference between { age: null } and { age: { $exists: false } }?
A: { age: null } matches documents where age field=null OR the field doesn't exist. { age: { $exists: false } } matches only documents where the age field is missing entirely.
GOTCHA: $in with an empty array { field: { $in: [] } } matches NO documents. If your code builds a dynamic filter list and it's empty, remember this will return 0 results, not all documents.
PRODUCTION: Your develop service filters issues by { status: { $in: ["open", "in-progress"] } }. Your sonarqube service filters projects by language: { language: { $in: ["go", "python"] } }. This pattern is everywhere.

Phase 4 Update Operators — Surgical Modifications

Never replace an entire document just to change one field. MongoDB provides operators to modify exactly what you need. These keep your code clean and fast.

Field Update Operators

Modify individual fields:
// $set: set field value (most common)
{ $set: { status: "active", updated: new Date() } }

// $unset: remove a field
{ $unset: { deprecated_field: "" } }

// $inc: increment a number field
{ $inc: { views: 1, score: 5 } }

// $mul: multiply a number
{ $mul: { price: 1.1 } }  // 10% increase

// $rename: rename a field
{ $rename: { "oldName": "newName" } }

// $min: update only if new value is smaller
{ $min: { salary: 50000 } }

// $max: update only if new value is larger
{ $max: { maxScore: 100 } }

// $currentDate: set field to current timestamp
{ $currentDate: { lastModified: true } }
  • $set is the most common in production
  • $inc is atomic (no race conditions)
  • $unset removes the field entirely

Array Update Operators

Modify array fields:
// $push: add element to array
{ $push: { tags: "go" } }

// $pull: remove matching elements from array
{ $pull: { tags: "deprecated" } }

// $addToSet: add to array only if not already present
{ $addToSet: { languages: "python" } }

// $pop: remove first (-1) or last (1) element
{ $pop: { history: 1 } }  // remove last

// $each: push multiple elements
{ $push: { tags: { $each: ["go", "api", "backend"] } } }

// $sort + $slice: sort array then keep first N
{ $push: {
    scores: { 
      $each: [85, 92],
      $sort: -1,
      $slice: 10
    }
  }
}
  • $push allows duplicates
  • $addToSet prevents duplicates (set behavior)
  • $pull is used in your develop service to remove resolved items

Upsert — Update OR Insert

Upsert pattern:
// Shell
db.users.updateOne(
  { email: "sid@example.com" },
  { $set: { name: "Sid", updated: new Date() } },
  { upsert: true }
)

// Go driver
opts := options.Update().SetUpsert(true)
result, err := col.UpdateOne(ctx,
  bson.M{"email": "sid@example.com"},
  bson.M{"$set": bson.M{"name": "Sid"}},
  opts,
)
// result.UpsertedID will be set if insert happened
  • Upsert = Update + Insert
  • If filter matches → update the document
  • If filter doesn't match → insert a new document
  • Eliminates need for find-then-insert pattern
  • Your nwayfw service uses this heavily for inventory management

$setOnInsert — Control Upsert Behavior

Only set fields on insert:
// Update: increment counter
// Insert: set counter = 1, set createdAt
db.stats.updateOne(
  { metric: "requests" },
  {
    $inc: { count: 1 },
    $setOnInsert: { 
      createdAt: new Date(),
      count: 1  // initialize count to 1
    }
  },
  { upsert: true }
)
  • $setOnInsert only applies when upsert inserts a new document
  • On updates, $setOnInsert is ignored
  • Perfect for initialization on first occurrence

BulkWrite — Batch Multiple Operations

Shell:
db.users.bulkWrite([
  {
    insertOne: { document: { name: "Sid", age: 28 } }
  },
  {
    updateOne: {
      filter: { email: "alice@example.com" },
      update: { $set: { active: true } }
    }
  },
  {
    deleteMany: { filter: { status: "deleted" } }
  }
])
// Returns: { insertedCount, modifiedCount, deletedCount }
Go Driver:
models := []mongo.WriteModel{
  mongo.NewInsertOneModel().SetDocument(bson.M{"name": "Sid"}),
  mongo.NewUpdateOneModel().
    SetFilter(bson.M{"email": "alice@example.com"}).
    SetUpdate(bson.M{"$set": bson.M{"active": true}}),
  mongo.NewDeleteManyModel().
    SetFilter(bson.M{"status": "deleted"}),
}

result, err := col.BulkWrite(ctx, models)
// result.InsertedCount, result.ModifiedCount, result.DeletedCount
  • BulkWrite sends all operations in one network call
  • Orders: ordered: true (stop on error), ordered: false (continue on error)
  • Your jfrog service uses this for batch artifact updates
  • 100 BulkWrite operations = 1 network call (vs 100 individual calls)

Interview Questions: Update Operators

Q: Explain the difference between $push and $addToSet.
A: $push always appends to an array, even if the value exists (allows duplicates). $addToSet only adds if the value doesn't already exist (set semantics, no duplicates). Use $addToSet for tags/labels, $push for logs/events.
Q: What is upsert and when would you use it?
A: Upsert = update + insert. If the filter matches an existing document, update it. If not, insert a new one. Advantages: (1) eliminates race conditions, (2) one operation instead of find-then-insert, (3) atomic. Your streaming service uses it for inventory updates.
Q: Why use BulkWrite instead of individual updateOne calls?
A: BulkWrite sends all operations in one network round-trip. 1000 individual calls = 1000 network round-trips (slow). One BulkWrite with 1000 models = 1 round-trip (fast). Can reduce latency from seconds to milliseconds for large batch operations.
GOTCHA: If you use $set: { } (empty object), MongoDB does nothing. Not an error, just silently no-op. This can hide bugs in your code if you're conditionally building the update object.
GOTCHA: $inc on a field that doesn't exist creates it with value=N. $inc: { counter: 1 } on a non-existent field results in counter=1. This is a feature (initialization) but watch out for unexpected fields.
PRODUCTION: Your jfrog service uses BulkWrite to update 1000s of artifacts in seconds. Your develop service uses $push to append events to issue history. Your sonarqube service uses $inc to update scan counters atomically without race conditions.

Phase 5 Aggregation Pipeline — Data Transformation Power

Aggregation is MongoDB's most powerful feature. Think of it as SQL's GROUP BY + SELECT + JOINs all built-in. This is what separates good MongoDB code from great code. Master this.

Pipeline Stages (In Order)

  • $match → Filter documents (like WHERE)
  • $sort → Order results
  • $skip → Skip first N
  • $limit → Take first N
  • $project → Select/reshape fields
  • $group → Summarize/aggregate
  • $unwind → Flatten arrays
  • $lookup → JOIN to another collection
  • $facet → Run multiple sub-pipelines
  • $out → Write results to collection
💡 Golden Rule: Always put $match FIRST to reduce documents early. Filtering 10M → 100 at the start is way faster than filtering after expensive operations.

$match: Filter Early

Start pipeline with $match:
db.orders.aggregate([
  { $match: { status: "completed", amount: { $gte: 100 } } },
  { $group: { _id: "$userId", total: { $sum: "$amount" } } }
])

// Go driver
pipeline := mongo.Pipeline{
  bson.D{{Key: "$match", Value: bson.D{
    {Key: "status", Value: "completed"},
  }}},
}
  • Filters input to the pipeline
  • Supports all query operators: $gt, $in, $and, etc.
  • Dramatically reduces data processed in downstream stages

$group: Summarize Data

Aggregate by field:
// Total spent per user
db.orders.aggregate([
  { $group: {
    _id: "$userId",
    total: { $sum: "$amount" },
    count: { $sum: 1 },
    avg: { $avg: "$amount" },
    max: { $max: "$amount" }
  }}
])

// Group ALL documents (pass null as _id)
db.orders.aggregate([
  { $group: {
    _id: null,
    totalRevenue: { $sum: "$amount" },
    avgOrder: { $avg: "$amount" }
  }}
])
Accumulators:
$sum     // total or count
$avg     // average
$min     // minimum
$max     // maximum
$count   // count documents
$push    // array of values (collect)
$addToSet // array of unique values
$first   // first value (with sort)
$last    // last value (with sort)
  • _id is the group-by field
  • _id: null = group everything
  • $sum: 1 counts documents

$project: Shape Output

Select and compute fields:
// Include only certain fields
{ $project: { name: 1, email: 1, _id: 0 } }

// Rename fields
{ $project: { userName: "$name" } }

// Compute new fields
{ $project: {
    fullName: { $concat: ["$first", " ", "$last"] },
    age: { $year: new Date() - "$birthYear" },
    isActive: { $cond: [
      { $eq: ["$status", "active"] },
      true,
      false
    ]}
  }
}
  • 1 = include, 0 = exclude
  • $fieldName references existing fields
  • Expression functions: $concat, $substr, $toUpper, $cond, etc.

$lookup: JOIN Collections

Join users with orders:
db.orders.aggregate([
  { $lookup: {
    from: "users",
    localField: "userId",
    foreignField: "_id",
    as: "user"
  }},
  { $project: {
    orderId: 1,
    amount: 1,
    "user.name": 1,
    "user.email": 1
  }}
])

// Go example
pipeline := mongo.Pipeline{
  bson.D{{Key: "$lookup", Value: bson.D{
    {Key: "from", Value: "users"},
    {Key: "localField", Value: "userId"},
    {Key: "foreignField", Value: "_id"},
    {Key: "as", Value: "user"},
  }}},
}
  • from: collection to join
  • localField: field in current doc
  • foreignField: field in foreign collection
  • as: array name for results (nested inside output doc)
  • Similar to LEFT JOIN in SQL
  • user is an array (can be empty if no match)

$unwind: Flatten Arrays

Expand array elements to separate docs:
// Before:
{ _id: 1, user: "Sid", tags: ["go", "api", "backend"] }

// After $unwind: "$tags"
{ _id: 1, user: "Sid", tags: "go" }
{ _id: 1, user: "Sid", tags: "api" }
{ _id: 1, user: "Sid", tags: "backend" }

// Then you can $group by tags
{ $unwind: "$tags" },
{ $group: { _id: "$tags", count: { $sum: 1 } } }
// Result: count of documents per tag
  • $unwind creates one output doc per array element
  • Required before you can group by array values
  • Can significantly increase document count in pipeline

Real Pipeline Example: Revenue Report

Calculate total revenue per user, top 10, last 30 days:
db.orders.aggregate([
  // 1. Filter to recent completed orders
  { $match: {
    status: "completed",
    createdAt: { $gte: new Date(Date.now() - 30*24*60*60*1000) }
  }},
  
  // 2. Group by user, sum revenue
  { $group: {
    _id: "$userId",
    totalRevenue: { $sum: "$amount" },
    orderCount: { $sum: 1 },
    avgOrder: { $avg: "$amount" }
  }},
  
  // 3. Sort descending
  { $sort: { totalRevenue: -1 } },
  
  // 4. Take top 10
  { $limit: 10 },
  
  // 5. Join with user details
  { $lookup: {
    from: "users",
    localField: "_id",
    foreignField: "_id",
    as: "userData"
  }},
  
  // 6. Shape output
  { $project: {
    userId: "$_id",
    _id: 0,
    totalRevenue: 1,
    orderCount: 1,
    avgOrder: 1,
    userName: { $arrayElemAt: ["$userData.name", 0] },
    userEmail: { $arrayElemAt: ["$userData.email", 0] }
  }}
])

Interview Questions: Aggregation

Q: Explain the aggregation pipeline. What order do stages execute?
A: Stages execute in the order you define them, left-to-right. The output of one stage becomes the input to the next. Always put $match first to reduce data early. Order matters: $match → $sort → $skip → $limit → $group is better than grouping first then filtering.
Q: What is the difference between $lookup and embedding?
A: Embedding stores related data in one document (one read). $lookup does a JOIN (slower, multiple reads). Use $lookup when data is shared between many documents or grows large. Embedding is faster for one-to-few relationships.
Q: When would you use $group with _id: null?
A: When you want to compute aggregates across ALL documents. Example: { $group: { _id: null, totalRevenue: { $sum: "$amount" } } } gives you the total revenue across all orders. Without _id:null, you'd group by a specific field.
Q: Why should $match come first in a pipeline?
A: Filter as early as possible to reduce documents in the pipeline. If you have 10M orders but only 100 completed ones, put $match first. Grouping 10M then filtering is 100x slower than filtering 10M to 100, then grouping 100.
GOTCHA: $unwind on an empty array or missing field drops the entire document. To keep docs with empty/missing arrays, use { $unwind: { path: "$tags", preserveNullAndEmptyArrays: true } }.
PRODUCTION: Your develop service uses aggregation to calculate metrics per developer: $match recent commits, $group by author, $lookup user data. Your sonarqube service aggregates scan results across projects: $group by language, $sum issues, $sort to get top projects by issue count.

Phase 6 Indexing & Query Performance — Make Queries Fast

Without indexes, MongoDB scans every document (Collection Scan = slow). With indexes, it jumps directly to matches (Index Scan = fast). This phase teaches you to think about performance from day 1.

What is an Index?

  • A B-tree data structure MongoDB maintains separately from your data
  • Without index: COLLSCAN = read ALL documents to find matches
  • With index: IXSCAN = jump directly to matching documents
  • Trade-off: indexes make reads faster but writes slightly slower (index must be updated)
  • Rule: index fields you frequently filter on, sort on, or query ranges

Index Types

  • Single-field: { email: 1 } → ascending or -1 descending
  • Compound: { userId: 1, createdAt: -1 } → multiple fields
  • Multikey: Auto-created when indexing array fields
  • Text: Full-text search: { $text: { $search: "..." } }
  • Unique: Prevents duplicate values: { unique: true }
  • TTL: Auto-deletes docs after N seconds (great for sessions)
  • Geospatial: For location queries: $near, $within
  • Sparse: Only index docs where field exists

ESR Rule for Compound Indexes

Order fields correctly in compound index:
// Rule: Equality → Sort → Range
// DON'T: { createdAt: -1, userId: 1, status: 1 }
// YES:   { userId: 1, status: 1, createdAt: -1 }

// Query: find users where status="active", sort by createdAt, filter by date range
// Filter by userId (equality) → filter by status (equality) → sort by createdAt → filter range
// Index: { userId: 1, status: 1, createdAt: -1 }
  • E: Equality fields first (exact match)
  • S: Sort fields next
  • R: Range fields last ($gt, $lt, $in)
  • A compound index on { a:1, b:1, c:1 } also supports queries on { a:1 } and { a:1, b:1 }, but NOT on { b:1 } alone

Reading Execution Plans

Use explain() to diagnose:
// Shell
db.users.find({ email: "x" }).explain("executionStats")

// Go driver
opts := options.Find().SetHint(bson.M{"email": 1})
cursor, _ := col.Find(ctx, filter, opts)

// Look for:
// "executionStages": {
//   "stage": "IXSCAN"  ← Good, used index
//   vs
//   "stage": "COLLSCAN" ← Bad, full scan
// },
// "totalDocsExamined": 1000,
// "nReturned": 10
// If examined >>> returned, you need a better index
  • IXSCAN = good (used index)
  • COLLSCAN = bad (full scan)
  • totalDocsExamined vs nReturned → if far apart, add an index
  • Use Compass's "Explain" tab for visual representation

Index Management

Create, list, delete indexes:
// Create index
db.users.createIndex({ email: 1 })
db.users.createIndex({ email: 1 }, { unique: true, name: "unique_email" })

// List all indexes
db.users.getIndexes()

// Drop index by name
db.users.dropIndex("unique_email")

// Go driver
indexModel := mongo.IndexModel{
  Keys: bson.D{{Key: "email", Value: 1}},
  Options: options.Index().SetUnique(true),
}
col.Indexes().CreateOne(ctx, indexModel)
  • Always give indexes meaningful names
  • Index names like email_1 are auto-generated but not descriptive
  • Background index builds (large collections) → default in v4.2+
  • Too many indexes = slow writes. Only index what you query.

Read Preference & Secondaries

  • In a replica set: 1 Primary + N Secondaries
  • Primary: All writes, default reads
  • Secondary: Can serve reads (data may be slightly stale)
  • SecondaryPreferred() in your code routes reads to secondaries to reduce primary load
  • Used in your develop service for heavy metric reads
  • Options: primary, primaryPreferred, secondary, secondaryPreferred, nearest

Interview Questions: Indexes

Q: Explain the ESR rule for compound indexes.
A: ESR = Equality, Sort, Range. In a compound index, put equality fields first, sort fields second, range fields last. This order allows MongoDB to use the index optimally. For query filter by userId (equality) + sort by date (sort) + range by amount, the index should be { userId: 1, createdAt: -1, amount: 1 }.
Q: What does IXSCAN vs COLLSCAN mean in explain output?
A: IXSCAN = index scan (good). MongoDB found an index and used it to jump directly to matching docs. COLLSCAN = collection scan (bad). MongoDB scanned every document. Always aim for IXSCAN. If you see COLLSCAN on a frequently-run query, create an index.
Q: Can you use a compound index for single-field queries?
A: Partially. A compound index on { a:1, b:1, c:1 } can be used for queries on a alone or a,b together. But it cannot be used for queries on just b or c alone because the index is ordered by a first.
Q: When would you use a unique index?
A: When you need to prevent duplicate values in a field. Example: email addresses, usernames, API keys. { unique: true } throws an error if you try to insert a document with a duplicate value. Prevents data integrity issues.
GOTCHA: Indexes help reads but slow writes (index must be updated). Never create an index for every field "just in case". Index only fields you actively query on. Too many indexes = slow inserts, updates, deletes.
GOTCHA: { $in: [] } with an empty array can't use a range index efficiently. MongoDB may not use the index if the array is dynamic and could be empty.
PRODUCTION: Your sonarqube service has compound indexes like { projectId: 1, createdAt: -1 } for fast "recent scans for project X" queries. Your jfrog service indexes artifacts by { repositoryId: 1, name: 1 } for unique constraint + fast lookups. Your develop service uses secondary reads for non-critical metric reads to avoid overwhelming the primary.

Phase 7 Schema Design — The Core Difference from SQL

In SQL, you normalize everything. In MongoDB, you design for your actual query patterns. This phase teaches you the two critical decisions: embedding vs referencing, and when each is right.

Embedding: Denormalization

Nest related data in one document:
// User WITH embedded address (denormalized)
{
  _id: ObjectId(...),
  name: "Sid",
  email: "sid@example.com",
  address: {
    street: "123 Main St",
    city: "SF",
    zip: "94105"
  }
}

// Pros: One read gets everything. No JOIN needed.
// Cons: If address shared between multiple users, duplicated data.
  • Use embedding when:
  • - Data is always read together (user + address)
  • - Embedded data is bounded (few items, not growing unbounded)
  • - Only one parent owns the child data
  • - Document size stays well under 16MB
  • Pros: one read, no JOINs, faster queries
  • Cons: data duplication if shared, harder to update shared data

Referencing: Normalization

Store just the ID (like foreign key):
// User WITH referenced address (normalized)
{
  _id: ObjectId(...),
  name: "Sid",
  email: "sid@example.com",
  addressId: ObjectId(...)  // reference to addresses collection
}

// Address in separate collection
{
  _id: ObjectId(...),
  street: "123 Main St",
  city: "SF",
  zip: "94105"
}

// Requires $lookup join:
db.users.aggregate([
  { $lookup: {
    from: "addresses",
    localField: "addressId",
    foreignField: "_id",
    as: "address"
  }}
])
  • Use referencing when:
  • - Data is shared between many parents (one address, many users)
  • - Child data is large or unbounded (1000s of order items per order)
  • - You query child independently
  • - Embedded doc would exceed 16MB limit
  • Pros: no duplication, shared data stays consistent
  • Cons: requires JOIN, slower initial query

Design Patterns

  • Subset Pattern: Embed top N items, reference the rest. Example: embed top 5 reviews in product doc, reference full list in separate collection
  • Bucket Pattern: Group time-series data into time buckets. Example: 1 hour of IoT readings grouped in one document
  • Extended Reference: Embed frequently-read fields of referenced doc to avoid JOINs. Example: embed user name + email in order doc even though user is referenced
  • Computed Pattern: Pre-compute aggregates on write to avoid expensive calculations on read. Example: store product rating + review count in product doc, updated when reviews change
  • Outlier Pattern: Flag documents with unusually large arrays for special handling

Real Examples from Your Codebase

  • Your sonarqube service: Embeds scan metadata in project doc (always read together), references detailed issues in separate collection (queried independently)
  • Your jfrog service: Embeds artifact properties in artifact doc, references repository as ID to avoid duplication (one repo, many artifacts)
  • Your develop service: Embeds recent issue comments (top 10), references full history in separate collection
  • Your broker service: Message data is large → references in separate collection, not embedded in broker doc

Interview Questions: Schema Design

Q: When would you embed vs reference?
A: Embed when data is always read together, bounded in size, and only one parent owns it (user + address). Reference when data is shared between many documents, grows unbounded, or you query it independently (user + orders). Reference also prevents the 16MB document limit.
Q: What is the 16MB document limit and why does it exist?
A: MongoDB limits documents to 16MB to prevent unbounded document growth that would degrade performance. Documents loaded into RAM must fit. If you're hitting 16MB, you're probably embedding too much data. Solution: reference that data in a separate collection instead.
Q: Explain the Subset Pattern.
A: Embed frequently-accessed data (top 5 reviews in product doc) while referencing less frequently-accessed data (full review history in separate collection). Balances performance (no JOIN for common case) with data management (don't embed unbounded data).
GOTCHA: Embedding the same data in multiple documents creates duplication. When that data updates, you must update EVERY document containing it. This is expensive and error-prone. Only embed if the data truly belongs to one parent.
PRODUCTION: Your services embed small, frequently-accessed data and reference large, shared data. This balance keeps queries fast without creating consistency nightmares. Your monitoring dashboards prove this: queries on embedded data are sub-100ms, queries requiring joins are 100-500ms.

Phase 8 Transactions & Data Integrity — ACID Guarantees

MongoDB supports ACID transactions (since v4.0). This phase explains single-document atomicity (always), multi-document transactions (when needed), and why good schema design can often avoid them.

Single-Document Atomicity (Always Guaranteed)

  • Any single-document operation is 100% atomic in MongoDB
  • This includes updateOne, even with $set, $inc, $push, etc.
  • Atomic = either the whole operation succeeds or fails. No partial updates.
  • Example: { $inc: { counter: 1 }, $set: { updated: now } } → both happen or neither
  • Race condition impossible: two concurrent increments = counter increases by 2, not 1

Multi-Document Transactions

When you need ACID across multiple documents:
// Shell
const session = db.getMongo().startSession()
session.startTransaction()
try {
  db.accounts.updateOne(
    { _id: "alice" },
    { $inc: { balance: -100 } },
    { session }
  )
  db.accounts.updateOne(
    { _id: "bob" },
    { $inc: { balance: +100 } },
    { session }
  )
  session.commitTransaction()
} catch (e) {
  session.abortTransaction()
  throw e
} finally {
  session.endSession()
}
Go driver:
session, _ := client.StartSession()
defer session.EndSession(context.Background())

err := session.WithTransaction(ctx, func(ctx context.Context) error {
  // Both ops must succeed
  col.UpdateOne(ctx, bson.M{"_id": "alice"},
    bson.M{"$inc": bson.M{"balance": -100}})
  col.UpdateOne(ctx, bson.M{"_id": "bob"},
    bson.M{"$inc": bson.M{"balance": 100}})
  return nil
})
// If error, both rollback. If nil, both commit.
  • Requirements: Replica Set OR Sharded Cluster (not standalone)
  • Requires: Connection to mongodb:// (not Atlas free tier M0)
  • If one operation fails, BOTH rollback. No partial state.
  • Use sessions to group operations

Write Concern: Durability Level

  • { w: 1 } (default) — Primary acknowledges write (fast, less safe)
  • { w: "majority" } — Majority of replica set acknowledges (safer, slower)
  • { j: true } — Write persisted to journal on disk (survives crash)
  • { w: 1, j: true } — Balance: acknowledged + journaled
  • Higher write concern = more durability, but slower writes
  • Atlas uses w: "majority" by default (safe for production)

Read Concern: Consistency Level

  • local (default) — Read latest data on primary (may not be replicated yet)
  • majority — Read only data that majority of nodes have (safe, slightly stale)
  • linearizable — Read reflects all completed writes (slow, strongest guarantee)
  • snapshot — Consistent point-in-time read (for transactions)
  • Higher read concern = more consistency, but slower reads

Interview Questions: Transactions

Q: Is single-document atomicity always guaranteed in MongoDB?
A: Yes. Any single-document operation is atomic. Even { $inc: { counter: 1 }, $set: { updated: now } } is all-or-nothing. This is why good schema design (embedding related fields) can often avoid multi-document transactions.
Q: When would you use multi-document transactions?
A: Only when you need to atomically update data across multiple documents. Example: transfer money (debit account A, credit account B) must both succeed or both fail. If you can embed related data, avoid transactions (slower, more complex).
Q: What is write concern and when would you change it?
A: Write concern controls how many nodes must acknowledge a write before returning. Default { w: 1 } is fast but less safe. { w: "majority" } is safer (production). { j: true } ensures persistence to disk. Choose based on durability requirements vs acceptable latency.
GOTCHA: Multi-document transactions only work on Replica Sets or Sharded Clusters. Standalone MongoDB does NOT support them. Atlas M0 (free tier) is standalone → no transactions. Upgrade to M2+ for transaction support.
PRODUCTION: Your services rarely need multi-document transactions because of good schema design (embedding). Your nwayfw service uses single-document atomicity for inventory updates: $inc quantity and $set lastModified together — atomic, no lock needed.

Working with BSON:

  bson.D{{Key: "$match", Value: bson.D{
    {Key: "status", Value: "active"},

// bson.A = array

// primitive.ObjectID = Go type for MongoDB _id

Interview Questions: Production MongoDB

Q: Explain what a replica set is and why it matters for production.
A: A replica set is a group of mongod processes (primary + secondaries) maintaining the same data. Advantages: (1) automatic failover if primary dies, (2) read scaling (reads on secondaries), (3) backups (backup from secondary without impacting primary). Production MongoDB is always a replica set, never standalone.
Q: What is the oplog and how does it work?
A: The oplog (operations log) is a capped collection on every replica set member containing all write operations. Secondaries replicate from primary by reading the oplog and applying operations. It's also the data source for Change Streams. If oplog is too small, secondaries can fall behind.
Q: Why shouldn't you create a new MongoDB client for each request?
A: Creating a client is expensive (connection negotiation, auth, pool initialization). Each request creating one means thousands of new connections per second (connection pool thrashing). Create once at startup, reuse. Connection pooling is automatic and handles concurrent requests efficiently.

Phase 11 Replica Sets Deep Dive & Failover

Understanding replica sets is essential for production work. You must know how primary election works, what happens on failure, and how to monitor health.

Q: What happens when the primary in a replica set fails?
A: Secondaries detect the primary is down (heartbeat timeout). They elect a new primary using majority consensus. Clients get redirected to the new primary. Write operations during this window fail (briefly). Typical failover: 10-30 seconds. This is why you monitor replica set health.
Q: Can you do a read-only query on a secondary?
A: Yes, using read preference secondary or secondaryPreferred. Data may be slightly stale (replication lag). Good for non-critical reads (metrics, reports). Not suitable for reads that must be current.
Q: What is replication lag?
A: The delay between primary applying a write and secondaries applying it. During high write load, replication lag increases. If secondary falls behind oplog size, it must do full resync (slow). Monitor replication lag; if it's large, your secondaries can't keep up.

Phase 12 Sharding at Scale — Horizontal Scaling

When a single replica set can't handle write throughput or data size, you shard data across multiple machines. This is the scaling interview topic that separates SDE1 from SDE2.

Sharding Basics

  • Sharding = splitting data across machines (horizontal scaling)
  • Each machine holds a shard (subset of data)
  • Sharded cluster components: Shard servers + Config servers + mongos (query router)
  • Your app connects to mongos, which routes queries to right shard
  • Each shard is itself a replica set (HA + sharding together)

Shard Key — Most Critical Decision

  • Shard key: Field MongoDB uses to decide which shard a document goes to
  • Chosen once, cannot be changed later (resharding required)
  • Good shard key: High cardinality, even distribution, matches query patterns
  • Bad shard key: Low cardinality (few unique values) → hot spots
  • Example good: { userId: 1 } if you frequently query by userId
  • Example bad: { status: 1 } (only 3 values, one shard gets all load)

Targeted vs Scatter-Gather

  • Targeted query: Filter includes shard key → routes to ONE shard → fast
  • Scatter-gather: Filter doesn't include shard key → broadcasts to ALL shards → slow
  • Design rule: Most common query must be targeted, not scatter-gather
  • If you have a query that runs 1000x/sec, make it targeted with the right shard key

Interview Questions: Sharding

Q: What makes a bad shard key?
A: (1) Low cardinality — few unique values (status: only 3 values) → hot spot. (2) Monotonically increasing values (timestamps) without hashing → all new writes go to one shard. (3) Doesn't match query patterns → scatter-gather queries. (4) Can't be unshard later.
Q: Explain range sharding vs hash sharding.
A: Range sharding: documents with similar shard key values go to same shard. Good for range queries. Bad if data monotonically increases (hot spot). Hash sharding: hash the shard key value for even distribution. Can't do efficient range queries. For timestamps as shard key, use hash sharding.

Phase 13 Change Streams & Event-Driven Architecture

Change Streams let you react to database changes in real time. This is essential for microservice architectures where one service needs to know when another's data changes.

What are Change Streams?

  • Real-time stream of insert/update/delete events on a collection
  • Built on oplog (replication log)
  • Requires replica set (doesn't work on standalone)
  • Application opens a cursor that blocks waiting for events
  • Use cases: cache invalidation, audit logs, sync to Elasticsearch, event-driven services

Change Stream Event Structure

  • operationType: "insert", "update", "delete", "replace"
  • fullDocument: Complete document (for inserts/replaces)
  • updateDescription: Only changed fields (for updates)
  • documentKey: The _id of affected document
  • ns: Namespace: { db, coll }
  • resumeToken: Token to resume from if consumer restarts

Resume Token — Fault Tolerance

  • Every event has a resume token (its _id)
  • If consumer crashes, save resume token to disk
  • On restart: Watch(..., SetResumeAfter(token))
  • Provides at-least-once delivery (may see duplicates)
  • Make event handlers idempotent

Go Pattern: Change Stream Consumer

Idiomatic Go implementation:
ctx := context.Background()
stream, _ := col.Watch(ctx, mongo.Pipeline{
  bson.D{{Key: "$match", Value: bson.D{
    {Key: "operationType", Value: bson.M{"$in": []string{"insert", "update"}}},
  }}},
})
defer stream.Close(ctx)

for stream.Next(ctx) {
  var event bson.M
  stream.Decode(&event)
  
  // Process event (must be idempotent)
  processEvent(event)
  
  // Save resume token
  saveResumeToken(stream.ResumeToken())
}
if err := stream.Err(); err != nil {
  // Reconnect with resume token
}
Q: What is a change stream and when would you use it?
A: Real-time stream of DB changes (insert/update/delete events). Use when one service needs to react to another service's data changes. Examples: cache invalidation, sync to search index, audit logs, event-driven microservices. Alternative: polling (wastes DB resources).
Q: What is a resume token and why does it matter?
A: Resume token is a checkpoint in the change stream. If your consumer crashes, save the token. On restart, resume from that token using SetResumeAfter. Prevents reprocessing old events (or losing new events). Essential for exactly-once delivery semantics.

Phase 14 Senior Interview Topics — SDE2/SDE3 Level

These questions separate senior from junior candidates. They test deep understanding of MongoDB internals, architecture trade-offs, and production problem-solving.

WiredTiger Storage Engine

  • Default storage engine since v3.2 (replaced MMAPv1)
  • Document-level locking: Two writes to different docs in same collection don't block each other
  • MVCC (Multi-Version Concurrency Control): Readers don't block writers, writers don't block readers
  • Compression: Data compressed on disk (snappy). Reduces disk by 60-80%
  • Internal cache: Default 50% of RAM. Working set should fit
  • How it helps: High concurrency = no writer-writer blocking

Anti-Patterns That Cause Production Issues

  • Unbounded arrays: Never $push forever. Hit 16MB limit. Use separate collection.
  • N+1 problem: Fetch 1 list, then N queries for details. Use $lookup or $in batching.
  • No indexes on frequently-queried fields: COLLSCAN = slow. Always confirm IXSCAN.
  • Using $where or JavaScript: JS executes per document. Use native operators.
  • Storing files as base64: Breaks 16MB limit. Use GridFS or S3.
  • ObjectId stored as string: Wastes space, breaks sorting. Always use ObjectId type.
  • Not handling ErrNoDocuments: FindOne returns this, not a real error.
  • Too many indexes: Slows writes. Index only fields you query.

MongoDB vs Other Databases (System Design)

  • MongoDB vs Redis: Redis in-memory (sub-ms latency, caching). MongoDB persistent disk (primary storage, richer queries)
  • MongoDB vs PostgreSQL: Postgres for relational + complex JOINs + strict schema. MongoDB for flexible schema + document data + horizontal scaling
  • MongoDB vs Cassandra: Cassandra write-optimized, no transactions, wide-column (extreme scale time-series). MongoDB rich queries, ACID transactions, document model
  • When to pick MongoDB: Flexible/evolving schema, document-shaped data, horizontal scaling needed, JSON-native APIs

Schema Validation ($jsonSchema)

  • MongoDB supports enforcing schema at collection level (not schema-less if you don't want to be)
  • db.createCollection("users", { validator: { $jsonSchema: {...} } })
  • Validation levels: strict (all writes) or moderate (only new/updated docs)
  • Can require fields, set types, patterns, ranges
  • Prevents garbage data from entering collection

Security: Authentication & Authorization

  • Authentication: WHO are you. Methods: SCRAM (default), X.509, LDAP, Kerberos
  • Authorization (RBAC): WHAT can you do. Roles: read, readWrite, dbAdmin, clusterAdmin
  • Least privilege: Each service gets only the permissions it needs
  • TLS/SSL: Always use encrypted connections. tls=true
  • Field-level encryption: Encrypt specific fields (SSN, credit card) end-to-end

Advanced Interview Questions

Q: Describe the MVCC model in WiredTiger and why it matters.
A: MVCC = Multiple-Version Concurrency Control. Multiple versions of data exist during concurrent operations. Readers see a consistent snapshot without blocking writers. Writers see their changes immediately. No reader-writer blocking. This is why MongoDB can handle high concurrency compared to traditional locking-based systems.
Q: Explain the N+1 problem in MongoDB and solutions.
A: N+1 = fetch 1 list (queries 1), then N individual lookups for each item (queries N). Total: 1+N queries (slow). Solutions: (1) $lookup in aggregation (one query). (2) { field: { $in: [array of IDs] } } (one query to fetch all). (3) Embedding if data is small and always needed.
Q: When would you use a capped collection?
A: Capped collection = fixed-size, overwrites oldest docs when full. Use for: logs, audit trails, activity feeds, rate-limit counters. Insertion order preserved. No delete individual docs. Great for "keep only recent N items" without explicit cleanup.
Q: How do you handle schema evolution in MongoDB?
A: (1) Add schemaVersion field. (2) Write new code to handle both old and new versions. (3) Backfill old documents gradually (or leave them as-is if backward-compatible). (4) Eventually drop old version support. No downtime needed — this is MongoDB's flexibility advantage over SQL.
Q: Explain the trade-off between embedding and referencing.
A: Embedding: one read = all data (fast), but duplication if shared, can hit 16MB limit. Referencing: no duplication, shared data consistent, but requires JOIN ($lookup, slower). Choose based on: data sharing (shared = reference), size (large/unbounded = reference), access patterns (always together = embed).
Q: What happens if your shard key causes a hot spot?
A: All writes go to one shard, others sit idle. That shard becomes the bottleneck. Solution: choose better shard key (higher cardinality, even distribution). For monotonically-increasing values (timestamps), use hash sharding. Once a hot shard key is chosen, you're stuck until resharding.
Q: How do you monitor MongoDB in production?
A: (1) Atlas Performance Advisor (suggests indexes). (2) Atlas Profiler (logs slow queries). (3) Metrics: operation latency, index usage, cache hit rate, replication lag. (4) otelmongo traces (your services). (5) currentOp() (running operations). (6) serverStatus() (cluster health).
Q: What is the difference between w:1 and w:"majority" write concern?
A: w:1 = primary acknowledges (fast, less safe, may lose data if primary crashes before replicate). w:"majority" = majority of replica set acknowledges (safe, slower, data survives single-node crash). Production typically uses majority. Trade-off: durability vs latency.

⚠️ Common Mistakes & Anti-Patterns

These are the patterns that cause 90% of MongoDB problems in production. Learn to spot them and avoid them.

Anti-Pattern #1: Creating New Client Per Request

❌ WRONG (Go):

for i := 0; i < 1000; i++ {
  client, _ := mongo.Connect(ctx)  // EXPENSIVE!
  collection := client.Database("db").Collection("col")
  collection.InsertOne(ctx, doc)
  client.Disconnect(ctx)            // Connection destroyed
}
// Result: 1000 connection attempts = SLOW + resource leak

✅ CORRECT:

client, _ := mongo.Connect(ctx)     // Once
defer client.Disconnect(ctx)
collection := client.Database("db").Collection("col")

for i := 0; i < 1000; i++ {
  collection.InsertOne(ctx, doc)    // Reuse connection
}

Why? Connection establishment is expensive (TCP handshake, authentication). Reuse connections via connection pooling.

Anti-Pattern #2: Ignoring mongo.ErrNoDocuments

❌ WRONG (Go):

var user User
err := col.FindOne(ctx, bson.M{"_id": id}).Decode(&user)
if err != nil {
  log.Fatal("User not found")  // WRONG! ErrNoDocuments is normal
}

✅ CORRECT:

var user User
err := col.FindOne(ctx, bson.M{"_id": id}).Decode(&user)
if err == mongo.ErrNoDocuments {
  // User doesn't exist (normal case, not an error)
  return fmt.Errorf("user not found")
} else if err != nil {
  // Real error (connection, timeout, etc.)
  return err
}

Why? mongo.ErrNoDocuments is NOT a database error—it's a normal result meaning "no match". Treating it as a fatal error crashes your app.

Anti-Pattern #3: Not Using Indexes on Query Fields

❌ WRONG (Shell):

db.users.find({ email: "alice@example.com" })
// Without index: scans ALL 1 million documents (COLLSCAN)
// Query takes 5+ seconds

✅ CORRECT:

db.users.createIndex({ email: 1 })
db.users.find({ email: "alice@example.com" })
// With index: binary search on index (IXSCAN)
// Query takes < 1ms

Why? Without indexes, MongoDB must read every single document. Indexes let it jump to matches instantly.

Anti-Pattern #4: Unbounded Arrays (16MB Document Limit)

❌ WRONG (Schema):

{
  "_id": user_id,
  "name": "Alice",
  "posts": [post1, post2, ..., post_1000000]  // Array grows forever
}
// Eventually hits 16MB limit → insertions fail

✅ CORRECT (Option 1 - Separate Collection):

// Collection: users
{ "_id": user_id, "name": "Alice" }

// Collection: posts
{ "_id": post_id, "userId": user_id, "content": "..." }

// Query: db.posts.find({ userId: user_id })

✅ CORRECT (Option 2 - Bounded Array with Bucket Pattern):

{
  "_id": user_id,
  "name": "Alice",
  "buckets": [
    { "date": "2024-01", "posts": [post1, post2, ...] },  // Max 100 per bucket
    { "date": "2024-02", "posts": [post3, post4, ...] }
  ]
}

Why? MongoDB documents have a 16MB hard limit. Arrays that grow indefinitely WILL break. Always cap them or move to separate collection.

Anti-Pattern #5: Not Checking Write Errors

❌ WRONG (Go):

result, _ := col.InsertOne(ctx, doc)  // Ignoring err!
fmt.Println(result.InsertedID)        // May not exist if insert failed

✅ CORRECT:

result, err := col.InsertOne(ctx, doc)
if err != nil {
  // Check error type
  if mongo.IsDuplicateKeyError(err) {
    log.Println("Duplicate key error")
  } else if ctx.Err() == context.DeadlineExceeded {
    log.Println("Context timeout")
  } else {
    log.Println("Insert failed:", err)
  }
  return err
}
fmt.Println(result.InsertedID)  // Safe to use now

Why? Write errors are silent failures. Your code thinks it worked when it didn't. Always check.

Anti-Pattern #6: Using $where (JavaScript Eval)

❌ WRONG (Shell):

db.users.find({ $where: "this.age > 30" })
// Evaluates JavaScript for EVERY document (no index possible)
// Performance: O(n) full scan, very slow

✅ CORRECT:

db.users.find({ age: { $gt: 30 } })
// Can use index on age field
// Performance: O(log n) binary search

Why? $where disables all query optimizations. Never use it. Use standard operators instead.

Anti-Pattern #7: Storing ObjectIds as Strings

❌ WRONG (Go):

type User struct {
  ID string `bson:"_id"` // Storing ObjectId as string
  Name string
}
// Can't index efficiently, comparison is string (wrong order)

✅ CORRECT:

type User struct {
  ID primitive.ObjectID `bson:"_id"`  // Native ObjectID
  Name string
}
// Indexing works, comparison is efficient

Why? ObjectIds are binary. Converting to strings wastes space and breaks sorting/indexing.

Anti-Pattern #8: The N+1 Problem

❌ WRONG (Go):

// Get all users
users, _ := col.Find(ctx, bson.M{})  // Query 1

// For each user, fetch their posts
for _, user := range users {
  posts, _ := postCol.Find(ctx, bson.M{"userId": user.ID})  // Query N
  // Total queries: 1 + N (SLOW)
}

✅ CORRECT (Using $lookup):

// One aggregation query fetches both
cursor, _ := col.Aggregate(ctx, mongo.Pipeline{
  bson.D{{Key: "$lookup", Value: bson.D{
    {Key: "from", Value: "posts"},
    {Key: "localField", Value: "_id"},
    {Key: "foreignField", Value: "userId"},
    {Key: "as", Value: "posts"},
  }}},
})
// Total queries: 1 (FAST)

Why? N+1 queries multiply latency. Use $lookup to fetch related data in one query.

Anti-Pattern #9: Forgetting to Close Cursors (Go)

❌ WRONG:

for i := 0; i < 1000; i++ {
  cursor, _ := col.Find(ctx, bson.M{})
  // Using cursor...
  // FORGOT cursor.Close(ctx)  ← Resource leak!
}
// After 1000 iterations: connection exhausted

✅ CORRECT:

for i := 0; i < 1000; i++ {
  cursor, _ := col.Find(ctx, bson.M{})
  defer cursor.Close(ctx)  // Always close!
  // Using cursor...
}

Why? Cursors hold server-side resources. Not closing them leads to connection pool exhaustion.

Anti-Pattern #10: Too Many Indexes

❌ WRONG:

db.users.createIndex({ name: 1 })
db.users.createIndex({ email: 1 })
db.users.createIndex({ age: 1 })
db.users.createIndex({ city: 1 })
db.users.createIndex({ country: 1 })
// Now INSERTs are slow (must update all 5 indexes)
// Memory bloat (indexes take space)

✅ CORRECT:

// Create only indexes for frequent queries
db.users.createIndex({ email: 1 })  // For login
db.users.createIndex({ status: 1, createdAt: -1 })  // For list queries

// Use explain to verify queries use indexes
db.users.find({...}).explain("executionStats")

Why? Each index slows writes and consumes RAM. Index only what you query frequently.

🔧 Troubleshooting & Debugging Guide

When something breaks, come here. This guide covers the most common errors and how to fix them.

Connection Issues

Error: "connect: connection refused"

  • Cause: MongoDB server not running
  • Fix: brew services start mongodb-community
  • Check: brew services list (should show "mongodb-community started")

Error: "authentication failed"

  • Cause: Wrong username/password in connection string
  • Fix: Verify connection string from Atlas dashboard
  • Check: mongosh "mongodb+srv://user:pass@cluster.mongodb.net/db"
  • Tip: If password has special characters, URL-encode them (@ → %40, # → %23)

Error: "no servers available" or "cluster not found"

  • Cause (Atlas): Your IP not in IP whitelist or cluster suspended
  • Fix: Go to Atlas → Network Access → Add your IP (or 0.0.0.0/0 for dev)
  • Fix: Check if cluster is "paused" → click Resume
  • Cause (Local): Wrong port or server crashed
  • Fix: Check port 27017: lsof -i :27017

Error: "context deadline exceeded"

  • Cause: Query taking too long (missing index) or network latency
  • Fix: Increase context timeout: ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
  • Better Fix: Add index to speed up query

Query Issues

Problem: "find() returns empty but I know data exists"

  • Check: Verify you're querying the right collection and database
  • use mydb → show collections → check collection name
  • Check: Query syntax correct? db.col.find({ status: "active" }) vs db.col.find({ status: active }) (quotes matter!)
  • Check: Data type matches? { age: 30 } vs { age: "30" } (number vs string)
  • Debug: db.col.countDocuments({}) → check if collection is empty

Problem: "Query is very slow"

  • Step 1: Analyze query with explain: db.col.find({...}).explain("executionStats")
  • Check: "executionStages.stage" — if "COLLSCAN", you're doing full collection scan (slow)
  • Check: If "IXSCAN", you're using an index (good)
  • Fix: Add index on query field: db.col.createIndex({ queryField: 1 })
  • Check: ESR rule for compound queries: Equality first, then Sort, then Range

Problem: "No matching documents returned but I expect some"

  • Common: Case sensitivity in strings: { name: "Alice" } won't match "alice"
  • Fix: Use $regex with case-insensitive: { name: { $regex: "alice", $options: "i" } }
  • Common: ObjectId comparison: { _id: "507f1f77bcf86cd799439011" } (string) won't match ObjectId
  • Fix: Use ObjectId("507f1f77bcf86cd799439011") or convert from your code

Problem: "duplicate key error" on insert

  • Cause: You have a unique index and trying to insert duplicate value
  • Check: db.col.getIndexes() → look for "unique: true"
  • Option 1: Use upsert: updateOne({...}, {...}, { upsert: true })
  • Option 2: Delete the conflicting document first, then insert
  • Option 3: Drop the unique index if no longer needed: db.col.dropIndex("indexName")

Data Issues

Problem: "Struct unmarshaling failed" (Go)

  • Cause: Document fields don't match Go struct
  • Example Wrong: type User struct { Name string } but document has { full_name: "Alice" }
  • Fix: Use bson tags: type User struct { Name string `bson:"full_name"` }
  • Fix: Or rename fields in document to match struct

Problem: "Can't decode nested object to struct" (Go)

  • Cause: Embedded document not properly typed
  • Wrong: type User struct { Address string } when Address is nested document
  • Fix: type User struct { Address struct { City string; Zip string } `bson:"address"` }

Problem: "Field type mismatch" on query

  • Example: Some docs have { age: 30 } (number), others have { age: "30" } (string)
  • Fix: Use $type to filter by type: { age: { $type: "int" } }
  • Better: Add validation: db.createCollection("users", { validator: { $jsonSchema: { properties: { age: { type: "int" } } } } })

Problem: "Hit 16MB document size limit"

  • Cause: Document with unbounded array grew too large
  • Fix: See Anti-Pattern #4 above — move array to separate collection or use bucket pattern
  • Check: db.col.find().sort({ $natural: -1 }).limit(1) → check size of largest doc

Performance Issues

Problem: "Insert speed is slow"

  • Check: How many indexes? Too many indexes slow writes
  • Fix: Drop unused indexes
  • Check: Using individual inserts in loop? Do BulkWrite instead
  • Fix: Group 1000 inserts into one BulkWrite call
  • Check: Write concern too high? (w: "majority" is slower than w: 1)
  • Fix: Use appropriate write concern for your needs

Problem: "Update is taking too long"

  • Check: Is there an index on the filter field?
  • Fix: db.col.createIndex({ status: 1 }) (if filtering by status)
  • Check: Update expression complex? Simplify if possible
  • Example: Use $set instead of fetching, modifying, replacing

Problem: "High memory usage on MongoDB server"

  • Check: Too many indexes? Each index uses RAM
  • Check: Connection pool too large? Reduce pool size
  • Check: Large aggregations without $limit or $out?
  • Fix: Add $limit to cap aggregation results
  • Fix: Use $out to write large results to collection instead of streaming

Atlas-Specific Issues

Error: "IP address not in access list"

  • Fix: Go to Atlas → Network Access → Add your IP
  • Tip: For development, use 0.0.0.0/0 (anywhere, NOT for production!)

Error: "Cluster is suspended"

  • Cause: M0 free tier auto-suspends after 60 days of inactivity
  • Fix: Go to Atlas → Clusters → click Resume

Error: "Exceeded storage quota"

  • Cause (M0): Free tier limited to 512MB
  • Fix: Delete unused databases/collections or upgrade to paid tier
  • Check: db.stats() → check "dataSize"

Connection String Issues

  • Wrong: Copying old connection string after password change
  • Fix: Always get fresh connection string from Atlas dashboard
  • Wrong: Special characters in password not URL-encoded
  • Fix: @ → %40, # → %23, : → %3A (use a URL encoder)

Debugging Checklist

When stuck, follow this order:

  • ✅ Step 1: Is MongoDB running? brew services list
  • ✅ Step 2: Can you connect? mongosh mongodb://localhost:27017
  • ✅ Step 3: Does the database/collection exist? show dbs → show collections
  • ✅ Step 4: Is there data? db.col.countDocuments({})
  • ✅ Step 5: Is query correct? Try simpler query first
  • ✅ Step 6: Run .explain("executionStats") to see query plan
  • ✅ Step 7: Check indexes: db.col.getIndexes()
  • ✅ Step 8: Review logs: mongod outputs errors to console or log file
