Phase 0 Setup & Tools — Before You Write a Single Query

Install everything. Learn what each tool does. Don't skip this — you'll struggle to practice without a working environment.

Install These (in this order)

  • MongoDB Community Server — the database itself
    brew install mongodb-community (macOS)
  • mongosh — MongoDB Shell, how you talk to the DB in terminal
  • MongoDB Compass — GUI to visually see your data (beginner-friendly)
  • MongoDB Atlas — free cloud cluster (no local install needed for practice)
  • VS Code Extension — MongoDB for VS Code (run queries inside VS Code)

Understand These 3 Terms First

  • mongod — the background server process (the engine)
  • mongosh — the shell you type commands in
  • Compass — visual tool, same as using pgAdmin for Postgres
Quick test: Run mongosh in terminal. If you see a > prompt, you're set up correctly.

First 5 Shell Commands to Know

  • show dbs — list all databases
  • use mydb — switch to (or create) a database
  • show collections — list all collections in current db
  • db.stats() — info about current database
  • exit — leave the shell

Phase 1 Core Concepts — What IS MongoDB?

Understand the mental model. MongoDB thinks differently than SQL. You MUST internalize these before writing any queries.

SQL → MongoDB Mental Shift

  • Table → Collection
  • Row → Document
  • Column → Field
  • JOIN → Embedded document or $lookup
  • Primary key → _id (auto-generated ObjectId)
  • Schema → Flexible (no fixed columns — each document can have different fields)

BSON — What Data Looks Like

  • MongoDB stores data as BSON (Binary JSON)
  • You write queries using JSON-like syntax
  • BSON supports extra types JSON doesn't: ObjectId, Date, Int32, Int64, Decimal128, Binary
  • _id: ObjectId("64a...") — every document has one, auto-created
  • In Go: primitive.ObjectID, primitive.DateTime

Key Data Types to Know

  • String — text
  • Number — Int32, Int64, Double, Decimal128
  • Boolean — true / false
  • Array — ["a", "b", "c"]
  • Object — nested document { name: "sid" }
  • ObjectId — unique 12-byte ID for every document
  • Date — timestamp
  • Null — empty value

Why MongoDB? (Not SQL)

  • Flexible schema — your CI/CD pipeline data has varying fields per service
  • Horizontal scaling — easy to shard across machines
  • JSON-native — matches how APIs send/receive data
  • Nested documents = no JOIN needed for simple reads
  • Great for: catalogs, events, logs, configs, pipelines, user profiles
  • Your codebase reason: each microservice stores different shape of data

Phase 2 CRUD Operations — The Foundation of Everything

Every MongoDB skill you build later depends on these 4 operations. Master all of them before moving on. This is 60% of what you will use daily.

Create (Insert)

  • db.users.insertOne({ name: "Sid", age: 25 })
  • db.users.insertMany([{...}, {...}])
  • MongoDB auto-creates the collection if it doesn't exist
  • MongoDB auto-assigns _id if you don't provide one
  • You CAN provide your own _id, but it must be unique

Read (Find)

  • db.users.find() — all documents
  • db.users.find({ age: 25 }) — filter by exact match
  • db.users.findOne({ name: "Sid" }) — first matching document
  • db.users.find({}, { name: 1, _id: 0 }) — projection (select fields)
  • db.users.find().limit(5) — limit results
  • db.users.find().sort({ age: 1 }) — sort ascending (−1 = descending)
  • db.users.countDocuments({ age: 25 }) — count matching

Update

  • db.users.updateOne({ name: "Sid" }, { $set: { age: 26 } })
  • db.users.updateMany({ role: "dev" }, { $set: { active: true } })
  • db.users.findOneAndUpdate(filter, update, { returnDocument: "after" }) — returns the updated doc
  • Upsert: { upsert: true } — inserts if document doesn't exist, updates if it does
  • replaceOne — replaces the entire document (not just a field)

Delete

  • db.users.deleteOne({ name: "Sid" }) — delete first match
  • db.users.deleteMany({ active: false }) — delete all matches
  • db.users.drop() — delete entire collection
  • db.dropDatabase() — delete entire database
  • Safe habit: always run find() with the same filter first to confirm what you're deleting
⚠️ Common Beginner Mistake: db.users.find() does NOT return an array — it returns a Cursor. Call .toArray() or iterate with forEach. In Go driver, you use cursor.All(ctx, &results).

Phase 3 Query Operators — Filtering Like a Pro

Basic find({ age: 25 }) only matches exact values. Query operators let you express "greater than", "in a list", "exists", etc. You use these constantly in real code.

Comparison Operators

  • $eq — equal to (same as plain { age: 25 })
  • $ne — not equal to
  • $gt — greater than
  • $gte — greater than or equal
  • $lt — less than
  • $lte — less than or equal
  • $in — value is in an array: { age: { $in: [25, 30] } }
  • $nin — value is NOT in an array
Used in your codebase: $in, $nin in sonarqube controller

Logical Operators

  • $and — ALL conditions must be true
  • $or — ANY one condition must be true
  • $not — negates a condition
  • $nor — none of the conditions are true
db.users.find({ $and: [{ age: { $gt: 20 } }, { active: true }] })
Used in your codebase: $and, $or in develop/issuemetrics.go

Element Operators

  • $exists — field exists (or doesn't): { phone: { $exists: true } }
  • $type — field is of a specific BSON type: { age: { $type: "int" } }
Used in your codebase: $exists in jfrog/artifacts.go

Array Operators

  • $all — array contains ALL these values: { tags: { $all: ["go","api"] } }
  • $size — array has exactly N elements: { tags: { $size: 3 } }
  • $elemMatch — at least one array element matches all conditions
Used in your codebase: $all, $size in sonarqube/projects.go

Evaluation Operators

  • $regex — pattern match: { name: { $regex: "^Sid" } }
  • $where — JavaScript expression (avoid in production)
  • $expr — use aggregation expressions inside a query filter
  • $mod — modulo: { qty: { $mod: [4, 0] } }

Projection (Controlling Output Fields)

  • db.users.find({}, { name: 1 }) — include only name + _id
  • db.users.find({}, { password: 0 }) — exclude password
  • Cannot mix include and exclude (except for _id)

Phase 4 Update Operators — Modifying Data Precisely

Never replace an entire document just to change one field. Update operators let you surgically modify exactly what you need. These are the operators you see in your codebase's $set, $pull calls.

Field Update Operators

  • $set — set a field value (most common): { $set: { age: 26 } }
  • $unset — remove a field: { $unset: { phone: "" } }
  • $inc — increment a number: { $inc: { views: 1 } }
  • $mul — multiply a number: { $mul: { price: 1.1 } }
  • $rename — rename a field: { $rename: { "old": "new" } }
  • $min — update only if new value is smaller
  • $max — update only if new value is larger
  • $currentDate — set field to current date/time
  • $setOnInsert — only applies when upsert creates a new document
Used in your codebase: $set, $setOnInsert in jfrog/artifacts.go

Array Update Operators

  • $push — add element to array: { $push: { tags: "go" } }
  • $pull — remove matching elements: { $pull: { tags: "old" } }
  • $addToSet — add to array only if not already there (no duplicates)
  • $pop — remove first (-1) or last (1) element
  • $pullAll — remove all matching values in a list
  • $push with $each — push multiple elements at once
  • $push with $sort + $slice — push + sort + trim array
Used in your codebase: $pull in develop/issuemetrics.go

Upsert — The Most Important Update Option

  • Upsert = Update + Insert
  • If a document matching the filter exists → update it
  • If a document matching the filter does NOT exist → insert a new one
  • Syntax: db.col.updateOne(filter, update, { upsert: true })
  • Use $setOnInsert for fields you only want on new documents
  • Without upsert: if no match, nothing happens
Real example from your codebase:
options.FindOneAndUpdate().SetUpsert(true).SetReturnDocument(options.After)
in nwayfw/streaming.go

BulkWrite — Update Many Documents Efficiently

  • Instead of calling updateOne 100 times in a loop, send all 100 ops in ONE network call
  • Supports: InsertOne, UpdateOne, UpdateMany, DeleteOne, DeleteMany, ReplaceOne
  • Can be ordered (stops on first error) or unordered (continues on errors)
  • Returns counts: inserted, matched, modified, deleted, upserted
  • This is what your jfrog service uses for artifact updates

Phase 5 Aggregation Pipeline — MongoDB's Most Powerful Feature

The aggregation pipeline is how you transform and analyse data. Think of it as: data flows through a series of stages, each stage transforming the output of the previous one. This is what your jfrog service uses. Learn this well — it is the most-asked interview topic.

Mental model: Imagine your data as water flowing through pipes. Each stage ($match, $group, $sort...) is a section of pipe that transforms the water before passing it to the next stage. The output of the last stage is your final result.

Stage 1: $match — Filter First

  • Acts like find() — filters documents
  • Always put $match FIRST to reduce the number of documents in the pipeline early
  • Uses the same query operators: $gt, $in, $and, etc.
  • { $match: { status: "active", age: { $gt: 18 } } }

Stage 2: $group — Summarize

  • Groups documents by a field and computes aggregates
  • _id is the group-by field (null = group everything)
  • Accumulators: $sum, $avg, $min, $max, $count, $push, $addToSet
{ $group: { _id: "$dept", total: { $sum: "$salary" } } }

Stage 3: $project — Shape Output

  • Like SQL SELECT — control which fields appear in the output
  • Include: { $project: { name: 1, age: 1 } }
  • Exclude: { $project: { password: 0 } }
  • Rename: { $project: { userName: "$name" } }
  • Compute new fields: { $project: { fullName: { $concat: ["$first", " ", "$last"] } } }

Stage 4: $sort, $limit, $skip

  • { $sort: { createdAt: -1 } } — sort newest first
  • { $limit: 10 } — take only first 10 results
  • { $skip: 20 } — skip first 20 (for pagination)
  • Order matters: always $sort before $limit
  • Pagination pattern: $sort → $skip → $limit

Stage 5: $unwind — Flatten Arrays

  • Takes each element of an array and creates a separate document for it
  • Input: { tags: ["go", "api", "mongo"] }
  • Output: 3 separate documents, one per tag
  • Required before you can $group by array elements
  • { $unwind: "$tags" }

Stage 6: $lookup — JOIN Between Collections

  • MongoDB's version of SQL LEFT JOIN
  • Joins documents from another collection based on a field match
{ $lookup: {
 from: "orders",
 localField: "_id",
 foreignField: "userId",
 as: "userOrders"
} }

Other Useful Stages

  • $addFields — add new computed fields without removing others
  • $count — count total matching documents in pipeline
  • $replaceRoot — make a nested document the new root
  • $out — write pipeline results into a new collection
  • $facet — run multiple sub-pipelines in parallel
  • $bucket — group into ranges (e.g. age 0-18, 18-30, 30+)

Aggregation Expressions (inside stages)

  • $concat — join strings
  • $toLower / $toUpper
  • $dateToString — format a date
  • $cond — if/else logic inside a stage
  • $ifNull — default value if field is null
  • $size — length of an array field
  • $arrayElemAt — get element at index from array
  • $filter — filter array inline without $unwind

Phase 6 Indexes & Performance — Make Queries Fast

Without indexes, MongoDB scans every document for every query (called a Collection Scan). With the right indexes, it jumps directly to matching documents. Your services define compound indexes — this phase explains exactly why.

What is an Index?

  • A sorted data structure that MongoDB maintains alongside your data
  • Without index → Collection Scan (reads every document)
  • With index → Index Scan (jumps directly to matching docs)
  • Trade-off: indexes make reads faster but writes slightly slower (index must be updated too)
  • Rule of thumb: index fields you frequently filter (find) or sort on

Index Types

  • Single Field — db.users.createIndex({ email: 1 })
  • Compound Index — index on multiple fields: { userId: 1, createdAt: -1 }
  • Multikey Index — auto-created when you index an array field
  • Text Index — full-text search: { $text: { $search: "mongodb" } }
  • Unique Index — prevents duplicate values: { unique: true }
  • TTL Index — auto-deletes documents after N seconds (great for sessions, logs)
  • Geospatial Index — for location queries ($near, $within)

Compound Index — ESR Rule

  • The order of fields in a compound index matters
  • Equality fields first (exact match: { userId: 1 })
  • Sort fields next (the field you sort on)
  • Range fields last ($gt, $lt, $in)
  • A compound index on { a: 1, b: 1, c: 1 } also supports queries on { a: 1 } and { a: 1, b: 1 } — but NOT on { b: 1 } alone
  • This is exactly how your sonarqube service defines its indexes

Explain Plan — Diagnose Slow Queries

  • db.users.find({ email: "x" }).explain("executionStats")
  • Look for: winningPlan.stage
  • IXSCAN = good (index was used)
  • COLLSCAN = bad (full scan, needs an index)
  • Check: totalDocsExamined vs nReturned — if they're far apart, you need a better index
  • Use Compass's "Explain" tab to visualize this visually

Index Management

  • db.users.getIndexes() — list all indexes
  • db.users.dropIndex("email_1") — remove by name
  • db.users.createIndex({ email: 1 }, { unique: true, name: "unique_email" })
  • Background index builds (large collections) → use { background: true } in older versions, default in v4.2+
  • Too many indexes = slow writes. Only index what you query on.

Read Preference — Secondary Reads

  • In a replica set, you have 1 Primary + N Secondary nodes
  • Primary — all writes go here; default for reads too
  • Secondary — can serve reads (data may be slightly stale)
  • SecondaryPreference() in your codebase routes read-heavy queries to secondaries to reduce load on primary
  • Used in develop/worker/issuemetrics.go — large metric reads go to secondary
  • Options: primary, primaryPreferred, secondary, secondaryPreferred, nearest

Phase 7 Schema Design — How to Structure Your Data

This is where MongoDB differs most from SQL. There is no single right answer — schema design depends on how your application reads data. This phase teaches you to make that decision correctly.

The Core Question

  • In SQL: normalize everything into separate tables, JOIN when reading
  • In MongoDB: design for your most common query pattern
  • The two choices are: Embedding vs Referencing
Embed when: data is always read together, child docs are few and bounded

Reference when: data is large, shared between many parents, or grows unboundedly

Embedding (Denormalization)

  • Nest related data inside the same document
  • One read = all data needed (no joins)
  • Example: user address inside user document
  • Good for: 1-1 relationships, 1-few relationships
  • Limit: MongoDB document max size is 16MB
  • Risk: data duplication if embedded data is shared

Referencing (Normalization)

  • Store ObjectId of related document (like a foreign key)
  • Requires $lookup in aggregation to join
  • Good for: many-to-many, large child datasets, shared data
  • Example: orders reference userId (don't embed full user inside every order)
  • Use $lookup only when needed — it's slower than embedding

Common Design Patterns

  • Subset Pattern — embed top 5 reviews in product, reference rest
  • Bucket Pattern — group time-series data into time buckets (e.g. IoT data per hour)
  • Outlier Pattern — flag documents that have unusually large arrays
  • Extended Reference — embed frequently-read fields of referenced doc to avoid lookups
  • Computed Pattern — pre-compute totals/averages on write to avoid expensive aggregations on read
  • Schema Versioning — add a schemaVersion field to handle migrations

Phase 8 Transactions & Sessions — ACID in MongoDB

MongoDB supports multi-document ACID transactions since v4.0. Before v4.0, only single-document operations were atomic. This phase explains when you need them and how they work.

Single-Document Atomicity (Always)

  • Any operation on a single document is always atomic in MongoDB
  • This includes: updateOne with $set, $push, etc. on one document
  • Atomic = either the whole operation succeeds or the whole thing fails. No partial updates.
  • This is why good schema design (embedding) can often avoid transactions entirely

Multi-Document Transactions

  • When you need to update multiple documents atomically (across collections)
  • Example: debit from account A AND credit to account B — both must succeed or both must fail
  • Requires a Replica Set (or Sharded Cluster) — does NOT work on standalone
  • Uses Session to group operations together
  • Pattern: startSession → startTransaction → do ops → commitTransaction → endSession

Write Concern — Durability

  • Controls how many nodes must acknowledge a write before MongoDB reports success
  • { w: 1 } — primary acknowledges (default)
  • { w: "majority" } — majority of replica set members acknowledge (safer)
  • { j: true } — write is persisted to journal before ack (durable on crash)
  • Higher write concern = more durability, but slightly slower writes

Read Concern — Isolation

  • Controls what data you read relative to write operations
  • local — read latest data on primary (may not be majority-committed)
  • majority — read only data that majority of nodes have (safe, may be slightly stale)
  • linearizable — strongest: reads reflect all completed writes (slow)
  • snapshot — consistent point-in-time read (for transactions)

Phase 9 MongoDB with Go Driver — Your Codebase Language

This is where everything connects to your actual microservices. The Go MongoDB driver (go.mongodb.org/mongo-driver) is used by ALL your services. Learn how it maps to what you've learned in Phases 1–8.

Setup & Connect

  • go get go.mongodb.org/mongo-driver/mongo
  • mongo.Connect(ctx, options.Client().ApplyURI(uri))
  • Always use context.WithTimeout for connection + queries
  • client.Ping(ctx, nil) — verify connection is alive
  • client.Database("mydb").Collection("users") — get collection handle
  • Use defer client.Disconnect(ctx) on shutdown

BSON in Go

  • bson.M{} — unordered map (most common for filters/updates)
  • bson.D{} — ordered document (use when order matters, e.g. aggregation)
  • bson.A{} — array: bson.A{bson.M{...}, bson.M{...}}
  • primitive.ObjectID — Go type for MongoDB _id
  • primitive.ObjectIDFromHex("abc...") — parse string to ObjectID
  • Struct tags: bson:"fieldName,omitempty"

CRUD in Go Driver

  • col.InsertOne(ctx, doc) → returns *InsertOneResult
  • col.InsertMany(ctx, []interface{}{...})
  • col.FindOne(ctx, filter).Decode(&result)
  • col.Find(ctx, filter) → cursor → cursor.All(ctx, &results)
  • col.UpdateOne(ctx, filter, bson.M{"$set": update})
  • col.DeleteOne(ctx, filter)
  • col.CountDocuments(ctx, filter)

Advanced Go Driver Patterns

  • col.FindOneAndUpdate(ctx, filter, update, opts) — returns the doc
  • options.FindOneAndUpdate().SetUpsert(true).SetReturnDocument(options.After)
  • col.BulkWrite(ctx, models) — batch operations
  • mongo.NewUpdateOneModel() — for BulkWrite
  • col.Aggregate(ctx, pipeline) → cursor
  • options.Find().SetSort(...).SetLimit(...).SetSkip(...)
All of these are used in your microservices — jfrog, nwayfw, sonarqube

OpenTelemetry Tracing (otelmongo)

  • All your services use otelmongo for distributed tracing
  • Wraps MongoDB driver to automatically create trace spans for each DB operation
  • Setup: otelmongo.NewMonitor() → pass to options.Client().SetMonitor(m)
  • Every query then shows up in your tracing backend (Jaeger/Tempo)
  • Zero code change needed in your query code — it's middleware

Error Handling Patterns

  • mongo.ErrNoDocuments — FindOne found nothing (not a real error)
  • mongo.IsDuplicateKeyError(err) — unique index violation
  • mongo.IsTimeout(err) — context deadline exceeded
  • Always check if err == mongo.ErrNoDocuments before treating it as a failure
  • Use context.WithTimeout(ctx, 5*time.Second) for all queries

Phase 10 Production & Atlas — Running MongoDB in the Real World

Everything up to Phase 9 is development knowledge. This phase is about running MongoDB reliably, monitoring it, and using MongoDB Atlas (which your microservices connect to).

Replica Set — High Availability

  • A replica set is a group of mongod processes that maintain the same dataset
  • Typically: 1 Primary + 2 Secondaries
  • If primary goes down → secondaries elect a new primary automatically
  • Reads can be distributed to secondaries (SecondaryPreference) — used in your code
  • All writes always go to primary, then replicated to secondaries
  • Oplog — the replication log (like WAL in Postgres)

MongoDB Atlas Concepts

  • Atlas = fully managed MongoDB in the cloud (AWS/GCP/Azure)
  • Free tier: M0 cluster — good enough for learning and small projects
  • Connection string format: mongodb+srv://user:pass@cluster.mongodb.net/dbname
  • Atlas Search — full-text search built on Lucene
  • Atlas Data API — HTTP REST API for MongoDB without a driver
  • Atlas Charts — visual dashboards on your MongoDB data
  • Atlas Triggers — run functions on DB change events

Connection Pooling

  • The Go driver maintains a connection pool internally
  • Create the client once at startup, share it across your application
  • Do NOT create a new mongo.Client per request — it's expensive
  • Configure pool: options.Client().SetMaxPoolSize(50).SetMinPoolSize(5)
  • Atlas M0 limit: 500 connections max. M10+: much higher.

Monitoring & Observability

  • Atlas Performance Advisor — suggests indexes for slow queries
  • Atlas Profiler — logs all queries above a threshold
  • MongoDB logs — mongod.log, configurable verbosity
  • db.currentOp() — see currently running operations
  • db.serverStatus() — memory, connections, opcounters
  • otelmongo — your services export traces for every query (already in your code)

Phase 11 Interview Prep — Questions Tied to Your Codebase

These are the actual questions interviewers ask. Every answer below is backed by real code in your workspace — you're not just memorizing, you're explaining production decisions you understand.

Category 1: Core Concepts

Q: What is MongoDB and when would you use it over SQL?
A: MongoDB is a document database storing JSON-like documents. Use it when data shape varies (like CI/CD pipeline data where each service stores different fields), when you need horizontal scaling, or when your data is naturally hierarchical/nested.
Q: What is BSON?
A: Binary JSON — MongoDB's internal storage format. It extends JSON with additional types like ObjectId, Date, Int32, Int64, Decimal128. In Go, we work with the bson and primitive packages.
Q: What is a Collection Scan vs Index Scan?
A: Collection Scan reads every document to find matches (O(n)). Index Scan uses a sorted B-tree structure to jump directly to matching documents (O(log n)). Use .explain("executionStats") to verify which one is happening.
Q: Is MongoDB ACID compliant?
A: Yes. Single-document operations are always atomic. Multi-document ACID transactions are supported since v4.0 on replica sets. In practice, good schema design (embedding related data) avoids the need for most multi-document transactions.

Category 2: CRUD & Operators

Q: Difference between $set and replaceOne?
A: $set modifies only the specified fields, leaving all other fields untouched. replaceOne replaces the entire document with a new one. In production, almost always use $set — replacing entire documents risks data loss.
Q: What is upsert and when do you use it?
A: Upsert = update + insert. If the filter matches an existing document, update it. If not, insert a new document. Used in your codebase: nwayfw/streaming.go uses SetUpsert(true) to ensure inventory records exist. Eliminates the need for a find-then-insert check.
Q: Explain BulkWrite and why you'd use it.
A: BulkWrite sends multiple write operations (insert, update, delete) in a single network round-trip. Instead of 100 individual updateOne calls, one BulkWrite with 100 models. Your jfrog/artifacts.go uses this for bulk artifact updates — drastically reduces network overhead and latency.
Q: What does $push vs $addToSet do?
A: $push always appends an element to an array, even if it already exists. $addToSet only adds the element if it's not already in the array (ensures uniqueness). Use $addToSet when the array should behave like a set.

Category 3: Aggregation & Indexes

Q: Explain the aggregation pipeline.
A: A series of stages where each stage transforms the output of the previous one. Common stages: $match (filter), $group (summarize), $project (shape), $sort/$limit/$skip (paginate), $unwind (flatten arrays), $lookup (join). Always put $match first to filter early.
Q: What is the ESR rule for compound indexes?
A: Equality fields first, Sort fields second, Range fields last. A compound index on { userId: 1, createdAt: -1 } supports queries that filter by userId AND sort by createdAt. Your sonarqube service defines compound indexes exactly this way.
Q: What is a TTL index?
A: A TTL (Time-To-Live) index automatically deletes documents after a specified number of seconds. Created with expireAfterSeconds option. Perfect for sessions, temporary tokens, logs, and rate-limiting windows — no cron job needed.
Q: What is read preference and why does your codebase use SecondaryPreference?
A: Read preference controls which replica set member handles a read. SecondaryPreference routes reads to secondaries first, reducing load on the primary. Your develop/issuemetrics.go uses it for heavy metric reads that don't need real-time freshness — so they don't compete with writes on the primary.

Category 4: Schema Design & Architecture

Q: When do you embed vs reference in MongoDB?
A: Embed when: data is always read together, the embedded data is bounded in size, and only one parent owns it. Reference when: data is shared between many parents, the child data grows unboundedly, or you need to query children independently.
Q: Why does MongoDB have a 16MB document limit?
A: To prevent unbounded document growth that would degrade performance. Documents in working memory must fit in RAM. The limit encourages correct schema design: if you're hitting 16MB, you're probably embedding too much data that should be referenced.

Phase 12 Sharding & Horizontal Scaling — The Scaling Interview Topic

Sharding is how MongoDB scales beyond a single machine. This is one of the most-asked system design topics in backend interviews. Even if you never set up a shard in production, you must be able to explain how it works.

What is Sharding?

  • Sharding = splitting data across multiple machines (horizontal scaling)
  • Each machine holds a shard — a subset of the total data
  • Compare: Vertical scaling = bigger machine. Horizontal scaling = more machines.
  • A sharded cluster has: Shard servers (data) + Config servers (metadata) + mongos (query router)
  • Your app connects to mongos, which routes queries to the right shard automatically
  • Each shard is itself a replica set (so you get HA + sharding together)

Shard Key — The Most Critical Decision

  • The shard key is the field MongoDB uses to decide which shard a document goes to
  • Chosen once, cannot be changed later without resharding
  • A bad shard key = hot spots (one shard gets all traffic)
  • A good shard key has: high cardinality (many unique values), even distribution, and aligns with your query patterns
  • Example good shard key: { userId: 1 } if you query by userId
  • Example bad shard key: { status: 1 } — only 3 values, creates hot spots

Sharding Strategies

  • Range Sharding — documents with similar shard key values go to the same shard. Good for range queries. Risk: hotspots if data is monotonically increasing (like timestamps).
  • Hash Sharding — MongoDB hashes the shard key value. Even distribution. Cannot do range queries efficiently.
  • Zone Sharding — Pin certain data ranges to specific shards. Used for data locality (e.g. EU data stays on EU servers for compliance).
  • For timestamps as shard key → use hash sharding to avoid the write hotspot on the latest chunk

Chunk Splitting & Balancing

  • Data is divided into chunks (contiguous ranges of the shard key)
  • When a chunk grows too large, MongoDB splits it automatically
  • The balancer moves chunks between shards to keep data evenly distributed
  • Balancing runs in the background and can impact performance — configure balancing windows for production
  • sh.status() — view sharding status in mongosh

Targeted vs Scatter-Gather Queries

  • Targeted query — filter includes the shard key. mongos routes to exactly ONE shard. Fast.
  • Scatter-gather query — filter does NOT include shard key. mongos broadcasts to ALL shards and merges results. Slow.
  • This is why your shard key must match your most common query pattern
  • Design rule: the query that runs 1000x/sec must be targeted, not scatter-gather

Interview Q&A: Sharding

  • Q: When would you shard? → When a single replica set can't handle write volume or data size. Typically 100GB+ or high write throughput.
  • Q: What makes a bad shard key? → Low cardinality (few unique values), monotonically increasing values without hashing, or values that don't match query patterns.
  • Q: Can you do transactions on a sharded cluster? → Yes, since MongoDB 4.2, multi-document transactions work across shards.
  • Q: What is mongos? → A query router process. It receives queries from your app and routes them to the correct shard(s) using the config server metadata.

Phase 13 Change Streams — Real-Time Event-Driven Architecture

Change Streams let your application react to database changes in real time, without polling. This is directly relevant to your microservices architecture — services that need to know when another service's data changes.

What are Change Streams?

  • Change Streams give you a real-time stream of all insert/update/delete events on a collection, database, or entire cluster
  • Built on top of the Oplog (MongoDB's replication log)
  • Requires a replica set (or sharded cluster) — does not work on standalone
  • Your app opens a cursor that blocks and waits for the next change event
  • Use cases: cache invalidation, audit logs, event-driven microservices, real-time dashboards, sync to Elasticsearch

What an Event Looks Like

  • operationType — "insert", "update", "delete", "replace"
  • fullDocument — the complete document after the change (for inserts/replaces)
  • updateDescription — only the changed fields (for updates)
  • documentKey — the _id of the affected document
  • ns — namespace: { db: "mydb", coll: "users" }
  • resumeToken — a token to resume the stream from if your app restarts

Resume Token — Fault Tolerance

  • If your consumer crashes, you lose your position in the stream
  • Every event has a _id field = the resume token
  • Save the resume token to disk/DB after processing each event
  • On restart: open the stream with startAfter: <savedToken>
  • This gives you at-least-once delivery — make your event handlers idempotent
  • In Go: collection.Watch(ctx, pipeline, options.ChangeStream().SetResumeAfter(token))

Filtering Events

  • You can pass an aggregation pipeline to Watch() to filter which events you receive
  • Only receive insert events: { $match: { operationType: "insert" } }
  • Only receive changes to a specific field: { $match: { "updateDescription.updatedFields.status": { $exists: true } } }
  • Filtering at the DB level is far more efficient than filtering in your application code

Change Streams in Go

  • cursor, err := col.Watch(ctx, mongo.Pipeline{matchStage})
  • defer cursor.Close(ctx)
  • for cursor.Next(ctx) { var event bson.M; cursor.Decode(&event) }
  • Run in a goroutine — it blocks waiting for events
  • Handle cursor.Err() and reconnect with resume token on network errors
  • Your nwayfw/streaming.go service is the closest thing to this pattern in your codebase

Oplog — What Powers Change Streams

  • The Oplog (Operations Log) is a special capped collection in every replica set member
  • Every write operation is recorded in the oplog before being applied
  • Secondaries replicate from the primary by reading the oplog
  • Change Streams tap into the oplog as their data source
  • Oplog has a fixed size (configurable) — older entries are overwritten. Size it correctly for your write volume.
  • rs.printReplicationInfo() — check oplog window (how far back in time it goes)

Phase 14 Backend Interview Deep Dive — What Separates SDE2 from SDE3

These are the topics that separate a candidate who "knows MongoDB" from one who understands it at a production level. Senior interviews test these specifically.

WiredTiger Storage Engine

  • MongoDB's default storage engine since v3.2 (replaced MMAPv1)
  • Document-level locking — two concurrent writes to different documents in the same collection do NOT block each other (MMAPv1 had collection-level locks)
  • MVCC (Multi-Version Concurrency Control) — readers don't block writers, writers don't block readers
  • Compression — data is compressed on disk by default (snappy compression). Reduces disk usage by ~60-80%.
  • Cache — WiredTiger uses its own internal cache (default: 50% of RAM). Working set should fit in this cache for best performance.
  • Interview Q: "How does MongoDB handle concurrent writes?" → Document-level locking via WiredTiger.

Security — Authentication & Authorization

  • Authentication — verifying WHO you are. MongoDB supports: SCRAM (default), X.509 certificates, LDAP, Kerberos
  • Authorization (RBAC) — verifying WHAT you can do. Roles: read, readWrite, dbAdmin, clusterAdmin, custom roles
  • Network security — always use TLS/SSL for connections. Enable with tls=true in connection string.
  • Field-level encryption — encrypt specific sensitive fields (SSN, credit card) so even DBAs can't read them in plaintext
  • Principle of least privilege — create a specific DB user per service with only the permissions it needs
  • Your connection string should be: mongodb+srv://user:pass@cluster/?tls=true&authSource=admin

Common Anti-Patterns (What NOT to Do)

  • Unbounded arrays — never use $push into an array that can grow forever. Hit 16MB doc limit. Use a separate collection instead.
  • Too many indexes — each index slows down writes. Index only fields you actively query. Delete unused indexes.
  • Not using projections — find({}) fetches ALL fields. Always project only what you need, especially on large documents.
  • Querying without index on large collections — always confirm IXSCAN with explain() before deploying a new query.
  • Using $where or JavaScript — executes JS per document, extremely slow. Use native operators instead.
  • Storing files as base64 in documents — breaks the 16MB limit. Use GridFS or object storage (S3).
  • ObjectId stored as string — wastes space and breaks sorting. Always store as ObjectId type.
  • Not handling ErrNoDocuments — FindOne returns this when nothing matches. Always check for it in Go.

Schema Validation ($jsonSchema)

  • MongoDB supports enforcing a schema at the collection level — not everything is allowed in
  • Set validation rules when creating a collection: db.createCollection("users", { validator: { $jsonSchema: {...} } })
  • Validation levels: strict (validate all writes) or moderate (only validate new/updated docs)
  • Can require fields, set types, min/max values, regex patterns
  • Interview Q: "MongoDB is schema-less, so how do you enforce data integrity?" → $jsonSchema validation + application-level validation (struct tags in Go).

Capped Collections & GridFS

  • Capped Collection — fixed-size collection that automatically overwrites oldest documents when full. Like a circular buffer.
  • Use for: logs, audit trails, activity feeds, rate-limit counters — anything where you only care about recent data
  • Create: db.createCollection("logs", { capped: true, size: 10485760, max: 1000 })
  • Insertion order is preserved. Natural sort is very fast. Cannot delete individual documents.
  • GridFS — MongoDB's spec for storing files larger than 16MB. Splits files into 255KB chunks stored in fs.chunks collection, metadata in fs.files. Used by your file-server service pattern.

N+1 Problem in MongoDB

  • N+1 = fetching 1 list, then making N individual DB calls for related data. Kills performance.
  • SQL solution: JOIN. MongoDB solution: $lookup in aggregation OR embed the related data.
  • Example: fetching 100 orders, then doing 100 individual findOne calls for each user = 101 DB calls
  • Fix: use $lookup to join in one aggregation pipeline, OR fetch all userIds in one $in query
  • In Go: col.Find(ctx, bson.M{"_id": bson.M{"$in": userIds}}) — one call instead of N
  • Interview Q: "How do you avoid N+1 in MongoDB?" → $lookup, $in batching, or embedding frequently-read fields.

MongoDB vs Other Databases — System Design Answers

  • MongoDB vs Redis: Redis = in-memory, sub-ms latency, for caching/sessions. MongoDB = persistent, richer queries, for primary data storage.
  • MongoDB vs Cassandra: Cassandra = write-optimized, wide-column, no transactions, best for time-series at extreme scale. MongoDB = more flexible queries, full ACID transactions, better for varied query patterns.
  • MongoDB vs PostgreSQL: Postgres = ACID by default, powerful JOINs, strict schema, better for relational data. MongoDB = flexible schema, horizontal scaling, better for document/hierarchical data.
  • When to pick MongoDB: flexible/evolving schema, document-shaped data (no normalization needed), need to scale horizontally, JSON-native API payloads.

More Interview Questions — Senior Level

  • Q: What is the oplog and how does replication work? → Primary writes to oplog. Secondaries tail the oplog and replay operations. It's a capped collection in the local database.
  • Q: What is MVCC in WiredTiger? → Multiple versions of a document exist during concurrent operations. Readers see a consistent snapshot without blocking writers.
  • Q: What happens if your shard key causes a hot spot? → All writes go to one shard, others sit idle. Use hash sharding or a more selective shard key.
  • Q: How do change streams differ from polling? → Change streams are push-based (event-driven), no wasted queries. Polling wastes DB resources querying for "any new data?" repeatedly.
  • Q: How do you handle schema changes in production without downtime? → Schema versioning pattern: add a schemaVersion field, write new code to handle both versions, backfill old documents gradually.
